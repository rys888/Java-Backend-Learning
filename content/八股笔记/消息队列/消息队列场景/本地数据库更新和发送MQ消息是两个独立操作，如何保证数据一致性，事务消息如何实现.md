
## **一、为什么本地事务和 MQ 消息会出现数据不一致？**

**核心问题：MySQL 本地事务和 MQ 消息发送是两个独立操作，无法通过普通的** **`@Transactional`** **保证原子性。**

例如，用户下单后，需要更新 MySQL 订单状态，并发送 MQ 消息通知库存服务。

**情况一：先更新数据库，再发送 MQ**

```text
MySQL 更新订单状态成功
         ↓
      事务提交
         ↓
    发送 MQ 消息
         ↓
      发送失败 ❌
```

结果：**数据库更新成功，但消息没有发送成功。**

**情况二：先发送 MQ，再提交数据库事务**

```text
发送 MQ 消息成功
         ↓
消费者收到消息并处理
         ↓
MySQL 本地事务提交失败 ❌
```

结果：**消息已经被消费，但数据库事务回滚。**

因此，需要通过额外机制保证数据库和 MQ 之间的**最终一致性**。

## **二、如何解决数据一致性问题？**

常见有两种方案：

|**方案**|**实现原理**|**适用场景**|
|---|---|---|
|**本地消息表（Outbox）**|业务数据与消息记录在同一个数据库事务中提交，再异步发送 MQ|RabbitMQ 常用方案|
|**事务消息**|通过半消息、事务执行、事务状态回查协调消息发送|RocketMQ 原生支持|

### **1. 本地消息表（RabbitMQ 推荐）**

**核心：利用 MySQL 本地事务，保证业务数据和待发送消息同时提交。**

```text
        MySQL 本地事务
              │
       ┌──────┴──────┐
       ↓             ↓
   更新订单状态    插入消息表
       │             │
       └──────┬──────┘
              ↓
          事务提交
              ↓
      异步发送 MQ 消息
              ↓
      RabbitMQ 返回 Confirm
              ↓
        更新消息发送状态
```

具体流程：

1. 在同一个 MySQL 事务中更新业务数据，并向本地消息表插入一条待发送消息。
2. 事务提交后，由后台任务扫描待发送消息并投递到 RabbitMQ。
3. 收到 RabbitMQ 的发送确认后，更新消息状态为已发送。
4. 如果发送失败或确认结果不明确，定时任务重新发送。
5. 消费者通过唯一索引或业务状态机保证消费幂等。

**优点：** 实现相对简单，不依赖 MQ 原生事务消息功能。

**缺点：** 需要维护消息表、重试机制和定时补偿任务。

注意：消息发送成功后，如果更新消息表状态失败，可能重复发送，因此消费者必须保证幂等。

## **三、事务消息如何实现？**

以 **RocketMQ 事务消息**为例。

**核心思想：先发送半消息，再执行本地事务，最后根据事务执行结果决定消息是否可以被消费者看到。**

### **1. 事务消息执行流程**

```text
生产者                  RocketMQ                 MySQL
   │                       │                       │
   ├── ①发送半消息 ────────→│                       │
   │                       │                       │
   │←── ②半消息确认 ────────┤                       │
   │                       │                       │
   ├── ③执行本地事务 ──────────────────────────────→│
   │                       │                       │
   │←───────────────────────┼──── ④事务执行结果 ────┤
   │                       │                       │
   ├── ⑤提交/回滚消息 ─────→│                       │
   │                       │                       │
   │                       ├── ⑥提交后消息可被消费  │
   │                       │                       │
```

具体步骤：

**① 发送半消息（Half Message）**

生产者先向 RocketMQ 发送一条半消息。

此时消息已经存储在 Broker 中，但消费者暂时无法消费。

**② 执行本地事务**

生产者收到半消息发送成功的确认后，执行 MySQL 本地事务。

**③ 提交或回滚消息**

根据本地事务执行结果，通知 RocketMQ：

- **COMMIT**：本地事务成功，提交消息，允许消费者消费。
- **ROLLBACK**：本地事务失败，回滚消息，消费者无法消费。
- **UNKNOWN**：事务结果不确定，等待 Broker 回查。

**④ 事务状态回查**

如果生产者执行完本地事务后宕机，RocketMQ 没有收到事务结果：

```text
RocketMQ
    ↓
发现半消息长期未提交
    ↓
向生产者发起事务状态回查
    ↓
查询 MySQL 本地事务执行结果
    ↓
已提交 → COMMIT
未提交 → ROLLBACK
不确定 → UNKNOWN
```

通过事务状态回查，解决本地事务执行完成后，生产者无法通知 MQ 的问题。

注意：回查必须有可靠的事务状态判断依据，不能简单地将查询异常视为事务失败。

## **四、面试回答（背诵版）**

**如何保证本地数据库事务和 MQ 消息的一致性？事务消息如何实现？**

由于 MySQL 本地事务和 MQ 消息发送是两个独立操作，普通的 `@Transactional` 无法保证二者的原子性，因此通常采用最终一致性方案。

主要有两种解决方式：

**1. 本地消息表：**

将业务数据更新和消息记录插入放在同一个 MySQL 事务中提交，然后异步发送 MQ 消息。通过发送确认、失败重试和定时补偿，保证消息最终能够成功投递。

**2. 事务消息：**

以 RocketMQ 为例，首先发送半消息，半消息成功后执行本地事务，再根据事务执行结果提交或回滚消息。如果事务结果没有成功通知 Broker，Broker 会通过事务状态回查确认本地事务结果。

此外，由于消息可能重复投递，消费者还需要通过唯一索引或业务状态机保证幂等性。

**一句话总结：本地消息表通过数据库事务保证业务数据与消息记录一致；RocketMQ 事务消息通过半消息、本地事务和事务状态回查实现最终一致性。**

**面试注意：** RabbitMQ 没有 RocketMQ 这种原生半消息事务机制。对于使用 RabbitMQ 的项目，通常优先考虑本地消息表 + Confirm + 重试补偿，而不是直接套用 RocketMQ 的事务消息方案。
