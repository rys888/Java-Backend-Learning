## **1. 什么是幂等写？**

**幂等写是指同一个写入操作执行一次和执行多次，最终产生的业务结果相同。**

例如 RabbitMQ 重复投递预约消息：

```text
第一次消费 → MySQL 创建预约记录 → 成功
第二次消费 → MySQL 创建预约记录 → 重复写入 ❌
```

因此，需要保证重复消费不会产生重复数据。

## **2. 如何保证幂等写？**

常见有三种方案：

|**方案**|**实现原理**|**适用场景**|
|---|---|---|
|**MySQL 唯一索引**|通过唯一约束阻止重复插入|订单创建、预约记录创建|
|**业务状态机 + CAS**|通过条件更新限制状态流转|订单支付、预约状态更新|
|**Redis SETNX**|利用原子操作进行消息去重|消息消费状态管理|

### **① MySQL 唯一索引**

例如，同一用户不能重复预约同一批次设备：

```sql
ALTER TABLE reservation
ADD UNIQUE KEY uk_user_batch(user_id, batch_id);
```

第一次消费插入成功，第二次消费触发唯一索引冲突。

**即使消息重复投递，也不会产生重复预约记录。**

### **② 业务状态机 + CAS**

例如订单只能从待支付变为已支付：

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 1001
AND status = 'UNPAID';
```

第一次执行：影响 1 行，更新成功。

第二次执行：影响 0 行，因为订单已经是 `PAID`。

**通过判断原始状态，避免重复执行状态变更。**

注意：影响 0 行时，需要查询当前状态，区分已经处理成功和业务状态异常。

### **③ Redis SETNX**

使用消息唯一 ID 进行去重：

```redis
SET message:1001 processing NX EX 60
```

- 设置成功：获得处理资格。
- 设置失败：说明可能有其他消费者正在处理，或者消息已经处理过。

但不能仅凭 SETNX 失败就直接 ACK，需要区分处理中和已完成状态，并处理消费者宕机等异常。

## Q：

**如何保证消息队列消费的幂等写？**

幂等写是指同一条消息重复消费，不会产生重复的业务结果。

常见方案有三种：

1. **MySQL 唯一索引**：通过业务唯一键防止重复插入。
2. **业务状态机 + CAS**：通过条件更新限制状态流转，避免重复修改。
3. **Redis SETNX**：利用原子操作进行消息去重，但需要配合消费状态管理和异常恢复机制。

实际项目中，通常优先使用 **MySQL 唯一索引和业务状态机保证核心业务幂等**，Redis 可以作为辅助去重手段。

**一句话总结：新增数据靠唯一索引，更新状态靠 CAS，消息去重可以借助 Redis SETNX。**
