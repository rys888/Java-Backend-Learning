
## **1. 为什么会出现消息重复消费？**

在 RabbitMQ 中，**消息重复消费主要是因为消费者已经处理完消息，但 RabbitMQ 没有收到 ACK 确认。**

例如：

```text
RabbitMQ
    ↓
消费者收到消息
    ↓
MySQL 插入订单成功
    ↓
消费者准备发送 ACK
    ↓
网络异常，ACK 丢失
    ↓
RabbitMQ 认为消息没有被成功消费
    ↓
重新投递消息
    ↓
消费者再次执行插入操作 ❌
```

因此，RabbitMQ 通常采用 **At-Least-Once（至少一次）** 的消息投递语义，消息可能被重复消费。

---

## **2. 如何解决消息重复消费？**

**核心方案：通过幂等性设计，保证同一条消息即使被多次消费，也不会产生重复的业务结果。**

常见有三种方式：

|**解决方案**|**实现原理**|**适用场景**|
|---|---|---|
|**MySQL 唯一索引**|利用数据库唯一约束防止重复插入|订单创建、预约记录创建|
|**Redis SETNX**|利用原子操作判断消息是否已经处理|消息去重、消费状态记录|
|**业务状态机**|根据业务状态判断是否允许执行操作|订单支付、预约状态流转|

### **① MySQL 唯一索引（推荐）**

例如，在你的研约通项目中，一个用户不能重复预约同一批次设备。

可以建立联合唯一索引：

```sql
UNIQUE KEY uk_user_batch (user_id, batch_id)
```

即使 RabbitMQ 重复投递消息：

```text
第一次消费：
插入预约记录 → 成功

第二次消费：
插入相同预约记录 → 唯一索引冲突
                     ↓
                判断记录已存在
                     ↓
                  ACK 确认
```

**优点：** 数据库层面保证不会重复插入，可靠性较高。

注意：唯一索引冲突需要区分正常的重复消费和其他业务异常，不能将所有数据库异常都当作消费成功。

### **② Redis SETNX**

利用 Redis 的 `SET NX` 实现消息去重。

```text
消费者收到消息
      ↓
SET message:id processing NX EX 60
      ↓
是否设置成功？
   ├── 是 → 执行业务逻辑
   └── 否 → 检查消息处理状态
```

但需要注意：

**不能简单地 SETNX 成功后就认为消息已经消费完成。**

例如：

```text
SETNX 成功
    ↓
消费者宕机
    ↓
业务逻辑没有执行
    ↓
消息重新投递
    ↓
SETNX 失败
    ↓
消息被跳过 ❌
```

因此，需要设计处理中、已完成等状态，并结合过期时间、失败恢复机制，避免消息丢失。

### **③ 业务状态机**

例如订单状态：

```text
待支付 → 已支付 → 已完成
```

消费者处理支付消息时，使用条件更新：

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = 1001
  AND status = 'UNPAID';
```

如果消息重复消费：

- 第一次执行：更新成功，影响 1 行。
- 第二次执行：状态已经是 `PAID`，影响 0 行。

这样就避免了重复更新。

不过，如果更新成功后还需要执行其他操作，也必须保证这些操作具有幂等性。

## **3. 面试回答（背诵版）**

**如何解决 RabbitMQ 消息重复消费？**

RabbitMQ 可能因为消费者 ACK 丢失、消费超时或消费者异常等原因重新投递消息，因此需要通过**消费幂等性**解决重复消费问题。

常见方案有三种：

1. **MySQL 唯一索引**：通过业务唯一键防止重复插入，例如同一用户不能重复预约同一批次设备。
2. **Redis SETNX**：通过原子操作进行消息去重，但需要结合消费状态和异常恢复机制。
3. **业务状态机**：通过 CAS 条件更新限制状态流转，防止重复执行相同业务操作。

在实际项目中，通常优先使用**数据库唯一索引和业务状态机**保证核心业务幂等，Redis 可以作为辅助去重手段。

**一句话总结：消息重复消费无法完全避免，关键是保证重复消费不会产生重复的业务效果。**
