## **1. 为什么会出现消息丢失？**

RabbitMQ 消息丢失主要发生在三个阶段：

1. **生产者发送消息时丢失**：网络异常，消息没有成功到达 RabbitMQ。
2. **RabbitMQ 存储消息时丢失**：消息已经到达 Broker，但服务器宕机，未持久化的消息丢失。
3. **消费者处理消息时丢失**：消费者尚未完成业务处理，就提前发送 ACK，随后发生异常。

因此，**解决消息丢失，需要分别保证生产者、MQ、消费者三个环节的可靠性。**

## **2. 如何解决消息丢失？**

|**阶段**|**解决方案**|**作用**|
|---|---|---|
|**生产者**|Publisher Confirm + Return|确认消息成功到达 Broker，并检查是否成功路由|
|**RabbitMQ**|队列持久化 + 消息持久化|降低 Broker 重启导致消息丢失的风险|
|**消费者**|手动 ACK + 重试机制 + 死信队列|确保业务处理成功后才确认消息|

### **① 生产者：Publisher Confirm + Return**

**Publisher Confirm（发布确认）**

生产者发送消息后，RabbitMQ 返回确认结果：

```text
生产者 → RabbitMQ
            ↓
       是否成功接收？
        ├── 是 → ACK
        └── 否 → NACK
```

如果生产者没有收到 ACK，或者收到 NACK，就需要根据消息状态进行重试或补偿。

**Publisher Return（消息退回）**

如果消息成功到达 Exchange，但是无法路由到任何队列，RabbitMQ 可以通过 Return 机制将消息退回生产者。

```text
生产者 → Exchange
             ↓
        是否成功路由？
        ├── 是 → Queue
        └── 否 → Return
```

注意：需要开启 `mandatory` 才能通过 Return 机制感知不可路由的消息。

**Confirm 保证消息到达 Broker，Return 用于感知消息无法路由到队列。**

但 Confirm 并不代表消息已经被消费者成功处理。

### **② RabbitMQ：消息持久化**

RabbitMQ 默认的非持久化消息和队列可能在 Broker 重启后丢失。

因此，需要：

- **Exchange 持久化**：设置 `durable=true`。
- **Queue 持久化**：设置 `durable=true`。
- **Message 持久化**：设置消息的 `deliveryMode=2`。

```text
生产者
   ↓
RabbitMQ
   ↓
持久化队列 + 持久化消息
   ↓
Broker 重启后恢复消息
```

注意：持久化不能保证绝对不丢失。对于更高可靠性要求，可以使用 **Quorum Queue（仲裁队列）**，通过多副本复制提高容错能力。

### **③ 消费者：手动 ACK**

如果使用自动 ACK，RabbitMQ 可能在消费者尚未完成业务处理时就认为消息已被成功消费。

例如：

```text
RabbitMQ → 消费者
               ↓
          自动 ACK
               ↓
          MySQL 写入失败
               ↓
          消息已经删除 ❌
```

**解决方案：使用手动 ACK，在业务处理成功后再确认消息。**

```text
RabbitMQ → 消费者
               ↓
          执行业务逻辑
               ↓
          是否处理成功？
          ├── 是 → ACK
          └── 否 → NACK / 重试
```

对于多次重试仍然失败的消息，可以将其转入**死信队列（DLQ）**，等待后续排查或补偿。

注意：死信队列本身并不能保证消息一定不丢失，还需要正确配置死信转发和持久化策略。

## **3. 面试回答（背诵版）**

**RabbitMQ 如何解决消息丢失问题？**

消息丢失主要发生在生产者、RabbitMQ 和消费者三个阶段，因此需要分别保证消息可靠性。

1. **生产者阶段**：通过 Publisher Confirm 确认消息是否成功到达 Broker，通过 Publisher Return 检查消息是否成功路由到队列，对于发送失败或状态不确定的消息进行重试或补偿。
2. **RabbitMQ 阶段**：开启 Exchange、Queue 和 Message 持久化，降低 Broker 重启导致消息丢失的风险，对于高可靠性场景可以使用 Quorum Queue。
3. **消费者阶段**：采用手动 ACK，确保业务处理成功后才确认消息；对于处理失败的消息，通过重试机制和死信队列进行异常处理。

此外，由于消息重试可能造成重复消费，因此还需要通过**唯一索引、业务状态机等方式保证消费幂等性**。

**一句话总结：生产者确认发送成功，MQ 可靠存储消息，消费者处理成功后再 ACK，同时通过重试补偿和幂等机制保证业务可靠性。**
