
## **什么是消息队列（MQ）？**

**消息队列（Message Queue，MQ）是一种用于应用程序之间异步通信的中间件。**

生产者将消息发送到消息队列，消费者从消息队列中获取消息并处理，从而实现系统之间的解耦。

### **1. 工作原理**

```text
传统同步调用：

用户下单 → 创建订单 → 扣减库存 → 发送通知 → 返回结果
             （需要等待所有操作完成）


引入消息队列：

用户下单 → 创建订单 → 发送MQ消息 → 返回结果
                          │
                     RabbitMQ
                          │
                   ┌──────┴──────┐
                   ↓             ↓
                扣减库存       发送通知
```

消息队列主要包含三个角色：

- **生产者（Producer）**：负责发送消息。
- **消息队列（MQ）**：负责接收、存储和转发消息。
- **消费者（Consumer）**：负责接收并处理消息。

### **2. 为什么使用消息队列？**

主要解决三个问题：

|**作用**|**解释**|
|---|---|
|**异步处理**|将非必要的同步操作改为异步执行，缩短请求响应时间|
|**应用解耦**|生产者不需要直接调用消费者，降低模块之间的依赖|
|**流量削峰**|高并发请求先进入消息队列，消费者按照自身处理能力逐步消费|

### **3. 结合你的研约通项目理解**

以实验设备限量预约为例：

**不使用 MQ：**

用户预约 → Redis 扣减名额 → MySQL 创建预约记录 → 返回结果。

**使用 RabbitMQ：**

用户预约 → Redis Lua 原子校验资格并扣减名额 → 发送 RabbitMQ 消息 → 返回受理结果。

消费者异步处理：

RabbitMQ → 消费者 → MySQL 创建预约记录 → 更新预约状态。

这样做的好处：

- **异步处理**：预约请求不需要等待数据库写入完成。
- **流量削峰**：高并发预约请求不会直接全部打到 MySQL。
- **应用解耦**：资格抢占与预约记录持久化分离。

需要注意：MQ 并不能天然保证消息不丢失、不重复，也不能自动保证 Redis 与 MySQL 的数据一致性，需要额外设计可靠性与补偿机制。

### **4. 面试回答（背诵版）**

消息队列是一种用于应用程序之间异步通信的中间件，主要由生产者、消息队列和消费者组成。

**引入消息队列主要是为了解决异步处理、应用解耦和流量削峰三个问题。**

例如在高并发预约场景中，可以先通过 Redis 完成资格校验和名额扣减，再将预约消息发送到 RabbitMQ，由消费者异步完成数据库持久化，从而降低请求响应时间，缓解数据库瞬时写入压力。

**但引入 MQ 也会增加系统复杂度，需要考虑消息可靠性、重复消费、消费积压以及数据最终一致性等问题。**
