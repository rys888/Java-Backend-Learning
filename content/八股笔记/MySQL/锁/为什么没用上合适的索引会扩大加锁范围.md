
因为 **InnoDB 的行锁是加在索引记录上的，而 MySQL 需要先找到数据，才能对相关记录加锁。**

**如果有合适的索引，MySQL 可以精准定位记录；如果没有合适的索引，就可能需要扫描大量记录，导致加锁范围扩大。**

### **① 有合适的索引**

假设有一张用户表：

```sql
CREATE TABLE user (
    id INT PRIMARY KEY,
    name VARCHAR(50),
    INDEX idx_name(name)
);
```

执行：

```sql
UPDATE user SET name = 'Tom' WHERE id = 3;
```

因为 `id` 是主键，MySQL 可以通过聚簇索引直接找到 `id = 3`。

```text
主键索引：

1    2    3    4    5
          🔒
```

在默认 RR 隔离级别下，对于已存在记录的主键等值查询，通常只需要对 `id = 3` 加记录锁。

### **② 没有合适的索引**

假设执行：

```sql
UPDATE user SET name = 'Tom' WHERE age = 20;
```

这里假设表中有 `age` 字段，但没有建立 `age` 索引。

MySQL 无法通过索引直接找到 `age = 20` 的记录，因此可能需要扫描整个聚簇索引。

```text
主键索引：

1    2    3    4    5
🔒   🔒   🔒   🔒   🔒
```

在默认 RR 隔离级别下，InnoDB 可能对扫描过程中涉及的大量索引记录及间隙加锁。

**即使最终只有一条记录满足** ** `age = 20` ****，也可能锁住大量其他记录，导致其他事务更新或插入数据时被阻塞。**

需要注意，具体加锁范围还与隔离级别和执行计划有关。例如 RC 隔离级别下，InnoDB 对不匹配记录的锁处理有所不同。

### **③ 为什么这会增加死锁风险？**

假设两个事务分别执行：

```sql
-- 事务 A
UPDATE user SET name = 'Tom' WHERE age = 20;

-- 事务 B
UPDATE user SET name = 'Jack' WHERE age = 30;
```

虽然两个事务想修改的记录不同，但如果没有合适的索引，都可能扫描并锁定大量记录。

这样就增加了锁竞争和事务等待的概率。在涉及多个锁、加锁顺序不一致等情况下，也会增加发生死锁的风险。

不过，**锁范围扩大不等于一定发生死锁**，也可能只是单纯的锁等待。

---

### **面试怎么回答？**

因为 InnoDB 的行锁是基于索引记录实现的。

如果 SQL 使用了合适的索引，就可以快速定位目标记录，通常只需要锁定少量索引记录。

如果没有合适的索引，MySQL 可能需要进行全表扫描，而 InnoDB 在执行加锁操作时，可能锁住扫描过程中涉及的大量索引记录及间隙，导致锁定范围扩大。

因此，合理建立索引不仅能提高查询效率，还能减少锁竞争，降低死锁发生的概率。

**一句话记忆：索引决定扫描范围，扫描范围影响加锁范围，加锁范围越大，锁竞争通常越严重。**
