
MySQL 事务的四大特性是 **ACID：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）**。

在 Java 后端面试中，面试官不仅会问事务有哪些特性，还经常追问：**InnoDB 是如何保证 ACID 的？**

## **一、事务的四大特性 ⭐⭐⭐⭐⭐**

假设有一个银行转账场景：

```sql
START TRANSACTION;

-- A 向 B 转账 100 元
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

这两条 SQL 需要作为一个整体执行。

### **1. 原子性（Atomicity）**

**定义：事务中的所有操作要么全部成功，要么全部失败，不允许只执行一部分。**

例如 A 向 B 转账 100 元：

- A 扣除 100 元成功。
- B 增加 100 元失败。

此时必须撤销 A 扣除 100 元的操作，恢复到事务开始之前的状态。

**实现原理：Undo Log（回滚日志）。**

InnoDB 在修改数据时，会记录用于回滚的相关信息。

如果事务执行失败，就可以利用 Undo Log 撤销已经执行的修改。

```text
事务开始
   ↓
修改数据
   ↓
记录 Undo Log
   ↓
事务失败
   ↓
利用 Undo Log 回滚
   ↓
恢复原来的数据
```

因此，**Undo Log 是 InnoDB 实现事务原子性的重要机制。**

### **2. 一致性（Consistency）**

**定义：事务执行前后，数据库必须从一个满足约束的状态转换到另一个满足约束的状态。**

例如：

```text
转账前：
A = 1000 元
B = 500 元
总金额 = 1500 元

转账后：
A = 900 元
B = 600 元
总金额 = 1500 元
```

事务执行前后，总金额保持不变。

但是需要注意：

**一致性不仅依赖数据库自身的机制，还依赖业务逻辑和约束条件。**

例如：

- 主键约束、唯一约束、外键约束。
- 原子性、隔离性、持久性等事务机制。
- 应用程序正确的业务逻辑。

假设转账代码错误地给 B 增加了 200 元，即使事务成功提交，数据库也无法自动知道这违反了业务规则。

因此，**一致性是事务最终要达到的目标，而其他三个特性以及数据库约束、业务逻辑共同帮助实现一致性。**

### **3. 隔离性（Isolation）⭐⭐⭐⭐⭐**

**定义：多个事务并发执行时，应该按照指定的隔离级别控制事务之间的相互影响。**

例如：

```text
事务 A：查询账户余额

事务 B：修改账户余额
```

如果没有合理的并发控制，就可能出现：

- 脏读
- 不可重复读
- 幻读

**实现原理：MVCC + 锁机制。**

InnoDB 主要通过以下机制实现事务隔离：

**① MVCC（多版本并发控制）**

MVCC 主要用于普通 SELECT 的一致性读。

它通过：

```text
Undo Log + Read View + 行记录中的版本信息
```

让事务能够读取符合自身可见性规则的数据版本，从而减少读写之间的相互阻塞。

**② 锁机制**

InnoDB 通过行锁、间隙锁、临键锁等机制，控制并发事务对数据的访问和修改。

例如两个事务同时修改同一条记录：

```sql
UPDATE account SET balance = balance - 100 WHERE id = 1;
```

InnoDB 会通过锁机制协调并发修改，避免两个事务无控制地同时更新同一条记录。

需要注意，具体使用哪些锁，以及 MVCC 如何判断版本可见性，取决于事务隔离级别和 SQL 类型。

### **4. 持久性（Durability）**

**定义：事务一旦成功提交，对数据库的修改就应该被持久保存，即使数据库发生崩溃，也能够恢复已提交的数据。**

例如：

```sql
UPDATE account SET balance = 900 WHERE id = 1;

COMMIT;
```

事务提交成功后，即使 MySQL 突然崩溃，也应该能够恢复这次修改。

**实现原理：Redo Log（重做日志）。**

为什么需要 Redo Log？

因为 InnoDB 修改数据时，通常先修改 Buffer Pool 中的数据页，而不是立即将数据页写入磁盘。

```text
执行 UPDATE
     ↓
修改 Buffer Pool 中的数据页
     ↓
记录 Redo Log
     ↓
事务提交
     ↓
后续将脏页刷入磁盘
```

如果事务提交后、脏页刷盘前 MySQL 崩溃，就可以在重启时利用 Redo Log 恢复已提交的修改。

这里还涉及 **WAL（Write-Ahead Logging，预写日志）** 思想：

**先保证相关日志持久化，再允许对应的数据页写入磁盘。**

需要注意，事务提交时 Redo Log 的刷盘行为还受到 `innodb_flush_log_at_trx_commit` 等配置影响。通常讨论的强持久性保证以适当的持久化配置为前提。

## **二、ACID 的实现原理总结**

|**事务特性**|**核心含义**|**InnoDB 主要实现机制**|
|---|---|---|
|原子性（A）|要么全部成功，要么全部失败|**Undo Log**|
|一致性（C）|事务前后满足数据约束和业务规则|**ACID 其他特性 + 数据库约束 + 业务逻辑**|
|隔离性（I）|控制并发事务之间的相互影响|**MVCC + 锁机制**|
|持久性（D）|提交后的修改能够持久保存|**Redo Log + WAL**|

你可以重点记忆：

```text
                 MySQL 事务 ACID
                        │
          ┌─────────────┼─────────────┐
          │             │             │
        原子性        隔离性        持久性
          │             │             │
          ▼             ▼             ▼
       Undo Log      MVCC + 锁     Redo Log
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                     一致性
                （最终保证目标）
```

这是一种便于记忆的简化模型，并不意味着一致性只由另外三个特性自动保证。

## **三、Undo Log、Redo Log 有什么区别？⭐⭐⭐⭐⭐**

这是面试官非常喜欢追问的问题。

|**对比**|**Undo Log**|**Redo Log**|
|---|---|---|
|中文名称|回滚日志|重做日志|
|主要作用|回滚事务、支持 MVCC|崩溃恢复|
|保障的特性|原子性|持久性|
|记录内容|用于撤销修改的信息|用于重做数据页修改的信息|
|典型使用场景|事务回滚、读取历史版本|MySQL 崩溃后恢复数据|

例如：

```sql
UPDATE account SET balance = 900 WHERE id = 1;
```

假设原来的余额是 1000 元。

可以这样理解：

**Undo Log：**

记录能够帮助恢复原来余额 1000 元的信息。

**Redo Log：**

记录能够帮助重做这次数据页修改的信息，确保提交后的余额变更可以恢复。

需要注意，Redo Log 并不是简单记录一条 `UPDATE` SQL，而是记录 InnoDB 数据页修改相关的重做信息。

## **四、面试怎么回答？⭐⭐⭐⭐⭐**

如果面试官问：

**“MySQL 事务有哪些特性？InnoDB 是如何实现的？”**

建议这样回答：

MySQL 事务主要有 ACID 四大特性，分别是原子性、一致性、隔离性和持久性。

**原子性**是指事务中的操作要么全部成功，要么全部失败。InnoDB 主要通过 Undo Log 实现，当事务需要回滚时，可以利用 Undo Log 撤销已经执行的修改。

**一致性**是指事务执行前后，数据库都应该满足相应的数据约束和业务规则。它依赖原子性、隔离性、持久性，以及数据库约束和正确的业务逻辑共同保证。

**隔离性**是指多个事务并发执行时，需要控制它们之间的相互影响。InnoDB 主要通过 MVCC 和锁机制实现，其中 MVCC 用于支持一致性读，锁机制用于协调并发访问和修改。

**持久性**是指事务提交后，修改的数据应该能够持久保存。InnoDB 主要通过 Redo Log 和 WAL 机制实现，即使数据库发生崩溃，也可以利用 Redo Log 恢复已提交的数据。

总结来说，InnoDB 通过 Undo Log 保证原子性，通过 MVCC 和锁机制实现隔离性，通过 Redo Log 保证持久性，并结合数据库约束和业务逻辑维护一致性。

**一句话记忆：Undo Log 管回滚，Redo Log 管恢复，MVCC 和锁管并发，一致性是最终目标。**

另外，面试官通常会顺着隔离性继续追问 **MySQL 的四种事务隔离级别，以及脏读、不可重复读、幻读分别是什么**，这部分建议紧接着复习。
