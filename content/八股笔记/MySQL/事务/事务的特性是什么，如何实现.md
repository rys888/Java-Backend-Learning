
[[#Q：MySQL 事务有哪些特性？InnoDB 是如何实现的？]]

MySQL 事务的四大特性是 **ACID：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）**。

面试里除了问这四个词，还经常往下追一层：**InnoDB 到底是怎么保证 ACID 的？** 前者背下来就行，后者才是真正要讲清楚的地方。

## 一、事务的四大特性 ⭐⭐⭐⭐⭐

先看一个银行转账场景：

```sql
START TRANSACTION;

-- A 向 B 转账 100 元
UPDATE account SET balance = balance - 100 WHERE id = 1;
UPDATE account SET balance = balance + 100 WHERE id = 2;

COMMIT;
```

这两条 SQL 必须作为一个整体执行，不能只成功一半。四个特性其实就是从不同角度描述这个“整体”。

### 1. 原子性（Atomicity）

**定义：事务里的所有操作要么全部成功，要么全部失败，不允许只执行一部分。**

A 向 B 转 100 元，A 扣钱成功、B 加钱失败，这个时候就必须把 A 扣掉的 100 元撤回来，恢复到事务开始之前的状态。

**实现原理：Undo Log（回滚日志）。** InnoDB 在修改数据时，会顺手记录一份用于回滚的信息。事务失败需要回滚时，就照着 Undo Log 把已经执行的修改一条条撤掉。

```text
事务开始
   ↓
修改数据
   ↓
记录 Undo Log
   ↓
事务失败
   ↓
利用 Undo Log 回滚
   ↓
恢复原来的数据
```

所以 **Undo Log 是 InnoDB 实现事务原子性的核心机制**。

### 2. 一致性（Consistency）

**定义：事务执行前后，数据库都必须从一个满足约束的状态，转换到另一个满足约束的状态。**

还是转账。转账前 A 有 1000 元、B 有 500 元，总金额 1500；转账后 A 900 元、B 600 元，总金额还是 1500。前后总金额不变，这就是这个场景下的一致性。

但这里有个容易理解错的地方：**一致性不只靠数据库，还依赖业务逻辑和约束条件。** 主键约束、唯一约束、外键约束管住数据本身；原子性、隔离性、持久性管住执行过程；应用程序还得把业务逻辑写对。假设转账代码写错了，给 B 加了 200 元，事务照样能成功提交，数据库并不知道这违反了业务规则。

所以 **一致性是事务最终要达到的目标，另外三个特性加上数据库约束和业务逻辑，都是在帮它达成这个目标**。

### 3. 隔离性（Isolation）⭐⭐⭐⭐⭐

**定义：多个事务并发执行时，按照指定的隔离级别控制事务之间的相互影响。**

比如事务 A 在查账户余额，事务 B 在改账户余额。没有合理的并发控制，就可能出现脏读、不可重复读、幻读。

**实现原理：MVCC + 锁机制。**

**① MVCC（多版本并发控制）**，主要用于普通 SELECT 的一致性读。它靠 **Undo Log + Read View + 行记录里的版本信息**，让事务读到符合自身可见性规则的数据版本，减少读写之间的相互阻塞。**② 锁机制**，InnoDB 通过行锁、间隙锁、临键锁等，控制并发事务对数据的访问和修改。比如两个事务同时改同一条记录：

```sql
UPDATE account SET balance = balance - 100 WHERE id = 1;
```

InnoDB 会用锁协调并发修改，避免两个事务无控制地同时更新同一行。

需要注意，具体用哪些锁、MVCC 怎么判断版本可见性，取决于隔离级别和 SQL 类型，不是固定一套。

### 4. 持久性（Durability）

**定义：事务一旦成功提交，对数据库的修改就应该持久保存，即使数据库崩溃也能恢复已提交的数据。**

**实现原理：Redo Log（重做日志）。**

为什么需要 Redo Log？因为 InnoDB 改数据时，通常先改 Buffer Pool 里的数据页，不会立刻写磁盘。每次提交都直接刷数据页，随机 I/O 太慢；一直不刷，崩溃了数据又丢了。Redo Log 就是折中方案：

```text
执行 UPDATE
     ↓
修改 Buffer Pool 中的数据页
     ↓
记录 Redo Log
     ↓
事务提交
     ↓
后续将脏页刷入磁盘
```

事务提交后、脏页刷盘前 MySQL 崩溃，重启时就能用 Redo Log 把已提交的修改重新做一遍。

这里体现的就是 **WAL（Write-Ahead Logging，预写日志）** 的思想：**先把日志持久化，再允许对应的数据页慢慢写磁盘。**

需要补一句，事务提交时 Redo Log 刷不刷盘还受 `innodb_flush_log_at_trx_commit` 影响。平时讨论的强持久性，是以合理的持久化配置为前提的。

## 二、ACID 的实现原理总结

|**事务特性**|**核心含义**|**InnoDB 主要实现机制**|
|---|---|---|
|原子性（A）|要么全部成功，要么全部失败|**Undo Log**|
|一致性（C）|事务前后满足数据约束和业务规则|**ACID 其他特性 + 数据库约束 + 业务逻辑**|
|隔离性（I）|控制并发事务之间的相互影响|**MVCC + 锁机制**|
|持久性（D）|提交后的修改能够持久保存|**Redo Log + WAL**|

重点记这张图：

```text
                 MySQL 事务 ACID
                        │
          ┌─────────────┼─────────────┐
          │             │             │
        原子性        隔离性        持久性
          │             │             │
          ▼             ▼             ▼
       Undo Log      MVCC + 锁     Redo Log
          │             │             │
          └─────────────┼─────────────┘
                        │
                        ▼
                     一致性
                （最终保证目标）
```

这是便于记忆的简化模型，并不意味着一致性只由另外三个特性自动保证。

## 三、Undo Log、Redo Log 有什么区别？⭐⭐⭐⭐⭐

这是面试官非常喜欢追问的问题。

|**对比**|**Undo Log**|**Redo Log**|
|---|---|---|
|中文名称|回滚日志|重做日志|
|主要作用|回滚事务、支持 MVCC|崩溃恢复|
|保障的特性|原子性|持久性|
|记录内容|用于撤销修改的信息|用于重做数据页修改的信息|
|典型使用场景|事务回滚、读取历史版本|MySQL 崩溃后恢复数据|

拿一条 SQL 举例：

```sql
UPDATE account SET balance = 900 WHERE id = 1;
```

假设原来的余额是 1000 元。**Undo Log** 记的是能帮助恢复回 1000 元的信息；**Redo Log** 记的是能帮助重做这次数据页修改的信息，保证提交后的余额变更在崩溃后可以恢复。

需要注意，Redo Log 并不是简单记录一条 `UPDATE` SQL，而是记录 InnoDB 数据页修改相关的重做信息。

# Q：MySQL 事务有哪些特性？InnoDB 是如何实现的？

MySQL 事务主要有 ACID 四大特性，分别是原子性、一致性、隔离性和持久性。

**原子性**是指事务中的操作要么全部成功，要么全部失败。InnoDB 主要通过 Undo Log 实现，事务需要回滚时，利用 Undo Log 撤销已经执行的修改。

**一致性**是指事务执行前后，数据库都应该满足相应的数据约束和业务规则。它依赖原子性、隔离性、持久性，以及数据库约束和正确的业务逻辑共同保证。

**隔离性**是指多个事务并发执行时，需要控制它们之间的相互影响。InnoDB 主要通过 MVCC 和锁机制实现，MVCC 用于支持一致性读，锁机制用于协调并发访问和修改。

**持久性**是指事务提交后，修改的数据应该能够持久保存。InnoDB 主要通过 Redo Log 和 WAL 机制实现，即使数据库发生崩溃，也可以利用 Redo Log 恢复已提交的数据。

**InnoDB 用 Undo Log 保证原子性，用 MVCC 和锁实现隔离性，用 Redo Log 保证持久性，再结合数据库约束和业务逻辑维护一致性。Undo Log 管回滚，Redo Log 管恢复，MVCC 和锁管并发，一致性是最终目标。**
