
MySQL 解决并发问题，**主要依靠锁机制、MVCC（多版本并发控制）和事务隔离级别**。

下面以 InnoDB 存储引擎为例。

## **一、MySQL 并发时会出现哪些问题？**

假设数据库中有一条记录：

```sql
id = 1
balance = 1000
```

现在有两个事务同时操作这条数据：

```text
事务 A                       事务 B
  │                            │
  ├── 查询余额 1000             │
  │                            ├── 修改余额为 500
  │                            │
  ├── 再次查询余额               │
  │                            │
  ▼                            ▼
```

如果没有合理的并发控制，就可能出现以下问题：

|**并发问题**|**含义**|
|---|---|
|脏读|读取到其他事务尚未提交的数据|
|不可重复读|同一事务两次读取同一行，结果不同|
|幻读|同一事务两次范围查询，符合条件的记录集合发生变化|
|丢失更新|两个事务基于旧数据进行修改，导致其中一次更新结果被覆盖|

MySQL 需要在**数据一致性和并发性能之间取得平衡**。

---

## 二、MySQL 如何解决并发问题？

### **1. 锁机制：解决并发修改冲突**

**锁机制的核心思想是：当多个事务同时操作同一份数据时，通过加锁控制访问顺序。**

例如：

```sql
-- 事务 A
BEGIN;

UPDATE account
SET balance = balance - 100
WHERE id = 1;
```

此时事务 A 会对相关记录加排他锁（X 锁）。

如果事务 B 同时执行：

```sql
-- 事务 B
BEGIN;

UPDATE account
SET balance = balance - 200
WHERE id = 1;
```

事务 B 通常需要等待事务 A 释放锁。

```text
             事务 A                  事务 B
                │                       │
                ▼                       ▼
          UPDATE id = 1           UPDATE id = 1
                │                       │
                ▼                       ▼
            获取 X 锁              请求 X 锁
                │                       │
                │                       ▼
                │                    阻塞等待
                │                       │
                ▼                       │
             COMMIT                     │
                │                       │
                ▼                       ▼
            释放 X 锁               获取 X 锁
                                        │
                                        ▼
                                    执行 UPDATE
```

这样就避免了两个事务无控制地同时修改同一条记录。

InnoDB 常见的锁包括：

|**锁类型**|**作用**|
|---|---|
|共享锁（S 锁）|允许多个事务同时持有共享锁，阻止冲突的排他锁|
|排他锁（X 锁）|控制对记录的排他访问|
|记录锁（Record Lock）|锁定索引记录|
|间隙锁（Gap Lock）|锁定索引记录之间的间隙|
|临键锁（Next-Key Lock）|记录锁与间隙锁的组合|

其中，**间隙锁和临键锁还可以在特定隔离级别及查询条件下，防止其他事务向锁定范围插入数据。**

需要注意，InnoDB 的行锁实际上是基于索引记录实现的，具体锁定范围与索引使用情况有关。

### **2. MVCC：解决读写并发冲突 ⭐⭐⭐⭐⭐**

如果所有查询都需要加锁，会发生什么？

```text
事务 A 正在修改数据
          ↓
事务 B 想要读取数据
          ↓
只能等待事务 A 提交
```

这会降低数据库的并发性能。

因此，InnoDB 引入了 **MVCC（Multi-Version Concurrency Control，多版本并发控制）**。

**MVCC 的核心思想是：通过保存数据的历史版本，让普通 SELECT 可以读取符合自身可见性规则的数据版本，而不必等待正在修改数据的事务。**

例如：

```text
原始数据：
balance = 1000

事务 A：
UPDATE balance = 500;
尚未提交

事务 B：
SELECT balance FROM account WHERE id = 1;
```

在 InnoDB 的 `READ COMMITTED` 或 `REPEATABLE READ` 隔离级别下，事务 B 执行普通一致性读时，通常可以读取到旧版本：

```text
              account
                 │
        ┌────────┴────────┐
        │                 │
        ▼                 ▼
    当前版本            历史版本
  balance = 500       balance = 1000
        │                 │
        ▼                 ▼
    事务 A 修改         Undo Log
     尚未提交
                          │
                          ▼
                  事务 B 读取 1000
```

**这样就实现了读写之间尽量不互相阻塞。**

#### **MVCC 是如何实现的？**

主要依靠三个部分：

**① 隐藏字段**

InnoDB 聚簇索引记录中包含事务 ID、回滚指针等系统字段，用于支持版本管理。

**② Undo Log**

保存用于构建历史数据版本的信息。

**③ Read View**

判断当前事务可以看到哪些数据版本。

```text
            MVCC
              │
    ┌─────────┼─────────┐
    │         │         │
    ▼         ▼         ▼
  事务ID    Undo Log   Read View
    │         │         │
    ▼         ▼         ▼
  标识版本   构建旧版本  判断可见性
```

需要注意，MVCC 主要用于**普通 SELECT 的一致性读**。`UPDATE`、`DELETE`、`SELECT ... FOR UPDATE` 等当前读仍然需要使用锁机制。

### **3. 事务隔离级别：控制并发事务的数据可见性**

MySQL 提供四种事务隔离级别：

|**隔离级别**|**脏读**|**不可重复读**|**幻读**|
|---|---|---|---|
|READ UNCOMMITTED|可能|可能|可能|
|READ COMMITTED|避免|可能|可能|
|REPEATABLE READ|避免|避免|特定场景仍需注意|
|SERIALIZABLE|避免|避免|避免|

**InnoDB 默认使用 REPEATABLE READ（可重复读）隔离级别。**

它主要通过 MVCC 和锁机制实现隔离：

- 对于普通 SELECT，利用 MVCC 实现一致性读。
- 对于 UPDATE、DELETE 等修改操作，利用锁机制控制并发。
- 对于锁定读，结合记录锁、间隙锁和临键锁等控制访问范围。

这里有一个重要区别：

**可重复读不代表所有情况下都不会出现幻读。**

在 InnoDB 中，普通快照读可以通过 MVCC 保持一致的读取视图，而当前读则需要结合锁机制防止特定范围内的并发插入。

## **三、还有一个常见问题：如何避免超卖？**

假设你开发一个预约系统，某设备只剩下一个名额。

两个用户同时预约：

```text
用户 A                       用户 B
   │                            │
   ▼                            ▼
查询剩余名额 = 1          查询剩余名额 = 1
   │                            │
   ▼                            ▼
准备扣减名额               准备扣减名额
```

如果业务逻辑没有做好并发控制，就可能出现超卖。

一种常见的解决方式是**数据库条件更新**：

```sql
UPDATE resource
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

这条 SQL 的关键在于：

**判断库存是否大于 0 和扣减库存是在同一条 UPDATE 语句中完成的。**

InnoDB 会通过锁机制协调并发更新。

假设库存为 1：

```text
用户 A 执行 UPDATE
          ↓
stock：1 → 0
          ↓
影响行数 = 1
          ↓
扣减成功

用户 B 执行 UPDATE
          ↓
发现 stock > 0 不成立
          ↓
影响行数 = 0
          ↓
扣减失败
```

这样可以防止库存被扣成负数。

在 Java 后端中，可以根据 `UPDATE` 返回的影响行数判断是否扣减成功。

不过，**防止库存超卖不等于防止用户重复预约**。后者还需要唯一索引、幂等控制等机制。

## **四、面试怎么回答？⭐⭐⭐⭐⭐**

如果面试官问：

**“MySQL 是如何解决并发问题的？”**

建议这样回答：

MySQL 的 InnoDB 存储引擎主要通过锁机制、MVCC 和事务隔离级别来解决并发问题。

首先是**锁机制**，主要用于控制并发事务对数据的修改。例如两个事务同时更新同一条记录时，InnoDB 会通过排他锁协调执行顺序，避免并发修改产生冲突。

其次是 **MVCC 多版本并发控制**，它主要通过 Undo Log、Read View 和事务版本信息实现，让普通 SELECT 可以读取符合可见性规则的数据版本，从而减少读写之间的阻塞，提高并发性能。

最后是**事务隔离级别**，MySQL 提供读未提交、读已提交、可重复读和串行化四种隔离级别。InnoDB 默认采用可重复读，通过 MVCC 和锁机制控制脏读、不可重复读和幻读等并发问题。

在实际业务开发中，如果涉及库存扣减、预约名额抢占等高并发场景，还可以结合数据库条件更新、唯一索引和幂等控制，进一步保证业务数据的正确性。

### **一句话总结**

**MySQL 通过锁机制控制写写冲突，通过 MVCC 提高读写并发能力，通过事务隔离级别控制数据可见性。**

另外要区分两个概念：**数据库并发控制**解决的是事务之间的访问冲突，而**业务并发安全**还可能需要条件更新、唯一约束和幂等设计。
