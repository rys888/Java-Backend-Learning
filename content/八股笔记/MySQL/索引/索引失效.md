
[[#Q：MySQL 中有哪些常见的索引失效场景]]

MySQL 中，**索引失效是指 SQL 查询时，原本建立的索引没有被有效利用，导致数据库可能进行全表扫描、全索引扫描，或者无法充分利用联合索引。**

需要注意：**索引失效并不代表索引被删除，而是 MySQL 优化器没有使用该索引，或者索引无法发挥预期作用。**

## **一、MySQL 常见的索引失效场景

假设有一张用户表：

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(50),
    age INT,
    city VARCHAR(50),
    INDEX idx_name(name),
    INDEX idx_age_city(age, city)
);
```

### **1. 对索引字段使用函数**

例如：

```sql
SELECT * FROM user WHERE LEFT(name, 3) = 'Eas';
```

这里对索引字段 `name` 使用了 `LEFT()` 函数。

由于 B+ 树按照原始 `name` 值排序，而不是按照 `LEFT(name, 3)` 的结果排序，因此普通 `idx_name` 索引通常无法直接用于快速定位。

**优化方式：**

```sql
SELECT * FROM user WHERE name LIKE 'Eas%';
```

这样可以利用 B+ 树的有序性进行前缀范围查找。

注意，MySQL 8.0.13+ 支持函数索引，建立匹配的函数索引后，也可能优化函数查询。

### **2. 对索引字段进行计算**

例如：

```sql
SELECT * FROM user WHERE age + 1 = 21;
```

如果 `age` 是索引字段，对它进行计算可能导致无法使用普通索引进行范围定位。

**优化方式：**

```sql
SELECT * FROM user WHERE age = 20;
```

**记忆：尽量不要在 WHERE 条件中的索引列上进行函数运算或算术计算。**

---

### **3. LIKE 以通配符开头**

例如：

```sql
SELECT * FROM user WHERE name LIKE '%son';
```

或者：

```sql
SELECT * FROM user WHERE name LIKE '%aso%';
```

由于字符串前面存在 `%`，无法确定从 B+ 树的哪个位置开始查找。

因此，普通 B+ 树索引通常无法用于高效的范围定位。

对比：

```sql
-- 通常可以使用索引范围查找
SELECT * FROM user WHERE name LIKE 'Ea%';

-- 通常无法使用索引范围查找
SELECT * FROM user WHERE name LIKE '%Ea';
```

**原因：B+ 树按照索引字段从左到右排序，因此更适合前缀匹配。**

不过，如果查询字段全部被索引覆盖，MySQL 仍可能选择扫描索引，而不是扫描整张表。

---

### **4. 联合索引不满足最左前缀原则 ⭐⭐⭐⭐⭐**

假设存在联合索引：

```sql
INDEX idx_age_city(age, city)
```

该联合索引按照：

```text
先按照 age 排序
       ↓
age 相同时按照 city 排序
```

因此：

```sql
-- 可以利用联合索引
SELECT * FROM user
WHERE age = 20 AND city = 'Beijing';
```

```sql
-- 可以利用联合索引的最左前缀
SELECT * FROM user
WHERE age = 20;
```

但如果：

```sql
SELECT * FROM user
WHERE city = 'Beijing';
```

由于跳过了最左侧的 `age`，通常无法直接利用联合索引进行高效定位。

**原因：联合索引中的 city 并不是全局有序的。**

需要注意，MySQL 8.0 的优化器在某些条件下可能采用 Index Skip Scan，因此不能绝对认为跳过最左列就一定不使用索引。

### **5. 隐式类型转换**

假设：

```sql
name VARCHAR(50)
```

并且 `name` 上存在索引。

执行：

```sql
SELECT * FROM user WHERE name = 123;
```

由于 `name` 是字符串类型，而 `123` 是数字，MySQL 可能需要进行隐式类型转换。

在这种情况下，字符串列可能被转换为数字进行比较，导致普通字符串索引无法用于有效定位。

**优化方式：**

```sql
SELECT * FROM user WHERE name = '123';
```

不过，隐式类型转换是否影响索引，需要结合字段类型和转换方向判断。

例如，整型索引列与可以转换为数字的字符串常量比较，不一定导致索引失效。

---

### **6. OR 条件中存在没有索引的字段**

例如：

```sql
SELECT * FROM user
WHERE name = 'Eason' OR age = 20;
```

假设 `name` 有索引，而 `age` 完全没有可用索引。

由于查询需要同时找到满足两个条件的记录，MySQL 可能认为全表扫描更加合适。

但如果两个条件都有合适的索引：

```sql
SELECT * FROM user
WHERE name = 'Eason' OR age = 20;
```

MySQL 就可能使用 **Index Merge（索引合并）**，利用多个索引完成查询。

因此：

**OR 不会必然导致索引失效，关键在于 OR 两侧是否有可用索引，以及优化器选择的执行计划。**

## **二、6 种索引失效场景总结**

| **场景**        | **示例**               | **原因**         |
| ------------- | -------------------- | -------------- |
| ① 使用函数        | `LEFT(name,3)='Eas'` | 普通索引无法直接定位函数结果 |
| ② 索引列计算       | `age+1=21`           | 改变了索引列的原始比较方式  |
| ③ LIKE 前置 `%` | `LIKE '%abc'`        | 无法利用索引前缀定位     |
| ④ 违反最左前缀      | `(a,b)` 只查 `b`       | 后续字段不是全局有序的    |
| ⑥ 隐式类型转换      | 字符串列与数字比较            | 可能导致索引列发生类型转换  |
| ⑦ OR 条件       | 一侧缺少可用索引             | 可能选择全表扫描       |


需要特别强调：上表中的部分情况属于**索引无法用于范围定位或无法充分利用**，并不意味着索引绝对不会被使用。

## Q：MySQL 中有哪些常见的索引失效场景


MySQL 常见的索引失效场景主要有以下几种。

第一，对索引字段使用函数或者进行计算，可能导致无法利用普通索引进行快速定位。

第二，使用 LIKE 模糊查询时，如果通配符 `%` 出现在开头，通常无法利用 B+ 树索引进行范围查找。

第三，联合索引不满足最左前缀原则，例如建立 `(a,b,c)` 索引，却跳过 a 直接查询 b，通常无法高效利用该索引。

第四，隐式类型转换以及 OR 条件中缺少合适索引，也可能影响索引的使用。
