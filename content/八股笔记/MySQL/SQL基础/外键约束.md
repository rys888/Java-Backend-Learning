外键约束（Foreign Key Constraint）是 MySQL 中用于**建立两张表之间的关联关系，并保证数据引用完整性**的一种约束。

**外键约束可以保证子表中的外键值，必须能够在父表中找到对应的记录（或者在允许的情况下为 NULL），从而避免出现无效的关联数据。**

## **一、什么是外键约束？⭐⭐⭐⭐⭐**

假设我们设计一个员工管理系统，存在两张表。

**部门表（父表）：**

|**id（主键）**|**department_name**|
|---|---|
|1|技术部|
|2|财务部|
|3|人事部|

**员工表（子表）：**

|**id（主键）**|**employee_name**|**department_id（外键）**|
|---|---|---|
|101|张三|1|
|102|李四|1|
|103|王五|2|

其中：

- `department.id` 是部门表的主键。
- `employee.department_id` 是员工表的外键。
- 外键指向部门表中的 `id` 字段。

它们的关系是：

```text
       department（父表）
       ┌────────────────┐
       │ id（主键）      │
       │ department_name│
       └────────┬───────┘
                │
                │ 外键引用
                │
                ▼
        employee（子表）
       ┌─────────────────┐
       │ id（主键）       │
       │ employee_name   │
       │ department_id   │
       └─────────────────┘
```

假设现在插入：

```sql
INSERT INTO employee
VALUES (104, '赵六', 999);
```

但是部门表中不存在 `id = 999` 的部门。

如果设置了外键约束，MySQL 就会拒绝这次插入。

**因为员工不能关联一个不存在的部门。**

---

## **二、MySQL 如何创建外键约束？**

首先创建部门表：

```sql
CREATE TABLE department (
    id BIGINT PRIMARY KEY,
    department_name VARCHAR(50)
) ENGINE = InnoDB;
```

然后创建员工表：

```sql
CREATE TABLE employee (
    id BIGINT PRIMARY KEY,
    employee_name VARCHAR(50),
    department_id BIGINT,

    CONSTRAINT fk_department
        FOREIGN KEY (department_id)
        REFERENCES department(id)
) ENGINE = InnoDB;
```

重点是：

```sql
FOREIGN KEY (department_id)
REFERENCES department(id)
```

含义是：

员工表中的 `department_id` 必须引用部门表中存在的 `id`。

注意：外键字段并不要求必须是主键，也不要求唯一。

例如：

```text
员工张三 → 部门1
员工李四 → 部门1
员工王五 → 部门2
```

多个员工可以属于同一个部门。

另外，**外键字段可以为 NULL，除非额外设置了 NOT NULL 约束。**

---

## **三、外键约束有什么作用？**

外键约束主要有两个作用。

### **1. 保证数据的引用完整性**

假设没有外键约束：

```sql
INSERT INTO employee
VALUES (104, '赵六', 999);
```

数据库可能允许插入。

但是部门表根本不存在 999 这个部门。

这样就会出现：

```text
employee.department_id = 999
             ↓
department.id = 999
             ↓
         不存在！
```

这就是无效的关联数据，也叫孤儿记录。

外键约束可以防止这种情况发生。

### **2. 约束关联数据的删除和更新**

假设部门表中：

```text
部门1：技术部
```

员工表中：

```text
张三 → 部门1
李四 → 部门1
```

如果直接执行：

```sql
DELETE FROM department
WHERE id = 1;
```

那么员工张三和李四引用的部门就不存在了。

为了避免这种情况，MySQL 提供了多种外键处理策略。

---

## **四、外键约束的删除和更新策略 ⭐⭐⭐⭐⭐**

常见的外键处理策略包括：

|**策略**|**含义**|
|---|---|
| `RESTRICT` |如果存在子表记录引用，禁止删除或更新父表对应记录|
| `NO ACTION` |在 MySQL InnoDB 中，效果与 RESTRICT 基本相同|
| `CASCADE` |删除或更新父表记录时，级联处理子表|
| `SET NULL` |删除或更新父表记录时，将子表对应外键设置为 NULL|

### **1. RESTRICT：限制操作**

例如：

```sql
FOREIGN KEY (department_id)
REFERENCES department(id)
ON DELETE RESTRICT
```

假设技术部还有员工：

```text
技术部
 ├── 张三
 └── 李四
```

此时删除技术部：

```sql
DELETE FROM department WHERE id = 1;
```

MySQL 会拒绝删除。

因为还有员工引用这个部门。

### **2. CASCADE：级联操作**

例如：

```sql
FOREIGN KEY (department_id)
REFERENCES department(id)
ON DELETE CASCADE
```

假设：

```text
技术部
 ├── 张三
 └── 李四
```

删除技术部时：

```sql
DELETE FROM department WHERE id = 1;
```

MySQL 会自动删除引用该部门的员工记录。

```text
删除技术部
    ↓
自动删除张三
    ↓
自动删除李四
```

**注意：级联删除需要谨慎使用，因为可能导致大量关联数据被自动删除。**

### **3. SET NULL：设置为空**

例如：

```sql
FOREIGN KEY (department_id)
REFERENCES department(id)
ON DELETE SET NULL
```

删除技术部后：

|**id**|**employee_name**|**department_id**|
|---|---|---|
|101|张三|NULL|
|102|李四|NULL|

员工记录仍然存在，只是暂时不属于任何部门。

使用这种策略时，外键字段必须允许为 NULL。

## **五、实际开发中一定要使用数据库外键吗？**

**不一定。很多 Java 后端项目会使用逻辑外键，而不是真正的数据库外键约束。**

这里需要区分两个概念。

**① 物理外键**

在数据库中真正定义：

```sql
FOREIGN KEY (department_id)
REFERENCES department(id)
```

数据库会自动检查引用完整性。

**② 逻辑外键**

数据库中只保留关联字段：

```sql
department_id BIGINT
```

但是不添加：

```sql
FOREIGN KEY
```

由 Java 业务代码维护关联关系。

例如：

```java
public void addEmployee(Employee employee) {

    // 1. 检查部门是否存在
    Department department =
            departmentMapper.selectById(
                    employee.getDepartmentId()
            );

    if (department == null) {
        throw new RuntimeException("部门不存在");
    }

    // 2. 插入员工
    employeeMapper.insert(employee);
}
```

不过，这种写法只是简单示例。

在真实项目中，还需要考虑并发情况下部门被删除、事务一致性等问题。仅仅在插入前查询一次，并不能完全替代数据库外键约束。

### **为什么有些项目不使用物理外键？**

主要有以下原因：

1. **减少数据库层面的耦合**：避免表之间存在大量强制依赖。
2. **便于分库分表**：跨数据库的关联通常无法通过普通外键约束实现。
3. **提高架构灵活性**：部分业务希望通过应用层控制删除、更新和数据校验。
4. **减少部分写入操作的约束检查开销**：但不代表去掉外键一定能显著提高性能。

不过，不使用外键也有缺点：

**数据一致性需要由应用程序自行维护，设计不当更容易产生孤儿记录。**

因此，不能简单地说物理外键不好。

对于数据关系明确、完整性要求高的单体系统，数据库外键往往很有价值；对于分布式系统或需要灵活拆分数据库的业务，逻辑外键则比较常见。

## **六、外键和 JOIN 有什么关系？**

这是一个很容易混淆的知识点。

**外键约束和 JOIN 不是一回事。**

外键约束负责保证数据的引用完整性。

JOIN 负责关联查询不同表中的数据。

例如：

```sql
SELECT
    e.employee_name,
    d.department_name
FROM employee e
JOIN department d
    ON e.department_id = d.id;
```

即使没有创建物理外键约束，只要两个表中存在关联字段，也可以正常进行 JOIN 查询。

因此：

```text
外键约束 → 保证关联数据的完整性

JOIN     → 实现多表关联查询
```

**没有外键约束，不代表不能进行多表关联查询。**

## **七、面试怎么回答？⭐⭐⭐⭐⭐**

如果面试官问：

**“MySQL 中的外键约束是什么？有什么作用？”**

可以这样回答：

外键约束是关系型数据库中用于建立表之间关联关系、保证引用完整性的一种约束。

例如员工表中的部门 ID 可以作为外键，引用部门表中的主键 ID。这样可以保证员工关联的部门真实存在，避免出现无效的关联数据。

此外，MySQL 还提供 RESTRICT、CASCADE、SET NULL 等外键处理策略，用于控制父表记录删除或更新时对子表的影响。

在实际开发中，外键可以分为物理外键和逻辑外键。物理外键由数据库维护引用完整性，而逻辑外键只保留关联字段，由应用程序负责数据一致性。

对于一些需要分库分表或灵活拆分服务的系统，可能会选择逻辑外键，但也需要额外考虑并发和数据一致性问题。

### **最后总结**

**外键约束的核心作用就是保证两张表之间的引用完整性。**

记住三个重点：

1. **外键引用**：子表的外键值必须对应父表中存在的记录，或者在允许时为 NULL。
2. **外键策略**：`RESTRICT` 限制操作，`CASCADE` 级联操作，`SET NULL` 将外键置空。
3. **实际开发**：物理外键由数据库维护约束，逻辑外键由应用程序维护关联关系。
