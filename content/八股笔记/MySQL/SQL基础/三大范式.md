
[[#Q：数据库三大范式是什么？]]

数据库三大范式（1 NF、2 NF、3 NF）是关系型数据库设计的基本规范，核心目的就一个：**减少数据冗余，避免插入、更新、删除时出现异常，保证数据一致性。**

三者是递进关系，后一个都建立在前一个的基础上：

- **第一范式（1 NF）：字段具有原子性，不可再分。**
- **第二范式（2 NF）：满足第一范式，非主属性必须完全依赖于候选键，不能存在部分依赖。**
- **第三范式（3 NF）：满足第二范式，非主属性不能传递依赖于候选键。**

下面结合具体的 MySQL 表设计一个个看。

## **一、第一范式（1 NF）：字段不可再分**

比如一张学生表，联系方式字段里塞了多个电话号码：

|**学号**|**姓名**|**联系方式**|
|---|---|---|
|1001|张三|13812345678、13987654321|
|1002|李四|13712345678|

这里的 `联系方式` 字段保存了多个电话号码。如果业务需要分别查询、修改每个号码，这种设计就不符合第一范式的要求。

改成两张表就解决了，学生表只放学生本身的信息，电话表一行存一个号码：

**学生表：**

|**学号**|**姓名**|
|---|---|
|1001|张三|
|1002|李四|

**学生电话表：**

|**学号**|**电话号码**|
|---|---|
|1001|13812345678|
|1001|13987654321|
|1002|13712345678|

这样每个字段都只保存一个独立的值。不过需要注意：**原子性是相对于业务需求而言的。** 比如完整地址要不要拆成省、市、区，取决于业务是否需要分别操作这些信息，不是字段里出现分隔符就一定要拆。

**第一范式的判断标准，是字段值在当前业务语义下不可再分。**

## **二、第二范式（2 NF）：消除部分依赖**

第二范式有两个要求：一是在满足第一范式的基础上，二是每个非主属性都必须完全依赖于每一个候选键，不能只依赖复合候选键的一部分。

### **1. 什么是部分依赖？**

假设一张学生选课表：

|**学号**|**课程号**|**学生姓名**|**课程名称**|**成绩**|
|---|---|---|---|---|
|1001|C 01|张三|Java|90|
|1001|C 02|张三|MySQL|85|
|1002|C 01|李四|Java|95|

一名学生可以选多门课程，一门课程也可以被多名学生选择，所以这张表的复合主键是：

```sql
PRIMARY KEY (student_id, course_id)
```

再来看各个字段的依赖关系：

```text
(学号, 课程号)
      │
      ├── 成绩       完全依赖
      │
      ├── 学生姓名   只依赖学号
      │
      └── 课程名称   只依赖课程号
```

`成绩` 要同时知道学号和课程号才能确定，属于完全依赖；`学生姓名` 只要知道学号就能确定，`课程名称` 只要知道课程号就能确定。后两者都只依赖复合主键的一部分，这就是**部分依赖**，不满足第二范式。

### **2. 如何修改？**

拆成三张表：学生信息、课程信息各自独立成表，选课表只保留“谁选了什么课、考了多少分”这个关系。

**学生表：**

|**学号（主键）**|**学生姓名**|
|---|---|
|1001|张三|
|1002|李四|

**课程表：**

|**课程号（主键）**|**课程名称**|
|---|---|
|C 01|Java|
|C 02|MySQL|

**选课表：**

|**学号**|**课程号**|**成绩**|
|---|---|---|
|1001|C 01|90|
|1001|C 02|85|
|1002|C 01|95|

此时依赖关系就干净了：

```text
学生表：
学号 → 学生姓名

课程表：
课程号 → 课程名称

选课表：
(学号, 课程号) → 成绩
```

非主属性对复合主键的部分依赖被消掉，也就满足了第二范式。

**第二范式的判断标准，是非主属性不能只依赖复合候选键的一部分。**

补充一点：如果一张表只有一个单字段候选键，也不存在其他复合候选键，那么在满足 1 NF 的前提下它自然满足 2 NF——因为压根不存在“复合键的一部分”。

## **三、第三范式（3 NF）：消除传递依赖 ⭐⭐⭐⭐⭐**

第三范式同样有两个要求：满足第二范式；非主属性不能通过其他非主属性传递依赖于候选键。

### **1. 什么是传递依赖？**

假设一张员工表：

|**员工 ID**|**员工姓名**|**部门 ID**|**部门名称**|
|---|---|---|---|
|1|张三|101|技术部|
|2|李四|101|技术部|
|3|王五|102|财务部|

假设一个员工只属于一个部门，一个部门 ID 唯一对应一个部门名称，那么依赖关系就是：

```text
员工ID → 部门ID → 部门名称
```

也就是说，根据员工 ID 可以确定部门 ID，根据部门 ID 又可以确定部门名称，所以员工 ID 能间接确定部门名称，这就是**传递依赖**。

为什么这种设计不好？假设技术部要改名叫研发部，就得把所有属于技术部的员工记录都改一遍：

```sql
UPDATE employee
SET department_name = '研发部'
WHERE department_id = 101;
```

只要有一条没改成功，就会出现同一个部门两个名字的情况：

```text
员工张三 → 研发部
员工李四 → 技术部
```

数据就不一致了。

### **2. 如何修改？**

拆成员工表和部门表两张。员工表只留部门 ID 这个外键，部门名称交给部门表管：

**员工表：**

|**员工 ID**|**员工姓名**|**部门 ID**|
|---|---|---|
|1|张三|101|
|2|李四|101|
|3|王五|102|

**部门表：**

|**部门 ID**|**部门名称**|
|---|---|
|101|技术部|
|102|财务部|

此时：

```text
员工表：
员工ID → 员工姓名
员工ID → 部门ID

部门表：
部门ID → 部门名称
```

技术部改名时只改部门表的一条记录：

```sql
UPDATE department
SET department_name = '研发部'
WHERE department_id = 101;
```

这样就避免了数据冗余和更新异常。

**第三范式的判断标准，是非主属性不能通过其他非主属性间接依赖候选键。**

严格来说，3 NF 的正式定义是：对于每个非平凡函数依赖 `X → A`，要么 X 是超键，要么 A 是主属性。面试中通常用“消除非主属性的传递依赖”来帮助理解。

## **四、三大范式之间的关系**

|**范式**|**核心要求**|**解决的问题**|
|---|---|---|
|第一范式（1 NF）|字段值具有原子性|一个字段存储多个独立值|
|第二范式（2 NF）|消除非主属性对候选键的部分依赖|非主属性只依赖复合候选键的一部分|
|第三范式（3 NF）|消除不符合规范的传递依赖|非主属性间接依赖候选键|

记忆的话按这个顺序走就行：

```text
第一范式（1NF）
    │
    │ 字段不可再分
    ▼
第二范式（2NF）
    │
    │ 消除部分依赖
    ▼
第三范式（3NF）
    │
    │ 消除传递依赖
    ▼
减少数据冗余，提高数据一致性
```

## **五、实际开发一定要遵守三大范式吗？**

**不一定。实际开发中通常优先遵守第三范式，但有时会为了查询性能做适当的反范式设计。**

比如之前做过的订单业务，假设有两张表：

**订单表：**

```text
order
├── id
├── user_id
├── total_amount
└── create_time
```

**用户表：**

```text
user
├── id
├── username
└── phone
```

订单列表如果要展示用户名，通常得关联查询：

```sql
SELECT o.id, u.username, o.total_amount
FROM orders o
JOIN user u ON o.user_id = u.id;
```

但在一些高频查询场景下，可能会选择在订单表里冗余一份用户信息：

```text
orders
├── id
├── user_id
├── username_snapshot
├── total_amount
└── create_time
```

这样就不用每次都去关联用户表了。

不过这里要区分两种情况：**历史快照**保存的是下单时的用户名，即使用户之后改了名，订单快照也不变，这本身有独立的业务意义；**冗余当前信息**存的是用户当前名称，目的是减少关联查询，需要额外维护数据同步，否则很容易出现不一致。

所以反范式虽然可能提升查询性能，代价是数据维护成本变高。

## Q：数据库三大范式是什么？


数据库三大范式是关系型数据库设计的基本规范，主要用于减少数据冗余，避免插入、更新和删除异常。

第一范式要求字段具有原子性，也就是每个字段在业务语义下不可再分。

第二范式要求在满足第一范式的基础上，非主属性必须完全依赖于候选键，不能只依赖复合候选键的一部分。

第三范式要求在满足第二范式的基础上，消除非主属性对候选键的不合理传递依赖。例如员工表中不应该同时保存部门 ID 和依赖于部门 ID 的部门名称，可以将部门信息拆分成独立的部门表。

实际开发中一般会优先遵守第三范式，但在一些高频查询场景下，也可能通过适当的数据冗余进行反范式设计，以减少关联查询，提高查询性能。


**1 NF：原子性；2 NF：消除部分依赖；3 NF：消除传递依赖。**
