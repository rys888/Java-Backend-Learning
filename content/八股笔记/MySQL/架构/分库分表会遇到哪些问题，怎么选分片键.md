## **一、分库分表会遇到哪些问题？**

假设我们把一张订单表 `orders` 拆成了 4 张表：

```text
orders_0
orders_1
orders_2
orders_3
```

### **① 跨库 JOIN 问题**

原来用户表和订单表在同一个数据库，可以直接 JOIN：

```sql
SELECT * FROM user u
JOIN orders o ON u.id = o.user_id;
```

但是分库分表后，用户数据和订单数据可能分布在不同数据库中。

**解决方法：** 尽量避免跨库 JOIN，可以通过应用层分别查询后组装数据，或者适当进行数据冗余。

### **② 分页和排序问题**

假设需要查询最新的 20 条订单。

但是订单分散在 4 张表中：

```text
orders_0 ──┐
orders_1 ──┤
orders_2 ──┼── 合并排序 ── 返回20条
orders_3 ──┘
```

无法简单地对一张表执行 `LIMIT 20` 就得到全局最新的 20 条订单。

**解决方法：** 分别查询各个分片，再进行结果合并和排序。数据量较大时，也可以考虑专门的搜索或分析系统。

### **③ 分布式事务问题**

假设一个业务操作需要同时修改两个数据库：

```text
数据库 A：扣减库存
数据库 B：创建订单
```

如果数据库 A 修改成功，但数据库 B 修改失败，就可能出现数据不一致。

**解决方法：** 根据业务选择分布式事务方案，或者通过消息队列、补偿机制等实现最终一致性。

RabbitMQ 消息队列实际业务遇到的分布式事务问题：创建订单+扣减库存

### **④ 分布式 ID 问题**

原来只有一张订单表，可以使用 MySQL 自增主键。

但是拆成 4 张表后：

```text
orders_0：id = 1
orders_1：id = 1
orders_2：id = 1
```

不同表可能产生重复 ID。

**解决方法：** 使用雪花算法（Snowflake）、号段模式等生成全局唯一 ID。

### **⑤ 数据倾斜问题 ⭐⭐⭐⭐⭐**

假设按照用户 ID 分片：

```java
int tableIndex = userId % 4;
```

如果某些用户的订单特别多，就可能导致：

```text
orders_0：100 万条
orders_1：100 万条
orders_2：800 万条  ← 热点分片
orders_3：100 万条
```

这样就会出现部分分片压力特别大，而其他分片比较空闲的情况。

**解决方法：** 选择分布相对均匀的分片键，必要时对热点数据进行特殊处理。

此外，后续增加分片数量还会涉及数据迁移和路由规则调整。

## 二、怎么选择分片键

**分片键就是决定一条数据应该存储在哪个数据库、哪张表中的字段。**

例如：

```java
int tableIndex = userId % 4;
```

这里的 `userId` 就是分片键。

选择分片键主要考虑三个方面。

### **① 尽量选择经常出现在查询条件中的字段**

假设订单系统经常执行：

```sql
SELECT * FROM orders WHERE user_id = 1001;
```

那么选择 `user_id` 作为分片键比较合适。

因为可以直接计算：

```java
1001 % 4 = 1;
```

然后只查询：

```text
orders_1
```

如果选择 `order_id` 作为分片键，但经常通过 `user_id` 查询订单，那么可能需要查询所有分片。

**因此，分片键应该尽量符合核心业务的查询方式。**

### **② 尽量选择数据分布均匀的字段**

例如：

- `user_id`：通常具有较高区分度，配合合理的哈希策略可以分散数据。
- `gender`：只有少数几个值，不适合作为普通哈希分片键。
- `status`：状态值较少，而且分布可能不均匀，也不适合。

**核心目的是避免大量数据集中在某一个分片中。**

### **③ 尽量选择不会频繁修改的字段**

例如：

- `user_id`：通常不会发生变化。
- `order_id`：创建后通常不会改变。
- `order_status`：可能频繁变化。

如果使用 `order_status` 作为分片键：

```text
待支付 → orders_0
已支付 → orders_1
```

订单状态变化后，可能需要把订单从一张表迁移到另一张表。

因此，**分片键最好具有稳定性。**

## Q：

分库分表后主要会遇到跨库 JOIN、分页排序、分布式事务、分布式 ID、数据倾斜以及后续扩容等问题。

对于分片键的选择，我主要考虑三个方面。

第一，尽量选择经常出现在查询条件中的字段，避免一次查询扫描所有分片。

第二，尽量选择数据分布均匀的字段，避免数据倾斜和热点分片。

第三，尽量选择不会频繁修改的字段，避免分片键变化导致数据迁移。

例如在订单系统中，如果业务主要是查询某个用户的订单，那么可以考虑使用 `user_id` 作为分片键；如果主要根据订单编号查询，则可以考虑使用 `order_id`。

**一句话记忆：分库分表的难点是跨分片操作；分片键的选择原则是查询频繁、分布均匀、字段稳定。**

还有一个很重要的取舍：**按** `user_id` **分片方便查询用户的所有订单，按**  `order_id` **分片方便根据订单号定位订单。没有绝对最好的分片键，关键看业务的核心查询场景。**
