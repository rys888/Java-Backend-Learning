[[#Q：主从延迟怎么解决]]


**MySQL 主从延迟，就是主库已经完成数据修改，但从库还没有及时同步，导致查询从库时读到旧数据。**

例如：

```text
主库：UPDATE balance = 500
           ↓
主库提交成功
           ↓
从库还没同步完成
           ↓
查询从库：balance = 1000
```

解决主从延迟，主要有以下 **5 种方法**。

### **① 强一致性读走主库（最常用 ⭐⭐⭐⭐⭐）**

对于余额、订单状态等需要立即读取最新数据的场景，直接查询主库。

例如：

```text
用户修改订单
      ↓
主库 UPDATE
      ↓
用户立即查询订单
      ↓
直接查询主库
```

**优点：** 能保证读取到主库已提交的最新数据，避免主从延迟带来的旧数据问题。

**缺点：** 增加主库的查询压力。

### **② 写后短时间内读主库**

例如用户修改个人资料：

```text
用户修改个人资料
      ↓
写入主库
      ↓
接下来几秒内读取主库
      ↓
之后恢复从库读取
```

这种方法叫作**写后读主库（Read Your Writes）**。

相比所有查询都走主库，可以减少主库压力，也可以降低读旧数据的概率

但固定等待几秒不能严格保证从库已经同步完成。

### Q：异步复制和半异步复制

可以把 **异步复制和半同步复制** 理解为一个问题：

**主库执行完 UPDATE 后，要不要等从库确认收到数据，才能告诉用户操作成功？**

我们通过一个具体例子来理解。

假设有两台 MySQL 服务器：

- **主库 A**：负责修改数据。
- **从库 B**：负责同步主库的数据。

用户执行：

```sql
UPDATE user SET balance = 500 WHERE id = 1;
```

原本 `balance = 1000`。

## 异步复制（Asynchronous Replication）

异步复制的核心特点是：**主库提交成功后，不需要等待从库，就可以直接告诉用户操作成功。**

执行过程：

```text
用户                 主库 A                  从库 B
 │                     │                       │
 │──── UPDATE ────────>│                       │
 │                     │                       │
 │                 修改数据                     │
 │                     │                       │
 │                 提交事务                     │
 │                     │                       │
 │<──── 返回成功 ───────│                       │
 │                     │                       │
 │                     │──── 发送 Binlog ─────> │
 │                     │                       │
 │                     │                   接收 Binlog
 │                     │                       │
 │                     │                   重放 Binlog
 │                     │                       │
 │                     │                   数据更新完成
```

注意：这是为了方便理解而画的示意图，实际 Binlog 传输可以与主库事务处理并行进行。

### **异步复制有什么问题？**

假设：

1. 主库把 `balance` 修改为 500。
2. 主库提交成功，并告诉用户修改成功。
3. 从库还没收到对应的 Binlog。
4. **主库突然宕机。**

此时：

```text
主库 A：balance = 500（但已经宕机）

从库 B：balance = 1000
```

如果直接把从库 B 提升为新的主库，**刚刚提交的修改就可能丢失。**

这就是异步复制的主要风险。

## 半同步复制（Semi-Synchronous Replication）

半同步复制的核心特点是：

**主库需要等待至少一个从库确认收到相关 Binlog，才能向用户返回事务提交成功。**

执行过程：

```text
用户                 主库 A                  从库 B
 │                     │                       │
 │──── UPDATE ────────>│                       │
 │                     │                       │
 │                 修改数据                     │
 │                     │                       │
 │                     │──── 发送 Binlog ─────>│
 │                     │                       │
 │                     │                   接收 Binlog
 │                     │                       │
 │                     │<──── 返回 ACK ──────── │
 │                     │    （确认收到）         │
 │                     │                       │
 │<──── 返回成功 ───────│                       │
 │                     │                       │
 │                     │                   重放 Binlog
 │                     │                       │
 │                     │                   数据更新完成
```

这里的 ACK 就是 **Acknowledgement（确认消息）**。

它相当于从库告诉主库：

你发给我的 Binlog，我已经收到并写入中继日志了。

主库收到确认后，才能向用户返回成功。

具体事务本地提交与等待 ACK 的先后顺序，取决于半同步复制的工作模式；这里主要展示客户端收到成功响应之前需要等待确认这一点。

### **半同步复制有什么好处？**

还是刚才的例子：

1. 主库把 `balance` 修改为 500。
2. 从库接收到对应的 Binlog，并返回 ACK。
3. 主库向用户返回成功。
4. 主库突然宕机。

此时虽然从库可能还没执行 UPDATE，但是：

**从库已经保存了相关 Binlog，可以继续重放，将 balance 更新为 500。**

因此，相比异步复制，半同步复制可以降低主库故障时的数据丢失风险。

不过，它不是绝对零数据丢失的保证。例如等待 ACK 超时后，MySQL 半同步复制可能退化为异步复制。

## 为什么半同步复制还是会出现主从延迟？

这是最重要的地方。

**因为从库收到 Binlog，不等于从库已经执行 Binlog。**

从库同步数据主要分为两个步骤：

```text
第一步：接收 Binlog
        ↓
写入 Relay Log（中继日志）
        ↓
向主库返回 ACK
        ↓
第二步：执行 Relay Log 中的事务
        ↓
更新从库数据
```

假设：

```text
主库 balance = 500

从库已经收到 Binlog
        ↓
向主库返回 ACK
        ↓
主库告诉用户修改成功
        ↓
但从库还没执行 UPDATE
        ↓
此时查询从库，balance 仍然是 1000
```

所以，**半同步复制主要解决的是数据丢失风险，而不是主从延迟问题。**

```
MySQL 主从复制主要有异步复制和半同步复制两种方式。

异步复制是指主库提交事务后，不需要等待从库确认，就可以直接向客户端返回成功，因此性能较好，但主库突然宕机时，可能存在数据丢失的问题。

半同步复制则要求主库等待至少一个从库确认收到相关 Binlog，才能向客户端返回成功，因此可以降低数据丢失风险。

但是半同步复制并不要求从库已经执行完 Binlog，所以仍然可能出现主从延迟。
```

### **④ 优化从库同步性能**

如果从库同步速度跟不上主库，可以考虑：

- **并行复制**：让从库使用多个工作线程并行应用事务。
- **提升从库硬件性能**：例如 CPU、磁盘 I/O。
- **减少大事务**：避免一次事务修改几十万条数据，拖慢复制。
- **优化慢 SQL**：减少从库查询对资源的占用。

这些方法主要用于**降低主从延迟本身**。

### **⑤ 监控主从延迟**

可以监控从库的复制状态，发现延迟过大时：

- 发出告警。
- 暂时将重要查询切换到主库。
- 排查网络、磁盘、SQL 和复制线程等问题。

### Q：主从延迟怎么解决

MySQL 主从延迟主要是因为主库提交事务后，从库还需要获取并应用 Binlog，因此主从数据可能短暂不一致。

对于解决方案，我会从两个方面考虑。

第一是业务层面，对于订单状态、余额等一致性要求较高的数据，可以采用强制读主库或者写后读主库的方式，避免读到旧数据。

第二是数据库层面，可以通过并行复制、优化慢 SQL、减少大事务以及提升从库硬件性能等方式降低复制延迟。

另外，半同步复制可以降低主库故障时的数据丢失风险，但不能保证从库已经应用事务，因此不能完全解决主从延迟问题。
