
单条 UPDATE 虽然会加锁，但是先读到应用里，在计算，最后写回不一定是一个受保护的整体

MySQL 中，**丢失更新是指两个事务同时读取同一条数据，并根据旧数据进行修改，导致其中一个事务的更新结果被另一个事务覆盖。**

常见的三种解决方式是：**原子条件更新、悲观锁和乐观锁。**

我们用一个库存扣减的例子理解。

假设数据库中：

```sql
id = 1
stock = 10
```

两个事务同时购买商品，各扣减 1 件库存。

如果没有做好并发控制：

```text
事务 A                     事务 B
   │                          │
读取 stock = 10          读取 stock = 10
   │                          │
计算 10 - 1              计算 10 - 1
   │                          │
更新 stock = 9           更新 stock = 9
   │                          │
   ▼                          ▼
```

最终库存为 `9`，但实际上应该为 `8`。

这就是典型的**丢失更新**。

## **一、原子条件更新 ⭐⭐⭐⭐⭐**

**核心思想：将判断条件和数据修改放在同一条 SQL 中，由数据库保证操作的原子性。**

例如：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = 1 AND stock > 0;
```

这条 SQL 完成两件事：

1. 判断库存是否大于 0。
2. 如果满足条件，直接扣减库存。

假设两个事务同时执行：

```text
初始 stock = 10

事务 A：stock = 10 - 1 = 9
事务 B：stock = 9 - 1 = 8

最终 stock = 8
```

InnoDB 会通过行锁协调并发更新，第二个事务不会直接拿之前读取的 `10` 覆盖第一个事务的结果。

另外，`stock > 0` 还能防止库存被扣成负数。

**优点：SQL 简单、性能较好，不需要提前查询库存。**

**适用场景：库存扣减、账户余额扣减、计数器更新等。**

注意，原子条件更新本身也会使用数据库锁，只是不需要应用程序显式加锁。

---

## **二、悲观锁（Pessimistic Lock）⭐⭐⭐⭐⭐**

**核心思想：假设并发冲突很容易发生，因此在读取数据时就提前加锁，阻止其他事务同时修改。**

MySQL 中通常通过 `SELECT ... FOR UPDATE` 实现。

例如：

```sql
BEGIN;

-- 查询库存并加排他锁
SELECT stock
FROM product
WHERE id = 1
FOR UPDATE;

-- 假设应用程序判断 stock > 0

UPDATE product
SET stock = 9
WHERE id = 1;

COMMIT;
```

假设两个事务同时操作：

```text
事务 A                       事务 B
   │                            │
SELECT ... FOR UPDATE      SELECT ... FOR UPDATE
   │                            │
成功获取锁                   等待锁释放
   │                            │
读取 stock = 10                 │
   │                            │
更新 stock = 9                  │
   │                            │
COMMIT                          │
   │                            │
释放锁                          │
                                ▼
                          获取锁并读取 stock = 9
                                │
                          更新 stock = 8
```

这样就不会出现两个事务都读取 `10`，然后分别更新为 `9` 的情况。

**优点：**

- 能有效控制并发修改冲突。
- 适合需要先查询、执行复杂业务判断，再修改数据的场景。

**缺点：**

- 其他事务可能阻塞等待。
- 锁持有时间过长会降低并发性能。

**适用场景：冲突频繁、业务逻辑复杂且需要严格控制并发修改的场景。**

注意，`SELECT ... FOR UPDATE` 必须在合适的事务范围内使用，否则锁可能很快就被释放。

---

## **三、乐观锁（Optimistic Lock）⭐⭐⭐⭐⭐**

**核心思想：假设并发冲突不经常发生，因此读取数据时不加锁，而是在更新时检查数据是否被其他事务修改。**

最常见的实现方式是 **Version 版本号机制**。

例如：

```text
id = 1
stock = 10
version = 1
```

事务 A 和事务 B 同时读取：

```text
事务 A：
stock = 10
version = 1

事务 B：
stock = 10
version = 1
```

事务 A 更新：

```sql
UPDATE product
SET stock = 9,
    version = version + 1
WHERE id = 1 AND version = 1;
```

更新成功：

```text
stock = 9
version = 2
```

事务 B 再尝试更新：

```sql
UPDATE product
SET stock = 9,
    version = version + 1
WHERE id = 1 AND version = 1;
```

由于当前 `version = 2`，不满足 `version = 1`。

因此：

```text
事务 A：更新成功，影响行数 = 1

事务 B：更新失败，影响行数 = 0
```

事务 B 可以重新读取最新数据，再决定是否重试。

**优点：**

- 读取时不需要提前加锁。
- 适合并发冲突较少的场景。

**缺点：**

- 冲突频繁时，可能需要多次重试。
- 重试会增加数据库负担。

**适用场景：冲突较少、读多写少，并且允许失败重试的业务。**

需要注意，乐观锁不是完全不使用数据库锁，而是**不提前持有业务记录的排他锁，更新时仍由 InnoDB 使用锁保证 SQL 的原子执行**。

---

## **四、三种解决方式的区别 ⭐⭐⭐⭐⭐**

|**对比**|**原子条件更新**|**悲观锁**|**乐观锁**|
|---|---|---|---|
|核心思想|一条 SQL 完成判断与修改|先加锁，再操作|更新时检查数据是否变化|
|实现方式| `UPDATE ... WHERE` | `SELECT ... FOR UPDATE` |Version + CAS|
|是否提前加锁|否|是|否|
|冲突处理|数据库协调更新|阻塞等待|更新失败，按需重试|
|性能特点|通常较高效|锁竞争可能影响性能|冲突少时较高效|
|适用场景|库存、余额、计数器|复杂事务、高冲突业务|低冲突、允许重试的业务|

这里的 CAS 指的是 **Compare And Swap（比较并交换）思想**：只有数据库中的版本号与之前读取的版本号一致，才允许更新。

### **三者最大的区别**

**原子条件更新：**

不提前查询旧值，直接让数据库完成判断和修改。

**悲观锁：**

我先把数据锁住，其他事务等我修改完成。

**乐观锁：**

我先不锁，更新时再检查有没有人修改过。

## **五、面试怎么回答？**

如果面试官问：

**“MySQL 如何解决事务丢失更新问题？”**

可以这样回答：

MySQL 中解决丢失更新问题，常见有三种方式：原子条件更新、悲观锁和乐观锁。

第一种是**原子条件更新**，将判断和修改放在同一条 UPDATE 语句中，例如 `SET stock = stock - 1 WHERE stock > 0`，由 InnoDB 保证更新的原子性。

第二种是**悲观锁**，通过 `SELECT FOR UPDATE` 提前对记录加锁，其他事务需要等待锁释放，适合并发冲突频繁或者业务判断复杂的场景。

第三种是**乐观锁**，通常通过 Version 版本号实现，更新时检查版本号是否发生变化。如果版本号一致就更新，否则更新失败并根据业务决定是否重试。

实际开发中，如果只是简单的库存扣减，我会优先考虑原子条件更新；如果需要复杂的读取和修改操作，可以考虑悲观锁；如果冲突较少且允许重试，可以考虑乐观锁。

**一句话记忆：原子更新直接改，悲观锁先锁再改，乐观锁比较后再改。**
