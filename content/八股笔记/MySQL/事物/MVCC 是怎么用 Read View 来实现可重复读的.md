
**在可重复读（RR）隔离级别下，事务第一次执行普通 SELECT 时会创建一个 Read View，后续查询一直使用这个 Read View，因此即使其他事务修改并提交了数据，当前事务仍然可以读取原来的版本。**


### **① 第一次查询：创建 Read View**

假设数据库中：

```text
balance = 1000
```

现在有两个事务：

```text
事务 A                         事务 B
  │                              │
  ├── BEGIN                      │
  │                              │
  ├── SELECT balance             │
  │   结果：1000                 │
  │                              │
  └── 创建 Read View ①           │
```

**Read View 可以理解为一张记录了当时哪些事务还在执行的名单，用来判断哪些数据版本可以看到。**

注意，它不是复制一份数据。

### **② 其他事务修改并提交**

接下来事务 B 修改余额：

```text
事务 A                         事务 B
  │                              │
  │                              ├── BEGIN
  │                              │
  │                              ├── UPDATE
  │                              │   balance = 500
  │                              │
  │                              └── COMMIT
```

此时数据库中的最新数据已经是：

```text
当前版本：balance = 500
                ↓
历史版本：balance = 1000（通过 Undo Log 获取）
```

### **③ 第二次查询：继续使用原来的 Read View**

事务 A 再次查询：

```sql
SELECT balance FROM account WHERE id = 1;
```

MySQL 会：

1. **继续使用 Read View ①**，而不是创建新的。
2. 检查最新版本 `balance = 500`，发现它由 Read View 创建之后才开始的事务修改，因此不可见。
3. 沿着 Undo Log 版本链找到旧版本 `balance = 1000`。
4. 返回 `1000`。

最终：

```text
事务 A 第一次查询：1000
事务 B 修改并提交：500
事务 A 第二次查询：1000
```

**这就是 MVCC 通过 Read View 实现可重复读的原理。**

---

### **那为什么 RC（读已提交）不能保证可重复读？**

区别只有一个：

- **RC：** 每次普通 SELECT 都创建新的 Read View，因此第二次查询能看到事务 B 已提交的 `500`。
- **RR：** 第一次普通 SELECT 创建 Read View，后续复用，因此第二次查询仍然看到 `1000`。

### **面试怎么回答？**

InnoDB 的 MVCC 主要通过 Read View 和 Undo Log 实现可重复读。

在 RR 隔离级别下，事务第一次执行快照读时会创建 Read View，后续快照读复用同一个 Read View。

当其他事务修改并提交数据后，当前事务会通过 Read View 判断新版本是否可见。如果不可见，就通过 Undo Log 找到之前的历史版本。

因此，同一个事务多次执行普通快照读，可以看到一致的数据快照，从而实现可重复读。

**你只需要记住：Read View 决定能看哪个版本，Undo Log 负责提供旧版本，RR 通过复用 Read View 实现可重复读。**

补充一个小细节：事务自己修改的数据仍然可以被自己看到，并不是所有查询结果都永远固定。
