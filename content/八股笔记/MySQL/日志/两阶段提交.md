
[[#Q：]]

**MySQL 的两阶段提交（2 PC），就是为了保证 Redo Log 和 Binlog 的一致性，避免数据库崩溃后出现数据不一致的问题。**
### **① 为什么需要两阶段提交？**

假设执行：

```sql
UPDATE user SET balance = 500 WHERE id = 1;
```

这里涉及两个日志：

- **Redo Log**：用于 InnoDB 崩溃恢复。
- **Binlog**：用于主从复制和数据恢复。

如果先写 Redo Log，写完后 MySQL 突然崩溃，Binlog 还没写入。

那么可能出现：

```text
主库：通过 Redo Log 恢复，balance = 500
从库：没有收到 Binlog，balance 仍然是 1000
```

这样主从数据就可能不一致。

### **② 两阶段提交怎么解决？**

MySQL 将事务提交分成两个阶段：

**第一阶段：Prepare（准备阶段）**

InnoDB 将 Redo Log 标记为 Prepare 状态。

**第二阶段：Commit（提交阶段）**

先写入 Binlog，再将 Redo Log 标记为 Commit 状态。

```text
执行 UPDATE
     ↓
修改数据，生成 Undo Log 和 Redo Log
     ↓
① Redo Log Prepare
     ↓
② 写入 Binlog
     ↓
③ Redo Log Commit
     ↓
事务提交成功
```

### **③ 如果中途崩溃怎么办？**

假设 Redo Log 已经进入 Prepare 状态：

- **Binlog 没有完整写入**：恢复时回滚事务。
- **Binlog 已经完整写入**：恢复时提交事务。

这样就能避免 Redo Log 和 Binlog 对事务提交结果的记录不一致。

### Q：

MySQL 的两阶段提交主要是为了保证 Redo Log 和 Binlog 的一致性。

第一阶段是 Prepare，先将 Redo Log 设置为准备状态。

第二阶段是 Commit，先写入 Binlog，再将 Redo Log 设置为提交状态。

如果中途发生崩溃，MySQL 可以根据 Binlog 是否完整写入来决定提交还是回滚处于 Prepare 状态的事务，从而保证两个日志的一致性。

**两阶段提交就是先让 Redo Log 准备好，再写 Binlog，最后确认提交，保证两个日志的一致性。**
