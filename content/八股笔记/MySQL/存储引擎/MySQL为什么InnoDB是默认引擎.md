[[#Q：MySQL 为什么选择 InnoDB 作为默认存储引擎？]]

先给结论：**InnoDB 从 MySQL 5.5.5 开始成为 MySQL 的默认存储引擎，主要是因为它支持事务、行级锁、MVCC、崩溃恢复和外键约束**，这些能力正好对得上高并发、高可靠业务的需求。在这个版本之前，默认引擎是 MyISAM，所以理解这个问题最直接的方式，就是把 InnoDB 和 MyISAM 摆在一起对比。

## **一、InnoDB 和 MyISAM 的区别**

|**对比**|**InnoDB**|**MyISAM**|
|---|---|---|
|事务|✅ 支持|❌ 不支持|
|锁机制|行级锁、表级锁|主要是表级锁|
|MVCC|✅ 支持|❌ 不支持|
|外键约束|✅ 支持|❌ 不支持|
|崩溃恢复|支持 Redo Log 等恢复机制|缺乏完整的事务崩溃恢复机制|
|索引结构|B+ 树，主键采用聚簇索引|B+ 树，索引与数据分离|
|并发性能|更适合高并发读写|写操作更容易产生锁竞争|
|适用场景|订单、支付、库存等业务|部分简单、读多写少的场景|

表里这些差异，真正起决定作用的是下面四点。

---

## **二、支持事务，保证数据一致性**

这是 InnoDB 能成为默认引擎最主要的原因。事务的作用简单说就是：**一组 SQL 要么全部生效，要么全部不生效**，中间出了意外，前面做的事一起撤销。

拿订单系统举例，用户下单时至少要执行两条 SQL：

```sql
-- 扣减库存
UPDATE product
SET stock = stock - 1
WHERE id = 1001 AND stock > 0;

-- 创建订单
INSERT INTO orders(user_id, product_id)
VALUES (1, 1001);
```

这两条是同一个业务动作里的两步，缺一步这条链路就是错的。如果库存扣减成功、订单创建却失败了，没有事务的话结果就是：**库存扣减成功 → 订单创建失败 → 库存少了但订单不存在 → 数据不一致**。库存凭空少一件，账也就对不上了。

InnoDB 支持事务，就能把这两个操作绑到一起：

```sql
START TRANSACTION;

UPDATE product
SET stock = stock - 1
WHERE id = 1001 AND stock > 0;

INSERT INTO orders(user_id, product_id)
VALUES (1, 1001);

COMMIT;
```

这里的 `START TRANSACTION` 是开启事务，后面两条 SQL 执行完只是"待提交"状态，最后 `COMMIT` 才真正生效。中途任何一步失败，执行 `ROLLBACK`，前面的修改会被一起抹掉。所以实际业务里还会再判断一下库存扣减是否成功（比如影响行数是不是 0），不成功就回滚，不然可能卖出超卖的库存。

这样保证下来就是一句话：**两个操作要么全部成功，要么全部回滚。**

事务要满足的四个特性（ACID）：

- **原子性（Atomicity）**：操作不可再分，要么全做，要么全不做
- **一致性（Consistency）**：事务前后数据都处于合法状态
- **隔离性（Isolation）**：并发事务之间互不干扰
- **持久性（Durability）**：提交后的修改不会丢

MyISAM 不支持事务，所以多条 SQL 的原子性没法靠回滚保证。

## **三、支持行级锁，提高并发性能**

锁的作用是控制并发修改同一份数据。InnoDB 和 MyISAM 在这里的差别就是锁的粒度：InnoDB 支持行级锁，MyISAM 主要用表级锁。

假设存在一张用户表：

```text
user
├── id = 1
├── id = 2
├── id = 3
└── id = 4
```

现在两个事务同时修改两条不同的记录：

```sql
-- 事务 A
UPDATE user SET age = 20 WHERE id = 1;

-- 事务 B
UPDATE user SET age = 25 WHERE id = 2;
```

**MyISAM 是表级锁**，事务 A 要改数据得先把整张表锁住，事务 B 即使只想改 id = 2，也必须等 A 放锁，两条本来互不相干的修改被迫排队，写操作一多就是锁竞争。**InnoDB 是行级锁**，A 锁住 id = 1 这条记录，B 锁住 id = 2，两条记录互不影响，可以并发执行，锁冲突自然就少了。

⚠️ 需要注意，**InnoDB 支持行级锁，不代表任何 SQL 都只会锁住一行**。实际锁多大范围，还要看有没有走索引、查询条件怎么写、当前隔离级别是什么。查询条件没走索引的时候，行锁是可能退化成锁全表的。

---

## **四、支持 MVCC，提高读写并发能力 ⭐⭐⭐⭐⭐**

MVCC 全称 Multi-Version Concurrency Control，即多版本并发控制。核心思想是：**给一行数据保留多个版本，让普通 SELECT 去读历史版本，不用等着正在改这行数据的写事务提交。**

例如事务 A 正在修改用户信息还没提交，事务 B 此时来查用户信息，读的是符合可见性规则的那个版本，不必等事务 A，读和写就能同时进行。

InnoDB 实现 MVCC 主要靠三样东西：

- **Undo Log**：提供历史版本所需的信息
- **Read View**：判断某个数据版本对当前事务是否可见
- **隐藏字段**：记录事务 ID 和回滚指针，用来追踪记录的各个版本

不过需要注意：**MVCC 只服务于普通 SELECT 的一致性读（快照读），并不代表所有读操作都不加锁**。比如

```sql
SELECT * FROM user WHERE id = 1 FOR UPDATE;
```

这种属于当前读，是实实在在加锁的，同样要考虑锁竞争。

---

## **五、支持崩溃恢复，提高数据可靠性**

假设数据库正在修改订单数据，服务器突然断电，数据会不会丢？InnoDB 靠的是完整的事务日志机制，其中最重要的就是 **Redo Log 和 Undo Log**。

**1. Redo Log —— 用来做崩溃恢复。** InnoDB 修改数据时并不是每次都直接写磁盘上的数据文件，而是先改内存里的数据页（Buffer Pool），同时把"改了什么"记进 Redo Log。事务提交时不需要等所有脏页都刷回磁盘，顺序是：**修改数据 → 改 Buffer Pool 中的数据页 → 记录 Redo Log → 事务提交 → 后续再把脏页刷入磁盘**。这样即使数据库异常崩溃，重启后也能拿持久化的 Redo Log，把那些已经提交但还没写进数据文件的修改重新做一遍。当然具体的持久性还受日志刷盘配置等因素影响。

**2. Undo Log —— 用来回滚和支撑 MVCC。** 它的两个用途：事务回滚、给 MVCC 提供历史版本。比如

```sql
START TRANSACTION;

UPDATE user SET age = 30 WHERE id = 1;

ROLLBACK;
```

执行 `ROLLBACK` 的时候，InnoDB 就是根据 Undo Log 里的信息把这次修改撤销掉，age 回到改动之前的值。

也就是说，相比 MyISAM，InnoDB 的事务恢复能力是一整套完整的机制，而不是只保证"写完不报错"。

---

## Q：MySQL 为什么选择 InnoDB 作为默认存储引擎？

面试口述版，按四点讲：

1. **事务**：InnoDB 支持事务，通过 ACID 保证数据一致性；MyISAM 不支持事务，多条 SQL 出问题没法回滚。
2. **行级锁**：InnoDB 是行级锁，MyISAM 是表级锁。并发修改不同记录时行锁不会互相阻塞，并发性能明显更好。
3. **MVCC**：InnoDB 通过 Undo Log 和 Read View 实现多版本并发控制，普通查询在一定条件下不需要等写事务。
4. **日志机制 + 外键**：Redo Log 负责崩溃恢复、Undo Log 负责回滚和 MVCC，事务恢复能力完整，另外还支持外键约束。

所以 MySQL 从 5.5.5 版本开始把默认存储引擎改成 InnoDB——事务一致性、并发性能、数据可靠性这三方面，它都比 MyISAM 更适合现代业务系统。

### **最后总结**

记住 InnoDB 的 **5 个核心优势**：

**① 事务：** 支持 ACID，保证事务操作的可靠性。

**② 行级锁：** 降低锁竞争，提高并发能力。

**③ MVCC：** 提高读写并发性能。

**④ Redo Log + Undo Log：** 支持崩溃恢复和事务回滚。

**⑤ 外键约束：** 保证关联数据的引用完整性。

一句话概括：**事务支持、高并发控制、数据恢复能力**，这三块就是 InnoDB 被选为默认引擎的底气。
