
- String：底层使用简单动态字符串（SDS），支持动态扩容，记录长度和空闲空间，保证二进制安全。
- List：底层使用快速列表（quicklist），结合了 listpack 和双向链表。当元素较少且较小时使用压缩列表，否则转换为双向链表。
- Hash：底层使用压缩列表或哈希表。当元素少且键值对较小时用 listpack ，否则用哈希表。
- Set：底层使用整数集合（intset）或哈希表。当所有元素都是整数且数量较少时用整数集合，否则用哈希表。
- Zset：当元素少时用 listpack，否则用跳表（有序）和哈希表（存储分值）配合。


Redis 的五种基本数据类型，你已经知道它们分别使用 SDS、quicklist、dict、intset、skiplist 等底层结构了。

## **一、先理解：Redis 数据类型和底层编码不是一回事**

例如：

```redis
SET name "Eason"
```

从使用者的角度看，`name` 是一个 String 类型。

但 Redis 内部并不是直接把所有 String 都以同一种形式保存。

Redis 会根据数据特点选择不同的编码。

可以这样理解：

```text
Redis 对外的数据类型
        │
        ▼
String / List / Hash / Set / Zset
        │
        ▼
Redis 根据数据特点选择底层编码
        │
        ▼
SDS / quicklist / dict / intset / listpack / skiplist
```

就像 Java 中：

```java
List<String> list = new ArrayList<>();
```

`List` 是对外提供的接口，`ArrayList` 是具体实现。

Redis 的逻辑类型和内部编码也可以这样类比，不过它们并不是 Java 那种接口继承关系。

# **二、String：为什么使用 SDS？**

### **1. 普通字符串有什么问题？**

我们知道，C 语言中的字符串通常使用字符数组保存：

```c
char str[] = "hello";
```

底层类似：

```text
h  e  l  l  o  \0
```

`\0` 表示字符串结束。

如果想知道字符串长度，需要从头遍历，直到遇到 `\0`。

因此，获取长度的时间复杂度为 **O(n)**。

另外，如果字符串中包含 `\0`，传统 C 字符串函数可能将其误认为字符串结束。

### **2. Redis 的 SDS 怎么解决？**

Redis 使用 SDS（Simple Dynamic String，简单动态字符串）。

可以将它简化理解为：

```text
SDS
┌────────────┬────────────┬────────────────┐
│ len        │ alloc      │ buf            │
├────────────┼────────────┼────────────────┤
│ 5          │ 10         │ hello          │
└────────────┴────────────┴────────────────┘
```

其中：

- `len`：当前字符串的实际长度。
- `alloc`：缓冲区的容量。
- `buf`：真正存储字符串数据的数组。

例如：

```redis
SET name "hello"
```

Redis 不需要遍历整个字符串就能获取长度，因为 SDS 已经记录了 `len`。

**获取 SDS 长度的时间复杂度为 O(1)。**

### **3. 为什么 SDS 支持动态扩容？**

假设当前字符串为：

```text
hello
```

现在执行：

```redis
APPEND name "world"
```

如果原来的缓冲区空间不足，Redis 就需要申请更大的内存空间。

SDS 通过动态扩容，减少频繁重新分配内存的开销。

另外，SDS 使用明确的长度字段，因此即使数据中包含 `\0`，也能正确保存。

这就是所谓的**二进制安全**。

### **4. 一个容易忽略的细节**

Redis String 的对象编码还包括：

|**编码**|**使用场景**|
|---|---|
|int|可以用整数形式保存的值|
|embstr|较短的字符串|
|raw|较长的字符串|

其中 `embstr` 和 `raw` 都与 SDS 有关，但内存分配方式不同。

**面试总结：SDS 通过记录长度和容量，实现 O(1) 获取长度、动态扩容以及二进制安全。**

# **三、List：为什么使用 quicklist？**

List 是有序列表，支持从两端插入和删除元素。

例如：

```redis
LPUSH tasks "task1"
LPUSH tasks "task2"
RPUSH tasks "task3"
```

现在 Redis 需要保存：

```text
task2 → task1 → task3
```

这里有一个问题：

**如果使用普通数组，插入删除可能需要移动元素；如果使用普通链表，每个节点又需要额外的指针空间。**

Redis 因此采用 quicklist。

## **1. quicklist 是什么？**

可以把 quicklist 理解为：

**双向链表 + 每个节点内部存储一批元素。**

Redis 7 中，每个节点内部通常使用 listpack。

```text
                  quicklist

       ┌─────────────────────┐
       │                     ▼
┌───────────────┐     ┌───────────────┐
│  节点 A        │ ⇄   │  节点 B       │
│               │     │               │
│  listpack     │     │  listpack     │
│ ┌───┬───┬───┐ │     │ ┌───┬───┬───┐ │
│ │ 1 │ 2 │ 3 │ │     │ │ 4 │ 5 │ 6 │ │
│ └───┴───┴───┘ │     │ └───┴───┴───┘ │
└───────────────┘     └───────────────┘
```

你可以把它想象成一列火车：

- 整列火车就是 quicklist。
- 每节车厢就是一个链表节点。
- 每节车厢里面装着多个元素。

### **2. 为什么不直接使用双向链表？**

假设 List 中有 10000 个元素。

如果每个元素都是一个独立的双向链表节点：

```text
元素1 ⇄ 元素2 ⇄ 元素3 ⇄ ... ⇄ 元素10000
```

每个节点都需要保存前驱指针和后继指针。

当元素很小时，这些指针带来的额外内存开销就比较明显。

quicklist 把多个元素放在一个紧凑的 listpack 中：

```text
节点1：[1,2,3,4,5]
节点2：[6,7,8,9,10]
```

这样可以减少链表节点数量，节省内存。

同时，由于节点之间仍然是双向链表，List 依然能够高效地从两端操作。

### **3. 为什么不全部使用 listpack？**

因为 listpack 是连续内存结构。

如果所有元素都存储在一个巨大的 listpack 中，插入和删除可能需要移动大量数据。

quicklist 将数据拆分到多个节点中，可以避免每次操作都影响整个列表。

**面试总结：quicklist 将双向链表与紧凑存储结构结合，在节省内存的同时保持较高的两端操作效率。**

注意：quicklist 并不是简单地在元素变多后转换成普通双向链表。Redis 7 的 List 主要采用 quicklist 编码，内部节点使用 listpack。

# **四、Hash：为什么使用 listpack 和 dict？**

Hash 用于保存字段与值的映射。

例如：

```redis
HSET user:1 name "Eason" age "20" city "Hangzhou"
```

逻辑结构：

```text
user:1
  │
  ├── name → Eason
  ├── age  → 20
  └── city → Hangzhou
```

Redis 需要考虑两种情况。

### **情况一：Hash 很小**

假设只有三个字段：

```text
name → Eason
age  → 20
city → Hangzhou
```

如果直接使用哈希表，每个字段都需要相应的哈希表结构和指针等开销。

对于只有几个字段的小 Hash，这些额外开销可能不划算。

所以 Redis 可以使用 **listpack**。

```text
listpack
┌──────┬───────┬─────┬────┬──────┬──────────┐
│ name │ Eason │ age │ 20 │ city │ Hangzhou │
└──────┴───────┴─────┴────┴──────┴──────────┘
```

listpack 将字段和值紧凑地存储在连续内存中。

优点是节省内存。

缺点是查找某个字段时，通常需要顺序扫描，时间复杂度为 **O(n)**。

但因为元素数量很少，所以扫描成本可以接受。

### **情况二：Hash 很大**

假设一个 Hash 中有 10000 个字段。

如果继续使用 listpack，查找字段就可能需要遍历大量元素。

这时 Redis 会使用 **哈希表**。

```text
dict
        │
        ▼
    哈希桶数组
┌──────────────────┐
│ bucket[0] ──→ ...│
│ bucket[1] ──→ ...│
│ bucket[2] ──→ ...│
│ bucket[3] ──→ ...│
└──────────────────┘
```

通过哈希函数计算字段对应的桶位置，平均情况下可以实现 O(1) 查找。

你可以将它类比为 Java 的 `HashMap`。

不过，Redis dict 的具体结构与 Java HashMap 不完全相同。

### **什么时候转换？**

Redis 7 中，Hash 默认使用 listpack 的典型条件是：

- 字段数量不超过 512。
- 字段和值的长度都不超过 64 字节。

对应配置：

```text
hash-max-listpack-entries 512
hash-max-listpack-value 64
```

超过相应限制后，通常会转换为 hashtable 编码。

**面试总结：Hash 数据量小时使用 listpack 节省内存，数据量大时使用 dict 提高查找效率。**

# **五、Set：为什么使用 intset 和 dict？**

Set 的特点是：

**元素无序，并且不允许重复。**

例如：

```redis
SADD user:ids 1001 1002 1003
```

## **1. intset：整数集合**

假设 Set 中全部是整数：

```text
1001、1002、1003
```

Redis 可以使用 intset：

```text
intset
┌──────┬──────┬──────┐
│ 1001 │ 1002 │ 1003 │
└──────┴──────┴──────┘
```

intset 的底层是**有序的整数数组**。

为什么要保持有序？

因为可以通过二分查找判断元素是否存在。

查询时间复杂度为 O(log n)。

不过，插入和删除可能需要移动数组元素，时间复杂度为 O(n)。

### **2. 为什么整数集合更省内存？**

假设需要存储：

```text
1、2、3、4、5
```

如果使用普通哈希表，需要维护哈希表结构、节点等信息。

而 intset 可以直接紧凑地存储整数。

另外，intset 会根据整数范围选择不同的整数宽度，例如 16 位、32 位或 64 位。

如果原本存储的都是小整数，后来加入一个较大的整数，intset 可能需要升级编码宽度。

### **3. dict：哈希表**

如果加入字符串：

```redis
SADD user:ids "hello"
```

intset 无法保存普通字符串，因此 Redis 可能转换为哈希表。

```text
Set
 │
 ▼
dict
 ├── 1001
 ├── 1002
 ├── 1003
 └── hello
```

这里有个重要细节：

**Set 使用哈希表时，元素通常存储在哈希表的 Key 中，而不需要为每个元素保存有业务意义的 Value。**

类似于 Java 的 `HashSet` 底层使用 `HashMap`。

### **4. Redis 7 的补充**

Redis 7.2 开始，Set 还引入了 **listpack 编码**，用于存储满足条件的小型非整数集合。

因此，最新版本的 Set 不能只记成 intset 和 dict 两种编码。

**面试总结：Set 使用 intset 紧凑存储小型整数集合，使用哈希表实现高效查找和去重；较新的 Redis 还支持 listpack 编码。**

# **六、Zset：为什么同时需要跳表和哈希表？⭐⭐⭐⭐⭐**

这是五种数据类型中最值得深入理解的一个。

Zset（Sorted Set）是有序集合。

每个元素都有一个 Score（分数），Redis 根据分数进行排序。

例如：

```redis
ZADD ranking 100 "Tom"
ZADD ranking 200 "Jack"
ZADD ranking 150 "Eason"
```

结果：

```text
Tom    → 100
Eason  → 150
Jack   → 200
```

现在 Redis 需要同时满足两个需求：

**① 根据分数排序，支持范围查询。**

例如：

```redis
ZRANGE ranking 0 -1
```

**② 根据成员快速查找对应分数。**

例如：

```redis
ZSCORE ranking "Eason"
```

如果只使用哈希表，无法高效维护排序。

如果只使用跳表，根据成员查找分数又不够高效。

所以 Redis 使用：

**跳表（skiplist）+ 哈希表（dict）。**

## **1. 跳表是什么？**

先看普通有序链表：

```text
10 → 20 → 30 → 40 → 50 → 60 → 70 → 80
```

如果要查找 70，就需要从头逐个查找。

时间复杂度为 O(n)。

跳表通过增加多层索引提高查找效率。

```text
第 3 层：10 ────────────────→ 50
         │                    │
第 2 层：10 ──────→ 30 ──────→ 50 ──────→ 70
         │          │          │          │
第 1 层：10 → 20 → 30 → 40 → 50 → 60 → 70 → 80
```

假设要查找 70：

先从最高层开始：

```text
10 → 50
```

再向下一层：

```text
50 → 70
```

就找到了目标。

**跳表通过多层索引，让查找、插入、删除在平均情况下达到 O(log n)。**

这和 MySQL 的 B+ 树一样，都是为了减少查找过程中需要访问的节点数量，但两者结构不同。

## **2. 为什么还需要 dict？**

假设现在要查询：

```redis
ZSCORE ranking "Eason"
```

如果只有跳表，Redis 主要按照 Score 排序，无法直接通过成员名称快速定位。

因此需要哈希表：

```text
dict
┌─────────┬───────┐
│ Member  │ Score │
├─────────┼───────┤
│ Tom     │ 100   │
│ Eason   │ 150   │
│ Jack    │ 200   │
└─────────┴───────┘
```

这样可以通过 Member 快速找到 Score，平均时间复杂度为 O(1)。

而跳表负责排序：

```text
skiplist

Tom(100) → Eason(150) → Jack(200)
```

两者配合：

|**操作**|**主要依赖的数据结构**|**时间复杂度**|
|---|---|---|
|根据 Member 查 Score|dict|平均 O(1)|
|根据 Score 范围查询|skiplist|O(log n + m)|
|按排名查询|skiplist|O(log n + m)|
|插入元素|dict + skiplist|平均 O(log n)|

其中 m 表示返回的元素数量。

需要注意，dict 和 skiplist 是同一个 Zset 的两种索引结构，并不是存储两套完全独立的成员字符串。

## **3. 为什么小 Zset 不使用跳表？**

如果只有几个元素：

```text
Tom(100)
Jack(200)
Eason(150)
```

使用跳表和哈希表会带来额外内存开销。

因此 Redis 7 默认使用 listpack 保存较小的 Zset。

当数据规模超过限制时，再转换为 skiplist 编码。

默认配置通常为：

```text
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

也就是说，当成员数量较少、成员长度较小时，使用 listpack 更节省内存。

**面试总结：Zset 小数据量时使用 listpack，大数据量时使用跳表加哈希表。跳表负责排序和范围查询，哈希表负责根据成员快速查询分数。**

# **七、五种类型放在一起理解**

|**Redis 类型**|**主要底层编码（Redis 7 系列）**|**为什么这样设计**|
|---|---|---|
|String|int、embstr、raw（字符串使用 SDS）|高效存储字符串，支持动态扩容|
|List|quicklist + listpack|兼顾两端操作效率与内存占用|
|Hash|listpack、dict|小数据节省内存，大数据快速查找|
|Set|intset、dict；7.2+ 还有 listpack|整数紧凑存储，哈希快速去重|
|Zset|listpack、skiplist + dict|兼顾排序、范围查询和成员查找|

你可以发现一个规律：

**Redis 的底层结构不是单纯追求时间复杂度最低，而是在时间复杂度与内存占用之间做权衡。**

例如：

- listpack：节省内存，但查找通常需要遍历。
- dict：查找快，但需要额外的哈希表结构。
- skiplist：有序查找快，但需要多层索引。
- quicklist：把多个元素紧凑存储，同时保留链表的两端操作优势。

---

## **八、面试怎么回答？**

Redis 五种基本数据类型的底层实现有所不同。

String 主要使用 SDS 保存字符串，通过记录长度和容量，实现 O(1) 获取长度、动态扩容和二进制安全。

List 使用 quicklist，结合双向链表和 listpack，在保证两端操作效率的同时减少内存开销。

Hash 在数据量较小时使用 listpack，节省内存；数据量较大时使用 dict，通过哈希表提高查找效率。

Set 对于小型整数集合可以使用 intset，通过有序整数数组节省空间；其他情况可以使用哈希表。

Zset 在数据量较小时使用 listpack，数据量较大时使用跳表和哈希表。跳表负责按照 Score 排序和范围查询，哈希表负责根据 Member 快速查找 Score。

Redis 采用多种底层编码，主要是为了根据数据规模，在内存占用和操作性能之间取得平衡。
