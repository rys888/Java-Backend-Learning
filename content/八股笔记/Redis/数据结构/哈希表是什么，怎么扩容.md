
[[#Q：]]

**Redis 哈希表扩容 = 创建一张更大的表 + 把旧表数据重新散列过去 + 为了不阻塞改成渐进式迁移 + 迁完释放旧表。**

Redis 的哈希表扩容主要依靠 **Rehash（重新哈希）**。因为一次性迁移大量数据会让 Redis 阻塞，所以又引入了**渐进式 Rehash**，把迁移工作打散到多次操作里完成。

在讲扩容之前，先分清三个容易混的东西：**Redis 是一个数据库，String / Hash / List 这些是 Redis 的数据类型，而 HashTable（哈希表）是 Redis 底层的数据结构。** 类比一下 MySQL，InnoDB 定位数据靠 B+ 树，Redis 定位 Key 靠哈希表。也就是说，哈希表回答的是"Redis 怎么找到这个 Key"，跟"这个 Value 是什么类型"完全是两回事。

### **一、为什么哈希表需要扩容？**

假设 Redis 的哈希表有 4 个桶：

```text
哈希表（4个桶）

0 → A
1 → B → C
2 → D
3 → E → F
```

要搞清楚桶里装的到底是什么，得先回到 Redis 的存储模型：**Redis 的 String、List、Hash、Set、ZSet 都遵循 Key-Value（键值对）存储模式。** 一个 Redis Key 对应一个 Value，而这个 Value 内部还可以继续包含多个 Field-Value 键值对。

```text
Redis 数据库
│
├── name    → "Eason"                  String
│
├── hobbies → ["Java", "Python"]       List
│
├── user:1  → {name:"Eason", age:20}   Hash
│
├── likes   → {1001, 1002, 1003}       Set
│
└── ranking → {Tom:100, Jack:200}      ZSet
```

所以上面图示里的 A、B、C、D、E、F 可以是 String，也可以是 List 之类的东西，反正都是 Key-Value 键值对，通过哈希算法被放进哈希表的某个桶里。落桶规则是 **桶下标 = 哈希值 % 桶数量**：

```text
hash("name") = 10
hash("age")  = 5
hash("city") = 9
```

4 个桶时取模，name 落到 2 号桶，age 和 city 都落到 1 号桶。age 和 city 撞到同一个桶，这就是**哈希冲突**。

回到问题本身：为什么需要扩容？因为存的元素越来越多，哈希冲突就越来越频繁，多个 Key 落进同一个桶就会形成链表，**链表过长会降低查询效率，所以需要扩容。**

顺带一提，哈希表并不是 Redis 里唯一的结构。Redis 找 Key 用哈希表，其他延伸操作（比如排序）可以用别的结构，比如跳表；MySQL 也一样，定位数据用 B+ 树，延伸操作用 Buffer Pool 这类东西。

### **二、Redis 哈希表怎么扩容？**

扩容的思路很直接：**新建一张容量更大的哈希表，把旧表的数据迁移过去。**

```text
扩容前：4个桶

0 → A
1 → B → C
2 → D
3 → E → F
```

```text
扩容后：8个桶

0 → A
1 → B
2 → C
3 → D
4 → E
5 → F
6 → null
7 → null
```

⚠️ 这里只是示意，元素实际落到哪个桶由哈希值和新表容量共同决定。

扩容过程：

1. 创建新的哈希表，通常扩容为原来的 2 倍。
2. 重新计算每个元素在新表中的位置。
3. 把旧哈希表的数据迁移到新表。
4. 迁移完成后释放旧哈希表。

但这里存在一个问题：**如果哈希表中有几百万个元素，一次性迁移可能导致 Redis 长时间阻塞。** 所以 Redis 引入了渐进式 Rehash。

### **三、什么是渐进式 Rehash？

核心就一句话：**不一次性迁移所有数据，而是把迁移任务分散到多次操作中完成。**

Rehash 过程中，Redis 的哈希表会同时维护两张表：**ht[0] 是旧哈希表，ht[1] 是新哈希表。**

第一步，创建新哈希表：

```text
ht[0]（旧表）        ht[1]（新表）

0 → A                0 → null
1 → B → C            1 → null
2 → D                2 → null
3 → E → F            3 → null
                     4 → null
                     5 → null
                     6 → null
                     7 → null
```

第二步，逐步迁移数据。Redis 用 **rehashidx** 记录迁移进度，每次只迁移一部分桶，而不是一次把整张表搬过去。

```text
ht[0]（旧表）        ht[1]（新表）

0 → null             0 → A
1 → null             1 → B
2 → D                2 → C
3 → E → F            3 → null
                     4 → null
                     5 → null
                     6 → null
                     7 → null
```

第三步，迁移期间的读写怎么处理？这一步是渐进式 Rehash 的关键，因为数据同时散落在两张表里：

- **查询**：先查旧表 ht[0]，找不到再查新表 ht[1]。
- **新增**：直接写入新表 ht[1]。
- **删除**：找到元素所在的表后删除。
- **更新**：找到元素所在的表后更新。

与此同时，Redis 会利用部分哈希表操作和定时任务推进迁移。

第四步，迁移完成：旧表数据全部迁完后，释放旧表，新表成为正式使用的哈希表。

### **四、Redis 什么时候触发扩容？**

Redis 用**负载因子（Load Factor）** 衡量哈希表的拥挤程度：**负载因子 = 元素数量 / 桶数量**。

常见扩容条件：

- **负载因子 ≥ 1**：没有正在进行的后台持久化子进程时，通常可以触发扩容。
- **负载因子 ≥ 5**：即使存在相关后台持久化子进程，也可以触发扩容。

阈值要跟持久化挂钩，是因为后台子进程本身就在消耗资源，这时候再来一次大规模迁移，性能会更糟，所以条件被放宽了。

注意，这是 Redis 经典字典实现中的扩容策略，不同 Redis 版本的具体实现可能存在差异。

### Q：

Redis 哈希表通过 Rehash 实现扩容。当负载因子达到一定阈值时，Redis 会创建一个更大的哈希表，将旧表的数据重新计算位置并迁移过去。

为了避免一次性迁移大量数据造成阻塞，Redis 采用渐进式 Rehash。具体来说，Redis 会同时维护新旧两张哈希表，通过 rehashidx 记录迁移进度，将迁移工作分散到多次操作中完成。在迁移期间，新增数据直接写入新表，查询需要兼顾新旧两张表。迁移完成后，释放旧表。

**Redis 哈希表扩容 = 创建新表 + 渐进式迁移 + 新旧表共存 + 释放旧表。**
