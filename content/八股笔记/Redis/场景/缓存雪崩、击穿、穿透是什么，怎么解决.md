
[[#Q：]]

Redis 的**缓存雪崩、缓存击穿、缓存穿透**是后端面试的三个高频问题。

它们有一个共同点：**大量请求没有命中 Redis，最后都打到 MySQL 上，导致数据库压力骤增。** 但三者的原因完全不一样——缓存雪崩是大量 Key 同时失效，或者 Redis 整体不可用；缓存击穿是某一个热点 Key 突然失效；缓存穿透是查的数据在 Redis 和 MySQL 里压根不存在。

## 一、缓存雪崩（Cache Avalanche）

### 1. 什么是缓存雪崩？

假设电商系统有 10 万个商品缓存，过期时间都设成 30 分钟。整条链路是：**10 万个商品 Key → TTL 都是 30 分钟 → 30 分钟后大量 Key 同时过期 → Redis 缓存大量未命中 → 大量请求访问 MySQL → MySQL 压力骤增，甚至宕机。**

这就是缓存雪崩。另外，Redis 服务突然宕机，大量请求没法访问缓存，同样会引发雪崩。

### 2. 怎么解决？

**① 给 TTL 加随机值（最常用）**

核心就是不要让大量 Key 在同一时间过期。原来写死 30 分钟：

```java
redisTemplate.opsForValue().set(
    key, value, 30, TimeUnit.MINUTES
);
```

改成在 30 的基础上随机加 1～10 分钟：

```java
int ttl = 30 + ThreadLocalRandom.current().nextInt(1, 11);

redisTemplate.opsForValue().set(
    key, value, ttl, TimeUnit.MINUTES
);
```

这里 `ThreadLocalRandom.current().nextInt(1, 11)` 取的是 [1, 11) 之间的整数，也就是 1～10。这样过期时间就散落在 31～40 分钟之间，集中失效的概率大大降低。

**② Redis 高可用**：用 Redis Sentinel 或者 Redis Cluster，避免单点宕机直接把整个缓存层打没。

**③ 限流与降级**：Redis 不可用的时候，限制打进 MySQL 的请求数量，别让数据库跟着一起崩。

**④ 缓存预热**：系统启动或者大型活动开始之前，提前把热点数据加载进 Redis，不要等第一个请求进来才去查数据库。

## 二、缓存击穿（Cache Breakdown）

### 1. 什么是缓存击穿？

缓存击穿指的是**某个访问量非常大的热点 Key 突然过期，大量并发请求同一时间打到 MySQL**。比如热门商品 `product:1001` 每秒有 100000 次请求，全都打在 Redis 上，Key 一过期，这些请求就同时去查 MySQL，数据库压力骤增。

⚠️ 注意区分：**缓存击穿针对的是单个热点 Key，缓存雪崩针对的是大量 Key 或者整个缓存服务。**

### 2. 怎么解决？

主要有两种方案。

#### 方案一：互斥锁（最常用）

核心思想是**缓存失效时只让一个线程去查 MySQL 并重建缓存，其他线程等着**。

```
             10000 个请求
                   │
                   ▼
                Redis
                   │
                缓存未命中
                   │
                   ▼
               尝试获取锁
                   │
          ┌────────┴────────┐
          ▼                 ▼
      线程 A 获取锁      其他线程获取失败
          │                 │
          ▼                 ▼
       查询 MySQL        等待并重试缓存
          │
          ▼
       重建 Redis 缓存
          │
          ▼
         释放锁
```

原本 10000 个请求会一起查 MySQL，加锁之后实际上只有一个线程负责重建缓存。伪代码：

```java
public Product queryProduct(Long id) {

    String key = "product:" + id;

    // 1. 查询 Redis
    Product product = getFromRedis(key);

    if (product != null) {
        return product;
    }

    // 2. 获取分布式锁
    RLock lock = redissonClient.getLock("lock:product:" + id);

    lock.lock();

    try {
        // 3. 双重检查
        product = getFromRedis(key);

        if (product != null) {
            return product;
        }

        // 4. 查询 MySQL
        product = productMapper.selectById(id);

        // 5. 重建缓存
        saveToRedis(key, product);

        return product;

    } finally {
        lock.unlock();
    }
}
```

这里最关键的一步是**拿到锁之后必须再查一次 Redis**。因为等锁的这段时间里，其他线程可能已经把缓存重建好了，直接返回就行，不用再查一遍 MySQL。这就是第 3 步那个"双重检查"的作用。上面的代码只保留了核心流程，真实项目里还要处理数据库查不到记录、锁等待超时、缓存重建失败这些情况。

#### 方案二：逻辑过期

逻辑过期就是**不靠 Redis 的 TTL 去删热点数据，而是在 Value 里自己存一个逻辑过期时间**：

```json
{
  "data": {
    "id": 1001,
    "name": "iPhone"
  },
  "expireTime": "2026-10-14 20:00:00"
}
```

读取流程：

```
查询 Redis
    │
    ▼
检查逻辑过期时间
    │
    ├── 未过期 → 直接返回
    │
    └── 已过期
          │
          ▼
       尝试获取锁
          │
          ├── 成功 → 异步重建缓存
          │
          └── 失败 → 返回旧数据
```

这样做的好处是**即使逻辑上已经过期，用户仍然能拿到旧数据，不用都堵在 MySQL 上**。缺点也很明显：**可能返回过期数据，保证不了强一致性**。所以它适合热门商品详情、热门文章这种允许短暂不一致的场景。

## 三、缓存穿透（Cache Penetration）

### 1. 什么是缓存穿透？

缓存穿透指的是**客户端查询的数据在 Redis 和 MySQL 中都不存在，每次请求都绕过缓存直接打到数据库**。比如数据库里的商品 ID 只到 1～10000，但有人一直请求 `GET /product/99999999`、`GET /product/88888888`、`GET /product/77777777` 这种不存在的 ID，请求走到 Redis 发现缓存不存在，再走到 MySQL 发现数据也不存在，返回 null。下一次请求同一个不存在的商品，Redis 里还是不存在，又查一遍 MySQL。如果有人恶意发送大量不存在的 ID，MySQL 压力就上来了。

### 2. 怎么解决？

#### 方案一：缓存空值（最常用）

当 MySQL 查不到数据时，把这个"空"也缓存到 Redis，TTL 一般设得比较短，比如 2 分钟。下次再查同一个 key，直接命中空值缓存返回，不会再访问 MySQL。

⚠️ 注意：**空值缓存的 TTL 之所以设得短，是因为现在不存在的数据之后可能被创建出来。** 另外，大量不同的无效 ID 还是会把缓存撑大，所以空值缓存挡不住真正的恶意穿透。

#### 方案二：布隆过滤器（Bloom Filter）

布隆过滤器是一种空间效率比较高的概率型数据结构，可以很快判断**某个元素是否可能存在于集合中**。比如商品 ID 有 1、2、3、4、5，先全部记录进布隆过滤器。这时候来了个 `product:999999` 的请求，布隆过滤器判断不存在，直接拒绝请求，连 Redis 和 MySQL 都不用碰；如果判断可能存在，才会继续往下走：**布隆过滤器 → Redis（未命中）→ MySQL**。

⚠️ 这里有个很重要的点：**布隆过滤器会误判，但正常不会漏判**。也就是说判断不存在就一定不存在（前提是过滤器维护正确），判断存在则不一定真的存在。所以它很适合用来挡大量无效请求，代价是要额外处理新数据写入后的过滤器更新，以及数据删除的问题。

## 四、三者的核心区别

|**对比**|**缓存雪崩**|**缓存击穿**|**缓存穿透**|
|---|---|---|---|
|核心原因|大量缓存同时失效|单个热点 Key 失效|查询的数据根本不存在|
|涉及 Key|大量 Key|单个或少数热点 Key|不存在的 Key|
|Redis 状态|大量缓存未命中或不可用|热点缓存未命中|一直无法缓存有效数据|
|MySQL 压力|大量请求同时涌入|热点请求集中涌入|无效请求持续访问|
|主要解决方案|随机 TTL、高可用|互斥锁、逻辑过期|缓存空值、布隆过滤器|

### 用一个例子理解

假设有一个商品查询系统：**缓存雪崩**是 10000 个商品的缓存同时过期，大量商品查询请求一起访问 MySQL；**缓存击穿**是 iPhone 这个热门商品的缓存突然过期，10 万个请求同时访问 MySQL；**缓存穿透**是有人不断查询商品 ID 为 99999999 的商品，但这个商品在 Redis 和 MySQL 中都不存在。

## Q：

面试如果被问到，可以这样答：

Redis 的缓存雪崩、击穿和穿透，都会导致大量请求绕过缓存访问数据库，但产生原因不同。

**缓存雪崩**是大量 Key 同时过期，或者 Redis 整体不可用。一般通过随机 TTL、Redis 高可用（Redis Sentinals, Redis Cluster）、缓存预热（将热点数据加载进 Redis）和限流降级（当 Redis 不可用，限制打进 MySQL 的服务适量）解决。

**缓存击穿**是某个热点 Key 突然过期，导致大量并发请求同时访问 MySQL。一般通过互斥锁控制缓存重建，或者通过逻辑过期返回旧数据并异步重建缓存。

**缓存穿透**是查询的数据在 Redis 和 MySQL 中都不存在，导致请求不断访问数据库。一般通过缓存空值或者布隆过滤器解决。

实际项目中一般会根据不同场景组合使用这些方案，而不是统一采用某一种方式。
