
Redis 实现限流（Rate Limiting），核心思想是：**利用 Redis 的原子操作，限制某个用户或接口在单位时间内能够发起的请求数量。**

例如：

限制每个用户每分钟最多发送 5 次短信验证码，超过次数直接拒绝请求。

Redis 常见的限流算法有四种：

1. 固定窗口计数器
2. 滑动窗口
3. 令牌桶**

## 一、固定窗口计数器 

### **1. 实现原理**

假设要求：

**每个用户在 60 秒内最多发送 5 次验证码。**

可以使用 Redis 的 `INCR` 和 `EXPIRE`。

```text
用户发送验证码
       │
       ▼
Redis INCR 计数
       │
       ▼
判断请求次数
       │
       ├── ≤ 5 → 放行
       │
       └── > 5 → 拒绝
```

例如：

```redis
INCR sms:limit:user:1001
EXPIRE sms:limit:user:1001 60
```

每次请求，计数器加 1。

|**请求次数**|**Redis 计数**|**结果**|
|---|---|---|
|第 1 次|1|放行|
|第 2 次|2|放行|
|第 3 次|3|放行|
|第 4 次|4|放行|
|第 5 次|5|放行|
|第 6 次|6|拒绝|

### **2. 为什么需要 Lua 脚本？**

因为 `INCR` 和 `EXPIRE` 是两条命令。

假设：

```text
① INCR 执行成功
② 服务突然宕机
③ EXPIRE 没有执行
```

那么这个 Key 可能永远不会过期。

因此，可以使用 Lua 脚本保证计数和设置过期时间的原子性：

```lua
local count = redis.call('INCR', KEYS[1])

if count == 1 then
    redis.call('EXPIRE', KEYS[1], 60)
end

if count > 5 then
    return 0
end

return 1
```

返回 `1` 表示放行，`0` 表示限流。

注意，这个示例采用**首次请求开始计时的固定时长窗口**，不是严格按自然分钟划分的窗口。超过阈值的请求仍会增加计数，但不会延长过期时间。

### **3. 固定窗口有什么缺点？**

**存在窗口边界问题。**

例如限制每分钟最多 5 次请求：

```text
12:00:00             12:01:00             12:02:00
   │                    │                    │
   │      5 次请求      │      5 次请求      │
   │    12:00:59        │    12:01:01        │
   └────────────────────┴────────────────────┘
```

如果按照自然分钟划分窗口，用户可以在：

- 12:00:59 发送 5 次请求。
- 12:01:01 再发送 5 次请求。

**结果：2 秒内发送了 10 次请求，却没有违反固定窗口的限制。**

这就是固定窗口的边界突发问题。

## 二、滑动窗口

滑动窗口就是为了解决固定窗口的边界问题。

### **1. 实现原理**

假设：

**任意连续 60 秒内，最多允许 5 次请求。**

Redis 可以使用 **ZSet（有序集合）** 实现。

你之前学过 ZSet，它可以根据 Score 对元素进行排序。

这里可以使用：

- Member：请求的唯一 ID。
- Score：请求时间戳。

例如：

```text
Key：rate:limit:user:1001

Member       Score（请求时间）
────────────────────────────
request-1    1000
request-2    2000
request-3    3000
request-4    4000
request-5    5000
```

当新请求到来时：

```text
① 删除 60 秒以前的请求记录
          │
          ▼
② 统计当前窗口内的请求数量
          │
          ▼
③ 判断是否超过 5 次
          │
    ┌─────┴─────┐
    ▼           ▼
  未超过       已达到上限
    │           │
    ▼           ▼
记录本次请求    拒绝请求
    │
    ▼
允许访问
```

### **2. Redis 如何实现？**

假设当前时间为 `1700000060000` 毫秒。

**① 删除窗口外的记录**

```redis
ZREMRANGEBYSCORE rate:limit:user:1001 -inf 1700000000000
```

**② 统计窗口内的请求数**

```redis
ZCARD rate:limit:user:1001
```

假设返回：

```text
4
```

说明当前窗口内有 4 次请求。

**③ 允许请求并记录**

```redis
ZADD rate:limit:user:1001 1700000060000 request-6
```

此时窗口内有 5 次请求。

下一次请求就会被拒绝。

实际使用时，**删除旧记录、统计数量、判断阈值和写入新记录需要通过 Lua 脚本原子执行**，否则多个并发请求可能同时判断未达到上限，导致限流失效。

此外，还需要给 ZSet 设置合理的 TTL，避免不再活跃的用户留下大量 Key。

### **3. 滑动窗口有什么优缺点？**

**优点：**

- 限流更加精确。
- 能解决固定窗口的边界突发问题。
- 适合验证码、登录接口等场景。

**缺点：**

- 需要存储窗口内的请求记录。
- 高并发下会增加 Redis 内存和操作开销。

因此，如果请求量特别大，可以考虑使用令牌桶。

## 三、令牌桶算法

令牌桶是实际项目中非常常见的限流算法。

### **1. 实现原理**

假设有一个桶：

```text
桶容量：10 个令牌
生成速度：每秒 2 个令牌
```

系统会按照固定速率向桶中补充令牌。

```text
         每秒生成 2 个令牌
                  │
                  ▼
          ┌──────────────┐
          │ ● ● ● ● ●    │
          │ ● ● ● ● ●    │
          └──────────────┘
                  │
                  ▼
             用户请求
                  │
          ┌───────┴───────┐
          ▼               ▼
       有令牌           没有令牌
          │               │
          ▼               ▼
      消耗一个令牌      拒绝或等待
          │
          ▼
        放行
```

### **2. 为什么令牌桶可以处理突发流量？**

假设：

```text
桶容量：10
补充速率：2 个/秒
```

如果系统一段时间没有请求，桶中会积累最多 10 个令牌。

此时突然来了 10 个请求：

**可以一次性放行这 10 个请求。**

之后令牌按照每秒 2 个的速度恢复。

所以令牌桶同时具有两个特点：

- **限制长期平均请求速率。**
- **允许一定程度的突发流量。**

这也是它与简单固定窗口计数器的重要区别。

### **3. Redis 怎么实现令牌桶？**

可以在 Redis 中保存：

```text
Key：rate:limit:api

tokens：当前剩余令牌数
lastRefillTime：上次补充令牌的时间
```

每次请求到来时：

1. 根据当前时间与上次补充时间，计算应该补充多少令牌。
2. 更新剩余令牌数，但不能超过桶容量。
3. 如果令牌数足够，就消耗一个令牌并放行。
4. 如果令牌不足，就拒绝请求。

这些步骤同样需要使用 Lua 脚本保证原子性。

在 Java 项目中，也可以使用 Redisson 提供的 `RRateLimiter`：

```java
RRateLimiter limiter =
        redissonClient.getRateLimiter("api:limit");

// 每秒最多补充 10 个许可
limiter.trySetRate(
        RateType.OVERALL,
        10,
        1,
        RateIntervalUnit.SECONDS
);

// 尝试获取许可
if (!limiter.tryAcquire()) {
    throw new RuntimeException("请求过于频繁");
}

// 执行业务
doBusiness();
```

这里的 `RateType.OVERALL` 表示所有使用该限流器的客户端共享限流额度。

注意：`RRateLimiter` 采用的是令牌桶类限流机制，实际突发行为还取决于具体版本和配置，不能简单理解为任何连续一秒内绝对不超过 10 次请求。

## 五、四种限流算法怎么选？

| **算法**   | **Redis 数据结构** | **优点**   | **缺点**      |
| -------- | -------------- | -------- | ----------- |
| **固定窗口** | String + INCR  | 实现简单、性能好 | 存在窗口边界问题    |
| **滑动窗口** | ZSet           | 限流精确     | 内存开销较大      |
| **令牌桶**  | Hash / Lua     | 允许突发流量   | 实现相对复杂      |

对于 Java 后端项目，我更推荐这样选择：

**场景一：短信验证码**

要求每个用户 60 秒内最多发送 5 次。

可以使用：

`Redis + Lua + 固定窗口`

如果要求任意连续 60 秒内严格限制 5 次，则选择滑动窗口。

**场景二：用户登录**  

⚠️：我的项目好像就使用了场景二的滑动窗口

要求每个用户 1 分钟内最多尝试登录 10 次。

可以使用：

`Redis ZSet + Lua + 滑动窗口`

**场景三：高并发预约接口**

要求控制整体请求速率，避免 Redis、RabbitMQ 和 MySQL 承受过大压力。

可以使用：

`Redisson RRateLimiter + 令牌桶`

但限流只是控制请求量，预约资格判断和库存扣减仍然需要 Redis Lua、数据库约束等机制保证正确性。

## Q：

Redis 实现限流主要有固定窗口、滑动窗口和令牌桶三种常见方案。

固定窗口通常使用 Redis 的 INCR 计数，并通过 EXPIRE 设置过期时间，限制单位时间内的请求次数。为了保证原子性，可以使用 Lua 脚本。

但是固定窗口存在边界突发问题，因此可以使用 ZSet 实现滑动窗口，将请求时间作为 Score，每次删除窗口外的记录，再统计当前窗口内的请求数量。

如果需要允许一定程度的突发流量，可以使用令牌桶算法，按照固定速率补充令牌，请求只有获取令牌后才能执行。

在 Java 项目中，可以直接使用 Redisson 的 RRateLimiter 实现分布式限流。

实际选择时，验证码等低频接口可以使用固定窗口或滑动窗口，高并发接口通常可以考虑令牌桶，并结合网关限流和服务降级保护系统。

### **最后总结**

**Redis 限流的核心是利用 Redis 的原子操作，让多个 Java 服务实例共享同一套限流状态。**

记住三个最重要的方案：

- **固定窗口：String + INCR + EXPIRE + Lua。**
- **滑动窗口：ZSet + 时间戳 + Lua。**
- **令牌桶：令牌补充与扣减 + Lua，或者 Redisson RRateLimiter。**

**一句话记忆：固定窗口实现简单，滑动窗口限制精确，令牌桶允许突发流量。**
