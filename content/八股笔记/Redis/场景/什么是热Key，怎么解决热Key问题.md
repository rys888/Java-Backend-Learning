
Redis 的 **Hot Key（热 Key）问题**是指：**某个 Key 在短时间内被大量请求频繁访问，导致 Redis 单个节点的 CPU、网络带宽等资源成为性能瓶颈。**

例如电商平台的普通商品 `product:1001` 是 10 QPS、`product:1002` 是 20 QPS，而热门商品 `product:9999` 是 100000 QPS。虽然 `product:9999` 只占用几 KB 内存，但每秒有 10 万次请求访问它，这就是典型的热 Key。

## **一、热 Key 和大 Key 有什么区别？**

这两个概念很容易混淆，前面学过 Redis 的 Big Key，对比一下：

|**对比**|**Big Key（大 Key）**|**Hot Key（热 Key）**|
|---|---|---|
|定义|Value 占用内存大或元素多|Key 被访问的频率高|
|核心问题|数据量太大|访问量太集中|
|主要危害|内存占用、阻塞、网络开销|CPU、网络带宽成为瓶颈|
|典型场景|一个 Hash 有 100 万个 Field|一个商品每秒被查询 10 万次|
|解决思路|拆分、分批读取、异步删除|本地缓存、Key 分散、限流|

**注意：一个 Key 可以既是 Big Key，又是 Hot Key。** 例如一个 10 MB 的商品详情 Key，每秒被读取 10 万次，就会同时存在两种问题。

---

## **二、热 Key 有什么危害？⭐⭐⭐⭐⭐**

### **① Redis 单节点性能瓶颈**

假设 Redis Cluster 有三个 Master：

```
               Java 服务
                   │
       ┌───────────┼───────────┐
       ▼           ▼           ▼
    Master A    Master B    Master C
     10 QPS      20 QPS     100000 QPS
                               │
                               ▼
                         热 Key 所在节点
```

前面学过 Redis Cluster：**Redis 通过哈希槽决定 Key 存储在哪个 Master 上**，因此一个 Key 通常只存储在一个 Master 上。即使集群有多个 Master，访问同一个热 Key 的请求仍然可能集中到一个节点。结果就是：**单节点 CPU 使用率升高，网络带宽可能被占满，请求响应时间增加，其他 Key 的访问也可能受到影响。**

### **② 可能引发缓存击穿**

假设热 Key `product:9999` 每秒有 10 万次请求访问，突然这个 Key 过期了，大量请求同时发现缓存不存在，可能一起访问 MySQL，这就是后面会学到的**缓存击穿问题**。

注意：**热 Key 不等于缓存击穿。热 Key 是访问频率高，缓存击穿是热点数据失效后大量请求穿透到数据库。**

---

## **三、如何发现热 Key？**

### **① redis-cli --hotkeys**

Redis 提供了热 Key 分析命令 `redis-cli --hotkeys`，可以帮助识别访问频繁的 Key。不过需要注意：**这个命令依赖 Redis 的 LFU 访问频率统计，因此通常需要配置 LFU 类型的内存淘汰策略。** 例如：

```redis
CONFIG SET maxmemory-policy allkeys-lfu
```

生产环境不要为了运行这个命令随意修改淘汰策略，因为可能影响现有缓存行为。

### **② 使用 Redis 监控指标**

可以结合**Redis 节点 CPU 使用率、网络输入输出流量、命令执行次数、应用层 Key 访问频率统计**来判断。例如在 Java 项目中统计出 `product:1001` 是 100 次/秒、`product:1002` 是 200 次/秒、`product:9999` 是 100000 次/秒，这样就能定位访问量异常集中的 Key。

还可以使用 `redis-cli --stat` 观察整体负载，或在短时间内使用 `MONITOR` 辅助排查。但 `MONITOR` 本身开销较大，不适合在高负载生产环境中长时间运行。

---

## **四、如何解决热 Key？⭐⭐⭐⭐⭐**

### **方案一：使用本地缓存（最常用）**

假设有三个 Spring Boot 实例，每个 Java 实例都使用 Caffeine 本地缓存保存热点数据：

```
                 用户请求
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
    Java A        Java B        Java C
       │            │            │
       ▼            ▼            ▼
    Caffeine     Caffeine     Caffeine
       │            │            │
       └────────────┼────────────┘
                    │ 缓存未命中
                    ▼
                  Redis
                    │
                    ▼
                  MySQL
```

请求流程是：先查本地 Caffeine，命中就直接返回；未命中再查 Redis，命中就返回并写入 Caffeine；Redis 也没命中才去查 MySQL。

**优点是**原本每秒有 10 万次请求访问 Redis，引入本地缓存后，大部分请求可以直接在 JVM 内存中完成，这样能够显著降低 Redis 的访问压力。**缺点是**不同 Java 实例的本地缓存彼此独立，容易出现数据不一致。例如 Java A 和 Java B 的本地缓存里商品价格都是 100 元，MySQL 改成 200 元后 Java A 更新成 200 元、Java B 还是 100 元，就不一致了。

因此，可以结合**本地缓存设置较短 TTL、Redis Pub/Sub 或 MQ 广播缓存失效消息、数据更新时主动清理相关缓存**。对于商品详情、配置数据等**读多写少、允许短暂不一致**的场景，本地缓存非常适合。

---

### **方案二：热 Key 拆分**

假设一个 Key `product:9999` 每秒有 10 万次请求，可以把它复制成多个 Key：`product:9999:1`、`product:9999:2`、`product:9999:3`、`product:9999:4`、`product:9999:5`，这些 Key 存储相同的数据。Java 读取时，随机选择其中一个：

```java
int index = ThreadLocalRandom.current().nextInt(1, 6);

String key = "product:9999:" + index;

Object value = redisTemplate.opsForValue().get(key);
```

这样可以把请求分散到不同的 Key 上，如果这些 Key 在 Redis Cluster 中分布到不同 Master，就能够分摊节点压力。

**注意：** 拆分后的 Key 必须实际分布到不同节点，否则可能无法缓解单节点热点；复制多个 Key 会增加内存开销；数据更新时需要同步更新或删除所有副本；这种方案适合只读或读多写少的数据。对于库存扣减等需要原子修改的数据，**不能简单复制多个库存 Key，否则可能造成库存不一致。**

---

### **方案三：读写分离**

Redis 主从架构可以让部分读请求访问 Replica，写请求走 Master。如果有多个 Replica，可以进一步分担读请求。但需要注意：**Redis 主从复制是异步的，因此 Replica 可能存在数据延迟。** 对于要求强一致性的读取，不适合随意使用从节点。另外，读写分离能否缓解热点，还取决于客户端是否真正把读请求分散到了多个 Replica。

---

### **方案四：限流与降级**

如果热 Key 是因为突发流量造成的，例如秒杀活动，可以使用限流：每秒 100000 次请求进来，只允许 10000 次通过，其余请求拒绝或降级。常见方式包括**网关限流、用户维度限流、接口维度限流、返回兜底数据**。限流不能消除热 Key，但可以防止流量超过系统承载能力。

---

## **五、实际项目应该选择哪种方案？**

|**业务场景**|**推荐方案**|**原因**|
|---|---|---|
|热门商品详情|Caffeine + Redis|降低 Redis 读取压力|
|热门文章内容|本地缓存、Key 副本|读多写少，适合缓存|
|秒杀库存|Redis Lua + 限流|保证原子性，控制请求量|
|热门配置数据|本地缓存 + 失效通知|读取频繁，更新较少|
|大量只读请求|Redis 读写分离|利用 Replica 分担读压力|

特别注意：**解决热 Key 并不是一律使用分布式锁。** 分布式锁主要解决并发互斥问题，而热 Key 的核心问题是访问流量集中。如果对所有热 Key 请求加锁，反而可能降低吞吐量。

## Q：

Redis 热 Key 是指某个 Key 在短时间内被大量请求频繁访问，导致请求集中在某个 Redis 节点上，从而造成 CPU、网络带宽等资源瓶颈。热 Key 还可能引发缓存击穿，如果热点数据突然过期，大量请求可能同时访问 MySQL。

解决热 Key 主要有四种方法。

第一，可以使用 Caffeine 等本地缓存，让热点数据直接在 JVM 内存中读取，减少 Redis 访问。

第二，可以将只读热 Key 复制成多个副本，并分散到 Redis Cluster 的不同节点。

第三，可以使用 Redis 主从读写分离，让多个 Replica 分担读请求。

第四，对于秒杀等突发高流量场景，可以通过限流和降级保护系统。

实际项目中，我会优先根据业务特点选择本地缓存或热点数据分散方案，同时考虑缓存一致性问题。

### **最后总结**

|**问题**|**解决方案**|
|---|---|
|热 Key 读取过于频繁|Caffeine 本地缓存|
|单个 Redis 节点压力过大|热 Key 副本分散|
|读请求过多|Redis 读写分离|
|突发流量过大|限流、降级|
|热 Key 过期导致缓存击穿|互斥重建、逻辑过期、热点预热|

**一句话记忆：Big Key 是数据太大，Hot Key 是访问太频繁；解决热 Key 的核心思路是减少 Redis 访问量、分散请求压力。**
