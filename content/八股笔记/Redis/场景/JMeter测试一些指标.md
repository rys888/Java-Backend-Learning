
JMeter 是 Java 后端常用的性能压测工具，主要用于测试系统在高并发情况下的性能表现。

在 Java 后端面试中，最重要的指标有 **QPS、TPS、平均响应时间、P 95、P 99、吞吐量、错误率和并发数**。

## **一、QPS：每秒查询数 ⭐⭐⭐⭐⭐**

QPS（Queries Per Second），表示**系统每秒能够处理多少次查询请求**。

例如，你使用 JMeter 压测商品查询接口：

```http
GET /product/1001
```

假设：

```text
10 秒内完成了 10000 次请求
```

那么：

QPS = 10000/10 = 1000

表示系统平均每秒处理 1000 次查询请求。

**QPS 越高，通常说明系统的查询处理能力越强。**

不过，QPS 高不一定代表性能好，还需要结合响应时间和错误率判断。

---

## **二、TPS：每秒事务数 ⭐⭐⭐⭐⭐**

TPS（Transactions Per Second），表示**系统每秒完成多少个事务**。

例如，在你的 Java 后端预约系统中：

```text
用户发起预约
     │
     ▼
校验预约资格
     │
     ▼
扣减库存
     │
     ▼
生成预约订单
```

如果将整个预约流程视为一个业务事务：

```text
10 秒内完成 5000 次预约
```

那么：

TPS = 5000/10 = 500

表示系统每秒完成 500 个预约事务。

### **QPS 和 TPS 有什么区别？**

|**指标**|**QPS**|**TPS**|
|---|---|---|
|含义|每秒查询数|每秒事务数|
|关注点|请求处理能力|业务事务处理能力|
|示例|每秒查询 1000 次商品|每秒完成 500 次预约|

需要注意：

**在 JMeter 中，如果一个事务只包含一个 HTTP 请求，那么 QPS 和 TPS 的数值可能相同。**

但如果一个事务包含多个 HTTP 请求，两者就可能不同。

另外，JMeter 报告中的 `Throughput` 是采样器或事务的吞吐量，并不天然等于业务 TPS。

---

## **三、平均响应时间（Average Response Time）**

平均响应时间表示：

**从客户端发送请求，到接收到完整响应，平均需要多长时间。**

例如，JMeter 发送了 5 次请求：

|**请求**|**响应时间**|
|---|---|
|第 1 次|10 ms|
|第 2 次|20 ms|
|第 3 次|30 ms|
|第 4 次|40 ms|
|第 5 次|100 ms|

那么：

Average=\frac{10+20+30+40+100}{5}=40 ms

平均响应时间为 40 ms。

**平均响应时间越低，通常说明系统响应越快。**

但是，平均响应时间存在一个问题：

它可能掩盖少数响应特别慢的请求。

这就需要引入 P 95、P 99。

---

## **四、P 95 和 P 99：百分位响应时间 ⭐⭐⭐⭐⭐**

这是性能压测中非常重要的指标。

### **① P 95 是什么？**

**P 95 表示约 95% 的请求响应时间不超过这个值。**

假设我们发送了 100 个请求，将响应时间从小到大排序：

```text
10ms、12ms、15ms ... 100ms ... 500ms
```

如果 P 95 = 100 ms：

表示大约 95% 的请求在 100 ms 内完成。

只有大约 5% 的请求响应时间超过 100 ms。

### **② P 99 是什么？**

**P 99 表示约 99% 的请求响应时间不超过这个值。**

例如：

```text
P95 = 100ms
P99 = 300ms
```

意味着：

- 大约 95% 的请求在 100 ms 内完成。
- 大约 99% 的请求在 300 ms 内完成。
- 最慢的约 1% 请求可能超过 300 ms。

注意，百分位数的具体计算方法可能存在差异，因此这里用的是便于理解的近似描述。

### **③ 为什么 P 99 很重要？**

假设两个系统：

|**指标**|**系统 A**|**系统 B**|
|---|---|---|
|平均响应时间|30 ms|35 ms|
|P 95|60 ms|50 ms|
|P 99|500 ms|80 ms|

虽然系统 A 的平均响应时间更低，但它的 P 99 高达 500 ms。

这说明系统 A 存在少量非常慢的请求。

而系统 B 的响应时间更加稳定。

因此，**平均响应时间反映整体速度，P 95、P 99 更能体现系统的尾部延迟。**

---

## **五、吞吐量（Throughput）**

吞吐量表示：

**系统在单位时间内处理了多少请求或事务。**

例如：

```text
100 秒内完成 50000 个 HTTP 请求
```

那么：

Throughput=\frac{50000}{100}=500\ requests/s

JMeter 中常见的吞吐量单位包括：

- requests/sec：每秒请求数。
- requests/min：每分钟请求数。
- requests/hour：每小时请求数。

### **吞吐量和 QPS 有什么区别？**

严格来说：

- **吞吐量**是更广泛的概念，可以衡量请求数、事务数或数据量。
- **QPS** 特指每秒查询数。

在 HTTP 接口压测中，如果每个请求都被当作一次查询，吞吐量和 QPS 可以使用相同的计算方式。

---

## **六、并发数（Concurrency）**

并发数表示：

**某一时刻系统正在同时处理多少个请求或事务。**

例如：

```text
客户端 A ──┐
客户端 B ──┤
客户端 C ──┼──→ Spring Boot
客户端 D ──┤
客户端 E ──┘
```

如果这 5 个请求同时处于处理中，那么此时的请求并发数为 5。

在 JMeter 中，通常通过线程组配置虚拟用户数。

例如：

```text
Number of Threads：100
Ramp-up Period：10s
Loop Count：100
```

表示：

- 配置 100 个虚拟用户。
- 在 10 秒内逐步启动这些用户。
- 每个用户循环执行 100 次测试计划。

**但是需要注意：JMeter 的线程数不一定等于服务器实际同时处理的请求数。**

因为虚拟用户还可能处于等待响应、定时器等待等状态。

---

## **七、错误率（Error Rate）**

错误率表示：

**压测过程中失败请求占总请求的比例。**

例如：

```text
总请求数：10000
失败请求：100
```

那么：

ErrorRate=\frac{100}{10000}\times 100\%=1\%

错误率越低，通常说明系统越稳定。

但是要特别注意：

**JMeter 默认不一定会把业务失败识别为请求失败。**

例如秒杀接口：

```json
{
  "code": 500,
  "message": "库存不足"
}
```

如果 HTTP 状态码仍然是 200，JMeter 可能将其统计为成功请求。

因此，需要根据业务响应添加断言，才能准确统计业务成功率。

另外，对于秒杀系统，库存不足可能是正常的业务结果，不应直接视为系统故障。

---

## **八、这些指标之间有什么关系？**

这里有一个非常重要的公式：

\boxed{并发数 \approx 吞吐量 \times 平均响应时间}

这实际上是 Little’s Law 在稳定系统中的一种应用。

例如：

```text
吞吐量：1000 requests/s
平均响应时间：0.05s
```

那么：

并发数 \approx 1000 \times 0.05 = 50

表示系统平均有约 50 个请求处于处理中。

注意，这里的并发数是**平均在途请求数**，不等于 JMeter 配置的线程数；公式还要求统计口径一致、系统处于相对稳定状态。

## **九、Java 后端项目压测重点看哪些指标？**

假设你用 JMeter 测试一个 Redis + RabbitMQ 的高并发预约接口，得到以下结果：

|**指标**|**测试结果**|**说明**|
|---|---|---|
|JMeter 线程数|100|配置了 100 个虚拟用户|
|QPS|1200|平均每秒完成 1200 次请求|
|平均响应时间|45 ms|请求平均耗时 45 ms|
|P 95|80 ms|约 95% 的请求不超过 80 ms|
|P 99|150 ms|约 99% 的请求不超过 150 ms|
|HTTP 错误率|0%|没有检测到 HTTP 请求失败|

以上是示例数据，不是真实压测结果。

如果用于简历，可以写成：

基于 Redis Lua 实现预约资格原子校验与库存扣减，结合 RabbitMQ 异步处理预约订单，在 100 线程压测下实现 1200 QPS、平均响应时间 45 ms、P 99 150 ms。

但对于异步预约系统，**接口返回成功不代表订单已经成功落库**。如果要说明预约业务真正完成的 TPS，还需要统计消费者成功处理并落库的订单数量。

## **十、面试怎么回答？**

JMeter 压测主要关注吞吐量、响应时间、并发数和错误率。

首先，QPS 表示每秒处理的查询请求数，TPS 表示每秒完成的业务事务数。

其次，平均响应时间反映请求的整体响应速度，而 P 95、P 99 反映尾部延迟。例如 P 99 为 100 ms，表示约 99% 的请求响应时间不超过 100 ms。

此外，还需要关注并发数和错误率，判断系统在高负载下是否能够稳定运行。

实际压测时，我会结合吞吐量、P 95、P 99 和错误率综合判断系统性能，而不是只看 QPS。

**最后记住：**

|**指标**|**一句话理解**|
|---|---|
|**QPS**|每秒处理多少次查询|
|**TPS**|每秒完成多少个事务|
|**Average**|请求平均需要多久|
|**P 95**|95% 的请求有多快|
|**P 99**|99% 的请求有多快|
|**Throughput**|单位时间处理多少工作量|
|**Concurrency**|同时有多少请求正在处理|
|**Error Rate**|请求失败的比例|

对于 Java 后端实习面试，**最值得重点掌握的是 QPS/TPS 的区别，以及为什么 P 95、P 99 比平均响应时间更能反映系统在高负载下的稳定性。**
