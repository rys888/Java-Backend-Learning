
在 Java 后端面试中，**秒杀系统如何处理高并发、如何防止超卖，以及为什么引入 RabbitMQ**，是一个非常典型的项目问题。

结合你使用的 **Spring Boot + Redis + Lua + RabbitMQ + MySQL + Redisson** 技术栈，我建议把整个秒杀系统理解成三个核心环节：

**Redis 负责快速判断资格，RabbitMQ 负责异步削峰，MySQL 负责最终的数据正确性。**

## **一、为什么秒杀系统容易出现问题？**

假设有一个秒杀活动：

- 商品库存：100 件。
- 同时参与秒杀的用户：10000 人。
- 每个用户最多购买一件。

如果采用传统方式：

```text
           10000 个秒杀请求
                   │
                   ▼
               Spring Boot
                   │
                   ▼
               查询 MySQL 库存
                   │
                   ▼
               判断库存是否充足
                   │
                   ▼
               扣减库存
                   │
                   ▼
               创建订单
```

会出现两个问题。

**问题一：数据库承受大量并发请求。**

10000 个请求同时访问 MySQL，容易导致数据库连接池耗尽、锁竞争严重、响应时间上升。

**问题二：可能发生库存超卖。**

假设只剩一件商品：

```text
线程 A：查询库存 = 1
线程 B：查询库存 = 1

线程 A：判断库存充足
线程 B：判断库存充足

线程 A：扣减库存
线程 B：扣减库存
```

如果缺少正确的并发控制，就可能产生超卖。

因此，需要重新设计秒杀链路。

---

# **二、整体架构：Redis + RabbitMQ + MySQL ⭐⭐⭐⭐⭐**

我建议采用以下架构：

```text
                  用户秒杀请求
                       │
                       ▼
                  Spring Boot
                       │
                       ▼
                 Redis Lua 脚本
                 ┌────────────┐
                 │ ① 校验库存 │
                 │ ② 校验资格 │
                 │ ③ 预扣库存 │
                 └────────────┘
                       │
              ┌────────┴────────┐
              ▼                 ▼
           抢购失败           抢购成功
              │                 │
              ▼                 ▼
           直接返回          RabbitMQ
                                │
                                ▼
                             Consumer
                                │
                                ▼
                          MySQL 事务
                          ┌────────────┐
                          │ ① 扣减库存 │
                          │ ② 创建订单 │
                          └────────────┘
                                │
                                ▼
                            ACK 消息
```

这套架构的核心思想是：

**将高并发资格竞争放在 Redis 中处理，将真正的数据库操作交给 RabbitMQ 消费者异步执行。**

下面逐步分析。

---

# **三、第一步：Redis Lua 实现库存预扣与一人一单**

这是秒杀系统防止超卖的第一道防线。

## **1. 为什么使用 Redis？**

假设有 10000 个请求，但只有 100 件商品。

如果所有请求都访问 MySQL：

```text
10000 请求 → MySQL
```

数据库压力很大。

但如果先通过 Redis 判断资格：

```text
10000 请求
     │
     ▼
   Redis
     │
     ├── 9900 个请求 → 直接拒绝
     │
     └── 100 个请求 → RabbitMQ
```

这样 MySQL 只需要处理获得资格的请求。

当然，实际通过数量还受到一人一单、请求重试等条件影响。

## **2. 为什么使用 Lua？**

假设分别执行三个 Redis 命令：

```text
① 查询库存
② 判断用户是否购买过
③ 扣减库存
```

如果这些操作分开执行，就可能出现并发问题。

因此，使用 Lua 脚本将多个操作组合为一个原子执行单元。

例如：

```lua
-- KEYS[1]：库存 Key
-- KEYS[2]：已购买用户 Set
-- ARGV[1]：用户 ID

local stock = tonumber(redis.call('GET', KEYS[1]))

-- 1. 判断库存
if not stock or stock <= 0 then
    return 1
end

-- 2. 判断是否重复购买
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 2
end

-- 3. 扣减库存
redis.call('DECR', KEYS[1])

-- 4. 记录购买资格
redis.call('SADD', KEYS[2], ARGV[1])

return 0
```

返回值：

|**返回值**|**含义**|
|---|---|
|0|抢购资格获取成功|
|1|库存不足|
|2|重复购买|

由于 Redis 执行 Lua 脚本时不会被其他客户端命令插入，因此可以保证库存判断、用户判重和库存扣减的原子性。

**注意：Lua 的原子执行不等于发生错误时可以自动回滚。** 实际实现还应保证 Key 类型正确、参数合法，并处理执行异常。

另外，正式秒杀系统还应校验活动时间、用户资格等条件。

### **面试重点**

面试官可能会问：

**为什么不直接使用 Redis 分布式锁？**

你可以回答：

因为秒杀资格判断主要涉及 Redis 中的库存校验、用户判重和库存扣减，这些操作可以通过 Lua 脚本原子执行。

相比先获取分布式锁再执行多条 Redis 命令，Lua 可以减少网络交互和锁竞争，更适合高并发场景。

# **四、第二步：RabbitMQ 实现异步削峰 ⭐⭐⭐⭐⭐**

这是你项目中非常值得重点介绍的部分。

## **1. 为什么要引入 RabbitMQ？**

假设 Redis 已经筛选出 100 个符合资格的用户。

如果这些请求同步访问 MySQL：

```text
Redis 资格校验成功
        │
        ▼
    MySQL 扣库存
        │
        ▼
    MySQL 创建订单
        │
        ▼
    返回用户
```

用户必须等待数据库完成操作。

如果数据库响应变慢，接口响应时间也会增加。

引入 RabbitMQ 后：

```text
Redis 资格校验成功
        │
        ▼
   发送 RabbitMQ 消息
        │
        ▼
   返回抢购受理结果
        │
        ▼
      Consumer
        │
        ▼
   MySQL 扣库存 + 创建订单
```

这样可以实现两个目的。

**① 异步解耦**

秒杀接口不必同步等待 MySQL 创建订单。

**② 流量削峰**

RabbitMQ 可以暂时缓存待处理的预约消息，消费者按照数据库能够承受的速度处理。

例如：

```text
瞬间产生 1000 条待处理消息
              │
              ▼
           RabbitMQ
              │
              ▼
        Consumer 并发数 = 10
              │
              ▼
         MySQL 逐步处理
```

这里的消费者并发数只是示例，需要根据数据库性能和实际压测结果调整。

需要注意：

**RabbitMQ 不是让 MySQL 的处理能力凭空提高，而是把瞬时流量转化为可控的异步处理压力。**

# **五、第三步：MySQL 保证不超卖 ⭐⭐⭐⭐⭐**

虽然 Redis 已经预扣库存，但 MySQL 仍然需要进行最终校验。

为什么？

因为 Redis 和 MySQL 是两个独立系统，可能发生消息重复、状态不一致或故障恢复等问题。

因此，MySQL 必须作为最终的正确性防线。

## **1. 使用条件更新防止超卖**

错误做法：

```sql
SELECT stock FROM voucher WHERE id = 1001;
```

查询库存后，再执行：

```sql
UPDATE voucher
SET stock = stock - 1
WHERE id = 1001;
```

这种写法没有在更新时检查库存，可能导致超卖。

正确做法：

```sql
UPDATE voucher
SET stock = stock - 1
WHERE id = 1001
  AND stock > 0;
```

然后检查受影响的行数。

```java
int rows = voucherMapper.decreaseStock(voucherId);

if (rows == 0) {
    throw new RuntimeException("库存不足");
}
```

**即使多个消费者并发执行，MySQL 也会通过条件更新保证库存不会被扣成负数。**

## **2. 使用唯一索引保证一人一单**

假设 RabbitMQ 因为消息重投，导致同一个用户的订单消息被消费两次。

可以在订单表添加唯一索引：

```sql
ALTER TABLE voucher_order
ADD UNIQUE KEY uk_user_voucher (user_id, voucher_id);
```

这样，同一个用户无法针对同一个活动重复创建订单。

如果业务允许同一用户在不同活动中购买相同商品，唯一索引就应该包含对应的活动或批次 ID。

## **3. 使用数据库事务**

库存扣减和订单创建必须处于同一个事务中。

```java
@Transactional
public void createOrder(OrderMessage message) {

    // 1. 扣减库存
    int rows = voucherMapper.decreaseStock(
        message.getVoucherId()
    );

    if (rows == 0) {
        throw new RuntimeException("库存不足");
    }

    // 2. 创建订单
    orderMapper.insert(message.toOrder());
}
```

这样：

- 库存扣减成功、订单创建成功：事务提交。
- 库存扣减成功、订单创建失败：事务回滚。

但要确保 `@Transactional` 确实通过 Spring 代理生效。

另外，重复消息不能简单地全部当成失败重试，否则可能产生无意义的重复消费。

# **六、第四步：RabbitMQ 如何保证消息可靠性？**

这是面试官很可能继续追问的地方。

假设 Redis 已经预扣库存，但 RabbitMQ 消息丢失了：

```text
Redis 库存：100 → 99
        │
        ▼
RabbitMQ 消息丢失
        │
        ▼
MySQL 没有创建订单
```

结果：

**Redis 少了一件库存，但 MySQL 没有对应订单。**

因此，需要设计消息可靠性机制。

### **① 生产者：Publisher Confirm**

生产者发送消息后，通过 Publisher Confirm 判断 Broker 是否确认接收。

但要注意：

**Confirm 只能确认 RabbitMQ 对消息的接收状态，不能保证消费者已经成功创建订单。**

### **② 路由失败：Publisher Return**

如果消息到达 Exchange，却没有成功路由到 Queue，可以通过 Return 机制感知路由失败。

### **③ 消费者：手动 ACK**

消费者应该在 MySQL 事务成功提交后，再确认消息：

```text
RabbitMQ 投递消息
        │
        ▼
Consumer 处理
        │
        ▼
MySQL 事务提交
        │
        ▼
Basic ACK
```

如果数据库操作失败，可以根据异常类型选择重试、拒绝或转入死信队列。

### **④ DLX / DLQ：死信交换机与死信队列**

对于多次重试仍然失败的消息，可以进入死信队列。

但死信队列并不等于问题已经解决。

还需要：

- 记录失败原因。
- 人工或自动补偿。
- 监控积压消息。
- 避免无限重试。

### **⑤ 处理消息不确定状态**

这是更深入的一个问题。

例如：

```text
Redis 预扣库存成功
        │
        ▼
发送 RabbitMQ 消息
        │
        ▼
生产者等待 Confirm 超时
```

此时消息可能已经到达 RabbitMQ，也可能没有到达。

**不能因为 Confirm 超时，就立即恢复 Redis 库存。**

否则可能出现：

```text
消息实际上已进入 RabbitMQ
        │
        ▼
生产者误以为发送失败
        │
        ▼
恢复 Redis 库存
        │
        ▼
消费者仍然创建订单
```

这可能造成库存状态不一致。

更可靠的方案是引入**预约请求账本或订单状态记录**，通过唯一请求 ID、可靠重试、状态查询和定时对账处理不确定状态。

对于严格要求 Redis 预扣成功后绝不丢失请求的系统，还需要解决 Redis 预扣与可靠消息记录之间的原子性缺口；单靠 Confirm、Return 和手动 ACK 并不能完全消除这个问题。

# **七、Redisson 分布式锁在这里有什么作用？**

你项目中还使用了 Redisson。

但这里有一个容易混淆的地方：

**Redis Lua 已经保证库存预扣的原子性，为什么还需要 Redisson？**

两者负责的环节不同。

|**技术**|**作用**|
|---|---|
|Redis Lua|原子校验资格、用户判重、预扣库存|
|RabbitMQ|异步削峰、解耦数据库操作|
|Redisson|辅助控制消费者并发执行|
|MySQL 唯一索引|防止重复订单|
|MySQL 条件更新|防止库存超卖|
|MySQL 事务|保证库存扣减和订单创建的原子性|

例如，消费者可以针对用户或订单获取 Redisson 锁，减少同一业务请求的并发冲突。

但是：

**Redisson 不能代替 MySQL 唯一索引。**

因为分布式锁可能过期，也可能在 Redis 故障转移时失效。

实际上，如果 MySQL 已经有可靠的唯一索引、条件更新和事务，Redisson 不一定是必需的，应根据实际锁竞争和业务需求决定是否保留。

# **八、如何保证 Redis 和 MySQL 最终一致？**

整个秒杀系统实际上维护了两份库存：

```text
Redis：资格预扣库存

MySQL：实际库存
```

正常情况下：

```text
Redis 预扣成功
       │
       ▼
RabbitMQ 消息投递
       │
       ▼
MySQL 扣库存并创建订单
       │
       ▼
最终状态一致
```

但如果消费失败，就需要补偿。

例如：

```text
Redis 预扣成功
       │
       ▼
RabbitMQ 消费失败
       │
       ▼
达到重试上限
       │
       ▼
确认该请求最终失败
       │
       ▼
恢复 Redis 库存和购买资格
```

这里需要特别注意：

**补偿操作必须具备幂等性。**

否则同一条失败消息被补偿两次，可能导致 Redis 库存被多次增加。

一种可行的设计是：

```text
预约请求状态：

PENDING → SUCCESS
    │
    └────→ FAILED → COMPENSATED
```

通过数据库状态流转或其他可靠记录，保证同一个请求只能完成一次有效补偿。

同时，定时任务可以对账：

- Redis 已预扣，但 MySQL 没有订单。
- MySQL 已创建订单，但请求状态未更新。
- 消息处于不确定状态。

发现异常后进行重试或补偿。

# **九、面试官可能会问：这套架构还有什么优化空间？**

我认为可以从三个方向回答。

**第一，入口限流。**

即使 Redis 性能很高，也不应该允许无限请求进入系统。

可以在网关或应用层使用令牌桶进行限流，防止瞬时流量压垮 Redis 和应用服务器。

**第二，防止重复请求。**

Redis Lua 中使用 Set 记录已经获得资格的用户，避免同一用户重复抢购。

但如果要防止同一个用户在请求处理中不断重试，还可以结合请求 ID 和订单状态查询。

**第三，异步结果查询。**

秒杀接口返回的应该是：

已受理，正在处理中。

而不是：

下单成功。

因为 RabbitMQ 消费者可能尚未完成数据库操作。

前端可以通过订单状态查询接口获取最终结果：

```text
PENDING：处理中
SUCCESS：下单成功
FAILED：下单失败
```

这能避免把 Redis 资格校验成功误认为订单创建成功。

## **十、面试怎么回答？⭐⭐⭐⭐⭐**

你可以直接使用下面这段回答：

在我的项目中，针对高并发秒杀场景，我采用了 **Redis Lua + RabbitMQ + MySQL** 的架构。

首先，在秒杀活动开始前，将库存预热到 Redis。用户发起请求时，通过 Lua 脚本原子完成库存判断、用户判重和库存预扣，避免多个线程并发操作导致超卖。

其次，用户获得秒杀资格后，将订单请求发送到 RabbitMQ，由消费者异步处理数据库操作。这样可以将瞬时高并发请求转化为可控的消费压力，减少数据库的直接访问。

在消费者端，我使用 MySQL 条件更新保证库存不会扣成负数，通过唯一索引防止重复下单，并利用数据库事务保证库存扣减和订单创建的原子性。

为了保证消息可靠性，还引入了 Publisher Confirm、Return、手动 ACK 和死信队列，处理消息发送失败、消费失败和重复投递等情况。

最后，对于 Redis 预扣成功但订单落库失败的情况，需要结合请求状态记录、幂等补偿和定时对账，保证 Redis 和 MySQL 的最终一致性。

整体上，Redis 负责高并发资格校验，RabbitMQ 负责异步削峰，MySQL 负责最终数据正确性。

## **十一、最后总结**

|**核心问题**|**解决方案**|
|---|---|
|大量请求直接访问 MySQL|Redis 前置资格校验|
|高并发导致库存超卖|Redis Lua 原子预扣 + MySQL 条件更新|
|同一用户重复下单|Redis Set 判重 + MySQL 唯一索引|
|瞬时流量过大|RabbitMQ 异步削峰|
|消息丢失|Confirm、Return、持久化及可靠重试|
|消息重复消费|唯一索引 + 消费幂等|
|消费失败|重试、DLQ、异常处理|
|Redis 与 MySQL 不一致|请求状态记录 + 幂等补偿 + 定时对账|
|秒杀接口压力过大|网关限流、请求去重|

### **最重要的是记住这句话：**

**Redis Lua 解决高并发资格竞争，RabbitMQ 解决异步削峰，MySQL 条件更新和唯一索引解决最终超卖与重复下单，可靠消息与补偿机制解决最终一致性。**

这也是你在 Java 后端项目面试中最应该重点讲清楚的技术链路。
