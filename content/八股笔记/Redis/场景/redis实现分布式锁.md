
Redis 实现分布式锁，核心就是利用  `SET NX EX` 命令实现加锁，利用 Lua 脚本保证安全释放锁。

实际 Java 项目中，也经常使用 **Redisson** 来实现分布式锁。

## **一、为什么需要分布式锁？**

假设你有两个 Spring Boot 实例：

```text
       用户发起预约
             │
      ┌──────┴──────┐
      ▼             ▼
 Spring Boot A  Spring Boot B
      │             │
      └──────┬──────┘
             ▼
          MySQL
```

如果两个实例同时修改同一份数据，就可能产生并发问题。

你可能想到使用 Java 的 `synchronized`：

```java
synchronized (this) {
    // 执行业务
}
```

但问题是：

 `synchronized` **只能控制同一个 JVM 内的线程，无法控制不同 JVM 之间的并发。**

因此，需要一个所有服务实例都能访问的锁。

Redis 就可以充当这个角色。

---

## **二、Redis 如何实现分布式锁？⭐⭐⭐⭐⭐**

### **① 使用 SET NX EX 加锁**

假设两个服务实例同时尝试获取锁：

```redis
SET lock:order:1001 uuid-A NX EX 30
```

解释一下：

|**参数**|**含义**|
|---|---|
| `lock:order:1001` |锁的 Key|
| `uuid-A` |当前锁持有者的唯一标识|
| `NX` |Key 不存在时才允许设置|
| `EX 30` |30 秒后自动过期|

这里最关键的是 **NX**。

例如：

```text
Spring Boot A
      │
      ▼
SET lock uuid-A NX EX 30
      │
      ▼
     OK（成功获取锁）


Spring Boot B
      │
      ▼
SET lock uuid-B NX EX 30
      │
      ▼
    nil（获取锁失败）
```

由于 Redis 的单条命令具有原子性，所以不会出现两个客户端同时成功获取同一把锁的情况。

**为什么必须设置过期时间？**

假设 A 获取锁后突然宕机，如果没有过期时间，这把锁可能一直无法释放，造成死锁。

设置 TTL 可以让锁在一定时间后自动释放。

注意：必须使用一条 `SET NX EX` 命令，不能拆成 `SETNX` 和 `EXPIRE` 两条命令，否则可能在设置过期时间之前宕机。

---

### **② 为什么不能直接 DEL 释放锁？**

假设：

```text
① A 获取锁，TTL = 30 秒

② A 执行业务耗时 35 秒

③ 30 秒时，A 的锁自动过期

④ B 成功获取同一把锁

⑤ A 执行结束，直接 DEL lock
```

此时会发生什么？

**A 把 B 的锁删除了！**

```text
A 的锁过期
     │
     ▼
B 获取锁
     │
     ▼
A 执行 DEL
     │
     ▼
B 的锁被错误删除
```

因此，释放锁时必须判断：

**当前锁是不是自己持有的。**

例如：

```redis
GET lock:order:1001
```

如果返回 `uuid-A`，说明锁仍然属于 A。

但是，不能简单地先 `GET` 再 `DEL`。

因为两条命令之间可能发生锁过期、其他客户端重新加锁的情况。

### **③ 使用 Lua 脚本安全释放锁**

```lua
if redis.call("GET", KEYS[1]) == ARGV[1] then
    return redis.call("DEL", KEYS[1])
else
    return 0
end
```

解释：

1. 读取锁对应的唯一标识。
2. 判断是否等于当前客户端的标识。
3. 如果相等，删除锁。
4. 如果不相等，不执行删除。

由于 Redis 执行 Lua 脚本时不会插入其他客户端的命令，因此**判断锁归属和删除锁是原子操作**。

到这里，就实现了一个基础的 Redis 分布式锁。

## **三、基础 Redis 分布式锁还有什么问题？**

虽然我们已经解决了互斥和误删问题，但还有一个关键问题：

**业务执行时间超过锁的过期时间怎么办？**

例如：

```text
A 获取锁，TTL = 30 秒
        │
        ▼
A 开始执行业务
        │
        ▼
执行到第 30 秒，锁过期
        │
        ▼
B 获取锁并开始执行业务
        │
        ▼
A 还没有执行结束
```

此时，A 和 B 可能同时执行业务。

因此，仅靠固定 TTL 无法保证长时间业务执行期间始终互斥。

这就引出了 **Redisson 的看门狗机制（Watchdog）**。

---

## 四、Redisson 如何实现分布式锁？

Redisson 是 Java 中常用的 Redis 客户端，提供了封装好的分布式锁。

例如：

```java
RLock lock = redissonClient.getLock("lock:order:1001");

lock.lock();

try {
    // 执行业务逻辑
} finally {
    lock.unlock();
}
```

相比手动实现，Redisson 解决了很多问题。

### **① 看门狗机制（Watchdog）**

Redisson 默认的锁租约时间通常为 30 秒。

当使用不指定固定租约时间的加锁方式时，Redisson 会启动看门狗机制。

**只要客户端正常运行并且锁仍由它持有，看门狗就会周期性地延长锁的过期时间。**

例如：

```text
A 获取锁
TTL = 30 秒
     │
     ▼
10 秒后，看门狗续期
TTL 重新延长至 30 秒
     │
     ▼
再过 10 秒，看门狗续期
TTL 重新延长至 30 秒
     │
     ▼
业务执行结束
     │
     ▼
主动释放锁
```

这样就可以降低业务执行时间超过 TTL 导致锁提前释放的风险。

但如果发生长时间 JVM 停顿、网络故障等问题，看门狗仍可能续期失败。

另外，**显式指定固定租约时间的加锁方式通常不会启用看门狗自动续期**。

### **② 可重入锁**

Redisson 的 `RLock` 默认是可重入锁。

什么意思？

假设线程 A 已经获取锁：

```java
lock.lock();

try {
    lock.lock();

    try {
        // 业务操作
    } finally {
        lock.unlock();
    }
} finally {
    lock.unlock();
}
```

同一个线程可以重复获取自己已经持有的锁，而不会把自己阻塞住。

Redisson 会记录锁持有者和重入次数，每次加锁增加计数，每次解锁减少计数，直到计数归零才真正释放锁。

### **③ 自动释放与安全解锁**

Redisson 还封装了：

- 加锁的原子性。
- 锁持有者身份校验。
- Lua 脚本安全解锁。
- 锁过期时间管理。
- 可重入机制。
- 等待锁和获取锁失败处理。

因此，**实际 Java 后端开发中通常优先使用 Redisson，而不是自己编写完整的分布式锁逻辑。**

## **五、Redis 分布式锁有什么局限性？**

需要特别注意：

**Redis 分布式锁不能在所有故障场景下保证绝对互斥。**

例如 Redis 主从复制是异步的：

```text
① A 在 Master 上成功获取锁

② Master 尚未将锁同步给 Replica

③ Master 宕机

④ Replica 被提升为新 Master

⑤ B 在新 Master 上成功获取锁
```

此时，A 和 B 都可能认为自己持有锁。

因此，对于库存扣减、订单创建等关键业务，不能只依赖 Redis 分布式锁。

还应该结合：

- MySQL 唯一索引：防止重复订单。
- 数据库事务：保证相关数据库操作的一致性。
- 条件更新或乐观锁：防止库存超卖。
- 幂等机制：避免重复执行。

## Q：

Redis 分布式锁主要通过 SET NX EX 命令实现。

NX 保证只有 Key 不存在时才能加锁成功，EX 设置过期时间，防止客户端宕机后锁无法释放。

加锁时还需要设置唯一标识，释放锁时通过 Lua 脚本判断锁是否属于当前客户端，并原子地删除，避免误删其他客户端的锁。

但是固定过期时间可能导致业务还没有执行完成，锁就已经过期。

因此，在 Java 项目中通常使用 Redisson。Redisson 提供了可重入锁、看门狗自动续期以及 Lua 脚本安全解锁等功能。

不过，由于 Redis 主从复制是异步的，故障转移时仍可能出现锁丢失，所以关键业务还需要数据库唯一索引、事务和幂等机制兜底。

### **最后总结**

|**技术**|**解决的问题**|
|---|---|
| `SET NX` |保证同一时刻只有一个客户端成功加锁|
| `EX` |防止客户端宕机后锁永久不释放|
|UUID|标识锁的持有者，避免误删|
|Lua 脚本|保证判断锁归属和删除锁的原子性|
|Redisson Watchdog|降低业务未结束但锁提前过期的风险|
|Redisson 可重入锁|允许同一线程重复获取锁|
|数据库唯一索引、事务等|为关键业务提供最终一致性和正确性保障|

**一句话记忆：Redis 分布式锁通过 SET NX EX 加锁、Lua 脚本安全解锁，Redisson 进一步提供可重入和看门狗自动续期机制。**
