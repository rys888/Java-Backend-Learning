Redis 和 MySQL 的缓存一致性问题，是 Java 后端面试中的高频问题。**最常用的解决方案是 Cache Aside（旁路缓存）模式：读数据时先查 Redis，缓存未命中再查 MySQL；更新数据时先更新 MySQL，再删除 Redis 缓存。** 但需要注意：**这种方案只能保证最终一致性，不能保证 Redis 和 MySQL 在任何时刻都完全一致。**

## **一、为什么会出现缓存一致性问题？**

假设 Redis 缓存了某个商品的价格，MySQL 和 Redis 里 `product:1001` 都是 100 元。现在用户修改了商品价格，MySQL 更新成 200 元，Redis 还是 100 元。这时候其他用户查询 Redis，获取的仍然是旧价格，这就是**缓存与数据库数据不一致**。

核心问题是：Redis 和 MySQL 是两个独立的系统，无法通过普通的数据库事务保证它们同时更新成功。

---

## Q：为什么推荐删除缓存，而不是更新缓存？⭐

假设用户修改商品价格，有两种方案。

### **方案一：更新 MySQL + 更新 Redis**

先更新 MySQL（100 → 200），再更新 Redis（100 → 200）。看起来没有问题，但在并发情况下可能发生异常。假设两个线程同时更新：

|**时间**|**线程 A**|**线程 B**|
|---|---|---|
|T 1|MySQL 更新为 200||
|T 2||MySQL 更新为 300|
|T 3||Redis 更新为 300|
|T 4|Redis 更新为 200||

最终 MySQL 是 300，Redis 是 200，出现数据不一致。

### **方案二：更新 MySQL + 删除 Redis**

先更新 MySQL（100 → 200），再删除 Redis 缓存。下一次查询时，缓存不存在就去查 MySQL，拿到最新数据 200，再重新写入 Redis：

```
查询 Redis
    │
    ▼
缓存不存在
    │
    ▼
查询 MySQL
    │
    ▼
获得最新数据 200
    │
    ▼
重新写入 Redis
```

这种方式避免了主动维护缓存值的复杂性。**所以 Cache Aside 模式通常采用更新数据库、删除缓存，而不是同时更新数据库和缓存。**

不过，删除缓存也不是完全没有并发问题。

## Q：先删除缓存，还是先更新数据库？

这是面试最喜欢问的地方。

### **① 先删除 Redis，再更新 MySQL**

假设 MySQL 和 Redis 都是 100，两个线程并发执行：

| **时间** | **线程 A（更新）**   | **线程 B（查询）**      |
| ------ | -------------- | ----------------- |
| T 1    | 删除 Redis 缓存    |                   |
| T 2    |                | 查询 Redis，发现不存在    |
| T 3    |                | 查询 MySQL，得到旧值 100 |
| T 4    |                | 将旧值 100 写入 Redis  |
| T 5    | 更新 MySQL 为 200 |                   |

最终 MySQL 是 200，Redis 是 100。**问题在于旧数据被重新写入了 Redis**，如果缓存没有 TTL，这种不一致可能持续很久。因此，不推荐简单地先删除缓存，再更新数据库。

### **② 先更新 MySQL，再删除 Redis（推荐）**

也就是 ① 更新 MySQL → ② 删除 Redis：

```java
public void updateProduct(Product product) {
    // 1. 更新数据库
    productMapper.updateById(product);

    // 2. 删除缓存
    redisTemplate.delete("product:" + product.getId());
}
```

假设 MySQL 和 Redis 都是 100，线程 A 更新商品时，先更新 MySQL 为 200，再删除 Redis 缓存；线程 B 查询 Redis 未命中，去查 MySQL 拿到 200，再重新写入 Redis 200。这样就可以在正常情况下保持缓存与数据库一致。

**但这里还有两个重要问题。**

## **四、先更新数据库，再删除缓存，就一定安全吗？**

**不一定。**

### **问题一：删除缓存失败**

假设 MySQL 更新成功（100 → 200），但 Redis 网络故障，删除缓存失败，最终 MySQL 是 200、Redis 是 100，又出现了数据不一致。

#### **解决方案：重试机制**

可以通过 MQ 或可靠的异步任务进行缓存删除重试：

```
       更新商品
           │
           ▼
       更新 MySQL
           │
           ▼
       删除 Redis
           │
     ┌─────┴─────┐
     ▼           ▼
   成功         失败
                 │
                 ▼
             记录重试任务
                 │
                 ▼
             异步重试删除
```

需要注意，**不能只依赖普通 MQ 消息发送**，因为可能出现 MySQL 更新成功、服务突然宕机、还没发送 MQ 消息的情况。所以如果业务对一致性要求较高，可以采用**事务消息表（Outbox）**：在更新 MySQL 的同一事务中记录缓存失效任务，再异步投递并重试；或者用 **Canal / Debezium 监听 Binlog**：监听 MySQL 数据变化，异步删除对应 Redis 缓存。这两种方案都需要考虑消息重复、失败重试和顺序问题。

### **问题二：并发查询导致旧数据回写**

即使先更新 MySQL，再删除 Redis，仍然存在一种极端情况。假设 Redis 中原本没有缓存：

|**时间**|**线程 A（查询）**|**线程 B（更新）**|
|---|---|---|
|T 1|查询 Redis，未命中||
|T 2|查询 MySQL，得到旧值 100||
|T 3||更新 MySQL 为 200|
|T 4||删除 Redis 缓存|
|T 5|将旧值 100 写入 Redis||

最终 MySQL 是 200，Redis 是 100。这是因为线程 A 查询数据库后，在写入 Redis 之前发生了延迟。虽然这种情况的发生条件相对苛刻，但确实存在。

#### **解决方案：设置合理的 TTL**

```redis
SET product:1001 "100" EX 60
```

即使发生旧数据回写，缓存也会在 60 秒后过期。但要注意：**TTL 只是限制不一致可能持续的时间，并不能保证立即一致。** 对于一致性要求更高的场景，可以进一步使用版本号校验、协调缓存重建与更新操作等机制。

## **五、延迟双删是什么？**

延迟双删也是一个经典面试知识点，执行过程是：① 删除 Redis 缓存 → ② 更新 MySQL → ③ 等待一段时间 → ④ 再次删除 Redis 缓存。

为什么需要第二次删除？因为在第一次删除缓存之后，可能有其他线程读取旧数据并重新写入 Redis（前面提到的并发查询导致的旧数据写入），第二次删除就是尝试清理这部分旧缓存：

```
线程 A                         线程 B
  │                              │
  ▼                              │
删除 Redis                        │
  │                              ▼
  │                        查询 MySQL 旧数据
  ▼                              │
更新 MySQL                       ▼
  │                        回写 Redis 旧数据
  ▼
等待一段时间
  │
  ▼
再次删除 Redis
```

这样可以降低旧数据长期存在的概率。但是：**延迟双删不是严格的一致性保证。** 因为延迟多久很难准确确定，而且第二次删除本身也可能失败。因此在实际项目中更推荐：**更新数据库 → 事务提交后删除缓存 → 删除失败可靠重试 → 设置 TTL 兜底。**

## **六、Spring Boot 项目应该怎么实现？**

这里有一个很容易被忽略的问题：**数据库事务还没提交，就删除了 Redis 缓存。**

```java
@Transactional
public void updateProduct(Product product) {
    productMapper.updateById(product);

    redisTemplate.delete("product:" + product.getId());
}
```

看起来是先更新数据库，再删除缓存，但实际执行顺序是：① 执行 UPDATE SQL → ② 删除 Redis 缓存 → ③ 方法结束 → ④ Spring 提交 MySQL 事务。在事务提交之前，其他线程可能查询 MySQL，读到旧数据并重新写入缓存。

因此，**删除缓存最好发生在数据库事务成功提交之后。** Spring 中可以通过事务同步回调实现：

```java
@Transactional
public void updateProduct(Product product) {
    productMapper.updateById(product);

    String key = "product:" + product.getId();

    TransactionSynchronizationManager.registerSynchronization(
        new TransactionSynchronization() {
            @Override
            public void afterCommit() {
                redisTemplate.delete(key);
            }
        }
    );
}
```

这样可以确保数据库事务成功提交后，再执行缓存删除。不过，这段代码只是演示事务提交后的删除时机，**如果事务提交后服务宕机，或者 Redis 删除失败，仍然可能导致缓存不一致**，生产环境中可以进一步引入可靠重试机制。

## **七、不同业务场景应该怎么选择？**

|**业务场景**|**推荐方案**|
|---|---|
|普通商品详情缓存|Cache Aside + TTL|
|用户信息缓存|更新 MySQL + 提交后删除 Redis|
|一致性要求较高的数据|Cache Aside + 可靠重试 / Binlog 订阅|
|热点商品缓存|Cache Aside + TTL + 缓存重建协调|
|秒杀库存|Redis 原子操作 + MySQL 条件更新 + 异步对账补偿|

特别注意：**秒杀库存不能简单套用普通商品详情缓存的方案。** 因为秒杀库存涉及并发扣减，Redis 可能承担资格判断和库存预扣的职责，需要结合 Lua、MySQL 事务、幂等和最终一致性机制设计。

## **八、面试怎么回答？⭐⭐⭐⭐⭐**

Redis 和 MySQL 的缓存一致性问题，主要是因为两者属于独立系统，无法通过普通数据库事务保证同时更新成功。

一般采用 Cache Aside 模式，读取时先查 Redis，未命中再查 MySQL；更新时先更新 MySQL，再删除 Redis 缓存。之所以选择删除缓存而不是更新缓存，是因为并发更新可能导致缓存写入顺序与数据库更新顺序不一致。同时，先删除缓存再更新数据库，容易导致其他线程读取旧数据并回写 Redis，因此通常推荐先更新数据库，再删除缓存。

但是这种方式仍然存在删除缓存失败、并发旧数据回写等问题。实际项目中，我会在数据库事务提交后删除缓存，并结合 TTL 和可靠重试机制降低不一致风险。对于一致性要求更高的业务，可以通过事务消息表或 Binlog 订阅实现缓存失效的可靠处理。

需要强调的是，这些方案主要保证最终一致性，而不是严格的强一致性。

### **最后总结**

|**问题**|**解决方案**|
|---|---|
|Redis 和 MySQL 数据不一致|Cache Aside|
|更新缓存可能发生乱序|删除缓存，而不是更新缓存|
|先删缓存导致旧数据回写|优先先更新数据库，再删除缓存|
|数据库事务尚未提交|事务提交后删除缓存|
|删除 Redis 失败|可靠重试、事务消息表、Binlog|
|极端并发导致旧数据回写|TTL、版本校验、缓存重建协调|
|要求严格强一致性|关键读写直接走数据库或使用更严格的协调机制|

**一句话记忆：Redis 和 MySQL 缓存一致性通常采用 Cache Aside，先更新数据库，事务提交后删除缓存，再通过 TTL 和可靠重试保证最终一致性。**
