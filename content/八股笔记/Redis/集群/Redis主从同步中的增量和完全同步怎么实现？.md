
Redis 主从同步主要有两种方式：**全量同步（完全同步）和增量同步**。

它们的核心区别是：

- **全量同步**：主节点把当前所有数据发送给从节点。
- **增量同步**：主节点只把从节点缺失的写命令发送过去。

Redis 通过 **PSYNC 命令、Replication ID、offset（复制偏移量）和 repl_backlog_buffer（复制积压缓冲区）** 来决定使用哪种同步方式。

## **一、全量同步是怎么实现的？⭐⭐⭐⭐⭐**

假设有两个 Redis 节点：

```text
Redis Master（主节点）
         │
         │ 数据同步
         ▼
Redis Replica（从节点）
```

当从节点第一次连接主节点时，通常需要进行全量同步。

### **① 从节点发送 PSYNC 命令**

从节点向主节点发送：

```redis
PSYNC ? -1
```

其中：

- `?`：表示不知道主节点的 Replication ID。
- `-1`：表示不知道当前复制偏移量。

相当于告诉主节点：

**我不知道之前同步到哪里了，请把数据完整同步给我。**

### **② 主节点生成 RDB 快照**

主节点收到请求后，通常会通过后台子进程生成 RDB 快照。

```text
          Master
             │
             ▼
       生成 RDB 快照
             │
             ▼
          dump.rdb
```

这个 RDB 文件包含生成快照时的数据库数据。

### **③ 主节点发送 RDB，从节点加载**

```text
          Master
             │
             │ 发送 RDB
             ▼
          Replica
             │
             ▼
       清空旧数据并加载 RDB
```

从节点加载 RDB 后，就拥有了主节点在快照时刻的数据。

**但是这里有一个问题：**

主节点生成和传输 RDB 的过程中，如果客户端继续执行写命令怎么办？

例如：

```redis
SET name Eason
SET age 20
```

这些操作发生在快照生成期间或之后，可能没有包含在 RDB 中。

### **④ 主节点发送后续写命令**

为了解决这个问题，主节点会保留全量同步期间产生的后续写命令，并发送给从节点。

```text
Master                          Replica
  │                                │
  │────── RDB 快照 ────────────────>│
  │                                │
  │────── 后续写命令 ──────────────>│
  │                                │
  │                                │
  │────── 持续复制写命令 ──────────>│
```

这样，从节点就可以逐渐追上主节点的数据状态。

**全量同步 = RDB 快照 + 快照期间及之后的增量写命令。**

## **二、增量同步是怎么实现的？⭐⭐⭐⭐⭐**

假设主从节点已经完成同步。

但是突然出现网络故障：

```text
Master                  Replica
  │                        │
  │────── 数据同步 ────────>│
  │                        │
  │       网络断开         │
  │          X             │
  │                        │
  │    Master 继续写入     │
  │                        │
```

网络断开期间，主节点仍然可能接收到写命令。

例如：

```redis
SET name Eason
SET age 20
INCR count
```

等到网络恢复时，从节点是否必须重新接收全部数据？

**不一定！Redis 可以通过增量同步，只补充断线期间缺失的数据。**

这里涉及三个关键概念。

### **① Replication ID：复制 ID**

每个主节点的复制历史都有对应的 Replication ID。

可以简单理解为：

**Replication ID 用来标识一段数据复制历史。**

从节点重新连接时，会提供自己记录的 Replication ID。

主节点据此判断双方的复制历史是否兼容。

### **② offset：复制偏移量**

offset 可以理解为：

**当前复制数据流已经处理到了哪个位置。**

例如：

```text
Master offset  = 1000
Replica offset = 800
```

表示：

- 主节点的复制流已经推进到位置 1000。
- 从节点只处理到了位置 800。

因此，从节点需要补充后续缺失的数据。

注意，offset 记录的是**复制数据流的字节位置**，不是执行了多少条命令。

### **③ repl_backlog_buffer：复制积压缓冲区**

这是增量同步最关键的数据结构。

**repl_backlog_buffer 是主节点维护的环形缓冲区，用来保存最近一段时间的复制数据流。**

例如：

```text
Master：

repl_backlog_buffer
┌──────────────────────────────────┐
│ ... 801 802 803 ... 999 1000    │
└──────────────────────────────────┘
```

假设：

```text
Master offset  = 1000
Replica offset = 800
```

如果缓冲区中仍然保留着从节点缺失的数据，那么主节点就可以直接发送这些数据。

```text
Master                           Replica
  │                                 │
  │<──── PSYNC replid 800 ──────────│
  │                                 │
  │──── 缺失的复制数据流 ───────────>│
  │                                 │
  │──── 后续持续同步 ───────────────>│
```

这样就不需要重新生成 RDB。

**增量同步 = 根据 offset，从 repl_backlog_buffer 中补发缺失的复制数据流。**

## **三、什么时候使用全量同步？什么时候使用增量同步？**

这也是面试的重点。

|**场景**|**同步方式**|**原因**|
|---|---|---|
|从节点第一次连接主节点|全量同步|没有可用的复制历史|
|从节点短暂断线后重连|通常增量同步|缺失的数据还在缓冲区|
|从节点长时间断线后重连|可能全量同步|缺失的数据已被覆盖|
|主从复制历史不兼容|全量同步|无法安全地续传|

举个例子：

假设复制积压缓冲区只能保留最近 1000 字节的数据。

```text
Master offset  = 5000
Replica offset = 4500
```

从节点缺失约 500 字节的数据，缓冲区还保留着。

因此可以增量同步。

但是：

```text
Master offset  = 5000
Replica offset = 2000
```

从节点缺失约 3000 字节的数据，缓冲区已经覆盖了较早的数据。

此时无法完成增量同步，需要全量同步。

所以：

**能否增量同步，关键取决于复制历史是否匹配，以及缺失的数据是否还在复制积压缓冲区中。**

## **四、面试怎么回答？**

Redis 主从同步主要分为全量同步和增量同步。

**全量同步**通常发生在从节点第一次连接主节点时。从节点通过 PSYNC 请求同步，主节点生成 RDB 快照并发送给从节点，从节点加载快照后，再接收快照期间及之后产生的写命令，最终完成数据同步。

**增量同步**通常发生在主从节点短暂断线后重新连接时。Redis 通过 Replication ID 判断复制历史是否兼容，通过 offset 判断从节点缺失的数据范围，再从 repl_backlog_buffer 中补发缺失的复制数据流。

如果缺失的数据已经被缓冲区覆盖，或者复制历史不兼容，就无法进行增量同步，需要重新执行全量同步。

### **五、最后记住这张图**

```text
             Replica 连接 Master
                       │
                       ▼
                 发送 PSYNC
                       │
                       ▼
            复制历史是否兼容？
                  /          \
                否            是
                │             │
                ▼             ▼
             全量同步     缺失数据还在
                          backlog 中？
                           /      \
                         否        是
                         │         │
                         ▼         ▼
                      全量同步   增量同步
```

**一句话记忆：全量同步靠 RDB，增量同步靠 repl_backlog_buffer，而 Replication ID + offset 用来判断能不能增量同步。**

另外要注意：**Redis 主从复制默认是异步的**，主节点执行完写命令后，不一定会等待从节点完成同步，因此主从之间可能存在短暂的数据不一致。
