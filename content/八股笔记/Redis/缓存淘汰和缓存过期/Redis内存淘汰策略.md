Redis 的内存淘汰策略，说的是内存用到 `maxmemory` 上限之后，Redis 该删掉哪些 Key 来腾地方。

一共 **8 种策略**，面试的重点就是 **LRU、LFU、TTL 三个算法，加上 allkeys 和 volatile 的区别**。LRU 这个思路在操作系统原理里也出现过，页面置换用的就是同一套逻辑。

## 一、8 种淘汰策略

所有策略都是在两个前缀的基础上再叠加具体算法：

**allkeys**：从 Redis 里所有 Key 中挑淘汰对象。

**volatile**：只从设置了过期时间的 Key 里挑。

| 淘汰策略                | 含义                           |
| ------------------- | ---------------------------- |
| **allkeys-lru**     | 从所有 Key 中淘汰最近最少使用的 Key       |
| **volatile-lru**    | 从设置了过期时间的 Key 中淘汰最近最少使用的 Key |
| **allkeys-lfu**     | 从所有 Key 中淘汰使用频率最低的 Key       |
| **volatile-lfu**    | 从设置了过期时间的 Key 中淘汰使用频率最低的 Key |
| **allkeys-random**  | 从所有 Key 中随机淘汰                |
| **volatile-random** | 从设置了过期时间的 Key 中随机淘汰          |
| **volatile-ttl**    | 优先淘汰剩余过期时间较短的 Key            |

其中 Redis 默认用的是 **noeviction**，也就是内存满了之后直接拒绝写操作。

⚠️ 注意 volatile 系列有个坑：**只要当前一个设了过期时间的 Key 都没有，它就没资格淘汰任何数据**，内存照样满着，效果上和 noeviction 一样。

## 二、LRU：最近最少使用

LRU（Least Recently Used）的核心思想是：

**一个 Key 很久没被访问，说明它将来被访问的概率也低，内存不够时优先淘汰它。**

假设 Redis 里有四个 Key，最近一次访问时间分别是：

- Key A：1 秒前访问
- Key B：5 分钟前访问
- Key C：10 秒前访问
- Key D：30 分钟前访问

这个时候内存满了：

```text
Redis 内存已满
       │
       ▼
检查 Key 的最近访问时间
       │
       ▼
淘汰 Key D
```

因为 Key D 已经 30 分钟没人访问了，是四个里面最久的。

### Redis 用的是标准 LRU 吗？

**不是，Redis 用的是近似 LRU。**

标准 LRU 要维护一条链表，每次访问 Key 都得把节点挪到链表头，有额外的内存开销和维护成本。Redis 为了性能换了个偷懒的做法：

1. 随机抽一批 Key 出来
2. 比较它们最近的访问时间
3. 挑其中最久没被访问的淘汰

实际实现里还有一个候选池（eviction pool），把多轮抽样里"最该淘汰"的 Key 攒起来，淘汰效果比纯随机抽样好很多。

**核心：LRU 关注的是最近一次访问时间。**

## 三、LFU：最不经常使用

LFU（Least Frequently Used）换了个维度：**不看多久没访问，看访问得勤不勤，频率低的先淘汰。**

假设四个 Key 的访问情况：

- Key A：访问了 1000 次
- Key B：访问了 10 次
- Key C：访问了 500 次
- Key D：访问了 2 次

内存满了之后：

```text
Redis 内存已满
       │
       ▼
比较 Key 的访问频率
       │
       ▼
淘汰 Key D
```

Key D 的访问频率最低。

### LRU 和 LFU 有什么区别？

区别用一个例子就能看出来。有两个 Key：

**Key A**：最近 1 小时被访问了 1000 次，最后一次访问是在 5 分钟前。

**Key B**：最近只被访问了 1 次，最后一次访问是在 1 秒前。

内存不足的时候，两种算法选的对象正好相反：

| 算法 | 更倾向淘汰 | 原因 |
|---|---|---|
| LRU | Key A | A 更久没有被访问 |
| LFU | Key B | B 的访问频率更低 |

⚠️ 这里容易搞混：**Redis 的 LFU 并不是简单记录 Key 被访问的总次数**，而是用**概率计数器 + 时间衰减机制**去估计访问频率，所以上面的例子只是帮助理解两种算法思路的简化模型，真实淘汰结果不一定完全按这个来。

**核心：LRU 看最近访问时间，LFU 看访问频率。**

## 四、TTL：优先淘汰即将过期的 Key

TTL（Time To Live）表示 Key 的剩余生存时间。假设四个 Key 的剩余时间分别是：

- Key A：剩余 100 秒
- Key B：剩余 10 秒
- Key C：剩余 500 秒
- Key D：剩余 5 秒

如果用 `volatile-ttl`，Redis 会优先淘汰剩余时间较短的那个，这里就是 Key D。

**但要注意**：Redis 并不是每次都扫全部 Key 去找 TTL 最短的那一个，还是通过抽样来选淘汰对象。

## 五、实际项目中应该选哪种策略？

拿一个常见的商品缓存场景来看，`product:1001`、`product:1002`、`product:1003` 分别缓存三个商品，其中：

- 商品 A 是热门商品，每天被访问几万次
- 商品 B 是普通商品，每天被访问几十次
- 商品 C 是冷门商品，几乎没人访问

这种场景更倾向于选 **allkeys-lfu**，优先保留高频访问的热点数据。因为缓存的主要目的就是提高热点数据的访问效率。

按业务特征选的话，大致是这样：

| 业务场景 | 推荐策略 |
|---|---|
| 普通缓存，关注近期热点 | `allkeys-lru` |
| 热点访问频率差异明显 | `allkeys-lfu` |
| 只允许淘汰带 TTL 的缓存 | `volatile-lru` / `volatile-lfu` |
| 不希望 Redis 自动删除数据 | `noeviction` |

⚠️ 如果同一个 Redis 实例里既有缓存，又有重要业务数据，比如库存、分布式锁，**不建议上 allkeys 系列**，重要 Key 一样会被当成普通数据淘汰掉。更稳妥的做法是按业务用途拆分 Redis 实例。

## 六、面试怎么回答？

8 种策略，可以分成四类：

- **noeviction**：不主动淘汰数据，也是 Redis 的默认策略
- **LRU**：优先淘汰最近最少使用的 Key
- **LFU**：优先淘汰访问频率最低的 Key
- **random 和 TTL**：随机淘汰，以及优先淘汰即将过期的 Key

前缀上，**allkeys 从所有 Key 中选择淘汰对象，volatile 只从设置了过期时间的 Key 中选择**。实际项目中如果 Redis 主要用于缓存，可以根据访问特征选 allkeys-lru 或 allkeys-lfu。

### 最后注意一个问题

**Redis 内存淘汰策略和 Redis 过期删除策略不是一回事。**

**内存淘汰**：Redis 内存达到限制时，为了释放空间而删除 Key。

**过期删除**：Key 的 TTL 到期后，Redis 通过惰性删除、定期删除等机制清理过期 Key。

一句话记住：**LRU 看多久没访问，LFU 看访问频率，TTL 看多久后过期。**
