
[[#Q：三种持久化方法]]
[[#Q：AOF 重写]]


Redis 主要有 **3 种持久化方式：RDB、AOF，以及 RDB + AOF 混合持久化**。

持久化的目的就是：**将内存中的数据保存到磁盘，避免 Redis 重启后数据全部丢失。**

## **一、RDB（快照持久化）**

**RDB 就是每隔一段时间，将 Redis 内存中的数据生成一份快照，保存到磁盘。**

例如：

```text
Redis 内存
┌───────────────────┐
│ name → Eason      │
│ age  → 20         │
│ stock → 100       │
└───────────────────┘
         │
         │ 生成快照
         ▼
    dump.rdb（磁盘）
```

Redis 可以通过 `BGSAVE` 创建子进程，在后台生成 RDB 文件。

**优点：**

- 文件紧凑，占用磁盘空间较小。
- 恢复速度快，适合大量数据的恢复。
- 适合数据备份。

**缺点：**

- 可能丢失最近一次快照之后的数据。
- 生成快照需要额外的 CPU 和内存资源，`fork` 也可能造成短暂阻塞。

例如每隔 5 分钟生成一次快照：

```text
10:00 → 生成 RDB
10:01 → 写入 A
10:02 → 写入 B
10:03 → Redis 宕机
```

如果没有其他持久化机制，A 和 B 就可能丢失。

---

## **二、AOF（追加文件持久化）

**AOF 就是将 Redis 执行的写命令记录到文件中，重启时通过这些记录恢复数据。**

例如执行：

```redis
SET name "Eason"
SET age 20
INCR age
```

AOF 会记录相应的写操作：

```text
appendonly.aof

SET name "Eason"
SET age 20
INCR age
```

这里是逻辑示意，实际 AOF 文件采用 Redis 协议格式。

Redis 重启时，可以通过加载 AOF 数据恢复之前的状态。

### **AOF 有三种刷盘策略**

|**策略**|**含义**|**特点**|
|---|---|---|
|always|每次写命令都执行刷盘操作|数据安全性高，性能开销较大|
|everysec|通常每秒刷盘一次|性能与安全性较平衡|
|no|由操作系统决定刷盘时机|性能开销较小，数据丢失风险较高|

其中，**everysec 是常用的默认策略**。

例如：

```text
10:00:00 → 写入 A
10:00:01 → AOF 刷盘
10:00:02 → 写入 B
10:00:02 → Redis 宕机
```

如果 B 还没有刷盘，就可能丢失。

因此，使用 `everysec` 时，通常可能丢失约 1 秒的数据。

### **AOF 的优缺点**

**优点：**

- 数据丢失风险通常比定期 RDB 快照更低。
- 可以通过刷盘策略平衡性能与可靠性。
- 支持 AOF 重写，减少冗余记录。

**缺点：**

- 通常比 RDB 占用更多磁盘空间。
- 持续记录写操作会产生额外 I/O 开销。
- 纯 AOF 日志恢复通常比 RDB 慢。

---

## **三、RDB + AOF 混合持久化**

既然 RDB 恢复快，而 AOF 数据丢失风险较低，能不能结合两者？

**可以，这就是混合持久化。**

混合持久化将 RDB 快照和 AOF 增量命令结合起来。

例如：

```text
Redis 内存
    │
    ▼
混合持久化数据
┌─────────────────────┐
│ RDB 快照             │
│                     │
│ name → Eason        │
│ stock → 100         │
├─────────────────────┤
│ AOF 增量命令         │
│                     │
│ DECR stock          │
│ SET age 20          │
└─────────────────────┘
```

恢复时：

1. 先加载 RDB 快照，快速恢复大部分数据。
2. 再执行后续 AOF 命令，恢复增量修改。

需要注意，Redis 7.x 的 AOF 使用多文件机制，混合持久化主要体现在 AOF 重写生成的基础文件中，并不是简单地将独立的 `dump.rdb` 和 AOF 文件拼接。

**优点：**

- 结合 RDB 恢复速度快的优势。
- 保留 AOF 增量记录，降低数据丢失风险。
- 通常比纯 AOF 日志恢复更快。

**缺点：**

- 实现和文件管理更加复杂。
- 仍然存在 AOF 刷盘间隔导致的数据丢失风险。
- AOF 重写仍然需要额外资源。

---

## **四、三种持久化方式对比 ⭐⭐⭐⭐⭐**

|**对比**|**RDB**|**AOF**|**混合持久化**|
|---|---|---|---|
|原理|定期保存数据快照|记录写操作|RDB 快照 + AOF 增量|
|数据安全性|相对较低|相对较高|相对较高|
|恢复速度|快|相对较慢|较快|
|文件大小|通常较小|通常较大|通常介于两者之间|
|性能开销|快照时集中产生|持续产生|两者兼有|
|适用场景|备份、快速恢复|对数据丢失较敏感|兼顾恢复速度与数据安全|

## Q：三种持久化方法

Redis 主要有三种持久化方式，分别是 RDB、AOF 和混合持久化。

**RDB 是快照持久化**，定期将内存中的数据保存到磁盘。优点是文件较小、恢复速度快，缺点是可能丢失最近一次快照之后的数据。

**AOF 是追加日志持久化**，通过记录写命令来恢复数据。它有 always、everysec 和 no 三种刷盘策略，默认是 everysec。优点是数据丢失风险较低，缺点是文件通常更大，恢复速度相对较慢。

**混合持久化结合了 RDB 和 AOF**，通过 RDB 快照快速恢复数据，再利用 AOF 增量命令恢复后续修改，兼顾恢复效率和数据安全性。

在实际项目中，可以根据业务对数据可靠性和恢复速度的要求选择合适的持久化方案。

**一句话记忆：**

- **RDB：** 保存数据快照，恢复快，但可能丢失较多数据。
- **AOF：** 记录写命令，数据更安全，但恢复相对慢。
- **混合持久化：** RDB + AOF，兼顾恢复速度与数据可靠性。



## AOF 重写

**AOF 重写（AOF Rewrite）就是 Redis 为了减少 AOF 文件体积，将大量冗余的写命令压缩成更少的命令。**

### **① 为什么需要 AOF 重写？**

假设我们对一个 Key 执行了 5 次操作：

```redis
SET count 1
INCR count
INCR count
INCR count
INCR count
```

最终：

```text
count = 5
```

如果 AOF 一直追加写命令，就会记录很多操作：

```text
AOF 文件：

SET count 1
INCR count
INCR count
INCR count
INCR count
```

但实际上，**Redis 恢复数据时，只需要知道 count 最终等于 5。**

因此，AOF 重写后可以简化为：

```redis
SET count 5
```

这样就减少了 AOF 文件的大小。

### **② AOF 重写是怎么实现的？**

这里有一个非常重要的知识点：

**AOF 重写不是读取旧 AOF 文件并删除重复命令，而是根据 Redis 当前内存中的数据状态，重新生成 AOF 文件。**

例如：

```text
Redis 内存：
name  = Eason
count = 5
```

Redis 会根据当前数据生成恢复这些数据所需的命令：

```redis
SET name Eason
SET count 5
```

整个过程可以简单理解为：

```text
旧 AOF 文件
    │
    │ 文件越来越大
    ▼
触发 AOF 重写
    │
    ▼
创建后台子进程
    │
    ▼
读取当前内存数据
    │
    ▼
生成新的 AOF 文件
    │
    ▼
完成切换，清理旧文件
```

### **③ 重写期间 Redis 还能处理请求吗？**

**可以！**

Redis 通常通过 `BGREWRITEAOF` 启动后台子进程执行重写。

假设重写开始时：

```text
count = 5
```

但重写过程中，客户端又执行：

```redis
INCR count
```

此时：

```text
count = 6
```

Redis 必须保证这次新增操作不会丢失。

在 Redis 7.x 中，AOF 使用多文件机制：

- 后台子进程生成新的基础文件。
- 主进程继续处理客户端请求，并将新的写操作记录到增量 AOF 文件。
- 重写完成后，通过清单文件管理新的基础文件和增量文件。

这样就能保证重写期间 Redis 仍然可以正常处理请求。

### Q：AOF 重写

AOF 重写是 Redis 为了减少 AOF 文件体积而提供的一种优化机制。

因为 AOF 不断追加写命令，可能产生大量冗余记录，所以 Redis 会根据当前内存中的数据状态，重新生成能够恢复这些数据的 AOF 文件，而不是直接修改旧文件。

AOF 重写通常通过后台子进程完成，不会长时间阻塞主线程处理请求。

Redis 7.x 采用多文件 AOF 机制，通过基础文件和增量文件保证重写期间新增的写操作不会丢失。

它的优点是减少文件大小、提高恢复效率，缺点是重写过程会消耗额外的 CPU、内存和磁盘 I/O 资源。

**一句话记忆：AOF 重写不是修改旧日志，而是根据当前内存数据重新生成更精简的持久化文件。**
