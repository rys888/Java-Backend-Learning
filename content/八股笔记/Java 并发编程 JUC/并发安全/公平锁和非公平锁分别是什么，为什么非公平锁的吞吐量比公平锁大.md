
**公平锁：尽量先来先得，排队久的线程优先。**  
**非公平锁：新来的线程可以直接参与抢锁，不保证严格先来先得。**

`ReentrantLock` 默认就是**非公平锁**。

公平锁和非公平锁，主要区别在于**新来的线程是否需要尊重已经排队等待的线程**。

- **公平锁**：获取锁时，通常会检查前面是否还有等待者，优先让等待时间更长的线程获取，减少插队和长期等待。比如 `new ReentrantLock(true)`。
- **非公平锁**：允许新来的线程先尝试获取锁，获取失败后再排队。这样可能出现后来的线程先拿到锁，但通常能减少交接期间的空闲，提高吞吐量。`ReentrantLock` 默认就是非公平锁。

非公平锁：

```
ReentrantLock lock = new ReentrantLock(false);
ReentrantLock lock = new ReentrantLock();
```

```
新线程来了
   ↓
先直接尝试抢锁
   ↓
┌─────────┴─────────┐
成功                失败
 ↓                   ↓
直接获得锁        进入AQS队列
                 排队等待
```

公平锁：

```
ReentrantLock lock = new ReentrantLock(true);
```

```
新线程来了
   ↓
前面有没有已经排队的线程？
   ↓
┌────────┴────────┐
有                没有
↓                  ↓
不能插队          尝试获得锁
↓
进入AQS队列
```

# **3. 为什么默认使用非公平锁？**

关键问题来了：

为什么不公平反而性能通常更好？

核心原因：

**可以减少线程挂起、唤醒以及上下文切换等调度成本，并提高锁在释放后被立即利用的机会。**

---

## **4. 公平锁的问题：唤醒老线程需要时间**

假设：

```text
A：持有锁
B：已经 park 等待
```

A：

```java
unlock();
```

公平锁希望：

```text
A释放
 ↓
唤醒B
 ↓
B恢复运行
 ↓
操作系统调度B
 ↓
B获得CPU
 ↓
B尝试获得锁
 ↓
执行
```

注意：

`unpark(B)` 并不意味着 B 马上就在 CPU 上运行。

B 之前可能：

```text
park
↓
WAITING
```

现在需要：

```text
unpark
↓
变得可运行
↓
等待操作系统调度
↓
真正运行
```

这一套存在调度成本。

---

# **5. 非公平锁可以让“正在运行的新线程”直接抢**

还是刚才：

```text
A刚释放锁
```

B 虽然已经等待很久：

```text
B：
park → 被唤醒 → 等待CPU调度……
```

这时候 E 正好正在 CPU 上运行：

```text
E：
lock()
 ↓
发现锁空闲
 ↓
CAS
 ↓
成功
```

于是：

```text
A释放
 ↓
E直接获得
 ↓
继续干活
```

可能避免：

```text
A → B
```

所需要的一部分：

**唤醒 + 调度 + 上下文切换成本。**

因此 CPU 能更快继续处理临界区任务。

---

# **7. 什么叫吞吐量？**


**单位时间内完成多少任务。**

比如：

```text
公平锁：
1秒完成 8000 个任务

非公平锁：
1秒完成 10000 个任务
```

非公平锁减少部分线程切换/调度成本后，CPU 可以把更多时间用于：

**真正执行业务代码。**

所以通常吞吐量更高。

---

# **8. 还有一个很重要的原因：线程上下文切换**

你后面学操作系统会专门碰到。

线程切换不是免费的：

```text
Thread A运行
     ↓
保存A的执行上下文
     ↓
调度Thread B
     ↓
恢复B的执行上下文
     ↓
B开始运行
```

这些过程：

**本身并没有完成你的业务，只是为了换线程。**

所以：

```text
频繁 park
+
频繁 unpark
+
频繁线程调度/上下文切换

→ 有额外开销
```

非公平锁允许当前正在运行或刚到达的线程直接竞争，在某些竞争场景下可以减少这些成本。

---

# **9. 那公平锁有什么好处？**

既然非公平锁性能通常更好，为什么还需要公平锁？

因为非公平锁存在：

**线程饥饿（starvation）的风险。**

例如 B：

```text
B：排队
```

结果：

```text
E插队
F插队
G又参与竞争
...
```

极端情况下：

```text
B：怎么还没轮到我？
```

所以：

```text
公平锁
↓
等待时间更可预测
↓
降低长期饥饿风险
```

代价：

```text
更多排队/唤醒/调度
↓
吞吐量通常下降
```

---

# **10. ReentrantLock 底层怎么体现公平和非公平？**

你已经学 AQS 了，所以这里很好理解。

公平锁获取锁时，会更关注：

**AQS 队列前面是否已经存在等待线程。**

可以粗略理解：

```text
公平锁：

state == 0
   ↓
锁空闲
   ↓
前面有人排队吗？
   ↓
有
   ↓
我不能直接抢
```

而非公平锁：

```text
state == 0
   ↓
先尝试 CAS 抢一下
   ↓
成功
   ↓
拿走
```

所以关键区别可以理解成：

```text
公平锁：
先看有没有前辈在排队
→ 再决定能不能抢

非公平锁：
有机会先抢
→ 不保证照顾排队顺序
```

---

# **11. 一个很容易被问的陷阱**

### **synchronized 是公平锁吗？**

不是。

`synchronized`  **不保证公平性。**

而 `ReentrantLock` 可以选择：

```java
// 非公平，默认
new ReentrantLock();

// 公平
new ReentrantLock(true);
```

所以这是 ReentrantLock 相比 synchronized 更灵活的地方之一。

## Q：什么是公平锁和非公平锁？为什么非公平锁吞吐量更高？

公平锁是指多个线程竞争锁时，尽量按照等待的先后顺序获取锁；非公平锁则不保证严格的等待顺序，新来的线程也可能直接参与锁竞争。

ReentrantLock 默认使用非公平锁，也可以通过构造参数 `true` 创建公平锁。

非公平锁吞吐量通常更高，是因为锁释放后，已经在 CPU 上运行的新线程可以直接尝试获取锁，而不一定必须等待队列中线程完成唤醒和调度，从而可能减少线程 park/unpark、调度以及上下文切换带来的开销，提高 CPU 和锁的利用率。

但是非公平锁可能使某些等待线程等待更久，存在饥饿风险；公平锁等待顺序更可预测，但通常需要付出一定吞吐量代价。
