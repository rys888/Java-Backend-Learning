在 Java 后端面试中，**内存泄漏（Memory Leak）和内存溢出（Out Of Memory，OOM）** 是 JVM 的高频问题。这两个概念经常一起出现，但它们并不是一回事。**内存泄漏：不需要的对象还占着内存，无法被正常回收。内存溢出：JVM 需要分配内存，但可用内存不足，无法完成分配。** 一个是"该扔的没扔"，一个是"想要的空间没有了"。

## 一、什么是内存泄漏（Memory Leak）？

### 1. 基本概念

Java 中不需要手动释放对象，因为 JVM 有垃圾回收机制（GC）。但 GC 有一个前提：**只有对象不再被 GC Roots 可达时，才有可能被回收。** 反过来说，只要还有一条从 GC Roots 出发的引用链指着某个对象，即使业务上早就不需要它了，GC 也动不了它，这就是内存泄漏。

看个例子：

```java
public class Demo {

    private static List<Object> list = new ArrayList<>();

    public static void main(String[] args) {

        while (true) {
            list.add(new Object());
        }
    }
}
```

`list` 是类的静态字段，每个 `new Object()` 都被 add 了进去：

```text
GC Roots
   │
   ↓
Demo 类的静态字段 list
   │
   ↓
ArrayList
   │
   ├── Object 1
   ├── Object 2
   ├── Object 3
   ├── Object 4
   └── Object ...
```

由于 `list` 是静态字段，它本身从 GC Roots 可达，又不断持有新对象的强引用，所以：GC 认为这些对象仍然可达；即使业务已经不需要其中某些对象，GC 也无法回收；对象不断增加，堆内存占用越来越大。如果这些对象已经没有业务价值，却仍然被持有，就属于**内存泄漏**。

需要注意：如果程序确实需要一直保存这些对象，那属于持续增长的内存使用，不一定是内存泄漏。判断的关键不是"对象多"，而是"对象还有没有用"。

### 2. 内存泄漏有什么危害？

内存泄漏不一定立即导致内存溢出，它的危险在于长期累积：

```text
程序正常运行
     ↓
不断创建对象
     ↓
部分无用对象仍被引用
     ↓
GC 无法回收
     ↓
堆内存占用持续增加
     ↓
GC 越来越频繁
     ↓
可用内存越来越少
     ↓
可能发生 OutOfMemoryError
```

**也就是说，内存泄漏不一定立即导致内存溢出，但长期的内存泄漏可能引发 OOM。**

## 二、什么是内存溢出（OOM）？

内存溢出指的是：**程序申请内存时，JVM 无法提供足够的内存，最终抛出 `OutOfMemoryError`。**

例如：

```java
public class Demo {

    public static void main(String[] args) {

        List<byte[]> list = new ArrayList<>();

        while (true) {
            list.add(new byte[1024 * 1024]);
        }
    }
}
```

这里每次创建一个约 1 MB 的数组。如果设置 `java -Xmx128m Demo`，表示最大堆内存为 128 MB，那么程序不断创建数组的过程是：

```text
JVM 堆内存：128MB

开始运行：
[■■□□□□□□□□] 20MB

运行一段时间：
[■■■■■□□□□□] 70MB

继续运行：
[■■■■■■■■□□] 110MB

继续分配：
[■■■■■■■■■■] 内存不足

       ↓

java.lang.OutOfMemoryError: Java heap space
```

此时 JVM 无法完成新的内存分配，就可能抛出 OOM。

**需要注意：OOM 不一定是内存泄漏导致的。** 比如 `byte[] data = new byte[1024 * 1024 * 1024];`，JVM 最大堆只有 256 MB，却尝试分配一个约 1 GB 的数组，就可能直接发生 OOM。这个过程不一定存在内存泄漏，只是申请的内存超过了 JVM 能提供的容量。

## 三、内存泄漏和内存溢出的区别 ⭐⭐⭐⭐⭐

|对比维度|内存泄漏（Memory Leak）|内存溢出（OOM）|
|---|---|---|
|本质|无用对象仍被引用，无法回收|内存不足，无法完成分配|
|是否一定报错|❌ 不一定|✅ 通常抛出 OutOfMemoryError|
|是否与 GC 有关|无用对象仍然可达，GC 无法回收|GC 后仍可能没有足够可用内存|
|是否一定相互关联|不一定导致 OOM|不一定由内存泄漏导致|
|常见原因|静态集合、ThreadLocal 未清理、监听器未注销|堆太小、对象过多、内存泄漏、直接内存不足|
|解决思路|找到无用对象被谁引用，释放不必要的引用|分析内存使用情况、对象分配及 JVM 配置|

最核心的一句：**内存泄漏是"对象该回收却回收不掉"，内存溢出是"内存不够用了"。** 内存泄漏可能导致内存溢出，但内存溢出 ≠ 一定发生了内存泄漏。

## Q：Java 后端有没有常见的内存泄漏场景

### 1. ThreadLocal 没有 remove() ⭐⭐⭐⭐⭐

```java
private static final ThreadLocal<User> USER_HOLDER =
        new ThreadLocal<>();
```

线程池里的工作线程会长期存活，如果代码这样写：

```java
public void process() {
    USER_HOLDER.set(new User());

    // 处理业务
}
```

set 进去的 User 就一直挂在线程上了：

```text
线程池中的工作线程
       │
       ↓
ThreadLocalMap
       │
       ↓
Entry
├── key：弱引用
└── value：强引用
             │
             ↓
           User对象
```

⚠️ 这里的设计是重点：**Entry 的 key 是弱引用，value 是强引用。** 所以 key 有可能被 GC 回收掉，变成 key 为 null 的 Entry；但 value 是强引用，只要线程还活着就一直不会释放。即使 key 被 GC 清除，value 也不一定立即释放。

所以推荐这样写：

```java
public void process() {
    try {
        USER_HOLDER.set(new User());

        // 处理业务

    } finally {
        USER_HOLDER.remove();
    }
}
```

`finally` 的作用是：**不管业务代码正常执行还是抛异常，都会执行 remove() 清理。**

不过要注意：**ThreadLocal 没有调用 remove() 不代表一定发生内存泄漏**，还要看线程生命周期、后续是否覆盖或清理 Entry 等因素。

### 2. 静态集合长期保存对象

```java
private static final List<User> USERS =
        new ArrayList<>();
```

如果持续 `USERS.add(new User())` 却不删除，静态集合就会一直持有这些对象。这是非常典型的内存泄漏风险。

### 3. 缓存没有设置淘汰策略

```java
private static final Map<Long, User> CACHE =
        new HashMap<>();
```

如果一直 `CACHE.put(userId, user)`，但没有最大容量限制、没有过期时间、没有淘汰机制，缓存就可能导致无限增长。对于 Java 后端项目，这也是需要重点关注的问题。

## Q：OOM 有哪些常见类型？

OOM 不只发生在堆中。JVM 运行时数据区分成堆、方法区、虚拟机栈、本地方法栈、程序计数器这几块，不同内存区域可能出现不同的问题：

|常见错误|可能原因|
|---|---|
|`OutOfMemoryError: Java heap space`|堆空间不足|
|`OutOfMemoryError: Metaspace`|类元数据占用过多，元空间不足|
|`OutOfMemoryError: Direct buffer memory`|直接内存不足|
|`OutOfMemoryError: unable to create native thread`|无法继续创建本地线程，可能受系统内存或线程数量限制|
|`StackOverflowError`|方法调用层次过深，栈空间不足|

特别注意最后一行：**`StackOverflowError` 不是 `OutOfMemoryError`，这两个不一样。** 比如：

```java
public void test() {
    test();
}
```

无限递归通常会导致 `java.lang.StackOverflowError`，因为每次方法调用都会创建新的栈帧，最终耗尽线程栈空间。

## 六、实际项目中如何排查？

假设一个 Spring Boot 项目运行一段时间后出现 `java.lang.OutOfMemoryError: Java heap space`，可以按照以下思路排查。

**第一步：查看 JVM 内存使用情况。** 通过 `jstat`、JDK Mission Control 等工具观察堆内存占用和 GC 情况。重点关注：Full GC 或其他老年代回收之后，堆内存占用是否仍然持续升高？这可能是内存泄漏的信号，但不能仅凭这一点确定。

**第二步：获取堆转储文件（Heap Dump）。** 可以在 JVM 启动参数中配置：

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/path/to/dumps
```

这样发生支持该机制的 OOM 时，JVM 可以自动生成堆转储文件。

**第三步：使用 MAT 分析。** 使用 Eclipse Memory Analyzer（MAT）分析堆转储，重点查看：哪些对象占用内存最多？哪些对象数量异常？哪些对象被长期持有？这些对象通过什么引用链连接到 GC Roots？

如果发现大量无用的 `User` 对象被某个静态 Map 引用，就可以进一步定位对应的代码。

**第四步：修复代码。** 例如清理无用引用、限制缓存容量、及时调用 `ThreadLocal.remove()` 等。注意：如果是直接内存、元空间或本地线程导致的 OOM，仅分析 Java 堆转储可能不够，还需要检查对应的内存区域。

## Q：谈谈你对内存泄漏和内存溢出的理解。

内存泄漏和内存溢出是两个不同的概念。

**内存泄漏**指的是程序中某些已经不再需要的对象，仍然被其他对象引用，导致 GC 无法正常回收这些对象。例如静态集合长期持有无用对象，或者线程池中使用 ThreadLocal 后没有及时清理，都可能造成内存泄漏。

**内存溢出**指的是 JVM 在申请内存时，无法提供足够的内存空间，最终抛出 `OutOfMemoryError`。例如堆内存不足、元空间不足等。

两者的关系是，内存泄漏可能导致内存溢出，但内存溢出不一定由内存泄漏引起，也可能是 JVM 内存配置过小，或者程序本身需要处理的数据量过大。

如果实际项目中遇到 OOM，我会先查看 JVM 的内存和 GC 情况。如果是堆内存问题，可以通过 Heap Dump 和 MAT 分析对象的内存占用以及 GC Roots 引用链，定位是否存在不合理的对象持有。



**内存泄漏：不该留的对象留住了。内存溢出：想申请内存，却没有足够空间了。**
