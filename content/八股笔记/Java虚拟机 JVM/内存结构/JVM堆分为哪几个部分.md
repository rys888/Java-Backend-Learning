
[[#Q：JVM 的堆分为哪几部分？]]

这个问题已经开始进入 **JVM 垃圾回收 GC** 了。面试里如果问 **“JVM 的堆分为哪几部分？”**，经典的**分代堆**视角下，先记这张图：

```text
                     JVM Heap
                        │
          ┌─────────────┴─────────────┐
          ↓                           ↓
       新生代                       老年代
    Young Generation              Old Generation
          │
    ┌─────┴──────────┐
    ↓                ↓
  Eden区          Survivor区
                  ┌────┴────┐
                  ↓         ↓
                 S0         S1
              From/To    To/From
```

也就是：**堆 = 新生代 + 老年代**，**新生代 = Eden + Survivor 0 + Survivor 1**。

---

### 1. 新生代 Young Generation

主要存放**新创建的、生命周期通常较短的对象**，比如 `User user = new User();`。在经典分代模型里，新对象通常优先分配到 Eden，所以新生代的结构大致是：

```text
Young Generation

┌──────────────────────────┐
│          Eden            │
│  Obj1 Obj2 Obj3 Obj4 ... │
├────────────┬─────────────┤
│     S0     │     S1      │
└────────────┴─────────────┘
```

为什么这么设计？因为 JVM 根据一个重要的经验假设：**绝大多数对象都是朝生夕死的。** 比如一个请求处理过程中创建的 DTO、临时 List、StringBuilder、各种临时对象，请求处理完很快就没用了。所以没必要一上来就把这些对象放进老年代。

---

### 2. Eden 区

Eden 可以理解成**新对象的主要出生地**，`new Object()` 出来的对象通常优先分配到这里。随着程序运行，Eden 里的对象越来越多、越来越满，到一定程度就可能触发新生代垃圾回收，传统术语经常叫 **Minor GC**。不过不同 GC 收集器的术语和具体行为会有所不同。

---

### 3. Survivor 区

Survivor 有两个，S0 和 S1，也经常叫 From Survivor / To Survivor，它们的角色会在回收过程中交换。

一开始 Eden 里全是对象，S0、S1 都是空的：

```text
Eden        S0        S1
对象对象     空         空
```

发生一次新生代回收，Eden 中大量对象死亡（Obj1 ❌、Obj2 ❌、Obj4 ❌，只有 Obj3、Obj5 存活），存活对象可能被复制到 Survivor：

```text
Eden        S0        S1
空          Obj3      空
            Obj5
```

下一轮 Eden 又有新对象：

```text
Eden        S0        S1
新对象...    Obj3      空
            Obj5
```

再次 GC 后，存活对象复制到另一块 Survivor：

```text
Eden        S0        S1
空          空         Obj3
                       Obj5
                       Obj8
```

于是 **S0 和 S1 会轮流承担 From / To 的角色。**

---

### 4. 对象活得足够久 → 老年代

JVM 会记录对象经历 GC 后存活的情况，流程大致是：

**对象出生 → Eden → 经历一次 GC 还活着 → Survivor → 再经历 GC 还活着 → Survivor → …… → 达到晋升条件 → Old Generation。**

所以老年代主要存**生命周期比较长的对象**，比如长期存活的业务对象、缓存结构等。但需要注意：**不是所有对象都一定严格走“Eden → Survivor → 老年代”**，某些大对象、空间不足、收集器策略等情况下，实际分配和晋升行为会有所不同。

---

### 5. 为什么要分新生代和老年代？

核心原因就是**不同对象的生命周期不同，可以采用不同的垃圾回收策略**。比如 100 个新对象，一次 GC 之后 90 多个都死了，那么新生代就很适合快速回收大量短命对象。而老年代里的对象往往活得很久，如果还像新生代一样频繁处理，就可能浪费资源。所以规律是：

**新生代 → 对象死亡率高 → 回收通常更频繁**
**老年代 → 对象通常存活时间长 → 回收通常相对少**

这就是**分代收集思想**。

---

### 6. Eden、S0、S1 的经典比例

八股里可能看到 **Eden : S0 : S1 = 8 : 1 : 1**，也就是传统 HotSpot / Parallel Scavenge 等场景中经常讲的经典默认比例：

```text
Young Generation

┌────────────────────────┐
│         Eden 80%       │
├────────────┬───────────┤
│  S0 10%    │ S1 10%    │
└────────────┴───────────┘
```

面试可以知道这个经典值，但**不要把 8:1:1 当成所有现代 JVM、所有 GC 收集器都固定如此。**

---

### 7. 方法区/元空间不属于堆的“老年代”

这个特别容易混。JDK 8 以后经常画成这样：

```text
JVM内存

Heap
├── Young
│   ├── Eden
│   ├── S0
│   └── S1
│
└── Old


Native Memory
└── Metaspace
```

所以 **Metaspace 元空间不是“堆里的第三个分代”**，它主要用于承载类元数据等。

---

### 8. 还要注意现代 GC 的区别

如果面试官只是问“JVM 堆怎么分”，按照 **新生代 + 老年代，新生代再分 Eden + S0 + S1** 回答，通常就是经典八股答案。但是如果继续追问 **“G1 也是这样物理连续划分的吗？”**，就不能这么回答了。

G1 会把堆划分成很多大小相同的 **Region**，大致是这样：

```text
Heap

┌────┬────┬────┬────┬────┐
│ E  │ O  │ S  │ E  │ O  │
├────┼────┼────┼────┼────┤
│ O  │ E  │ H  │ S  │ E  │
└────┴────┴────┴────┴────┘

E = Eden
S = Survivor
O = Old
H = Humongous
```

它仍然有**分代概念**，但不是传统意义上必须有一大片连续的 Eden、一大片连续的 Old。所以目前准备实习面试，可以建立两层认识：

**经典分代模型：Young + Old，Young = Eden + S0 + S1。**
**现代收集器具体堆布局可能不同，例如 G1 使用 Region。**

---

## Q：JVM 的堆分为哪几部分？

在经典的分代垃圾回收模型中，JVM 堆主要分为**新生代和老年代**。新生代又进一步分为 **Eden 区和两个 Survivor 区，也就是 S0 和 S1**。

新创建的对象通常优先在 Eden 区分配，经历新生代 GC 后仍然存活的对象可能进入 Survivor 区，并在两个 Survivor 区之间复制；对象存活达到一定条件后会晋升到老年代。

这样分代主要是因为大部分对象生命周期很短，根据对象不同的生命周期采用不同的回收策略，可以提高垃圾回收效率。不过像 G1 这样的现代垃圾收集器采用 Region 化的堆布局，物理结构并不完全等同于传统的连续新生代和老年代划分。




⚠️：这条生命周期在后面学 GC 学习也会用到：

**对象出生 → Eden → Survivor → Survivor → …… → Old。**
