
[[#Q：JVM 为什么既有解释器，又有 JIT 编译器？]]

JVM 同时拥有**解释器（Interpreter）和 JIT 即时编译器（Just-In-Time Compiler）**，主要是为了兼顾**程序启动速度和长期运行性能**。

先记住一句话：

**解释器启动快，但重复执行代码的效率通常较低；JIT 编译器需要额外的编译时间，但生成的机器码执行效率通常更高。两者结合，可以让 Java 程序既能快速启动，又能在运行过程中不断优化性能。**

## **一、为什么不能只使用解释器？**

Java 程序经过 `javac` 编译后，会生成字节码：

```text
Java 源代码
    ↓
javac 编译
    ↓
Java 字节码
    ↓
JVM 解释器
    ↓
执行程序
```

解释器的优点是：**不需要提前把整个程序编译为机器码，可以较快开始执行。**

但是，假设有这样一段代码：

```java
public int add(int a, int b) {
    return a + b;
}

public void test() {
    for (int i = 0; i < 1000000; i++) {
        add(i, 1);
    }
}
```

如果只使用解释器，`add()` 方法每次执行时都需要经过字节码解释执行的过程。

即使它被调用了 100 万次，解释器仍然需要反复处理相应的字节码。

因此：

**解释器适合快速启动，但对于频繁执行的代码，执行效率通常不如优化后的机器码。**

---

## **二、为什么不能只使用 JIT 编译器？**

既然 JIT 能够将字节码编译为机器码，为什么不直接把所有代码都交给 JIT？

主要有三个原因。

### **1. JIT 编译需要时间**

假设一个 Spring Boot 项目中有 10000 个方法。

如果 JVM 启动时就把所有方法编译成机器码：

```text
启动 JVM
    ↓
编译大量 Java 方法
    ↓
生成机器码
    ↓
开始执行程序
```

就会产生额外的启动开销。

而解释器可以直接开始执行字节码，不需要等待大量方法完成编译。

### **2. 并不是所有代码都会频繁执行**

例如：

```java
public void login() {
    // 用户登录
}

public void exportReport() {
    // 导出报表
}
```

假设：

- `login()` 每分钟调用 10000 次。
- `exportReport()` 每天只调用 1 次。

显然，花费较多时间深度优化 `login()` 更有价值。

如果所有方法都进行 JIT 编译，就可能把 CPU 时间浪费在很少执行的代码上。

因此，JVM 会优先编译**热点代码**。

### **3. JIT 需要收集运行时信息**

JIT 的一个重要优势是能够根据程序的实际运行情况进行优化。

例如：

```java
public void process(Payment payment) {
    payment.pay();
}
```

假设程序运行过程中，`payment` 绝大多数时候都是 `WechatPayment` 类型。

JIT 可以根据运行时收集的类型信息，尝试进行方法内联等优化。

而这些信息在程序刚启动时可能还不充分。

因此：

**先解释执行并收集运行信息，再对热点代码进行 JIT 优化，可以获得更好的长期运行性能。**

## **三、解释器和 JIT 是如何配合工作的？⭐⭐⭐⭐⭐**

HotSpot JVM 通常采用解释执行和 JIT 编译相结合的方式。

```text
              Java 字节码
                   │
                   ▼
               解释器执行
                   │
                   ▼
           收集代码运行信息
                   │
                   ▼
             是否为热点代码？
               /       \
              /         \
            否           是
            │            │
            ▼            ▼
       继续解释执行     JIT 编译
                         │
                         ▼
                    生成机器码
                         │
                         ▼
                    执行机器码
```

举个例子：

```java
public static int calculate(int a, int b) {
    return a + b;
}
```

假设这个方法不断被调用：

**第一阶段：解释执行**

JVM 刚开始通过解释器执行 `calculate()`。

**第二阶段：识别热点代码**

随着方法调用次数增加，JVM 通过计数器和运行时信息判断该方法是否值得编译。

**第三阶段：JIT 编译**

JVM 将 `calculate()` 编译为本地机器码，并可能进行方法内联等优化。

**第四阶段：执行机器码**

后续调用可以直接执行编译后的机器码，提高运行效率。

需要注意，现代 HotSpot JVM 通常还采用 **C 1、C 2 分层编译**，并不是简单地从解释器一次性切换到最终机器码。

## **四、为什么说 Java 程序需要预热？**

你可能听说过：

**Java 程序刚启动时性能一般，运行一段时间后性能会逐渐提升。**

这与 JIT 有很大关系。

例如：

```text
程序刚启动
    ↓
大量代码通过解释器执行
    ↓
JVM 逐渐识别热点代码
    ↓
C1 编译器进行快速编译
    ↓
C2 编译器进行更深入的优化
    ↓
热点代码执行效率提升
```

这个过程就是 JVM 预热（Warm-up）的重要组成部分。

不过，程序预热还可能涉及类加载、缓存初始化、连接池建立等其他因素。

对于长期运行的 Java 后端服务，JIT 优化能够发挥较大的价值。

## Q：JVM 为什么既有解释器，又有 JIT 编译器？

JVM 同时拥有解释器和 JIT 编译器，主要是为了兼顾程序的启动速度和长期运行性能。

解释器可以直接执行 Java 字节码，不需要提前编译为机器码，因此启动速度比较快。但是，对于频繁执行的代码，解释执行会产生重复的解释开销。

JIT 编译器则可以将热点代码编译成本地机器码，并进行方法内联、逃逸分析等优化，提高执行效率。不过，JIT 编译本身需要消耗时间和 CPU 资源。

因此，JVM 通常先通过解释器执行代码，同时收集运行信息。当发现热点代码后，再交给 JIT 编译器进行优化。

这样既避免了启动时编译大量代码的开销，又能提高热点代码的长期执行效率。

## **六、最后记住三个重点**

|**对比**|**解释器**|**JIT 编译器**|
|---|---|---|
|执行方式|解释执行字节码|将字节码编译为机器码后执行|
|启动速度|较快|需要额外编译时间|
|长期执行效率|通常较低|通常较高|
|适合场景|冷代码、程序启动阶段|热点代码、长期运行阶段|
|额外开销|解释执行开销|编译时间和 CPU 开销|

**一句话记忆：**

**解释器保证 Java 程序快速启动，JIT 编译器保证热点代码高效执行，两者结合实现启动速度与运行性能的平衡。**
