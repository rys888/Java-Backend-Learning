[[#Q：哪些对象可以作为 GC Roots？]]

GC Roots 是 JVM 可达性分析算法的起点。判断对象死活的时候，JVM 不是看这个对象本身有没有被谁引用着，而是从一组根引用出发，顺着对象之间的引用链往下搜：能走到的算存活，走不到的就可能被当成垃圾。

所以 GC Roots 决定了"从哪里开始找还活着的对象"，选得对不对，直接决定一个对象会不会被误回收。

## **一、可达性分析是怎么走的**

假设堆里是这么一串对象，其中 A、B、C 能被根引用到，D 和 E 谁也够不着：

```text
             GC Roots
                 │
                 ▼
              对象 A
                 │
                 ▼
              对象 B
                 │
                 ▼
              对象 C


              对象 D ◄────► 对象 E
```

从 GC Roots 出发，**A、B、C 可以到达，属于存活对象；D、E 无法到达，属于垃圾回收候选对象**。哪怕 D 和 E 互相引用，只要整个环都够不到根，还是可以一起回收。这也是可达性分析能解决引用计数法循环引用问题的原因。

## **二、四类最常见的 GC Roots**

面试里重点掌握这四类。

### **1. 虚拟机栈中引用的对象 ⭐⭐⭐⭐⭐**

主要是指线程正在执行的方法中，栈帧的局部变量表所引用的对象：

```java
public void test() {
    User user = new User();
}
```

```text
线程栈
┌────────────────┐
│ 局部变量 user  │
└───────┬────────┘
        │
        ▼
     User 对象
       （堆）
```

`user` 这个引用活着的时候，它指向的 `User` 对象就能从 GC Roots 走到，不会被回收。

需要注意的是，**不是栈里出现过的变量都算 GC Roots**。只有当前还活跃的引用才算，方法执行完、栈帧出栈之后，这个局部变量就跟着没了，它指向的对象也就不再因为这条线而存活。所以为什么"方法里 new 出来的对象，方法结束后就可能被回收"，根就在这儿。

这里容易搞混的一点：局部变量表里存的是**引用**，对象本体在堆里。栈上的是根，堆上的是被根指向的对象。

### **2. 方法区中类静态属性引用的对象 ⭐⭐⭐⭐⭐**

```java
public class UserManager {
    private static User user = new User();
}
```

```text
类的静态字段 user
        │
        ▼
     User 对象
       （堆）
```

`user` 是静态字段，存在方法区（JDK 8 之后是元空间）里。只要类还没被卸载，这个静态引用就一直有效，它指向的 `User` 对象也就一直可达。JDK 8 之后字符串常量池挪到了堆里，但类静态字段引用的对象作为 GC Roots 这一点没有变。

这也是为什么**静态集合特别容易引发内存泄漏**：

```java
private static final List<User> users = new ArrayList<>();
```

不断往 `users` 里 add，却从来不清理，集合本身被静态字段一直引用着，里面的每个元素也跟着一直被引用着，GC 看它们全是活的，回收不掉。项目里做本地缓存、全局 Map 的时候，这一类问题很常见。

### **3. 方法区中常量引用的对象 ⭐⭐⭐⭐**

```java
public class Test {
    private static final String NAME = "Java";
}
```

运行时常量池保存在方法区里，里面存的对象引用同样可以当根用。比如 `"Java"` 这个字符串对象，被常量池引用着，就属于这一类。

不过这里有个容易混的地方：**并不是所有 `static final` 字段都属于常量池引用**。像 `private static final String NAME = "Java";` 这种编译期就能确定值的字面量，走的是常量池；而 `private static final User USER = new User();` 这种对象字段，是运行时才初始化的，应该按静态字段引用来理解，只是它恰好被 `final` 修饰了而已。

### **4. 本地方法栈中 JNI 引用的对象 ⭐⭐⭐**

JNI（Java Native Interface）允许 Java 调用 C、C++ 这类本地代码。如果本地方法通过 JNI 引用了某个 Java 对象，JVM 也得把这个 JNI 引用算进 GC Roots。

原因很简单：**本地代码不受 JVM 管理，JVM 看不到那边还有没有人在用这个对象。** 不把 JNI 引用算成根，对象可能在 C 代码还在用的时候就被回收了。

## **三、HotSpot 里还有哪些 GC Roots**

除了上面四类，实际实现里还会把下面这些引用也算作根：

- **活动线程对象**：JVM 需要维护的存活线程相关引用。
- **同步锁持有的对象**：被 `synchronized` 相关机制持有的对象，锁还没释放，对象不能被回收。
- **JVM 内部引用**：类加载器、常驻的异常对象、基本类型对应的 Class 对象等。
- **JVMTI 等本地工具持有的引用**：调试、监控工具可能持有对象引用。

这一类属于补充项，面试答完四类再带一句就够。不同 JVM 实现和垃圾收集器枚举 GC Roots 的方式会有差异，不用背死。

## Q：哪些对象可以作为 GC Roots？

JVM 用可达性分析判断对象是否存活，从 GC Roots 出发沿着引用链搜索，走不到的对象就可以被回收。

GC Roots 主要包括四类：**虚拟机栈中局部变量引用的对象、方法区中类静态属性引用的对象、方法区中常量引用的对象、本地方法栈中 JNI 引用的对象**。

除此之外，活动线程、被同步锁持有的对象、JVM 内部引用（类加载器、异常对象等）以及 JVMTI 等本地工具持有的引用，在 HotSpot 中也属于 GC Roots 的枚举范围。

**一句话记忆：栈里的局部变量、静态字段、常量池、JNI 引用，这四类是最核心的根。**
