
[[#Q：Java 对象为什么会进入老年代？]]

Java 对象进入**老年代（Old Generation）**，主要是因为 JVM 认为这个对象存活时间较长，或者根据内存分配情况，需要将它放入老年代。

首先记住一个结论：

**对象进入老年代主要有三种常见情况：长期存活、动态年龄判断、空间分配担保。**

另外，在某些垃圾收集器中，大对象也可能直接进入老年代。

## **一、先理解对象正常的生命周期**

在经典分代垃圾收集器中，Java 堆通常划分为：

```text
                    Java 堆
                       │
          ┌────────────┴───────────┐
          │                        │
        新生代                    老年代
          │                        │
    ┌─────┼─────┐                  │
    │     │     │                  │
   Eden   S0    S1                Old
```

假设：

```java
User user = new User();
```

一般情况下，对象首先在 Eden 区分配。

随着垃圾回收不断进行：

```text
创建 User 对象
       ↓
    Eden 区
       ↓
   第一次 Young GC
       ↓
   对象仍然存活
       ↓
   Survivor 区
       ↓
   多次 Young GC
       ↓
   对象仍然存活
       ↓
     老年代
```

这里最关键的是：

**对象不是因为创建时间长就自动进入老年代，而是通常需要在多次垃圾回收中存活下来。**

---

## **二、第一种：对象长期存活 ⭐⭐⭐⭐⭐**

这是最常见、最容易理解的情况。

JVM 会在对象头中记录对象的 GC 年龄。

在经典分代收集器中：

- 对象在 Eden 中创建。
- 经历 Young GC 后仍然存活，并被复制到 Survivor 区，年龄通常变为 1。
- 之后每经历一次 Young GC 并存活，年龄通常增加 1。
- 达到晋升年龄阈值后，进入老年代。

例如：

```text
第一次 Young GC
      ↓
对象年龄 = 1
      ↓
第二次 Young GC
      ↓
对象年龄 = 2
      ↓
第三次 Young GC
      ↓
对象年龄 = 3
      ↓
     ...
      ↓
达到晋升年龄阈值
      ↓
    进入老年代
```

在一些经典 HotSpot 分代收集器中，可以通过参数设置晋升年龄上限：

```bash
-XX:MaxTenuringThreshold=15
```

不过，**15 不是所有垃圾收集器都固定使用的晋升年龄**，实际晋升年龄还会受到收集器策略和内存情况的影响。

### **举个例子**

```java
public class UserService {

    private static final User USER = new User();
}
```

这里的 `USER` 被静态字段长期引用。

如果对应的类一直存活，那么这个 `User` 对象通常也会长期存活。

在采用分代回收的 JVM 中，它就有可能经过多次 Young GC 后晋升到老年代。

注意：**被 static 引用不代表直接进入老年代，而是因为对象可能长期存活。**

---

## **三、第二种：动态年龄判断 ⭐⭐⭐⭐**

有时候，对象还没有达到设定的晋升年龄，就可能提前进入老年代。

为什么？

因为 **Survivor 区空间有限**。

假设 Survivor 区只有 10 MB。

经过 Young GC 后：

```text
Survivor 区

┌──────────────────────────┐
│ 年龄1的对象：6MB          │
│ 年龄2的对象：3MB          │
│ 年龄3的对象：1MB          │
└──────────────────────────┘
```

虽然这些对象还没有达到最大晋升年龄，但 Survivor 区已经比较拥挤。

为了避免 Survivor 区存放过多对象，某些垃圾收集器会根据对象年龄分布和 Survivor 空间目标，动态调整晋升年龄阈值。

```text
Survivor 空间压力较大
          ↓
调整晋升年龄阈值
          ↓
部分对象提前进入老年代
```

**因此，对象不一定非要经历 15 次 Young GC 才进入老年代。**

这里的具体年龄判断规则依赖垃圾收集器，不能认为所有 JVM 都采用完全相同的策略。

---

## **四、第三种：Survivor 空间不足 ⭐⭐⭐⭐⭐**

假设某次 Young GC 后，有大量对象仍然存活。

```text
Young GC 后

存活对象：20MB

Survivor 可用空间：10MB
```

此时：

```text
存活对象
   │
   ├── 部分对象 → Survivor
   │
   └── 无法容纳的对象 → 老年代
```

在允许这种晋升策略的经典分代收集器中，部分对象可能直接晋升到老年代。

这与前面的动态年龄判断有区别：

- **动态年龄判断**：根据对象年龄分布和 Survivor 空间目标，提前调整晋升阈值。
- **Survivor 空间不足**：存活对象无法全部放入 Survivor，需要考虑直接晋升。

当然，如果老年代也没有足够空间，就可能导致进一步的垃圾回收，甚至发生 OOM。

---

## **五、第四种：大对象直接进入老年代**

这是一种需要结合具体垃圾收集器理解的情况。

假设：

```java
byte[] data = new byte[10 * 1024 * 1024];
```

这里创建了一个约 10 MB 的数组。

如果对象比较大，某些垃圾收集器可能选择直接在老年代分配，以避免在新生代反复复制大对象。

但要注意：

**并不是所有大对象都会直接进入老年代。**

例如，G 1 使用 Region 管理堆，超过特定大小的对象可能作为 Humongous Object 分配到专门的 Humongous Region，而不是简单地按照传统 Eden → Survivor → Old 的路径处理。

---

## Q：Java 对象为什么会进入老年代？

在经典分代垃圾回收机制中，对象通常首先在 Eden 区分配，经过 Young GC 后仍然存活的对象会进入 Survivor 区。

对象进入老年代主要有几种情况。

第一种是**长期存活**，对象经过多次 Young GC 后，年龄达到晋升阈值，就会进入老年代。

第二种是**动态年龄判断**，JVM 可能根据 Survivor 区的空间情况，提前调整对象晋升年龄。

第三种是 **Survivor 空间不足**，如果一次 Young GC 后存活对象过多，Survivor 无法容纳，部分对象可能直接晋升到老年代。

此外，在某些垃圾收集器中，大对象也可能直接分配到老年代。

不过，具体的晋升策略与使用的垃圾收集器有关。


**对象进入老年代，不一定是因为它活得足够久，也可能是因为 Survivor 放不下，或者垃圾收集器决定提前晋升。**
