
[[#Q：]]


系统频繁发生 **Full GC**，说明 JVM 正在频繁尝试回收大量堆内存，可能导致较长的 Stop-The-World（STW）停顿，影响接口响应时间和吞吐量。

面试中，这道题重点不是背 GC 算法，而是掌握一套**从现象定位到根因分析的排查流程**。

## **一、先确认 GC 情况**

首先确认三个问题：

1. Full GC 是否真的频繁？
2. 每次 Full GC 耗时多久？
3. Full GC 后堆内存是否明显下降？

可以使用：

```bash
jstat -gcutil <pid> 1000
```

表示每隔 1 秒查看一次 JVM 的 GC 情况。

重点关注：

|**指标**|**含义**|
|---|---|
|YGC|Young GC 次数|
|YGCT|Young GC 累计耗时|
|FGC|Full GC 次数|
|FGCT|Full GC 累计耗时|
|O|老年代使用率|
|M|元空间使用率|

注意：这些指标的具体含义与 JVM 版本、垃圾收集器有关。例如 G 1 的部分 GC 统计口径与传统分代收集器不同，因此最好结合 GC 日志判断实际发生的 GC 类型。

**重点观察 Full GC 后内存是否恢复。**

例如：

```text
情况 A：

Full GC 前：老年代 95%
Full GC 后：老年代 30%

说明大量对象能够被回收。
```

```text
情况 B：

Full GC 前：老年代 95%
Full GC 后：老年代 92%

说明大部分对象仍然存活。
```

第二种情况需要重点怀疑**内存泄漏、长期存活对象过多或堆容量不足**。

但仅凭回收率还不能直接断定存在内存泄漏。

---

## **二、查看 GC 日志，确定 Full GC 原因 ⭐⭐⭐⭐⭐**

GC 日志是排查 Full GC 最重要的依据之一。

对于 JDK 8，可以配置：

```bash
-XX:+PrintGCDetails
-XX:+PrintGCDateStamps
-Xloggc:/logs/gc.log
```

对于 JDK 9 及以上，可以使用：

```bash
-Xlog:gc*:file=/logs/gc.log:time,uptime,level,tags
```

通过 GC 日志，主要分析：

**① Full GC 发生的频率**

例如每隔几分钟就发生一次，还是短时间连续发生。

**② Full GC 的触发原因**

可能包括：

- 老年代空间不足。
- 大对象分配或晋升失败。
- 元空间不足。
- 显式调用 `System.gc()`。
- 垃圾收集器自身的分配或回收压力。

**③ GC 前后的内存变化**

重点判断是否存在大量无法回收的对象。

需要注意，不同垃圾收集器的触发机制不同。例如 G 1 出现 `G1 Humongous Allocation` 时，不代表一定直接触发 Full GC，还需要结合后续日志判断。

---

## **三、排查是否存在内存泄漏 ⭐⭐⭐⭐⭐**

这是面试官最希望听到的排查方向之一。

### **1. 什么是内存泄漏？** [[内存泄漏和内存溢出]]

Java 有 GC，为什么还会发生内存泄漏？

因为 GC 只能回收不可达对象。

如果一个对象已经没有业务价值，但仍然被其他存活对象引用，GC 就无法回收它。

例如：

```java
public class UserCache {

    private static final Map<Long, User> CACHE = new HashMap<>();

    public static void addUser(User user) {
        CACHE.put(user.getId(), user);
    }
}
```

如果系统不断向这个静态 Map 添加用户，但从不清理：

```text
static HashMap
      │
      ├── User 1
      ├── User 2
      ├── User 3
      ├── ...
      └── User 1000000
```

这些对象会长期保持可达状态。

随着缓存不断增长，堆内存可能被占满，导致频繁 GC。

### **2. 如何定位内存泄漏？**

可以使用：

```bash
jmap -dump:live,format=b,file=heap.hprof <pid>
```

生成堆转储文件（Heap Dump）。

注意，生成 Heap Dump 可能造成明显停顿和磁盘开销，生产环境需要谨慎操作。

也可以考虑使用：

```bash
jcmd <pid> GC.heap_dump /logs/heap.hprof
```

然后通过以下工具分析：

- **MAT（Memory Analyzer Tool）**
- VisualVM
- JProfiler

重点查看：

**① Histogram**

查看哪些对象数量最多、占用内存最大。

**② Dominator Tree（支配树）**

分析哪些对象持有大量内存。

**③ GC Roots 引用链**

找出对象为什么没有被回收。

例如：

```text
GC Root
   │
   ▼
static HashMap
   │
   ▼
大量 User 对象
```

这样就能发现静态集合长期持有对象的问题。

## **四、排查对象创建速度是否过快**

频繁 Full GC 不一定是内存泄漏，也可能是**对象分配速度太快，导致垃圾回收跟不上**。

例如：

```java
public List<Order> queryOrders() {

    List<Order> orders = new ArrayList<>();

    for (int i = 0; i < 1000000; i++) {
        orders.add(new Order());
    }

    return orders;
}
```

如果这种代码在高并发环境下频繁执行：

```text
大量创建对象
      │
      ▼
Eden 区快速填满
      │
      ▼
频繁 Young GC
      │
      ▼
部分对象晋升老年代
      │
      ▼
老年代压力增大
      │
      ▼
可能触发 Full GC
```

这里涉及你之前学过的 **TLAB**。

TLAB 可以提高对象分配效率，但不能减少对象实际占用的堆内存。

因此，**TLAB 解决的是分配竞争问题，而不是对象创建过多导致的内存压力。**

可以结合 GC 日志、JFR、对象分配分析工具，判断哪些代码在大量创建对象。

常见优化包括减少不必要的临时对象、避免一次性加载大量数据、使用分页或流式处理。

## **五、排查 JVM 堆内存配置**

假设一个 Java 服务实际需要 4 GB 堆内存，但 JVM 只配置：

```bash
-Xms512m
-Xmx1g
```

即使不存在内存泄漏，也可能因为堆容量不足而频繁 GC。

可以查看 JVM 参数：

```bash
jcmd <pid> VM.flags
```

重点关注：

```text
-Xms：初始堆大小
-Xmx：最大堆大小
```

但不能简单认为：

Full GC 频繁，就直接把 Xmx 调大。

因为如果根本原因是内存泄漏，增大堆只能延缓问题出现。

**正确做法是先分析对象存活情况，再判断是否需要扩容。**

## **六、排查大对象和元空间问题**

### **1. 大对象分配**

例如：

```java
byte[] data = new byte[100 * 1024 * 1024];
```

一次创建 100 MB 的数组。

如果频繁分配大对象，可能导致堆空间压力增加。

对于 G 1，大对象可能被识别为 Humongous Object，占用特殊的 Humongous Region。

如果大量大对象频繁创建和回收，可能增加 GC 压力。

### **2. 元空间不足**

元空间（Metaspace）主要存储类元数据。

如果系统频繁动态生成类，或者存在类加载器泄漏，就可能导致元空间持续增长。

例如：

- 大量动态代理类。
- CGLIB 动态生成类。
- 自定义 ClassLoader 未正确释放。

可以使用：

```bash
jcmd <pid> VM.metaspace
```

查看元空间使用情况（具体命令支持情况取决于 JDK 版本）。

如果 GC 日志中出现 Metaspace 相关的触发原因，就需要进一步排查类加载数量和 ClassLoader 的生命周期。

## **七、实际排查流程**

假设你的 Spring Boot 服务原本响应时间为 50 ms，突然增加到 2 秒，并且监控发现 Full GC 频繁。

我会按照下面的流程排查：

```text
            系统频繁 Full GC
                   │
                   ▼
         ① jstat 查看 GC 情况
                   │
                   ▼
          ② 分析 GC 日志
             确认触发原因
                   │
                   ▼
       ③ 观察 Full GC 后内存变化
                   │
          ┌────────┴────────┐
          ▼                 ▼
     内存明显下降        内存下降很少
          │                 │
          ▼                 ▼
   排查对象分配速度    排查长期存活对象
   堆容量与晋升压力    内存泄漏或容量不足
          │                 │
          └────────┬────────┘
                   │
                   ▼
         ④ Heap Dump + MAT
                   │
                   ▼
          ⑤ 定位具体代码
                   │
                   ▼
          ⑥ 优化并重新压测
```

另外，如果 GC 日志明确指向元空间、显式 GC 或大对象分配，应优先沿对应方向排查，而不是一开始就生成 Heap Dump。

## Q：

如果系统频繁发生 Full GC，我会先**通过 `jstat` 和 GC 日志确认 Full GC 的频率、耗时以及触发原因**。

检查堆内存配置：**年轻代、老年代比例**是否合适，是否过小

接着重点观察 Full GC 前后的堆内存变化。

如果 Full GC 后内存下降很少，说明存在大量长期存活对象，我会重点排查**内存泄漏或堆容量不足**，通过 `jmap` 或 `jcmd` 生成 Heap Dump，再使用 MAT 分析对象占用情况和 GC Roots 引用链。

如果 Full GC 后内存能够明显下降，但仍然频繁触发 GC，我会重点检查对象创建速度、Young GC 频率、对象晋升情况以及堆内存配置是否合理。

此外，还需要排查**大对象分配、元空间不足**、`System.gc()` 调用等问题。

最后，根据具体原因优化代码或调整 JVM 参数，并通过 GC 日志和压测验证优化效果。

### **最后总结**

|**排查方向**|**工具**|**重点**|
|---|---|---|
|**GC 频率与耗时**| `jstat` |Full GC 是否频繁|
|**GC 触发原因**|GC 日志|为什么触发 Full GC|
|**内存泄漏**|Heap Dump + MAT|哪些对象无法回收|
|**对象创建过快**|JFR、GC 日志|对象分配速率是否过高|
|**堆容量不足**| `jcmd` |Xmx 是否合理|
|**大对象分配**|GC 日志、JFR|是否存在大量大对象|
|**元空间问题**| `jcmd` |类元数据是否持续增长|

**一句话记忆：频繁 Full GC，先看 GC 日志，再看回收效果；回收不掉查内存泄漏，回收得掉查分配速率和堆容量，最后结合具体 GC 原因优化。**
