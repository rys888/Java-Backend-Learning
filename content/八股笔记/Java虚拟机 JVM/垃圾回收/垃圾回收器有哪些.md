[[#Q：Java 有哪些垃圾收集器？]]

Java 中常见的垃圾收集器（Garbage Collector）主要有 **Serial、ParNew、Parallel、CMS、G 1、ZGC 和 Shenandoah**。

对于 Java 后端实习面试，你不需要掌握所有收集器的底层实现，但需要知道**它们分别有什么特点、适用于什么场景，以及有什么区别**。

## **一、Java 常见的垃圾收集器**

先看一个整体分类：

```text
              Java 垃圾收集器
                     │
        ┌────────────┴────────────┐
        │                         │
     经典收集器                现代收集器
        │                         │
   ┌────┼────┐              ┌─────┼─────┐
   │    │    │              │     │     │
 Serial Parallel CMS         G1   ZGC  Shenandoah
   │
 ParNew（与 Serial 类似的年轻代并行收集器）
```

注意：这是一种便于学习的分类，并不是 JVM 官方严格的分类方式。

### **1. Serial GC：串行垃圾收集器**

**特点：使用单个 GC 工作线程进行垃圾回收。**

```text
应用线程：████████      ████████
GC线程：          ████
                  ↑
             Stop The World
```

这里的 **Stop The World（STW）**，就是垃圾回收期间暂停应用线程的执行。

Serial GC 的特点：

- 实现简单。
- GC 时需要暂停应用线程。
- 适合堆较小、CPU 资源有限的场景。

**一句话：Serial GC 是单线程垃圾回收器。**

---

### **2. ParNew GC：并行年轻代垃圾收集器**

ParNew 可以理解为 Serial 年轻代收集器的多线程版本。

```text
应用线程：████████          ████████

GC线程1：        ████
GC线程2：        ████
GC线程3：        ████
```

它的特点是：

- 使用多个 GC 线程并行回收年轻代。
- 回收期间仍然需要 STW。
- 历史上经常与 CMS 配合使用。

ParNew 属于较老的收集器，在现代 JDK 中已经被移除。

---

### **3. Parallel GC：并行垃圾收集器 ⭐⭐⭐⭐**

Parallel GC 同样使用多个线程执行垃圾回收，但它更注重**吞吐量**。

什么是吞吐量？

假设程序运行 100 秒：

- 执行用户代码：95 秒。
- 垃圾回收：5 秒。

那么：

吞吐量=\frac{95}{95+5}=95\%

Parallel GC 的主要目标，就是让 CPU 尽可能多地执行用户代码，而不是进行垃圾回收。

它的特点：

- 多线程并行回收。
- GC 期间存在 STW。
- 注重吞吐量。
- 适合批处理、后台计算等场景。

**一句话：Parallel GC 追求高吞吐量。**   **回收工作在STW 期间完成**

---

### **4. CMS：并发标记清除收集器 ⭐⭐⭐⭐**

CMS 全称为：

**Concurrent Mark Sweep**

即并发标记清除。

它的主要目标是：

**尽可能减少垃圾回收造成的应用停顿。**

CMS 的部分工作可以与应用线程并发执行。

```text
应用线程：██████████████████████████

GC线程：     ██████████████
                 ↑
             并发执行
```

但是，CMS 并不是完全没有 STW。

例如，初始标记和重新标记阶段仍然需要暂停应用线程。

CMS 的主要缺点：

1. 使用标记-清除算法，容易产生内存碎片。
2. 并发回收需要占用一定的 CPU 资源。
3. 可能发生并发模式失败，导致更严重的停顿。

**CMS 已经在 JDK 14 中被移除。**

因此，现在主要把它作为历史知识了解。

**一句话：CMS 追求低停顿，但存在内存碎片问题。**

---

## **二、G 1 GC：现代 Java 中的重要垃圾收集器 ⭐⭐⭐⭐⭐**

G 1 全称为：

**Garbage First Garbage Collector**

G 1 是 Java 后端面试中非常值得重点掌握的垃圾收集器。

它从 **JDK 9 开始成为 HotSpot Server VM 的默认垃圾收集器**。

### **1. G 1 的核心特点**

传统分代垃圾收集器通常将堆划分为连续的新生代和老年代。

而 G 1 将堆划分为多个大小相同的 Region。

```text
                G1 堆内存

┌──────┬──────┬──────┬──────┐
│ Eden │ Old  │ Eden │ Old  │
├──────┼──────┼──────┼──────┤
│  S   │ Old  │ Eden │ Free │
├──────┼──────┼──────┼──────┤
│ Old  │ Free │  S   │ Old  │
└──────┴──────┴──────┴──────┘
```

其中：

- Eden：存储新创建的对象。
- Survivor：存储经历 GC 后仍然存活的年轻代对象。
- Old：存储长期存活的对象。
- Free：空闲 Region。

G 1 仍然保留分代思想，但不同代的 Region 不必连续排列。

### **2. 为什么叫 Garbage First？**

因为 G 1 会估算不同 Region 的垃圾回收收益和回收成本。

在满足停顿时间目标的前提下，优先选择回收收益较高的 Region。

例如：

```text
Region A：垃圾占比 80%
Region B：垃圾占比 20%
Region C：垃圾占比 60%
```

G 1 会综合考虑垃圾量、存活对象复制成本等因素，选择合适的 Region 进行回收。

并不是简单地只看垃圾比例。

### **3. G 1 的优点**

- 可以并发执行部分垃圾回收工作。
- 通过 Region 管理堆内存。
- 支持年轻代回收和混合回收。
- 能够根据停顿时间目标调整回收策略。
- 通过对象转移和整理减少内存碎片。

例如：

```bash
-XX:+UseG1GC
```

启用 G 1。

还可以设置停顿时间目标：

```bash
-XX:MaxGCPauseMillis=200
```

表示希望 GC 停顿时间控制在约 200 ms 的目标范围内。

**注意：200 ms 是软目标，不是 JVM 保证的最大停顿时间。**

**一句话：G 1 通过 Region 管理堆，兼顾吞吐量和可预测的停顿时间。**

---

## **三、ZGC：低延迟垃圾收集器 ⭐⭐⭐⭐**

ZGC 的核心目标是：

**尽可能缩短垃圾回收导致的应用停顿。**

它和 G 1 最大的区别在于设计侧重点。

G 1 更注重吞吐量与停顿时间之间的平衡。

ZGC 则更加注重低延迟。

### **ZGC 为什么停顿时间短？**

因为它将大量垃圾回收工作设计为与应用线程并发执行。

例如：

```text
G1：

应用线程：████████    ████████    ████████
GC停顿：          ████        ████


ZGC：

应用线程：████████████████████████████
GC线程：     █████████████████
                 ↑
             大量工作并发执行
```

上图只是示意，ZGC 仍然存在少量 STW 阶段，并不是完全没有停顿。

ZGC 的特点：

- 以低延迟为主要目标。
- 大量回收工作与应用线程并发执行。
- 能够处理较大的堆。
- 适合对响应时间敏感的应用。

需要注意，ZGC 在不同 JDK 版本中经历了重要演进，例如引入分代 ZGC，因此具体实现和参数会随 JDK 版本变化。

---

## **四、Shenandoah GC**

Shenandoah 也是一种低延迟垃圾收集器。

它与 ZGC 有相似的设计目标：

**尽量让垃圾回收工作与应用线程并发执行，减少 STW 停顿。**

不过，Shenandoah 和 ZGC 的底层实现机制并不相同。

对于 Java 后端实习面试，知道它是一种低延迟垃圾收集器即可。

---

## **五、几种垃圾收集器对比 ⭐⭐⭐⭐⭐**

|**垃圾收集器**|**主要特点**|**侧重点**|
|---|---|---|
|Serial|单线程回收|简单、低资源开销|
|ParNew|多线程年轻代回收|并行回收，历史收集器|
|Parallel|多线程并行回收|**高吞吐量**|
|CMS|并发标记清除|**低停顿**，已移除|
|G 1|Region 管理、分代回收|**吞吐量与停顿时间平衡**|
|ZGC|大量回收工作并发执行|**低延迟**|
|Shenandoah|并发回收与对象转移|**低延迟**|

这里有一个非常容易混淆的知识点。

### **并行和并发有什么区别？**

**并行（Parallel）：多个 GC 线程一起执行垃圾回收。**

```text
应用线程：████████          ████████

GC线程1：        ██████
GC线程2：        ██████
```

GC 期间，应用线程可能全部暂停。

**并发（Concurrent）：GC 线程和应用线程在同一时间段内共同推进工作。**

```text
应用线程：████████████████████████

GC线程：     ██████████████
```

因此：

**并行强调多个 GC 线程一起工作，并发强调 GC 和应用线程能够同时推进。**

两者并不矛盾，一个垃圾收集器可以同时使用并行和并发技术。

## Q：Java 有哪些垃圾收集器？


Java 常见的垃圾收集器包括 Serial、ParNew、Parallel、CMS、G 1 和 ZGC 等。

Serial 是单线程垃圾收集器，实现比较简单；Parallel 使用多线程并行回收，主要追求高吞吐量。

CMS 是一种以低停顿为目标的并发垃圾收集器，但是由于采用标记-清除算法，容易产生内存碎片，而且已经在 JDK 14 中被移除。

G 1 是比较重要的现代垃圾收集器，它将堆划分为多个 Region，根据回收收益和停顿时间目标选择回收区域，兼顾吞吐量和停顿时间。

ZGC 则更加注重低延迟，通过让大量垃圾回收工作与应用线程并发执行，尽可能缩短 STW 停顿。

如果是普通 Java 后端应用，我会优先了解 G 1；如果业务对响应延迟要求非常严格，也会考虑 ZGC，并结合实际压测结果选择。



Serial 单线程，Parallel 重吞吐，CMS 降停顿，G 1 求平衡，ZGC 低延迟。**
