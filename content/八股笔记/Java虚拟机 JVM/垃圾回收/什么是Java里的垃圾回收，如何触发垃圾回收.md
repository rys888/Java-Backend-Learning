[[#Q：什么是 Java 垃圾回收？如何触发垃圾回收？]]
[[#Q：JVM 如何判断一个对象是不是垃圾？⭐⭐⭐⭐]]

Java 里的**垃圾回收（Garbage Collection，简称 GC）**就是 JVM 自动管理内存的一套机制：自动找出那些已经不再使用的对象，把它们占的内存收回来，避免无用对象一直占着堆空间。这也是 Java 后端面试的高频八股题。

这道题面试官一般从三个方面问：**什么是垃圾回收？JVM 怎么判断一个对象可以被回收？什么情况下会触发垃圾回收？** 下面按这三块整理。

## **一、什么是 Java 的垃圾回收？**

对象创建的时候，JVM 通常会在堆里分配一块内存来存放它：

```java
User user = new User();
```

换成方法里的写法：

```java
public void test() {
    User user = new User();
}
```

方法执行时，局部变量 `user` 放在虚拟机栈的栈帧里，指向堆中的 `User` 对象：

```text
          JVM 内存

虚拟机栈                   堆
   │                       │
   │                    User对象
   │                       ↑
   └──── user引用 ──────────┘
```

方法执行结束，栈帧出栈，局部变量 `user` 跟着消失。这时候如果没有任何其他引用指向这个 `User` 对象，它就变成了没人引用的对象，可能被回收。

**GC 的作用，就是识别这些不再可达的对象，并回收它们占用的内存。**

这里要留意：**对象没有引用之后，不代表 JVM 会立即回收它**，具体回收时机由 JVM 和垃圾收集器决定。

## Q：JVM 如何判断一个对象是不是垃圾？⭐⭐⭐⭐

主要有两种判断思路。

### **1. 引用计数法**

原理很简单：**每个对象维护一个引用计数器，多一个引用指向它，计数器加一；引用失效，计数器减一；减到 0 就认为这个对象可以回收。**

比如：

```java
User user1 = new User();
User user2 = user1;
```

```text
user1 ──┐
        ├──→ User对象（引用计数 = 2）
user2 ──┘
```

接着 `user1 = null;`，引用计数变成 1；再 `user2 = null;`，引用计数变成 0，这时就认为对象可以回收了。

但引用计数法有个明显的坑：**单独用的话解决不了循环引用。**

```java
class Node {
    Node next;
}

Node a = new Node();
Node b = new Node();

a.next = b;
b.next = a;

a = null;
b = null;
```

```text
        Node A
          │ ↑
          ↓ │
        Node B

外部已经没有引用指向它们
```

此时外部已经没有有效引用能走到 A 和 B，但它俩还互相指着对方。单看引用计数，**Node A 和 Node B 的计数都还是 1**，谁都回收不掉。

所以**主流 JVM 的垃圾回收并不是单纯依靠引用计数法。**

### **2. 可达性分析算法（Reachability Analysis）⭐⭐⭐⭐⭐**

这是 Java GC 判断对象是否存活的核心思路：**从一组称为 GC Roots 的根对象或根引用出发，沿着引用关系向下搜索，如果某个对象无法从 GC Roots 到达，那么它就可能被回收。**

```text
                 GC Roots
                    │
                    ▼
                 Object A
                    │
                    ▼
                 Object B
                    │
                    ▼
                 Object C


          Object D ←→ Object E
```

其中 A、B、C 可以从 GC Roots 到达，属于可达对象；D、E 虽然互相引用，但无法从 GC Roots 到达，因此可以被回收。**这也正好解决了引用计数法处理不了循环引用的问题。**

#### **GC Roots 包括哪些？**

常见的 GC Roots 来源有：

|**GC Roots 来源**|**示例**|
|---|---|
|虚拟机栈中的引用|正在执行的方法中的局部变量引用|
|类的静态字段引用| `static User user` |
|JNI 引用|Native 方法持有的 Java 对象|
|JVM 内部引用|某些 JVM 内部需要保持存活的对象|

注意这里是有效的根引用，并不是所有历史上创建过的局部变量或静态字段都永久作为 GC Roots。

## **三、什么情况下会触发垃圾回收？⭐⭐⭐⭐⭐**

这里是这道题的重点：**垃圾回收通常由 JVM 根据内存使用情况和垃圾收集器的策略自动触发。**

结合之前学过的 JVM 堆结构来理解，经典分代模型长这样：

```text
                  JVM 堆
                    │
          ┌─────────┴─────────┐
          │                   │
        新生代               老年代
          │                   │
     ┌────┼────┐              │
     │    │    │              │
   Eden  S0   S1           Old
```

### **1. Eden 区空间不足**

这是最常见的触发场景之一。假设不停创建对象：

```java
public void test() {
    for (int i = 0; i < 10000; i++) {
        User user = new User();
    }
}
```

在经典分代收集器里，新对象通常优先分配到 Eden 区。对象一多，Eden 慢慢被占满，放不下新对象时就会触发一次 Young GC：

```text
Eden 空间逐渐被占满
         ↓
无法继续正常分配
         ↓
触发 Young GC / Minor GC
         ↓
回收不再存活的对象
         ↓
为新对象腾出空间
```

举个小例子：Eden 里依次放了 `[A][B][C][D][E][F]`，其中只有 A、C、F 还活着。GC 之后，无用的对象被回收，存活对象按照收集器策略进入 Survivor 等区域。

这就是经典的 **Minor GC** 场景。不过需要注意，现代垃圾收集器不一定使用固定的 Eden、S0、S1 分区，具体触发方式也会有所不同。

### **2. 老年代空间不足**

在经典分代模型中，长期存活的对象可能被晋升到老年代：

```text
新生代
   ↓
多次 GC 后仍然存活
   ↓
晋升到老年代
```

如果老年代空间不足，JVM 可能需要执行老年代回收，或者触发更大范围的垃圾回收。这里需要区分三个概念：

|**GC 类型**|**主要含义**|
|---|---|
|Young GC / Minor GC|回收年轻代|
|Old GC|主要针对老年代进行回收|
|Full GC|对堆进行更全面的回收，具体范围依收集器而定|

**注意：老年代空间不足不等于一定立即触发 Full GC。** G1、ZGC 等现代垃圾收集器具有不同的回收策略，可能通过并发回收等方式处理内存压力。

### **3. JVM 检测到内存压力**

除了某个内存区域空间不足，垃圾收集器还可能根据堆内存占用情况、对象分配速度、老年代使用比例、GC 预测与调度策略这些因素主动启动垃圾回收。比如 G1 可以根据堆占用情况启动并发标记周期，而不必等到整个堆完全耗尽。

所以：**GC 并不一定要等到内存满了才会执行。**

### **4. 主动调用 System.gc()**

Java 允许程序员主动请求垃圾回收：

```java
System.gc();
```

例如：

```java
public class Demo {
    public static void main(String[] args) {

        User user = new User();

        user = null;

        System.gc();
    }
}
```

但是一定要注意：**`System.gc()` 只是向 JVM 发出垃圾回收请求，并不能保证立即执行 GC，也不保证一定触发 Full GC。** 具体行为取决于 JVM 实现、垃圾收集器和相关参数。

在实际 Java 后端项目中，通常不建议随意调用 `System.gc()`，因为它可能造成额外的 GC 开销，甚至引发较长的停顿。

## **四、GC 和内存溢出有什么关系？**

前面刚学过内存泄漏和内存溢出，可以把这几个知识点联系起来。假设：

```java
private static final List<byte[]> LIST = new ArrayList<>();

public static void main(String[] args) {

    while (true) {
        LIST.add(new byte[1024 * 1024]);
    }
}
```

执行过程是这样的：

```text
不断创建对象
      ↓
堆内存占用增加
      ↓
JVM 尝试进行垃圾回收
      ↓
但是 LIST 仍然持有对象
      ↓
这些对象仍然可达
      ↓
GC 无法回收它们
      ↓
可用内存越来越少
      ↓
最终可能发生 OOM
```

**GC 并不是万能的**，如果无用对象仍然被强引用持有，GC 也无法直接将它们回收。这就是为什么 Java 虽然有自动垃圾回收机制，仍然可能发生内存泄漏。

## Q：什么是 Java 垃圾回收？如何触发垃圾回收？

Java 的垃圾回收，也就是 GC，是 JVM 自动管理内存的一种机制，主要负责识别和回收不再使用的对象，减少程序员手动管理内存的负担。

JVM 主要通过可达性分析算法判断对象是否存活，从 GC Roots 出发遍历对象引用关系，如果某个对象无法从 GC Roots 到达，那么它就可能被垃圾回收。

GC 通常由 JVM 根据内存使用情况自动触发。例如在经典分代垃圾收集器中，Eden 区空间不足时通常会触发 Minor GC，回收新生代中的无用对象；老年代空间不足时，也可能触发老年代回收或者 Full GC。此外，JVM 还可能根据堆内存占用比例和垃圾收集器的策略主动执行 GC。

程序员也可以通过 `System.gc()` 请求垃圾回收，但这只是一个建议，并不能保证 JVM 立即执行，也不保证一定触发 Full GC。

---

## **六、最后记住三个重点**

**① GC 是什么？** JVM 自动识别并回收不再需要的对象所占用的内存。

**② 如何判断对象是否可以回收？** 主要通过 GC Roots 进行可达性分析，而不是单纯使用引用计数法。

**③ 什么情况下触发 GC？**

```text
JVM 自动触发
    │
    ├── 新生代空间不足
    │      └── Young GC / Minor GC
    │
    ├── 老年代空间不足
    │      └── 老年代回收 / 可能 Full GC
    │
    └── 收集器根据内存占用等策略
           └── 主动启动回收


程序员请求
    │
    └── System.gc()
           └── 不保证立即执行
```

**一句话记忆：GC 通过可达性分析判断对象是否存活，并根据内存压力和收集器策略自动触发垃圾回收。**
