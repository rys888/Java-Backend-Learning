
[[#Q：什么是 Java 垃圾回收？如何触发垃圾回收？]]
[[#Q：JVM 如何判断一个对象是不是垃圾？⭐⭐⭐⭐]]

Java 中的**垃圾回收（Garbage Collection，简称 GC）**，是 JVM 自动管理内存的一种机制，也是 Java 后端面试中的高频八股题。

首先记住一句话：

**垃圾回收就是 JVM 自动识别并回收不再使用的对象所占用的内存，避免无用对象长期占据内存空间。**

面试官通常会从三个方面考察：

1. 什么是垃圾回收？
2. JVM 如何判断对象可以被回收？
3. 什么情况下会触发垃圾回收？

## **一、什么是 Java 的垃圾回收？**

我们之前学过 Java 对象的创建过程：

```java
User user = new User();
```

执行这段代码时，JVM 通常会在堆中分配内存，用于存储 `User` 对象。

假设：

```java
public void test() {
    User user = new User();
}
```

当 `test()` 方法执行结束后：

```text
          JVM 内存

虚拟机栈                   堆
   │                       │
   │                    User对象
   │                       ↑
   └──── user引用 ──────────┘
```

方法执行结束，栈帧出栈，局部变量 `user` 不再存在。

如果没有其他引用指向这个 `User` 对象：

```text
虚拟机栈                   堆
   │                       │
   │                    User对象
   │                       ↑
   │                       │
   └── 原来的引用已消失 ── ×
```

那么这个对象就可能成为垃圾回收的对象。

**GC 的作用，就是识别这些不再可达的对象，并回收它们占用的内存。**

需要注意：

**对象没有引用后，不代表 JVM 会立即回收它。**

垃圾回收的具体时机由 JVM 和垃圾收集器决定。

## Q：JVM 如何判断一个对象是不是垃圾？⭐⭐⭐⭐

主要有两种判断思路：

### **1. 引用计数法**

原理非常简单：

每个对象维护一个引用计数器，有一个引用指向它，计数器就加一；引用失效，计数器就减一。

例如：

```java
User user1 = new User();

User user2 = user1;
```

此时：

```text
user1 ──┐
        ├──→ User对象（引用计数 = 2）
user2 ──┘
```

如果：

```java
user1 = null;
```

引用计数变为 1。

继续：

```java
user2 = null;
```

引用计数变为 0。

这时就认为对象可以回收。

但是引用计数法有一个明显的问题：

**无法单独解决循环引用。**

例如：

```java
class Node {
    Node next;
}
```

```java
Node a = new Node();
Node b = new Node();

a.next = b;
b.next = a;

a = null;
b = null;
```

此时：

```text
        Node A
          │ ↑
          ↓ │
        Node B

外部已经没有引用指向它们
```

虽然两个对象已经无法从程序中的有效根引用访问，但它们仍然互相引用。

如果单纯使用引用计数法：

```text
Node A 引用计数 = 1

Node B 引用计数 = 1
```

它们就无法被回收。

因此，**主流 JVM 的垃圾回收并不是单纯依靠引用计数法。**

### **2. 可达性分析算法（Reachability Analysis）⭐⭐⭐⭐⭐**

这是 Java GC 判断对象是否存活的核心思路。

**从一组称为 GC Roots 的根对象或根引用出发，沿着引用关系向下搜索。如果某个对象无法从 GC Roots 到达，那么它就可能被回收。**

例如：

```text
                 GC Roots
                    │
                    ▼
                 Object A
                    │
                    ▼
                 Object B
                    │
                    ▼
                 Object C


          Object D ←→ Object E
```

其中：

- A、B、C 可以从 GC Roots 到达，属于可达对象。
- D、E 虽然互相引用，但无法从 GC Roots 到达，因此可以被回收。

**这就解决了引用计数法无法处理循环引用的问题。**

#### **GC Roots 包括哪些？**

常见的 GC Roots 来源有：

|**GC Roots 来源**|**示例**|
|---|---|
|虚拟机栈中的引用|正在执行的方法中的局部变量引用|
|类的静态字段引用| `static User user` |
|JNI 引用|Native 方法持有的 Java 对象|
|JVM 内部引用|某些 JVM 内部需要保持存活的对象|

注意：这里说的是有效的根引用，并不是所有历史上创建过的局部变量或静态字段都永久作为 GC Roots。

## **三、什么情况下会触发垃圾回收？⭐⭐⭐⭐⭐**

这是你这道题的重点。

**垃圾回收通常由 JVM 根据内存使用情况和垃圾收集器的策略自动触发。**

我们结合之前学过的 JVM 堆结构来理解。

经典分代模型：

```text
                  JVM 堆
                    │
          ┌─────────┴─────────┐
          │                   │
        新生代               老年代
          │                   │
     ┌────┼────┐              │
     │    │    │              │
   Eden  S0   S1           Old
```

### **1. Eden 区空间不足**

这是最常见的触发场景之一。

假设不断创建对象：

```java
public void test() {
    for (int i = 0; i < 10000; i++) {
        User user = new User();
    }
}
```

在经典分代收集器中，新对象通常优先分配到 Eden 区。

```text
Eden 区

┌───────────────────────────┐
│ User1 User2 User3 User4...│
└───────────────────────────┘
```

随着对象不断创建：

```text
Eden 空间逐渐被占满
         ↓
无法继续正常分配
         ↓
触发 Young GC / Minor GC
         ↓
回收不再存活的对象
         ↓
为新对象腾出空间
```

例如：

```text
GC 前：

Eden
[A][B][C][D][E][F]

其中 A、C、F 仍然存活


GC 后：

Eden 中的无用对象被回收

存活对象根据收集器策略
进入 Survivor 等区域
```

这就是经典的 **Minor GC** 场景。

不过需要注意，现代垃圾收集器不一定使用固定的 Eden、S 0、S 1 分区，具体触发方式也会有所不同。

### **2. 老年代空间不足**

在经典分代模型中，长期存活的对象可能被晋升到老年代。

例如：

```text
新生代
   ↓
多次 GC 后仍然存活
   ↓
晋升到老年代
```

如果老年代空间不足，JVM 可能需要执行老年代回收，或者触发更大范围的垃圾回收。

这里需要区分三个概念：

|**GC 类型**|**主要含义**|
|---|---|
|Young GC / Minor GC|回收年轻代|
|Old GC|主要针对老年代进行回收|
|Full GC|对堆进行更全面的回收，具体范围依收集器而定|

**注意：老年代空间不足不等于一定立即触发 Full GC。**

例如 G 1、ZGC 等现代垃圾收集器具有不同的回收策略，可能通过并发回收等方式处理内存压力。

### **3. JVM 检测到内存压力**

除了某个内存区域空间不足，垃圾收集器还可能根据：

- 堆内存占用情况
- 对象分配速度
- 老年代使用比例
- GC 预测与调度策略

主动启动垃圾回收。

例如 G 1 可以根据堆占用情况启动并发标记周期，而不必等到整个堆完全耗尽。

因此：

**GC 并不一定要等到内存满了才会执行。**

### **4. 主动调用 System.gc()**

Java 允许程序员主动请求垃圾回收：

```java
System.gc();
```

例如：

```java
public class Demo {
    public static void main(String[] args) {

        User user = new User();

        user = null;

        System.gc();
    }
}
```

但是一定要注意：

 `System.gc()` 只是向 JVM 发出垃圾回收请求，并不能保证立即执行 GC。

而且：

```java
System.gc();
```

也不保证一定触发 Full GC。

具体行为取决于 JVM 实现、垃圾收集器和相关参数。

在实际 Java 后端项目中，通常不建议随意调用 `System.gc()`，因为它可能造成额外的 GC 开销，甚至引发较长的停顿。

## **四、GC 和内存溢出有什么关系？**

你之前刚学过内存泄漏和内存溢出，可以把这几个知识点联系起来。

假设：

```java
private static final List<byte[]> LIST = new ArrayList<>();

public static void main(String[] args) {

    while (true) {
        LIST.add(new byte[1024 * 1024]);
    }
}
```

执行过程：

```text
不断创建对象
      ↓
堆内存占用增加
      ↓
JVM 尝试进行垃圾回收
      ↓
但是 LIST 仍然持有对象
      ↓
这些对象仍然可达
      ↓
GC 无法回收它们
      ↓
可用内存越来越少
      ↓
最终可能发生 OOM
```

因此：

**GC 并不是万能的。**

如果无用对象仍然被强引用持有，GC 也无法直接将它们回收。

这就是为什么 Java 虽然有自动垃圾回收机制，仍然可能发生内存泄漏。

## Q：什么是 Java 垃圾回收？如何触发垃圾回收？

Java 的垃圾回收，也就是 GC，是 JVM 自动管理内存的一种机制，主要负责识别和回收不再使用的对象，减少程序员手动管理内存的负担。

JVM 主要通过可达性分析算法判断对象是否存活，从 GC Roots 出发遍历对象引用关系，如果某个对象无法从 GC Roots 到达，那么它就可能被垃圾回收。

GC 通常由 JVM 根据内存使用情况自动触发。例如，在经典分代垃圾收集器中，当 Eden 区空间不足时，通常会触发 Minor GC，回收新生代中的无用对象；当老年代空间不足时，也可能触发老年代回收或者 Full GC。

此外，JVM 还可能根据堆内存占用比例和垃圾收集器的策略主动执行 GC。

程序员也可以通过 `System.gc()` 请求垃圾回收，但这只是一个建议，并不能保证 JVM 立即执行，也不保证一定触发 Full GC。

## **六、最后记住三个重点**

**① GC 是什么？**

JVM 自动识别并回收不再需要的对象所占用的内存。

**② 如何判断对象是否可以回收？**

主要通过 GC Roots 进行可达性分析，而不是单纯使用引用计数法。

**③ 什么情况下触发 GC？**

```text
JVM 自动触发
    │
    ├── 新生代空间不足
    │      └── Young GC / Minor GC
    │
    ├── 老年代空间不足
    │      └── 老年代回收 / 可能 Full GC
    │
    └── 收集器根据内存占用等策略
           └── 主动启动回收


程序员请求
    │
    └── System.gc()
           └── 不保证立即执行
```

**一句话记忆：GC 通过可达性分析判断对象是否存活，并根据内存压力和收集器策略自动触发垃圾回收。**
