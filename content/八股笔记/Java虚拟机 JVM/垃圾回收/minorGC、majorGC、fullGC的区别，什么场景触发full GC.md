
[[#Q：Minor GC、Major GC 和 Full GC 有什么区别？什么情况下会触发 Full GC？]]

Java 中的 **Minor GC、Major GC 和 Full GC**，主要区别在于**垃圾回收的范围不同**。

尤其需要掌握：**Full GC 为什么会触发，以及为什么要尽量减少 Full GC。**

先记住一个结论：

**Minor GC 主要回收新生代，Major GC 主要回收老年代，Full GC 通常对整个 Java 堆进行更全面的回收。**

不过需要注意，Major GC 的定义在不同资料和垃圾收集器中并不完全统一。

## **一、Minor GC、Major GC、Full GC 有什么区别？**

先回顾经典分代垃圾收集器的堆结构：

```text
                  JVM 堆
                     │
          ┌──────────┴──────────┐
          │                     │
        新生代                 老年代
          │                     │
    ┌─────┼─────┐               │
    │     │     │               │
   Eden   S0    S1             Old
```

### **1. Minor GC：新生代垃圾回收 ⭐⭐⭐⭐⭐**

**Minor GC 主要负责回收新生代中的垃圾对象。**

在经典分代收集器中，新对象通常优先分配到 Eden 区。

例如：

```java
public void test() {
    for (int i = 0; i < 10000; i++) {
        User user = new User();
    }
}
```

随着对象不断创建，Eden 区的空间逐渐被占满。

```text
不断创建对象
     ↓
Eden 空间不足
     ↓
触发 Minor GC
     ↓
回收新生代垃圾对象
     ↓
存活对象进入 Survivor
或根据条件晋升老年代
```

**Minor GC 的特点：**

- 主要回收新生代。
- 通常触发比较频繁。
- 由于新生代中大量对象生命周期较短，回收通常比较快。
- 经典分代收集器的 Minor GC 通常需要 STW。

注意，Minor GC 虽然主要回收新生代，但判断年轻代对象是否存活时，也需要考虑来自老年代等区域的引用。

### **2. Major GC：老年代垃圾回收 ⭐⭐⭐⭐**

**Major GC 通常指针对老年代的垃圾回收。**

例如：

```text
对象长期存活
     ↓
晋升到老年代
     ↓
老年代内存占用增加
     ↓
触发老年代回收
```

老年代中的对象通常存活时间较长，因此回收可能涉及更多存活对象的处理。

不过这里有一个容易混淆的地方：

**Major GC 并不是一个在所有 JVM 和垃圾收集器中都具有统一含义的术语。**

有些资料将 Major GC 理解为老年代 GC，也有些资料将它与 Full GC 混用。

因此，实际分析 GC 日志时，应该根据具体垃圾收集器判断。

### **3. Full GC：全堆垃圾回收 ⭐⭐⭐⭐⭐**

**Full GC 通常指对整个 Java 堆进行更全面的垃圾回收。**

在经典分代模型中，可以简单理解为：

```text
                 Full GC
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
        新生代               老年代
          │                   │
     Eden、S0、S1             Old
```

它通常还可能涉及类卸载等工作，具体范围取决于垃圾收集器。

Full GC 的特点：

- 回收范围通常更大。
- 可能需要处理大量存活对象。
- 通常比普通 Young GC 开销更高。
- 在常见 HotSpot 收集器中，Full GC 往往伴随较长的 STW 停顿。

**所以，在 Java 后端项目中，我们通常希望避免频繁发生 Full GC。**

---

## **二、三种 GC 的区别总结**

|**对比**|**Minor GC**|**Major GC**|**Full GC**|
|---|---|---|---|
|回收区域|新生代|主要是老年代|通常是整个 Java 堆|
|常见触发原因|新生代分配空间不足|老年代回收需求|严重内存压力、分配失败等|
|触发频率|通常较高|通常较低|希望尽量少|
|回收耗时|通常较短|取决于收集器|通常较长|
|是否 STW|经典实现通常需要|取决于收集器|常见实现通常需要|
|性能影响|相对较小|视情况而定|可能明显影响响应时间|

这里要强调：

**不是每次老年代空间不足都会直接触发 Full GC，也不是每个垃圾收集器都有独立的 Major GC。**

例如，G 1 可以通过 Mixed GC 回收年轻代和部分老年代 Region，不必每次都执行 Full GC。

# **三、什么情况下会触发 Full GC？⭐⭐⭐⭐⭐**

这是面试的重点。

常见的触发场景主要有以下几种。

## **1. 老年代空间不足**

这是经典分代垃圾收集器中比较常见的场景。

假设：

```text
老年代总容量：100MB

已使用：95MB

剩余：5MB
```

现在有一个对象需要从新生代晋升到老年代：

```text
需要晋升的对象：10MB
```

但是：

```text
老年代剩余空间：5MB

需要空间：10MB
```

空间不足。

此时 JVM 可能尝试进行垃圾回收。

```text
对象需要晋升
      ↓
老年代空间不足
      ↓
尝试进行必要的垃圾回收
      ↓
仍然无法满足分配需求
      ↓
可能触发 Full GC
```

如果 Full GC 后仍然没有足够空间，就可能发生：

```java
java.lang.OutOfMemoryError: Java heap space
```

**注意：老年代空间不足是 Full GC 的可能触发原因，而不是必然触发条件。**

---

## **2. 对象晋升失败（Promotion Failure）**

你之前学过：

对象通常先进入 Eden，经过 Young GC 后，仍然存活的对象可能进入 Survivor，之后再晋升到老年代。

```text
Eden
  ↓
Young GC
  ↓
Survivor
  ↓
多次 GC 后存活
  ↓
老年代
```

但是，如果对象需要晋升，而老年代没有足够空间：

```text
Young GC
    ↓
发现大量存活对象
    ↓
Survivor 放不下
    ↓
尝试晋升老年代
    ↓
老年代空间不足
    ↓
晋升失败
```

在某些经典分代垃圾收集器中，晋升失败可能导致 Full GC。

因此：

**对象晋升失败也是 Full GC 的一个常见原因。**

需要注意，它和老年代空间不足有一定联系，但侧重点不同：

- 老年代空间不足：强调老年代整体的空间压力。
- 晋升失败：强调年轻代对象向老年代转移时无法完成分配。

---

## **3. 主动调用 System.gc()**

Java 提供了一个方法：

```java
System.gc();
```

例如：

```java
public class Demo {

    public static void main(String[] args) {

        User user = new User();

        user = null;

        System.gc();
    }
}
```

在一些 HotSpot 配置中，调用 `System.gc()` 可能触发 Full GC。

但是：

 `System.gc()`  **只是请求 GC，不保证一定执行 Full GC。**

具体行为取决于垃圾收集器及 JVM 参数。

例如，某些配置会忽略显式 GC 请求，某些收集器则可能使用并发回收来响应。

实际 Java 后端开发中，通常不建议随意调用：

```java
System.gc();
```

因为它可能造成不必要的垃圾回收开销。

---

## **4. 元空间内存压力过大**

你之前学过：

**元空间（Metaspace）主要存储类元数据，使用本地内存，不属于 Java 堆。**

假设应用不断动态生成类：

```text
不断生成新类
      ↓
类元数据不断增加
      ↓
元空间使用量增加
      ↓
达到相关 GC 阈值
      ↓
JVM 尝试触发 GC
      ↓
尝试卸载不再需要的类
```

在某些 HotSpot 收集器或配置下，元空间内存压力可能触发 Full GC。

但并非所有情况下都会直接执行 Full GC，现代收集器可能通过并发标记和类卸载处理。

如果类无法卸载，且元空间达到上限，最终可能发生：

```java
java.lang.OutOfMemoryError: Metaspace
```

**这里要注意：元空间不在堆中，但元空间的内存压力仍然可能影响 JVM 的 GC 行为。**

---

## **5. G 1 垃圾回收器发生回收失败**

这是现代 Java 后端项目中值得了解的情况。

G 1 正常情况下主要通过：

- Young GC：回收年轻代 Region。
- Concurrent Mark：并发标记存活对象。
- Mixed GC：回收年轻代以及部分老年代 Region。

来管理堆内存。

但是，如果 G 1 无法及时回收足够的空间，可能发生对象转移失败等问题。

例如：

```text
应用不断创建对象
       ↓
堆内存占用持续增加
       ↓
G1 尝试 Young GC / Mixed GC
       ↓
回收速度跟不上分配速度
       ↓
对象转移或分配失败
       ↓
可能退化为 Full GC
```

这种情况通常意味着 JVM 已经面临比较严重的内存压力。

因此，在使用 G 1 的 Java 后端项目中，如果发现频繁 Full GC，需要重点排查：

- 堆空间是否不足。
- 是否存在大量长期存活对象。
- 对象分配速度是否过快。
- 是否存在内存泄漏。

## **四、为什么 Full GC 会影响 Java 后端性能？**

假设你开发了一个 Spring Boot 项目：

```text
用户
 │
 ▼
Spring Boot
 │
 ▼
MySQL / Redis
```

正常情况下：

```text
请求1：20ms
请求2：25ms
请求3：18ms
```

但是如果 JVM 发生一次较长的 STW Full GC：

```text
时间线：

应用执行 ────────┐
                 │
                 ▼
              Full GC
              STW 800ms
                 │
                 ▼
应用恢复 ────────────────
```

这段时间内，应用线程暂停执行 Java 代码。

原本只需要 20 ms 的请求，可能因为等待 GC 而耗费数百毫秒甚至更长时间。

这会影响：

**平均响应时间、P 95/P 99 响应时间，以及系统吞吐量。**

所以在高并发 Java 后端项目中，GC 调优的一个重要目标就是：

**避免频繁或耗时过长的 Full GC，减少垃圾回收对业务响应时间的影响。**

不过，GC 调优不等于单纯追求 Full GC 次数为零，还需要综合考虑吞吐量、停顿时间和内存占用。

## Q：Minor GC、Major GC 和 Full GC 有什么区别？什么情况下会触发 Full GC？


Minor GC 主要回收新生代，通常在 Eden 区空间不足时触发，回收比较频繁，但一般耗时较短。

Major GC 通常指老年代垃圾回收，不过这个概念在不同垃圾收集器中的定义并不完全统一。

Full GC 通常指对整个 Java 堆进行更全面的垃圾回收，回收范围比较大，在常见 HotSpot 收集器中往往伴随较长的 STW 停顿。

Full GC 的常见触发场景包括：第一，老年代空间不足；第二，Young GC 时对象晋升失败；第三，显式调用 `System.gc()`；第四，元空间内存压力过大；第五，G 1 等垃圾收集器在正常回收无法满足内存需求时发生退化。

不过，这些情况是否真正触发 Full GC，还需要结合具体的垃圾收集器判断。

在实际 Java 后端项目中，如果 Full GC 频繁发生，我会重点排查堆内存配置、对象分配速度、长期存活对象和内存泄漏问题。

## **六、最后记住三个重点**

**① 三种 GC 的区别**

```text
Minor GC → 主要回收新生代

Major GC → 主要回收老年代（术语不完全统一）

Full GC  → 通常回收整个 Java 堆
```

**② Full GC 常见触发场景**

```text
                 Full GC
                    │
       ┌────────────┼────────────┐
       │            │            │
   老年代不足    晋升失败    System.gc()
       │            │            │
       └────────────┼────────────┘
                    │
              元空间压力
                    │
              G1 回收失败
```

**③ 为什么要减少 Full GC？**

**因为 Full GC 通常回收范围更大，可能造成较长时间的 STW，从而影响 Java 后端服务的响应时间和吞吐量。**

**一句话记忆：Minor 回收年轻代，Major 回收老年代，Full 回收范围更大；老年代不足、晋升失败、元空间压力和回收退化，都可能导致 Full GC。**
