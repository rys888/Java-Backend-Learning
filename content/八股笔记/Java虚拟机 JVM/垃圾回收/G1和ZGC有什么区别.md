G 1 和 ZGC 都是 HotSpot JVM 中以**降低垃圾回收停顿时间**为重要目标的垃圾收集器，但两者的设计思路不同。

**G 1 更注重吞吐量和停顿时间之间的平衡，而 ZGC 更注重极低的 GC 停顿时间。**

对于 Java 后端实习面试，重点掌握 **STW、并发回收、对象转移和适用场景**这四个方面即可。

## **一、G 1 和 ZGC 的核心区别 ⭐⭐⭐⭐⭐**

|**对比维度**|**G 1**|**ZGC**|
|---|---|---|
|核心目标|平衡吞吐量和停顿时间|尽可能降低 GC 停顿|
|内存布局|Region 分区管理|基于分区的堆管理|
|并发标记|支持|支持|
|对象转移|主要在 STW 阶段进行|主要与应用线程并发进行|
|STW 时间|通常为毫秒级，可能更长|通常非常短，目标为亚毫秒级|
|吞吐量|通常具有较好的综合表现|可能需要付出一定吞吐量代价|
|分代机制|支持分代|新版 ZGC 支持分代|
|适用场景|通用 Java 后端服务|对响应延迟非常敏感的服务|
|默认情况|JDK 9 起为 HotSpot 默认 GC|通常需要主动配置|

需要注意，实际停顿时间和吞吐量取决于 JDK 版本、堆大小和业务负载，并不是 ZGC 在所有场景下都比 G 1 快。

---

## **二、最大的区别：对象转移时是否需要 STW ⭐⭐⭐⭐⭐**

这是理解 G 1 和 ZGC 最关键的地方。

### **1. G 1：主要在 STW 阶段转移对象**

我们之前学习过 G 1 的三种主要工作：

- Young GC：回收年轻代。
- 并发标记：分析对象存活情况。
- Mixed GC：回收年轻代和部分老年代。

其中，G 1 的并发标记可以与应用线程同时执行。

但是，**Young GC 和 Mixed GC 中的对象复制、转移工作，主要需要暂停应用线程。**

例如：

```text
G1 垃圾回收

应用线程：████████    暂停    ████████████
                         │
GC 线程：   并发标记     对象转移
                         │
                        STW
```

假设一个 Region 中有大量存活对象：

```text
Region A：

[A][垃圾][B][垃圾][C]
```

G 1 需要将 A、B、C 复制到其他 Region。

如果存活对象比较多，对象转移可能耗费较长时间，导致 STW 增加。

虽然 G 1 可以通过控制回收集合的大小来尽量降低停顿，但无法完全消除对象转移带来的 STW 开销。

### **2. ZGC：对象转移主要并发执行**

ZGC 的一个重要特点是：

**对象转移的大部分工作可以与应用线程同时执行。**

例如：

```text
ZGC 垃圾回收

应用线程：██████████████████████████

GC 线程：    并发标记 → 并发转移
```

也就是说，ZGC 不需要像 G 1 一样，在一次较长的 STW 中完成主要对象转移工作。

因此，即使堆内存较大，ZGC 也能够将 GC 停顿控制在很低的水平。

当然，ZGC 并不是完全没有 STW，只是需要暂停应用线程的阶段通常非常短。

**一句话：G 1 主要在 STW 中转移对象，ZGC 主要并发转移对象。**

---

## **三、ZGC 为什么能够并发转移对象？⭐⭐⭐⭐⭐**

这里涉及 ZGC 的两个重要技术：

**有色指针（Colored Pointers）和读屏障（Load Barriers）。**

### **1. 有色指针**

普通对象引用可以简单理解为：

```text
对象引用 → 对象内存地址
```

而 ZGC 会利用指针中的部分位保存 GC 相关的状态信息。

可以简单理解为：

```text
对象引用
   │
   ├── 对象地址信息
   │
   └── GC 状态信息
```

这些信息可以帮助 ZGC 判断引用是否需要处理。

注意：这里的“颜色”并不是真正的颜色，而是指针中的标记信息；具体编码方式与 JDK 版本有关。

### **2. 读屏障**

假设一个对象原本存放在地址 A：

```text
User 对象 → 地址 A
```

ZGC 正在将对象转移到地址 B：

```text
地址 A → 地址 B
```

但是应用线程可能仍然持有指向旧地址 A 的引用。

那么问题来了：

**如果对象已经移动，应用线程访问旧地址怎么办？**

ZGC 可以通过读屏障等机制，在应用线程读取对象引用时检查并处理相关状态。

简化理解：

```text
应用线程读取对象引用
          ↓
        读屏障
          ↓
检查引用是否需要修正
          ↓
必要时处理或更新引用
          ↓
访问正确的对象
```

这样，即使 GC 线程正在移动对象，应用线程也可以继续运行。

这就是 ZGC 能够实现并发对象转移的重要基础。

不过，实际 ZGC 还需要转发表、引用修正等机制配合，并不是只靠读屏障就能完成并发转移。

## **四、G 1 和 ZGC 的性能侧重点不同**

假设你开发了一个 Spring Boot 服务。

正常情况下：

```text
请求1：20ms
请求2：25ms
请求3：18ms
```

### **使用 G 1**

如果某次 GC 需要较长时间复制存活对象：

```text
正常请求：20ms

发生 GC：
请求 → STW 100ms → 业务处理 20ms

总耗时可能达到 120ms
```

### **使用 ZGC**

ZGC 将主要对象转移工作并发执行：

```text
正常请求：20ms

发生 GC：
请求 → 短暂 STW → 业务处理

GC 造成的额外停顿通常较小
```

所以，ZGC 更适合对响应延迟要求非常严格的系统。

但有一个容易忽略的问题：

**低停顿不等于高吞吐量。**

ZGC 需要通过并发 GC 线程、读屏障等机制完成回收工作。

这些操作也会消耗 CPU 和内存资源。

因此，在一些业务场景下，G 1 的整体吞吐量可能更高。

---

## **五、实际 Java 后端项目应该选择哪个？**

### **G 1：更适合一般 Java 后端服务**

例如：

- 电商订单系统。
- 企业管理平台。
- 普通 Spring Boot Web 服务。
- 大多数没有极端延迟要求的业务系统。

G 1 能够在吞吐量和停顿时间之间取得较好的平衡。

对于普通 Java 后端项目，**优先使用默认的 G 1，通常是合理的起点**。

### **ZGC：更适合低延迟服务**

例如：

- 对尾延迟要求严格的在线服务。
- 大堆内存、存活对象较多的服务。
- 希望尽量降低 GC 对 P 99 响应时间影响的系统。

如果一个系统非常关注响应时间的稳定性，ZGC 值得重点考虑。

不过，最终仍然应该通过 GC 日志、吞吐量和 P 95/P 99 延迟等指标进行验证。

## **六、补充：ZGC 也有分代机制吗？**

有。

早期 ZGC 采用非分代设计。

后来引入了 **Generational ZGC（分代 ZGC）**：

- JDK 21：引入分代 ZGC。
- JDK 23：分代 ZGC 成为 ZGC 的默认模式。
- JDK 24：移除了非分代 ZGC。

因此，不能简单认为：

**G 1 有分代，ZGC 没有分代。**

在现代 JDK 中，G 1 和 ZGC 都可以利用分代思想提高垃圾回收效率。

## Q：G 1 和 ZGC 有什么区别？

可以这样回答：

G 1 和 ZGC 都是以降低垃圾回收停顿时间为重要目标的垃圾收集器，但是两者的侧重点不同。

首先，G 1 更注重吞吐量和停顿时间之间的平衡，而 ZGC 更注重极低的 GC 停顿。

其次，两者最大的区别在于对象转移阶段。G 1 虽然支持并发标记，但是 Young GC 和 Mixed GC 中的对象转移主要需要 STW；而 ZGC 可以通过有色指针、读屏障等技术，实现对象的并发转移，从而大幅减少停顿时间。

最后，在实际应用中，G 1 比较适合大多数普通 Java 后端服务，而 ZGC 更适合对响应延迟特别敏感的系统。

不过 ZGC 的并发回收和屏障机制也存在一定开销，因此并不是所有场景下都优于 G 1。

---

## **八、最后记住三个重点**

|**重点**|**G 1**|**ZGC**|
|---|---|---|
|**设计目标**|吞吐量与停顿平衡|极低停顿|
|**对象转移**|主要需要 STW|主要并发执行|
|**适用场景**|通用 Java 后端|低延迟服务|

**一句话记忆：G 1 通过 Region 和回收集合控制停顿，ZGC 通过有色指针、读屏障和并发对象转移进一步降低停顿。**

面试时如果只能讲一个核心区别，就讲：

**G 1 的主要对象转移工作需要 STW，而 ZGC 可以并发转移对象，因此 ZGC 通常能够实现更低的 GC 停顿时间。**
