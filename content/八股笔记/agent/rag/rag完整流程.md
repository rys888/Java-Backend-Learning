
[[#Q：介绍一下 RAG 的完整工作流程]]


RAG 的核心链路就两块：**离线建知识库，在线检索增强生成**。Java 后端面试按这条主线讲基本够用，不过它只是核心链路，不是涵盖所有工程细节的完整流程。

## 一、离线阶段（知识库构建）

```text
原始文档
   ↓
文档加载（Document Loading）
   ↓
文档解析与清洗（Parsing）
   ↓
文本切分（Chunking）
   ↓
向量化（Embedding）
   ↓
存入向量数据库（pgvector）
```

**文档加载**：加载 PDF、Word、Markdown 等企业制度文件，并解析成文本。

**文本切分（Chunking）**：把长文档拆成多个较小的 Chunk，避免文档过长，同时提高后续检索的针对性。

**向量化（Embedding）**：用 Embedding 模型把每个 Chunk 转成高维向量，系统才能按语义相似度检索文本。

**向量入库**：把 Chunk 的文本、向量和元数据（来源、权限、版本等）存进 PostgreSQL + pgvector。

需要纠正一个常见误区：**离线阶段不是只执行一次，而是在首次建库以及文档新增、修改、删除时执行。** 平时用户提问不需要重新处理整个知识库。

## 二、在线阶段（检索增强生成）

```text
用户提问
   ↓
Query Rewrite（查询改写）
   ↓
Embedding（问题向量化）
   ↓
Retrieval（粗排检索）
   ↓
Rerank（精排重排序）
   ↓
Context Building（上下文构建）
   ↓
Prompt Assembly（提示词拼接）
   ↓
LLM Generation（模型生成）
   ↓
返回答案
```

### 1. Query Rewrite：查询改写

作用是提高用户问题的可检索性。比如用户提问“买个显示器要找谁签字？”，改写为“企业员工申领办公显示器需要经过哪些审批流程？”。

用户提问可能口语化、语义模糊，直接拿去检索不一定能匹配到知识库里的片段。

### 2. Embedding：问题向量化

把用户问题转成向量，才能做语义相似度检索。这里和离线阶段的 Embedding 不一样：**离线阶段是把文档 Chunk 转成向量，在线阶段是把用户 Query 转成向量。** 两边要用兼容的向量表示，相似度计算才有意义。

### 3. Retrieval：粗排检索

从大量知识片段里快速找出可能相关的候选内容。比如知识库有 10 万个 Chunk，先检索出相关性较高的 Top 20。

一种更进一步的方案是混合检索：

```text
              用户 Query
                  ↓
          ┌───────┴───────┐
          ↓               ↓
       向量检索         关键词检索
          ↓               ↓
       Top 20           Top 20
          └───────┬───────┘
                  ↓
              RRF 融合
                  ↓
              候选 Chunk
```

相比单纯的向量检索，混合检索能同时兼顾语义相似性和关键词精确匹配。

### 4. Rerank：精排重排序

对粗排得到的候选 Chunk 再做一次更精细的相关性判断。

比如粗排结果是：企业办公设备申领流程、超过 500 元的审批制度、显示器采购规范。用户实际问的是“800 元的显示器需要谁审批？”，经过 Rerank 后顺序可能变成：超过 500 元的审批制度、企业办公设备申领流程、显示器采购规范，最后取最相关的 Top 5 作为上下文。

**Rerank 是可选的优化环节，不是所有 RAG 系统都必须使用。**

另外，**RRF 融合和 Rerank 不是同一个概念**。RRF 融合的是不同检索器的排名，Rerank 是进一步判断候选文档和问题的相关性，面试里不要把两者混着说。

### 5. Prompt Assembly：构建提示词

把用户问题和检索到的知识组合起来交给 LLM。例如：

```text
你是企业采购制度智能助手。

请严格根据以下知识回答问题。
如果知识中没有相关内容，请拒绝回答。

【知识库内容】
普通员工单次申领金额超过500元，
需要部门负责人审批。

【用户问题】
申请800元的显示器需要谁审批？
```

这一步就是 RAG 里的 **Augmentation（增强）**，用外部知识增强模型的回答能力。

### 6. LLM Generation：生成答案

大模型根据提供的知识生成自然语言答案：根据企业采购审批制度，普通员工单次申领金额超过 500 元需要部门负责人审批，因此申请 800 元的显示器需要部门负责人审批。

如果系统实现了来源引用，还可以附上对应制度的名称、章节及页码。

## 三、工程上还要补哪些能力

核心链路之外，工程化的 RAG 通常还要补三块：

| 环节 | 作用 |
|---|---|
| Metadata Filtering | 根据用户角色过滤知识 |
| Citation | 返回答案对应的制度来源 |
| Abstention | 没有足够证据时拒绝回答 |

再往外还有文档版本更新、异常处理、日志监控和效果评估，不过面试介绍核心链路时不用全部展开。

## Q：介绍一下 RAG 的完整工作流程

RAG 的工作流程主要分为离线知识库构建和在线检索增强生成两个阶段。

首先是离线阶段，系统加载企业制度文档，经过解析、清洗和 Chunking，把长文档切分为多个文本片段。然后通过 Embedding 模型把 Chunk 转换为向量，连同原始文本和元数据存入 PostgreSQL + pgvector。

在线阶段，用户提出问题后，系统首先根据用户身份确定知识访问权限，并对 Query 进行必要的改写。接着把 Query 向量化，通过 pgvector 做语义检索，同时用 PostgreSQL 关键词检索补充，再通过 RRF 算法融合两路检索结果。

对候选文档可以进一步用 Rerank 模型精排，选取最相关的 Chunk 作为上下文，与用户问题和系统提示词一起发送给 LLM。

最后，大模型根据检索证据生成答案，系统对来源引用进行校验。如果没有足够的有效证据，就拒绝回答，从而降低模型幻觉风险。

## 总结

核心链路：

**离线：Loading → Chunking → Embedding → Storage**

**在线：Query Rewrite → Retrieval → Rerank → Prompt → LLM**

落到实际工程上，链路会更长一些：

**离线：文档加载 → 解析清洗 → Chunking → Embedding → 向量库**

**在线：权限校验 → Query Rewrite → Embedding → 混合检索 → RRF → 可选 Rerank → Prompt → LLM → 引用校验与拒答**
