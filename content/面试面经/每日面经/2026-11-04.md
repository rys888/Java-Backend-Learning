## Java 基础与集合

### 01 HashMap 的存储与查找原理

**Q：** HashMap 的底层实现是什么？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** HashMap 根据键的哈希值定位桶，再通过 equals 区分发生冲突的键。JDK 8 中桶采用链表或红黑树，链较长且数组容量足够时才树化，容量不足时优先扩容；元素数量超过容量与负载因子的乘积也会触发扩容。哈希分布均匀时查询平均接近 O(1)，但不能保证所有场景都为常数时间。它允许 null 键和值，不保证遍历顺序，也不适合并发修改。

### 02 HashMap并发修改有哪些风险

**Q：** 是线程安全的吗？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**Q：** HashMap 会有死循环问题吗？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：HashMap没有为并发修改提供同步保证，多线程put可能发生覆盖、丢更新或读取到不符合预期的结果，size和遍历也不能视为一致快照。JDK 7扩容的链表成环问题不能直接套到JDK 8，但8仍不是线程安全容器。共享可变映射应使用ConcurrentHashMap或统一外部锁，先查后改等复合业务也需原子API或完整加锁。

### 03 常见集合中哪些支持线程安全访问

**Q：** 如果要用线程安全的数据结构，有什么替代方案？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：常用ArrayList、HashMap、HashSet不提供并发修改安全保证。可按需求使用ConcurrentHashMap、CopyOnWriteArrayList或阻塞队列，也可用Collections的同步包装；Vector和Hashtable的方法虽有同步，复合操作仍可能产生竞争。并发Map的“先判断再写入”应使用putIfAbsent、compute等原子接口。CopyOnWrite适合读多写少，写入会复制数组；遍历同步包装集合通常仍需外部加同一把锁。

## Java 并发与 JVM

### 04 synchronized与锁优化

**Q：** synchronized 的底层实现大概是怎么样的？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** synchronized通过对象监视器提供互斥及可见性，可修饰实例方法、静态方法或代码块，锁对象分别取决于实例、类或指定对象。传统HotSpot锁优化会涉及偏向锁、轻量级锁和重量级监视器，并可能使用自旋、锁消除与锁粗化降低开销。需要说明版本边界：偏向锁从JDK 15起默认禁用并废弃，较新JDK的轻量级锁实现也有变化，不能将旧版对象头状态与固定升级路径直接套用于所有版本。

### 05 线程获取的对象监视器锁对应什么

**Q：** 线程锁锁的到底是什么？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：以synchronized为例，线程竞争的是某个对象关联的监视器，保护范围由共同遵守的锁协议决定，并非自动锁住对象的全部字段。实例同步方法锁当前this，静态同步方法锁对应Class对象，代码块锁括号中的对象。两个线程必须使用同一把锁才能互斥；同一对象的普通方法仍可被其他线程调用。应选稳定、私有且职责明确的锁，避免锁引用变化。

### 06 ThreadLocal的场景与风险

**Q：** ThreadLocal 有了解吗？大概是怎么回事？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**Q：** ThreadLocal 在什么场景下会用到？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** ThreadLocal为**每个线程保存独立变量**，常用于请求上下文或事务资源绑定，不负责让同一对象的并发访问自动安全。线程池会复用线程，任务结束后若不remove，旧数据可能串到下个任务；ThreadLocalMap的弱键也不能替代清理，因为值仍可能被线程长期引用。应在finally中清理，异步任务需要显式传递必要上下文，不能假设换线程后原值仍然可见。

## MySQL

### 07 SELECT COUNT(*)经过哪些执行节点

**Q：** MySQL 执行一条 select count(*) 的关键节点有哪些？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：以MySQL 8.0与InnoDB为例，请求经过连接与权限检查、SQL解析、优化器选访问路径，再由执行器调用存储引擎扫描并聚合，最终返回计数。COUNT(* )统计符合条件的行，包括字段为NULL的行。无过滤条件时通常选择较小的可用二级索引扫描，没有合适索引则扫描聚簇索引；InnoDB受事务可见性影响，不能直接使用一个全局精确行数。具体扫描路径仍需看执行计划。

### 08 哪些情况使索引难以有效定位数据

**Q：** 常见的索引失效场景有哪些？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：常见情况有在索引列上进行函数或运算、某些隐式类型转换、联合索引缺少可用前导列，以及LIKE以通配符开头，导致普通B+树难以形成有效查找范围。OR条件能否利用索引要结合各分支与优化器判断。即使存在可用索引，选择性低或回表成本高时优化器也可能选扫描。应区分无法有效定位和成本选择，结合EXPLAIN与实际数据验证，避免把范围条件后的列一概说成完全无用。

### 09 LIKE查询是否一定无法使用索引

**Q：** like 查询一定会导致索引失效吗？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：不一定。普通B+树索引下，LIKE以固定字符串开头，如name LIKE 'abc%'，通常能提取前缀范围；以%或_开头往往不能靠前缀定位，但覆盖索引扫描仍可能出现，不能等同于完全不访问索引。实际选择还受字符集、排序规则、参数形式及数据选择性影响。应通过EXPLAIN区分范围扫描与全索引扫描，前缀匹配之后也可能需要检查完整LIKE条件。

### 10 MySQL常见存储引擎及区别

**Q：** MySQL 的存储引擎有哪些？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：常见引擎有InnoDB、MyISAM、MEMORY等。MySQL 8.0默认InnoDB，支持事务、崩溃恢复、外键和行级锁，适合常见业务表。MyISAM不支持事务，主要使用表级锁；MEMORY将数据保存在内存中，重启后数据会丢失，不能代替持久业务存储。选择应看事务、一致性、恢复能力和访问模式，不能单凭读写速度作结论。

### 11 不同MySQL存储引擎如何存放索引与数据

**Q：** 存储引擎中索引是怎么存储的？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：InnoDB通常以B+树组织索引，聚簇索引叶子保存完整行，二级索引叶子保存索引键和主键，读取其他列时可能再查聚簇索引。没有显式主键时按规则选择合适唯一键或生成隐藏行标识。MyISAM的索引与数据分开存放，索引叶子通过数据地址定位记录。MEMORY可使用HASH或BTREE索引。回答应先明确引擎，不能把所有引擎的索引叶子都说成保存行数据。
[[B+树特性]]



### 12 如何利用覆盖索引减少回表

**Q：** 如何避免回表？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：让查询所需的过滤、返回等列尽量由同一个索引提供，可以减少从二级索引再次访问聚簇索引的操作。例如按业务查询模式设计联合索引并只选择必要列，避免无目的SELECT * 。InnoDB二级索引通常包含主键，查询主键也可被覆盖。索引越宽越占空间、增加写入成本，不能把全部字段都塞入索引；需要结合EXPLAIN与实测验证，事务可见性等细节也可能影响实际访问。

## Redis

### 13 Redis常用基本数据类型

**Q：** Redis 常见的数据结构有哪些？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：常用类型包括String、Hash、List、Set和ZSet。String适合简单缓存或计数，Hash适合对象字段，List适合两端操作的序列，Set适合去重及交并差，ZSet适合按分数排序和范围查询。类型是对外的数据语义，底层编码会随元素数量、大小及版本变化。选型应结合查询与更新方式、内存和过期粒度；Stream等也是Redis支持的类型，不能把传统五种说成全部类型。

### 14 Redis Set与ZSet的底层编码如何选择

**Q：** ZSet 和 Set 的底层实现有了解吗？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：Set提供无序去重语义，常见编码是哈希表或小型纯整数集合的intset；Redis 7.2起还支持小型Set使用listpack。ZSet维护成员与分数，小集合可用紧凑编码，Redis 7常见listpack，较大集合通常结合字典与跳跃表，分别支持按成员查分和有序范围遍历。编码会按版本、元素大小及数量阈值转换，可用OBJECT ENCODING核实，不能只凭类型断言编码。

### 15 缓存穿透、击穿与雪崩的区别及应对

**Q：** 缓存雪崩、穿透、击穿分别是怎么回事？怎么解决？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：穿透是反复查询缓存和数据库都不存在的数据，可用参数校验、短期空值缓存或布隆过滤器减少回源，注意误判及数据新增。击穿是热点键失效引发大量并发回源，可用互斥重建、预热或逻辑过期。雪崩是大量键集中失效或缓存整体故障，可通过过期时间打散、限流降级和高可用减轻影响。方案要明确容忍的旧数据时间和数据库承载能力，不能忽略超时与失败。

### 16 如何降低布隆过滤器假阳性概率

**Q：** 如何提高布隆过滤器的准确性，降低假阳性概率？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：布隆过滤器用位数组与多个哈希位置判断成员，误判率取决于位数、哈希次数和实际插入量。应按预期元素数量与目标误判率设计，增加每个元素可用的位数，并选择合适的哈希次数；哈希越多并非总越准确，也会增加计算成本。容量明显超出设计值时应扩容或重建，并保证数据同步。普通布隆过滤器不能直接清位删除，阳性结果仍需查询真实存储确认。

## RabbitMQ / 消息队列

### 17 RocketMQ的核心架构组件有哪些

**Q：** RocketMQ 的架构由哪几部分组成？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** AI参考答案：以经典RocketMQ 4.x架构为例，Producer发送消息，Broker负责存储、投递及消费进度等服务，Consumer订阅处理，NameServer提供Broker与Topic路由发现。客户端查询路由后与相应Broker通信，NameServer不负责保存业务消息。Topic下有多个队列，可分布在不同Broker上。部署时还需考虑副本、高可用与消费组；RocketMQ 5.x还可能涉及Proxy等组件，应明确版本和部署模式。

### 18 为什么使用消息队列

**Q：** 你在项目中用它来做什么？ [来源 01](https://www.nowcoder.com/discuss/868599400765874176)

**A：** 消息队列常用于异步处理、服务解耦和削峰，让请求先完成必要的准入与落账，再由消费者处理后续任务。它会引入重复投递、积压、顺序和一致性问题，不能只说性能更高；要说明确认机制、失败重试、幂等、监控与补偿。用户必须立即得到最终结果或强事务提交时，不能把仅已入队解释为业务成功，需设计处理中状态或改用合适的同步链路。
