## Java 基础与集合

### 01 == 与 equals 的区别

**Q：** ==和equals的区别 [来源 01](https://www.nowcoder.com/discuss/926599685232422912)

**A：** == 对基本类型比较数值，对引用类型比较是否指向同一对象；equals 是对象的方法，默认实现也比较引用，但 String 等类重写后按内容判断。业务对象需要按关键字段判等时，应同时重写 equals 和 hashCode，保证相等对象具有相同哈希值，否则放入 HashMap、HashSet 可能出现查找或去重异常。比较字符串内容通常用 equals，并注意接收者为 null 时的空指针问题。

### 02 HashMap 的存储与查找原理

**Q：** 了解hashmap吗 [来源 01](https://www.nowcoder.com/discuss/926599685232422912)

**A：** HashMap 根据键的哈希值定位桶，再通过 equals 区分发生冲突的键。JDK 8 中桶采用链表或红黑树，链较长且数组容量足够时才树化，容量不足时优先扩容；元素数量超过容量与负载因子的乘积也会触发扩容。哈希分布均匀时查询平均接近 O(1)，但不能保证所有场景都为常数时间。它允许 null 键和值，不保证遍历顺序，也不适合并发修改。

### 03 ArrayList 与 HashSet 的区别

**Q：** ArrayList 和 HashSet 有什么区别？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** ArrayList 基于动态数组，允许重复、保留列表顺序，适合按下标访问和顺序处理；HashSet 通过哈希结构去重，不提供下标，也不保证遍历顺序。ArrayList 的按下标访问通常为 O(1)，contains 一般需要 O(n) 扫描；HashSet 在哈希分布良好时 contains、add 平均接近 O(1)，但取决于哈希与判等实现。需要去重选 Set，需要位置和重复元素选 List，不能只根据“哪种更快”决定。

### 04 HashSet 在 JDK 7 与 JDK 8 中的实现

**Q：** HashSet 底层实现（JDK 1.7 vs 1.8）？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** HashSet 底层使用 HashMap，把元素作为键，并为所有键关联同一个占位对象，所以去重依赖 hashCode 与 equals。JDK 7 的 HashMap 桶主要是链表，JDK 8 增加红黑树，在冲突较多且数组容量达到条件时树化；容量较小时会先扩容。这个变化改善了部分冲突场景，但不让集合天然线程安全，也不保证有序；元素加入后修改影响判等的字段，可能破坏正常查询与去重。

## Java 并发与 JVM

### 05 自定义线程池与七个核心参数

**Q：** 线程池的基本参数有哪些，说几个即可 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**A：** ThreadPoolExecutor常见七个参数是corePoolSize、maximumPoolSize、keepAliveTime、时间单位、任务队列、ThreadFactory和拒绝处理器。配置需结合CPU或IO特征、下游容量、允许排队时间和资源限制，不能只套公式。优先使用有界队列，并给线程命名、监控活跃数和拒绝次数；长队列可能延迟扩容，最大线程数也不能超出系统可承受范围。

### 06 OOM 与频繁 GC 如何排查

**Q：** OOM与频繁GC怎么办 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**A：** 先结合异常类型、GC 日志和监控区分堆不足、元空间、直接内存或线程资源耗尽，不能看到 OOM 就只调大堆。堆问题可分析堆转储中的大对象、支配关系和 GC Roots，判断是正常容量需求、分配过快还是对象被长期持有；频繁 GC 还需看回收后占用、停顿时间和分配速率。优先修复泄漏、无界队列等根因，再通过压测决定容量或收集器参数，抓取诊断数据也要控制线上开销。

### 07 JVM的职责

**Q：** 说一下JVM组成 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**A：** JVM负责执行Java字节码，提供类加载、运行时内存管理、解释与即时编译以及垃圾回收等能力。通常先由javac把源码编译为class文件，再由具体JVM实现加载和执行；跨平台来自统一字节码规范与各平台的JVM实现。回答时区分JDK开发工具、运行环境和JVM，也不要把Java内存模型JMM与JVM运行时内存区域混为一谈。

## MySQL

### 09 如何统计每个年级各班的学生数

**Q：** 一个表，有学生id，年级，班级，如何设计sql查询每个班多少个学生 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**A：** 假设 student 表中每行代表一名学生，字段为 id、grade、class，可以写 SELECT grade, class, COUNT(*) AS student_count FROM student GROUP BY grade, class。把年级一起分组，是为了避免不同年级的同名班级合并。COUNT(*) 统计行数，COUNT(字段) 会忽略该字段为 NULL 的行。若还要展示没有学生的班级，应从班级表 LEFT JOIN 学生表，并统计学生ID，不能对连接后的空行直接用 COUNT(*)。

## Redis

### 10 如何保证缓存与数据库的一致性

**Q：** 如何保证缓存和数据库的一致性 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**Q：** Redis 怎么解决缓存一致性？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** 常见 Cache-Aside 方案以数据库为准：读取先查缓存，未命中再查库并回填；写入先提交数据库事务，再删除缓存，后续读取重建。删除失败需要可靠重试或消息补偿，并以 TTL 限制陈旧时间。并发读写仍可能出现旧值回填，所以它通常提供最终一致性，不能直接保证强一致；更高要求可结合版本校验、串行化更新，或对关键读取直接访问数据库，再根据延迟和业务容忍度选择方案。

**项目结合（AI）**：研约通 EquipmentServiceImpl.updateEquipment 先 updateById，再调用 deleteEquipmentCache；设备状态变更和删除也会删缓存，符合数据库为准的失效思路。实际代码没有给删除失败增加可靠补偿，也存在并发回填边界，因此应表述为缓存失效策略，不能说已实现数据库与缓存强一致。可靠补偿或版本控制是后续优化建议。

### 11 Redis Set 与 ZSet 的区别

**Q：** Set 和 ZSet 的区别？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** Set 保存不重复成员，不维护分数排序，适合标签、去重和集合交并差；ZSet 同样保证成员唯一，但每个成员关联一个分数，可以按分数或排名查询，适合排行榜和延时任务的时间索引。选择时主要看是否需要排序、范围和排名，而不是是否允许重复；两者都不允许相同成员出现多份。ZSet 还要明确分数精度与同分成员的排序规则，避免把它当成可任意重复的有序列表。

### 12 微博热搜排行榜如何存储和更新

**Q：** 微博热搜排行榜怎么存？怎么更新？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** 可以用 ZSet 的成员保存话题ID、score 保存热度，通过 ZADD 更新分数，用 ZINCRBY 增量更新，再按分数倒序取 Top N；标题等详情单独存储，避免把所有信息塞进成员字符串。热度可综合浏览、搜索和互动并定期衰减，批量重算时先构建新版本再切换，降低读到半成品的风险。还要约定同分排序、保留条数、异常流量去重和数据恢复方式；具体权重属于业务设计，不应编造平台真实算法。

### 13 缓存删除后大量请求回源怎么办

**Q：** 删除缓存后大量请求打到数据库怎么办（缓存击穿）？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** 这是热点 key 失效造成的缓存击穿，区别于访问不存在数据的缓存穿透和大量 key 同时失效的雪崩。可以为同一热点 key 做互斥重建：获得锁后再次检查缓存，只有必要时才查库回填，其他请求有限等待或降级；锁必须有过期时间并校验持有者后释放。允许短暂旧数据时可用逻辑过期和异步刷新。还需限制数据库并发，因为锁超时、等待耗尽或缓存故障仍可能导致并发回源。

**项目结合（AI）**：研约通设备详情实际调用 CacheClient.queryWithMutex：未命中后尝试按 key 加锁，持锁后双检再回源，最后按 UUID 标识通过 Lua 释放锁。源码还设置了有限重试，耗尽后直接查库，因此不能说任何情况下都只有一个请求回源。queryWithLogicalExpire 虽存在于工具类，但设备详情并未调用，不能当作已启用的优化。

### 14 逻辑过期的 key 不设置 TTL 有什么问题

**Q：** 逻辑过期方案中，不设 TTL 的 key 一直放着会不会有问题？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** 逻辑过期把业务失效时间放进缓存值，查询发现过期时可以先返回旧数据，再由受控异步任务刷新，以降低热点失效时的阻塞。但不设置 Redis TTL 会让冷数据长期占内存，数据被删除后也可能留下旧值，必须设计清理任务、容量限制或更长的物理过期时间。它适合允许短暂陈旧的热点数据，不适合必须立即读到最新值的业务；刷新失败、并发刷新和线程池拥塞也需要明确降级策略。

### 16 如何避免重复下单或重复预约

**A：** 先明确哪些请求属于同一次业务操作，为它们分配稳定的业务请求号，在数据库建立唯一约束，并让业务写入与幂等记录在同一事务内完成。重复请求应查询并返回原结果，处理中则返回明确状态。Redis SET NX、短期令牌或前端按钮防抖可以减少重复流量，但锁过期、请求超时后重试仍可能发生，不能代替持久化约束。预约还要明确取消后能否再次预约，避免唯一键把合法操作一起拦住。

### 17 策略模式的好处与边界

**Q：** 项目中策略模式具体怎么用的 [来源 02](https://www.nowcoder.com/discuss/926952182883053568)

**A：** 策略模式把一组可替换算法或规则封装为实现同一接口的对象，由调用方根据上下文选择策略，适合计费、校验等存在稳定调用契约而规则多变的场景。它能减少把所有分支堆在一个大方法中的耦合，方便单独测试，但会增加类和选择逻辑，并不消除分支本身。规则很少且变化不大时不必强行抽象；项目是否已使用需看实际代码，不能仅凭有接口就认定采用了策略模式。

### 18 如何用 JMeter 验证一人一单和不超卖

**Q：** 怎么用 Jemeter 测试观测一人一单、防超卖的正确性？ [来源 03](https://www.nowcoder.com/feed/main/detail/8b78085106ae45a4bada11cb75141d8f)

**A：** 先准备可回滚的测试数据，分别构造同一用户重复提交、多用户竞争有限库存、超时重试等场景，并通过并发线程与同步启动制造竞争。响应码和成功率只是过程指标，还应在测试后核对数据库：同一业务唯一键的有效订单不重复、库存不为负、成功订单数量与库存扣减一致，失败请求没有残留扣减。测试账号和请求号要参数化，避免把测试脚本重复数据造成的错误当成服务端问题；这些属于验证方案，不代表项目已做过压测。

### 19 Git 版本回退如何选择 revert 与 reset

**Q：** git如何进行版本回退 [来源 01](https://www.nowcoder.com/discuss/926599685232422912)

**A：** 已经推送并由多人共享的提交，通常用 git revert 生成一个抵消目标改动的新提交，保留历史，便于协作审查。git reset 会移动当前分支指针：soft 保留暂存和工作区，mixed 重置暂存区但保留工作区，hard 还会覆盖受影响的已跟踪文件。reset 更适合整理尚未共享的本地提交，不能把两者理解成习惯不同的等价操作；操作前应确认未提交改动和团队分支状态。

### 20 AI 代码能运行就能直接用于业务吗

**Q：** AI生成的代码运行起来没问题，也能够在业务中使用，你是否会直接把它应用到项目里 [来源 01](https://www.nowcoder.com/discuss/926599685232422912)

**A：** 能运行只能说明某条路径没有立即报错，不能证明需求、边界和并发语义正确。我会先对照接口契约检查权限、事务、错误处理与依赖使用，再补正常、异常和边界测试；涉及金额、库存或幂等时，还要验证并发与重试。随后做代码审查和必要的集成验证，再按项目发布流程上线。AI 生成的实现仍由提交者负责，不能把演示成功或模型自述当作测试证据。

### 21 AI 生成代码持续不符合要求怎么办

**Q：** 假如AI生成代码一直不合你心意怎么办 [来源 01](https://www.nowcoder.com/discuss/926599685232422912)

**A：** 先把需求拆成小而可验证的任务，说明输入输出、约束、现有接口及不能改动的范围，并给出一个最小失败样例或失败测试。让 AI 先解释理解和改动位置，再逐步实现，每轮检查差异并运行对应验证；发现偏离就回到明确的验收条件，而不是不断追加模糊指令。多轮仍失败时，应缩小问题、自己定位关键逻辑或改为手工实现，避免累积无法解释的补丁。
