# 一、先看结果：三次查询 + 一次改动，Redis 里发生了什么

下面这张表是本篇的「答案」，后面几节拆开讲每一步是怎么发生的。

| # | 谁 | 请求 | `GET lab:equipment:3` | 锁 | 查库 | 写完之后的 Redis |
|---|---|---|---|---|---|---|
| 1 | 学生 101 | `GET /equipment/3` | `null`（key 不存在） | 拿到（值 `f5c216db…`，EX 10） | **查**（3 条 SELECT） | `lab:equipment:3` = 设备 3 的 JSON，EX **1800~2040** 秒；锁被自己删掉 |
| 2 | 学生 102 | `GET /equipment/3` | **命中**（非空 JSON） | 不碰 | **不查** | 一模一样（一个字都没动） |
| 3 | 学生 101 | `GET /equipment/99999` | `null`（key 不存在） | 拿到 | 查（1 条 SELECT，查到 null） | `lab:equipment:99999` = `""`，EX **120** 秒；锁被自己删掉 |
| 4 | 李老师（uid 2） | `PUT /equipment/3/status?status=MAINTENANCE` | — | 不碰 | 不查缓存 | `lab:equipment:3` 被 **DEL**（锁也不在） |

**接口返回**：第 1、2 行 `200` + 设备 VO；第 3 行 `200` + `{"success":false,"errorMsg":"设备不存在",…}`（`EquipmentController:34-36` 走的是 `Result.fail`，**不是 404**，HTTP 状态还是 200）；第 4 行 `200`。

## 1.1 三个变体（同一条链路，换个时机）

**变体 A：学生 101 和 102 同时按下（并发）**

两个请求都 `GET` 到 `null`，一起去抢 `lock:lab:equipment:3`。只有一个能成功：

| 请求 | 抢锁 | 接下来 |
|---|---|---|
| 101（先抢到） | `SETNX` 成功 | 二次检查 → 查库 → 写缓存 → 解锁 |
| 102（没抢到） | `SETNX` 返回 0 | `sleep(50ms)` → `continue` **回到循环顶部重读缓存** |

102 那一轮睡醒后再 `GET`：101 已经把 JSON 写进去了 → 直接命中返回，**一共只查了一次库**。如果 102 睡醒时 101 还没写完（比如回源超过 50ms），它就再睡 50ms 再来一轮——最多 20 轮。

**变体 B：学生 101 两分钟内再查一次设备 99999**

第二次 `GET lab:equipment:99999` 拿到的是 **`""`**（空串，不是 null）→ 直接 `return null`，**不查库、不抢锁**。

**变体 C：王老师去改设备 3 的状态**

设备 3 属于实验室 2，而实验室 2 的管理员是**李老师（uid 2）**。王老师（uid 3，LAB_ADMIN）调同一个接口：`@RequireRole(LAB_ADMIN)` 这一层**放行**，但进到 `assertEquipmentManageable` → `laboratoryService.assertManageable(2)` 时抛 `403 无权管理该实验室`（`EquipmentServiceImpl:99-104`、`LaboratoryServiceImpl:25-34`）。**403 在最前面，连缓存都没走到。**

# 三、读路径入口：`EquipmentServiceImpl:53-62`

## 3.1 逐行

```java
@Override
public EquipmentVO queryEquipmentById(Long id) {              // :54
    return cacheClient.queryWithMutex(                        // :55
            CACHE_EQUIPMENT_KEY,                              // :56  keyPrefix
            id,                                               // :57  id
            EquipmentVO.class,                                // :58  反序列化目标类型
            this::queryEquipmentByIdFromDb,                   // :59  dbFallback（方法引用）
            equipmentCacheTtlMinutes(),                       // :60  TTL 数值（先算好）
            TimeUnit.MINUTES);                                // :61  TTL 单位
}                                                             // :62
```

- `:55` 整条读路径**只有这一个入口**，没有第二个调用方。
- `:56` 传的是**前缀**，不是完整 key —— key 由 `CacheClient` 拼（`keyPrefix + id`）。
- `:57` 传入的 `id` 会被复用三次：拼缓存 key、拼锁 key、回源时当参数。
- `:58` 只用来在缓存命中时做 `JSONUtil.toBean(json, type)`。
- `:59` 是「缓存没命中时怎么查库」的回调，传的是本类私有方法 `queryEquipmentByIdFromDb`。
- `:60` **TTL 在调用点算好再传进去**，`CacheClient` 自己不知道抖动这回事。

**例子里的对应值**——学生 101 那次 `GET /equipment/3`，六个参数是：

| 形参 | 实参 |
|---|---|
| `keyPrefix` | `"lab:equipment:"` |
| `id` | `3L` |
| `type` | `EquipmentVO.class` |
| `dbFallback` | `EquipmentServiceImpl::queryEquipmentByIdFromDb` |
| `time` | `equipmentCacheTtlMinutes()` 的返回值（§3.2） |
| `unit` | `TimeUnit.MINUTES` |

## 3.2 TTL 是怎么算出来的

`EquipmentServiceImpl:126-128`：

```java
private long equipmentCacheTtlMinutes() {
    return CACHE_EQUIPMENT_TTL + RandomUtil.randomLong(0, CACHE_EQUIPMENT_TTL_JITTER);
    //     30                      + [0, 5)
}
```

`RandomUtil.randomLong(0, 5)` 的参数是 **min 含、max 不含**，所以实际只会取到 `0/1/2/3/4`（**取不到 5**，这一点实测过）。于是：

| 项 | 值 |
|---|---|
| 可能的 TTL | 30、31、32、33、34 分钟 —— **最大 34，到不了 35** |
| 换算成秒 | 1800、1860、1920、1980、2040 秒 |
| 例子（09:00:00 写入）的过期时刻 | 09:30:00 ~ 09:34:00 之间（整分钟） |

**抖动的用处只有一句话**：同一时刻批量写进来的 key 不要在同一个时刻一起过期。除此之外这条 TTL 没有任何别的逻辑。

# 四、`CacheClient.queryWithMutex` 逐行

`utils/CacheClient.java:139-180`，整段只有 42 行。

## 4.1 两个 key 的拼装

```java
public <R, ID> R queryWithMutex(
        String keyPrefix, ID id, Class<R> type, Function<ID, R> dbFallback, Long time, TimeUnit unit) {
    String key = keyPrefix + id;                        // :141  缓存 key
    String lockKey = LOCK_CACHE_KEY + keyPrefix + id;   // :142  锁 key
```

- `:141` `keyPrefix + id` → 缓存 key。
- `:142` `"lock:" + "lab:equipment:" + id` → 锁 key。**锁 key 是把整个缓存 key 再加一个 `lock:` 前缀**，不是独立的命名空间。

**例子里的对应值**：

| 表达式 | 拼出来的字符串 |
|---|---|
| `key` | `lab:equipment:3` |
| `lockKey` | `lock:lab:equipment:3` |
| 设备 99999 那次 | `lab:equipment:99999` / `lock:lab:equipment:99999` |

## 4.2 主循环第 1 段：先读缓存，三个分支

```java
    for (int attempt = 0; attempt < MUTEX_MAX_RETRY; attempt++) {   // :144  最多 20 轮
        String json = stringRedisTemplate.opsForValue().get(key);   // :145  ① 读缓存
        if (StrUtil.isNotBlank(json)) {                             // :146
            return JSONUtil.toBean(json, type);                     // :147  ② 有值 → 反序列化返回
        }
        if (json != null) {                                         // :149
            return null;                                            // :150  ③ 值是 "" → 返回 null
        }
```

- `:145` 每进一轮循环**先读一次缓存**，然后才考虑抢锁（顺序很重要，见 §4.3）。
- `:146` 用 `StrUtil.isNotBlank`：`null`、`""`、`"   "` 都算 blank。
- `:149` 用 `json != null`：能走到这里的 `json` 只可能是 **`""`**（空值缓存），因为非空已在 `:146` 返回、`null` 不满足 `!= null`。

**三个分支与本篇例子的对应**：

| `json` | 含义 | 返回 | 本篇哪一次请求走到这 |
|---|---|---|---|
| `"{...}"` | 命中真实数据 | `JSONUtil.toBean(...)` | 学生 102 那次（第 2 行） |
| `""` | 命中「设备不存在」标记 | `null` | 变体 B：两分钟内再查 99999 |
| `null` | key 不存在（或已过期） | 继续往下 → 抢锁 | 学生 101 第一次查设备 3（第 1 行） |

## 4.3 第 2 段：抢锁；抢不到就睡 50ms 回到循环顶部

```java
        String lockValue = UUID.randomUUID().toString(true);        // :153  本次抢锁的标识
        if (!tryLock(lockKey, lockValue)) {                         // :154
            sleepQuietly(MUTEX_RETRY_INTERVAL_MS);                  // :155  睡 50 毫秒
            continue;                                               // :156  回到 :144 重来一轮
        }
```

- `:153` 用的是 **hutool 的 `cn.hutool.core.lang.UUID`**（不是 `java.util.UUID`），`toString(true)` 得到**去掉横线的 32 位十六进制**，例如 `f5c216db9fa14ffebef291347c216a84`。这个值就是「这把锁是我的」的凭证。
- `:154` 调 `tryLock`（§5.1），内部是 `SETNX + EX 10`。
- `:156` 的 `continue` 是重点：**抢不到锁不是直接返回错误，而是回到循环顶部重新读一次缓存**。因为持锁的那个线程可能已经把缓存建好了，下一轮 `:145` 就命中了。

**例子里的对应值**（学生 101，09:00:00）：这一句在 Redis 里等价于

```
127.0.0.1:6379> SET lock:lab:equipment:3 "f5c216db9fa14ffebef291347c216a84" NX EX 10
OK
```

**变体 A 里学生 102 的遭遇**：`SETNX` 返回 nil（key 已存在）→ `tryLock` 返回 false → 睡 50 毫秒 → `continue`。

## 4.4 第 3 段：二次检查 → 查库 → 写回

```java
        try {                                                       // :159
            String cached = stringRedisTemplate.opsForValue().get(key);   // :160  再读一次
            if (StrUtil.isNotBlank(cached)) {                             // :161
                return JSONUtil.toBean(cached, type);                     // :162
            }
            if (cached != null) {                                         // :164
                return null;                                              // :165
            }
            R r = dbFallback.apply(id);                                   // :167  真查库
            if (r == null) {                                              // :168
                stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);   // :169  写空值
                return null;                                              // :170
            }
            this.set(key, r, time, unit);                                 // :172  写缓存
            return r;                                                     // :173
        } finally {
            unlock(lockKey, lockValue);                                   // :175  无论成功失败都解锁
        }                                                                 // :176
```

逐段说：

- **`:160` 二次检查**：从「本轮 `:145` 读到 null」到「`tryLock` 成功」之间隔了一小段时间，上一个持锁线程可能刚好写完缓存并释放锁。不检查这一下，就会白查一次库。
- **`:161-166` 和 `:146-151` 是同一套三分支**，只是这次读的是 `cached`。
- **`:167` `dbFallback.apply(id)`**：对设备就是调 `EquipmentServiceImpl.queryEquipmentByIdFromDb(id)`（§4.5）。
- **`:168-171` 查不到 → 写 `""`**，TTL 用 `CACHE_NULL_TTL`（**2 分钟**），**不是**调用点传进来的 30 多分钟。
- **`:172` 写回真值**，走 `this.set`（§4.6），TTL 用调用点算好的 `time`/`unit`。
- **`:175` 在 `finally` 里**：查库抛异常、写缓存抛异常，都会解锁。

## 4.5 回源做了什么：`queryEquipmentByIdFromDb`

`EquipmentServiceImpl:106-124`：

```java
private EquipmentVO queryEquipmentByIdFromDb(Long id) {                       // :106
    Equipment equipment = getById(id);                                        // :107
    if (equipment == null) {                                                  // :108
        return null;                                                          // :109
    }
    EquipmentVO equipmentVO = BeanUtil.copyProperties(equipment, EquipmentVO.class);   // :111
    Laboratory laboratory = laboratoryService.getById(equipment.getLaboratoryId());    // :112
    if (laboratory != null) {                                                 // :113
        equipmentVO.setLaboratoryName(laboratory.getName());                   // :114
        equipmentVO.setCampus(laboratory.getCampus());                         // :115
        equipmentVO.setBuilding(laboratory.getBuilding());                     // :116
        equipmentVO.setRoom(laboratory.getRoom());                             // :117
    }
    EquipmentCategory category = equipmentCategoryService.getById(equipment.getCategoryId());   // :119
    if (category != null) {                                                   // :120
        equipmentVO.setCategoryName(category.getName());                       // :121
    }
    return equipmentVO;                                                       // :123
}
```

- `:107` 查 `tb_equipment`；`:111` 把实体字段**同名拷贝**进 VO。
- `:112` 再查 `tb_laboratory`，把实验室的 4 个字段**打平**塞进 VO；`:119` 再查 `tb_equipment_category`，塞 `categoryName`。
- **所以一个设备详情 = 3 条 SELECT**，且有 2 条是与设备无关的「拼展示字段」。

**例子里的对应值**（设备 3）：

| 步骤 | SQL 实际查的 | 拿到的值 | 写进 VO 的字段 |
|---|---|---|---|
| `:107` | `tb_equipment WHERE id = 3` | 高效液相色谱仪 / B205-1 / AVAILABLE / booking_enabled=1 / image=NULL | 前 12 个字段（含 2 个时间） |
| `:112` | `tb_laboratory WHERE id = 2` | 分析测试实验室 / 主校区 / 理科楼 / B205 | `laboratoryName` `campus` `building` `room` |
| `:119` | `tb_equipment_category WHERE id = 2` | 化学分析 | `categoryName` |

查设备 99999 时，`:107` 就返回 null，**`:111` 之后的两次查询不会发生**——1 条 SELECT 结束。

## 4.6 写回的到底是什么：裸 VO JSON，没有 `RedisData` 包装

`CacheClient:50-52`：

**注意这里写的是 `JSONUtil.toJsonStr(value)`，也就是 VO 本身**——`{"data":..., "expireTime":...}` 那个包装形状只属于 `setWithLogicalExpire`（§7.2），**互斥锁这条路上不存在**。

这份 JSON 有 4 个「不看代码猜不到」的点（都是用 hutool 5.7.17 跑本地小片段实测出来的，没有连 Redis）：

| 现象 | 原因 |
|---|---|
| **没有 `image` 这个键** | 设备 3 的 `image` 是 NULL，hutool 默认**忽略 null 字段**（不是写成 `"image":null`） |
| `createTime` / `updateTime` 是**数字** `1791252000000` | hutool 把 `LocalDateTime` 写成了 **epoch 毫秒**，不是 `"2026-10-06T10:00:00"` 这种可读字符串（反序列化时再按同一时区还原成 `LocalDateTime`） |
| `status` 是字符串 `"AVAILABLE"` | 枚举写成 `name()` |
| 键的排列顺序**不是字段声明顺序** | hutool 按它自己遍历到的属性顺序写；Redis 不关心顺序，反序列化也不依赖顺序 |

`EquipmentCacheTest:160` 那个用例（`shouldPreserveEveryEquipmentFieldThroughHutoolJsonRoundTrip`）断言的就是「这些字段过一遍 hutool JSON 往返后还相等」。

## 4.7 空值缓存那条路（用设备 99999 代入）

`:168-171` 展开成 Redis 命令：

```
127.0.0.1:6379> SET lab:equipment:99999 "" EX 120
```

| 项 | 值 |
|---|---|
| key | `lab:equipment:99999`（**和真值同一个 key 形状**） |
| 值 | `""`（**空字符串**，不是 `null`、不是 `"null"`、不是别的 key） |
| TTL | `CACHE_NULL_TTL` = `2L` + `TimeUnit.MINUTES` = **120 秒** |
| 写入时刻 | 09:00:00 |
| 过期时刻 | **09:02:00** |

**为什么空值用「同一个 key + 空串」**：`CacheClient` 的三分支判断里，`""` 是唯一能和「key 不存在（`null`）」区分开的标记。写空串而不是不写，是为了让**同一个不存在的 id 在 2 分钟内只打一次 DB**；代价是这条 id 若在 2 分钟内真的被建出来，也会继续回「设备不存在」，**最长 2 分钟不可见**。空值 TTL 取 2 分钟（远比真值的 30 分钟短），就是为了把这个不可见窗口压小。

**第二次查同一个 id（变体 B）**：`GET` 拿到 `""` → `:146` `isNotBlank("")` 为 false → `:149` `"" != null` 为 true → `:150` `return null`。**不抢锁、不查库**。

## 4.8 20 轮都没抢到锁的兜底

```java
        }                                        // 循环结束（:177 的 }）
        return dbFallback.apply(id);             // :179
```

最坏 20 × 50ms ≈ **1 秒**过去仍抢不到锁，就**直接查库**返回。

**注意这条路径查完库不回写缓存**，也不涉及锁（本来就没拿到）。含义：缓存刚失效时如果并发很高，那些一直没抢到锁的请求会**每个都打一次 DB**，只是它们不会去重建缓存。

# 五、锁：`tryLock` / `unlock`

## 5.1 加锁

`CacheClient:182-186`：

```java
private boolean tryLock(String key, String value) {
    Boolean flag = stringRedisTemplate.opsForValue()
            .setIfAbsent(key, value, MUTEX_LOCK_TTL_SEC, TimeUnit.SECONDS);   // SET key value NX EX 10
    return BooleanUtil.isTrue(flag);
}
```

`setIfAbsent(key, value, timeout, unit)` 就是 Redis 的 `SET key value NX EX timeout`：

- **`NX`**：key 不存在才设置成功（返回 true），已存在返回 false。这一句就是「抢锁」。
- **`EX 10`**：10 秒后自动删除，防止持锁线程崩了之后锁永远不释放。
- **`value` 是 UUID**：解锁时用它确认「这把锁还是我的」。

## 5.2 解锁（Lua 比较后删）

`CacheClient:188-190`：

```java
private void unlock(String key, String value) {
    stringRedisTemplate.execute(UNLOCK_SCRIPT, Collections.singletonList(key), value);
}
```

脚本 `resources/unlock.lua`（全文 6 行）：

```lua
-- 比较线程标示与锁中的标示是否一致
if(redis.call('get', KEYS[1]) ==  ARGV[1]) then
    -- 释放锁 del key
    return redis.call('del', KEYS[1])
end
return 0
```

**先 `GET` 比对 value，相等才 `DEL`**，两步在 Redis 里原子执行。

**为什么要比对**：学生 101 的锁 10 秒到期自动消失了、学生 103 抢到了同一把锁；此时 101 的回源终于做完走到 `unlock`，如果直接 `DEL`，**删掉的是 103 的锁**——第 4 个线程立刻又能抢到锁。比对之后 101 发现锁里的 UUID 不是自己的，就不删（`CacheClientMutexTest:130` 那个用例断言的就是这一点）。

脚本加载（`CacheClient:38-44`）：

```java
private static final DefaultRedisScript<Long> UNLOCK_SCRIPT;

static {
    UNLOCK_SCRIPT = new DefaultRedisScript<>();
    UNLOCK_SCRIPT.setLocation(new ClassPathResource("unlock.lua"));
    UNLOCK_SCRIPT.setResultType(Long.class);
}
```

## 5.4 `lock:lab:equipment:3` 的完整生命周期

| 阶段 | 谁 | Redis 里发生什么 |
|---|---|---|
| 创建 | 学生 101 的请求线程（`:154` 抢锁成功） | `SET lock:lab:equipment:3 "f5c216db…" NX EX 10` |
| 值 | 该线程自己 new 出来的 hutool UUID（32 位十六进制，无横线） | 只有它知道这个值 |
| 存活期 | 回源 + 写缓存期间 | 正常是毫秒级；**如果超过 10 秒**，key 被 Redis 自动删掉，别的线程可以抢到同一把锁 |
| 删除 | **还是 101 那个线程**，在 `:175` 的 `finally` 里 | `EVAL unlock.lua 1 lock:lab:equipment:3 f5c216db…` → `GET` 相等 → `DEL` |
| 删不掉的情况 | 锁已过期、且已被别人重新设置 | `GET` 拿到的不是自己的 UUID → 脚本返回 0，**不删** |
| 例子里的结果 | 学生 101 那 3 条 SELECT 只用了几毫秒 | 锁在 09:00:00 被创建、在 09:00:00.0x 被自己删掉；**永远不会等到 09:00:10 的 TTL** |

**这把锁不是 Redisson 的锁**，是手写的 `SETNX + Lua 删除`。项目里 `RedissonConfig:22-29` 确实创建了 `RedissonClient`，但**设备缓存这条链路完全没用到它**；Redisson 的锁只用在对 `reservation:batch` 的消费与对账上（`ReservationMessageConsumer:129-131` 的 `redissonClient.getLock("lock:reservation:" + userId)`，`ReservationReconcileServiceImpl:61`）。两套锁的 key 前缀注意别混：`lock:` 是人写的、`lock:reservation:` 是 Redisson 的。

**致命缺陷在 `:99-102`：`StrUtil.isBlank(json) → return null`，没有 `dbFallback.apply(id)`。** 这个方法假定缓存**一定被预热过**（Redis 里永远有这个 key，只是值里的 `expireTime` 到了）。但这个项目里：

- **没有任何地方预热**：`setWithLogicalExpire` 只被 `CacheClient:126` 自己内部调用过（全项目 grep 的结果见上），没有初始化器、没有启动时加载。

另外两个事实（都读代码确认过，不是推测）：

- `RedisData.data` 声明成 `Object`，反序列化回来是 `cn.hutool.json.JSONObject`，所以 `:105` 的强转不会失败；`expireTime` 在写入时**不可能是 null**（`:58` 一定赋值）。所以 `:106`/`:108` 不构成 NPE 风险。

**结论：这个方法既没有调用方（死代码），写出来的逻辑也不能直接启用 —— 要用必须先补上 `if (StrUtil.isBlank(json)) { ...dbFallback + 写缓存... }` 这段。**

## 8.5 当前实现的 4 条边界

- **`queryWithPassThrough`（`CacheClient:63-91`）与 `queryWithLogicalExpire`（`:93-137`）零调用**，后者还有 `:99-102` 「未命中直接 return null、不回源」的缺陷，且项目里没有任何预热入口 —— 留在类里容易被误当成可选方案启用；要用得先补回源分支。
- **第 20 轮兜底（`:179`）只查库、不回写缓存**：缓存刚失效时的并发尖峰里，没抢到锁的请求每个都打一次 DB，重建只由持锁那一个请求完成。
- **删缓存（`EquipmentServiceImpl:131`）没有重试、没有延迟双删**，`DEL` 失败就只能等 TTL（最长 34 分钟）自然过期；读路径写回缓存时也不做任何版本/时间戳校验。
- **只有单个设备详情走缓存**：列表 `queryEquipmentPage`（`EquipmentServiceImpl:46-51`）直接查库；`LaboratoryServiceImpl` 全类不碰 Redis。三组可调参数（空值 TTL 2 分钟、锁 TTL 10 秒、重试 20×50ms）都是**硬编码常量**，无配置项。
