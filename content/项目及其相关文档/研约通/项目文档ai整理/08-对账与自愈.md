# 08 · 对账与自愈

> **只讲代码在做什么。** 07 篇留下的那些非终态账本行（`PRE_ACCEPTED` / `PUBLISHED` / `UNKNOWN`），由本篇的定时任务收尾。顺带两条生命周期补偿：取消后没还成的名额、以及到期没核验的爽约。
>
> **全篇用一个例子从头走到尾**：`tb_reservation_request` 里**学生 102** 那条 `request_id = 645827360351847424`、卡在 `PUBLISHED` 的账本行，被 **09:15 那一轮**定时任务捞起来收敛掉。每个代码块后面都写「例子里的对应值」。
>
> **先说清楚这是哪条时间线。** 102 在正常路径下是**成功**的：05 篇 §6 就是「跟着学生 102 走一遍」，06 篇讲他这条消息怎么投递，07 篇讲账本怎么从 `PRE_ACCEPTED` 走到 `CONFIRMED`，10 篇讲李老师把他的死信**重放成功**。本篇摆的是同一个人、同一批数据的**另一条岔路**：这条岔路上**没有人去点重放**，于是账本一直挂着，直到 09:15 被对账收敛成 `COMPENSATED`。
>
> **主线看 05 / 06 / 07 / 10 篇，本篇只讲这个变体。** 同一个存储快照在两篇里只能有一种结局，所以下面每个数字都按这条岔路重新摆一遍（06 篇 §1.2 的变体 A/B、10 篇 §1.1 的变体 A 用的也是这种写法）。

# 零、先把例子摆出来

## 0.1 那条卡住的账本行（假设变体：这条岔路上 102 没人重放）

学生 102 在 **2026-10-07 09:00:01** 点了「预约」，目标批次是 **批次 7**（设备 3 高效液相色谱仪，5 个名额）。他这一路上：`submit` 校验通过 → `RedisIdWorker` 生成 `reservationId = 645827360351847424` → 往账本插一行 `PRE_ACCEPTED` → 抢到名额 → 投递消息、收到 broker ACK → 账本 CAS 成 `PUBLISHED`（`ReservationServiceImpl:282-284`，时间线见 10 篇 §1 第 4 步）。

**然后就是本篇要讲的那条岔路**：消费者 `persistWithLock` 等 `lock:reservation:102` 等了 2 秒没拿到，返回 null → 写 `fail_reason = 'LOCK_TIMEOUT'` → `basicNack` 进死信队列（`ReservationMessageConsumer:60-65`；为什么会等超时见 10 篇 §2.2 / §2.3）。**`tb_reservation` 里始终没有 `645827360351847424` 这一行**，死信台账 `tb_reservation_dlq` 里躺着 **id = 1**（`status = 'NEW'`、`replay_count = 0`、`failure_reason = 'LOCK_TIMEOUT'`）。

**10 篇的主线是李老师在 09:00:08 就把它重放了** —— 重放那次消费者拿到锁、落库成功、账本走到 `CONFIRMED`。**本篇的岔路是：没人点重放。** 台账 id = 1 一直挂着 `NEW`，这条请求也就一直卡着，直到 09:15 被对账扫到。

09:15 这一刻，`tb_reservation_request` 里批次 7 的全部行：

| `request_id` | `user_id` | `batch_id` | `status` | `fail_reason` | `create_time` | `update_time` |
|---|---|---|---|---|---|---|
| 645827360351847423 | 101 | 7 | `CONFIRMED` | NULL | 09:00:00 | 09:00:00 |
| **645827360351847424** | **102** | **7** | **`PUBLISHED`** | **`LOCK_TIMEOUT`** | **09:00:01** | **09:00:03** |
| 645827360351847425 | 103 | 7 | `PUBLISHED` | NULL | 09:00:01 | 09:00:01 |
| 645827360351847426 | 104 | 7 | `CONFIRMED` | NULL | 09:00:01 | 09:00:02 |
| 645827360351847427 | 105 | 7 | `CONFIRMED` | NULL | 09:00:02 | 09:00:03 |
| 645827360351847428 | 106 | 7 | `COMPENSATED` | `SOLD_OUT` | 09:00:02 | 09:00:02 |

**非终态的定义在 `enums/ReservationRequestStatus.java:14-15`**：

```java
private static final List<ReservationRequestStatus> NON_TERMINAL_STATUSES =
        Collections.unmodifiableList(Arrays.asList(PRE_ACCEPTED, PUBLISHED, UNKNOWN));
```

五个状态里只有 `PRE_ACCEPTED` / `PUBLISHED` / `UNKNOWN` 是「还没走完」，`CONFIRMED` / `COMPENSATED` 是终点（同文件 `:17-19` 的 `isTerminal()`）。

**例子里的对应值**：上面 6 行里**只有 102 和 103 是非终态**。它就是本篇要处理的那一堆。

停在非终态的原因（同一批请求，走出三种结局）：

| 行 | 为什么停在这个状态 |
|---|---|
| 102 `PUBLISHED` / `LOCK_TIMEOUT`（09:00:03） | 投递是成功的（broker ACK → 账本 CAS 成 `PUBLISHED`），但**消费者没落库**：`persistWithLock` 等 `lock:reservation:102` 2 秒超时 → `return null` → 写 `fail_reason = 'LOCK_TIMEOUT'` → `basicNack` 进死信（`ReservationMessageConsumer:60-65`）。 |
| 103 `PUBLISHED`（09:00:01） | 消息投递成功，**消费者也落库了**，但落库之后紧接着的 `markConfirmedSafely` 那次 CAS 没成功（返回 `false` 只打一行 `warn`，抛异常也只打一行 `error`，两种情况都不影响它后面的 `basicAck`，`ReservationMessageConsumer:99-112` 与 `:70-71`）。**账本就这么停在 `PUBLISHED`，可它其实落了库**。 |
| 101 / 104 / 105 `CONFIRMED` | 正常走完：消费者落库 → 账本 CAS 成 `CONFIRMED`。 |

**102 和 103 这两行的账本状态一模一样（都是 `PUBLISHED`），现实却相反** —— 一个没落库、一个落了库。这正是 §3.3 要讲的那件事：**账本状态决定不了对账往哪边走**。

**注意 104**：他的账本行是 `CONFIRMED`，但他 09:12 把自己的预约取消了。**取消不改账本**（`ReservationServiceImpl.cancel` 里没有任何 `reservationRequestService` 调用），账本只记录「请求这条链路」的终局，`CANCELLED` 是 `tb_reservation` 那边的事（09 篇）。104 的事在 §四 会用到。

另一张表也在等着被扫 —— `tb_reservation` 里有两行是「取消过」的：

| `id` | `user_id` | `batch_id` | `status` | `quota_released` | `update_time` | 怎么来的 |
|---|---|---|---|---|---|---|
| 645827360351847425 | 103 | 7 | `CANCELLED` | `1` | 09:05:00 | 103 自己在 **09:05:00** 取消了，取消时名额**还成**了（09 篇的正线） |
| 645827360351847426 | 104 | 7 | `CANCELLED` | **`0`** | 09:12:05 | 104 在 09:12 取消，但**还名额那一步失败了**，等 §四 的定时补偿 |

§四 的 SQL 只认 `status = 'CANCELLED' AND quota_released = 0`，所以这两行里**只有 104 那行会被捞走**，103 那行不会被重复处理。

## 0.2 这一刻 Redis 里长什么样

```
127.0.0.1:6379> GET reservation:batch:quota:7
"1"

127.0.0.1:6379> SMEMBERS reservation:batch:users:7
1) "101"
2) "102"
3) "104"
4) "105"

127.0.0.1:6379> TTL reservation:batch:quota:7
(integer) 197100
```

- `quota:7 = "1"`：5 个名额先被 101~105 全拿走（`"5"` → `"0"`，05 篇 §1 那张表），然后 **103 在 09:05 取消，Lua 还回来一个**（`"0"` → `"1"`，09 篇 §1、§6.3）。106 那次 Lua 在 `GET` 之后就 `return 2`，**没有执行 `DECR`**，所以他不占名额。
- `users:7 = {101,102,104,105}`：103 已经在 09:05 被 `SREM` 掉了（同一个 Lua 的 `SREM users:7 "103"`）。
- **102 和 104 都还在这个 Set 里** —— 他们俩的名额都还没还回去（102 的名额从来没人还过，104 的取消还失败了）。这两个人正好就是本轮要处理的两个。
- `TTL 197100`：`publish` 时设的是 `endTime(1791446400) + 24h − now(1791334800)` = **198000 秒**（55 小时），从 09:00 到 09:15 走掉 900 秒，剩 197100。

# 一、先看结果：09:15:00.110 那一轮跑完了什么

## 1.1 时间线

下面这张表是本篇的「答案」，后面各节拆开讲每一步怎么发生的。

| # | 时刻 | 发生了什么 | 这一步之后存储变成什么 |
|---|---|---|---|
| ① | 09:15:00.110 | 第 N 轮调度触发（`fixedDelay` 5 分钟一轮） | — |
| ② | | `tryLock("lock:reservation:reconcile", 0ms)` 抢到锁 | 锁被本实例持有，跑完自动释放 |
| ③ | | `before = 09:15:00.110 − 10min = 09:05:00.110` | — |
| ④ | | `listStale` 取回 **2 行**，按 `update_time` 升序：**103（`09:00:01`）在前**、102（`09:00:03`）在后 | — |
| ⑤ | | 处理 **103**：`tb_reservation` 里**查到了** `645827360351847425` | — |
| ⑥ | | 103 → CAS 成 `CONFIRMED` | 账本行 `status=CONFIRMED`，`fail_reason` 仍是 `NULL` |
| ⑦ | | 处理 **102**：`tb_reservation` 里查不到 `645827360351847424` | — |
| ⑧ | | 102 → 先还名额：`rollback(7, 102)` | `quota:7` `"1"` → **`"2"`**；`users:7` 从 `{101,102,104,105}` 变成 `{101,104,105}` |
| ⑨ | | 102 → 再宣告终结：CAS 成 `COMPENSATED` | 账本行 `status=COMPENSATED`、`fail_reason=RECONCILE_NO_RESERVATION`、`update_time→09:15:00` |
| ⑩ | | `releasePendingQuotas`：捞出 104 那行（`CANCELLED` + `quota_released=0`） | `quota:7` `"2"` → **`"3"`**；`users:7` 变成 `{101,105}`；`tb_reservation.quota_released` `0` → `1` |
| ⑪ | | `markNoShows`：0 行 | 一个字节都没动 |
| ⑫ | 09:15:00.4xx | `finally` → `unlock()` | 锁释放，等下一个 5 分钟 |

**注意顺序是「先 103、后 102」** —— `listStale` 是 `ORDER BY update_time ASC`（§3.1），103 那行停在 `09:00:01`，比 102 的 `09:00:03` 早。同一批请求，谁先卡住谁先被处理，跟 id 大小无关（两行 id 恰好也是 103 小，但排序依据是时间）。

## 1.2 汇总对象里填的值

对账那一趟生成一个 `ReconcileSummaryDTO`（`dto/ReconcileSummaryDTO.java`，五个 `int` 字段，只读），并打出这行日志（`ReservationReconcileServiceImpl:79-81`）：

```
预约对账完成：scanned=2，confirmed=1，compensated=1，skipped=0，failed=0
```

| 字段 | 值 | 出处 |
|---|---|---|
| `scanned` | `2` | `staleRequests.size()`，就是 102 那一行 + 103 那一行 |
| `confirmed` | `1` | 103 走「其实已经成功了」分支，CAS 成功 |
| `compensated` | `1` | 102 走「确实没成功」分支，CAS 成功 |
| `skipped` | `0` | 没有一条 CAS 被别人抢先 |
| `failed` | `0` | 没有一条抛异常 |

第二行日志（`:85-87`）因为 `released > 0` 也打了：

```
预约生命周期补偿完成：releasedQuotas=1，noShows=0
```

`noShows=0` 是因为批次 7 的使用时段是 **2026-10-08 14:00 ~ 16:00**，`end_time` 还没到 —— 爽约那条 SQL 一条都挑不出来（§五）。

## 1.3 为什么是 09:15 这一轮，而不是 09:10

扫描窗口是 `update_time < now − 10 分钟`（`<` 是**严格小于**）。102 那行的 `update_time` 是 `09:00:03`：

| 轮次（`now`） | `before = now − 10min` | 102 那行（`09:00:03`）进扫描吗 |
|---|---|---|
| 09:05:00.120 | 08:55:00.120 | 否 |
| 09:10:00.150 | **09:00:00.150** | 否 —— `09:00:03` 不早于 `09:00:00.150`，**差 3 秒就被挡在外面** |
| **09:15:00.110** | **09:05:00.110** | **是** —— `09:00:03 < 09:05:00.110` |

（103 那行 `09:00:01` 同理：09:10 那轮 `before = 09:00:00.150`，`09:00:01` 也进不去，两行一起等到 09:15 才被捞走。）

**「恰好 10 分钟」那一轮能不能扫到，取决于 `now` 的毫秒部分。** 这也是阈值存在的意义：一条刚提交的请求有 10 分钟窗口，让正常流程（消费者落库 + 账本 CAS）自己走完，对账不要去抢它的活。

# 二、调度开关与调度入口

## 2.1 `SchedulingConfig` —— 全部内容就这些

`config/SchedulingConfig.java`（9 行，全文）：

```java
@Configuration
@EnableScheduling

}
```

`@EnableScheduling` 一开，Spring 就会扫所有 `@Scheduled` 方法。**没有线程池配置**，用的是 Spring Boot 默认的单线程调度器（`spring.task.scheduling.pool.size` 没配，默认 1）。全项目只有这一个 `@Scheduled`（`ReservationReconcileServiceImpl:57`）。

## 2.2 对账任务本体：`scheduledReconcile`

`ReservationReconcileServiceImpl.java:54-72`

```java
/**
 * 定时调度薄壳：分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证。
 */
@Scheduled(
        fixedDelayString = "${yanyuetong.reservation.reconcile-interval-ms:300000}",
        initialDelayString = "${yanyuetong.reservation.reconcile-initial-delay-ms:300000}")
public void scheduledReconcile() {
    RLock lock = redissonClient.getLock(RedisConstants.LOCK_RESERVATION_RECONCILE_KEY);
    boolean locked;
    try {
        locked = lock.tryLock(0, TimeUnit.MILLISECONDS);
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new IllegalStateException("预约对账获取分布式锁时被中断", e);
    }
    if (!locked) {
        log.debug("预约对账未获取到分布式锁，跳过本轮");
        return;
    }
```

逐句：

- **`fixedDelayString`**（`:58`）而不是 `fixedRateString` —— 是「**上一轮跑完之后**再等 5 分钟」，不是每 5 分钟起一轮。一轮跑得久，下一轮自动往后顺延。
- **`initialDelayString`**（`:59`）：第一轮在应用启动 **5 分钟**后。yaml 里没有这个 key，取默认值 `300000`。
- **`:61` 锁 key 是 `RedisConstants.LOCK_RESERVATION_RECONCILE_KEY`**，字面量在 `utils/RedisConstants.java:18`：

  ```java
  public static final String LOCK_RESERVATION_RECONCILE_KEY = "lock:reservation:reconcile";
  ```
- **`:64` `lock.tryLock(0, TimeUnit.MILLISECONDS)`**：只传两个参数 —— **等待时间 0 毫秒，没有传 `leaseTime`**。
  - `waitTime = 0` 表示**抢不到就立刻返回 false，不排队、不等**。
  - 不传 `leaseTime` → 走 Redisson 的**看门狗**续期：只要持有线程还活着，锁就不会在任务跑到一半时过期。`config/RedissonConfig.java:22-29` 只设了地址和密码，**没有覆盖 `lockWatchdogTimeout`**，所以是 Redisson 的默认租期（30 秒）并按租期的 1/3 自动续期。
- **`:65-68`**：`tryLock` 抛 `InterruptedException`（线程在等锁时被打断）→ 恢复中断标志 + 抛 `IllegalStateException`。注意 `waitTime = 0` 时基本不会阻塞，所以这个 catch 实际很少进。
- **`:69-72` 没抢到锁 → `log.debug` + `return`，本轮什么都不做**。多实例部署时，这说明别的实例正在跑。**跳过，不是等待。**

## 2.3 拿到锁之后，三件事串行

`ReservationReconcileServiceImpl.java:74-92`

```java
    try {
        ReconcileSummaryDTO summary = reconcile(reconcileLimit);
        if (summary.getScanned() == 0) {
            log.debug("预约对账本轮无陈旧请求");
        } else {
            log.info("预约对账完成：scanned={}，confirmed={}，compensated={}，skipped={}，failed={}",
                    summary.getScanned(), summary.getConfirmed(), summary.getCompensated(),
                    summary.getSkipped(), summary.getFailed());
        }
        int released = releasePendingQuotas(reconcileLimit);
        int noShows = markNoShows(reconcileLimit);
        if (released > 0 || noShows > 0) {
            log.info("预约生命周期补偿完成：releasedQuotas={}，noShows={}", released, noShows);
        }
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

- **`reconcile` → `releasePendingQuotas` → `markNoShows` 依次串行**（`:75`、`:83`、`:84`），共用同一把锁和同一个 `reconcileLimit`。
- **三个方法各用一次 `reconcileLimit`**（都是 200），不是共享一个 200 的总额。
- **`reconcile` 抛异常的话，`releasePendingQuotas` 和 `markNoShows` 这一轮就不跑了** —— `finally` 只负责解锁。
- **`:89` `isHeldByCurrentThread()`**：Redisson 的 `unlock()` 只能由持有线程调用，非持有线程调会抛 `IllegalMonitorStateException`。先判一下更稳。

**例子里的对应值**：09:15 这一轮三件事都跑了 —— `reconcile`（scanned=2）、`releasePendingQuotas`（released=1）、`markNoShows`（0 行）。

# 三、账本对账 `reconcile` 逐行

`ReservationReconcileServiceImpl.java:95-146`，方法是 `public` 的（`IReservationReconcileService` 只暴露这一个方法），接口注释写着「本方法不加事务、不获取分布式锁，可由测试或人工任务直接调用」。

## 3.1 先算扫描窗口，再把那批行捞出来

`ReservationReconcileServiceImpl.java:100-103`

```java
LocalDateTime before = LocalDateTime.now()
        .minus(reconcileThresholdMs, ChronoUnit.MILLIS);
List<ReservationRequest> staleRequests = reservationRequestService.listStale(before, limit);
```

`listStale` 在 `ReservationRequestServiceImpl.java:74-88`：

```java
@Override
public List<ReservationRequest> listStale(LocalDateTime before, int limit) {
    if (limit <= 0) {
        return Collections.emptyList();
    }
    List<ReservationRequest> requests = reservationRequestMapper.selectList(
            new LambdaQueryWrapper<ReservationRequest>()
                    .in(ReservationRequest::getStatus,
                            ReservationRequestStatus.nonTerminalStatuses())
                    .lt(ReservationRequest::getUpdateTime, before)
                    .orderByAsc(ReservationRequest::getUpdateTime)
                    .orderByAsc(ReservationRequest::getRequestId)
                    .last("LIMIT " + limit));
    return requests == null ? Collections.emptyList() : requests;
}
```

拼出来的 SQL 等价于：

```sql
SELECT * FROM tb_reservation_request
 WHERE status IN ('PRE_ACCEPTED','PUBLISHED','UNKNOWN')
   AND update_time < ?
 ORDER BY update_time ASC, request_id ASC
 LIMIT 200
```

四个点：

- **`status IN` 的三个值来自 `ReservationRequestStatus.nonTerminalStatuses()`**，是**写死的三个**，不是「不等于终态」—— 以后加一个状态要记得改 `:14-15`。

- 枚举存的是 `name()`：`application.yaml:43` 配了 `default-enum-type-handler: org.apache.ibatis.type.EnumTypeHandler`，所以 `status` 列里就是 `'PRE_ACCEPTED'` 这样的字符串。

### 3.5.1 补偿用的那个 Lua

`utils/ReservationQuotaRollbackExecutor.java:30-46`

```java
/**
 * 返回 0 表示用户本来就未占用名额（重复补偿或从未占用），名额不变；
 * 返回 1 表示用户确实占用名额且名额键存在，已归还一个名额；
 * 返回 2 表示用户确实占用名额但名额键已不存在，仅清理用户标记、不归还名额。
 */
public int rollback(Long batchId, Long userId) {
    String quotaKey = RESERVATION_BATCH_QUOTA_KEY + batchId;
    String usersKey = RESERVATION_BATCH_USERS_KEY + batchId;
    Long result = stringRedisTemplate.execute(
            RESERVATION_ROLLBACK_SCRIPT,
            Arrays.asList(quotaKey, usersKey),
            userId.toString());
    if (result == null || (result != 0L && result != 1L && result != 2L)) {
        throw new IllegalStateException("预约名额回滚脚本返回异常：" + result);
    }
    return result.intValue();
}
```

**两条 key 和 05 篇抢名额时用的完全是同一对**（`utils/RedisConstants.java:20-21`）：

```java
public static final String RESERVATION_BATCH_QUOTA_KEY = "reservation:batch:quota:";
public static final String RESERVATION_BATCH_USERS_KEY = "reservation:batch:users:";
```

脚本 `resources/reservationRollback.lua`（**全文 8 行**）：

```lua
if redis.call('SREM', KEYS[2], ARGV[1]) == 0 then
    return 0
end
if redis.call('EXISTS', KEYS[1]) == 1 then
    redis.call('INCR', KEYS[1])
    return 1
end
return 2
```

逐行：

| 行 | 在干什么 |
|---|---|
| 1-3 | `SREM users:{batchId} {userId}`。**返回 0 说明这个人本来就不在 Set 里** → 直接 `return 0`，**什么都不做**。这就是「重复补偿不重复加名额」的那道闸。 |
| 4-7 | 人确实在 Set 里（`SREM` 返回 1，已经被移除了）→ 看 `EXISTS quota:{batchId}`。存在 → `INCR` 名额 → `return 1`：**名额真的还回去了一个**。 |
| 8 | 人确实在 Set 里，但 quota key 已经不存在（TTL 到期 / 批次被关时删掉）→ `return 2`：**只清用户标记，不归还名额**。这时候也没什么可还的 —— key 都没了。 |

**三种返回值的语义在 Java 侧的注释里逐字写着**（`:30-34`），返回值也做了白名单校验（`:42-44`），不是 0/1/2 就抛 `IllegalStateException`。

**参数约定：`KEYS[1]` = quota key，`KEYS[2]` = users key，`ARGV[1]` = userId**。注意 `rollback` 只传了 `userId` 一个参数 —— 和抢名额的脚本不一样，**它不需要窗口时间、也不需要 TTL**。

**例子里的对应值**（102 这次补偿，`batchId = 7`、`userId = 102`）：

| 步 | 命令 | 之前 | 之后 | 返回值 |
|---|---|---|---|---|
| 1 | `SREM reservation:batch:users:7 102` | `{101,102,104,105}` | `{101,104,105}` | `1`（人确实在） |
| 2 | `EXISTS reservation:batch:quota:7` | — | — | `1`（key 还在，TTL 剩 197100） |
| 3 | `INCR reservation:batch:quota:7` | `"1"` | **`"2"`** | — |
| 4 | `return 1` | — | — | **`rollback` 返回 1 = 「确实占用、已归还一个名额」** |

**`reservation:batch:quota:7` 从 `"1"` 变成 `"2"`**（`"1"` 是 103 在 09:05 取消时还回来的那个，见 §0.2）。

**103 那次补偿不存在** —— 他走的是分支 A，`rollback` 根本没被调用。他的名额早在 09:05 由他自己的取消还回去了（09 篇），所以这里不欠他什么；`users:7` 里也早就没有 103 了。

### 3.5.2 那条顺序要求：先做补偿，再宣告终结

**这一处的「文件:行号」是 `src/main/java/com/yanyuetong/service/impl/ReservationReconcileServiceImpl.java:124-126`**，相邻三行原文：

```java

125:  rollbackExecutor.rollback(request.getBatchId(), request.getUserId());
```

顺序是 **`:125` 先 `rollback`，`:126` 才 CAS 改状态**。

为什么不能反过来（`:124` 那行注释就是答案）：

- 如果**先**把状态推成 `COMPENSATED`、**再**还名额，而还名额那一步抛异常 → 这一行已经不是非终态了，`listStale` 的 `status IN (非终态)` 永远筛不到它，**名额再也回不来**。
- 现在这个顺序下，`rollback` 抛异常 → 控制流直接跳到 `:136` 的 `catch`，`casStatusWithFailReason` 根本没执行 → **这一行留在非终态，下一轮还会被扫到**，重试直到成功。

`rollback` 本身也是**幂等**的（Lua 第 1-3 行的 `SREM == 0 → return 0`）：所以「上一轮还了名额但 CAS 失败、这一轮重跑」不会把名额还两次，最多是 `SREM` 返回 0 然后原样返回。

**同一个顺序在项目里还有两处**（本篇只负责 `:124-126` 这一处）：`releasePendingQuotas` 的 `:159` 在 `:160-164` 之前（§四），以及 06 篇 `publishReservationMessage` 里「先 `rollback`、再 CAS 成 `COMPENSATED`」那一段（`ReservationServiceImpl:287-311`）。

- **`recordReconcileFailureSafely`**（`:177-184`）：

  `RECONCILE_ATTEMPT_FAILED_REASON` 是另一个类常量（`:31`），值是 **`"RECONCILE_ATTEMPT_FAILED"`**。**内层再包一层 try** —— 连「记录失败原因」这件事都不允许把整轮带下水。

- **`recordFailReason` 会把 `update_time` 推到现在**（`ReservationRequestServiceImpl.java:64-72`）：

  ```java
  // 首次写入失败原因会触发 MySQL 的 ON UPDATE，但重复写入同一原因是 no-op，
  // 不会自动推进 update_time；这里必须显式赋值，避免持续失败行重新钉在扫描窗口队首。
  return reservationRequestMapper.update(null, new LambdaUpdateWrapper<ReservationRequest>()
          .eq(ReservationRequest::getRequestId, requestId)
          .set(ReservationRequest::getFailReason, failReason)
          .set(ReservationRequest::getUpdateTime, LocalDateTime.now())) == 1;
  ```
  因为「重复写同一个 `fail_reason`」对 MySQL 来说是 no-op，不会触发 `ON UPDATE` —— 必须**显式赋 `update_time`**。结果是**失败的行下一轮不会立刻被扫到，要再等 10 分钟**（`update_time < now − 10min` 又成立了）。这就是为什么 `listStale` 要 `ORDER BY update_time ASC`：不推时间的话，一条持续失败的行会一直钉在队首，每轮都占一个 `LIMIT 200` 的位置。

- **对账没有重试上限**。反复失败的行就一直留在非终态、每 10 分钟被重试一次，直到成功。**`dlq-max-replay: 3` 管不到这里** —— 那是 `ReservationDlqServiceImpl:60` 读的、死信**手动重放**的次数上限（10 篇）。**对账这条路径完全不碰 `tb_reservation_dlq`**：它只按 `tb_reservation` 主键在不在来判，死信台账里有没有行、`replay_count` 是几，它一概不看。
  - 例子里的 102 **在死信台账里确实有一行**（`id = 1`、`status='NEW'`、`replay_count = 0`、`failure_reason = 'LOCK_TIMEOUT'`，消息被 `basicNack` 进去的）。但对账不读它，所以这行在这一轮**原样不动**。
  - 这条岔路上没人点重放；假如后来有人去点，重放会先查账本：`request.getStatus() == COMPENSATED` → `discard(deadLetter, replayCount, "COMPENSATED", "请求已补偿，无法重放")`（`ReservationDlqServiceImpl:191-203`，`discard` 打上的标记是 `DISCARD:COMPENSATED`，同文件 `:307-311`）—— **丢弃、不落库**。也就是说 `COMPENSATED` 一旦写下，就**堵住了迟到的重放**，不会出现「名额已还 + 又落了一单」的超发。

**例子里的对应值**：这一轮 102 和 103 都没抛异常，`failed = 0`，`recordReconcileFailureSafely` 一次都没调用，账本里也没有任何一行的 `fail_reason` 是 `RECONCILE_ATTEMPT_FAILED`。

# 四、取消后的名额补偿：`releasePendingQuotas`

场景：用户取消预约时，`cancel` 已经先把 `tb_reservation` 改成了 `CANCELLED`，然后去还名额 —— **还名额那一步失败了**（`ReservationServiceImpl:162-175`，日志「取消预约后 Redis 名额归还失败，等待定时补偿」）。接口照样返回成功，`quota_released` 留在 `0`，等定时任务来补。

`ReservationReconcileServiceImpl.java:148-175`

```java
/**
 * 重试取消时未成功的 Redis 名额归还。返回本轮完成处理的条数。
 */
public int releasePendingQuotas(int limit) {
    if (limit <= 0) {
        return 0;
    }
    List<Reservation> pending = reservationMapper.selectPendingQuotaReleases(limit);
    int released = 0;
    for (Reservation reservation : pending) {
        try {
            rollbackExecutor.rollback(reservation.getBatchId(), reservation.getUserId());
            int updated = reservationMapper.update(null,
                    new LambdaUpdateWrapper<Reservation>()
                            .eq(Reservation::getId, reservation.getId())
                            .eq(Reservation::getQuotaReleased, false)
                            .set(Reservation::getQuotaReleased, true));
            if (updated == 1) {
                released++;
            }
        } catch (Exception e) {
            log.error("取消预约 Redis 名额补偿失败：reservationId={}，batchId={}，userId={}",
                    reservation.getId(), reservation.getBatchId(), reservation.getUserId(), e);
            deferPendingQuotaReleaseSafely(reservation);
        }
    }
    return released;
}
```

`selectPendingQuotaReleases` 的 SQL（`resources/mapper/ReservationMapper.xml:44-51`）：

```sql
SELECT r.id, r.user_id, r.batch_id, r.status, r.quota_released,
       r.create_time, r.update_time
FROM tb_reservation r
WHERE r.status = 'CANCELLED' AND r.quota_released = 0
ORDER BY r.update_time ASC, r.id ASC
LIMIT #{limit}
```

**筛选条件就是「已取消 **且** 还没还成」** —— `quota_released` 是 `tb_reservation` 上的一个 `tinyint NOT NULL DEFAULT 0` 标记位（`db/phase9_reservation_lifecycle.sql:4`），含义是「取消时名额是否已归还 Redis」。**这里没有时间窗口**，只要挂着 `0` 就一直会被捞。

逐句：

- **`:159` `rollback` 在前，`:160-164` 打标记在后** —— 和 §3.5.2 同一个顺序。
- **`:163` 的 `.eq(Reservation::getQuotaReleased, false)` 是 CAS 条件**：如果别的实例已经标过了，影响 0 行。`quotaReleased` 在实体里是 `Boolean`（`entity/Reservation.java:31`）。
- **返回的是 `updated == 1` 的条数**。注意 `rollback` 返回 `0`（这人本来就没占名额）时也会走到打标记并把标记打上 —— 这是对的：**标记的含义是「这条已经处理过了」，不是「真的还了名额」**。
- **catch 里不推进任何状态**，而是调 `deferPendingQuotaReleaseSafely`（`:186-195`）：

  ```java
  private void deferPendingQuotaReleaseSafely(Reservation reservation) {
      try {
          reservationMapper.update(null, new LambdaUpdateWrapper<Reservation>()
                  .eq(Reservation::getId, reservation.getId())
                  .set(Reservation::getUpdateTime, LocalDateTime.now()));
      } catch (Exception e) {
          log.error("取消预约 Redis 名额补偿重试时间推进失败：reservationId={}",
                  reservation.getId(), e);
      }
  }
  ```
  **把 `update_time` 推到现在** —— 因为 `selectPendingQuotaReleases` 是 `ORDER BY update_time ASC, id ASC`，不推时间的话这条失败记录会一直排在队首，每轮都占一个 `LIMIT 200` 的名额，把后面的挤出去。手法和 §3.6 的 `recordFailReason` 一样（都是显式推 `update_time`），理由也一样。

**例子里的对应值**（学生 104）：

| 项 | 值 |
|---|---|
| 命中的行 | `tb_reservation` 的 `id = 645827360351847426`，`user_id = 104`，`batch_id = 7`，`status = CANCELLED`，`quota_released = 0`，`update_time = 09:12:05` |
| `rollback(7, 104)` | `SREM users:7 104` → 返回 1（104 在 `{101,104,105}` 里）→ `EXISTS quota:7` = 1 → `INCR "2"` → **`"3"`** → 返回 **1** |
| 打标记的 SQL | `UPDATE tb_reservation SET quota_released = 1 WHERE id = 645827360351847426 AND quota_released = 0` |
| 影响行数 | `1` → `released++` |
| 这一趟之后 | `quota:7 = "3"`，`users:7 = {101,105}`，那行 `quota_released = 1` |
| 返回给 `scheduledReconcile` 的 | `released = 1` |

**和 §3.5 的分工**：两处都是还名额，但**标记打在不同的表上** —— 对账分支 B 打的是 `tb_reservation_request.status = 'COMPENSATED'`，这里打的是 `tb_reservation.quota_released = 1`。两处都容易漏，所以两处都有定时兜底。

# 五、爽约：`markNoShows`

`ReservationReconcileServiceImpl.java:197-205`

```java
/**
 * 批次已结束且仍未核验的预约置为爽约。爽约不归还任何名额。
 */
public int markNoShows(int limit) {
    if (limit <= 0) {
        return 0;
    }
    return reservationMapper.markNoShows(LocalDateTime.now(), limit);
}
```

SQL（`resources/mapper/ReservationMapper.xml:53-68`）：

```sql
UPDATE tb_reservation
SET status = 'NO_SHOW'
WHERE id IN (
    SELECT id
    FROM (
        SELECT r.id
        FROM tb_reservation r
        JOIN tb_reservation_batch b ON r.batch_id = b.id
        WHERE r.status = 'RESERVED'
          AND b.end_time < #{now}
          AND b.status <> 'CANCELLED'
        LIMIT #{limit}
    ) eligible
)
```

- **条件三条**：预约还是 `RESERVED`（没被核验成 `COMPLETED`）、**批次的 `end_time` 已经过了**、批次本身不是 `CANCELLED`。
- **多套一层 `SELECT id FROM (...) eligible`**：MySQL 不允许在 `UPDATE` 的 `WHERE` 里直接子查询同一张表，用派生表绕过（派生表会被物化）。
- **`RESERVED` → `NO_SHOW`**，没有中间状态，**没有 `WHERE` 到具体 id**，一次最多改 `limit` 行。
- **注释那句「爽约不归还任何名额」**：这里只改 `tb_reservation.status`，**没有调 `rollbackExecutor`**。名额是随 `reservation:batch:quota:{batchId}` 的 TTL 一起消失的（`publish` 时设的 TTL 是 `endTime + 24h`，例子里的 quota key 在 2026-10-09 16:00 后过期）。
- **爽约之后这个人仍然占着「同一批次」的槽位**：`ReservationStatus.occupyingStatuses()` 里 `NO_SHOW` 和 `COMPLETED` 都算占用（`enums/ReservationStatus.java:19-20`），判据必须和 `tb_reservation.active_flag` 生成列严格一致（`phase9_reservation_lifecycle.sql:5`：`CASE WHEN status='CANCELLED' THEN NULL ELSE 1 END`）—— 所以爽约后**不能再对同一批次发起预约**。

**例子里的对应值**：这一轮 `now = 2026-10-07T09:15:00.110`，批次 7 的 `end_time` 是 **2026-10-08 16:00**，`2026-10-08 16:00 < 2026-10-07 09:15` 不成立 → 一条都挑不出来 → `markNoShows` 返回 **0**。

（要等到 2026-10-08 16:00 之后某轮，批次 7 里那些还是 `RESERVED` 的行才会被刷成 `NO_SHOW`。101、105 如果没人核验，到那时就是这一支的输入；103 那行已经是 `CANCELLED`，`status = 'RESERVED'` 就把它挡在外面了。）

# 六、当前实现的边界

1. **判定只看 `tb_reservation` 主键在不在，不看那行的状态**（`:111`）。如果那行已经被取消（`status='CANCELLED'`），对账照样把账本推成 `CONFIRMED` —— 账本说「成功」，事实表说「取消」，两边并不冲突（账本记的是请求链路），但**别把账本的 `CONFIRMED` 当成「预约还有效」**。例子里的 103 就是这一条：他 09:05 取消了，账本还是被推成 `CONFIRMED`。
2. **名额已经还不回来时，`rollback` 不会报错**。如果 quota key 已经因 TTL 过期 / 批次被关而消失，Lua 走到 `EXISTS = 0` 分支返回 **2**，只 `SREM` 清掉用户标记、**不 `INCR`**（`ReservationQuotaRollbackExecutor:30-34` 逐字写了这个语义）。此时账本照样会被推成 `COMPENSATED`，看起来「补偿成功」，实际名额是随 key 一起没的。
3. **`reconcile-limit: 200` 是每轮每任务的硬上限**。陈旧账本行超过 200 条时，排在后面的要等下一轮（5 分钟后）；`reconcile` / `releasePendingQuotas` / `markNoShows` **各取 200，不是共享一个 200 的总额**。而失败的行会被显式推 `update_time` 往后排（`ReservationRequestServiceImpl:64-72`、`:186-195`），极端情况下一直在队尾排队。
4. **多实例下那把锁只减少重复工作，不保证互斥正确性** —— 源码注释自己写着（`:55`）。`tryLock(0)` 抢不到就跳过，意味着**持锁实例那一轮挂掉（进程被 kill、锁随看门狗过期）时，这一轮就没人补**；反过来两个实例同时跑也不会把名额 `INCR` 两次（Lua 先 `SREM` 判过），但 `confirmed` / `skipped` 的计数会各算各的 —— 那只是日志里的数字，不是数据。

## 7.3 对账会写进 `fail_reason` 的两个值

**源码里对账只写这两个**（`ReservationReconcileServiceImpl:30-31`），都是 `private static final String`：

| 常量 | 值 | 什么时候写 | 之后的状态 |
|---|---|---|---|
| `NO_RESERVATION_FAILURE_REASON` | `"RECONCILE_NO_RESERVATION"` | 分支 B：`tb_reservation` 里没有这一行，已补偿 | 推到 `COMPENSATED`（终态） |
| `RECONCILE_ATTEMPT_FAILED_REASON` | `"RECONCILE_ATTEMPT_FAILED"` | 这一条处理时抛了异常 | **状态不动**，留在非终态，下一轮重试 |

两个常量名和字符串值都照抄源码，**一个字母都不能改**。注意第二个**只写 `fail_reason`、不碰 `status`** —— 它和第一个不是一类东西：一个是结论，一个是「这轮没做成」的痕迹。
