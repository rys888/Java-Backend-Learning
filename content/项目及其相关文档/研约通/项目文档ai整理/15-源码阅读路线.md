## 怎么读：三条纪律

### 纪律一：先读签名、注释、枚举，不要逐行读

**每一步的正确读法是：**

1. **看方法签名**——参数和返回值告诉你这个方法关心什么；
2. **看类注释和方法注释**——**这个项目的注释质量很高**，很多设计理由直接写在注释里（比如对账那句「分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证」）；
3. **看枚举定义**——状态机的全部可能取值都在这；
4. **最后才看实现**——而且要**带着问题看**（「这里为什么先做 A 再做 B」）。

**为什么？因为逐行读会淹没在细节里。** 你先要知道「这个方法在整条链路的哪个位置、它的契约是什么」，细节才有地方挂。

### 纪律二：遇到 Lua 先自己写伪代码

**不要直接读那 27 行 Lua。** 先问自己：

> 「如果要我用 Java 写一个方法，保证『查名额、查时段、查重复、扣减』这四步不被并发插入，我会怎么写？会遇到什么问题？」

**你写下伪代码、发现到处是窗口之后，再去读 `reservation.lua`——那 27 行就会变得极其清晰。** 顺序反过来的话，你只会觉得「哦，一段脚本」。

### 纪律三：每读一个方法，问「如果这一步失败了会怎样」

**这是这个项目的主线，也是它区别于普通 CRUD 项目的地方。** 具体是四个问题：

1. **如果这一步抛异常了，会留下什么状态？**
2. **这个状态能被后续的哪个机制发现？**
3. **如果不能被发现——那就是一个缺口，记下来。**
4. **如果能被发现，是哪个定时任务 / 哪次条件更新 / 哪个 Lua 的返回值？**

**配合 `12-异常场景推演.md` 用**：那份文档的 20 个场景，就是这四问的 20 次演练。

## Day 1 —— 请求是怎么进来的

**目标**：画出**任意一个请求**从进入 Tomcat 到进入 Controller 的完整路径，说清三个拦截器各自做什么、顺序为什么重要。

**预计 2.5 小时。**

### 先看什么（按顺序）

| 序 | 文件 | 重点看什么 |
|---|---|---|
| 1 | `config/MvcConfig.java` | **三个拦截器的注册顺序**（`order(0)` / `order(1)` / `order(2)`）和 `excludePathPatterns` |
| 2 | `utils/RefreshTokenInterceptor.java` | `preHandle` 里**四次提前返回**；`afterCompletion` 里的 `UserHolder.removeUser()` |
| 3 | `utils/LoginInterceptor.java` | 只有 5 行——**它是怎么做到「只查 ThreadLocal」的**？ |
| 4 | `utils/RoleInterceptor.java` | **两级注解查找**（方法优先，再类）；`instanceof HandlerMethod` 那个早退 |
| 5 | `utils/UserHolder.java` | `ThreadLocal` 的 `saveUser` / `getUser` / `removeUser` |
| 6 | `annotation/RequireRole.java` | `@Target({METHOD, TYPE})` ——**为什么两种都支持** |
| 7 | `service/impl/UserServiceImpl.java` | `sendCode` / `login` / `logout` 三个方法 |
| 8 | `config/WebExceptionAdvice.java` | 四种异常分别映射成什么状态码 |
| 9 | `dto/Result.java` + `dto/UserDTO.java` + `dto/LoginFormDTO.java` | 统一返回体；**注意 `LoginFormDTO` 只有两个字段** |

### 再看什么

**先合上源码，自己在纸上画一遍**：

```
请求 ──► RefreshTokenInterceptor(order 0)
            │  有 token 且 Redis 里有 → UserHolder.saveUser + 续期
            │  无 token / Redis 里没有 → 直接放行
            ▼
         LoginInterceptor(order 1)   [排除 /user/code, /user/login]
            │  UserHolder 为空 → 401 拦截
            ▼
         RoleInterceptor(order 2)
            │  有 @RequireRole 且角色不匹配 → 403 拦截
            ▼
         Controller
            ▼
         返回时依次 afterCompletion（★ 逆序）
```

**画完之后对照源码检查三件事**：

1. **为什么 `RefreshTokenInterceptor` 必须是 `order(0)`？** —— 因为它要**最先**把用户放进 ThreadLocal，最后的 `afterCompletion` 才能清理。**如果顺序反了，`UserHolder.removeUser()` 永远不会执行 → ThreadLocal 泄漏**（Tomcat 线程池复用，下一个请求可能拿到上一个用户的身份）。
2. **`LoginInterceptor` 里的 `UserHolder.getUser()` 是唯一的数据来源吗？** —— 是。**它不查 Redis、不查数据库。** 这是「认证逻辑集中在一处」的做法。
3. **`logout` 为什么最后还有一行 `UserHolder.removeUser()`？** —— 因为 `afterCompletion` 也会做一次，**这里是「当前请求内立刻生效」**——`UserHolder.getUser()` 是 ThreadLocal，删了之后本线程内就查不到了。

### 必须搞懂的 5 个问题

1. **三个拦截器的顺序能不能换？** 换哪两个会出问题、出什么问题？
2. **`RefreshTokenInterceptor` 里那四次提前返回分别是什么？** 为什么「token 为空」和「Redis 里查不到」都要 `return true` 而不是 `return false`？
3. **`RoleInterceptor` 的权限校验发生在 `LoginInterceptor` 之后**——如果顺序反了会怎样？
4. **登录用的 Redis Hash 里存的是什么？** 为什么 `BeanUtil.beanToMap` 要配 `setFieldValueEditor`？（**提示：Redis Hash 的值只能是字符串**）
5. **`WebExceptionAdvice` 里 `BadRequestException` 映射成 400、`ServiceUnavailableException` 映射成 503**——**这个 503 在业务上代表什么特殊含义？**

### 学完能脱离源码讲出什么

> 「请求进来先过 `RefreshTokenInterceptor`：它从 `authorization` 头拿 token，去 Redis 查 `login:token:{token}` 这个 Hash，查到就反序列化成 `UserDTO` 放进 `ThreadLocal`，并把 TTL 重置为 30 分钟。**它的顺序必须是 0**，因为 `afterCompletion` 是逆序执行的——**只有它的 `preHandle` 成功了，`removeUser` 才会被调用**，否则 ThreadLocal 会泄漏。
>
> 然后 `LoginInterceptor` 只做一件事：**检查 ThreadLocal 里有没有用户**，没有就 401。它排在第二是因为**它依赖第一个拦截器的结果**。
>
> 最后 `RoleInterceptor` 检查 `@RequireRole` 注解——**方法上的优先于类上的**，所以同一个 Controller 里的读接口可以不标注解（默认放行）、写接口标 `@RequireRole(LAB_ADMIN)`。」

## Day 2 —— 业务模型与只读链路

**目标**：走通「查设备详情」这条读链路，说清**三种缓存防护各自解决什么、以及它们的一致性边界**。

**预计 2 小时。**

### 先看什么（按顺序）

| 序 | 文件 | 重点看什么 |
|---|---|---|
| 1 | `enums/ReservationBatchStatus.java` + `enums/BookingState.java` | **两套状态**各自的取值；`BookingState.of` 的**判定顺序** |
| 2 | `enums/ReservationStatus.java` | `occupyingStatuses()` 包含哪几个状态？ |
| 3 | `service/impl/ReservationBatchServiceImpl.java` | `fillBookingState` ——**`BookingState` 唯一的写入点** |
| 4 | `utils/RedisConstants.java` | **所有 Redis key 的前缀和 TTL 都在这**——先通读一遍，后面每天都要回来看 |
| 5 | `utils/CacheClient.java` | `queryWithMutex` 的**双重检查**；`MUTEX_MAX_RETRY` 的值；空值缓存写在哪一行 |
| 6 | `service/impl/EquipmentServiceImpl.java` | 详情查询怎么调 `CacheClient`；**更新时是 `delete` 还是 `set`** |
| 7 | `resources/unlock.lua` | 三行——**为什么解锁必须用 Lua** |
| 8 | `service/impl/LaboratoryServiceImpl.java` | `assertManageable`——**归属校验的三跳查询** |

### 再看什么

**把「缓存防护」和「一致性」分成两个问题看：**

| 问题 | 机制 | 参数 |
|---|---|---|
| 缓存穿透 | 空值缓存 | `CACHE_NULL_TTL = 2` **分钟**（**为什么比正常 TTL 短 15 倍？**） |
| 缓存击穿 | 互斥锁 + 双重检查 | `MUTEX_MAX_RETRY = 20`，每次 `sleep(50)` |
| 缓存雪崩 | TTL 抖动 | `30min + [0, 5min)`，**在调用点算，不侵入 `CacheClient.set`** |

**然后专门看两个「没做」的地方：**

1. **更新时用 `delete` 而不是 `set`**——想清楚**为什么写缓存不安全**（提示：并发下「写库」和「写缓存」的顺序无法保证）；
2. **`deleteEquipmentCache` 没有 try/catch**——**如果 Redis 删除失败，会发生什么？** 接口报错但数据已经写成功了，而缓存里的旧值要等 30 分钟 TTL。

### 必须搞懂的 5 个问题

1. **`BookingState` 和 `ReservationBatchStatus` 有什么区别？为什么其中一个不能入库？**
2. **`queryWithMutex` 里为什么要有第二次检查缓存？** 没有会怎样？
3. **手写的 `SETNX` 锁为什么需要 UUID 归属令牌？** 用 `unlock.lua` 而不是 `get` 然后 `del`，防的是什么？
4. **抢锁重试 20 次失败之后，代码做了什么？** （提示：直查库 **且不回写缓存**）——**这个兜底在什么情况下会变成数据库的雪崩入口？**
5. **`assertManageable` 是哪三跳查询？为什么权限校验要查这么深？**

### 学完能脱离源码讲出什么

> 「设备详情的缓存用的是 Cache Aside，一条读路径上叠了三种防护：**空值缓存防穿透**（查不到也写一个空字符串，TTL 只有 2 分钟）、**互斥锁重建防击穿**（拿到锁之后要**双重检查**缓存，因为等锁期间别人可能已经建好了）、**TTL 抖动防雪崩**（30 分钟加一个 0–5 分钟的随机量）。
>
> **更新时是删除缓存而不是写缓存**——因为并发下写缓存可能用旧值覆盖新值，而删除不携带数据，永远安全。
>
> **一致性边界是**：最坏情况下缓存里的旧值会存活 30 分钟（TTL 兜底），因为删除缓存没有补偿逻辑。**但这只影响展示，不影响业务判定**——`submit` 里对设备和批次的校验是**直查数据库**的，不走缓存。」

**场景 C：Lua 执行完之后、消息投递之前，进程被 `kill -9`。** **Redis 里是什么？MySQL 里是什么？谁会发现它？多久之后？**

### 必须搞懂的 5 个问题

> **这五个是「这一天没白读」的判据。**

1. **`reservation.lua` 里 6 个返回码的顺序，为什么时段检查在名额检查之前、去重检查在名额检查之后？** 这带来一个什么副作用？
2. **名额键的 TTL 为什么是「`endTime` + 24 小时」而不是「`bookingEndTime`」？** （**提示：取消操作在预约截止之后仍然允许**）
3. **`submit` 里那个 `now` 是在哪一行算的？它在 Lua 里被用了几次？** 为什么 Java 侧和 Lua 侧都要校验时间窗口？
4. **`publishReservationMessage` 把投递结果分成哪三类？`UNKNOWN` 这一类的判定条件是什么？它为什么绝不归还名额？**
5. **`submit` 为什么不能加 `@Transactional`？** 说出至少两个理由。

### 学完能脱离源码讲出什么

> 「`POST /reservation` 进来之后，Controller 不做任何并发处理，全交给 `ReservationServiceImpl.submit`。
>
> 第一步是一串**前置校验**——批次存在、状态是 `PUBLISHED`、设备可用、当前时间在预约窗口内。**这些校验读的是数据库，不是缓存。**
>
> 然后**生成 `reservationId`**（`RedisIdWorker`，时间戳左移 32 位加上一个 Redis 自增的当日序号），**紧接着在 MySQL 写一条 `PRE_ACCEPTED` 的账本记录**。**顺序很重要：账本在扣 Redis 之前写。** 因为 Redis 是易失的，如果先扣 Redis 再写账本，中间崩溃就会留下一个没有任何记录的已扣名额，**对账永远扫不到它，名额永久泄漏**。
>
> 第三步是**跑 Lua 脚本抢名额**。脚本做四件事：校验批次存在、校验预约窗口、校验名额、校验重复，然后 `DECR` 加 `SADD`。**这四件事必须在同一个脚本里，因为多条命令之间的间隙就是超卖窗口**——两个并发请求可以都通过检查，然后都扣减，扣成负数。
>
> 第四步是**投递 MQ 并同步等发布确认**，超时 5 秒。这里我把它分成**三种结果**：成功、**确定失败**（连接异常 / NACK / 被退回）、**不确定**（超时）。**只有确定失败才当场归还名额**；不确定的账本置成 `UNKNOWN`，**什么都不归还**——因为消息可能已经进队列了，归还就会超发。
>
> 最后账本置 `PUBLISHED`，返回 `reservationId`。落库是消费者异步做的。」

> 结果如果是 `PERSISTED` 或 `DUPLICATE`，账本置 `CONFIRMED`，**最后才 ACK**——**ACK 放在所有副作用之后**。」

### 必须搞懂的 5 个问题

1. **`publisher-confirm` 和 `publisher-returns` 各自覆盖哪个失败点？** 只开一个会漏掉什么？
2. **`publisher-confirm-type: correlated` 和 `simple` 的区别是什么？** 如果配成 `simple`，第 3 天的 `getFuture().get(...)` 会怎样？
3. **`basicNack` 的三个参数是什么？为什么 `requeue` 必须是 `false`？**
4. **为什么 DLQ 消费者不用 Jackson，而用 `SimpleMessageConverter` 加原始 `Message`？**
5. **死信重放的五道检查分别是什么？** 其中哪一道划出了一个「时间窗口」？（**提示：对账阈值 10 分钟**）

### 学完能脱离源码讲出什么

> 「生产端有两道确认：**publisher-confirm** 回答「broker 收到了吗」，**publisher-returns 加 mandatory** 回答「broker 放进队列了吗」。**这两道必须都开，因为它们覆盖的是不同的失败点**——只开 confirm 的话，路由键匹配不到任何队列，broker 照样回 ACK，**消息被静默丢弃**。
>
> 而且 **`mandatory` 和 `publisher-returns` 必须成对出现**——`mandatory=false` 时 broker 会直接丢弃路由失败的消息，`ReturnCallback` 永远不会触发，**而且没有任何报错**。
>
> **`publisher-confirm-type` 必须是 `correlated` 不能是 `simple`**，因为代码里用 `CorrelationData` 的 future 同步等结果，`simple` 模式下那个 future 不会被完成。

>
> 失败走 `basicNack(requeue=false)` 进死信。**`requeue=false` 是关键**，`true` 会无限循环。DLQ 的消费者用原始字节加 `SimpleMessageConverter`，**避免反序列化失败的消息再经过 Jackson 形成失败循环**。
>
> **死信重放有五道检查**，其中最后一道是「账本是否已 `COMPENSATED`」——**这划出了一个约 10 分钟的黄金恢复窗口**：超过对账阈值之后，请求已经被补偿、名额已经归还，**这时再重放就会超发，所以会被拒绝**。」

### 再看什么：把「三个不变式」找出来

**对账任务里藏着三条可以独立成立的不变式，把它们找出来并说清各自防什么：**

| 不变式 | 代码位置 | 防什么 |
|---|---|---|

| **重复写同一个值也要显式推进 `update_time`** | `recordFailReason` 的注释 | **MySQL 的 `ON UPDATE` 在值不变时不触发**，会让持续失败的行永远钉在扫描窗口队首 |

4. **`rollback` 返回 0 / 1 / 2 分别是什么含义？** 为什么返回 2 的时候**不能** `INCR`？（**提示：`INCR` 一个不存在的 key 会创建一个没有 TTL 的 key**）
5. **为什么说「分布式锁只管性能，不管正确性」？** 如果锁失效、两个实例同时扫同一批数据，**每一个副作用分别靠什么保证幂等？**

### 学完能脱离源码讲出什么

> 「对账任务每 5 分钟跑一次，扫出 `update_time` 早于「现在减 10 分钟」且状态非终态的请求，**用『`tb_reservation` 里有没有这个 id 的行』来裁决**——有就推 `CONFIRMED`，没有就归还 Redis 名额并推 `COMPENSATED`。
>
> 它还有两个配套任务：`releasePendingQuotas` 补偿「取消时 Redis 归还失败」的记录（扫 `status='CANCELLED' AND quota_released=0`），`markNoShows` 把批次已结束仍未核验的预约置为爽约（**爽约不归还名额**）。
>
> **★ 对账里最重要的一条不变式是「必须先补偿、再改状态」**——因为如果先改状态再补偿，补偿失败时那条记录已经是终态了，**对账永远不会再扫到它，名额就永久泄漏**。反过来，补偿失败时状态还留着非终态，下一轮会继续重试；**而且因为补偿脚本本身是幂等的，重复执行是安全的**。
>
> **★ 分布式锁只用来减少多实例的重复工作，正确性不押在锁上**——因为锁会失效（GC 停顿、网络分区）。真正的保证是：**状态迁移用 CAS 条件更新**（只有一个实例的 `affectedRows == 1`）、**名额归还走幂等 Lua**（`SREM` 的返回值就是幂等令牌）、**`quota_released` 用 CAS 置位**。所以即使锁完全失效，结果和单实例完全一样。
>
> **退避不用计数器**（表里根本没有这一列），而是**推进 `update_time` 让这条记录退出陈旧窗口**。而这里有一个 MySQL 的坑：**`ON UPDATE CURRENT_TIMESTAMP` 在写入的值和当前值相同时不触发**——所以重复写同一个 `fail_reason` 时必须**显式写 `update_time`**，否则持续失败的行会永远排在扫描队列的队首，**把对账的 `limit` 配额耗尽，让整个自愈机制停摆**。」

## Day 7 —— 取消 / 核验 / 爽约

**目标**：说清**「取消」这个动作里为什么有那么长的一段注释**，以及**为什么 Redis 归还必须在特定条件下才执行**。

| 4 | `controller/ReservationController.java` | `cancel` 和 `verify` 两个接口 |
| 5 | `mapper/ReservationMapper.xml` 的 `markNoShows` | 为什么有一条 `b.status <> 'CANCELLED'` |

### 再看什么：手工推演这个场景

**这是全项目推理密度最高的地方，值得单独推演一遍：**

```
T1  R1：用户 U 抢到名额        → Redis users = {U}，MySQL 有 R1（RESERVED）
T2  U 取消 R1（第 1 次）        → 数据库 CAS 成功（TRANSITIONED）→ Redis 归还 → users = {}
T3  U 重新抢到 R2               → Redis users = {U}，MySQL 有 R2（RESERVED）
T4  U 再次提交「取消 R1」       → 数据库 CAS 失败（ALREADY_CANCELLED）
        ★ 问题：这时能调用 Redis 归还吗？
```

**推演 T4 如果调用归还会发生什么**——**两个方向的错误**：

- Redis 名额 +1（归还了 R1 的），**但 R2 还占着** → **超发**；
- 那个多出来的名额被某个用户抢到（Lua 通过），落库时被唯一索引拒绝 → **Redis 少了一个名额，但 MySQL 里没有对应预约行** → **名额泄漏**。

**所以答案是不能。** 这就是注释里那句话的含义：**只有本事务真正完成跃迁（`TRANSITIONED`）才允许归还名额。**

### 必须搞懂的 5 个问题

1. **`ReservationCancelOutcome` 四个值在 `ReservationServiceImpl.cancel` 里分别怎么处理？** 哪一个分支**必须什么都不做**？
2. **`reservationRollback.lua` 的幂等粒度是什么？** 为什么它在这个场景下**不够用**？
3. **`cancel` 的批次名额回补用了 `WHERE remaining_quota < total_quota`**——这个条件的必要性是什么？为什么失败时**只打 warn 不报错**？
4. **为什么 Redis 归还要放在 `@Transactional` 之外？** 如果放在事务里，失败回滚会怎样？
5. **`complete` 里「重复核验」返回 `false` 而不是报错**——这个选择和 `cancel` 的处理方式有什么共同的原则？

### 学完能脱离源码讲出什么

> 「取消分成两步：**数据库事务内**做 `RESERVED → CANCELLED` 的状态跃迁（CAS，带 `user_id` 条件防越权）并回补批次名额；**事务外**归还 Redis 名额。
>
> **顺序和位置都是有讲究的**：
>
> 一是**必须先提交事实，再做可能失败的补偿**——如果 Redis 归还在事务里，失败回滚会把「预约已取消」这个事实也回滚掉，`releasePendingQuotas` 就永远扫不到这条记录了；
>
> 二是**只有真正完成了 `TRANSITIONED` 跃迁的那一次调用才允许归还名额**。因为 `reservationRollback.lua` 的幂等粒度是 `(batchId, userId)`，而业务需要的粒度是 `reservationId`——**用户取消 R1 后重新预约得到 R2，再重复取消 R1 时，`SREM` 会移除 R2 的占位标记**，导致 Redis 多出名额而 MySQL 仍占用 R2，**既超发又打开名额泄漏**。
>
> 所以真正的保护在上层：**用『CAS 的 `affectedRows == 1`』这个一次性事件来决定要不要调用归还**。这是这个项目里我最喜欢的一处设计——**当底层操作的幂等粒度不够时，用一层「触发条件本身是一次性的」来补偿它。**」

| 名额回补 | `remaining_quota < total_quota` | 回补超上限 |
| 预约状态迁移 + 权限 | `status = ? AND user_id = ?` | 重复取消、越权 |
| 幂等标记 | `quota_released = false` | 重复归还 |

### 必须搞懂的 5 个问题

1. **`updateById` 和条件更新的本质区别是什么？** 用 SQL 的语言说清「判定和使用合并成一次原子操作」。
2. **为什么权限判定要下推到 `WHERE user_id = ?`**，而不是先查出来再用 Java 判断？
3. **项目里 `@Transactional` 只有 3 处，它们共同满足哪两个条件？** 反过来，`submit` 违反的是哪一条？
4. **`active_flag` 的 `GENERATED ALWAYS AS (...) STORED` 是怎么模拟「部分唯一索引」的？** 为什么 `NULL` 在这里是关键？为什么 Java 代码里零引用？
5. **`RedisIdWorker` 的 ID 位结构是什么？** 它和雪花算法的三个关键差异是什么？**它有什么问题？**

### 学完能脱离源码讲出什么

> 「这个项目有 16 处条件更新，核心手法是**把判定条件写进 `UPDATE` 的 `WHERE` 里**。比如扣名额是 `WHERE id = ? AND remaining_quota > 0`——**InnoDB 的行锁保证 `WHERE` 在锁内重新求值**，所以并发下第二个事务会看到第一个扣减后的值，`affectedRows` 是 0，**不需要再查一次库去确认**。
>
> 而 `updateById` 是读-改-写三步，两个线程可以都读到 `remaining=1`、都判断大于 0、都写 0——**两个都成功但只扣了 1**。
>
> **权限判定也用同样手法**：取消和核验的 UPDATE 都带 `user_id` 条件，这样越权请求的 `affectedRows` 天然是 0。
>
> **`@Transactional` 全项目只有 3 处**，都满足两个条件：**至少两步数据库写，而且不含任何网络调用**。`submit` 违反的是第二条——它有 Redis 操作和**最长 5 秒的同步等 MQ 确认**。加事务会有两个后果：一是长事务占用数据库连接（**Hikari 默认只有 10 个**），二是**事务能回滚的只有那条账本 INSERT，Redis 扣减不在事务里**——**回滚反而制造了「Redis 已扣、账本没了」的名额泄漏。**
>
> **唯一索引那块用了一个技巧**：需求是「一个用户在一个批次里只能有一条有效预约，但取消后可以重新预约」——**这是部分唯一索引，MySQL 不支持**。解法是加一个生成列 `active_flag`（`CANCELLED` 时为 `NULL`，否则为 1），对 `(user_id, batch_id, active_flag)` 建唯一索引。**利用「NULL 在唯一索引里不等于 NULL」，任意多行可以同时是 NULL，但只能有一行是 1。** 所以 Java 代码里对这个字段的引用数是 0——**它不是业务字段，是索引的载体。**」

## 附录 B：读完之后的三个自检

**读完这 8 天，你应该能不查源码回答这三个问题。答不出来就回去补对应的一天。**

### 自检 1（对应 Day 3 + Day 4）

> **一个学生点「预约」，从他的手指落到屏幕，到 Redis 里扣掉一个名额、MySQL 里多出一条预约行，中间经过了哪些步骤？每一步失败会怎样？**

**判据**：能说出**六步**、能说出**账本为什么在扣 Redis 之前写**、能说出**为什么超时不能归还名额**。

### 自检 2（对应 Day 6）

> **如果 RabbitMQ 从下午 3 点开始完全不可达，到 3 点半恢复，中间这半小时提交的预约会出现什么现象？最后会怎样？**

**判据**：能说出**「确定未投递 → 当场归还名额 → `COMPENSATED`」**这条路径、能说出**用户看到 503**、能说出**不需要对账介入**（因为是当场处理的）、以及**Redis 和 MySQL 都回到一致状态**。

### 自检 3（对应 Day 6 + Day 8）

> **如果 Redis 里的名额键被误删了，会发生什么？能不能恢复？**

**判据**：能说出**「该批次所有人都预约不了」**（Lua 第一行 `EXISTS` 返回 1）、能说出**页面却显示还有名额**（`fillRemainingQuotaFromRedis` 读不到键会回落 MySQL）、**并且能说出「当前代码没有任何路径能重建这个键」**——因为 `setIfAbsent` 要求批次是 `DRAFT`，而 `close`/`cancel` 只删不建。

**★ 第三个自检是最有价值的**，因为**它能证明你是真的读了所有写这个键的地方**，而不是只读了主链路。
