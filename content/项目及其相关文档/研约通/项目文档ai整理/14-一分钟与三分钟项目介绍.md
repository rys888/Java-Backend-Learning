## 一、30 秒版 —— 自我介绍里的一句话

> 「我做过一个高校实验资源预约平台的后端，叫**研约通**。
>
> 业务模型是**实验室 → 设备 → 预约批次 → 预约单**四层。技术栈是 **Spring Boot + MySQL + Redis + RabbitMQ**。
>
> 这个项目的核心难点是**高并发下的名额分配**——要同时做到**不超卖、不丢单、可自愈**。我用 **Redis Lua 脚本**做原子准入、**RabbitMQ** 做异步落库、加一张**请求状态账本**和**定时对账任务**来保证最终一致。」

**★ 说完停住。** 30 秒版的目的是**给出钩子**，不是讲完。**钩子是『不超卖、不丢单、可自愈』这九个字**——面试官如果感兴趣，会问下去。

**如果对方只回一个「哦」，那就到此为止，不要自己展开。**

## 二、1 分钟版 —— 简历项目栏被点名

> 「研约通是一个高校实验室预约平台。业务上，管理员为设备创建**预约批次**——设定开放时段、使用时段和名额上限；学生在开放窗口内抢名额。
>
> 需求可以拆成三条硬要求：**不超卖、不丢单、可自愈**。
>
> **不超卖**靠把「查名额 + 查时段 + 查重复 + 扣减」四步写进一个 **Lua 脚本**，利用 Redis 单线程保证原子性——这里不能用多条命令，因为检查和扣减之间的空隙就是超卖窗口。
>
> **不丢单**是关键设计。我没有直接用 MQ 异步下单，而是先做了一件事：**在扣 Redis 名额之前，先在 MySQL 里写一条 `PRE_ACCEPTED` 的请求账本记录**。这样无论后面在哪一步崩溃，MySQL 里都有一条可被扫描的记录。然后我给投递结果定义了**三种**：成功、**确定失败**、**不确定**——只有确定失败才立即归还名额，不确定的绝不归还，因为消息可能已经到了。
>
> **自愈**靠一个**定时对账任务**：10 分钟后账本还是非终态的，就去查 `tb_reservation` 里有没有对应的行——有就推成功，没有就归还名额。这个任务的正确性**不依赖分布式锁**，靠的是 CAS 条件更新和 Lua 补偿脚本的幂等。」

**★ 1 分钟版的落点是「三种投递结果」和「账本」这两个设计。**

**为什么？因为它们是最能体现『你懂分布式』而不是『你会用中间件』的地方。** 会配 RabbitMQ 的人很多，**知道「超时要单独归一类」的人不多。**

## 三、3 分钟版 —— 正式的项目介绍环节

**按四段讲：业务与难点 → 主链路 → 三个关键设计 → 边界与取舍。**

### 第一段：业务模型与难点（约 35 秒）

> 「这个项目是高校实验室预约平台，业务模型四层：**实验室 → 设备 → 预约批次 → 预约单**。
>
> 为什么批次要独立成一张表？因为只有设备 ID 无法表达『某个时段有几个名额』——名额必须挂在具体的开放窗口上。而且**预约窗口和使用时段是两个不同的时间区间**：前者决定什么时候能抢，后者决定什么时候能用。这两段时间之间有一条不变式——**必须先抢完才能开始用**。
>
> 难点在**瞬时并发加名额有限**：一个热门时段可能几百人同一秒点击。而这正好是一个适合用 Redis 加消息队列解决的问题。」

### 第二段：主链路（约 45 秒）

> 「一次预约的完整链路是六步：
>
> 一是用 **Redis 自增生成全局唯一 ID**；二是**在 MySQL 写一条 `PRE_ACCEPTED` 的请求账本**；三是跑 **Lua 脚本**原子抢名额；四是投递 MQ 并**同步等发布确认**；五是账本置为 `PUBLISHED`；六是消费者落库——**在同一个数据库事务里扣批次名额和插入预约行**，然后账本置 `CONFIRMED`，最后手动 ACK。
>
> 顺序上有讲究：**账本在扣 Redis 之前写**，这是整个设计的支点；**ACK 在所有副作用之后**，而不是落库之前。」

### 第三段：三个关键设计（约 60 秒）

> 「有三个我认为比较关键的设计。
>
> **第一是把投递结果分成三类**，而不是成功和失败两类：成功、**确定失败**、**不确定**。连接异常和 NACK 是确定失败，可以当场归还名额；**超时是不确定，绝不能归还**——因为消息可能已经进队列了，归还就超发。不确定的归到一个 `UNKNOWN` 状态，**10 分钟后由对账任务用『MySQL 里有没有这行数据』来裁决**。
>
> **第二是账本的状态机是五个状态**，而且 `UNKNOWN` **是非终态不是终态**——这是它存在的意义，终态就永远不会被对账扫到。
>
> **第三是对账任务的正确性不依赖分布式锁。** 锁只用来减少多实例的重复工作；真正的保证是**每次状态迁移都用 CAS 条件更新**，每次名额归还都走一个**幂等的 Lua 脚本**。所以即使锁失效、两个实例同时扫同一批数据，结果和单实例完全一样。」

### 第四段：边界与取舍（约 40 秒）

> 「最后说两个我自己清楚的边界。
>
> **一是没有压测过，所以给不出吞吐数字。** 但我可以定性地判断瓶颈：`submit` 里**同步等 MQ 确认，超时是 5 秒**，而 Hikari 连接池用的是默认的 10 个连接——**这是最先会出问题的地方**。
>
> **二是『确定失败』里我把连接异常也归进去了。** 严格说连接在写出消息的瞬间断开时，消息可能已经到 broker 了——**这是一个有兜底的乐观假设**：MySQL 侧的条件更新和唯一索引仍然会拦住超发。」

**★ 3 分钟版的关键是第四段。** 很多人讲完前三段就停了，**而第四段才是区分『我写的』和『我背的』的地方。**

**面试官听到「这个边界我清楚，兜底在哪我也清楚」，和听到「我这个方案能抗高并发」，是两种完全不同的评价。**

## 四、技术深挖版 —— 面试官说「这个点展开讲讲」

**对方挑了哪个词，就展开哪一段。不要主动全部倒出来。**

### A. 如果问「Lua 脚本」→ 讲为什么必须是一个脚本

> 「`reservation.lua` 做四件事：**校验批次是否开放、校验预约窗口、校验名额、校验是否重复，然后扣减**。
>
> 为什么必须写成一个脚本？**因为多条命令之间有间隙**。如果用 Java 分四条命令写，两个并发请求可以这样交错：A 查完说没重复，B 也查完说没重复，A 扣到 0，B 扣到 **-1**——**超卖**。这就是典型的 check-then-act 竞态。
>
> Redis 单线程保证单条命令原子，**但多条命令之间可以被插入**。Lua 脚本在 Redis 里是作为一个整体执行的，**执行期间不处理其他客户端的命令**，所以间隙就消失了。
>
> **顺带说一点**：Redis 6 之后的 `MULTI`/`EXEC` 事务也做不到这件事——事务里**不能根据中间结果做分支**，`EXEC` 是把命令排队一次性执行，你没法写 `if quota <= 0 then ...`。**所以这个场景只能用 Lua。**
>
> **脚本返回 0 到 5 六个码**，Java 侧映射成枚举和中文消息。这个设计的好处是**所有判定逻辑在同一个脚本里可读地排在一起**，Java 只负责翻译。
>
> 有一个顺序上的细节：**时段检查排在名额检查之前**，所以一个过了窗口、名额也满的批次，用户看到的是『预约已截止』而不是『名额已约满』——**这是更准确的信息**。
>
> 还有一处：**去重检查排在名额检查之后**，所以一个已经预约过的用户在名额耗尽后重试，拿到的是『名额已约满』而不是『你已预约过』。**这个顺序是必要的**，因为如果去重在前，用户在取消后重新预约的场景下会走到名额检查——**两种顺序都安全，当前的选择只是把更基础的信息排在了前面。**」

### B. 如果问「消息可靠性」→ 讲三道确认 + 三种结果

> 「**生产端两道、消费端一道。**
>
> **生产端第一道是 publisher-confirm**：broker 收到消息后回 ACK/NACK。配置必须是 **`correlated`** 而不是 `simple`，因为 `simple` 模式下 `CorrelationData` 的 future 不会被完成——**那我的 `getFuture().get(5, SECONDS)` 会永远阻塞到超时**。
>
> **第二道是 publisher-returns 加 `mandatory=true`**。这两个**必须成对出现**：只配 `publisher-returns` 而 `mandatory` 是 false，broker 会把路由失败的消息**直接丢弃**，`ReturnCallback` 永远不会触发，**而且没有任何报错**。`mandatory=true` 才让 broker 把消息退回并触发回调。
>
> **这两道覆盖的是不同的失败点**：confirm 回答『broker 收到了吗』，returns 回答『broker 放进队列了吗』。**只开 confirm 的话，路由键写错、没有任何队列绑定——broker 照样回 ACK，消息被静默丢弃。**
>
> **消费端是手动 ACK 加 `prefetch=1`**，而且关掉了自动重试。关重试的原因是**手动 ACK 模式下 Spring 默认的 recoverer 不会真正 nack**——如果不关，异常消息会卡住消费者。同时给容器配了 `ConditionalRejectingErrorHandler` 加 `setRejectManual(true)`，**因为反序列化失败发生在监听器方法之前，那时应用还没拿到 Channel，根本没机会自己 nack。**
>
> **最后是死信**：业务队列在声明时就绑定了 `x-dead-letter-exchange`，所以 `basicNack(requeue=false)` 之后 broker 自动转发到 DLQ。**`requeue=false` 是关键**——`true` 的话消息会重新入队、立刻又被同一个消费者拿到、又失败，**无限循环把队列堵死**。
>
> **DLQ 的消费者用原始 `Message` 加 `SimpleMessageConverter`，不用 Jackson**——**因为死信里最需要留存的就是反序列化失败的消息**，再用 Jackson 会形成失败循环。类注释写明了这一点。」

### C. 如果问「最终一致性」→ 讲账本 + 对账 + 三个不变式

> 「**核心是两张表和一条不变式。**
>
> 账本表 `tb_reservation_request` 有五个状态：`PRE_ACCEPTED`、`PUBLISHED`、`UNKNOWN`、`CONFIRMED`、`COMPENSATED`。**终态只有后两个**，前三个都会被对账扫描。
>
> **`requestId` 和 `reservationId` 是同一个值**——这样对账只需要『查一次主键』就能判断这次预约成没成功，不需要任何映射表。
>
> 对账任务每 5 分钟跑一次，扫出 `update_time` 早于『现在减 10 分钟』且状态非终态的请求：**能查到预约行就推 `CONFIRMED`，查不到就归还名额推 `COMPENSATED`**。
>
> **这里有一条我觉得最重要的不变式：必须先补偿、再改状态。** 因为如果先改状态再补偿，补偿失败时那条记录已经是终态了，**对账永远不会再扫到它，名额就永久泄漏**。反过来，补偿失败时状态还留着非终态，下一轮会继续重试；**而且因为补偿脚本本身是幂等的，重复执行是安全的。**
>
> 我把它总结成一句话：**先做不可逆的、幂等的副作用，再记录它已经发生。** 这个模式在项目里出现三次——对账的补偿、取消后的名额归还、以及 `releasePendingQuotas`。」

### D. 如果问「幂等」→ 讲三层幂等和粒度问题

> 「**消费侧有三层幂等，粒度各不相同。**
>
> **第一层是 `persist` 里的两个判断**：同 id 同 user 同 batch 算『同一次预约的重复投递』，直接返回 `DUPLICATE` 不重复扣名额；同 user 同 batch 但不同 id 算『业务上的重复』，也返回 `DUPLICATE`。
>
> **这里有一个我认为做得很细的地方**：第一个判断**只判那个三元组，不判 `existing != null`**。因为如果判宽了，一条『主键撞了但归属对不上』的消息会被当成幂等重复而**静默 ACK**——**消息消失了，死信队列里什么都没有，运维完全不知道出过事**。所以它让其他所有冲突继续走到 `insert`，由主键约束抛异常，被消费端捕获后 `basicNack` **进死信队列留痕**。
>
> **第二层是 Redisson 用户锁**，保证同一用户的消息串行处理。
>
> **第三层是唯一索引 `uk_user_batch_active`**，这是最终的、不可绕过的防线。
>
> **三层的分工是**：锁减少冲突（性能）、查询处理可预期的重复（语义）、唯一索引兜住所有意料之外的情况（正确性）。**前两层都可以失效，第三层不会。**
>
> **★ 而这个唯一索引本身是一个技巧**：需求是『一个用户在一个批次里同时只能有一条有效预约，但取消后可以重新预约』——**这是 PostgreSQL 的部分唯一索引，MySQL 不支持**。解法是加一个**生成列** `active_flag`，`status = 'CANCELLED'` 时为 `NULL`，否则为 1，然后对 `(user_id, batch_id, active_flag)` 建唯一索引。**利用『NULL 在唯一索引里不等于 NULL』这个特性，就等价于部分唯一索引。**
>
> **★ 计数幂等还有一个粒度问题我要主动说**：归还名额的 Lua 脚本用 `SREM` 的返回值做幂等令牌——**它的粒度是 `userId`，不是 `reservationId`**。所以在『用户取消 R1 后重新预约得到 R2、然后又重复取消 R1』的场景下会出错：`SREM` 会移除 R2 的占位标记。**真正的保护在上层**——取消操作里只有真正完成了 `RESERVED → CANCELLED` 状态跃迁的那一次，才允许调用归还。**这段推理项目里有一段很长的注释，是代码里注释最长的一处。**」

### E. 如果问「缓存」→ 讲三种范式和边界

> 「设备详情用的是 **Cache Aside**，一条读路径上叠了三种防护：**空值缓存防穿透、互斥锁重建防击穿、TTL 抖动防雪崩**。
>
> **更新时用删除而不是写入缓存**——因为并发下写缓存可能用旧值覆盖新值（两个更新请求的『写库』和『写缓存』顺序可能不一致），而**删除永远是安全的**：它不携带数据，最坏结果只是多一次未命中。
>
> **互斥重建里有双重检查**：拿到锁之后要重新读一次缓存。**因为『第一次检查未命中』和『拿到锁』之间有时间差**，持锁的线程可能已经把缓存建好了。没有双重检查的话，等锁的线程会排队一个一个去查库——**互斥锁就退化成了串行查询**。
>
> **★ 而这个项目的一致性边界我要说清楚**：缓存的陈旧只会让**展示**不准确，**不会让一个不可维护的设备被预约成功**——因为 `submit` 里对设备和批次的校验是**直查数据库**的，不走缓存。**当一个字段参与业务判定时，读它必须走权威数据源。**
>
> **★ 边界也有两个**：一是缓存删除**没有补偿**，删失败的话旧值最长存活 30 分钟（TTL 兜底）；二是抢锁重试 20 次仍失败会直查库**且不回写缓存**，那种情况下热键并发会全部压到数据库——**而抢锁重试是 `sleep(50)` 阻塞 Tomcat 线程的，最坏占 1 秒**。」

### F. 如果问「数据库」→ 讲 CAS 和事务边界

> 「**项目里有 16 处条件更新（CAS），每一处都在防一个具体的竞态。**
>
> 核心手法是**把判定条件写进 UPDATE 的 WHERE 里**。比如扣名额：`UPDATE ... SET remaining_quota = remaining_quota - 1 WHERE id = ? AND remaining_quota > 0`。
>
> **为什么不能用 `updateById`**：那是读-改-写三步，两个线程可以都读到 `remaining=1`、都判断大于 0、都写 0——**两个都成功但只扣了 1，超卖**。而 `SET x = x - 1` 让读和写在一句话里，`WHERE x > 0` 让判定也在同一把行锁里——**判定和使用被合并成了一个原子操作**。**返回值 `affectedRows` 就是判定结果，不需要再查一次。**
>
> **权限判定也用同样的手法**：取消和核验的 UPDATE 里都带 `WHERE user_id = ?`。这样越权请求的 `affectedRows` 天然是 0，**不存在『判断通过但执行的是别人的数据』的窗口**。
>
> **★ 而 `@Transactional` 全项目只有 3 处**，这 3 处都满足两个条件：**至少两步数据库写，而且不包含任何网络调用**。
>
> **`submit` 绝对不能加事务**，因为它里面有 Redis 操作和**最长 5 秒的同步等 MQ 确认**。加了之后：一是事务跨越网络等待，**Hikari 默认 10 个连接，10 个并发就能打满**；二是**事务能回滚的只有那一条账本 INSERT，Redis 的扣减不在事务里**——所以回滚反而制造了『Redis 已扣、账本没了』的名额泄漏，**正好是它本来要防的问题**。
>
> **对账和 DLQ 重放也不能加事务**，因为它们是循环处理一批记录、**需要每条独立成败**，而不是全部回滚。」

## 附：三个「不要」

1. **不要说「海量流量」「亿级并发」「高可用架构」。** 这个项目**没有做过压测、没有部署过多实例、没有高可用方案**。**说了会被追问，追问就露馅。**
2. **不要只说「用了 Redis」「用了 RabbitMQ」。** 面试官想听的是**为什么用、不用会怎样、代价是什么**。**技术名词本身不加分，取舍才加分。**
3. **不要回避边界。** 「这个我没测过」「这个当前实现没有兜底」——**这两句话在面试里是加分项**，前提是**后面能跟上『兜底在哪』或者『应该怎么改』**。
