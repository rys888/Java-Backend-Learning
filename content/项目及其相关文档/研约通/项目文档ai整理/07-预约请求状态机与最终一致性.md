# 三、第 1 步：`submit` 建账本 —— 落成 `PRE_ACCEPTED`

`ReservationServiceImpl.java:108-115`

```java

    reservationRequestService.createPreAccepted(reservationId, user.getId(), batchId);   // :110

    throw new ServiceUnavailableException("预约失败，请重试");                  // :114

```

**逐句**：

- `:108` 生成 id（`RedisIdWorker` 是「秒级时间戳 + 按天自增计数」，见 05 篇 §7，**不是雪花算法**）。
- `:110` 插账本，**在抢名额之前**——先记账，再去 Redis 抢。
- `:111-114` 插入抛异常（比如主键已存在）→ 打 error 日志 + 抛 `ServiceUnavailableException` → `WebExceptionAdvice` 映成 **503**。

`ReservationRequestServiceImpl.java:23-31`：

```java
ReservationRequest request = new ReservationRequest()
        .setRequestId(requestId).setUserId(userId).setBatchId(batchId)   // :25-28
        .setStatus(ReservationRequestStatus.PRE_ACCEPTED);               // :29
reservationRequestMapper.insert(request);                                // :30
```

**逐句**：

- `:25-28` 链式 set 建实体（`@Accessors(chain = true)`）。`createTime` / `updateTime` **不设**——交给 MySQL 的 `DEFAULT CURRENT_TIMESTAMP`。
- `:29` 状态写死 `PRE_ACCEPTED`，**这是这一行唯一一次「出生状态」**。
- `:30` 一条 `INSERT`。接口注释（`IReservationRequestService:11`）写明：「`requestId` 已存在时抛异常」——不做「已存在就跳过」，重复主键直接抛，由 `:111` 的 catch 转成 503。

**为什么先写 `PRE_ACCEPTED` 而不是等抢到名额再写**：写完这一行，`reservationId` 就成了一条**可查的账**。后面不管是抢名额被拒、投递失败、消费者落库炸了，都有固定的一行可以改/可以扫——否则失败发生在哪一步都无处留痕。

**`reservationId` 怎么来的**：05 篇 §7 已展开——`(1791363600 − 1640995200) << 32 | 1024` = `645827360351847424`。`:108` 的 `"reservation"` 是 key 前缀，只影响计数 key 的名字，不影响返回值。

**例子里的对应值** —— 这条 INSERT 插进去的行（`INSERT INTO tb_reservation_request (request_id, user_id, batch_id, status) VALUES (645827360351847424, 102, 7, 'PRE_ACCEPTED')`）：

| `request_id` | `user_id` | `batch_id` | `status` | `fail_reason` | `create_time` | `update_time` |
|---|---|---|---|---|---|---|
| `645827360351847424` | 102 | 7 | **`PRE_ACCEPTED`** | `NULL` | 2026-10-07 09:00:00 | 2026-10-07 09:00:00 |

**紧接着的 ⑩ 步不影响这一行**：`ReservationServiceImpl:116` 的 `tryAcquire` 只动 Redis，学生 102 拿到 `SUCCESS`（05 篇 §3.6：`quota:7` 从 `"5"` 变 `"3"`、`users:7` 加进 102）。账本此刻**还是 `PRE_ACCEPTED`**。

# 四、第 2 步：投递 ACK —— 落成 `PUBLISHED`

`ReservationServiceImpl:136` 调 `publishReservationMessage(reservationId, user.getId(), batchId, now)`。这个方法的完整逐行在 06 篇；这里只讲**它怎么改账本**。

## 4.1 先判定投递结果（`ReservationServiceImpl:248-280`）

这一段只求一个三值结论 `PublishOutcome`。**发送与等待的逐行细节见 06 篇 §3**，这里只看它怎么定档（判据全在下面这些行）：

| 行 | 判据 | `outcome` | `failureReason`（逐字） |
|---|---|---|---|
| `:251-255` | `convertAndSend` 发出，`correlationData` 带 `reservationId`（`:246`） | — | — |
| `:256` | `getFuture().get(5, TimeUnit.SECONDS)`——**最多等 5 秒**；等不到抛 `TimeoutException`，落到 `:276` | — | — |
| `:257-259` | `!confirm.isAck()`：broker 明确没收下 | `DEFINITELY_NOT_DELIVERED` | `CONFIRM_NACK` |
| `:260-262` | 收下了但 `getReturnedMessage() != null`（交换机退回） | `DEFINITELY_NOT_DELIVERED` | `CONFIRM_RETURN` |
| `:264` | 两条都没命中 | **`ACKED`** | — |
| `:266-270` | `AmqpConnectException`：**连不上 broker** | `DEFINITELY_NOT_DELIVERED` | `AMQP_CONNECT_FAILED` |
| `:271-275` | `InterruptedException`：线程被打断 | `UNKNOWN` | — |
| `:276-280` | 其余异常（含 5 秒等待超时） | `UNKNOWN` | — |

**`ACKED` 是唯一能走到 `PUBLISHED` 的一档**，其余两支的处置在 §6.1 / §6.2。注意 `:266-270` 的「连不上」**不进 `UNKNOWN`**——连都连不上，是确定的没发出去。另外先记住 `:307-310`：确定失败那支里，回滚 Redis 抛异常时**里面的 CAS 根本不会执行**，账本留在 `PRE_ACCEPTED`（日志原文「账本保留非终态」）——这是 §9 那条不变式的由来。

## 4.2 `markPublishedWithRetry` 逐行（`ReservationServiceImpl:331-360`）

```java
for (int attempt = 1; attempt <= 2; attempt++) {                  // :332  ← 重试 2 次
    try {
        if (reservationRequestService.casStatus(
                reservationId,
                ReservationRequestStatus.PUBLISHED,                   // :336
                ReservationRequestStatus.PRE_ACCEPTED)) {             // :337  ← 期望集合只有一个
            return;
        }
        log.warn("预约消息 ACK 后账本置为 PUBLISHED 失败", ...);      // 影响 0 行只打日志，不中断
    } catch (RuntimeException e) { log.error("...置为 PUBLISHED 异常", ...); }
}
// 重试耗尽：若账本已被消费者/对账推进为终态，这是正常的先后竞争，不是故障
try {
    ReservationRequest current = reservationRequestService.getByRequestId(reservationId);  // :349
    if (current != null && current.getStatus().isTerminal()) {                             // :350
        return;                                     // 打一行 info 后正常返回
    }
} catch (RuntimeException e) { return; }            // 只打 error
log.error("预约消息 ACK 后账本更新重试耗尽：reservationId={}", reservationId);   // :359
```

**逐句**：

- `:332` **重试 2 次**。失败（影响 0 行）或抛异常都算一次尝试，只打日志不中断。
- `:334-337` CAS 把账本从 `PRE_ACCEPTED` 推进到 `PUBLISHED`（`ACKED` 分支在 `:282-285` 调这个方法）。**期望集合只有一个 `PRE_ACCEPTED`**，比别处窄——这条路的语义是「消息刚发出去，账本本该还是 `PRE_ACCEPTED`」；它已经不是了，说明有别的角色先动了它。
- `:349-354` 重试耗尽后**读一次账本**，如果已经是终态（`CONFIRMED` / `COMPENSATED`）→ 打一行 `info` 正常返回。**这是全项目 `isTerminal()` 唯一的一处生产调用**（§8.1）。
- `:359` 不是终态（比如停在 `UNKNOWN`）→ 打 error。**这条记录交给对账**（08 篇）。

**例子里的对应值**：`:251-256` 发到 `reservation.exchange` / `reservation.create`，broker 回 `ack = true`、无 returned message；`:334-337` 执行 `UPDATE tb_reservation_request SET status='PUBLISHED' WHERE request_id=645827360351847424 AND status IN ('PRE_ACCEPTED')`，**影响 1 行**，该行变成 `status = PUBLISHED`、`fail_reason = NULL`。接口此刻已返回 `200` + `645827360351847424`（`ReservationServiceImpl:137`），而 `tb_reservation` 里**还没有行**。

# 五、第 3 步：消费者落库 —— 落成 `CONFIRMED`

队列 `reservation.create.queue`（`RabbitMQConfig:28`），消费者 `mq/ReservationMessageConsumer.java`。

## 5.1 入口：读账本，拦掉已补偿的（`:39-57`）

```java
long deliveryTag = message.getMessageProperties().getDeliveryTag();          // :44
try {
    ReservationRequest request = reservationRequestService.getByRequestId(   // :46
            messageDTO.getReservationId());
    if (request == null) {                                                   // :48
        log.warn("预约请求账本不存在，继续落库：...", ...);                    // 不拦，继续落库
    } else if (request.getStatus() == ReservationRequestStatus.COMPENSATED) {   // :51
        // 该请求已被对账判定终结并归还名额；若此时仍落库，就会形成「MySQL 有行 + Redis 名额已归还」的超发。
        log.warn("预约请求已被补偿，拒绝落库并确认消息：...", ...);
        channel.basicAck(deliveryTag, false);                                // :55
        return;
    }
```

**逐句**：

- `:44` 取 `deliveryTag`，后面 ACK/NACK 都用它。
- `:46-47` **先查一次账本**（`SELECT ... WHERE request_id = ?`，走主键）。`:48-50` 查不到（比如 INSERT 失败但消息还是发出去了）→ 打 warn **不拦**。
- `:51-57` **账本已经是 `COMPENSATED` → 拒绝落库，`basicAck` 直接确认消息走人**。理由写在注释里：对账已经把名额还回 Redis 了，这时候再落库就是「MySQL 有行 + Redis 名额已归还」的超发。

`:51` 是一次**普通读 + Java 判断**，不是 CAS；读完到落库之间没有任何锁保护账本状态。也就是说这一层是「尽量拦」，真正的兜底靠对账（08 篇）。

**例子里的对应值**：`getByRequestId(645827360351847424)` 返回一行，`status = 'PUBLISHED'`，**不是 `COMPENSATED`**，所以继续往下走。

- `:136-141` 组装 `tb_reservation` 的实体。`:137` **`setId` 用的是 `reservationId`**——账本主键和预约事实主键是**同一个值**。`:140` 状态固定 `RESERVED`。

## 5.3 `persist` 逐行（`ReservationPersistenceServiceImpl:26-62`）

```java
@Override
@Transactional                                                        // :27
public ReservationPersistResult persist(Reservation reservation) {
    Reservation existing = reservationMapper.selectById(reservation.getId());     // :29
    if (existing != null
            && existing.getUserId().equals(reservation.getUserId())
            && existing.getBatchId().equals(reservation.getBatchId())) {          // :30-32
        // 只有「同 id 且同 user 且同 batch」才算同一次预约的重复投递（含 DLQ 重放），
        // 幂等确认、不重复扣名额。同 id 但归属不同是异常的主键冲突，必须继续走到
        // insert 由主键约束抛出，交给消费端既有的 catch(DuplicateKeyException) 进死信队列；
        // 若在此提前返回 DUPLICATE，那条未落库的消息会被静默 ACK，DLQ 上不留任何痕迹。
        return ReservationPersistResult.DUPLICATE;                                // :37
    }
    Integer existingCount = reservationMapper.selectCount(
            new LambdaQueryWrapper<Reservation>()
                    .eq(Reservation::getUserId, reservation.getUserId())
                    .eq(Reservation::getBatchId, reservation.getBatchId())
                    .in(Reservation::getStatus, ReservationStatus.occupyingStatuses()));   // :43
    if (existingCount > 0) {
        return ReservationPersistResult.DUPLICATE;                                // :45
    }

    // 必须先扣减名额；影响 0 行时直接返回，库中不会留下未扣名额的预约。
    boolean quotaDecremented = reservationBatchService.update(
            new LambdaUpdateWrapper<ReservationBatch>()
                    .eq(ReservationBatch::getId, reservation.getBatchId())
                    .gt(ReservationBatch::getRemainingQuota, 0)                   // :52
                    .setSql("remaining_quota = remaining_quota - 1"));            // :53
    if (!quotaDecremented) {
        return ReservationPersistResult.QUOTA_CONFLICT;                           // :55
    }

    if (reservationMapper.insert(reservation) != 1) {                             // :58
        throw new IllegalStateException("预约记录持久化失败");
    }
    return ReservationPersistResult.PERSISTED;                                    // :61

```

**逐句**：

- `:27` `@Transactional` 包住整个方法，扣名额和插入在同一事务里。
- `:29` 按主键查一次。`:30-38` **「同 id 且同 user 且同 batch」** 才算重复投递 → `DUPLICATE`。三个条件缺一不可：同 id 但归属不同说明是别的问题，**不能在这里提前返回**，得让它走到 `:58` 的 `insert` 由主键约束抛 `DuplicateKeyException`，好让上层 `:80-85` 把它 NACK 进 DLQ（否则那条消息会被静默 ACK、DLQ 上没痕迹）。
- `:39-46` 换个维度再查一次：**这一对 `(user_id, batch_id)` 是不是还有占着槽位的行**——`occupyingStatuses()` = `[RESERVED, COMPLETED, NO_SHOW]`（§8.3），和 `active_flag` 生成列严格一致。命中就 `DUPLICATE`。
- `:49-53` **先扣 MySQL 名额**：`UPDATE tb_reservation_batch SET remaining_quota = remaining_quota - 1 WHERE id = ? AND remaining_quota > 0`。影响 0 行（名额已到 0）→ `:55` 返回 `QUOTA_CONFLICT`，**事务里什么都没留下**。
- `:58-60` 才插 `tb_reservation`；`:61` 返回 `PERSISTED`。

**「先扣名额再插入」这个顺序的用处**：扣减失败就直接 return，**库里不会留下一行「没扣名额的预约」**。反过来（先插再扣）则要么留下脏行，要么靠回滚。

**例子里的对应值**：

| 步 | SQL | 影响行数 |
|---|---|---|
| `:29` | `SELECT * FROM tb_reservation WHERE id = 645827360351847424` | 0 行 → `existing = null` |
| `:39-43` | `SELECT COUNT(*) ... WHERE user_id=102 AND batch_id=7 AND status IN ('RESERVED','COMPLETED','NO_SHOW')` | `0` |
| `:49-53` | `UPDATE tb_reservation_batch SET remaining_quota = remaining_quota - 1 WHERE id=7 AND remaining_quota > 0` | **1**（数字减 1） |
| `:58` | `INSERT INTO tb_reservation (id, user_id, batch_id, status, create_time) VALUES (645827360351847424, 102, 7, 'RESERVED', '2026-10-07 09:00:00')` | **1** |
| 返回 | `PERSISTED` | |

> **MySQL 的 `remaining_quota` 和 Redis 的 `quota:7` 是两本账。** 到 102 这条落库时，MySQL 侧被 `:53` 减掉 1。具体从几减到几，取决于 101 那条消息有没有先被消费（`remaining_quota` 是共享行，两条消息谁先落库不保证）——但**不管当时是几，`:52` 的 `> 0` 保证了不会减成负数**。

# 六、第 4 步：失败路径

失败分成**两组**，区别是「改不改 `status`」。

- `:41-43` **`expectedStatuses` 为空直接抛 `IllegalArgumentException`**（接口注释 `IReservationRequestService:19`：「避免退化成无条件覆盖」）——**不存在「无条件改状态」的调用方式**，每个调用点都得写明「从哪些状态可以过来」。

## 7.3 `recordFailReason`（`:64-72`，**不改 `status`**）

```java
@Override
public boolean recordFailReason(long requestId, String failReason) {
    // 首次写入失败原因会触发 MySQL 的 ON UPDATE，但重复写入同一原因是 no-op，
    // 不会自动推进 update_time；这里必须显式赋值，避免持续失败行重新钉在扫描窗口队首。
    return reservationRequestMapper.update(null, new LambdaUpdateWrapper<ReservationRequest>()
            .eq(ReservationRequest::getRequestId, requestId)
            .set(ReservationRequest::getFailReason, failReason)
            .set(ReservationRequest::getUpdateTime, LocalDateTime.now())) == 1;
}
```

```sql
UPDATE tb_reservation_request
   SET fail_reason = ?, update_time = ?
 WHERE request_id = ?
```

**这是三个原语里唯一一个没有 `status IN (...)` 的**——它压根不碰 `status`，所以不需要 CAS。

**为什么要显式 `.set(update_time)`**：`update_time` 带 `ON UPDATE CURRENT_TIMESTAMP`，但 MySQL **只在至少一列的值真的变化时才更新它**。同一条消息被重放、失败原因还是 `QUOTA_CONFLICT`，值没变，`ON UPDATE` 不触发，`update_time` 就停在原地，这行会一直钉在 `listStale` 的队首（`orderByAsc(updateTime)`）反复被扫、挤掉后面真正该扫的行。显式赋 `LocalDateTime.now()` 保证每次调用都往后推。

**两种失败**（`requestId` 不存在 → 影响 0 行 → 返回 `false`；SQL 抛异常 → 由调用方 `recordFailReasonSafely` 接住）都只打日志。

## 8.1 `isTerminal()`（`enums/ReservationRequestStatus.java:17-19`）

**覆盖两个状态：`CONFIRMED` 和 `COMPENSATED`。** 其余三个（`PRE_ACCEPTED` / `PUBLISHED` / `UNKNOWN`）都返回 false。

**生产代码里只被调一次**：`ReservationServiceImpl:350`，在 `markPublishedWithRetry` 重试耗尽后用来判断「账本是不是已经被别的角色推到终态了」（§4.2）。

`isTerminal()` 和 `nonTerminalStatuses()` **是两个独立维护的集合**——前者是 `if` 判断，后者是列表常量，两者没有共用代码。测试里各有一条断言防止它们收窄后漏项（`ReservationRequestStateTest:135`、`ReservationReconcileTest:198`）。

## 8.2 `nonTerminalStatuses()` —— 声明与三处调用点

**声明**（`enums/ReservationRequestStatus.java:14-15, :21-23`）：

```java
private static final List<ReservationRequestStatus> NON_TERMINAL_STATUSES =              // :14-15
        Collections.unmodifiableList(Arrays.asList(PRE_ACCEPTED, PUBLISHED, UNKNOWN));
public static List<ReservationRequestStatus> nonTerminalStatuses() { return NON_TERMINAL_STATUSES; }  // :21-23
```

**三个非终态：`PRE_ACCEPTED` / `PUBLISHED` / `UNKNOWN`**。它是 `static final` 常量，用 `Collections.unmodifiableList` 包了一层（拿到的列表不能改），**不是每次调用重新算的**。全项目（`src/main/java`）一共三处调用：

| # | 位置 | 那一行长什么样 | 用途 |
|---|---|---|---|
| 1 | `mq/ReservationMessageConsumer.java:104` | `ReservationRequestStatus.nonTerminalStatuses().toArray(...)` | `markConfirmedSafely` 里当 **CAS 期望集合**，把落库成功的那条账本推进到 `CONFIRMED` |
| 2 | `service/impl/ReservationRequestServiceImpl.java:82` | `.in(ReservationRequest::getStatus, ReservationRequestStatus.nonTerminalStatuses())` | `listStale` 的**扫描筛选条件**——只捞非终态 |
| 3 | `service/impl/ReservationReconcileServiceImpl.java:33-34` | `private static final ReservationRequestStatus[] NON_TERMINAL_STATUSES = ... .toArray(...)` | 类加载时**固化成数组**，在 `:115`（→ `CONFIRMED`）和 `:130`（→ `COMPENSATED`）两处当 CAS 期望集合 |

**三处都要求「集合只多不少」**：

- #1 少一个 → 该状态的账本永远推不到 `CONFIRMED`，明明落库了却停在非终态。
- #2 少一个 → 对账永远扫不到这个状态的行，**长期挂着没人管**。
- #3 少一个 → 对账看得见（#2 的 `listStale` 捞出来了）但 CAS 期望集合里没有它，`updated == false` → 计入 `skipped`，**每轮空转**。而且 #3 是 `static final`：类加载时取一次，**改了枚举但没重启进程，这一份数组不会更新**。

## 8.3 和 `ReservationStatus` / `active_flag` 的关系

先说结论：**这两套集合之间没有任何代码或 DDL 层面的绑定**，是两张表各自独立的判定。

| | `ReservationRequestStatus`（账本） | `ReservationStatus`（事实） |
|---|---|---|
| 表 | `tb_reservation_request` | `tb_reservation` |
| 值 | `PRE_ACCEPTED` / `PUBLISHED` / `CONFIRMED` / `UNKNOWN` / `COMPENSATED` | `RESERVED` / `CANCELLED` / `COMPLETED` / `NO_SHOW` |
| 终态集合 | `{CONFIRMED, COMPENSATED}`（`isTerminal()`） | `{CANCELLED, COMPLETED, NO_SHOW}`（`isTerminal()` = `!= RESERVED`） |
| 非终态集合 | `nonTerminalStatuses()` = `[PRE_ACCEPTED, PUBLISHED, UNKNOWN]` | 没有这个方法 |
| 另一个集合 | 无 | `occupyingStatuses()` = `[RESERVED, COMPLETED, NO_SHOW]` |
| 谁用它做筛选 | `listStale`（`ReservationRequestServiceImpl:82`） | `persist` 查重复（`ReservationPersistenceServiceImpl:43`） |

**唯一有 DDL 级对应关系的是 `occupyingStatuses()` 和 `active_flag`**：`ReservationStatus:14-17` 的注释逐字写着「判据必须与 `tb_reservation.active_flag` 生成列严格一致：`CASE WHEN status = 'CANCELLED' THEN NULL ELSE 1 END`。因此除 `CANCELLED` 之外的状态都算占用 —— `COMPLETED` / `NO_SHOW` 的行仍占着槽位」。

**账本侧的 `nonTerminalStatuses()` 和 `active_flag` 没有任何关系**——`active_flag` 只看 `tb_reservation.status`，而 `tb_reservation` 的 `status` 里根本没有 `PRE_ACCEPTED` 这些值。两套枚举的**语义对应是间接的、靠对账维持的**：账本 `CONFIRMED` 大致意味着 `tb_reservation` 里有那一行，`COMPENSATED` 大致意味着没有。但这是对账**判定出来的结果**（08 篇），不是 schema 强制的约束。

# 九、一条全局不变式：先做补偿，再宣告终结

**「先把该还的还回去、该做的做完，再把账本 CAS 成终态。」** 顺序反了就会丢补偿——一旦账本是终态，对账再也不会扫到它，那个没做完的动作就永远没人重试了。

源码里逐处核实：

## 9.1 位置一：投递确定失败 —— `ReservationServiceImpl.java`

```

289	            int rollbackCode = reservationQuotaRollbackExecutor.rollback(batchId, userId);
290	            log.warn("预约消息确定未投递，名额回滚完成：reservationId={}，rollbackCode={}",
291	                    reservationId, rollbackCode);
292	            try {
```

**第 289 行回收名额，第 293 行才把账本置 `COMPENSATED`**——中间只隔了一个 `log.warn`。

而且这个顺序是**双向**的：`:307-310` 的 `catch (RuntimeException rollbackException)` 把 CAS 整个包在外面，**回滚抛异常时 `:293` 的 CAS 根本不会执行**，日志写的就是「账本保留非终态」。

## 9.2 位置二：对账判定没落库 —— `ReservationReconcileServiceImpl.java`


同一形状还出现在 `releasePendingQuotas`：`:159` 先 `rollback`，`:160-164` 再把 `tb_reservation.quota_released` CAS 成 `true`。这是取消场景的重试路径，`status` 不涉及。

## 9.3 位置三：取消路径 —— 这是**反方向**的一条，别混

位置一、二说的是「先补偿、后终结」；**取消这条路的要求正好相反：只有 CAS 跃迁真的成功了，才允许补偿。**

`ReservationServiceImpl.cancel`（`:140-176`）：

```

157	            // 重新打开名额泄漏（……并静默 ACK）。
158	            // 只有本事务真正完成跃迁（TRANSITIONED）才允许归还名额。   ← 判据
```

**顺序**：

## 9.4 消费者侧对这条不变式的「读」

`ReservationMessageConsumer:51-57`（§5.1）：落库**之前**读一次账本，如果是 `COMPENSATED`（对账已经把名额还回去了）就拒绝落库、`basicAck` 走人。它和 §9.1/9.2 是配套的两半：那两处保证「还了名额就一定置 `COMPENSATED`」，这里保证「看到 `COMPENSATED` 就一定不再落库」。**这一读不在任何锁里**（`:129` 那把锁按 userId 加，对账不拿它），所以是「尽量拦」，兜底还是对账。

# 十一、记在案的问题

- **`UNKNOWN` 是怎么产生的**：只有两条路，都在 `ReservationServiceImpl:271-280` —— 等 confirm 时线程被 `InterruptedException` 打断，或者 `getFuture().get(5, TimeUnit.SECONDS)` 抛了别的异常（**包括 5 秒等待超时抛出的 `TimeoutException`**），确实不知道消息进没进队列。`AmqpConnectException` 那一路是确定的没发出去（`AMQP_CONNECT_FAILED`），**不是 `UNKNOWN`**。
- **谁来兜底**：`ReservationReconcileServiceImpl` 的定时任务（`@EnableScheduling` 在 `config/SchedulingConfig:7`）。`listStale` 的非终态集合含 `UNKNOWN`，判据是「`tb_reservation` 里有没有这一行」——有就 `CONFIRMED`，没有就 rollback + `COMPENSATED`。所以它最终会被推进，但**是三个非终态里唯一一个「有明确产生时刻、没有明确结束时刻」的**。
- **有没有可能长期挂着**：有。定时任务 `fixedDelay`/`initialDelay` 默认 `300000ms`、扫描阈值 `reconcile-threshold-ms` 默认 `600000ms`、每轮 `limit` 默认 200 条（`application.yaml:51-53`），正常节奏下约 10 分钟到终态；但**进程没在跑对账**（`@Scheduled` 的 Bean 没加载、调度线程被占满）或每轮都计入 `failed`，这行就一直是 `UNKNOWN`。`ReservationReconcileServiceImpl:180` 的 `recordReconcileFailureSafely` 会把 `update_time` 推到现在，失败行**不会**因老化被永久跳过，但同时也被推到队尾——**每轮都要重新等满 10 分钟**，没有退避也没有告警升级。
- **两套枚举没有 schema 级的对应**：`nonTerminalStatuses()` 与 `tb_reservation.active_flag` 生成列之间没有任何约束或代码引用；`isTerminal()` 与 `nonTerminalStatuses()` 也是两个独立维护的集合（一个 `if`、一个列表常量），靠测试断言（`ReservationRequestStateTest:135`、`ReservationReconcileTest:198`）防止收窄后漏项。
