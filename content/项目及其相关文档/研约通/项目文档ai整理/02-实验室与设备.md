# 一、先看结果：五步走完，各存储变成什么

| # | 谁 | 请求 | 中途经过 | 之后 |
|---|---|---|---|---|
| 1 | 李老师(2) | `POST /equipment` | 拦截器放行 → `saveEquipment` → `assertManageable(2)` 通过 → `save` | `tb_equipment` 多出 **id=13** 一行；Redis 无变化；返回 `{"success":true,"data":13}` |
| 2 | 学生 101 | `GET /laboratory/2` | 无权限注解，只过登录拦截器 | `200` + 实验室 2 的 VO（**没有 `adminUserId`**） |
| 3 | 学生 101 | `GET /equipment/page?current=1&laboratoryId=2` | XML join 三张表 | `200` + `data` 共 4 台，**第一台就是 id 13**，`total = 4` |
| 4 | 学生 101 | `POST /equipment` | `RoleInterceptor`：101 的 role 是 `USER`，不在 `{LAB_ADMIN}` 里 | `403`，**响应体为空**（一个字节都没有） |
| 5 | 王老师(3) | `PUT /equipment` 改设备 3 | `RoleInterceptor` 放行 → `assertEquipmentManageable` → 查设备 3 的 `laboratory_id=2` → 查实验室 2 的 `admin_user_id=2` → `2 != 3` | `403` + `{"success":false,"errorMsg":"无权管理该实验室"}` |

**第 1 步之后设备详情的缓存条数没有变化**（还是 0 条），这是后面 §6.3 要讲的。

# 二、进 Controller 之前：靠外的那道门

本篇每个接口都要先过这条链：`RefreshTokenInterceptor`(order 0) → `LoginInterceptor`(order 1) → `RoleInterceptor`(order 2)。**三个拦截器的注册顺序、`RoleInterceptor` 逐行、`UserHolder` 与 ThreadLocal 的生命周期都在 01 篇「三、每个请求进来：三个拦截器」，这里不重复**；下面只记 02 篇自己的信息。

## 2.1 本篇哪些接口带 `@RequireRole`

| 接口 | `@RequireRole` |
|---|---|
| `GET /laboratory/{id}`、`GET /laboratory/list`、`GET /equipment/{id}`、`GET /equipment/page`、`GET /equipment-category/list` | 无 |
| `POST /laboratory`、`PUT /laboratory`、`DELETE /laboratory/{id}` | `LAB_ADMIN` |
| `POST /equipment`、`PUT /equipment`、`PUT /equipment/{id}/status`、`DELETE /equipment/{id}` | `LAB_ADMIN` |

**读接口一律不带注解，写接口一律 `LAB_ADMIN`**。本系统只有 `USER` / `LAB_ADMIN` 两个角色（`enums/UserRole.java:3-6`），所以「带注解」和「只有管理员能调」在本篇是一回事。不带注解的接口仍然要登录——`LoginInterceptor` 覆盖除 `/user/code`、`/user/login` 外的所有路径。

## 2.2 例子里的对应（第 4 步）

学生 101 的 role 是 `USER`，在 `RoleInterceptor` 的循环里匹配不上 `@RequireRole(LAB_ADMIN)`，走到末两行 `response.setStatus(403); return false;`（`RoleInterceptor.java:41-42`）。

**只设状态码，不写响应体、也不抛异常** → HTTP `403`，**响应体为空**，`EquipmentController.saveEquipment`（`:46-50`）一行都没执行，MySQL 和 Redis 都没被碰。

**同样是 403，数据级校验给出的是另一种**：王老师那次的 `ForbiddenException` 走 `WebExceptionAdvice`，带 `Result` JSON。两个 403 并排在 §5.4。

# 三、管理端新增设备：跟着李老师走一遍

## 3.1 Controller 只做两件事

`controller/EquipmentController.java:46-50`

```java
@PostMapping
@RequireRole(UserRole.LAB_ADMIN)
public Result saveEquipment(@RequestBody Equipment equipment) {
    return Result.ok(equipmentService.saveEquipment(equipment));
}
```

- `@PostMapping` 不带路径，配上类上的 `@RequestMapping("/equipment")`，完整路径是 `POST /equipment`。
- **`@RequestBody Equipment` 直接把 JSON 反序列化成实体**——没有单独的 DTO，也没有字段白名单。前端多传的字段如果实体里有同名属性，一样会被接收。
- 返回值是 `Result.ok(新id)`。

**李老师发的请求体**（字段就是 `frontend/src/views/admin/equipment/AdminEquipmentListView.vue:174-188` 那个表单）：

```json
{
  "laboratoryId": 2,
  "categoryId": 2,
  "name": "电感耦合等离子体质谱仪",
  "location": "B205-4",
  "description": "用于痕量元素定性定量分析。",
  "image": "",
  "usageRequirement": "需提前提交样品消解方案。",
  "status": "AVAILABLE",
  "bookingEnabled": true
}
```

两点：

- **没有 `id` 字段**。新增走的是自增主键，前端表单里根本没有 id 这一项。
- `laboratoryId` / `categoryId` 上面写的是数字；前端表单实际发出去的是**字符串**（下拉项的值是 `String(item.id)`），Jackson 反序列化到 `Long` 字段时会自动转——两种写法都能落库。

## 3.2 Service：先校验归属，再落库

`service/impl/EquipmentServiceImpl.java:64-69`

```java
@Override
public Long saveEquipment(Equipment equipment) {
    laboratoryService.assertManageable(equipment.getLaboratoryId());
    save(equipment);
    return equipment.getId();
}
```

三行：

1. **`assertManageable(equipment.getLaboratoryId())`**——设备自己没有管理员字段，**它的归属完全由所属实验室决定**。传 2，就是问「实验室 2 归不归我管」。
2. `save(equipment)`——MyBatis-Plus `ServiceImpl` 的默认 `INSERT`。
3. `return equipment.getId()`——`insert` 之后自增主键被回填进实体，所以这里拿到的是数据库生成的新 id。

**例子里的对应**：`assertManageable(2L)` 通过（下一节），`save` 插一行，返回 **13L**。

## 3.3 `assertManageable` 到底怎么判断

`service/impl/LaboratoryServiceImpl.java:24-34`

```java
@Override
public void assertManageable(Long laboratoryId) {
    UserDTO user = UserHolder.getUser();
    if (user == null) {
        throw new ForbiddenException("无权管理该实验室");        // ①
    }
    Laboratory laboratory = getById(laboratoryId);              // ② 查 tb_laboratory
    if (laboratory == null || !user.getId().equals(laboratory.getAdminUserId())) {
        throw new ForbiddenException("无权管理该实验室");        // ③
    }
}
```

- **① 用户为空 → 403**。同一个方法被多处调用，这一句是兜底。
- **② 一次查库**：按 `laboratoryId` 查 `tb_laboratory`。
- **③ 两个条件合在一个 `if` 里**：
  - `laboratory == null`：实验室不存在，也抛 403（**不是 404**——不区分「不存在」和「不归你管」，避免泄露存在性）。
  - `!user.getId().equals(laboratory.getAdminUserId())`：拿当前登录用户的 id 和这一行的 `admin_user_id` 比。**注意是 `user.getId().equals(...)`，用 userId 去调 equals，就算 `adminUserId` 是 null 也只会返回 false，不会 NPE**（`Laboratory.java:37-38` 的注释：`null` 表示未分配，未分配时任何人都不能管理）。
  - 用的是 `adminUserId` 字段，**完全没有读 `status`**。实验室是不是 `CLOSED` / `MAINTENANCE`，这个方法不关心。

**例子里的对应（第 1 步）**：

| 步 | 实际值 |
|---|---|
| ① | `UserHolder` 里是李老师（uid 2，`LAB_ADMIN`） |
| ② | `SELECT ... FROM tb_laboratory WHERE id = 2` → 分析测试实验室，`admin_user_id = 2` |
| ③ | `2.equals(2)` → true，取反 false；`laboratory` 也不为 null → **不抛异常** |

## 3.4 `save` 生成的 SQL 和 DB 里那一行

`save(equipment)` 是 MyBatis-Plus 的默认实现，等价于按实体的非 null 字段拼一条 `INSERT`：

```sql
INSERT INTO tb_equipment
  (laboratory_id, category_id, name, description, location, image, usage_requirement, status, booking_enabled)
VALUES
  (2, 2, '电感耦合等离子体质谱仪', '用于痕量元素定性定量分析。', 'B205-4', '', '需提前提交样品消解方案。', 'AVAILABLE', 1)
```

- **列清单里没有 `id`**：`@TableId(type = IdType.AUTO)`，主键交给 MySQL 自增。
- **列清单里没有 `create_time` / `update_time`**：实体里这两个字段是 null，MyBatis-Plus 默认的插入策略是「忽略 null 字段」，所以它们不出现在 SQL 里，由建表语句的 `DEFAULT CURRENT_TIMESTAMP` 填上（`db/phase2_laboratory_equipment.sql:38-39`）。
- **`status` 存的是枚举名字符串**：`application.yaml:42-43` 配了 `default-enum-type-handler: org.apache.ibatis.type.EnumTypeHandler`，`EquipmentStatus.AVAILABLE` 落库就是 `'AVAILABLE'`。
- **`image` 存的是空串不是 NULL**：前端表单会发 `"image": ""`，空串不是 null，所以照样进列清单。（如果请求里干脆不带这个字段，这一列才是 NULL。）
- **`booking_enabled` 是 `tinyint(1)`**，`true` → `1`。

**插完之后 `tb_equipment` 的这一行**：

| id | laboratory_id | category_id | name | description | location | image | usage_requirement | status | booking_enabled | create_time | update_time |
|---|---|---|---|---|---|---|---|---|---|---|---|
| **13** | 2 | 2 | 电感耦合等离子体质谱仪 | 用于痕量元素定性定量分析。 | B205-4 | `''` | 需提前提交样品消解方案。 | `AVAILABLE` | **1** | 插入那一刻 | 插入那一刻 |

**Redis 一个字节都没动。** 没有 `lab:equipment:13`，因为写路径里不存在任何缓存写入。

## 3.5 返回的 `Result` 长什么样

`dto/Result.java:18-29`

```java
public static Result ok()                   { return new Result(true, null, null, null); }
public static Result ok(Object data)        { return new Result(true, null, data, null); }
public static Result ok(List<?> data, Long total) { return new Result(true, null, data, total); }
public static Result fail(String errorMsg)  { return new Result(false, errorMsg, null, null); }
```

四个字段 `success / errorMsg / data / total`，`@AllArgsConstructor` 按这个顺序塞进去。三个重载的区别只在于 `data` 和 `total` 传不传。

**但序列化出来的 JSON 只有非 null 字段**——`application.yaml:23-24`：

```yaml
jackson:
  default-property-inclusion: non_null # JSON处理时忽略非空字段
```

所以：

| 构造方式 | 实际响应体 |
|---|---|
| `Result.ok(13L)` | `{"success":true,"data":13}` |
| `Result.ok()` | `{"success":true}` |
| `Result.ok(records, 4L)` | `{"success":true,"data":[...],"total":4}` |
| `Result.fail("设备不存在")` | `{"success":false,"errorMsg":"设备不存在"}` |

**例子里的对应（第 1 步的响应）**：

```json
{"success":true,"data":13}
```

`errorMsg` 和 `total` 都是 null，所以两个键根本不出现在 JSON 里。

`controller/LaboratoryController.java:40-52`

# 五、数据级校验：王老师改实验室 2 的设备

接口级放行 ≠ 数据级放行。**王老师的 role 是 `LAB_ADMIN`，所以 §2 那道拦截器会让他过；真正拦住他的是 Service 里的 `assertManageable`。**

## 5.1 `updateEquipment` 逐行

`service/impl/EquipmentServiceImpl.java:71-82`

```java
@Override
public void updateEquipment(Equipment equipment) {
    Equipment existing = getById(equipment.getId());            // ① 查库里的旧设备
    assertEquipmentManageable(existing);                        // ② 校验旧设备所属的实验室
    // 禁止把设备"搬"进别人的实验室
    if (equipment.getLaboratoryId() != null
            && !equipment.getLaboratoryId().equals(existing.getLaboratoryId())) {
        laboratoryService.assertManageable(equipment.getLaboratoryId());   // ③ 目标实验室也要校验
    }
    updateById(equipment);                                      // ④ 更新
    deleteEquipmentCache(equipment.getId());                    // ⑤ 删缓存
}
```

- **① 先查旧值**：后面两步都要用旧的 `laboratoryId` 和新值比。
- **② 校验「它现在在哪」**：这一步只保证你管得着旧实验室，不管新实验室。
- **③ 校验「它要去哪」**：只有请求里带了 `laboratoryId` 且和旧的**不一样**时才执行。少了这一步，一个管理员就能把自己的设备改挂到别人的实验室下面——所以迁移目标也必须校验。
- **④⑤ 写完立刻删缓存**：不然 §4.6 的详情接口会继续返回旧值。
- **顺序很重要**：②在③前面。**旧实验室不归你管的话，请求在②就 403 了，③根本没机会执行**——后面王老师的例子里走的就是这一支。

## 5.2 `assertEquipmentManageable` 逐行

`service/impl/EquipmentServiceImpl.java:98-104`

```java
/** 设备不存在与不归当前用户管，统一按无权处理（不区分，避免泄露存在性） */
private void assertEquipmentManageable(Equipment existing) {
    if (existing == null) {
        throw new ForbiddenException("无权管理该设备");        // ①
    }
    laboratoryService.assertManageable(existing.getLaboratoryId());   // ②
}
```

- **① 设备不存在 → 403 而不是 404**，注释写明是为了不泄露存在性。
- **② 这一行就是本篇要核实的答案**：`assertEquipmentManageable` 拿的是**设备这一行的 `laboratory_id`**，把它交给 `assertManageable`；`assertManageable` 再去查**那个实验室的 `admin_user_id`**，和当前登录用户比。也就是：

```
设备 -> laboratory_id -> tb_laboratory.admin_user_id -> 和当前 userId 比
```

**它不查 `tb_equipment` 上的任何其他字段，也不查实验室的 `status`。**

王老师发的请求：


**所以前端不能只按状态码处理**：同样是 403，一个没有 body 可以读。

# 六、设备的其余写操作

这三个写操作在 §3（新增）、§5（修改）讲过的部分不重复：**开头都是同一个 `assertEquipmentManageable` 归属校验（§5.2），成功之后都调同一个 `deleteEquipmentCache`**。下面只写各自独有的差异。

## 6.1 改状态 `PUT /equipment/{id}/status?status=AVAILABLE`

`controller/EquipmentController.java:59-72`（同样带 `@RequireRole(LAB_ADMIN)`）在调 Service 之前，先用 `EquipmentStatus.valueOf(statusValue)` 把字符串转成枚举：

```java
    try {
        status = EquipmentStatus.valueOf(statusValue);        // ① 只认枚举名，大小写敏感
    } catch (IllegalArgumentException | NullPointerException e) {
        return Result.fail("设备状态不合法");                  // ② 在 Controller 里就拦掉
    }
```

- **①** `"available"` 会抛 `IllegalArgumentException`。
- **② 非法值是 `Result.fail(...)` + HTTP 200**——这里没抛异常，不走 `WebExceptionAdvice`。这是本接口独有的错误表达方式。

`service/impl/EquipmentServiceImpl.java:84-89` 里，除了 §5.2 那道归属校验和收尾的删缓存，中间只有 `updateById(new Equipment().setId(id).setStatus(status))`：只构造带 `id` 和 `status` 两个字段的对象，`updateById` 忽略 null 字段，SQL 就是 `UPDATE tb_equipment SET status = ? WHERE id = ?`，**其他字段一个都不覆盖**。

**例子里的对应**（归属校验传的是设备 13 查出来的 `laboratory_id = 2`，§5.2 那条链）：

```
PUT /equipment/13/status?status=MAINTENANCE
→ UPDATE tb_equipment SET status = 'MAINTENANCE' WHERE id = 13
→ DEL lab:equipment:13   →   {"success":true}
```

## 6.2 删除：设备没有依赖检查，实验室有

`EquipmentServiceImpl.java:91-96` 的 `deleteEquipment` 是 `assertEquipmentManageable(getById(id))` → `removeById(id)` → `deleteEquipmentCache(id)`，**中间没有任何依赖检查**：不管有没有预约批次挂在这台设备上，直接删。实验室的删除（`LaboratoryServiceImpl.java:56-66`）在 `assertManageable(id)` 之后多一次 `equipmentMapper.selectCount(...eq(Equipment::getLaboratoryId, id))`，数出来大于 0 就抛 `BadRequestException`（400）。

**例子里的对应**：李老师删实验室 2 → `selectCount` 得到 4（设备 3、4、10、13）→ 400 `该实验室下仍有 4 台设备，请先转移或删除设备`。

## 6.3 缓存删除：谁改谁删

`EquipmentServiceImpl.java:126-132` 的 `deleteEquipmentCache(id)` 删 `"lab:equipment:" + id`（TTL 是 `30 + [0,5)` 分钟，`RedisConstants.java:12-14`）。**调它的只有三个写操作**：`updateEquipment`（`EquipmentServiceImpl.java:81`）、`updateEquipmentStatus`（`:88`）、`deleteEquipment`（`:95`），只有 delete、没有重试或补偿；而 **`saveEquipment`（`:64-69`）不调**——新设备的 id 刚生成，缓存里不可能有旧值（§0.4 里 `lab:equipment:13` 本来就不存在）。这条规则靠每个写方法自己记得，没有统一兜底，记在 §8.6。

# 七、三个边界样本：校验到底看哪些字段

`cast.md` 里有三组真实数据，专门用来验证「校验看了什么、按什么顺序看」。系统里有两处**完全独立**的校验，分开说。

## 7.1 管理端写操作的校验：只看 `admin_user_id`

`assertManageable`（§3.3）只做两件事：查实验室、比 `admin_user_id`。**不读 `status`。**

| 样本 | 王老师（uid 3）能不能管 | 依据 |
|---|---|---|
| 实验室 4（`MAINTENANCE`）+ 设备 7、8 | **能**。`4.admin_user_id = 3` | `LaboratoryServiceImpl.java:31` 只比 `adminUserId` |
| 实验室 2 的设备 3 | **不能**。`2.admin_user_id = 2 != 3` | 同上，403 |
| 实验室 3（`OPEN`）| 能 | 同上 |

**所以「实验室是 `MAINTENANCE`」这件事，在管理端这条路上根本不参与判断**：王老师可以照常给实验室 4 新增设备（`saveEquipment` → `assertManageable(4)` 通过），李老师也可以照常改实验室 1、2 下的任何设备。

## 7.2 预约时的设备校验：看 `status` 和 `booking_enabled`，不看实验室

这段在 05 篇的 `submit` 里，但三个样本说的就是它，所以在这里把顺序讲清楚。`service/impl/ReservationServiceImpl.java:95-100`：

```java
Equipment equipment = equipmentService.getById(batch.getEquipmentId());
if (equipment == null
        || equipment.getStatus() != EquipmentStatus.AVAILABLE
        || !Boolean.TRUE.equals(equipment.getBookingEnabled())) {
    throw new BadRequestException("设备当前不可预约");
}
```

**三个条件用 `||` 连起来，从左到右短路求值**：

```
① equipment == null ?            → 是则 400「设备当前不可预约」
② status != AVAILABLE ?          → 是则 400（③ 不再求值）
③ bookingEnabled != TRUE ?       → 是则 400
```

三个样本代进去：

| 样本 | `status` | `booking_enabled` | 停在哪一步 | 结果 |
|---|---|---|---|---|
| **设备 2**（透射电子显微镜） | `MAINTENANCE` | `0` | **②** | 400 `设备当前不可预约`。**`booking_enabled = 0` 这个事实根本没被读到** |
| **设备 11**（冷冻切片机） | `MAINTENANCE` | `1` | **②** | 400 `设备当前不可预约`。**`booking_enabled = 1` 也救不了它，状态先判且短路** |
| **设备 7 / 8**（GPU 工作站 / 高性能计算节点） | `AVAILABLE` | `1` | 三个条件都不成立 → **通过** | 设备这一关放行 |

**设备 7/8 是关键**：它们自己 `AVAILABLE` 且 `booking_enabled = 1`，但所属的**实验室 4 是 `MAINTENANCE`**。而上面这 5 行代码里**只出现 `equipmentService.getById`，没有 `laboratoryService`**——**实验室状态在这条链路上从来没被读到**。所以实验室 4 停不停机，对预约判定没有任何影响。

> 前提是批次本身可用：在设备校验之前，`submit` 已经先判了批次存在、批次是 `PUBLISHED`、以及当前时间在预约窗口内（`ReservationServiceImpl.java:81-107`，05 篇逐条讲）。设备 7/8 真被约上，还要有挂在它们下面的 `PUBLISHED` 批次。

## 7.3 查询侧：状态只是可选筛选

- `GET /equipment/{id}`（§4.6）：**没有任何状态过滤**。设备 2 的详情照样 200，`status` 字段照样返回 `"MAINTENANCE"`。状态由前端展示，不由后端拦。
- `GET /equipment/page`（§4.4）：`status` / `bookingEnabled` 是 `<if>` 里的**可选筛选**，不传就不过滤。所以：

| 请求 | 返回 |
|---|---|
| `GET /equipment/page`（不带条件） | 全 12 台 |
| `GET /equipment/page?status=MAINTENANCE` | 设备 2、6、11 |
| `GET /equipment/page?bookingEnabled=1` | 除设备 2、6 外的 10 台 |
| `GET /equipment/page?status=MAINTENANCE&bookingEnabled=1` | 只有设备 11 |

```
  │      VALUES (2,2,'电感耦合等离子体质谱仪',...,'AVAILABLE',1)
  │      → MySQL 回填 id = 13
  │
  └─ return Result.ok(13L)  →  200  {"success":true,"data":13}
```

**存储变化**：`tb_equipment` 多出 id=13 一行；`tb_laboratory`、`tb_equipment_category`、Redis 全都没变。

## 8.2 学生 101 那条浏览路径

```
GET /laboratory/2                                  → 200 实验室 VO（无 adminUserId）
GET /equipment/page?current=1&laboratoryId=2       → 200 data 4 台，第一台是 id 13，total=4
```

设备列表是**两次 join 现查的**，不是缓存；设备详情 `GET /equipment/13` 第一次查会写 `lab:equipment:13`（03 篇）。

## 8.6 当前项目边界（源码里能看到的问题）

- **`GET /equipment/{id}` 和 `GET /equipment/page` 都不按实验室状态过滤**，实验室 4 是 `MAINTENANCE` 时，它下面的设备 7、8 依然以 `AVAILABLE` 对外展示。
- **删除设备没有依赖检查**：`deleteEquipment`（`EquipmentServiceImpl.java:91-96`）只校验归属就 `removeById`，挂在它下面的预约批次会变成孤儿数据；实验室删除反而有这道检查。
- **错误有两种表达方式**：`RoleInterceptor` 的 403 没有响应体，`WebExceptionAdvice` 的 403 有 `Result` JSON；`updateEquipmentStatus` 的非法状态值又是「HTTP 200 + `fail`」。前端要分别处理。
- **缓存的删除靠每个写方法自觉**：`updateEquipment` / `updateEquipmentStatus` / `deleteEquipment` 各自调一次 `deleteEquipmentCache`，`saveEquipment` 不调（新增不需要）。没有统一兜底，新增写操作时容易漏。
