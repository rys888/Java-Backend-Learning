# 一、先看结果：这条预约在库里的一生

学生 102 在 2026-10-07 09:00 点了「预约批次 7」，随后在 2026-10-08 14:00 的使用时段里被李老师核验完成。下面两张表就是这一套动作之后库里的样子，中间过程在 §五～§七 拆开讲。

## 1.1 `tb_reservation_request` —— 同一时刻就写下的账本行

| `request_id` | `user_id` | `batch_id` | `status` | `fail_reason` | `create_time` | `update_time` |
|---|---|---|---|---|---|---|
| **645827360351847424** | 102 | 7 | **`CONFIRMED`** | `NULL` | 2026-10-07 09:00:00 | 落库那一刻 |

`status` 走过三站：`PRE_ACCEPTED`（写出去了）→ `PUBLISHED`（消息投递成功）→ `CONFIRMED`（落库完成）。

## 1.2 `tb_reservation` —— 事实表里最终的那一行

| `id` | `user_id` | `batch_id` | `status` | `quota_released` | `active_flag` | `create_time` | `update_time` |
|---|---|---|---|---|---|---|---|
| **645827360351847424** | 102 | 7 | **`COMPLETED`** | `0` | **`1`** | 2026-10-07 09:00:00 | 核验那一刻 |

两列不是 INSERT 进去的：`active_flag` 是**生成列**（§5），`quota_released` 和 `status` 都是后面 UPDATE 改出来的。

## 1.3 `tb_reservation_batch` 第 7 行

| `id` | `total_quota` | `remaining_quota` | `status` |
|---|---|---|---|
| 7 | 5 | **4** | `PUBLISHED` |

`5 → 4` 是落库时被扣的（§7.2 第 ⑤ 条）。**核验完成不归还名额**，所以还剩 4。

## 1.4 三个变体（同一个例子，换个结局）

**变体 A：学生 102 在 10-08 16:00 之前自己取消了**

`tb_reservation.status` `RESERVED` → **`CANCELLED`**，生成列跟着重算，`active_flag` `1` → **`NULL`**；`quota_released` `0` → **`1`**；`tb_reservation_batch.remaining_quota` `4` → **`5`**；Redis `reservation:batch:quota:7` `4` → **`5`**，users 集合里 `SREM` 掉 102。

**这一行取消之后不再占唯一键槽位** —— 学生 102 可以重新约批次 7，见 §5.2。

**变体 B：学生 102 约完之后，104 想同时约第二次**

第二次请求会拿到**新的 `reservationId`**（`RedisIdWorker` 每次递增），Redis 的 `SISMEMBER` 先拦住，返回 `3 DUPLICATE`。真要走到库，`uk_user_batch_active` 也会拒掉（§5）。

**变体 C：管理员的定时任务把一条过期未核验的预约置为爽约**

`status` 从 `RESERVED` → **`NO_SHOW`**，`active_flag` **仍然是 `1`**（只有 `CANCELLED` 才变 `NULL`）。名额不归还。所以爽约过的用户**不能再约同一个批次**。

# 二、迁移链与零外键

## 2.1 执行顺序

`phase0_baseline.sql:2` 写明了顺序：

```
phase0_baseline → phase2_laboratory_equipment → phase3_user_role → phase5_lab_ownership
→ phase5_reservation_batch → phase7_reservation → phase8_consistency → phase9_reservation_lifecycle
```

`phase10_drop_legacy_tables.sql` 是独立的死表清理：10 条 `DROP TABLE IF EXISTS`（`:5-32`），删掉课程遗留的 `tb_shop` / `tb_voucher` / `tb_seckill_voucher` 等，注释里逐个标了 DROP 时点的行数（`tb_shop` 14 行、`tb_blog` 4 行、`tb_voucher` 1 行）。

## 2.2 零外键

```bash
find src -type f \( -name "*.sql" -o -name "*.xml" \) -exec grep -Hni "foreign key\|REFERENCES" {} +
```

**没有任何命中。** 八张表、十个迁移脚本，一个 `FOREIGN KEY` 都没有。

这意味着：

- **表间关系全靠 SQL 里的 `LEFT JOIN` 和 Java 代码维护**。`ReservationMapper.xml:14-17` 一次 JOIN 三张表（`tb_reservation` → `tb_reservation_batch` → `tb_equipment` → `tb_laboratory`）把设备名、实验室名拼出来。
- **可以插入「孤儿行」**：把 `tb_reservation` 的 `batch_id` 写成 999 不会被数据库拦下——拦它的是 Java 侧的前置校验（`ReservationServiceImpl.java:88-91`，`getById(batchId) == null` 就抛 400）。
- **删父行不会级联、也不会报错**。`LaboratoryServiceImpl.java:60` 删实验室时，是用一条 `update(...).eq(Equipment::getLaboratoryId, id)` 手动把设备挂空，而不是靠 `ON DELETE SET NULL`。

**例子里的对应值**：`tb_reservation.batch_id = 7`、`tb_reservation_batch.equipment_id = 3`、`tb_equipment.laboratory_id = 2` 这三段关系，数据库层面互不认识，是 Java 端查出来的。

## 2.3 幂等 ALTER 的写法

`phase3_user_role.sql:1-6` 全文：

```sql
SET @col := (SELECT COUNT(*) FROM information_schema.COLUMNS
             WHERE TABLE_SCHEMA = DATABASE() AND TABLE_NAME = 'tb_user' AND COLUMN_NAME = 'role');
SET @sql := IF(@col = 0,
  'ALTER TABLE `tb_user` ADD COLUMN `role` varchar(16) NOT NULL DEFAULT ''USER'' COMMENT ''角色：USER/LAB_ADMIN'' AFTER `icon`',
  'SELECT ''tb_user.role already exists'' AS skipped');
PREPARE stmt FROM @sql; EXECUTE stmt; DEALLOCATE PREPARE stmt;
```

逐行：

- `:1-2` 数 `information_schema.COLUMNS` 里 `tb_user` 有没有 `role` 列，结果塞进 `@col`。
- `:3-5` 把要执行的 SQL **当成字符串**拼进 `@sql`——所以 `'USER'` 要写成 `''USER''`（四个引号），`'角色：USER/LAB_ADMIN'` 同理。
- `:6` `PREPARE` + `EXECUTE` + `DEALLOCATE`：MySQL 不允许直接执行变量里的 SQL，必须走这条预处理通道。

**为什么要这么绕**：MySQL 的 `ADD COLUMN` 没有 `IF NOT EXISTS`，重复执行会直接报错中断迁移。`CREATE TABLE IF NOT EXISTS` 反而是原生的，所以建表脚本没这层包装。`phase5_lab_ownership.sql:1-6` 是一模一样的模板，只换了表名、列名和 SQL 字符串。

**例子里的对应值**：`phase5_lab_ownership.sql:12-14` 随后执行

```sql
UPDATE `tb_laboratory`
SET `admin_user_id` = (SELECT `id` FROM `tb_user` WHERE `phone` = '13900000001')
WHERE `id` IN (1, 2) AND `admin_user_id` IS NULL;
```

把实验室 1、2 挂到李老师名下。`WHERE ... AND admin_user_id IS NULL` 让这条 UPDATE 重跑也不会覆盖别人改过的归属。`:16-18` 是对王老师和实验室 3、4 的对称操作。

## 2.4 `phase9` 没有这层保护

`phase9_reservation_lifecycle.sql:2-10` 是两条**裸 `ALTER TABLE`**，没有 `information_schema` 包装。重复执行会报「Duplicate column name」，它本来就是一次性迁移。

**这也是为什么 `phase9` 是唯一一个把「回滚步骤」写在注释里的文件**（`:12-18`）——没有幂等保护，就只能靠人工。

# 三、逐表要点

只贴和结论相关的那几行，其余列用表格概述。

## 3.1 `tb_user` —— 唯一索引名拼错了

`phase0_baseline.sql:5-15`，关键是最后三行：

```sql
`id` bigint(20) UNSIGNED NOT NULL AUTO_INCREMENT COMMENT '主键',
`phone` varchar(11) CHARACTER SET utf8mb4 COLLATE utf8mb4_general_ci NOT NULL COMMENT '手机号码',
...
PRIMARY KEY (`id`) USING BTREE,
UNIQUE INDEX `uniqe_key_phone`(`phone`) USING BTREE
) ENGINE = InnoDB AUTO_INCREMENT = 1010 ...
```

**索引名逐字是 `uniqe_key_phone`** —— `uniqe` 少了一个 `u`，不是 `unique`。这是课程模板带过来的拼写，项目里没有改。它是真实存在的瑕疵：改它得 `ALTER TABLE ... RENAME INDEX`，也就一直留着了。

`phase3_user_role.sql:4` 加了角色列：

```sql
ADD COLUMN `role` varchar(16) NOT NULL DEFAULT 'USER' COMMENT '角色：USER/LAB_ADMIN' AFTER `icon`
```

**`password` 字段在表里，但登录流程不用它**（01 篇：登录走手机号 + 验证码，token 存 Redis）。

**例子里的对应值**：学生 102 那行 `id=102 / phone=<11 位手机号> / nick_name='' / role='USER'`；种子管理员靠 `phase3:8-10` 的 `INSERT ... ON DUPLICATE KEY UPDATE role='LAB_ADMIN'` 按 `phone` 定位，本题假设它落在 `id=2`。

## 3.2 `tb_laboratory` —— `admin_user_id` 是数据级授权的唯一依据

`phase2:1-14` 建表（`status` 默认 `'OPEN'`，索引 `idx_campus`、`idx_name`），`phase5_lab_ownership.sql:4` 加列：

```sql
ADD COLUMN `admin_user_id` bigint unsigned NULL COMMENT '负责管理员用户id' AFTER `status`,
ADD KEY `idx_admin_user_id` (`admin_user_id`)
```

**列可为 NULL**，`LaboratoryServiceImpl.saveLaboratory` 建的时候会 `setAdminUserId(user.getId())`，所以 NULL 只可能来自历史数据或直接改库。`Laboratory.adminUserId` 的注释写明了后果：「null 表示未分配（未分配时任何人都不能管理）」。

**这个索引有实际调用方**：`ReservationMapper.xml:37-39` 的 `AND l.admin_user_id = #{adminUserId}` 和 `ReservationBatchMapper.xml:39-41` 的同名条件。管理端分页就是靠它把「我负责的实验室下的预约 / 批次」筛出来的。

**例子里的对应值**：`tb_laboratory` 第 2 行 `admin_user_id = 2`（李老师），所以李老师能核验 102 这条预约；王老师（`admin_user_id` 是 3、4）走 `assertManageable` 会拿到 403。

## 3.3 `tb_equipment_category` / `tb_equipment`

`tb_equipment_category`（`phase2:16-25`）有个真唯一键：

```sql
UNIQUE KEY `uk_name` (`name`) USING BTREE
```

分类名不能重——这是那张表唯一的约束。

`tb_equipment`（`phase2:27-45`）四个单列索引，对应 `EquipmentMapper.xml` 里那几个 `<if>`：

```sql
KEY `idx_laboratory_id` (`laboratory_id`) USING BTREE,
KEY `idx_category_id` (`category_id`) USING BTREE,
KEY `idx_name` (`name`) USING BTREE,
KEY `idx_status` (`status`) USING BTREE
```

注意 `idx_name` 和 `EquipmentMapper.xml:23-25` 的 `e.name LIKE CONCAT('%', #{q.name}, '%')` **对不上**：`LIKE` 的前缀是 `%`，B+ 树索引用不上，这个索引在这条查询里是白建的。其余三个条件都是等值，索引有效。**`tb_equipment` 没有 `admin_user_id`**——设备归属由 `laboratory_id` 决定，权限校验必须 join 到实验室（02 篇）。

**例子里的对应值**：设备 3 是 `laboratory_id=2 / category_id=2 / status='AVAILABLE' / booking_enabled=1`，两个开关都开，所以能约。

## 3.4 `tb_reservation_batch` —— 两组时间 + 两份名额

`phase5_reservation_batch.sql` 全文 17 行，重点是这四组：

```sql
`start_time`         datetime NOT NULL COMMENT '使用开始时间',
`end_time`           datetime NOT NULL COMMENT '使用结束时间',
`booking_start_time` datetime NOT NULL COMMENT '预约开放时间',
`booking_end_time`   datetime NOT NULL COMMENT '预约截止时间',
`total_quota`        int NOT NULL COMMENT '总名额',
`remaining_quota`    int NOT NULL COMMENT '剩余名额',
`status`             varchar(16) NOT NULL DEFAULT 'DRAFT' COMMENT '状态：DRAFT/PUBLISHED/CLOSED/CANCELLED',
KEY `idx_booking_window` (`booking_start_time`, `booking_end_time`) USING BTREE
```

**两组时间各管各的**：

| 组 | 列 | 语义 | 谁在用 |
|---|---|---|---|
| 使用窗口 | `start_time` / `end_time` | 用户实际用设备的时间 | 核验前置检查（`ReservationLifecycleServiceImpl:94`）、爽约判定（`ReservationMapper.xml:63`） |
| 预约窗口 | `booking_start_time` / `booking_end_time` | 可以下单的时间 | `submit` 的第 ⑥⑦ 项检查、Lua 的窗口判定、`BookingState.of(...)` |

**`remaining_quota` 是 MySQL 侧的名额**，和 Redis 的 `reservation:batch:quota:{id}` 是两份独立计数（05/06 篇）。两边什么时候动：

| 动作 | MySQL `remaining_quota` | Redis quota |
|---|---|---|
| `publish` | 不动（建批次时 = `total_quota`） | `SETNX = totalQuota` |
| 消费者落库 | `-1`（`WHERE remaining_quota > 0`） | 已在 Lua 里 `DECR` |
| 取消 | `+1`（`WHERE remaining_quota < totalQuota`） | `rollback` 里 `INCR` |
| 对账补偿 | 不动 | `rollback` 里 `INCR` |
| 爽约 / 核验 | 不动 | 不动 |

**`remaining_quota` 没有任何 CHECK 约束**，上下限全靠两条 UPDATE 的 `WHERE` 兜住。

**例子里的对应值**：批次 7 的 `total_quota = 5`；学生 102 落库后 `remaining_quota = 4`；同批的 101、103、104、105 也各扣一次，最终 `0`。

## 3.5 `tb_reservation` —— 主键非自增

`phase7_reservation.sql:1-11` 建表：

```sql
`id`          bigint unsigned NOT NULL COMMENT '预约id（RedisIdWorker 生成，非自增）',
...
PRIMARY KEY (`id`) USING BTREE,
UNIQUE KEY `uk_user_batch` (`user_id`, `batch_id`) USING BTREE,
KEY `idx_batch_id` (`batch_id`) USING BTREE,
KEY `idx_user_id` (`user_id`) USING BTREE
```

`phase9` 把最后那两行改掉了（§5.1）。`create_time` / `update_time` 都是 `DEFAULT CURRENT_TIMESTAMP`，`update_time` 还带 `ON UPDATE CURRENT_TIMESTAMP`——**任何一次 UPDATE 都会把它推到当前时间**，后面有两处代码专门利用 / 规避这个行为。

**例子里的对应值**：`id = 645827360351847424`（不是 1、2、3 这样的自增值），`user_id = 102`，`batch_id = 7`。

## 3.6 `tb_reservation_request` —— 和事实表共用同一个 id

`phase8_consistency.sql:1-12`：

```sql
`request_id`  bigint unsigned NOT NULL COMMENT '请求id（RedisIdWorker，与预约id同源）',
`status`      varchar(16) NOT NULL COMMENT 'PRE_ACCEPTED/PUBLISHED/CONFIRMED/UNKNOWN/COMPENSATED',
`fail_reason` varchar(255) DEFAULT NULL COMMENT '失败原因（DLQ 治理用）',
PRIMARY KEY (`request_id`) USING BTREE,
KEY `idx_status_update_time` (`status`, `update_time`) USING BTREE,
KEY `idx_user_batch` (`user_id`, `batch_id`) USING BTREE
```

**注释里的「与预约id同源」是字面意思**：`submit` 生成一个 `reservationId`，先拿它当 `request_id` 插账本（`ReservationServiceImpl.java:110`），再把它塞进 MQ 消息（`:136`），消费者最后拿同一个值当 `tb_reservation.id`（`ReservationMessageConsumer.java:137`）。**两张表的主键值是同一个数**，不是「两张表各有一份 id 但相等」。

`idx_status_update_time` 是给对账扫描用的：`ReservationRequestServiceImpl.java:79-86` 的 `WHERE status IN (...)` + `update_time < ?` + `ORDER BY update_time`，和索引列序完全对得上。**`idx_user_batch` 在代码里没有调用方**——没有任何按 `(user_id, batch_id)` 查账本的 SQL 语句，它是留着的。

**例子里的对应值**：`request_id = 645827360351847424`（和 `tb_reservation.id` 同一个数）、`user_id = 102`、`batch_id = 7`。

## 3.7 `tb_reservation_dlq` —— 没有唯一键

`phase8_consistency.sql:14-26`：

```sql
`reservation_id` bigint unsigned DEFAULT NULL COMMENT '解析出的预约id，解析失败为 NULL',
`payload`        text,
`failure_reason` varchar(512),
`replay_count`   int NOT NULL DEFAULT 0 COMMENT '已重放次数',
`status`         varchar(16) NOT NULL DEFAULT 'NEW' COMMENT 'NEW/REPLAYED/DISCARDED',
PRIMARY KEY (`id`),
KEY `idx_reservation_id` (`reservation_id`),
KEY `idx_status_create_time` (`status`, `create_time`)
```

**没有唯一键，同一 `reservation_id` 可以有多行。** `ReservationDlq` 的类注释明确接受这个取舍：「同一死信在落库成功、确认前崩溃时可能被重复投递并产生重复行，这是治理日志允许的取舍；事实来源仍是 tb_reservation，本表不做去重。」**例子里的对应值**：0 行 —— 学生 102 这条预约全程正常，没有消息进死信。

## 3.8 主键策略

MyBatis-Plus 的 `@TableId(type = ...)` 逐个体检：

# 四、那个 id 是谁生成的

`ReservationServiceImpl.java:108`：

```java
long reservationId = redisIdWorker.nextId("reservation");
```

`RedisIdWorker.java:27-41`（05 篇 §7 已逐行展开）：

```java
public long nextId(String keyPrefix) {
    LocalDateTime now = LocalDateTime.now();                 // 2026-10-07T09:00:00
    long nowSecond = now.toEpochSecond(ZoneOffset.UTC);      // ① 用 UTC → 1791363600
    long timestamp = nowSecond - BEGIN_TIMESTAMP;            // ② BEGIN_TIMESTAMP = 1640995200L → 150368400
    String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));   // ③ → "2026:10:07"
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);   // ④ → 1024
    return timestamp << COUNT_BITS | count;                  // ⑤ → 645827360351847424
}
```

| 步 | 表达式 | 例子里的值 |
|---|---|---|
| ① | UTC epoch 秒 | `1791363600` |
| ② | `1791363600 − 1640995200` | `150368400` |
| ③ | 当天日期 | `"2026:10:07"` |
| ④ | `INCR icr:reservation:2026:10:07` | `1024` |
| ⑤ | `150368400 << 32 \| 1024` | **`645827360351847424`** |

**为什么不靠自增**——三条都是硬理由，不是风格偏好：

1. **id 要在行存在之前就用**。`submit` 的顺序是「生成 id → 写账本 → 抢 Redis 名额 → 投 MQ → 同步返回给前端」（`ReservationServiceImpl.java:108-137`）。自增值只有 `INSERT` 那一刻才由 MySQL 分配，`submit` 根本拿不到它。
2. **两张表要共用一个 id**。账本的 `request_id` 和事实表的 `id` 是同一个数（§3.6）。两张各自 `AUTO_INCREMENT` 的表不可能天然对齐。
3. **消息重放要靠它幂等**。DLQ 重放时消息里带的还是那个 id，`INSERT` 撞主键就会被拒（`ReservationMessageConsumer.java:80-85`）。

**`RedisIdWorker` 的计数器在 Redis 里**，`INCR` 本身是原子的，多实例部署不需要额外协调。

**例子里的对应值**：同一批的兄弟 id 尾数递增 —— 101 → `…846423`、102 → `…846424`、103 → `…846425`、104 → `…846426`、105 → `…846427`、106 → `…846428`。

# 五、`uk_user_batch_active` —— 三列唯一键与生成列

## 5.1 `phase9` 的两条 ALTER 逐行

`phase9_reservation_lifecycle.sql:2-10`：

```sql
ALTER TABLE `tb_reservation`
  ADD COLUMN `status` varchar(16) NOT NULL DEFAULT 'RESERVED' COMMENT '生命周期状态',
  ADD COLUMN `quota_released` tinyint NOT NULL DEFAULT 0 COMMENT '取消时名额是否已归还Redis',
  ADD COLUMN `active_flag` tinyint GENERATED ALWAYS AS (CASE WHEN `status`='CANCELLED' THEN NULL ELSE 1 END) STORED COMMENT '仅约束活跃预约',
  ADD KEY `idx_status_quota_released` (`status`,`quota_released`);

ALTER TABLE `tb_reservation`
  DROP INDEX `uk_user_batch`,
  ADD UNIQUE KEY `uk_user_batch_active` (`user_id`,`batch_id`,`active_flag`);
```

逐行：

- `:3` `status` 默认 `'RESERVED'` —— 已有的历史行会被填成这个值。
- `:4` `quota_released` 默认 `0`，语义是「取消时 Redis 名额是否已经还回去了」，是 08 篇对账的抓手。
- `:5` **`active_flag` 是生成列**。`GENERATED ALWAYS AS (...)` 表示值由表达式算出来，INSERT / UPDATE 都不能直接写它；`STORED` 表示**物化存储**（不是 `VIRTUAL` 的现算），只有物化的列才能进索引。
- `:6` `idx_status_quota_released` 给「捞出还没归还名额的取消单」用：`ReservationMapper.xml:44-51` 的 `WHERE r.status = 'CANCELLED' AND r.quota_released = 0`，索引列序正好对上（`ORDER BY r.update_time` 不在这两列里，排序仍要额外做）。
- `:9` 先删掉旧的两列唯一键 `uk_user_batch`；`:10` 再建三列的 `uk_user_batch_active`。

## 5.2 为什么这么绕：学生 103 取消之后想再约同一个批次

需求是：「**同一个用户对同一个批次，同时只能有一条有效预约**，但取消过的历史记录要留着」。MySQL 没有「部分唯一索引」（只对满足条件的行建唯一约束）。

生成列就是绕开这一点的办法：

| `status` | `active_flag` | 在 `uk_user_batch_active` 里的身份 |
|---|---|---|
| `RESERVED` | `1` | 占槽位 |
| `COMPLETED` | `1` | 占槽位 |
| `NO_SHOW` | `1` | 占槽位 |
| **`CANCELLED`** | **`NULL`** | **不占槽位** |

**关键在 MySQL 的一条规则：唯一索引不约束含 `NULL` 的行**——`(103, 7, NULL)` 可以出现任意多行。所以：

```
(103, 7, 1)      ← 最多一行（活跃的那条）
(103, 7, NULL)   ← 可以有任意多条（每次取消留下一条）
(103, 7, NULL)
```

**用学生 103 走一遍**：

1. 10-07 09:00 学生 103 约批次 7 → 落库一行 `(id=…846425, user_id=103, batch_id=7, status='RESERVED', active_flag=1)`。
2. 10-07 12:00 他取消 → `status` 改成 `'CANCELLED'`，生成列跟着重算，**`active_flag` 自动变成 `NULL`**。
3. 10-07 13:00 他改主意又想约批次 7 → 新的 `reservationId` → `INSERT (user_id=103, batch_id=7, status='RESERVED')`，这一行的 `active_flag` 算出来是 `1`。
4. 数据库里此时是 `(103,7,NULL)` 和 `(103,7,1)` 两行——**三列组合不冲突，INSERT 成功**。

**如果没有 `active_flag` 这个弯**，还是原来的两列 `uk_user_batch (user_id, batch_id)`，第 3 步就会被唯一键拒掉：**学生 103 取消一次就永远约不了批次 7 了**。

反过来说，`(103, 7, 1)` 只允许一行 —— **重复预约仍然是被数据库拦住的那条线**（§7.4）。

## 5.3 Java 侧必须一字不差

`enums/ReservationStatus.java:13-20`：

```java
/**
 * 占用 (user_id, batch_id) 唯一键槽位的状态集合，判据必须与 tb_reservation.active_flag
 * 生成列严格一致：CASE WHEN status = 'CANCELLED' THEN NULL ELSE 1 END。
 * 因此除 CANCELLED 之外的状态都算占用 —— COMPLETED / NO_SHOW 的行仍占着槽位，
 * 该用户不能再对同一批次发起预约（与生成列拒绝插入的行为一致）。
 */

        Collections.unmodifiableList(Arrays.asList(RESERVED, COMPLETED, NO_SHOW));
```

`occupyingStatuses()` 只有**一个调用方**：`ReservationPersistenceServiceImpl.java:39-46` 落库前的判重：

```java
Integer existingCount = reservationMapper.selectCount(
        new LambdaQueryWrapper<Reservation>()
                .eq(Reservation::getUserId, reservation.getUserId())
                .eq(Reservation::getBatchId, reservation.getBatchId())
                .in(Reservation::getStatus, ReservationStatus.occupyingStatuses()));

```

**这段 Java 判重和数据库唯一键是同一件事的两遍实现**：一遍是「先查再决定」（给用户一个干净的 `DUPLICATE` 返回值），一遍是「插进去被拒」（并发下的最后防线）。

**实体类里没有 `activeFlag` 字段**——`grep -rn "activeFlag"` 在整个 `src/main/java` 只命中上面那句 Javadoc 注释。生成列是纯 DB 侧的东西，Java 这边与它对应的只有这个枚举列表。

## 5.4 两边不一致会怎样

`occupyingStatuses()` 比生成列**窄**（比如漏了 `NO_SHOW`）和**宽**（比如把 `CANCELLED` 也算进去）后果完全不同：

| 方向 | 例子 | 后果 |
|---|---|---|
| Java **窄**于 SQL | 列表少了 `NO_SHOW` | 爽约过的用户再约，Java 判重放行 → `INSERT` 撞 `uk_user_batch_active` → 抛 `DuplicateKeyException` → `ReservationMessageConsumer.java:80-85` 走 `basicNack` **进死信**。本该是「你已经约过了」的 400，变成一条要人工处置的死信。 |
| Java **宽**于 SQL | 列表多了 `CANCELLED` | 取消过的用户再约，被 Java 判成 `DUPLICATE` → 消费者 `:68-72` 对 `DUPLICATE` 是 **`basicAck` + 把账本置 `CONFIRMED`**。**消息被确认掉了，`tb_reservation` 里永远不会有这行**，而 Redis 名额在第一步就已经扣了 —— 静默丢一条预约。 |

所以注释里那句「必须与生成列严格一致」不是文档洁癖，是两种 bug 的分界线。

# 七、CAS 更新逐条

「CAS」在这里指 `UPDATE ... WHERE 旧状态`，靠**影响行数是不是 1** 来判断自己有没有抢到这次状态跃迁。「先 SELECT 判状态、再 UPDATE」的写法在项目里一处都没有。

## 7.1 Mapper XML 里的 `<update>`

`mapper` 目录下只有三个 XML（`EquipmentMapper.xml`、`ReservationBatchMapper.xml`、`ReservationMapper.xml`），其中只有一个 `<update>`。

`ReservationMapper.xml:53-68`：

```xml
<update id="markNoShows">
    UPDATE tb_reservation
    SET status = 'NO_SHOW'
    WHERE id IN (
        SELECT id
        FROM (
            SELECT r.id
            FROM tb_reservation r
            JOIN tb_reservation_batch b ON r.batch_id = b.id
            WHERE r.status = 'RESERVED'
              AND b.end_time &lt; #{now}
              AND b.status &lt;&gt; 'CANCELLED'
            LIMIT #{limit}
        ) eligible
    )
</update>
```

逐句：

- `SET status = 'NO_SHOW'` —— 唯一被改的列。生成列 `active_flag` 因此**保持 `1`**（只有 `CANCELLED` 才变 `NULL`）。
- 内层 `SELECT` 从事实表 join 批次表，挑出「还是 `RESERVED`、批次使用时段已过、批次不是取消态」的 id。
- 外面又套了一层 `( ... ) eligible`。**这层不是多余的**：MySQL 禁止在 `UPDATE` 的子查询里直接读被更新的表，套一层派生表（会被物化成临时表）就绕开了。
- `LIMIT #{limit}` 限制一轮处理多少条；`ReservationReconcileServiceImpl.java:84` 传的是 `reconcileLimit`，值来自 `application.yaml:53` 的 `yanyuetong.reservation.reconcile-limit: 200`。

**和别的 CAS 不一样的地方**：`status='RESERVED'` 只写在内层子查询里，**外层 `UPDATE ... WHERE id IN (...)` 没有再判一次 `status`**。其它 CAS 都是把条件放在同一条 UPDATE 的 WHERE 上，这一条是「物化 id 列表 → 按 id 更新」两步。

**例子里的对应值**：学生 102 这条预约如果在 10-08 16:00（`end_time`）之后仍停在 `RESERVED`，会被这条捞到并改成 `NO_SHOW`；本题他按时核验了，所以 `status` 停在 `COMPLETED`。

`ReservationMapper.xml:44-51` 是配套的读侧，用的正是 `idx_status_quota_released`：

```xml
<select id="selectPendingQuotaReleases" resultType="com.yanyuetong.entity.Reservation">
    SELECT r.id, r.user_id, r.batch_id, r.status, r.quota_released,
           r.create_time, r.update_time
    FROM tb_reservation r
    WHERE r.status = 'CANCELLED' AND r.quota_released = 0
    ORDER BY r.update_time ASC, r.id ASC
    LIMIT #{limit}
</select>
```

**例子里的对应值**：学生 102 走变体 A 取消后，如果 `ReservationServiceImpl.java:165-169` 那次置位失败，这行就会出现在这里，被下一轮对账捞出来。

## 7.3 「影响 0 行」各自代表什么

同一句 `== 0`，在各处含义完全不同：

| 位置 | 影响 0 行 = | 代码怎么处理 |
|---|---|---|
| `cancel`（②） | 「不是一条我能取消的 `RESERVED`」 | 再查一次，分三种情况返回（`:51-60`） |
| `complete`（④） | 「不在 `RESERVED` 了」 | 再查一次，`COMPLETED` 就返回 false，否则抛 400（`:107-111`） |
| 取消回补（③） | 「MySQL 侧已经满了，不该再加」 | 只打 warn（`:67-72`） |
| `persist` 扣名额（①） | 「名额真的没了」 | 返回 `QUOTA_CONFLICT`，消息不 ACK |
| `quota_released`（⑤⑥） | 「别人已经置过位了」 | 不处理（⑤ 直接忽略，⑥ 不计数） |
| `casStatus` 系（⑧⑨） | 「账本已经不在期望状态了」 | 返回 false，调用方打日志 |
| DLQ（⑮⑯） | 「被并发抢先了」 | `rejected(...)` |

**没有一处是「先 SELECT 判状态、再 UPDATE」**。`cancel` 和 `complete` 里确实有 `selectById`，但那是**前置校验 + 影响 0 行之后的兜底诊断**，不是状态跃迁的依据。

## 7.4 唯一键兜底

`uk_user_batch_active` 是最后一道防线。即使 §5.3 那段 Java 判重因为并发漏了（两个请求都查到 `existingCount = 0`），`INSERT` 也会被唯一键拒掉：

```
ERROR 1062 (23000): Duplicate entry '102-7-1' for key 'tb_reservation.uk_user_batch_active'
```

`ReservationMessageConsumer.java:80-85` 接住 `DuplicateKeyException` 走 `basicNack`，注释里写了为什么不能 ACK：「若 ACK，这条未落库的消息会静默消失且 DLQ 无痕迹」。

**注释里的推理值得留意**：同一用户的消息已经被 `lock:reservation:{userId}` 串行化了，所以走到这个 catch 的冲突，正常路径下应该是 `reservationId` 的主键冲突（DLQ 重放），而不是用户重复预约撞 `uk_user_batch_active`。**但两个键的冲突走的是同一个 catch** —— 不管撞的是哪个，结果都是 NACK 进死信。

`ReservationPersistenceServiceImpl.java:29-38` 还有一处配套的取舍：开头的幂等检查只认「**同 id 且同 user 且同 batch**」才算重复投递；「同 id 但归属不同」是异常的主键冲突，**故意不提前返回**，让它走到 `INSERT` 去撞主键、进死信。

**例子里的对应值**：学生 102 是第一次约批次 7，`selectById` 出来 `null`、`selectCount` 出来 0，两处都没拦，直接进 ① 扣名额。

| 位置 | 方法 | 事务里包着什么 |
|---|---|---|
| `ReservationPersistenceServiceImpl.java:27` | `persist` | ① `UPDATE remaining_quota - 1` + `<insert>` 一条 `tb_reservation` |
| `ReservationLifecycleServiceImpl.java:30` | `cancel` | ② `UPDATE status='CANCELLED'` + ③ `UPDATE remaining_quota + 1` |
| `ReservationLifecycleServiceImpl.java:77` | `complete` | ④ `UPDATE status='COMPLETED'`（单条，事务只为了让语义统一） |

**`persist` 那处的事务是真起作用的**：如果 `INSERT` 撞了唯一键抛异常，① 那次名额扣减会跟着回滚——不会留下「名额扣了但预约没落库」的批次。`complete` 那处则只是单条 UPDATE，加不加事务结果一样。

## 8.2 预期有、实际没有

| 位置 | 为什么「预期有」 | 为什么实际没有 |
|---|---|---|
| **`ReservationServiceImpl.submit`**（`:79-138`） | 它写了 `tb_reservation_request`，后面还有 Redis 和 MQ | **跨了三种存储**（MySQL 账本、Redis Lua、RabbitMQ）。Redis 和 MQ 不参与 JDBC 事务，包进来只会造成「MySQL 回滚了但 Redis 名额已经扣掉」 |
| **`ReservationServiceImpl.cancel`**（`:140-176`） | 它改了 `tb_reservation.quota_released` | 它调用的 `reservationLifecycleService.cancel` **自己有事务**（那是另一个 bean，代理生效）；挂上事务后，后面的 Redis rollback 一旦抛异常会把已经提交的状态跃迁一起回滚，反而丢掉「已取消」这个事实 |
| **`ReservationMessageConsumer.onReservationMessage`**（`:39-97`） | 它做落库 | 落库本身在 `reservationPersistenceService.persist` 里（有事务）。消费者这一层再包一层，只是把「异常处理 / ACK 决策」也拖进事务边界，而 ACK 不是数据库动作 |
| `ReservationBatchServiceImpl.publish`（`:112-156`） | Redis `SETNX` + MySQL `UPDATE` 两步 | 它用的是另一种补偿：UPDATE 影响 0 行时把刚建的 quota key `delete` 掉（`:148-155`），注释写明「MySQL remains authoritative; stale quota has a finite TTL」 |
| `ReservationBatchServiceImpl.close` / `cancel`（`:159-193`） | 各自一条 UPDATE + 一次 Redis `delete` | 单条 UPDATE 在 autocommit 下本身就是原子的；Redis 删 key 失败只留下有 TTL 的残留 |
| `ReservationRequestServiceImpl` / `ReservationDlqServiceImpl` 的全部方法 | 改账本、改死信台账 | 每个方法都只有一条 INSERT 或一条 CAS UPDATE，autocommit 够用 |
| `ReservationReconcileServiceImpl.scheduledReconcile`（`:60-93`） | 一轮里改很多行 | **刻意不加**：方法注释写「单条异常不会回滚或中断本轮其他请求」（`:96-98`），逐条各自成事才对 |
| `ReservationServiceImpl.verify`（`:179-195`） | 核验 | 它只做权限判定，真正的状态跃迁委托给 `complete`（那处有事务） |

**一句话总结**：有事务的三处，共同点是「**一次要改两行以上、且都在 MySQL 里**」。只要跨出了 MySQL，或者只需要改一行，项目就改用状态 CAS + 补偿。

## 8.3 `cancel` 为什么拆成两段

```
① ReservationLifecycleServiceImpl.cancel   ← @Transactional（两条 UPDATE，同一事务）
② ReservationServiceImpl.cancel            ← 无事务（Redis rollback + CAS 置 quota_released=1）
```

② 在 ① 提交之后执行。**中间崩溃的话，`quota_released` 还是 0**，08 篇对账的 `releasePendingQuotas` 会把它捞出来重试（用的就是 §7.1 那条 `selectPendingQuotaReleases`）。

`ReservationServiceImpl.java:152-160` 那段注释还解释了一个更细的坑：只有本次调用**真的完成了 `RESERVED→CANCELLED` 跃迁**（`TRANSITIONED`）才允许碰 Redis 和 `quota_released`；幂等路径（`ALREADY_CANCELLED`）必须直接 `return`。注释原文给出的理由是：

> 用户可能在取消 R1 之后重新预约得到 R2，此时对 R1 的重复取消会 SREM 掉 R2 在 Redis 中的占位标记 —— Redis 多出名额而 MySQL 仍占用 R2，既超卖又重新打开名额泄漏。

**对应到本篇例子**：学生 102 取消（R1）之后又在 13:00 重新约上批次 7（R2，新的 `reservationId`）。此时有人对着 R1 再点一次取消——如果那次重复取消也去执行 Redis `SREM`，删掉的是 **R2 的占位**。

## 9.3 当前实现里几处值得留意的地方

- **零外键**是全局选择：好处是迁移自由，代价是所有引用完整性都压在 Java 校验上——任何绕过 Service 层的写库（脚本、运维手改）都能造出孤儿行。
- **`tb_reservation_batch` 没有防重叠的数据库约束**：同一设备使用时段不能重叠这条规则只在 `ReservationBatchServiceImpl.validatePublishInvariants:307-315` 里用一个 `count(...)` 实现，是「先查再写」；两个管理员同时对同一设备发批次时，理论上都能查到 0 条重叠。
- **`active_flag` 的语义在 DB 和 Java 各写一份**（生成列表达式 + `occupyingStatuses()`），靠注释约定保持一致，没有测试或约束把两边钉在一起。
- **`markNoShows` 外层 UPDATE 没有再判一次 `status`**（`ReservationMapper.xml:53-68`），`status='RESERVED'` 只写在内层子查询里，和其它 CAS 的写法不同。
