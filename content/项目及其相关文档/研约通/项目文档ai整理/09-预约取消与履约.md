# 一、先看结果：103 点下取消之后

这一节是本篇的「答案」，后面几节拆开讲每一步怎么发生的。

| 存储 | 取消之前 | 取消之后 |
|---|---|---|
| `tb_reservation`(…846425)`.status` | `RESERVED` | **`CANCELLED`** |
| `tb_reservation`(…846425)`.quota_released` | 0 | **1** |
| `tb_reservation`(…846425)`.update_time` | 09:00:0x | 09:05:00 |
| `tb_reservation_batch`(7)`.remaining_quota` | 0 | **1** |
| Redis `reservation:batch:quota:7` | `"0"` | **`"1"`** |
| Redis `reservation:batch:users:7` | `{101,102,103,104,105}` | **`{101,102,104,105}`** |
| HTTP | — | **`200` + `{"success":true}`** |

**名额回到了 1，103 从 users Set 里消失了。** 注意 `quota` 和 `users` 是被两条**不同**的语句改的：`quota` 由 Redis 里的 Lua 脚本 `INCR`（§六），`users` 由同一个脚本 `SREM`。

**`update_time` 为什么会被推到现在**：`tb_reservation.update_time` 的定义是 `ON UPDATE CURRENT_TIMESTAMP`（`phase7_reservation.sql:6`），而项目里没有 `MetaObjectHandler` 自动填充，实体上也没有 `@TableField(fill=…)`——两次 `UPDATE` 各自让 MySQL 自己更新这个列。

## 1.1 四个变体（同一个例子，换成不同的处境）

| 变体 | 处境 | `ReservationCancelOutcome` | HTTP |
|---|---|---|---|
| ① 就是上面这条 | 103 第一次取消自己的 …846425 | `TRANSITIONED` | `200 {"success":true}` |

# 二、`ReservationStatus` 四个状态，谁占着名额

`enums/ReservationStatus.java`

```java
public enum ReservationStatus {
    RESERVED,
    CANCELLED,
    COMPLETED,
    NO_SHOW;

    /**
     * 占用 (user_id, batch_id) 唯一键槽位的状态集合，判据必须与 tb_reservation.active_flag
     * 生成列严格一致：CASE WHEN status = 'CANCELLED' THEN NULL ELSE 1 END。
     * 因此除 CANCELLED 之外的状态都算占用 —— COMPLETED / NO_SHOW 的行仍占着槽位，
     * 该用户不能再对同一批次发起预约（与生成列拒绝插入的行为一致）。
     */
    private static final List<ReservationStatus> OCCUPYING_STATUSES =
            Collections.unmodifiableList(Arrays.asList(RESERVED, COMPLETED, NO_SHOW));

    public boolean isActive()   { return this == RESERVED; }
    public boolean isTerminal() { return this != RESERVED; }
    public static List<ReservationStatus> occupyingStatuses() { return OCCUPYING_STATUSES; }
}
```

- **`occupyingStatuses()` 是三个**：`RESERVED` / `COMPLETED` / `NO_SHOW`。**只有 `CANCELLED` 不占。**
- 它和表里那个生成列是**同一件事的两种写法**。`phase9_reservation_lifecycle.sql` 里有**两条** `ALTER TABLE`，各取关键一行：

```sql
-- 第 2-6 行那条 ALTER 里的生成列
ADD COLUMN `active_flag` tinyint GENERATED ALWAYS AS
  (CASE WHEN `status`='CANCELLED' THEN NULL ELSE 1 END) STORED COMMENT '仅约束活跃预约',
-- 第 8-10 行那条 ALTER 里的唯一键（同时 DROP 掉了旧的 `uk_user_batch`）
ADD UNIQUE KEY `uk_user_batch_active` (`user_id`,`batch_id`,`active_flag`);
```

**`active_flag` 对 `CANCELLED` 的行是 `NULL`，而 MySQL 的唯一索引不约束 `NULL`。** 所以同一用户在同一批次下可以有多行 `CANCELLED`，但最多只有一行非 `CANCELLED`。这是用生成列模拟「部分唯一索引」。

**`occupyingStatuses()` 在 Java 里只有一个用点**——`ReservationPersistenceServiceImpl.java:39-46`（06 篇讲的第二层去重）：落库前先数一遍「这个用户在这个批次下有没有占着槽位的行」。

**例子里的对应**：取消之前，103 的 …846425 是 `RESERVED` → 占着槽位，且生成列 `active_flag = 1`，唯一键 `(103, 7, 1)` 生效。取消之后 `status` 变 `CANCELLED` → 生成列自动变 `NULL` → **槽位空出来了**：103 可以重新对批次 7 发起预约（新 `reservationId`、新行，唯一键不冲突）。

**实体和 VO 里的对应字段**（`entity/Reservation.java` / `vo/ReservationVO.java`）：

```java
// Reservation.java：@TableId(value = "id", type = IdType.INPUT) ← 主键由 RedisIdWorker 生成后带进来
private Long id;  private Long userId;  private Long batchId;
private ReservationStatus status;  private Boolean quotaReleased;
private LocalDateTime createTime;  private LocalDateTime updateTime;
// 注意：实体里没有 activeFlag 字段——生成列不能写，也没映射它
```

`ReservationVO` 在此基础上多了 `equipmentName` / `laboratoryName` / `startTime` / `endTime` / `bookingStartTime` / `bookingEndTime`（三个 `LEFT JOIN` 查出来的），**`status` 和 `quotaReleased` 都在 VO 里**。所以 103 取消之后重开详情页看到的是 `status: "CANCELLED"`、`quotaReleased: true`，前端按 `statusMap` 渲染成「已取消」且不再显示取消按钮（`frontend/src/constants/statusMap.js:3-6`）。

状态图（横向是取消，纵向是另外两条路）：

```
        insert（消费者落库）
              │
              ▼
        ┌──────────┐   cancel     ┌───────────┐
        │ RESERVED │─────────────▶│ CANCELLED │  ← 唯一不占槽位的状态
        └────┬─────┘              └───────────┘
             │
             │ verify（管理员）        对账 markNoShows（08 篇）
             ▼                        （batch.end_time 已过且未核验）
        ┌───────────┐              ┌─────────┐
        │ COMPLETED │              │ NO_SHOW │
        └───────────┘              └─────────┘
          仍占槽位                    仍占槽位
```

**`COMPLETED` / `NO_SHOW` 仍占槽位**——用户在这一批次的预约已用掉，不能再约同一批次（与生成列的拒绝行为一致）。

# 四、`ReservationServiceImpl.cancel` 逐行

`service/impl/ReservationServiceImpl.java:140-176`。**这个方法没有 `@Transactional`**（整个项目只有 3 处 `@Transactional`，一处都不在 `ReservationServiceImpl` 里）——事务全在 §五 那个方法里。

## 4.1 开头两行

```java
@Override
public void cancel(Long reservationId) {
    UserDTO user = requireUser("无权取消该预约");                            // ① 未登录 → 403
    Reservation reservation = reservationMapper.selectById(reservationId);   // ② 读一次，只为拿 batchId
    ReservationCancelOutcome outcome = reservationLifecycleService.cancel(
            reservationId, user.getId(), LocalDateTime.now());               // ③ 走事务
```

- **① `requireUser`**（`ReservationServiceImpl.java:228-234`）：`UserHolder` 里没用户就抛 `ForbiddenException("无权取消该预约")` → **403**。
- **② 这一次读没有做归属判断**，它唯一的用途是第 164 行取 `batchId`。**③ 里会再查一次，并在那里校验归属。** 也就是说 `cancel` 一共查了 3 次这一行（②、③ 里查一次、CAS 失败时再查一次）。
- **`LocalDateTime.now()` 是现在这一刻**，一路传进 lifecycle，只用于和 `batch.endTime` 比（§五 5.2）。

**例子里的对应**：`user.getId() = 103`；② 读到的就是 §0.2 那一行（`RESERVED` / `quota_released = 0` / `batch_id = 7`）；③ 传进去的 `now = 2026-10-07T09:05:00`（`epoch 1791335100`）。

## 4.2 outcome 到 HTTP 的分支

```java
    if (outcome == ReservationCancelOutcome.NOT_FOUND) {
        throw new ForbiddenException("无权取消该预约");                     // ④ 403
    }
    if (outcome == ReservationCancelOutcome.NOT_CANCELLABLE) {
        throw new BadRequestException("当前状态不可取消");                   // ⑤ 400
    }
    if (outcome != ReservationCancelOutcome.TRANSITIONED) {
        // ...（见 4.3）
        return;                                                          // ⑥ 幂等返回，什么都不做
    }
```

| outcome | 这里做什么 | `WebExceptionAdvice` 映射 | 响应体 |
|---|---|---|---|
| `NOT_FOUND` | 抛 `ForbiddenException` | `WebExceptionAdvice:25-30` → 403 | `{"success":false,"errorMsg":"无权取消该预约"}` |
| `NOT_CANCELLABLE` | 抛 `BadRequestException` | `WebExceptionAdvice:18-23` → 400 | `{"success":false,"errorMsg":"当前状态不可取消"}` |
| `ALREADY_CANCELLED` | 直接 `return` | 不抛异常 → 200 | `{"success":true}` |
| `TRANSITIONED` | 往下走 ⑦⑧⑨ | 200 | `{"success":true}` |

**注意 `NOT_FOUND` 这个名字很 misleading**：它既包括「这行不存在」，也包括「这行存在但不是你的」（§五 5.1）。两种情况在代码里走的是同一个分支、回的是同一句话，**源码里没有做任何区分**。

**例子里的对应**：

- 变体①：outcome 是 `TRANSITIONED` → 三个 `if` 全不进 → 走 ⑦⑧⑨ → `200 {"success":true}`。
- 变体②：outcome 是 `ALREADY_CANCELLED` → 第 152 行 `ALREADY_CANCELLED != TRANSITIONED` 为真 → `return` → `200 {"success":true}`，**Redis 一个字节都没动**。
- 变体③：`NOT_CANCELLABLE` → 400 `{"success":false,"errorMsg":"当前状态不可取消"}`。
- 变体④（不存在 / 越权）：`NOT_FOUND` → 403 `{"success":false,"errorMsg":"无权取消该预约"}`。

## 4.3 ⑥ 后面那段注释在说什么

这是整个 `cancel` 里注释最长的一段（`ReservationServiceImpl.java:153-158`）：

```java
        // ALREADY_CANCELLED：本次调用没有发生 RESERVED→CANCELLED 的状态跃迁，幂等返回。
        // 绝不能在此路径触碰 Redis 或 quota_released：rollback 的 Lua 虽然自身幂等，
        // 但用户可能在取消 R1 之后重新预约得到 R2，此时对 R1 的重复取消会 SREM 掉
        // R2 在 Redis 中的占位标记 —— Redis 多出名额而 MySQL 仍占用 R2，既超卖又
        // 重新打开名额泄漏（再次抢名额会在落库时被唯一键拒成 DUPLICATE 并静默 ACK）。
        // 只有本事务真正完成跃迁（TRANSITIONED）才允许归还名额。
```

**拆成两句**：

- 走到这个 `if` 只剩 `ALREADY_CANCELLED`（前两个值已经被 ④⑤ 拦掉），直接返回——**「绝不能碰 Redis 或 `quota_released`」**是硬约束。
- 注释里的场景是：103 取消 R1（…846425）后**又重新预约得到 R2**（新 id，`users` 里又有了他），这时再点一次 R1 的取消，脚本第一行 `SREM users 103` 删掉的会是 **R2 的占位**——Redis 名额 +1 而 MySQL 里 R2 还 `RESERVED`，既超卖又让 103 能再抢一次。（事故细节和为什么方向必须这样，见 §七。）

前端也照这个语义写（`frontend/src/views/reservation/ReservationDetailView.vue:165-171`）：

```js
// 后端 TRANSITIONED 与 ALREADY_CANCELLED 都返回同形的 Result.ok()；重复取消是
// 静默幂等路径，后端刻意不碰 Redis 以防名额泄漏。200 不能证明本次发生了状态
// 迁移，任何成功类提示在幂等路径上都会误导，故必须重新拉取服务端最新状态。
if (result.status >= 200 && result.status < 300) {
  await loadDetail()
  return
}
```

**103 点第二次取消时，界面提示不会说「已取消」，而是静默重取一次详情**——因为 200 分不出是①还是②。

## 4.4 事务之外的补偿：Lua 回滚 + 打标记

```java
    try {
        int rollbackCode = reservationQuotaRollbackExecutor.rollback(
                reservation.getBatchId(), user.getId());                    // ⑦ Redis：SREM + INCR
        reservationMapper.update(null,
                new LambdaUpdateWrapper<Reservation>()
                        .eq(Reservation::getId, reservationId)
                        .eq(Reservation::getQuotaReleased, false)            // ⑧ CAS 条件
                        .set(Reservation::getQuotaReleased, true));          // ⑨ 打标记
        log.info("取消预约后 Redis 名额归还完成：reservationId={}，rollbackCode={}",
                reservationId, rollbackCode);
    } catch (RuntimeException e) {
        log.error("取消预约后 Redis 名额归还失败，等待定时补偿：reservationId={}，batchId={}，userId={}",
                reservationId, reservation.getBatchId(), user.getId(), e); // ⑩ 只记日志，不抛
    }
}
```

- **⑦** 调 `rollbackExecutor`（§六）。`reservation.getBatchId()` 用的是第 143 行那次快照读到的值。
- **⑧⑨** 把 `quota_released` 从 `0` 改成 `1`，等价于：

```sql
UPDATE tb_reservation
   SET quota_released = 1
 WHERE id = 645827360351847425 AND quota_released = 0
```

  **`.eq(quotaReleased, false)` 是 CAS 条件**，保证同一行不会被重复处理。
- **⑦⑧⑨ 整体都在事务之外** —— 第 ③ 行的 `@Transactional` 早就提交了。
- **⑩ catch 里不抛异常，只打日志「等待定时补偿」。** 补偿者是 `ReservationReconcileServiceImpl.releasePendingQuotas`（08 篇），它扫的正是 `status='CANCELLED' AND quota_released=0` 的行（`ReservationMapper.xml:44-51`）。
- **这里没有检查 ⑨ 的影响行数**（对账那处有 `if (updated == 1)`，`ReservationReconcileServiceImpl.java:165`），只打了 info 日志。

**例子里的对应**（变体①）：

| 语句 | 作用 |
|---|---|
| ⑦ `rollback(7, 103)` | `SREM reservation:batch:users:7 "103"` → 1；`INCR reservation:batch:quota:7` → `"1"`；返回 **1** |
| ⑧⑨ UPDATE | `quota_released` 0 → 1，影响 1 行 |
| ⑩ | 没进 catch，接口最终 `200 {"success":true}` |

# 五、`ReservationLifecycleServiceImpl.cancel` 逐行（带 `@Transactional`）

`service/impl/ReservationLifecycleServiceImpl.java:29-74`。**事务边界就在这里**：整段（CAS 跃迁 + MySQL 名额回补）在一个事务里，出方法即提交。

## 5.1 归属校验

```java
@Override
@Transactional
public ReservationCancelOutcome cancel(Long reservationId, Long userId, LocalDateTime now) {
    Reservation reservation = reservationMapper.selectById(reservationId);
    if (reservation == null || !userId.equals(reservation.getUserId())) {
        return ReservationCancelOutcome.NOT_FOUND;                       // ① 不存在 或 不是本人的
    }

    ReservationBatch batch = reservationBatchMapper.selectById(reservation.getBatchId());
    if (batch == null) {
        return ReservationCancelOutcome.NOT_FOUND;                       // ② 批次没了也当 NOT_FOUND
    }
```

**① 才是真正的越权闸门**：`userId` 是调用方从 `UserHolder` 里拿的当前登录用户，`reservation.getUserId()` 是这一行的主人，**不相等就返回 `NOT_FOUND`**。不存在和不是本人的**返回同一个值**，调用方统一转成 403。

**例子里的对应**：

| 请求 | ① 的比较 | 返回 |
|---|---|---|
| 103 取消自己的 …846425 | `103.equals(103)` → true | 不返回，继续往下 |
| 103 取消 101 的 …846423 | `103.equals(101)` → false | `NOT_FOUND` → 403「无权取消该预约」 |
| 103 传 `999` | `reservation == null` | `NOT_FOUND` → 403「无权取消该预约」 |

## 5.2 时间检查——**在数据变更之前**

```java
    if (now.isAfter(batch.getEndTime())) {
        throw new BadRequestException("预约已结束，无法取消");              // ③ 400
    }
```

- **读的是批次的 `end_time`**（使用时段结束）。
- 违反时**抛异常**而不是返回 outcome——它绕过了调用方 ④⑤⑥ 那三个分支，直接 400。所以这一条**不在 `ReservationCancelOutcome` 的四个取值里**。
- **没有任何 SQL 参与**，就是 Java 侧一次 `LocalDateTime` 比较：`now(2026-10-07 09:05) > batch.end_time(2026-10-08 16:00)`。

**例子里的对应**：

| 场景 | `now`（epoch） | `now > endTime`(1791446400) | 结果 |
|---|---|---|---|
| 变体① 09:05 取消 | 1791335100 | false | 不拦，继续走到 CAS |
| 10-08 15:00 取消（批次**已经开始了**但没结束） | 1791442800 | false | **不拦**，照样能取消 |
| 10-08 16:30 取消（批次**已结束**） | 1791448200 | true | 抛 `BadRequestException` → `400 {"success":false,"errorMsg":"预约已结束，无法取消"}` |

**取消的判据只看 `end_time`，不看 `start_time`** —— 所以「批次已开始、还没结束」这个窗口里依然能取消。

## 5.3 CAS 跃迁

```java
    int transitioned = reservationMapper.update(null,
            new LambdaUpdateWrapper<Reservation>()
                    .eq(Reservation::getId, reservationId)
                    .eq(Reservation::getUserId, userId)                        // ④ 三重条件
                    .eq(Reservation::getStatus, ReservationStatus.RESERVED)
                    .set(Reservation::getStatus, ReservationStatus.CANCELLED));
    if (transitioned == 0) {
        Reservation current = reservationMapper.selectById(reservationId);
        if (current == null || !userId.equals(current.getUserId())) {
            return ReservationCancelOutcome.NOT_FOUND;                     // ⑤
        }
        if (current.getStatus() == ReservationStatus.CANCELLED) {
            return ReservationCancelOutcome.ALREADY_CANCELLED;             // ⑥ 已经是取消态
        }
        return ReservationCancelOutcome.NOT_CANCELLABLE;                   // ⑦ COMPLETED / NO_SHOW
    }
```

等价的 SQL：

```sql
UPDATE tb_reservation
   SET status = 'CANCELLED'
 WHERE id = 645827360351847425
   AND user_id = 103
   AND status = 'RESERVED'
```

**④ 是纯 CAS，三个条件一个都不能少**：`id` 定位行、`user_id` 再兜一次归属（防「读完之后换了主人」）、`status = 'RESERVED'` 保证只从「还没终结的活跃态」出发。

**影响行数的两种含义**（这是这段代码的核心）：

| `transitioned` | 含义 | 后续 |
|---|---|---|
| **1** | 本事务真的把这一行从 `RESERVED` 推到了 `CANCELLED` | 继续走 5.4 回补名额，最后返回 `TRANSITIONED` |
| **0** | 什么都没改（行不存在 / 不是你的 / 状态已不是 `RESERVED`） | **再查一次**，用 ⑤⑥⑦ 三个分支区分原因 |

**为什么要再查一次**：`UPDATE` 只告诉你「没改到」，不告诉你为什么。再读一遍拿当前状态，才能把三种原因分开。

**例子里的对应**：

| 变体 | ④ 的三重条件 | `transitioned` | 走哪个分支 |
|---|---|---|---|
| ① 103 第一次取消 | `id=…425` ✓、`user_id=103` ✓、`status='RESERVED'` ✓ | **1** | 不进 `if`，去 5.4 |
| ② 103 再点一次 | `status='CANCELLED'` ✗ | 0 | 复查 → `current.status == CANCELLED` → **`ALREADY_CANCELLED`** |
| ③ 行已被李老师核验成 `COMPLETED` | `status='COMPLETED'` ✗ | 0 | 复查 → 既不是 `CANCELLED` → **`NOT_CANCELLABLE`** |
| ④ 103 去改 101 的行 | `user_id=101` ✗ | 0 | 复查 → `103.equals(101)` false → **`NOT_FOUND`** |

**注意 `NOT_CANCELLABLE` 是「兜底分支」**：⑤⑥ 都没命中时返回它。所以它覆盖的是「当前状态是 `COMPLETED` 或 `NO_SHOW`」——`RESERVED` 不可能到这里（那样 CAS 就会影响 1 行了）。

**③ 变体要成立的窗口很窄**：核验要求 `now >= batch.start_time`（10-08 14:00，见 §八），取消要求 `now <= end_time`（10-08 16:00）。所以「已被核验、但批次还没结束」这个窗口是 **10-08 14:00 ～ 16:00**，只有落在这里的取消才会拿到 `NOT_CANCELLABLE`。批次一过 16:00，先被 ③ 的时间检查拦成 400「预约已结束，无法取消」。

## 5.4 MySQL 侧的名额回补

```java
    int quotaRestored = reservationBatchMapper.update(null,
            new LambdaUpdateWrapper<ReservationBatch>()
                    .eq(ReservationBatch::getId, reservation.getBatchId())
                    .lt(ReservationBatch::getRemainingQuota, batch.getTotalQuota())   // ⑧ 上限保护
                    .setSql("remaining_quota = remaining_quota + 1"));
    if (quotaRestored == 0) {
        // MySQL 未回补名额（批次名额已达 totalQuota 上限，或批次行在事务内已变更），
        // 而 Redis 侧仍会 +1。方向保守（不会超卖），但会形成台账偏离，必须留痕以便对账排查。
        log.warn("取消预约后批次名额未回补：reservationId={}，batchId={}，affectedRows=0",
                reservationId, reservation.getBatchId());
    }
    return ReservationCancelOutcome.TRANSITIONED;
}
```

```sql
UPDATE tb_reservation_batch
   SET remaining_quota = remaining_quota + 1
 WHERE id = 7
   AND remaining_quota < total_quota
```

- **`.lt(remainingQuota, totalQuota)` 是上限保护**：防止回补到超过 `total_quota`。
- **影响 0 行时只打 warn，不抛异常，照样返回 `TRANSITIONED`。** 注释解释了原因：调用方（事务外）的 Redis `INCR` 照做，所以这一瞬间 **Redis 比 MySQL 多一个名额**。方向保守（名额多不会超卖），但台账会偏离，所以留痕。
- **只有 CAS 影响 1 行才会走到这里**——`transitioned == 0` 的三个分支都在上面 `return` 了。

**例子里的对应**：`batches(7).remaining_quota = 0`，`total_quota = 5`，`0 < 5` 成立 → 执行 `remaining_quota = 0 + 1 = 1`，影响 1 行 → 不进 warn 分支 → 返回 `TRANSITIONED`。

**事务到这里提交。** 提交之后，MySQL 已经是 `CANCELLED` + `remaining_quota = 1`，而 Redis 还是 `quota = "0"`、`users` 里还有 103 —— 中间隔着 §4.4 那几步。**这个「MySQL 已还、Redis 未还」的窗口方向是保守的**（用户抢不到多出来的名额），最坏情况就是靠对账补上（§九）。

# 六、`reservationRollback.lua` 逐行

`src/main/resources/reservationRollback.lua`，**8 行**（路径就在 `resources` 根下，`ReservationQuotaRollbackExecutor.java:20` 用的是 `new ClassPathResource("reservationRollback.lua")`）。

## 6.1 参数约定 —— 拿 103 那次回滚代入

包装器 `ReservationQuotaRollbackExecutor.java:35-46`：

```java
public int rollback(Long batchId, Long userId) {
    String quotaKey = RESERVATION_BATCH_QUOTA_KEY + batchId;
```

| 位置 | 是什么 | 例子里（103 取消批次 7） |
|---|---|---|
| `KEYS[1]` | quota key | `"reservation:batch:quota:7"` |
| `KEYS[2]` | users key | `"reservation:batch:users:7"` |

## 6.2 逐行

```lua
if redis.call('SREM', KEYS[2], ARGV[1]) == 0 then
    return 0
end
if redis.call('EXISTS', KEYS[1]) == 1 then
    redis.call('INCR', KEYS[1])
    return 1
end
return 2
```

**第 1-3 行：先试着把人从 users Set 里删掉**

`SREM KEYS[2] ARGV[1]` 的返回值是「实际删掉了几个元素」（0 或 1）。

- 返回 **0**（他本来就不在 Set 里）→ `return 0`：**这一支一条写命令都没执行成功，配额一个字节都没动。** 语义是「他本来就没占着名额」——重复补偿、或者压根没占用过。
- 返回 **1**（确实删掉了他）→ 说明**他确实占着一个名额**，于是继续往下看名额键还在不在。

**先把 `SREM` 放在最前面，是「判断有没有占名额」的手段**：`SREM` 本身就是原子的「删并告诉我删掉了没」，一步顶两步。

**第 4-7 行：配额键还在吗**

- `EXISTS KEYS[1] == 1` → `INCR KEYS[1]` → `return 1`：**归还一个名额**。
- `EXISTS KEYS[1] == 0` → 跳出 `if`，`return 2`：**只清理了用户标记，不归还名额**。语义是「他确实占着，但名额键已经没了」——这时 `INCR` 会把一个本该不存在的 key 重新创建成脏数据，所以宁可不还。

**第 8 行 `return 2`** 是 fall-through 的兜底，没有自己的条件。

## 6.3 返回值 → 三种情况

`ReservationQuotaRollbackExecutor.java:30-34` 的 javadoc 逐字是：

```java
/**
 * 返回 0 表示用户本来就未占用名额（重复补偿或从未占用），名额不变；
 * 返回 1 表示用户确实占用名额且名额键存在，已归还一个名额；
 * 返回 2 表示用户确实占用名额但名额键已不存在，仅清理用户标记、不归还名额。
 */
```

| 返回值 | 条件 | 例子里什么时候出现 |
|---|---|---|
| **0** | `SREM` 返回 0 —— 他不在 users Set 里 | 这行已经被补偿过一次（脚本又跑了一遍），或他在 Redis 里从头到尾都没占过名额 |
| **1** | `SREM` 返回 1 且 `EXISTS quota` = 1 | **变体①的正常路径**：`SREM users:7 "103"` → 1，`EXISTS quota:7` → 1，`INCR "0"→"1"` |
| **2** | `SREM` 返回 1 但 `EXISTS quota` = 0 | 见下面这段 |

**关于 2**：源码里**没有一条稳定的业务路径**会落进这一支。看着最像的是「批次被 `close`/`cancel` 之后来取消」，但那两条路是**两个 key 一起删**的（`ReservationBatchServiceImpl.java:172`、`:192` 都是 `delete(Arrays.asList(quotaKey(id), usersKey(id)))`）——users key 没了，`SREM` 先返回 0，走的是 `return 0`。

真正可能落进 2 的只有**两个 key 的过期时刻之间的缝隙**：quota 的 TTL 在 `publish` 时设（`ReservationBatchServiceImpl.java:122-132`），users 的 TTL 在每次抢成功时重设（05 篇 §3.6），**两者的目标时刻都是 `endTime + 24h`，但 Redis 回收过期 key 不是同一毫秒完成的**。在 users 还没被回收、quota 已经没了的那个瞬间调 `rollback`，就会 `SREM` 成功 + `EXISTS` 为 0 → 返回 2。

Java 侧的校验（第 42-44 行）只允许 0/1/2 三个值，其他（包括 `null`）一律 `throw new IllegalStateException`。

**例子里的对应** —— 103 那次等价的 `redis-cli` 写法：

```
EVAL "$(cat reservationRollback.lua)" 2 \
     reservation:batch:quota:7 reservation:batch:users:7 \
     103
      ↑
    userId

执行过程：
  SREM  reservation:batch:users:7  "103"   → 1
  EXISTS reservation:batch:quota:7         → 1
  INCR  reservation:batch:quota:7          → "0" 变 "1"
  return 1
```

**结果**：

```
reservation:batch:quota:7   "0" → "1"
reservation:batch:users:7   {101,102,103,104,105} → {101,102,104,105}
```

**`quota:7` 的 TTL 没有被重设** —— 脚本里没有 `EXPIRE`，它还是 `publish` 时设的那个 `endTime + 24h − now`（05 篇：198000 秒）。**只有 `users` 的 TTL 会被 05 篇那个 `reservation.lua` 在抢成功时重设**，回滚这边一次都不碰 TTL。

# 七、为什么这里必须「先跃迁、再补偿」

**这是本篇最重要的一段。** 同一个项目里，**补偿和终结的先后顺序有两种写法，方向正好相反**，而且两个方向都是对的——因为它们在补的东西不一样。

## 7.1 两条路的顺序，逐行对照

**取消这条路：先跃迁，后补偿**

| 顺序 | 语句 | `文件:行号` |
|---|---|---|
| 1 | `reservationLifecycleService.cancel(...)` —— 走 `@Transactional`，里面执行 CAS 跃迁 | `ReservationServiceImpl.java:144-145` |
| 1' | `UPDATE tb_reservation SET status='CANCELLED' WHERE … AND status='RESERVED'` | `ReservationLifecycleServiceImpl.java:45-50` |
| 2 | **准入门**：`if (outcome != TRANSITIONED) return;` | `ReservationServiceImpl.java:152-160` |
| 3 | `reservationQuotaRollbackExecutor.rollback(batchId, userId)` —— Redis 归还名额 | `ReservationServiceImpl.java:163-164` |
| 4 | `UPDATE tb_reservation SET quota_released=1 WHERE … AND quota_released=0` | `ReservationServiceImpl.java:165-169` |

**其它两条路：先补偿，后终结**

| 路径 | 先补偿 | 后宣告终结 | `文件:行号` |
|---|---|---|---|
| 对账（消息没投出去 / 查不到预约行） | `rollbackExecutor.rollback(request.getBatchId(), request.getUserId())` | `casStatusWithFailReason(… COMPENSATED …)` | `ReservationReconcileServiceImpl.java:125` → `:126-130` |
| 投递确定失败（`DEFINITELY_NOT_DELIVERED`） | `reservationQuotaRollbackExecutor.rollback(batchId, userId)` | `casStatusWithFailReason(… COMPENSATED …)` | `ReservationServiceImpl.java:289` → `:293-298` |

对账那处还专门留了注释（`ReservationReconcileServiceImpl.java:124`）：

```java
// 必须先补偿再推进终态：补偿失败时保留非终态，下一轮才能继续重试。
```

## 7.2 为什么取消这条路必须反过来

**理由一：Redis 的补偿不回滚，MySQL 的事务会回滚。**

`ReservationLifecycleServiceImpl.cancel` 是 `@Transactional` 的（第 30 行）。如果补偿写在它**前面**，而且这段事务后来因为任何原因回滚（比如 5.4 那条 `UPDATE tb_reservation_batch` 抛异常，或者连接断开），那结果就是：

- MySQL：状态**还是** `RESERVED`，`remaining_quota` **没变** → 这次取消等于没发生；
- Redis：`SREM` + `INCR` 已经执行了，**且不会跟着回滚** → 名额凭空多出来一个，103 也从 users Set 里消失了。

**用户手上那张 `RESERVED` 的预约还在，名额却已经还回去了。** 他再抢一次（`SISMEMBER` 已经不认他）就又多占一个。先跃迁就没有这个问题：CAS 成功是「这一步真的做了」的证据，之后才谈得上补偿。

**理由二：重复取消会 `SREM` 掉同一个人下一次预约的占位。**

Lua 脚本是幂等的——但它幂等的方式是「**看 `SREM` 删掉了没有**」，而不是「看这是第几次调用」。所以：

```
103 取消 R1(…425)  → TRANSITIONED，SREM users 103，quota "0"→"1"
103 重新预约批次 7  → 新行 R2(…999)，reservation.lua SADD users 103，quota "1"→"0"
103 又点了一次 R1 的取消
```

如果这次也去调 `rollback`：`SREM users 103` **成功删除**（删的是 R2 的占位）→ `EXISTS quota` = 1 → `INCR` → **`quota` 变成 `"1"`**。

而 MySQL 侧 R2 还是 `RESERVED`、`remaining_quota` 还是 0。于是：

| | MySQL | Redis |
|---|---|---|
| 名额 | 0 剩余 | 1 剩余 |
| 103 | R2 占着槽位 | 不在 users Set 里 |

**Redis 比 MySQL 多一个名额，而且 103 自己也不在去重集合里了。** 接下来无论谁来抢这个多出来的名额，都会在落库那一步被挡（`ReservationPersistenceServiceImpl`）：

- **103 自己抢** → `:39-46` 第二层去重命中 R2（`occupyingStatuses` 含 `RESERVED`）→ `ReservationPersistResult.DUPLICATE`；
- **别人抢** → `:49-53` 扣名额那一步要求 `remaining_quota > 0`，而它是 0 → `ReservationPersistResult.QUOTA_CONFLICT`。

两种结果都不会落库，但 Redis 侧的名额已经被减掉了——这行的账就歪了（06 篇的死信与 08 篇的对账要处理它）。

所以调用方在 `ReservationServiceImpl.java:152-160` 把那道门关死：**只有本事务真的完成了 `RESERVED→CANCELLED` 跃迁，才允许动 Redis。** `ALREADY_CANCELLED` 这条路上，「什么都不做」本身就是正确行为。

**两种顺序为什么都对**：对账和投递失败那两条路上，被补偿的是**一件已经确定不会成立的事**（消息没投出去、MySQL 里没有这行），补偿的幂等性由「`SREM` 删没删到」保证，重试安全；所以「先补偿」可以把「补偿没做完」的标记留在非终态的账本上，让下一轮继续重试。而取消这条路上，状态跃迁**本身就是那件事**——没跃迁就说明这次调用没有消费任何名额，也就不该还。

# 八、核验与爽约：另外两个终态是谁推进的

`ReservationStatus` 里的 `COMPLETED` / `NO_SHOW` 在本篇正文之外，但**两条都有真实入口**，不是「定义了没人调」。

## 8.1 `COMPLETED` —— 管理员核验

入口是接口：`POST /reservation/{id}/verify`，带 `@RequireRole(UserRole.LAB_ADMIN)`（`ReservationController.java:56-61`）。

`ReservationServiceImpl.verify`（`ReservationServiceImpl.java:178-195`）做五层归属校验，**全部抛 `ForbiddenException`（403）**：

| 层 | 校验 | 文件:行号 |
|---|---|---|
| ① | `requireUser("无权核验该预约")` —— 已登录 | `:180` |
| ② | `selectById(reservationId) != null` —— 预约存在 | `:181-184` |
| ③ | `getById(batchId) != null` —— 批次存在 | `:185-188` |
| ④ | `getById(equipmentId) != null` —— 设备存在 | `:189-192` |
| ⑤ | `laboratoryService.assertManageable(laboratoryId)` —— **这个实验室归我管** | `:193` |

**②③④ 三个「不存在」也统一报 403 而不是 404**，和 02 篇里 `assertEquipmentManageable` 的处理一致。

**⑤ 是真正的权限判定**：预约 → 批次 → 设备 → 实验室，比 `admin_user_id`（01 篇）。**例子里的对应**：批次 7 挂在设备 3、实验室 2 下，管理员是李老师（uid 2）——只有他能核验；王老师（uid 3）打这个接口会在 ⑤ 被 `assertManageable` 拦成 403。

`ReservationLifecycleServiceImpl.complete`（`:76-112`）的时间条件和取消**正好相反**：

| 操作 | 读哪个字段 | 拒绝条件 | 违反时 |
|---|---|---|---|
| 取消 | `batch.endTime` | `now > endTime` | `400 预约已结束，无法取消` |
| 核验 | `batch.startTime` | `now < startTime` | `400 预约尚未开始，无法核验` |

也就是说，**核验只能在 `[startTime, endTime]` 这个使用时段里做**（例子：2026-10-08 14:00 ～ 16:00）；取消必须在 `endTime` 之前。

核验的 CAS 是 `WHERE id=? AND status='RESERVED'`（**没有 `user_id`**，因为操作者是管理员不是本人），`complete` 返回的 `boolean` 在 `ReservationServiceImpl.java:194` **没有被接收**，HTTP 一律 200。

**核验不动名额**：没有 `remaining_quota` 的加减，也没有 `rollback`。

## 8.2 `NO_SHOW` —— 对账任务，没有接口

`NO_SHOW` **没有任何接口能触发**，唯一的调用者是定时对账（08 篇）：

- 调度：`ReservationReconcileServiceImpl.scheduledReconcile`，`@Scheduled(fixedDelayString = "${yanyuetong.reservation.reconcile-interval-ms:300000}")`（`:57-59`，默认 5 分钟一轮），第 84 行调 `markNoShows`；
- SQL（`ReservationMapper.xml:53-68`）的判据就三条：

```sql
UPDATE tb_reservation SET status = 'NO_SHOW'
WHERE id IN ( SELECT r.id
              FROM tb_reservation r JOIN tb_reservation_batch b ON r.batch_id = b.id
              WHERE r.status = 'RESERVED'           -- 还是活跃态
                AND b.end_time < #{now}             -- 使用时段已过
                AND b.status <> 'CANCELLED'         -- 批次本身没被取消
              LIMIT #{limit} )
```

> 这三行在 XML 里写成 `&lt;` / `&lt;&gt;`（`ReservationMapper.xml:63-64`），是 XML 的实体转义，对应的 SQL 就是上面的 `<` / `<>`。

**爽约不还名额、也不改 `quota_released`**（保持 0）。注意这让 `releasePendingQuotaReleases` 的筛选条件（`status='CANCELLED' AND quota_released=0`，`ReservationMapper.xml:44-51`）不会误捡到爽约行——因为 `status` 已经变成 `NO_SHOW` 了。

**例子里的对应**：如果 103 既没取消、10-08 16:00 过后也没人来核验，那么下一轮对账（10-08 16:05 左右）会把 …846425 置成 `NO_SHOW`；103 仍然占着 `(103, 7)` 的槽位，不能再约批次 7。

# 九、当前实现的几条边界

- **`ReservationServiceImpl.cancel` 没有 `@Transactional`**（已核实：全项目只有 3 处 `@Transactional`——`ReservationLifecycleServiceImpl` 两处、`ReservationPersistenceServiceImpl` 一处，`ReservationServiceImpl` 一处都没有）。所以「MySQL 跃迁」和「Redis 归还 + `quota_released` 打标记」分属两个事务边界：中间那一小段 MySQL 已还、Redis 未还（方向保守，不会超卖）。而且 4.4 的 catch **只记日志不抛**，`200` 不能证明 Redis 真的还成功了，兜底靠 `releasePendingQuotas`（08 篇）。
- **`ReservationServiceImpl.java:143` 那次读只在 `:164` 用了 `batchId`，没有任何空值/归属判断。** 如果这一读拿到 `null`（消费者还没落库），而 `ReservationLifecycleServiceImpl.java:32` 那次读恰好拿到非 `null` 的行（insert 刚好提交），`outcome` 会是 `TRANSITIONED`，紧接着 `:164` 的 `reservation.getBatchId()` 会 NPE；更麻烦的是 `:173` 的日志参数里又写了一次 `reservation.getBatchId()`，**在 catch 块里再抛一次 NPE**，`cancel` 直接冒到 `WebExceptionAdvice.handleRuntimeException` → `500 {"success":false,"errorMsg":"服务器异常"}`。窗口极窄（两次读之间），但源码里没有防它。
- **取消和异步落库撞在一起的常见形态是 403**：`submit` 返回 200 之后消费者才落库，用户在这个间隙点取消，两次 `selectById` 都是 `null` → `NOT_FOUND` → `403 无权取消该预约`。此时 Redis 的 `users` 里已经**有**他（05 篇的 `SADD` 在投递消息之前），MySQL 里却还没有行——所以此时名额是「Redis 占着、MySQL 无行」，取消被拒而不是静默失败，几秒后重试即可。
- **取消的下界只看 `batch.endTime`，不看 `startTime`**：批次一旦开始使用（10-08 14:00 之后）只要还没结束就仍可取消，`remaining_quota` 照样回补。但发布时有一条不变式——`booking_end_time` 不能晚于 `start_time`（`ReservationBatchServiceImpl.java:297-299`）——所以能取消的时刻必然已经过了预约窗口，**回补出来的这个名额谁也抢不到**（`remaining_quota` 的回补对此刻已经没有实际意义，只是为了让台账自洽）。

## 10.2 `ReservationCancelOutcome` 四个取值

| outcome | 返回条件（`ReservationLifecycleServiceImpl.cancel`） | 调用方动作 | HTTP | 响应体 |
|---|---|---|---|---|
| `TRANSITIONED` | `:45-50` CAS 影响 1 行 | `:163-169` 调 `rollback` + `SET quota_released=1` | 200 | `{"success":true}` |
| `ALREADY_CANCELLED` | `:51-58` CAS 影响 0 行，复查后 `status == CANCELLED` | `:152-160` **直接 return，不碰 Redis** | 200 | `{"success":true}` |
| `NOT_CANCELLABLE` | `:51-59` CAS 影响 0 行，复查后是 `COMPLETED` / `NO_SHOW` | `:149-151` 抛 `BadRequestException` | 400 | `{"success":false,"errorMsg":"当前状态不可取消"}` |
| `NOT_FOUND` | `:32-35` 行不存在或 `user_id` 不是当前用户；`:38-40` 批次不存在；`:53-55` CAS 后复查行没了/换主人 | `:146-148` 抛 `ForbiddenException` | 403 | `{"success":false,"errorMsg":"无权取消该预约"}` |

**不在 outcome 里的那条**：`:41-43` `now.isAfter(batch.getEndTime())` → 抛 `BadRequestException("预约已结束，无法取消")` → 400。

**例子里四个变体各命中哪个**：①第一次取消 → `TRANSITIONED`；②再点一次 → `ALREADY_CANCELLED`；③取消已被核验成 `COMPLETED` 的行 → `NOT_CANCELLABLE`；④取消不存在的 id、或 103 取消 101 的 `…846423` → `NOT_FOUND`（同一个响应体）。另有：批次已结束后来取消 → 400「预约已结束，无法取消」。
