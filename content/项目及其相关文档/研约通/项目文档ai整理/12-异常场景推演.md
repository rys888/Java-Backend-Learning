# 12 · 异常场景推演（20 个）

> **只讲代码在做什么。** 前十一篇讲正常流程，本篇把每一个环节**故意打断**，看系统落到什么状态。
>
> 每个场景固定六段：**发生了什么 → 哪个机制处理 → 最终 Redis → 最终 MySQL → 最终 Request → 是否需要人工处理**。
> 「最终」三段一律写成**具体值**：key 名 + 值、表名 + 行的字段值、账本 `status` 与 `fail_reason` 的取值。
>
> 凡是当前代码没解决的，一律写「当前项目边界」，不替项目编造能力。

## 阅读前（二）：三个必须记住的事实

| # | 事实 | 出处 |
|---|---|---|
| A | **账本 `tb_reservation_request` 在扣 Redis 之前就已落库**，所以「Redis 已扣、MySQL 没落库」永远是一条**能被扫描到的持久化记录** | `ReservationServiceImpl:108-115`、[07 篇](07-预约请求状态机与最终一致性.md) |
| B | **`tb_reservation.id` 与账本 `request_id` 同源同值**，所以「MySQL 有没有这一行」就是「这笔请求成没成」的判据 | `ReservationPersistenceServiceImpl:29-38`、[08 篇](08-对账与自愈.md) |
| C | **对账每 5 分钟扫一次「超过 10 分钟仍未终结」的账本行**，收敛到 `CONFIRMED` 或 `COMPENSATED` | `ReservationReconcileServiceImpl:57-59`、`:101-103` |

## 阅读前（三）：怎么读这 20 个场景

**这 20 个场景是 20 个互相独立的「把某一环故意弄坏」推演，不是同一条时间线上真的发生了 20 件事。** 所以：同一个人在好几个场景里当主角是正常的；每个场景开头都写清**谁、在什么时刻、做什么动作**，正文数值只在这个场景内部自洽；与 06/07/08/09/10 篇有出入的地方一律标注是**变体**——主干事实（102 成功、103 取消）以那几篇为准。

# 第一组：正常与乐观路径

## 场景 1：全链路正常

**谁、在什么时刻、做什么** 学生 **102**，**2026-10-07 09:00:00**，`POST /reservation`，请求体 `{"batchId": 7}`。他是第 2 个到 Lua 的。

**发生了什么** 无任何异常。

**哪个机制处理** 正常路径，没有补偿。关键的一步是抢名额，`reservation.lua` 全文 27 行：

```lua
if redis.call('EXISTS', KEYS[1]) == 0 then return 1 end                  -- :1-3
-- 窗口判定 :5-13（now < bookingStart → 4；now > bookingEnd → 5）
local quota = redis.call('GET', KEYS[1])                                 -- :15
if not quota or tonumber(quota) <= 0 then return 2 end                   -- :16-18
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then return 3 end      -- :20-22
redis.call('DECR', KEYS[1])                                              -- :24
redis.call('SADD', KEYS[2], ARGV[1])                                     -- :25
redis.call('EXPIRE', KEYS[2], ARGV[5])                                   -- :26
return 0                                                                 -- :27
```

- `:1` `EXISTS quota:7` = 1 → 不返回 1；`:8` `1791334800 < 1791334800` 为假；`:11` `1791334800 > 1791367200` 为假；
- `:15` `GET reservation:batch:quota:7` → `"4"`（101 刚扣过一次）；`:16` `tonumber("4") <= 0` 为假；
- `:20` `SISMEMBER reservation:batch:users:7 "102"` → 0（还没抢过）；
- `:24-26` 三条命令在**同一个脚本里原子执行**：名额 −1、userId 进 Set、重设 Set 的 TTL；`:27` 返回 0。

Java 侧的调用与后续（`ReservationServiceImpl`）：

| 行 | 动作 |
|---|---|
| `:81-107` | 七项前置检查（`batchId` 非空 / 已登录 / 批次存在且 `PUBLISHED` / 设备存在且 `AVAILABLE` 且 `bookingEnabled` / `now` 在窗口内） |
| `:108` | `redisIdWorker.nextId("reservation")` → `645827360351847424` |
| `:110` | `createPreAccepted(...)` → 往账本插一行 `PRE_ACCEPTED`（`ReservationRequestServiceImpl:24-31`） |
| `:116` | `tryAcquire(...)` → 上面那次 Lua → `SUCCESS` |
| `:136` | `publishReservationMessage(...)` → broker `ACKED` → `markPublishedWithRetry` 把账本 CAS 成 `PUBLISHED`（`:282-285`、`:331-360`）；消费者再 `persist` 落库（`ReservationMessageConsumer:59`、`:142`）并 `markConfirmedSafely`（`:99-112`）CAS 成 `CONFIRMED` |

**最终 Redis** `reservation:batch:quota:7` `"4" → "3"`（`:24` `DECR`）；`reservation:batch:users:7` `{101} → {101,102}`（`:25` `SADD`，TTL 被 `:26` 重设成 198000）；`icr:reservation:2026:10:07` `"1024"`（`RedisIdWorker` 的 `INCR`，用来拼 id）。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | 1 行：`id=645827360351847424`、`user_id=102`、`batch_id=7`、`status=RESERVED`、`quota_released=0`、`create_time=2026-10-07 09:00:00` |
| `tb_reservation_batch`(7) | `remaining_quota` **4 → 3**（`ReservationPersistenceServiceImpl:49-53` 的条件扣减） |
| `tb_reservation_request` | `request_id=645827360351847424 / 102 / 7 / CONFIRMED / fail_reason=NULL` |

**最终 Request** `645827360351847424` 那行 `status = CONFIRMED`（终态）。

**是否人工** 不需要。HTTP `200` + `645827360351847424`。

> 账本被改的顺序可能是 `PRE_ACCEPTED → PUBLISHED → CONFIRMED`，也可能跳过 `PUBLISHED` 直接到 `CONFIRMED`（消费比 `markPublishedWithRetry` 快时）。`markPublishedWithRetry:347-354` 专门处理这个先后竞争：重试耗尽时发现账本已是终态就打一条 `log.info` 返回，不当故障。

## 场景 2：★ Redis 扣名额后应用宕机

**谁、在什么时刻、做什么** 学生 **105**，09:00:00 提交（第 5 个到 Lua）；进程在 T4 被 `kill -9`。

**这是「账本为什么必须写在扣 Redis 之前」的唯一理由。**

**发生了什么**

```
T1  生成 reservationId = 645827360351847427
T2  写账本 PRE_ACCEPTED        ✅ 已提交（独立事务，ReservationServiceImpl:110）
T3  Lua 执行完 DECR + SADD     ✅ Redis 已扣（quota:7 "1"→"0"，users:7 加进 105）
T4  进程被 kill -9             ❌ prepare 好的消息从未发出
```

**哪个机制处理** 宕机现场**没有任何机制**（进程都没了）。处理它的是**重启之后的对账**，`ReservationReconcileServiceImpl.reconcile`：

```java
LocalDateTime before = LocalDateTime.now().minus(reconcileThresholdMs, ChronoUnit.MILLIS); // :101-102
List<ReservationRequest> staleRequests = reservationRequestService.listStale(before, limit); // :103
...
if (reservationMapper.selectById(request.getRequestId()) != null) { ... continue; }          // :111
// 必须先补偿再推进终态：补偿失败时保留非终态，下一轮才能继续重试。                      // :124
rollbackExecutor.rollback(request.getBatchId(), request.getUserId());                        // :125
boolean updated = reservationRequestService.casStatusWithFailReason(                          // :126
        request.getRequestId(), ReservationRequestStatus.COMPENSATED,
        NO_RESERVATION_FAILURE_REASON, NON_TERMINAL_STATUSES);                               // :126-130
```

- `:101-102` `before = now − 600000ms`（10 分钟，`application.yaml:52`），所以 105 那行要等到 09:10 之后才够「陈旧」；
- `:103` `listStale` 的条件是 `status IN (PRE_ACCEPTED, PUBLISHED, UNKNOWN) AND update_time < before`（`ReservationRequestServiceImpl:79-86`）——105 那行 `update_time` 停在 T2，命中；
- `:111` `selectById(645827360351847427)` 返回 `null` → 走补偿分支（**如果 Redis 先扣、账本后写，这一句查不到任何东西，对账无从下手，这一格名额永久泄漏**）；
- `:125` 调用 `reservationRollback.lua`：`:1-3` 先 `SREM users:7 "105"`，返回 **1**（105 确实在集合里，不早退）；`:4` `EXISTS quota:7` = 1 → `:5` `INCR` 把 `"0"` 还原成 `"1"` → 返回 1；
- `:126-130` 先补偿成功后，才用 CAS 把账本推到 `COMPENSATED` 并写 `fail_reason`。

**最终 Redis** `reservation:batch:quota:7` `"1" → "0"`（Lua `DECR`）`→ "1"`（对账 `INCR` 还原）；`reservation:batch:users:7` `{101,102,103,104} → {101,…,105} → {101,102,103,104}`（105 被 `SREM`）。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | **没有** `id=645827360351847427` 这一行（消费者从未收到消息） |
| `tb_reservation_batch`(7) | `remaining_quota = 1`——101～104 四条落库各扣 1（`5 − 4 = 1`），**未被改动** |
| `tb_reservation_request` | `645827360351847427 / 105 / 7 / COMPENSATED / RECONCILE_NO_RESERVATION` |

**最终 Request** `COMPENSATED`（`RECONCILE_NO_RESERVATION` 来自 `ReservationReconcileServiceImpl:30`）。

**是否人工** 不需要。用户视角：请求无响应，重新提交即可（名额已恢复成 `"1"`）。

## 场景 14：用户同时提交两个相同预约

**谁、在什么时刻、做什么** 学生 **101**，09:00:00 手快点了两次，两个 `POST /reservation` 都带 `{"batchId": 7}`。

**发生了什么** 双击 / 前端重试 / 网络重发，两个请求几乎同时到达。

**哪个机制处理** 两个请求拿到**两个不同的 `reservationId`**（`…846423` 和 …846429，`INCR` 递增），所以它们不是同一笔请求。拦截在 Redis 的**去重集合**：

```lua
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then   -- reservation.lua:20
    return 3                                             -- :21  DUPLICATE
end
```

`:20` 问的是「101 已经在 `reservation:batch:users:7` 里了吗」。`SISMEMBER`、`DECR`（`:24`）、`SADD`（`:25`）在**同一脚本内原子执行**，两个请求必然一先一后：

| 请求 | Lua 停在 | 返回 | 之后 |
|---|---|---|---|
| 先到的（`…846423`） | `:27` | **0** | 正常走完，账本 `CONFIRMED` |
| 后到的（`…846429`） | `:21` | **3** | 走 `ReservationServiceImpl:117-135`：CAS `{PRE_ACCEPTED} → COMPENSATED` + `fail_reason = "DUPLICATE"`，然后抛 `BadRequestException(resultCode.getMessage())` |

`fail_reason` 写的是**枚举名**（`ReservationResultCode:12` 的 `DUPLICATE`），不是中文；中文（`"你已预约过该批次"`）只用于回给前端。

**最终 Redis** `reservation:batch:quota:7` `"5" → "4"`（只被 `DECR` 一次）；`reservation:batch:users:7` `不存在 → {101}`（只被 `SADD` 一次）。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | 1 行：`id=645827360351847423 / 101 / 7 / RESERVED / quota_released=0` |
| `tb_reservation_batch`(7) | `remaining_quota` **5 → 4** |
| `tb_reservation_request` | **2 行**：`…846423 / 101 / 7 / CONFIRMED / NULL` 和 `…846429 / 101 / 7 / COMPENSATED / DUPLICATE` |

**最终 Request** 一条 `CONFIRMED`，一条 `COMPENSATED`。

**是否人工** 不需要。前端收到一次 `200` + `645827360351847423`，一次 `400` + `你已预约过该批次`。

> 拆成 `SISMEMBER` / `DECR` / `SADD` 三条命令的话，两个请求可能**都**通过检查再各自 `DECR` → 名额扣两次、只落一条预约 → 泄漏 + 超订。这是必须用 Lua 的直接理由（05 篇 §3.6）。

## 场景 15：多人同时抢 5 个名额

**谁、在什么时刻、做什么** 学生 **101～106** 六个人都在 09:00:00 点「预约」。下面用这六个人算具体数；**把参与者换成 20 个人，走的是同一条 Lua，结果同构：5 个成功、其余全部 `SOLD_OUT`**。

**发生了什么** 并发提交，批次 7 只有 `total_quota = 5`。

**哪个机制处理** 四层防线：

| 层 | 机制 | 作用 |
|---|---|---|
| ① | `reservation.lua` 原子跑完 `EXISTS → 窗口 → GET → SISMEMBER → DECR → SADD` | **恰好 5 个**返回 0，其余返回 2 |
| ② | `lock:reservation:{userId}`（Redisson，消费端 `ReservationMessageConsumer:129-131`） | 串行化**同一用户**的消息（本场景不涉及） |
| ③ | `ReservationPersistenceServiceImpl:49-53` 的 `.gt(remainingQuota, 0)` 条件扣减 | MySQL 第二道闸，防 Redis 计数偏离 |
| ④ | `uk_user_batch_active` 唯一索引 | 兜底防重复 |

第 ① 层的判定顺序也是**返回码的顺序**（05 篇 §3.7）：

```
EXISTS quota?      no  → 1 BATCH_NOT_OPEN
now < bookStart?   yes → 4 BOOKING_NOT_STARTED
now > bookEnd?     yes → 5 BOOKING_EXPIRED
quota <= 0?        yes → 2 SOLD_OUT          ← 106 停在这里
SISMEMBER users?   yes → 3 DUPLICATE
否则：DECR + SADD + EXPIRE → 0 SUCCESS       ← 101~105 走完
```

**最终 Redis** `reservation:batch:quota:7` `"5" → "4" → "3" → "2" → "1" → "0"`（106 那次没 `DECR`）；`reservation:batch:users:7` `{} → {101} → {101,102} → … → {101,…,105}`。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | **5 行**：`…846423~…846427`，`user_id` 分别 101～105，全部 `RESERVED`、`quota_released=0` |
| `tb_reservation_batch`(7) | `remaining_quota` **5 → 0** |
| `tb_reservation_request` | **6 行**：5 行 `CONFIRMED` + `645827360351847428 / 106 / 7 / COMPENSATED / SOLD_OUT` |

**最终 Request** 5 条 `CONFIRMED`、1 条 `COMPENSATED`。

**是否人工** 不需要。5 个人拿到 `200`，106 拿到 `400` + `名额已约满`。

**当前项目边界**：**没有做过压测，没有容量数据**，「能扛多少并发」给不出数字。能说清的是瓶颈位置——每个预约请求要打一次 MySQL 写账本、一次 Redis Lua、一次等 5 秒超时的 MQ confirm（`ReservationServiceImpl:256`），响应时间主要花在最后一项上。

## 场景 19：两个服务实例同时执行对账

**谁、在什么时刻、做什么** 部署了 2 个实例，09:15 两边 `@Scheduled` 同时触发；两边都扫到了学生 **105** 卡在 `PRE_ACCEPTED` 的那行 `645827360351847427`。

**发生了什么** 两个实例跑同一批陈旧账本行。

**哪个机制处理** 两层，职责分离：

```java
RLock lock = redissonClient.getLock(RedisConstants.LOCK_RESERVATION_RECONCILE_KEY);  // :61
locked = lock.tryLock(0, TimeUnit.MILLISECONDS);                                     // :64
if (!locked) { log.debug("预约对账未获取到分布式锁，跳过本轮"); return; }              // :69-72
```

`tryLock(0, MS)` 的等待时间是 **0**——抢不到锁的实例**直接跳过整轮，不等待**。方法注释把定位写死了：

> `定时调度薄壳：分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证。`（`:55`）

第二层是**即使锁完全失效**也成立的兜底：CAS 用 `update(...) == 1`（`ReservationRequestServiceImpl:44-47`），`rollback` 用 `reservationRollback.lua:1` 的 `SREM` 返回值当令牌。锁失效、两边都扫了 105 那行时：

| 谁先 | `SREM users:7 "105"` | `INCR quota:7` | CAS | 结果 |
|---|---|---|---|---|
| 实例 A | 返回 **1** | `"0"` → `"1"` | 影响 **1** 行 | `compensated++` |
| 实例 B | 返回 **0** | **不执行** | 影响 **0** 行 | `skipped++` |

**最终 Redis** `reservation:batch:quota:7` `"0" → "1"`（恰好加一次，第二个实例的 `SREM` 返回 0 就早退了）；`reservation:batch:users:7` `{101,…,105} → {101,102,103,104}`。

**最终 MySQL** `tb_reservation_request` 那行恰好迁移**一次**到 `COMPENSATED / RECONCILE_NO_RESERVATION`；另一实例的 CAS 返回 0，只体现在 `skipped` 计数里（`ReservationReconcileServiceImpl:79-81` 的日志）。

**最终 Request** 与单实例完全相同：`COMPENSATED`。

**是否人工** 不需要。

**当前项目边界**
- 没有指标统计「跳过轮次」，从监控上看不出锁是否被某个实例长期霸占（只有一条 `log.debug`）。
- 看门狗在 `reconcile` 线程存活期间**无限续期**。若某实例卡在一次没有超时的 DB 调用上，**锁永不释放 → 全集群对账静默停摆**，且无告警。

# 第二组：生产者侧故障（投递阶段）

> 这一组的核心是 `ReservationServiceImpl.publishReservationMessage` 的**三态模型**（`:248-280`、`:362-366`）：`ACKED` / `DEFINITELY_NOT_DELIVERED` / `UNKNOWN`。
> **只有「确定没投出去」才归还名额；「不确定」必须保持占用。**
>
> 场景 3、4、5 走的是**同一段代码**，只是 `outcome` 被不同分支设成 `DEFINITELY_NOT_DELIVERED`、`failureReason` 不同。所以场景 3 写全六段，4、5 只列差异。

## 场景 3：RabbitMQ 完全不可达

**谁、在什么时刻、做什么** 学生 **101**（第 1 个到 Lua），09:00:00 提交。broker 挂了 / 端口不通。

**发生了什么** `convertAndSend` 直接抛 `AmqpConnectException`。

**哪个机制处理**

```java
} catch (AmqpConnectException e) {                      // ReservationServiceImpl:266
    log.error("预约消息连接 RabbitMQ 失败：...", ...);      // :267-268
    outcome = PublishOutcome.DEFINITELY_NOT_DELIVERED;   // :269
    failureReason = "AMQP_CONNECT_FAILED";               // :270
}
```

落到 `DEFINITELY_NOT_DELIVERED` 分支（`:287-312`），**顺序不能反**：

| 顺序 | 动作 | 代码 |
|---|---|---|
| ① | `reservationQuotaRollbackExecutor.rollback(7, 101)`——**先补偿** | `:289` |
| ② | CAS `{PRE_ACCEPTED, PUBLISHED} → COMPENSATED` + `fail_reason` | `:293-298` |
| ③ | 抛 `ServiceUnavailableException("预约失败，请重试")` | `:311` |

① 里那次 `rollback` 跑的是 `reservationRollback.lua`：`SREM reservation:batch:users:7 "101"` 返回 1 → `EXISTS quota:7` = 1 → `INCR` → 返回 1。

**最终 Redis** `reservation:batch:quota:7` `"5" → "4"`（Lua `DECR`）`→ "5"`（`rollback` 的 `INCR` 还原）；`reservation:batch:users:7` `不存在 → {101}`（抢成功时 `SADD`）`→ {}`（被 `SREM` 掉；**key 还在，只是空 Set**，TTL 198000 仍在）。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | **无行** |
| `tb_reservation_batch`(7) | `remaining_quota = 5`，**未变** |
| `tb_reservation_request` | `645827360351847423 / 101 / 7 / COMPENSATED / AMQP_CONNECT_FAILED` |

**最终 Request** `COMPENSATED`。

**是否人工** 不需要。用户看到 `503` + `预约失败，请重试`，名额已恢复，可直接重试。

> **① ② 顺序反了会怎样**：先 CAS 成 `COMPENSATED` 再 `rollback`，而 `rollback` 失败 → 账本已是终态 → 对账**再也不会扫到它** → 名额永久泄漏。这是全项目反复出现的不变式：**先做补偿，再宣告终结**（共三处，见文末速查）。

## 场景 5：Message 被 Return

**谁、在什么时刻、做什么** 学生 **105**（第 5 个到 Lua），09:00:00 提交 `{"batchId": 7}`。**发生了什么** broker 收下了消息，但**路由不到任何队列**（routing key 写错 / 队列被删 / 绑定丢失），把它退回生产者。

**哪个机制处理** 同一段代码的第三个分支：

```java

    outcome = PublishOutcome.DEFINITELY_NOT_DELIVERED;       // :261
    failureReason = "CONFIRM_RETURN";                        // :262
} else {
    outcome = PublishOutcome.ACKED;                          // :264
}
```

**`else if` 的位置是关键**：`isAck() == true` **不代表投递成功**，只表示 broker 收下了；必须先查 `getReturnedMessage()`。这就是 `publisher-returns: true`（`application.yaml:32`）+ `setMandatory` 存在的意义——把「路由失败」从静默丢弃变成可见的可编程信号。

路径同场景 3。

**最终 Redis** `reservation:batch:quota:7` `"1" → "0" → "1"`；`reservation:batch:users:7` `{101,102,103,104} → {101,…,105} → {101,102,103,104}`。

**最终 Request** `COMPENSATED`。

**是否人工** 数据不需要；**但需要修配置**——`CONFIRM_RETURN` 持续出现说明路由配置错了，那是应用层配置问题，不是运行时故障。

> 没有 producer-returns 的话，broker 会**静默丢弃**这条无法路由的消息同时回 `ack`。生产者判定 `ACKED` → 账本 `PUBLISHED` → 名额保持占用 → 用户拿到成功响应，而消息永不被消费。**10 分钟后对账才发现「无预约行」→ 归还名额 → `COMPENSATED`。** 用户以为成功，预约却不存在。

## 场景 6：★ Confirm Timeout

**谁、在什么时刻、做什么** 学生 **103**（第 3 个到 Lua），09:00:00 提交 `{"batchId": 7}`。**发生了什么** 消息发出去了，broker 5 秒内没回执。

> 08 篇把同一条岔路安排在 **102**（`LOCK_TIMEOUT`）身上，10 篇也是。本篇换成 103，是为了不和 06/07 篇「102 成功」的主线打架——这是一条**变体**。

**这是「为什么超时不立即归还名额」的答案所在。**

**哪个机制处理**

```java
CorrelationData.Confirm confirm = correlationData.getFuture().get(5, TimeUnit.SECONDS);  // :256
//                                                              ↑ 抛 TimeoutException
} catch (Exception e) {                                                                   // :276
    log.error("预约消息发送结果不确定：...", ...);                                          // :277-278
    outcome = PublishOutcome.UNKNOWN;                                                     // :279  ★ 不是 DEFINITELY_NOT_DELIVERED

```

`TimeoutException` 没有专门的 `catch`，落到**泛化的 `catch (Exception e)`**。然后走 `UNKNOWN` 分支（`:314-328`）：

| 顺序 | 动作 | 代码 |
|---|---|---|
| ① | **不动 Redis**（不归还名额，整个分支里没有 `rollbackExecutor` 调用） | — |
| ② | CAS `{PRE_ACCEPTED, PUBLISHED} → UNKNOWN` | `:315-319` |
| ③ | 抛 `ServiceUnavailableException("预约结果待确认，请稍后查询")` | `:328` |

**超时的语义是「我不知道」，不是「它失败了」。** 消息很可能已经入队、甚至已经落库：归还名额会与已落库的预约叠加 → 超发；标记成功则若消息真丢了名额被永久占用。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation` | **暂无** `…846425` 行（消息在不在队列里还不知道） |
| `tb_reservation_batch`(7) | `remaining_quota = 3`（101、102 落库各扣 1） |
| `tb_reservation_request` | `645827360351847425 / 103 / 7 / UNKNOWN / NULL` |

**最终 Request** `UNKNOWN`——**非终态**（`ReservationRequestStatus:14-15`）。

**10 分钟后的两个分支**（`ReservationReconcileServiceImpl:111-135`）：

| 分支 | 对账发现 | 处理 | 终态 |
|---|---|---|---|
| **A：消息其实到了** | `selectById(…846425) != null` | 只 CAS 推状态，**不归还名额**（`:112-121`，`continue`） | `CONFIRMED`（场景 7） |

**当前项目边界**：分支 A 下用户拿到 `503 预约结果待确认`，但预约**实际是成功的**。这是**已知的、有意的取舍**：宁可让极少数用户看到「报错但实际成功」，也绝不冒超发风险。要消除这个体验问题需要改成「先返回 pending + 前端轮询」，项目没做。

## 场景 8：Consumer 收到同一消息两次

**谁、在什么时刻、做什么** 学生 **102** 那条消息（`reservationId = 645827360351847424`）被 broker 重投一次。**发生了什么** 上一次处理完了但 ACK 在网络丢失 / 连接抖动，或有人从 DLQ 重放。

**哪个机制处理** `persist` 的第一道判断——**按主键判重**：

```java

        && existing.getUserId().equals(reservation.getUserId())
        && existing.getBatchId().equals(reservation.getBatchId())) {               // :30-32
    return ReservationPersistResult.DUPLICATE;                                     // :37  ★ 不插、不扣名额
}
// 同 id 但归属不同 → 继续走到 insert，让主键约束抛异常、消息进 DLQ（:33-36 注释）
```

三个条件必须**同时**成立：`id` + `user_id` + `batch_id`。`:29` 命中 102 那行、`:30-32` 三个字段都对上 → `:37` 返回 `DUPLICATE`。返回到消费者：

```java

case DUPLICATE:

    channel.basicAck(deliveryTag, false);                 // :71
```

`DUPLICATE` 走的是 **ACK 不是 NACK**——重复投递是预期内的正常情况，不该进 DLQ。`markConfirmedSafely`（`:99-112`）会再 CAS 一次 `CONFIRMED`，账本已是终态 → CAS 返回 0 → 打一行 `log.warn("预约已落库但账本置为 CONFIRMED 未生效")`，仅此而已。

**最终 Request** `CONFIRMED`。

**是否人工** 不需要。

**当前项目边界**：判重依赖**主键存在性**，没有 payload 内容校验。ID 由 `RedisIdWorker` 保证唯一，所以实际撞不上，但这层判重是**基于 ID 信任**的。

## 场景 9：Consumer 数据库事务失败

**谁、在什么时刻、做什么** 学生 **104**，09:00:02 他的消息被投递。**发生了什么** `persist` 执行到一半 MySQL 连接断开 / 死锁 / 超时。

## 场景 11：Consumer 一直失败

**谁、在什么时刻、做什么** 学生 **105** 的消息每次投递都失败（payload 里的 `batchId` 指向已删除的批次 / 持续死锁）。**发生了什么** 失败原因是**永久性**的，重投多少次都一样；他与场景 9 走**同一段代码**。

**哪个机制处理** 系统里不存在「无限重试直到撑爆」的路径：

| 轮次 | 动作 |
|---|---|
| 第 1 次消费 | `persist` 抛异常 → 事务回滚 → `recordFailReasonSafely(…846427, "PERSIST_EXCEPTION:XXX")`（`:92-94`）→ `basicNack(deliveryTag, false, false)`（`:95`） |
| 消息 | 进 `reservation.dlx` → `reservation.create.dlq` → 台账 1 行 `status='NEW'`、`replay_count=0` |
| **之后** | **消息不再被投递**（`requeue=false` + 无自动重试）——静静躺在 DLQ 里，**不会「一直失败」** |
| 10 分钟后 | 对账扫到非终态账本行 → 无预约行 → `rollback` 归还名额 → `COMPENSATED`（`:124-130`） |

两个开关合起来保证了这一点：

- `retry.enabled: false`（`application.yaml:38-39`，注释：手动 ack 模式下默认 recoverer 不会真正 nack、会卡死消费者）；
- `basicNack(deliveryTag, false, false)` 第三个参数 `requeue=false`——**不重新入队**。

**最终 Redis** `reservation:batch:quota:7` `"1" → "0"`（Lua 扣）→ `"1"`（对账归还）；`reservation:batch:users:7` `{101,…,104}` → `{101,…,105}` → `{101,102,103,104}`。

**最终 MySQL** `tb_reservation` 无 `…846427` 行；`tb_reservation_batch`(7) `remaining_quota = 1`；账本 `…846427 / 105 / 7 / COMPENSATED / RECONCILE_NO_RESERVATION`；`tb_reservation_dlq` 1 行 `status='NEW'`、`replay_count=0`。

**最终 Request** `COMPENSATED`。

**是否人工** 需要，但要分两件事：

| 事项 | 现状 |
|---|---|

## 场景 12：DLQ 重放同一消息

**谁、在什么时刻、做什么** 李老师（**uid 2**，`LAB_ADMIN`，实验室 2 的管理员，所以管得到设备 3 / 批次 7），09:00:08 对 `tb_reservation_dlq` 的 **id = 1** 调 `POST /reservation-dlq/1/replay`。**发生了什么** 09:00:20 他又点了一次，而这条死信是**学生 102 的消息**（`reservationId = 645827360351847424`）因 `LOCK_TIMEOUT` 进的 DLQ。

```java

    return rejected("死信记录已处理，不能重复重放", toVO(deadLetter));             // :166  ★ 挡住第二次重放
if (replayCount >= maxReplay) return rejected("已达到最大重放次数", ...);          // :173-174
if (message == null) return discard(..., "PAYLOAD_NOT_REPLAYABLE", ...);         // :178-181
```

## 场景 13：Redis 补偿执行两次

**谁、在什么时刻、做什么** 学生 **104** 的预约 `…846426`：09:12:00 他调 `cancel`，Redis 侧归还成功但 `quota_released` 那步 UPDATE 失败。**发生了什么** 09:15 定时任务的 `releasePendingQuotas` 又补偿一次，同一笔名额被归还两次。

**哪个机制处理** `reservationRollback.lua` 的**幂等令牌**——`SREM` 的返回值就是「这是不是我第一次归还」（`:1-3` `SREM == 0` 就直接 `return 0`，`INCR` 不执行；`:4-6` 名额键还在就 `INCR` 并返回 1；`:8` 名额键不存在只返回 2，不归还名额）。

| 第几次调用 | `SREM users:7 "104"` | `INCR quota:7` | 返回码 | 含义（`ReservationQuotaRollbackExecutor:30-33` 的注释） |
|---|---|---|---|---|
| 第 1 次（09:12 `cancel` 里，`ReservationServiceImpl:163-164`） | **1** | `"0"` → `"1"` | **1** | 确实占用过，已归还一个 |
| 第 2 次（09:15 `releasePendingQuotas`，`ReservationReconcileServiceImpl:159`） | **0** | **不执行** | **0** | 本来就未占用，名额不变 |

**必须在 Lua 里**：拆成「`SREM` → 按返回值决定是否 `INCR`」两条命令，中间被打断就会出现「`SREM` 已执行、`INCR` 没执行」→ 标记丢了、名额也没还，且重试无从判断。

**最终 Redis** `reservation:batch:quota:7` `"0" → "1"`（第 1 次 `INCR`）`→ "1"`（第 2 次原地不动）；`reservation:batch:users:7` `{101,102,103,104,105} → {101,102,103,105}`。

**最终 MySQL** `tb_reservation` 的 `…846426`：`status = CANCELLED`、`quota_released` 第 1 次 UPDATE 失败仍是 **0** → 第 2 次那句 `UPDATE ... WHERE id=… AND quota_released = 0`（`ReservationReconcileServiceImpl:160-164`）影响 **1** 行 → 变 **1**；`tb_reservation_batch`(7) `remaining_quota` 在 09:12 那次 `cancel` 里已 `0 → 1`（`ReservationLifecycleServiceImpl:62-66`）。

**最终 Request** 与取消无关——账本 `…846426` 仍是 `CONFIRMED`（`ReservationServiceImpl.cancel` 里没有任何 `reservationRequestService` 调用）。

**是否人工** 不需要。

**⚠️ 前提不能忘**：这个幂等性的语义前提是「集合里没有这个 userId」等价于「该用户没有有效占用」。**用户「取消后重新预约」时前提会破裂**——`users` 集合里的同一个 `userId` 在 T1 代表 R1、在 T3 代表 R2，脚本无从区分（09 篇 §5）。所以本场景的结论只在「同一用户同一批次没有第二次有效预约」时成立；真正保证安全的是**上层的状态跃迁一次性**（`ReservationServiceImpl.cancel:152-160` 那句早返回），**不是 Lua 本身**。**Lua 幂等的粒度是 userId，业务需要的粒度是 reservationId，两者不等价。**

**谁、在什么时刻、做什么** 李老师（**uid 2**）在 09:00:00.001 调 `POST /reservation-batch/7/close`。**发生了什么** 同一瞬间学生 **101** 的提交刚过 Java 校验、Lua 已经通过、消息还没被消费。


**是否人工** 不需要。

**为什么安全**：`close` **不归还任何已有预约的名额**（只删 Redis 键，不动 MySQL 的 `remaining_quota`，也不改已有预约状态）→ MySQL 侧自洽；Redis 键删掉后**没人能再预约这个批次**（`EXISTS` 闸门）→ 不需要 Redis 侧计数正确。

**当前项目边界**
- **`close` 删 Redis 键是不可逆的**：批次状态是 `CLOSED` 而非 `CANCELLED`，但**没有 reopen 接口**（`publish` 只允许 `DRAFT`，`:115-117`）。误关批次只能改库恢复。

- `complete`（核验）也不检查 `batch.status`（`ReservationLifecycleServiceImpl:90-96` 只看 `now >= startTime`），所以已关批次里的预约仍能被核验成 `COMPLETED`。

## 场景 18：用户重复取消

**谁、在什么时刻、做什么** 学生 **103** 在 **09:05:00** 调 `POST /reservation/645827360351847425/cancel`（成功）。**发生了什么** **09:05:30** 他又点了一次同一个接口。

**哪个机制处理** 三层，从里到外：

```java
int transitioned = reservationMapper.update(null, new LambdaUpdateWrapper<Reservation>()
        .eq(Reservation::getId, reservationId)
        .eq(Reservation::getUserId, userId)
        .eq(Reservation::getStatus, ReservationStatus.RESERVED)     // LifecycleServiceImpl:49  CAS
        .set(Reservation::getStatus, ReservationStatus.CANCELLED)); // :50
if (transitioned == 0) {                                            // :51
    Reservation current = reservationMapper.selectById(reservationId);
    if (current == null || !userId.equals(current.getUserId())) return NOT_FOUND;   // :53-55
    if (current.getStatus() == ReservationStatus.CANCELLED) return ALREADY_CANCELLED; // :56-58
    return NOT_CANCELLABLE;                                                          // :59
}
```

`:49` 是 CAS——**只有第一次能改到 1 行**。第二次 `transitioned == 0` → `:56-58` 读出 `CANCELLED` → 返回 `ALREADY_CANCELLED`。然后是最外层的早返回（`ReservationServiceImpl:152-160`，项目里注释最长的一段）：

```java
if (outcome != ReservationCancelOutcome.TRANSITIONED) {
    // ALREADY_CANCELLED：本次调用没有发生 RESERVED→CANCELLED 的状态跃迁，幂等返回。
    // 绝不能在此路径触碰 Redis 或 quota_released：rollback 的 Lua 虽然自身幂等，
    // 但用户可能在取消 R1 之后重新预约得到 R2，此时对 R1 的重复取消会 SREM 掉
    // R2 在 Redis 中的占位标记 —— Redis 多出名额而 MySQL 仍占用 R2。
    // 只有本事务真正完成跃迁（TRANSITIONED）才允许归还名额。
    return;
}
```

**第 1 次（09:05:00）**：`transitioned = 1` → `TRANSITIONED` → `:163-164` `rollback(7, 103)`：`SREM reservation:batch:users:7 "103"` 返回 1 → `EXISTS quota:7` = 1 → `INCR`；`:165-169` `UPDATE ... WHERE id=…846425 AND quota_released = 0` 把 `quota_released` 置 1；`ReservationLifecycleServiceImpl:62-66` 把 `remaining_quota` `0 → 1`。

**第 2 次（09:05:30）**：`transitioned = 0` → `ALREADY_CANCELLED` → `:152-159` **直接 `return`，Redis 和 `quota_released` 一个字都没动**。

**最终 Redis** `reservation:batch:quota:7` `"0" → "1"`（第 1 次 `INCR`）`→ "1"`（第 2 次不执行，**不会变成 `"2"`**）；`reservation:batch:users:7` `{101,102,103,104,105} → {101,102,104,105}`（103 只被 `SREM` 一次）。

**最终 MySQL**

| 表 | 内容 |
|---|---|
| `tb_reservation`(…846425) | `status = CANCELLED`、`quota_released = 1`、`update_time = 2026-10-07 09:05:00` |
| `tb_reservation_batch`(7) | `remaining_quota` **0 → 1**（只 +1 一次） |
| `tb_reservation_request` | `645827360351847425 / 103 / 7 / CONFIRMED / NULL`——**取消不改账本**（账本只跟踪创建流程） |

**最终 Request** 与取消无关。

**是否人工** 不需要。用户视角：两次都返回 `200`（第二次幂等）。

> 没有那个早返回、改成「无脑 `rollback`」，会在「取消 R1 → 重新预约 R2 → 再次取消 R1」这条时间线上：`SREM` 掉 R2 的占位标记 → Redis 多出 1 个名额而 R2 在 MySQL 仍占着 → **既超卖、又让该用户能再抢一次**，而再抢一次落库会被唯一键拒成 `DUPLICATE` 并**静默 ACK** → **名额永久泄漏，对账（已终态）再也不会看它**。
>
> **这是唯一一条自动机制无法恢复的泄漏路径。**

# 第五组：跨存储一致性

## 场景 20：★ Redis 数据与 MySQL 不一致

两个方向的可恢复性完全不同，必须分开答。

### 方向一：Redis 比 MySQL **紧**（名额少了 / 键丢了）

**谁、在什么时刻、做什么** 学生 **106** 在 09:30 打开批次 7 的详情页，页面显示「还剩 5 个名额」，他点了「预约」。**发生了什么** 此刻 `reservation:batch:quota:7` 已经被 LRU 淘汰 / Redis 未持久化重启后丢掉了。

| 环节 | 行为 | 代码 |
|---|---|---|
| **准入** | `EXISTS quota:7 == 0` → 返回 **1 `BATCH_NOT_OPEN`** → **所有用户都预约不了这个批次** | `reservation.lua:1-3` |
| 枚举转换 | `fromCode(1)` → `BATCH_NOT_OPEN`，中文 `"批次未开放预约"` | `ReservationQuotaExecutor:63-68`、`ReservationResultCode:10` |

| **展示** | 读不到键 → `log.warn("批次名额键不存在，回落 MySQL：batchIds={}")` → **页面显示 MySQL 的 5**（看起来「有名额」） | `ReservationBatchServiceImpl:344-354` |
| **对账** | **不管这件事**。对账判据是「账本有没有非终态」，而失败请求会被立即置为 `COMPENSATED` → **没有非终态行可扫** | `ReservationReconcileServiceImpl:103` |

**最终 Redis** `reservation:batch:quota:7` **不存在**（无人重建）；`reservation:batch:users:7` 也不存在。

**最终 MySQL** `tb_reservation_batch`(7) `remaining_quota = 5`（正确、但不可用）；`tb_reservation` 无新行；账本多 1 行 `…846428 / 106 / 7 / COMPENSATED / BATCH_NOT_OPEN`。

**最终 Request** 期间所有尝试都被置为 `COMPENSATED`（`fail_reason = "BATCH_NOT_OPEN"`），**即时终结**。

**是否人工** ✅ **需要，而且当前没有自动化手段。**

会**写**这个 key 的路径只有 5 条：`publish:128-132` 的 `setIfAbsent(key, totalQuota, ttlSeconds)`、`close:172` 与 `cancel:192` 的 `delete`、`reservation.lua:24` 的 `DECR`、`reservationRollback.lua:5` 的 `INCR`。**只有第一条能建键，而它要求批次是 `DRAFT`**（`ReservationBatchServiceImpl:115-117`：`if (batch.getStatus() != DRAFT) throw new BadRequestException("仅草稿批次可发布")`）。所以对**已经是 `PUBLISHED` 的批次**丢键后：不能重新 publish、没有 repair/rebuild 接口、对账不修（无终态请求）→ 只能**关闭批次再新建一个**（丢掉原有预约数据的关联），或**手工往 Redis 写键**。

**当前项目边界**：**没有任何代码路径能「从 MySQL 重建 Redis 名额键」**。触发条件不算罕见：Redis 未开持久化时重启就会发生；`application.yaml:13-22` 只配了连接与连接池，检测到缺键时也只打 `log.warn` 而不告警。

### 方向二：Redis 比 MySQL **松**（计数偏大）

**谁、在什么时刻、做什么** 同样是学生 **106** 在 09:30 提交。**发生了什么** 此刻 `reservation:batch:quota:7` 偏大（比如 `"1"`），而 MySQL 的 `remaining_quota` 已经是 `0`。

**哪个机制处理**

| 层 | 机制 | 代码 |
|---|---|---|
| ① 准入闸门 | Redis 宽松 → 多放行 1 个用户通过 Lua（返回 0） | `reservation.lua:16-18` |
| ② **MySQL 第二道闸** | `.gt(remainingQuota, 0)` → **影响 0 行** → 返回 `QUOTA_CONFLICT` | `ReservationPersistenceServiceImpl:49-56` |
| ③ 消费者 | `recordFailReasonSafely(…846428, "QUOTA_CONFLICT")` + `basicNack(requeue=false)` → 消息进 DLQ | `ReservationMessageConsumer:73-76` |
| ④ 对账 | 账本非终态 → 无预约行 → `rollback`（`SREM` 返回 0 → 不 `INCR`）→ `COMPENSATED` | `ReservationReconcileServiceImpl:124-130` |

**最终 Redis** `reservation:batch:quota:7` **仍然偏大**（多出来的名额没被纠正回去）。

**最终 MySQL** `tb_reservation_batch`(7) `remaining_quota = 0`（正确，**没有超卖**）；`tb_reservation` 无 `…846428` 行；账本 `…846428` `fail_reason` 先写 `QUOTA_CONFLICT`，10 分钟后 CAS 成 `COMPENSATED / RECONCILE_NO_RESERVATION`；`tb_reservation_dlq` 1 行。

**最终 Request** 那个用户的请求 `COMPENSATED`；账本没有泄漏。

**是否人工** 数据不需要（**没有超卖**）。⚠️ 但 **Redis 的偏离不会被纠正**。

**当前项目边界**：这是「单向核对」的必然结果——对账的判据是「`tb_reservation` 里有没有这一行」（`:111`），它**从不比对 `remaining_quota` 与 Redis 计数的数值**。所以 **MySQL 永远不会超卖**（条件扣减兜住），**Redis 的计数偏离会一直存在**。代价从「超卖」降级成了「一部分用户看到失败 + DLQ 多几条待处理记录」——可接受的降级，但不是自愈。真要修好需要**周期性全量核对**（把所有 `PUBLISHED` 批次的 `remaining_quota` 与 Redis 计数比对，不一致时以 MySQL 为准重建），**项目里没有这个任务**。

### 场景 20 小结

| 方向 | 会超卖吗 | 会泄漏名额吗 | 能否自动恢复 | 用户感知 |
|---|---|---|---|---|
| Redis 比 MySQL 紧（键丢/少了） | 不会 | 不会 | **不能** | 页面显示还剩 5，106 一点就报 `400 批次未开放预约` |
| Redis 比 MySQL 松（多了） | **不会**（MySQL 兜住） | 不会 | 不纠正偏离，但也不恶化 | 106 预约失败并进 DLQ |

## 速查

**一条主线：所有「不需要人工」都长这样**

```
学生 105 抢名额：Redis 已扣（quota:7 "1"→"0"）
                 │
    账本留痕（…846427 = PRE_ACCEPTED / PUBLISHED / UNKNOWN，非终态）
                 │
    MQ 没落地    │
                 ▼
        对账（每 5 分钟一轮，扫 update_time 早于 10 分钟前的非终态行）
                 │
        ┌────────┴────────┐
  tb_reservation 有行    tb_reservation 无行
        │                     │
  CAS → CONFIRMED       rollback 名额（quota:7 "0"→"1"）
  （不归还名额）          → CAS → COMPENSATED
   场景 7（103）            场景 2 / 6 分支 B / 9（105、103、104）
```

**需要人工处理的只有 3 个场景**

| 场景 | 为什么 | 有没有工具 |
|---|---|---|
| **20 方向一**（Redis 名额键丢失） | 没有任何路径能从 MySQL 重建 Redis 名额键 | 没有，只能 `redis-cli` 或关闭重建批次 |
| **17**（李老师取消批次 7） | 已有的 3 条 `RESERVED` 预约既不作废也不归还名额 | 没有，且未登记在 README |
| **11 / 9**（DLQ 有记录） | 需管理员（李老师 uid 2）决定重放还是丢弃，且**必须在 10 分钟内** | 有接口，但无告警、无积压监控 |

**三处「先做补偿，再宣告终结」（顺序反了就会永久泄漏名额）**

| 位置 | 先 | 后 |
|---|---|---|
| `publishReservationMessage` 确定未投递（场景 3/4/5：101/104/105） | `rollback` 名额 | CAS `{PRE_ACCEPTED,PUBLISHED} → COMPENSATED`（`:289` → `:293-298`） |
| 对账分支 B（场景 2/6 分支 B/9） | `rollback` 名额 | CAS `{非终态} → COMPENSATED`（`:125` → `:126-130`） |
| `releasePendingQuotas`（场景 13，104） | `rollback` 名额 | `SET quota_released = 1`（`:159` → `:160-164`） |

**反方向的另一条不变式：只有真正跃迁成功才允许补偿（场景 18，103）**

| 位置 | 先 | 后 |
|---|---|---|
| `ReservationServiceImpl.cancel` | CAS `RESERVED → CANCELLED` | 只有 `TRANSITIONED` 才 `rollback` + 置 `quota_released`（`:152-160` 的早返回） |

**四条「恰好一次」的保证，各自靠什么**

| 要保证什么 | 靠什么 | 不靠什么 |
|---|---|---|
| 名额不超发 | MySQL 的 `.gt(remainingQuota, 0)` 条件扣减（`ReservationPersistenceServiceImpl:49-53`） | Redis 计数（它可能偏大，场景 20 方向二） |
| 消息重复投递不出问题 | `tb_reservation` 主键判重 → `DUPLICATE` → ACK（`:29-38`、`:67-72`） | ACK 本身（场景 8/10） |
| 名额归还只发生一次 | `reservationRollback.lua:1-3` 把 `SREM` 返回值当令牌（场景 13/19） | 上层调用次数 |
| 重复取消不多还名额 | `ReservationServiceImpl.cancel:152-160` 只认 `TRANSITIONED`（场景 18） | Lua 的幂等（粒度是 userId，不够） |

**本篇记录到的实现不足（4 条）**

- **Redis 名额键丢失无任何自动恢复路径**（场景 20 方向一）：不能重新 `publish`、无 repair 接口、对账不修；检测到缺键只打 `log.warn` 不告警。
- **批次 `cancel` 没有定义已有预约的命运**（场景 17）：预约永远停在 `RESERVED`、占着 `uk_user_batch_active`、名额不归还；README 与 MIGRATION_STATUS 都没登记。
- **DLQ 的 10 分钟重放窗口没有文档、没有告警**（场景 9/11/12）：超过 `reconcile-threshold-ms` 后请求已被补偿，重放会被置 `DISCARDED`，预约找不回来；DLQ 积压深度也没有监控。
- **生产者超时后用户认知与系统事实不一致**（场景 6 分支 A/7）：对账会把账本改成 `CONFIRMED`，但用户那一次拿到的是 `503 预约结果待确认`；改「先返回 pending + 前端轮询」项目没做。
