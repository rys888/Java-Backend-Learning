## 二、三条必须先建立的认知

### 1. Redis 负责「谁能进」，MySQL 负责「进来的对不对」

这不是「缓存 + 数据库」的常规关系。**Redis 是准入判定的权威**（名额计数器 + 去重集合，由 Lua 原子判定），**MySQL 是账实相符的权威**（预约行 + `remaining_quota`）。

**两者允许短暂不一致——因为不一致不是要被消除的状态，而是要被收敛的过程。** 收敛靠三层：同步补偿（当场）→ 异步消费（秒级）→ 定时对账（最坏 15 分钟）。

### 2. 这套系统的真正难点不是"抢"，是"抢完之后"

**抢名额本身（Redis + Lua）只占了不到 200 行代码。** 剩下 90% 的复杂度都在处理这些情况：

- 消息发出去了但不知道 broker 收没收到；
- Redis 扣了名额但 MySQL 没有预约行；
- 用户取消了但 Redis 名额没还回去；
- 消费失败、死信、重放、重复投递……

**面试官想听的也是这部分。** 如果只讲「我用 Lua 解决了超卖」，那和网上的秒杀教程没有区别。

### 3. 项目的价值在于「边界清楚」

**这个项目没有微服务、没有分库分表、没有压测数据、没有可观测性。** 这些不是遗漏，是**有意的取舍**。

**所以讲的时候必须主动说边界**——**不要用「海量流量」「亿级并发」「高可用架构」描述它。** 详见 [00 篇 §8](00-项目全景.md) 与 [13 篇 Q58–Q63](13-项目面试问答.md)。

## 五、几条使用提醒

1. **有疑问就去核对源码。** 每处结论都写了 `文件:方法`，路径都在本文档里可查。
2. **折叠块先自己想。** 自测题的价值在于「先答再看」，直接展开等于没做。
3. **12 篇不要在 05–11 之前读。** 它是"把正常流程分别打断"，不知道正常流程就看不出打断的意义。
4. **99 篇不是字典，是索引。** 读源码遇到一个概念时回来查，或者面试前用它快速自检。
5. **11 篇建议提前读。** 05–09 里到处是 CAS、条件更新、唯一索引、`@Transactional`，**这些机制的载体都在 11 篇**。

## 六、源码与文档不一致的 14 处

**已在 [00 篇 §7](00-项目全景.md) 完整登记**，其中最重要的 3 处（它们描述的是**核心机制**，而且**描述的是不存在的东西**）：

| # | 文档说的 | 源码实际 |
|---|---|---|
| 1 | README §9③：用 `UPDATE ... SET active_flag = 0 WHERE active_flag = 1` 判定 `QUOTA_CONFLICT` | **该 SQL 语法上不可能执行**（`active_flag` 是生成列）。`QUOTA_CONFLICT` 真实来源是 `ReservationPersistenceServiceImpl:55` 的 `remaining_quota > 0` 条件更新 |
| 2 | README §1/§4：对账会「重新投递」、超阈值「进死信」 | **对账既不重投也不写死信。** 全项目只有两处 `convertAndSend`：首次投递 + **人工**重放 |
| 3 | README §9②：失败**次数**超过阈值 → 补偿 | **不存在计数字段。** `reconcile-threshold-ms` 是**时间窗口**（默认 10 分钟），退避靠**推进 `update_time`** |

> **面试时的正确态度**：这些不一致**不是「有人在撒谎」，而是「文档描述的是设计意图，代码演进后没同步」**。**但既然源码是事实来源，讲的时候必须以源码为准。**（[13 篇 Q62](13-项目面试问答.md) 就是问这个的。）
