# 一、先看结果：李老师的两个动作之后，表里变成了什么

## 1.1 建行之前：表里没有这一行

`src/main/resources/db/phase5_reservation_batch.sql` 里**只有 `CREATE TABLE`，没有一条 `INSERT`**：批次表是空的，`id` 完全由自增产生。例子假设这台库里此前已经建过 6 个批次，所以李老师这次自增拿到 **7**。

## 1.2 时间线

| 时间（+08:00） | 李老师的动作 | `tb_reservation_batch` 里那一行 | Redis |
|---|---|---|---|
| 2026-10-06 20:00 | `POST /reservation-batch` | **新增一行，`id=7`**：`status=DRAFT`、`remaining_quota=5`、`create_time=20:00` | 不碰 |
| 2026-10-07 09:00 | `POST /reservation-batch/7/publish` | **同一行**：`status` → `PUBLISHED`、`remaining_quota` 重新写成 `5`、`update_time=09:00` | 新增 `reservation:batch:quota:7 = "5"`，TTL `198000` 秒 |

**发布之后 Redis 里的样子**（05 篇 §0.2 把它当成开局条件）：

```
127.0.0.1:6379> GET reservation:batch:quota:7      → "5"
127.0.0.1:6379> TTL reservation:batch:quota:7      → (integer) 198000
127.0.0.1:6379> EXISTS reservation:batch:users:7   → (integer) 0
```

`users:7` 还不存在——它是学生抢名额的时候才由 Lua 建的（05 篇 §3.6）。**这条 `quota:7` 就是本篇交给 05 篇的东西。**

## 1.3 学生 101 那一刻看到什么（2026-10-07 09:00）

| 页面 | 请求 | 拿到 |
|---|---|---|
| 批次列表 | `GET /reservation-batch/page?current=1` | `records[0]` 就是批次 7：`status=PUBLISHED`、`bookingState=OPEN`、`remainingQuota=5`（来自 Redis） |

# 三、新建：`POST /reservation-batch`

## 3.1 请求体长什么样

`@RequestBody ReservationBatch batch`（`Controller:30`）——**没有专门的入参 DTO，前端 JSON 直接映射到实体**，所以 `createBatch` 返回的就是新行的 `id`（`Long`），被 `Result.ok(...)` 包进 `data`。实体字段（`entity/ReservationBatch.java`）：`id`(`:22-23`，`IdType.AUTO`)、`equipmentId`(`:25`)、`startTime`(`:27`)、`endTime`(`:29`)、`bookingStartTime`(`:31`)、`bookingEndTime`(`:33`)、`totalQuota`(`:35`)、`remainingQuota`(`:37`)、`status`(`:39`)、`createTime`(`:41`)、`updateTime`(`:43`)——四个时间是 `LocalDateTime`、`status` 是枚举 `ReservationBatchStatus`，都不是字符串。

**时间字段是 `LocalDateTime`，收的必须是 ISO 字符串**（带 `T`）。依据是两条：

1. 项目里**没有任何自定义 Jackson 配置**（`config/` 下只有 MvcConfig、MybatisConfig、RabbitMQConfig、RedissonConfig、ReservationDlqListenerConfig、SchedulingConfig、WebExceptionAdvice），实体上也没有 `@JsonFormat`；`application.yaml` 的 `spring.jackson` 下**只配了 `default-property-inclusion: non_null`**，没有 `date-format`。所以日期走 Spring Boot 默认的 JavaTimeModule，即 ISO-8601 的 `T` 分隔形式。
2. 前端 `views/admin/batch/AdminBatchListView.vue:128-158` 四个 `el-date-picker` 全部写死 `value-format="YYYY-MM-DD[T]HH:mm:ss"`，发出去的正是带 `T` 的字符串。

所以李老师这个请求体是：

```json
{
  "equipmentId": 3,
  "startTime": "2026-10-08T14:00:00",
  "endTime": "2026-10-08T16:00:00",
  "bookingStartTime": "2026-10-07T09:00:00",
  "bookingEndTime": "2026-10-07T18:00:00",
  "totalQuota": 5
}
```

**六个字段，没有 `id`、没有 `status`、没有 `remainingQuota`。** 前端 `formPayload()`（`AdminBatchListView.vue:342-352`）就发这六个：表单里虽然有一个「实验室」下拉，但它只是用来筛设备选项的，**不进请求体**。

**如果把 `T` 换成空格**（`"2026-10-08 14:00:00"`）——Jackson 的 `LocalDateTimeDeserializer` 认不出这个格式，抛 `HttpMessageNotReadableException`，被 `WebExceptionAdvice:46-49` 兜成 **400 + `{"success":false,"errorMsg":"请求体格式错误"}`**，`createBatch` 一行都不会执行。（`frontend/scripts/verify-admin.mjs` 里有一条用例就是跑这个：把 payload 里的 `T` 全换成空格，断言 400 + `请求体格式错误`，并断言管理端批次总数没变。）

**例子里的对应**：注意 `equipmentId` 前端实际上是当**字符串**发的（`el-select` 上绑的是 `:value="String(item.id)"`），Jackson 把 `"3"` 转成 `Long 3`，不影响后面。

## 3.2 `createBatch` 逐行

`service/impl/ReservationBatchServiceImpl.java:58-73`

```java
@Override
public Long createBatch(ReservationBatch batch) {
    validateCreateShape(batch);                          // ① 必填字段非空
    assertEquipmentManageable(batch.getEquipmentId());   // ② 归属校验：管得着这台设备吗
    ReservationBatch entity = new ReservationBatch()
            .setEquipmentId(batch.getEquipmentId()).setStartTime(batch.getStartTime())           // ③
            .setEndTime(batch.getEndTime()).setBookingStartTime(batch.getBookingStartTime())     // ③ 六个字段
            .setBookingEndTime(batch.getBookingEndTime()).setTotalQuota(batch.getTotalQuota())   // ③ 逐个 set
            .setRemainingQuota(batch.getTotalQuota())    // ④ 剩余名额 = 总名额
            .setStatus(ReservationBatchStatus.DRAFT);    // ⑤ 写死 DRAFT
    save(entity);                                        // ⑥ INSERT
    return entity.getId();                               // ⑦ 返回自增 id
}
```

- **③ 逐个字段 set，而不是 `save(batch)`**：这样前端就算传了 `id` / `status` / `remainingQuota` / `createTime`，也**全部被丢掉**——`entity` 是一张只填了 6 个字段的新对象。
- **④ `remainingQuota = totalQuota`**（例子 5 → 5）；**⑤ 状态写死 `DRAFT`**，前端传什么状态都没用。
- **⑦ `save(entity)` 之后 `entity.getId()` 才有值**——MyBatis-Plus 把自增主键回填进了实体，所以 `createBatch` 能把它当返回值。

**例子里的对应**：③ 全部取到值，④ `remainingQuota = 5`，⑤ `status = DRAFT`，⑥ 插一行，⑦ 返回 `7`。HTTP 响应是 `{"success":true,"data":7}`。

## 3.4 `assertEquipmentManageable`：数据级权限

`ReservationBatchServiceImpl:268-278`

```java
private Equipment assertEquipmentManageable(Long equipmentId) {
    if (equipmentId == null) throw new BadRequestException("设备id不能为空");
    Equipment equipment = equipmentService.getById(equipmentId);      // ① 查设备
    if (equipment == null) throw new ForbiddenException("无权管理该批次");   // ② 设备不存在
    laboratoryService.assertManageable(equipment.getLaboratoryId());  // ③ 一路查到实验室归属
    return equipment;
}
```

`LaboratoryServiceImpl.assertManageable`（`:25-34`）就三件事：`UserHolder` 里没人 → 403；`getById(laboratoryId)` 查不到、或 `user.getId()` 不等于 `laboratory.getAdminUserId()` → **403「无权管理该实验室」**；都相等才放行（实验室侧细节见 02/03 篇）。

**批次表里没有「归属」这一列**——`tb_reservation_batch` 只有 `equipment_id`。所以权限是**沿 `batch → equipment → laboratory.admin_user_id` 两级找上去**的：批次 7 的 `equipment_id=3` → 设备 3 的 `laboratory_id=2` → 实验室 2 的 `admin_user_id=2`，和李老师的 `userId=2` 相等 → 放行。

**例子里的三个人分别是什么结果**：

| 谁 | 走到哪 | 结果 |
|---|---|---|
| 李老师（uid 2） | `实验室 2.admin_user_id = 2` | **通过**，继续建批次 |
| 王老师（uid 3，也是 `LAB_ADMIN`） | 接口级 `@RequireRole` 放行，`3 != 2` | **403 `无权管理该实验室`** |
| 学生 101 | 连 `RoleInterceptor` 都没过 | **403**（空 body） |

**「王老师」这一路正是「接口级权限」和「数据级权限」的区别**：`@RequireRole` 只看角色是 `LAB_ADMIN`，所有管理员都过；`assertManageable` 才看这台设备归谁管。

**例子里的对应**：`equipmentId = 3` 非空 → ① 查到设备 3 → ② 不为 null → ③ `laboratoryId = 2`，归属相等 → 返回设备 3（`createBatch` 没用返回值，`publish` 用了）。

## 3.5 INSERT 之后那一行的完整字段值

`save(entity)`（`:71`）执行的是一条 `INSERT INTO tb_reservation_batch ...`。建表语句 `phase5_reservation_batch.sql:1-17`：

```sql
`status`          varchar(16) NOT NULL DEFAULT 'DRAFT' COMMENT '状态：DRAFT/PUBLISHED/CLOSED/CANCELLED',
`create_time`     timestamp NULL DEFAULT CURRENT_TIMESTAMP COMMENT '创建时间',
`update_time`     timestamp NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP COMMENT '更新时间',
```

`createTime` / `updateTime` 在实体里没有自动填充注解，`createBatch` 也没有 `set` 它们——MyBatis-Plus 默认的字段策略是 `NOT_NULL`（null 字段不进 INSERT 语句），所以这两列取建表语句里的默认值，即插入那一刻。

| ② | 使用时段先后 | `10-08 14:00 isBefore 10-08 16:00` = true | 通过 |
| ③ | 预约窗口先后 | `10-07 09:00 isBefore 10-07 18:00` = true | 通过 |
| ④ | 预约截止 ≤ 使用开始 | `10-07 18:00 isAfter 10-08 14:00` = **false** | 通过 |
| ⑤ | 预约截止 > 现在 | `10-07 18:00 isAfter 10-07 09:00` = true | 通过 |
| ⑥ | 设备可约 | `AVAILABLE` 且 `booking_enabled = true` | 通过（**用的是 ② 查出来的 `equipment`，没有第二次查库**） |
| ⑦ | 同设备时段不重叠 | `count = 0` | 通过 |

**⑦ 是标准区间相交公式**：`已有.start < 新.end AND 已有.end > 新.start` 就算重叠，排除了自己（`.ne(id)`）和已取消的批次（`.ne(status, CANCELLED)`）——所以「取消掉一个旧批次再建同时间的新批次」是允许的。

**而 ⑦ 是一个「先查后写」的竞态缺口**：`count(...)`（`:307-312`）查完到 `:137` 的 CAS UPDATE 之间**没有任何锁**，CAS 的 `WHERE` 里也**没有重叠条件**——两个并发 `publish` 可以各自都查不到对方、双双通过 ⑦（§9 第 3 条）。

**⑥ 只看设备，不看实验室**：整个 `validatePublishInvariants` 没有一处碰 `laboratory`。所以把批次挂到**设备 7（自己 `AVAILABLE`，但所属实验室 4 是 `MAINTENANCE`）**上，发布照样能过（§9 第 2 条）。

**①②③④ 全是「建草稿时没查、发布时才查」的那几项**（§3.3 说 `validateCreateShape` 只查非空）：草稿可以是错的，**发布是不让错的批次出去的最后一关**。

**例子里的对应**：七条全过，`publish` 继续往下走。

|---|---|
| `key` | `"reservation:batch:quota:7"` |

**这条命令等价于**：`SET reservation:batch:quota:7 "5" NX EX 198000`。

**⑤ 为什么「已存在」要当错误**：`setIfAbsent` 只在 key 不存在时写成功。所以它同时挡住两件事——**重复调用 `publish`**，和 **Redis 里残留的旧 key**（比如进程崩在了下面第 148-155 行的回滚之前）。两种都返回 `400 发布占用标记已存在，疑似重复发布`。

**例子里的对应**：批次 7 是第一次发布，key 不存在 → `quotaCreated = true` → 继续。

## 5.6 `remainingQuota` 从哪来：SQL 查出来，Redis 覆盖

`ReservationBatchServiceImpl:326-358`

```java
private void fillRemainingQuotaFromRedis(List<ReservationBatchVO> batches) {
    List<ReservationBatchVO> published = batches.stream()
            .filter(batch -> batch.getStatus() == ReservationBatchStatus.PUBLISHED)  // ① 只处理 PUBLISHED
            .collect(Collectors.toList());
    if (published.isEmpty()) return;                       // ① 其余状态不查 Redis，直接用 MySQL 值

    List<String> keys = published.stream()
            .map(batch -> quotaKey(batch.getId())).collect(Collectors.toList());   // ② "…:quota:7"
    try {
        List<String> quotas = stringRedisTemplate.opsForValue().multiGet(keys);    // ③ 一次 mget
        if (quotas == null) { /* 打 warn，保留 MySQL 值 */ return; }
        for (int i = 0; i < published.size(); i++) {
            if (quotas.get(i) != null)
                published.get(i).setRemainingQuota(Integer.valueOf(quotas.get(i)));  // ④ Redis 值覆盖 VO
            else
                missingBatchIds.add(published.get(i).getId());                       // ⑤ key 不存在 → 保留 MySQL 值
        }
    } catch (RuntimeException e) {
        // ⑥ Redis 挂了 → 打 warn，回落 MySQL
    }
}
```

- **① 只对 `PUBLISHED` 处理**：`DRAFT` / `CLOSED` / `CANCELLED` 不查 Redis，**直接用 MySQL 那一列的值**；**③ `multiGet`**：一页所有的名额 key 一次拿完，不是循环 `get`。
- **④ 拿到就覆盖**：所以 `remainingQuota` 的语义是「**Redis 有就用 Redis 的，Redis 没有就用 MySQL 的**」。

**例子里的对应**：批次 7 是 `PUBLISHED` → ② `keys = ["reservation:batch:quota:7"]` → ③ `multiGet` 返回 `["5"]` → ④ VO 上的 `remainingQuota` 被写成 `5`（和 MySQL 里的 5 一样，看不出差别——但如果 05 篇里 5 个学生抢完，MySQL 那一列还是 5，Redis 已经是 `"0"`，列表页显示的就是 `0`）。

**两种「拿不到」**（key 不存在 ⑤、Redis 抛异常 ⑥）都打 `warn` 日志然后**保留 MySQL 的值**，接口不失败。

# 六、`bookingState` 怎么算出来的（本篇最重要的一段）

## 6.1 两套状态，别混

| | `ReservationBatchStatus` | `BookingState` |
|---|---|---|
| 存哪 | **数据库列 `status`** | **不存库，每次读的时候现算** |
| 取值 | `DRAFT` / `PUBLISHED` / `CLOSED` / `CANCELLED`（4 个） | `DRAFT` / `NOT_STARTED` / `OPEN` / `EXPIRED` / `CLOSED` / `CANCELLED`（6 个） |
| 谁写 | `createBatch` / `publish` / `close` / `cancel` | **没人写**，`fillBookingState` 每次现算 |
| 在 VO 里 | `status`（原样带出来） | `bookingState`（算出来的） |

**`BookingState` 是「持久状态 + 时间」算出来的展示状态**，前端拿它决定按钮能不能点。两套状态**可以相同也可以不同**：一个 `PUBLISHED` 的批次，`bookingState` 可能是 `NOT_STARTED`、`OPEN` 或 `EXPIRED`，取决于**看的那一刻**。

## 6.2 `BookingState.of` 逐行

`enums/BookingState.java:6-11` 是取值（`DRAFT / NOT_STARTED / OPEN / EXPIRED / CLOSED / CANCELLED`），`:13-33` 是算法：

```java
public static BookingState of(ReservationBatchStatus status,
                              LocalDateTime bookingStartTime,
                              LocalDateTime bookingEndTime,
                              LocalDateTime now) {
    if (status == ReservationBatchStatus.DRAFT) return DRAFT;            // ① :17-19
    if (status == ReservationBatchStatus.CLOSED) return CLOSED;          // ② :20-22
    if (status == ReservationBatchStatus.CANCELLED) return CANCELLED;    // ③ :23-25
    if (now.isBefore(bookingStartTime)) return NOT_STARTED;              // ④ :26-28
    if (!now.isAfter(bookingEndTime)) {                                  // ⑤ :29-31
        return OPEN;
    }
    return EXPIRED;                                                      // ⑥ :32
}
```

一行一行看：

- **①②③ 先看持久状态，不看时间**：`DRAFT` / `CLOSED` / `CANCELLED` 三个状态**直接返回同名值**，后面的时间判断一行都不执行。**只有 `PUBLISHED` 会往下走**——这是整个方法的骨架：前三个分支是「状态优先」，后三个分支是「时间优先」。
- **④ `now.isBefore(bookingStartTime)`** → `NOT_STARTED`（还没到预约开放时间）。
- **⑤ `!now.isAfter(bookingEndTime)`** → `OPEN`。**注意这里是否定式**：`!now.isAfter(x)` 等价于 `now <= x`，所以**边界那一刻算 `OPEN`**（闭区间）。写成 `now.isBefore(bookingEndTime)` 就会变成开区间，18:00:00 那一刻会掉到 `EXPIRED`——**这个 `!` 是边界语义的关键**。
- **⑥ 兜底 `EXPIRED`**：走到这里必然满足 `PUBLISHED` 且 `now > bookingEndTime`。

`of` 是**纯函数**：只吃四个入参，不查库、不读 Redis、不看系统时间。**`now` 是调用方传进来的**（这一点很重要——同一页记录共用同一个 `now`，见 §5.4）。

## 6.3 把批次 7 和 `now = 2026-10-07 09:00` 代进去

调用点是 `fillBookingState`（`ReservationBatchServiceImpl:318-324`）：

```java
private void fillBookingState(ReservationBatchVO batch, LocalDateTime now) {
    batch.setBookingState(BookingState.of(
            batch.getStatus(),
            batch.getBookingStartTime(),
            batch.getBookingEndTime(),
            now));
}
```

四个实参全部来自 VO 和调用方，**`now` 就是 §5.4 第 ⑤ 行取的那一个**：

| 形参 | 实参（例子） |
|---|---|
| `status` | `PUBLISHED`（CAS 之后的值） |
| `bookingStartTime` | `2026-10-07T09:00:00` |
| `bookingEndTime` | `2026-10-07T18:00:00` |
| `now` | `2026-10-07T09:00:00` |

代入伪代码逐行走一遍：

```
① status == DRAFT?                PUBLISHED == DRAFT          → false，往下
② status == CLOSED?               PUBLISHED == CLOSED         → false，往下
③ status == CANCELLED?            PUBLISHED == CANCELLED      → false，往下
④ now.isBefore(bookingStart)?     09:00 isBefore 09:00        → false，往下
⑤ !now.isAfter(bookingEnd)?       !(09:00 isAfter 18:00)      → !false = true → return OPEN ★
⑥ （走不到）
```

**学生 101 在 2026-10-07 09:00:00 看到的是 `bookingState = "OPEN"`。**

**第 ④ 步是「刚好卡在边界上」**：`isBefore` 是严格小于，`09:00 isBefore 09:00` 为 false，所以**预约开放的那一秒就已经是 `OPEN`**，不是 `NOT_STARTED`。**第 ⑤ 步同理**：`18:00:00.000` 那一刻还是 `OPEN`，指针到 `18:00:00.001` 才变成 `EXPIRED`。

## 6.4 六个取值各自什么时候出现

同一个批次 7（`bookingStart = 10-07 09:00`，`bookingEnd = 10-07 18:00`），只换「看的那一刻」和「持久状态」：

| `status`（库里） | `now` | 命中分支 | `bookingState` | 前端按钮 |
|---|---|---|---|---|
| `DRAFT` | 任意 | ① | `DRAFT` | 未发布（且**学生根本看不到这条**，§5.4 的 `publicOnly`） |
| `PUBLISHED` | 10-07 **08:59** | ④ | `NOT_STARTED` | 未开始预约（灰） |
| `PUBLISHED` | **10-07 09:00** | ⑤ | **`OPEN`** | **立即预约（可点）** |
| `PUBLISHED` | 10-07 **18:00:00.000** | ⑤ | `OPEN` | 立即预约（**边界还是开的**） |
| `PUBLISHED` | 10-07 **18:00:00.001** | ⑥ | `EXPIRED` | 已截止（灰） |
| `CLOSED` | 任意 | ② | `CLOSED` | 已关闭（灰） |
| `CANCELLED` | 任意 | ③ | `CANCELLED` | 已取消（灰） |

**前三行「任意」和后面四行的区别就是「状态优先还是时间优先」**：一个 `CLOSED` 的批次，就算 `now` 落在预约窗口正中间，返回的也是 `CLOSED` 而不是 `OPEN`；反过来，`PUBLISHED` 的批次在三个不同时刻看会拿到三个不同的值（`NOT_STARTED` → `OPEN` → `EXPIRED`），**而库里那一行的 `status` 一直是 `PUBLISHED` 没变过**——这就是 `bookingState` 这一层存在的理由：它是同一行数据在不同时间的不同含义。

**前后端不会打架**：`NOT_STARTED` 那一格对应的后端防线是 `submit` 里的 `now.isBefore(bookingStartTime)`（05 篇 §6.1 第 ⑥ 项，抛 `400 预约尚未开始`）——**同一条判定**。前端按钮的 `disabled` 只是提前告诉用户，不是唯一的防线。

## 6.5 这个值去哪了：前端按钮

`bookingState` 是字符串，前端靠一张映射表决定按钮（`frontend/src/constants/statusMap.js`）：

| `bookingState` | `label` | `actions` |
|---|---|---|
| `DRAFT` | 未发布 | `[]` |
| `NOT_STARTED` | 未开始预约 | `[]` |
| **`OPEN`** | **可预约** | **`['submit']`** ← 只有这个能点 |
| `EXPIRED` | 已截止 | `[]` |
| `CLOSED` | 已关闭 | `[]` |
| `CANCELLED` | 已取消 | `[]` |

详情页 `views/batch/BatchDetailView.vue:114-117` 就三行逻辑：`resolveStatus('BookingState', batch.bookingState)` 拿到上表这一行，`canSubmit = actions.includes('submit')`，`bookingStateLabel = label`；按钮上是 `:disabled="!canSubmit"`，不可点时下面显示「当前不可预约：{{ bookingStateLabel }}」（`:64-72`）。

**例子里的对应**：`bookingState = "OPEN"` → `canSubmit = true` → 「立即预约」**可点**，提示文字不显示。如果学生 101 是 08:59 打开的这一页，`bookingState = "NOT_STARTED"` → 按钮灰掉，显示「当前不可预约：未开始预约」。

**前端不自己算状态**——它只读后端给的 `bookingState` 再查表，时间比较全部在后端（`BookingState.of`）做完。

# 七、详情：`GET /reservation-batch/7`

```java
@Override
public ReservationBatchVO queryBatchById(Long id) {
    ReservationBatchVO batch = getBaseMapper().selectBatchDetailById(id);       // ① JOIN 查一条

            && batch.getStatus() != ReservationBatchStatus.PUBLISHED

    fillRemainingQuotaFromRedis(Collections.singletonList(batch));              // ③ 名额（Redis）

    return batch;
}
```

- **③④ 和列表页是同一对方法**——列表用 `for` 循环批量调，详情传一个 `singletonList`。**同一个批次的 `bookingState` 在列表页和详情页必然一致**（只差两次请求的 `now` 几毫秒）。
- **② Controller 把 null 变成 `Result.fail("预约批次不存在")`**（`Controller:62-66`）：**HTTP 状态仍是 200，靠 `success: false` 表达失败**，不是 404 也不是 403。**用「不存在」而不是「你没权限」**，就不会泄露「这个 id 上有个草稿」。

**例子里的对应**：学生 101（`role = USER`）请求 `GET /reservation-batch/7`——

| 批次 7 的状态 | ② 的判断 | 返回 |
|---|---|---|
| `DRAFT`（还没发布） | 非管理员 且 状态不是 `PUBLISHED`/`CLOSED` → 命中 | `null` → `200 + {"success":false,"errorMsg":"预约批次不存在"}` |
| `PUBLISHED` | 第二个条件为 false，整个 `&&` 为 false | 完整 VO，`bookingState = "OPEN"`、`remainingQuota = 5`（和 §5.5 那条 JSON 除 `total` 外一样） |

**同一个批次在列表页和详情页是两种挡法**：列表靠 SQL 的 `status IN ('PUBLISHED','CLOSED')`（§5.4）**把行过滤掉**，详情靠这个 `if` **把行变成 null**。发布前，学生 101 走哪个接口都看不到批次 7。

# 八、`close` 和 `cancel`

两个方法结构几乎一样（`ReservationBatchServiceImpl:158-173` / `:175-193`），合在一起看差异。以 `close` 为例：

```java
@Override
public void close(Long id) {
    ReservationBatch batch = getRequiredBatch(id);                             // 查这一行
    assertEquipmentManageable(batch.getEquipmentId());                         // 归属校验，同 publish
    if (batch.getStatus() != ReservationBatchStatus.PUBLISHED)
        throw new BadRequestException("仅已发布批次可关闭");                     // 前置状态门
    boolean updated = update(null, new LambdaUpdateWrapper<ReservationBatch>()
            .eq(ReservationBatch::getId, id)
            .eq(ReservationBatch::getStatus, ReservationBatchStatus.PUBLISHED)  // CAS，和 publish 同一套思路
            .set(ReservationBatch::getStatus, ReservationBatchStatus.CLOSED));
    if (!updated) throw new BadRequestException("批次状态已变化，关闭失败");
    stringRedisTemplate.delete(Arrays.asList(quotaKey(id), usersKey(id)));      // 删两个 key
}
```

`cancel` 只有三处不一样：

| | `close` | `cancel` |
|---|---|---|
| 前置状态门 | `!= PUBLISHED` → 400「仅已发布批次可关闭」 | `!= DRAFT && != PUBLISHED` → 400「仅草稿或已发布批次可取消」 |
| CAS 条件 | `.eq(status, PUBLISHED)` | `.in(status, DRAFT, PUBLISHED)` |
| 目标状态 | `CLOSED` | `CANCELLED` |
| 删 Redis | 两个 key 都删 | 两个都删（`DRAFT` 批次本来没有这两个 key，删不存在的 key 是空操作） |

**删掉 `quota:7` 就是「关上预约」的动作本体**——05 篇的 Lua 第一步就是 `EXISTS quota`，key 没了，后面的学生一律拿到 `1 BATCH_NOT_OPEN`（05 篇 §3.2 / 变体 C）。**两个方法都不动 `tb_reservation` 里已有的预约行。**

**状态机**：`DRAFT ─publish→ PUBLISHED ─close→ CLOSED`；`DRAFT` / `PUBLISHED` 都能 `cancel → CANCELLED`；`CLOSED` 与 `CANCELLED` 都是终态，没有「重新打开」的动作。

**例子里的对应**：李老师发布后立刻 `close` 批次 7 → 那一行变 `CLOSED`、Redis 两个 key 被删；**101～105 已经拿到的预约单不受影响**，只是没人能再抢。学生 101 打开列表仍能看到批次 7（`CLOSED` 在公开白名单里，§5.3），但 `bookingState = "CLOSED"`、按钮灰。

# 九、当前实现的几个点

- **`createBatch` 几乎不校验**：`validateCreateShape`（`:248-258`）只查六个字段非空，**不查 `totalQuota >= 1`、不查时间先后、不查设备状态、不查时段重叠**——这些全推到 `publish` 的 `validatePublishInvariants`。所以库里可以长期躺着时间颠倒、名额为 0 的草稿。
- **`publish` 的设备校验不连带实验室**：`:303-306` 只看 `equipment.getStatus()` 和 `bookingEnabled`，**从没读过所属实验室的 `status`**。所以挂在实验室 4（`MAINTENANCE`）下的设备 7/8，批次照样能发布、学生照样能约（05 篇 §6.1 第 ⑤ 项同样只看设备）。
- **重叠检查是「先查后写」**：`:307-315` 的 `count(...)` 和 `:137` 的 CAS UPDATE 之间没有锁，CAS 的 `WHERE` 里也没有重叠条件，两个并发 `publish` 理论上可以都通过检查。
- **详情页的可见性只看角色、不看归属**：`:202-204` 只判断 `role == LAB_ADMIN`，**没有像 `queryManagePage`（`:231`）那样带上 `admin_user_id`**——所以任意一个 `LAB_ADMIN` 都能 `GET` 到别的实验室的 `DRAFT` 批次详情。列表页有归属过滤，详情页没有。

| 边界 | 结果 |
|---|---|
| 草稿批次 | 学生在**列表**里查不到（SQL 过滤）、在**详情**里是「不存在」（返回 null） |
| `publish` 先写 Redis 再 CAS MySQL | MySQL 失败就把刚写的 key 删掉（删不掉靠 TTL） |
| 重复发布 | `setIfAbsent` 返回 false → `400 发布占用标记已存在，疑似重复发布` |
| `now == bookingStart` / `now == bookingEnd` | 都是 `OPEN`（`isBefore` 与 `!isAfter` 的两端闭合），过一毫秒才 `EXPIRED` |
| `DRAFT` / `CLOSED` / `CANCELLED` | 时间不参与判断，直接返回同名 `bookingState` |
| 页大小 | 永远 5（`SystemConstants.java:5`），接口没有 `size` 参数 |
| `remainingQuota` | Redis 有就用 Redis，Redis 没有/挂了就用 MySQL |

**key 与常量**：`reservation:batch:quota:{id}`（String，值 = `totalQuota` 文本，`publish` 时 `SET NX EX`）、`reservation:batch:users:{id}`（Set，`publish` 不建，05 篇的 Lua 建）、TTL = `(end_time + 24h) - now` 秒（例子 198000）、批次表 `tb_reservation_batch`（`status` 列默认 `'DRAFT'`，两个时间列默认 `CURRENT_TIMESTAMP`）。
