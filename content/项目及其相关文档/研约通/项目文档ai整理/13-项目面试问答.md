## Q1. 介绍一下你的项目

**推荐回答**

「研约通是一个高校实验资源预约平台的后端服务。业务模型是四层：**实验室 → 设备 → 预约批次 → 预约单**。管理员为某台设备创建预约批次，设定开放时段、使用时段和名额上限；学生在开放窗口内抢名额提交预约。

技术栈是 **Spring Boot 单体应用 + MySQL + Redis + RabbitMQ**，Java 8。整个项目要同时满足三条要求：**不超卖、不丢单、可自愈**。

我重点做的是预约这条主链路。核心设计是把 **Redis 当作高并发的准入闸门**（用 Lua 脚本把「查名额 + 查时段 + 查重复 + 扣减」做成一个原子操作），**MySQL 当作账实相符的权威**，中间用一张**请求状态账本表**加一个**定时对账任务**缝合起来。

源码规模是 99 个主文件、16 个测试类。」

**面试官继续追问：你自己写了哪一部分？**

「这个项目是从一个课程项目（黑马点评）重构来的——**基础设施是复用的**，业务域是整体替换的。

具体说：`CacheClient`（缓存穿透/击穿/雪崩）、`RedisIdWorker`（全局唯一 ID）、双拦截器登录续期、RabbitMQ 的异步下单骨架，这些**来自原项目，我做了 de-Shop 改造**（把商铺域换成实验室域）。

**业务逻辑、并发方案、状态账本、对账任务、死信治理这些是我新写的。** 比如 `reservation.lua` 的返回码体系、`tb_reservation_request` 的五态状态机、`ReservationReconcileServiceImpl` 的三段对账逻辑、`active_flag` 生成列模拟部分唯一索引——都是这个项目里新增的。

**我应该诚实说的一点**：原项目的课程业务实体（商铺、笔记、优惠券、秒杀）已经**永久删除**了，`phase10_drop_legacy_tables.sql` 里能看到删了哪 10 张表。」

## Q2. 为什么要做这个项目？解决什么真实问题？

**推荐回答**

「高校实验室的设备和时段是**稀缺资源**，而预约的典型特征是**瞬时并发 + 名额有限**——一个热门的开放时段，可能几百个学生在同一秒点『预约』。

这正好是一个**适合用 Redis + MQ 来解的场景**：Redis 做原子准入、MQ 做异步落库。所以我把它当成一个**把『高并发 + 最终一致』讲清楚**的练手项目，而不是一个 CRUD 项目。

我刻意把三条硬要求写在 README 第一行：**不超卖、不丢单、可自愈**。后面所有的设计都是为这三条服务的。」

**面试官继续追问：为什么说『不丢单』比『不超卖』难？**

**追问回答**

**「不超卖」是一个『阻止』问题，『不丢单』是一个『恢复』问题。**

**不超卖**只需要一个正确的原子判定——把临界区收进 Lua，问题就解决了，**是静态的、可穷举的**。

**不丢单**要面对的是**进程崩溃、网络超时、消息丢失**这类**『事件从未发生』**的故障。这类故障的特点是：**没有任何回调会被触发**，所以不能靠事件驱动来兜底——你必须有一个**主动的、周期性的扫描**去发现它们。

我在这个项目里学到的关键点是：**对账任务是必需的不是可选的。** 光有 publish confirm、手动 ACK、死信队列是不够的——它们都是**事件驱动**的，只能覆盖『事件发生了但结果是失败』；**『事件根本没发生』只能靠定时扫描。** 这就是为什么 `tb_reservation_request` 这张账本表是整个设计的支点。」

## Q3. 为什么「预约批次」必须独立成一张表？

**推荐回答**

「因为只有 `equipmentId` 无法表达任何一条『限时限量』的语义。具体说不能表达：**

1. **『某个时段有几个名额』**——名额总得挂在某个具体的开放窗口上，否则『余量 3』是对谁而言的 3？
2. **『什么时间开放抢』**——预约窗口和使用时段是**两个不同的时间区间**（`bookingStartTime/bookingEndTime` vs `startTime/endTime`）；
3. **『这个时段过了没有』**；
4. **『这批被撤回了没有』**——需要一个状态机。

**批次把「设备的一段使用时段 + 一段预约窗口 + 名额上限与余量 + 一个状态机」打成了一个『可预约的原子单位』。**

代码层面的硬证据：`ReservationServiceImpl.submit(Long batchId)` **收的参数就是 `batchId`**，请求体 DTO 只有这一个字段——**学生预约的对象是批次，不是设备**。」

**面试官继续追问：`bookingStartTime/bookingEndTime` 和 `startTime/endTime` 有什么区别？**

**追问回答**

「**两段时间，四个语义完全不同：**

| 字段 | 含义 | 谁关心 |
|---|---|---|
| `bookingStartTime` / `bookingEndTime` | **预约窗口**——什么时候可以来抢名额 | 只影响 `POST /reservation` |
| `startTime` / `endTime` | **使用时段**——学生实际去用设备的时间 | 影响核验（`verify` 要求 `now >= startTime`）和爽约判定（`markNoShows` 要求 `endTime < now`） |

**发布不变式 `I4` 规定了它们的关系：`bookingEndTime <= startTime`**——**必须先抢完，才能开始用**。

**这个约束有一个漂亮的推论**：由 I4（`bookingEndTime <= startTime`）和 I5（`bookingEndTime > now`）可以推出 `startTime > now`，再由 I2（`startTime < endTime`）推出 `endTime > now`。**所以不需要单独校验『使用时段在未来』——它是被推导出来的，不是一条独立的规则。** 这避免了规则冗余（冗余的规则会有一天不一致）。

**还有一个副作用值得注意**：因为推得出 `endTime > now`，`ReservationQuotaExecutor.tryAcquire` 里算 users 集合的 TTL 时**恒为正**。这个类的注释就写明了这一点：『调用方已确认窗口开放：now ≤ bookingEndTime ≤ startTime < endTime，因此 Set 的 TTL 恒为正。』」

## Q4. 你的项目里有两套「状态」，为什么？

**推荐回答**

「是的，而且**一套入库、一套不入库**——这个区分很关键。

| | `ReservationBatchStatus` | `BookingState` |
|---|---|---|
| 值 | `DRAFT` / `PUBLISHED` / `CLOSED` / `CANCELLED`（4 个） | `DRAFT` / `NOT_STARTED` / `OPEN` / `EXPIRED` / `CLOSED` / `CANCELLED`（6 个） |
| 入库 | ✅ `tb_reservation_batch.status` | ❌ **只在读取时算**，写进 VO 给前端 |
| 决定者 | **管理员的显式动作** | 管理员动作 **+ 时间流逝** |

**`BookingState` 不能入库的根本原因是：它是 `(status, bookingStartTime, bookingEndTime, now)` 的纯函数，而 `now` 每毫秒都在变。含 `now` 的状态不可能持久化**——落库的值下一秒就过期。而且系统里**没有任何事件**会去触发一次 UPDATE 把它刷新（没有『到点了把 NOT_STARTED 刷成 OPEN』的定时任务），所以只能在读取时算。

**写入点唯一**：`ReservationBatchServiceImpl.fillBookingState`。消费方只有前端。

**判定顺序是先状态后时间**：`BookingState.of` 先判 `DRAFT`/`CLOSED`/`CANCELLED`，再判时间窗口。**因为管理员的显式动作必须优先于时间流逝**——一个 `CLOSED` 的批次，即使当前时间还在预约窗口内，也必须是 `CLOSED` 而不是 `OPEN`。」

**面试官继续追问：那前端拿到 `BookingState` 能干什么？**

**追问回答**

「**驱动按钮的可见性和文案。** 这是它存在的唯一理由——`OPEN` 显示『立即预约』，`NOT_STARTED` 显示『未开始』，`EXPIRED` 显示『已截止』，`SOLD_OUT`……（抱歉，`SOLD_OUT` 不在 `BookingState` 里，它是 Lua 的返回码）。

**但要说清楚一个边界**：`BookingState` 是**展示用的**，**不是权威的**。真正的准入判定在 `ReservationServiceImpl.submit` 和 `reservation.lua` 里各自独立做了一遍。

**为什么要有这个『重复』？** 因为 `BookingState` 是**读的时候算的**，算完到用户点击之间可能已经过了几秒——**用展示状态做准入判定就是 TOCTOU**。所以 **`submit` 必须自己再校验一次**（它确实做了：`now.isBefore(bookingStartTime)` → 抛『预约尚未开始』）。

**这是这个项目里一个通用的原则：永远不用『读时算出来的状态』做写操作的判据。**」

## Q5. 一个学生提交预约，数据经过哪些表和中间件？按顺序说。

**推荐回答**

「完整链路是六步：

| 步 | 动作 | 存储 | 代码 |
|---|---|---|---|
| ① | 生成 `reservationId` | **Redis** `INCR icr:reservation:yyyy:MM:dd` | `RedisIdWorker.nextId("reservation")` |
| ② | 写账本 `PRE_ACCEPTED` | **MySQL** `tb_reservation_request` | `ReservationRequestServiceImpl.createPreAccepted` |
| ③ | 原子抢名额（`DECR` + `SADD`） | **Redis** `reservation:batch:quota:{id}` / `:users:{id}` | `reservation.lua` via `ReservationQuotaExecutor.tryAcquire` |
| ④ | 投递消息 + 等发布确认 | **RabbitMQ** | `ReservationServiceImpl.publishReservationMessage` |
| ⑤ | 账本 → `PUBLISHED` | **MySQL** | `markPublishedWithRetry` |
| ⑥ | 消费者落库（扣名额 + 插预约行，**同一事务**）→ 账本 → `CONFIRMED` → 手动 ACK | **MySQL** | `ReservationPersistenceServiceImpl.persist` + `ReservationMessageConsumer` |

**★ 三个顺序上的讲究，这是这道题真正的考点：**

1. **① 在 ② 之前**：得先有 ID 才能记账。而且 ID 来自 Redis，说明**一次预约要打两次 Redis**（一次取 ID、一次抢名额）——这是 `RedisIdWorker` 的代价。
2. **② 在 ③ 之前**：**这是整个设计的支点。** 先在 MySQL 留下凭据，再去动 Redis 这个易失存储。见 Q38。
3. **⑤ 在 ⑥ 之后但在 ④ 之后**：账本置 `PUBLISHED` 表示『我确认消息投出去了』。但如果消息消费极快，⑥ 可能先于 ⑤ 执行——**所以状态图里有一条 `PRE_ACCEPTED → CONFIRMED` 的直达边，`PUBLISHED` 不是必经点。**」

**面试官继续追问：④ 里「等发布确认」是阻塞的吗？**

**追问回答**

「**是阻塞的，而且是这套设计里最大的性能问题。**

`publishReservationMessage` 里是这么等的：

```java
CorrelationData.Confirm confirm = correlationData.getFuture().get(5, TimeUnit.SECONDS);
```

**同步等 5 秒。** 所以：

- **正常情况**下 broker 几毫秒就回，用户几乎无感；
- **broker 慢的时候**，用户请求会**卡满 5 秒**才拿到 `503 预约结果待确认`；
- 更严重的是，**这 5 秒里 Tomcat 线程被占着**、**数据库连接可能也被占着**——如果 `submit` 上有 `@Transactional`，那 5 秒就在事务里（**所以 `submit` 绝对不能加 `@Transactional`**，见 Q39）。

**当前项目边界**：我在 README 和文档里没有给任何吞吐数字，因为**从没做过压测**。但如果被问『瓶颈在哪』，我的答案是：**同步等 confirm 是第一优先要改的点。** 改法是异步化——投递后立即返回『受理中』，用另一个线程或者 confirm 回调去推进账本状态，前端轮询结果。**当前项目没做这个改造。**」

## Q6. 这个项目最难的技术点是什么？

**推荐回答**

「**不是 Lua，也不是 MQ 配置，而是『Redis 扣了名额之后的那个时间窗口』。**

具体说：Lua 脚本执行完，名额已经扣掉了，但 MySQL 里还没有预约行——**中间这段『Redis 已扣、MySQL 未落』的窗口里的任何一步失败，都会造成名额泄漏或者超卖。**

我数过至少有四类失败会落在这个窗口里：

| 失败 | 现象 |
|---|---|
| 应用进程被 kill | Redis 已扣，消息从未发出 |
| RabbitMQ 不可达 | Redis 已扣，消息发不出去 |
| Confirm 超时 | **不知道**消息有没有到 |
| 消费者落库失败 | 消息到了，但 MySQL 写失败 |

**处理这个窗口的思路是三步：**

1. **先留下凭据**——在扣 Redis **之前**先往 `tb_reservation_request` 写一条 `PRE_ACCEPTED`。这样无论后面怎么失败，MySQL 里都有一条可被扫描的记录。
2. **区分『确定失败』和『不确定』**——只有**确定没投出去**（连接失败、NACK、消息被退回）才立即归还名额；**超时归为 `UNKNOWN`，绝不归还**，因为消息可能已经成功了，归还就会超发。
3. **用对账任务做最终裁决**——10 分钟后那条账本行还是非终态，就去查 `tb_reservation` 里有没有对应的行。有 → 说明成功了，推成 `CONFIRMED`；没有 → 说明失败了，归还名额推成 `COMPENSATED`。

**这三步合起来，才让『Redis 扣了名额之后宕机』从一个不可恢复的泄漏变成一个 10 分钟内自动收敛的状态。**"

**面试官继续追问：第 2 步里『超时绝不归还』的代价是什么？**

**追问回答**

「**代价是用户体验：用户会看到『失败』，而预约其实成功了。**

在 `UNKNOWN` 分支里代码抛的是 `ServiceUnavailableException("预约结果待确认，请稍后查询")`，HTTP 503。但如果消息其实已经入队并被消费落库了，那么：

- Redis 名额**合法地被占用**（对应一条真实存在的预约）；
- MySQL 里**有**这条预约；
- 用户去『我的预约』**能看到它**。

**所以用户实际是预约成功的，但他收到了一次错误提示。** 这是**有意的取舍**——我认为宁可让极少数用户在 broker 慢响应时看到『报错但实际成功』，也**绝不冒超发的风险**。因为超发是不可接受的业务事故，而一次错误的提示是可以解释的。

**要彻底消除这个体验问题**，正确的做法是改成『先返回 pending + 前端轮询结果』。**当前项目没做**——这是一个我主动承认的改进点。」

**举两个例子：**

- **`ReservationRequestStateTest.shouldRejectEmptyExpectedStatuses`**：钉住「CAS 的 `expectedStatuses` 不能为空数组」这个守卫。如果哪天有人去掉 `ReservationRequestServiceImpl` 里那个空数组检查，`.in(status, new Status[0])` 会生成 `IN ()` ——那是 SQL 语法错误，或者更糟：条件被静默忽略，**CAS 退化成无条件更新**。

**同时我要诚实说一个反面**：`MIGRATION_STATUS.md` 里登记了几处**『无判别力证据』**的改动——比如把 `LOGIN_USER_TTL` 从 36000 改成 30，他们没有写测试，因为**实验证明这个常量写不出有判别力的测试**（要么断言常量值本身，那是『为过而过』；要么走完整 HTTP 流程等 30 分钟）。**他们把这个登记下来，而不是假装测过了。** 我觉得这个态度比覆盖率数字更重要。」

# 第二层 · 技术选型与架构决策

## Q8. 为什么用 Redis 做名额，不直接用数据库行锁？

**推荐回答**

「**因为数据库行锁会把并发吞吐压死。**

如果不用 Redis，名额只能在 MySQL 里，那么『查名额 → 判断 → 扣减』就是三条 SQL，中间是超卖窗口。要堵住它只有两条路：

1. **`SELECT ... FOR UPDATE` 悲观锁**——把整行锁住，串行化所有抢同一个批次的学生；
2. **乐观锁（版本号/CAS 重试）**——冲突时失败重试，高并发下大量重试。

**两条路都会把压力集中在数据库行锁上。** 一个热门批次可能在同一秒有几百个请求，全部排队等同一把行锁——**数据库连接被长时间占用，响应时间线性上升**。

**Redis 的优势是：**

- **单线程模型 + Lua 脚本**，天生支持『把多个操作合成一个原子操作』，**不需要显式加锁**；
- **内存操作**，延迟在微秒级；
- 名额判定是**纯数值比较**，没有事务语义的需求——**它只是『谁能进』，不是『账本对不对』**。

**所以我把职责切开了：Redis 管准入（快、原子、易失），MySQL 管账实相符（慢、持久、可对账）。** 这也解释了为什么我允许两边不一致——**它们本来就不是同一份东西**。」

**面试官继续追问：那如果 Redis 挂了，系统还能用吗？**

**追问回答**

「**不能预约，但不会错。**

`reservation.lua` 的第一行就是：

```lua
if redis.call('EXISTS', KEYS[1]) == 0 then
    return 1        -- BATCH_NOT_OPEN
end
```

**Redis 不可达时，`tryAcquire` 会直接抛连接异常**，被 `submit` 的错误处理捕获，用户拿到失败。**没有『降级到直接写 MySQL』的兜底路径。**

**这个选择的理由**：如果降级到 MySQL，那么**准入判定的语义就变了**（从 Redis 计数变成 MySQL 条件更新），而**两边的计数本来就可能不一致**——降级会导致行为不可预测。**『拒绝服务』比『行为不确定』更安全。**

**顺带说一个更细的点**：即使 Redis 正常，**如果某个批次的 quota 键丢了**（LRU 淘汰、未持久化重启、误删），这个批次的 Lua 会永远返回 `BATCH_NOT_OPEN`——**所有人都预约不了，而 MySQL 里名额明明还在。**

**而且没有代码路径能重建这个键。** 我核对过所有会写这个键的地方：`publish` 用 `setIfAbsent` 写（但**要求批次是 `DRAFT`**）、`close`/`cancel` 只删、Lua 里只 `DECR`/`INCR`（都要求键已存在）。**对已经 `PUBLISHED` 的批次，没有任何办法重建。** 而 `fillRemainingQuotaFromRedis` 读不到键时会『回落 MySQL』——但那只是**展示层的回落**，准入层依然是拒绝的。**用户在页面上看到『还剩 5 个名额』，一点就报错。**

**这是这个项目里我认为最严重的一个缺口**，也是我主动记在文档里的『当前实现不足』。加固方向是给批次加一个『重建名额键』的管理接口（以 MySQL 的 `remaining_quota` 为准，用 `SELECT user_id FROM tb_reservation WHERE batch_id=? AND status IN (...)` 重建 `users` 集合）。」

## Q9. 为什么用 RabbitMQ？直接同步写库不行吗？

**推荐回答**

「**同步写库能保证正确性，但会把三件事绑在一起：响应时间、事务边界、重试能力。**

- **响应时间**：用户要等『扣 MySQL 名额 + 插预约行』两次写完成；
- **事务边界**：事务长了，数据库连接占用时间变长，并发能力下降；
- **重试能力**：用户在等着，失败了没有重试余地，只能立刻告诉他失败。

**用了 MQ 之后**，用户拿到的是『请求已被受理』——Redis 已扣名额、账本已落 `PRE_ACCEPTED`——落库在后台异步完成。**响应快、事务短、失败可重试。**

**代价是引入了最终一致的复杂度**：需要一个状态机跟踪进度、需要区分三种投递结果、需要一个定时对账任务收敛『事件从未发生』的故障、需要幂等消费应对重投。

**一句话总结这个取舍：MQ 把『同步的可靠性问题』换成了『异步的一致性问题』。** 这笔交易划不划算，取决于用户能否接受短暂的不确定状态。**预约场景可以**（点完就走，几秒后查『我的预约』能看到），所以成立。」

**面试官继续追问：那为什么不用 Kafka？**

**追问回答**

「**因为需要的特性 Kafka 给不了，或者要额外搭。**

这个项目真正用到的 RabbitMQ 能力是：

1. **`publisher-confirm`（`correlated` 模式）**——**每条消息**带 `CorrelationData` 回调，能拿到 ACK/NACK；
2. **`publisher-returns` + `setMandatory(true)`**——**路由失败**时消息被退回并触发回调；
3. **单条 `basicAck` / `basicNack(requeue=false)`**——消费者**逐条**控制确认；
4. **DLX / DLQ**——broker 原生死信路由。

**Kafka 的模型不一样**：它是分区日志 + 消费者位移（offset），**没有『单条消息确认』的概念**（只有位移提交），**也没有原生 DLX**——死信要靠自己写转发主题。用 Kafka 做这个场景，等于**放弃掉这套现成的可靠性原语，自己重造一遍**。

**而且这个项目的数据量完全不构成选 Kafka 的理由**——Kafka 的价值在吞吐量级（百万级/秒）和日志式回放，这里的量级差好几个数量级。

**所以 README 里也写了：不使用 Kafka 是『有意的设计取舍』，当前业务量级下它们是纯负债。**

**★ 但要承认另一面**：RabbitMQ 的 **`prefetch: 1`** 是为了保证消息级顺序和公平分发，这会**限制单个消费者的吞吐**——它一次只拿一条。如果将来真的上量，`prefetch` 和消费者并发数是第一批要调的参数。**当前项目没有做过这方面的调优或压测。**」

## Q10. 为什么用 MyBatis-Plus 而不是 JPA？

**推荐回答**

「**因为这个项目里手写 SQL 的地方很多，而 MyBatis-Plus 的 `LambdaUpdateWrapper` 正好是 CAS 写法的好载体。**

具体的：

1. **16 处条件更新（CAS）**。MyBatis-Plus 的写法很直白：

```java
update(null, new LambdaUpdateWrapper<ReservationBatch>()
        .eq(ReservationBatch::getId, id)
        .eq(ReservationBatch::getStatus, ReservationBatchStatus.PUBLISHED)   // ← CAS 条件
        .set(ReservationBatch::getStatus, ReservationBatchStatus.CLOSED));
```

`LambdaUpdateWrapper` 的**类型安全**（`ReservationBatch::getStatus` 而不是字符串）配合 IDE 重构，比手写 XML 强很多。

2. **复杂的 JOIN 查询用 XML**。`ReservationMapper.xml` 的列表查询要 `LEFT JOIN` 设备、实验室、批次三张表，还带条件过滤和排序，XML 写起来更直观。
3. **`markNoShows` 那种带子查询的批量 UPDATE** 也只能手写。

**选 JPA 的话**：CRUD 更省事，但**这套 CAS 条件更新还是要退回 `@Modifying @Query` 写原生 SQL**，而 JPA 的原生 SQL 体验还不如 MyBatis 直接。」

**面试官继续追问：MyBatis-Plus 只配了分页插件？还有别的可用插件没用吗？**

**追问回答**

「**对，`MybatisConfig` 里只有一个 `PaginationInnerInterceptor(DbType.MYSQL)`。三个常用的没配：**

1. **`OptimisticLockerInnerInterceptor` + `@Version`**——**这个项目有意没用**。因为它需要给表加 `version` 列，而**这个项目的并发控制全是业务语义的 CAS**（`WHERE status = 'PUBLISHED'`），比通用版本号更精确。加了版本号反而会和 CAS 条件打架。**`tb_reservation_batch` 也确实没有 `version` 列。**
2. **`BlockAttackInnerInterceptor`**——**这个挡住全表 UPDATE / DELETE 的插件没配。** 这是一个**真实的保护缺口**：如果哪天有人写了一个漏掉 `WHERE` 的 `update`，MyBatis-Plus 会**真的更新整张表**。当前代码里没有这样的写法，但**没有插件兜底**。
3. **`MetaObjectHandler`**——`createTime` / `updateTime` 的自动填充没配。但**这也不需要**，因为 DDL 里用了 `DEFAULT CURRENT_TIMESTAMP` 和 `ON UPDATE CURRENT_TIMESTAMP`，**由 MySQL 负责**。

**★ 第 3 点引出了一个必须知道的坑**（也是 `README §9` 记录的两个易错点之一）：**MySQL 的 `ON UPDATE CURRENT_TIMESTAMP` 在「写入的值与当前值相同」时不会更新时间戳。**

所以 `ReservationReconcileServiceImpl` 在对账失败退避时，**必须显式地写 `update_time`**：

```java
.update(null, wrapper.eq(...).set(ReservationRequest::getUpdateTime, LocalDateTime.now()))
```

**如果不显式写，只改 `fail_reason`，而 `fail_reason` 恰好和上次一样（比如反复都是同一个异常），那么 `ON UPDATE` 就不触发，`update_time` 不动，这条记录会永远留在『陈旧窗口』里被反复扫描、无法退避。** 这个坑有专门的回归用例：`ReservationReconcileTest.shouldAdvanceUpdateTimeWhenSameReconcileFailureRepeats`。」

## Q11. 登录为什么用 UUID token 而不是 JWT？为什么不用 Session？

**推荐回答**

「**先说不为什么用 Session**：Session 存在 **Tomcat 单机内存**里。这个项目要跑多实例（`lock:reservation:reconcile` 这个分布式锁的存在本身就证明了部署形态是多实例，异常场景 19 号就是『两个实例同时对账』）。多实例下 Session 会导致：

- 用户在第 1 个实例登录，请求被负载均衡分到实例 2 → **掉线**；
- 实例重启 → **该实例上所有用户全部掉线**。

只能靠 sticky session（牺牲负载均衡）或 session 复制（复杂且有一致性问题）。**Redis 是独立于应用实例的共享存储，天然解决**，顺带还解决了跨端问题（App/小程序带一个 `authorization` 请求头比 Cookie 自然）。

**再说为什么不用 JWT**：

JWT 的核心价值是**『无状态』——服务端不存东西，靠签名验证**。但**这个项目恰恰需要『有状态』**：

1. **要能踢人**——`logout` 就是 `DELETE login:token:{token}`，**删除后那个 token 立刻完全失效**。JWT 做不到这点（除非维护黑名单，那就又有状态了）；
2. **要能滑动续期**——`RefreshTokenInterceptor` 每次请求把 TTL 重置为 30 分钟。JWT 的过期时间**写在 payload 里、签了名，改不了**（要改就得重新签发）；
3. **要能存可变信息**——Redis 里存的是 Hash（`id` / `nickName` / `icon` / `role`），改了角色**下次请求就生效**。JWT 的 payload 是签发时固化的，**改角色得等 token 过期**。

**既然本来就要依赖 Redis 做会话存储，JWT 的『无状态』优势就完全用不上了——它只是一个更长的、还要额外验签的字符串。**

**★ 诚实说清两者的安全性**：UUID token 的安全性**依赖于 UUID 的不可预测性**（`UUID.randomUUID()` 是加密安全的随机源，122 位熵，不可枚举）**和 Redis 的访问控制**。它的弱点是：**如果 token 泄漏了，服务端无法区分是本人还是攻击者**（JWT 也一样）。所以真正重要的是 TTL 要短——这就是为什么 `LOGIN_USER_TTL` 从 36000 分钟压到了 30 分钟。」

**面试官继续追问：那你的 token 有什么已知的安全问题？**

**追问回答**

「**有三个，都是真实存在的，我主动说：**

1. **🔴 没有绝对有效期。** 30 分钟是**滑动过期**（`RefreshTokenInterceptor` 每次请求续期），**没有 absolute timeout**。所以**一个被盗的 token，只要攻击者持续请求，就永远不会失效**。正确做法是『滑动 TTL + 一个记录首次登录时间的绝对上限』，**当前没做**。

2. **🔴 验证码用后不删。** `UserServiceImpl.login` 校验通过后**没有 `DELETE login:code:{phone}`**，所以**同一个验证码在 2 分钟 TTL 内可以重复使用任意多次**。正确做法是校验成功后立即删除（或用 Redis 6.2 的 `GETDEL` 做原子取删），**验证码必须是一次性凭证**。

3. **🔴 `sendCode` 没有任何限流。** 可以对同一手机号无限次调用 `POST /user/code`。现在不会造成实际损失（因为 `UserServiceImpl.sendCode` 只是 `log.debug` 把验证码打出来，**根本没接短信网关**），但**一旦接上真实网关就是短信轰炸 + 真金白银的损失**。

**另外还有一个不那么严重的**：`tb_user.password` 这一列存在、`User` 实体里也有这字段，但**零读写**——密码登录从未实现，`LoginFormDTO` 里的 `password` 字段在 Phase 10 清理时已经删掉了。所以**种子管理员 `13900000001` 没有密码，只能验证码登录**（而验证码只打日志，本地要登录管理员得去控制台捞）。」

## Q12. 为什么 8 张表一个外键都没有？

**推荐回答**

「**这是一个一致的、有意的取舍**——整个 `db/` 目录 grep 不到一个 `FOREIGN KEY`。

**好处有三个：**

1. **迁移脚本无顺序耦合**——可以先建 `tb_equipment` 再建 `tb_laboratory`，不用管依赖顺序；
2. **删数据不需要级联处理**——`phase10_drop_legacy_tables.sql` 能直接 `DROP` 掉 10 张课程表，如果它们之间有外键就得按拓扑序删；
3. **高并发写没有外键的额外锁开销**——InnoDB 在插入子表行时会对外键引用的父表行加共享锁，高并发下这是真实的争用点。

**代价也有三个：**

1. **数据库不保证引用完整性**——`tb_equipment.laboratory_id` 可以指向一个不存在的实验室；
2. **删除依赖必须靠应用层自己检查**；
3. **孤儿数据只能靠 `LEFT JOIN` 让读不崩，不能靠约束拒写**。

**第 3 点在这个项目里有具体的体现**：`ReservationMapper.xml` 的预约列表查询用的是 **`LEFT JOIN`**（设备、实验室、批次三张都是）。所以**即使某台设备被删了，历史预约仍然能查出来**——只是设备名字段为 null，**不会因为 `INNER JOIN` 而『丢行』**。这是一个正确的选择：**用户的历史预约不应该因为管理员删了设备就凭空消失。**」

**面试官继续追问：那删除依赖的检查做得完整吗？**

**追问回答**

「**不完整，这里有一个真实的不对称，我要主动指出来：**

| 删除操作 | 检查依赖吗 |
|---|---|
| `deleteLaboratory` | ✅ **检查**——有设备依赖就拒绝 |
| `deleteEquipment` | ❌ **不检查**——删了之后，挂在这个设备上的 `tb_reservation_batch` 会成为孤儿 |

**`README §15` 只登记了 `deleteLaboratory` 的保护（『删除实验室是行为变更：现在会拒绝删除仍挂有设备的实验室』），完全没有提 `deleteEquipment` 也缺这个检查。**

**这个缺口的影响是可控的**（孤儿批次靠 `LEFT JOIN` 不会让读崩，而且批次本身还有 `status` 会拦住新预约），**但它是一个真实的漏项**——同一个项目里，两张有依赖关系的表，一张检查了一张没检查，**这种不对称本身就是缺陷的信号**。

**修法很简单**：在 `deleteEquipment` 里加一个 `selectCount` 查 `tb_reservation_batch`（可以只算非 `CANCELLED` 的）。**但当前代码没有。**」

## Q13. 为什么是单体应用，不用微服务？

**推荐回答**

「**因为这个项目的数据量级和团队规模都不构成拆分的理由，而拆分是有成本的。**

README §15 里明确写了这个取舍：**不使用微服务 / 注册中心 / 分库分表 / ES / Kafka / 分布式事务框架——当前业务量级下它们是纯负债。**

具体说，微服务会带来这些**必然的**新问题：

1. **分布式事务**——拆开之后『扣 Redis 名额』和『写 MySQL 预约行』如果跨服务，就没有本地事务可以兜底了。**但当前设计恰恰依赖了『账本 + 预约行在同一个库、可以用一个事务』**（`persist` 上有 `@Transactional`，把『扣名额』和『插预约行』绑在一起）。
2. **服务间调用失败**——本来一个 `selectById` 变成一次 RPC，多了超时、重试、熔断的复杂度。
3. **可观测性成本**——调用链追踪、日志聚合、指标采集，这些不建起来，微服务就是灾难。
4. **运维成本**——多套部署、配置、健康检查。

**而拆分能换来的『独立伸缩、独立部署、技术异构』在这个项目里一个都用不上**——因为**瓶颈是数据一致性逻辑本身，不是某个模块的计算量**。

**★ 什么时候应该拆？** 如果将来出现：预约模块 QPS 远超其他模块需要独立扩容、或者死信治理要独立成运维平台、或者对账任务需要独立的失败隔离——那时候再拆。**现在拆就是提前优化。**」

**面试官继续追问：那这个项目里最像『微服务』的设计是什么？**

**追问回答**

「**是分布式锁——`lock:reservation:reconcile`。**

这个锁的存在说明：**对账任务被设计成可以在多个实例上同时运行，但同一时刻只有一个真正执行。**

```java
RLock lock = redissonClient.getLock(RedisConstants.LOCK_RESERVATION_RECONCILE_KEY);
locked = lock.tryLock(0, TimeUnit.MILLISECONDS);    // 不等，抢不到就跳过整轮
if (!locked) { log.debug(...); return; }
```

**而这里有一个我认为是这个项目最值得讲的设计判断**——开发者把锁的定位写在了方法注释里：

> **『定时调度薄壳：分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证。』**

**换句话说：锁只管效率，正确性不押在锁上。**

**为什么不押在锁上？** 因为**分布式锁本身会失效**——GC 停顿导致租约过期、网络分区、看门狗线程挂掉。**押在锁上，锁一失效数据就错了；押在数据库条件更新和幂等操作上，锁失效最坏只是多做一遍无用功。**

所以对账任务有**两层保护**：

1. **锁**（性能层）：抢不到就跳过；
2. **CAS + 幂等**（正确性层）：账本迁移是 `UPDATE ... WHERE request_id = ? AND status IN (非终态)`，**只有一个实例的 `affectedRows == 1`**，另一个计入 `skipped`；Redis 归还走 `reservationRollback.lua`，**`SREM` 的返回值就是幂等令牌**。

**这就是异常场景 19 号『两个实例同时对账』的完整答案：即使锁完全失效、两个实例都扫了同一批，结果仍然与单实例完全相同。**」

## Q14. 你的 pom.xml 里为什么排除了 Spring Boot 管理的 Redis 依赖？

**推荐回答**

「因为**要覆盖 Boot 2.3.12 管理的版本**，而且**要补一个 Boot 没引入但必须有的依赖**。

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-data-redis</artifactId>
    <exclusions>
        <exclusion><artifactId>spring-data-redis</artifactId><groupId>org.springframework.data</groupId></exclusion>
        <exclusion><artifactId>lettuce-core</artifactId><groupId>io.lettuce</groupId></exclusion>
    </exclusions>
</dependency>
<dependency><artifactId>spring-data-redis</artifactId><version>2.6.2</version></dependency>
<dependency><artifactId>lettuce-core</artifactId><version>6.1.6.RELEASE</version></dependency>
<dependency><artifactId>commons-pool2</artifactId></dependency>
```

**三个具体原因：**

1. **Boot 2.3.12 管理的 Lettuce 版本太旧**，需要升到 6.1.6.RELEASE（同时 `spring-data-redis` 也要配套升到 2.6.2，否则 API 不兼容）；
2. **`commons-pool2` 是 Lettuce 连接池的必需依赖，但 Boot 的 starter 默认不引入它**——**不加它，`spring.redis.lettuce.pool.*` 的配置完全不生效**，因为连接池根本不存在；
3. `spring-boot-starter-data-redis` 还是会引入 Lettuce 的**自动配置**，所以不能整个排除，只能**排除掉传递依赖再显式声明版本**。

**★ 这里有一个反差值得注意**：`application.yaml` 里**精细调了 Lettuce 连接池**——

```yaml
spring.redis.lettuce.pool:
  max-active: 10
  max-idle: 10
  min-idle: 1
  time-between-eviction-runs: 10s
```

**但完全没有配 `spring.datasource.hikari.*`**——MySQL 连接池用的是 **Hikari 的默认值（`maximum-pool-size: 10`、`connection-timeout: 30s`）**。

**这个不对称是有代价的**：这 10 个 MySQL 连接要和**用户请求 + MQ 消费者线程 + 对账定时任务**共享。如果对账扫 200 条记录、每条都要查库，连接池很容易被打满，而 `connection-timeout` 默认 30 秒会导致请求**挂 30 秒才报错**。

**我把它记在文档里作为一个真实的配置缺口。** 加固方向：显式配 Hikari（`maximum-pool-size` 按并发量调、`connection-timeout` 降到 3–5 秒让失败快速暴露），并给对账任务用独立的连接池或限流。**当前没做。**」

**面试官继续追问：那你这套版本覆盖会不会有兼容风险？**

**追问回答**

「**有，而且这是一个真实的维护成本。**

`spring-data-redis` 2.6.2 是给 Spring Framework 5.3.x 设计的，而 **Boot 2.3.12 带的是 Spring Framework 5.2.x**。这是一个**跨小版本的混搭**。

它现在能工作，是因为**这个项目用到的 Redis API 都很基础**：`StringRedisTemplate` 的 `opsForValue` / `opsForHash` / `opsForSet`、`execute(RedisScript, keys, args...)`、`expire`、`delete`。这些 API 在 2.x 里是稳定的，没有用到 2.6 才引入的新特性。

**风险在于**：
1. **升级 Boot 时会打架**——如果哪天升到 Boot 2.7+，它管理的 `spring-data-redis` 版本可能又和现在显式声明的 2.6.2 冲突，**这套 exclusion 就要重新调整**；
2. **运行时可能出现 `NoSuchMethodError`**——如果某个代码路径恰好走到一个 2.6 修改过签名的方法。**当前没有触发，但这个风险是存在的、无法静态排除的**；
3. **没有测试能覆盖这个风险**——单元测试跑在同一个 classpath 上，不会发现版本不匹配。

**正确的长期做法是升级整个 Boot 版本**（顺带把 Java 8 也升上去），而不是局部覆盖依赖版本。**但升级 Boot 的兼容改动量很大，所以当前选择了『先让它跑起来并记录风险』。** 这属于 README 里说的『诚实登记』那一类。」

# 第三层 · Redis 与 Lua 高并发准入

## Q15. 讲讲 `reservation.lua` 做了什么。

**推荐回答**

「它把**一次预约的准入判定**做成了一个原子操作。完整脚本 27 行，逐段是：

```lua
-- ① 闸门：名额键不存在 = 批次没开放
if redis.call('EXISTS', KEYS[1]) == 0 then
    return 1                                    -- BATCH_NOT_OPEN
end

-- ② 预约窗口校验
local now = tonumber(ARGV[2])
local bookingStartTime = tonumber(ARGV[3])
local bookingEndTime = tonumber(ARGV[4])
if now < bookingStartTime then return 4 end     -- BOOKING_NOT_STARTED
if now > bookingEndTime then return 5 end       -- BOOKING_EXPIRED

-- ③ 名额校验
local quota = redis.call('GET', KEYS[1])
if not quota or tonumber(quota) <= 0 then
    return 2                                    -- SOLD_OUT
end

-- ④ 去重校验
if redis.call('SISMEMBER', KEYS[2], ARGV[1]) == 1 then
    return 3                                    -- DUPLICATE
end

-- ⑤ 真正扣减
redis.call('DECR', KEYS[1])
redis.call('SADD', KEYS[2], ARGV[1])
redis.call('EXPIRE', KEYS[2], ARGV[5])
return 0                                        -- SUCCESS
```

**参数约定**：`KEYS[1]` = 名额计数器（String），`KEYS[2]` = 已预约用户集合（Set）；`ARGV[1]` = userId，`ARGV[2..4]` = now / bookingStart / bookingEnd（都是**秒级 epoch**），`ARGV[5]` = users 集合的 TTL 秒数。

**★ 关键点：第 ③④ 步的『检查』和第 ⑤ 步的『扣减』在同一个脚本里，中间不可能被其他命令插入。** 这就是它防超卖的全部原理。」

**面试官继续追问：为什么用 `tonumber(ARGV[2])` 而不是直接比较？**

**追问回答**

「因为**Redis 的 Lua 里所有参数都是字符串**。

`ARGV` 是从 `stringRedisTemplate.execute(script, keys, args...)` 传进来的，Spring Data Redis 把它们序列化成字符串。所以 `ARGV[2]` 是 `"1759824000"` 这样的字符串。

**如果不 `tonumber` 就比大小，Lua 的 `<` / `>` 对两个字符串是做字典序比较**，会得到完全错误的结果——比如 `"1000" < "900"` 在字典序里是 `true`（因为 `'1' < '9'`），**时间比较就彻底错了**。

**`ARGV[1]`（userId）故意不做 `tonumber`**，因为它要传给 `SISMEMBER` / `SADD`——**集合里的成员就是字符串**，转了反而要对齐格式。它是 `userId.toString()` 传进来的。

**`redis.call('GET', KEYS[1])` 返回的 `quota` 也要 `tonumber`**——同理，Redis 返回的是字符串。而且代码里做了 `not quota` 的判断：**如果键在两行之间被删了，`GET` 会返回 `false`**（Lua 里 Redis 的 nil 是 `false`），这时也按 `SOLD_OUT` 处理，避免 `tonumber(false)` 报错。」

## Q16. 为什么必须用 Lua？拆成多条命令会怎样？

**推荐回答**

「**因为『检查』和『扣减』之间的空隙就是超卖窗口。**

如果用 Java 分三条命令写：

```java
if (redisTemplate.opsForSet().isMember(usersKey, userId)) return DUPLICATE;
Integer quota = Integer.valueOf(redisTemplate.opsForValue().get(quotaKey));
if (quota <= 0) return SOLD_OUT;
redisTemplate.opsForValue().decrement(quotaKey);      // ← 和上面的检查之间是空隙
redisTemplate.opsForSet().add(usersKey, userId);
```

**两个并发请求可以这样交错：**

```
时刻  请求 A                      请求 B
 T1   SISMEMBER → false（不重复）
 T2                              SISMEMBER → false（也不重复）  ← 两个都通过了检查
 T3   GET quota → 1
 T4                              GET quota → 1
 T5   DECR → 0
 T6                              DECR → -1                     ← 超卖！
```

**这就是典型的 TOCTOU（Time-of-Check to Time-of-Use）问题。**

**Redis 是单线程处理命令的**，所以**一条命令本身是原子的**——但**多条命令之间可以被其他客户端的命令插入**。Lua 脚本在 Redis 里是**作为一个整体执行的**，执行期间**不会处理其他任何客户端的命令**。所以把它写进 Lua，那个空隙就不存在了。

**★ 一个重要的细节**：Redis 6 之后有 `MULTI`/`EXEC` 事务，但**事务里不能根据中间结果做分支**——`EXEC` 是把命令**排队**然后一次性执行，**你没法在事务里写 `if quota <= 0 then ... end`**。所以这个场景**只能用 Lua**，不能用事务。

**★ 而且这个项目连『返回码』都放进了 Lua**：脚本返回 1/2/3/4/5 而不是抛异常，Java 侧用 `ReservationResultCode.fromCode` 映射成枚举和中文消息。**这样做的好处是所有判定逻辑在同一个脚本里可读地排在一起，Java 侧只负责翻译。**」

**面试官继续追问：那 Redisson 的分布式锁不能替代 Lua 吗？**

**追问回答**

「**能，但代价大得多，而且引入了新的失败模式。**

用 Redisson 的话得这么写：

```java
RLock lock = redissonClient.getLock("lock:batch:" + batchId);
lock.lock();
try {
    // 查名额、查时段、查重复、扣减
} finally {
    lock.unlock();
}
```

**问题：**

1. **锁的粒度是批次**，同一批次的所有请求**完全串行化**——`DECR` 本身是原子的，**却被一把锁串起来了**。Lua 的做法**没有锁**，靠单线程天然串行，吞吐高得多；
2. **多了一次网络往返**（加锁）+ **一次**（解锁），而 Lua 只有一次；
3. **引入了锁失效的新故障模式**——租约到期而业务没执行完，就会有两个线程同时进临界区；看门狗能缓解，但看门狗线程本身也可能挂。

**所以正确的判断是：能用『单条原子的服务端操作』解决的地方，就不要用分布式锁。** Lua 脚本就是 Redis 提供的『自定义原子操作』机制。

**★ 但这个项目里两种都用了，因为它们解决的问题不同：** Lua 解决**跨用户的并发准入**（无锁、高吞吐）；Redisson 锁解决**同一用户的消息串行化**和**对账任务的多实例互斥**（这两个场景需要的是『互斥』，不是『原子计数』）。**见 Q26。**」

## Q17. 那 6 个返回码分别是什么？顺序有讲究吗？

**推荐回答**

「| 码 | 枚举 | 消息 | 含义 |
|---|---|---|---|
| 0 | `SUCCESS` | — | 抢到了 |
| 1 | `BATCH_NOT_OPEN` | 批次未开放预约 | 名额键不存在 |
| 2 | `SOLD_OUT` | 名额已约满 | 名额 ≤ 0 |
| 3 | `DUPLICATE` | 你已预约过该批次 | 已在去重集合里 |
| 4 | `BOOKING_NOT_STARTED` | 预约尚未开始 | `now < bookingStartTime` |
| 5 | `BOOKING_EXPIRED` | 预约已截止 | `now > bookingEndTime` |

**★ 顺序非常有讲究，有两处值得说：**

**第一，时段检查（4/5）在名额检查（2）之前。** 所以一个已经过了预约窗口、而且名额也满了的批次，用户看到的是**『预约已截止』而不是『名额已约满』**——**这是更准确的信息**。如果反过来，用户会以为是名额问题而反复重试，而实际上**再等也没用**。

**第二，去重检查（3）在名额检查（2）之后。** 这有一个**容易被忽略的副作用**：**如果名额已经耗尽了，那么一个『已经预约过的用户』再点一次，拿到的是 `SOLD_OUT(2)` 而不是 `DUPLICATE(3)`。**

从用户体验看这是**次优的**——更准确的提示应该是『你已预约过该批次』。**但它不影响正确性**，因为两个码最终都是被拒绝。

**★ 而且这个顺序是必要的**：如果去重检查放在名额检查之前，那么一个已预约的用户在名额满了之后重试，会拿到 `DUPLICATE`；**但如果中间他已经取消过一次**（Redis 的 `users` 集合里已经没有他了），这个检查就放行，然后走到名额检查——**这仍然是正确的**。所以两种顺序都安全，**当前的选择只是把『批次还能不能约』这个更基础的信息排在了前面**。」

**面试官继续追问：这些返回码在 Java 侧怎么处理的？**

**追问回答**

「`ReservationQuotaExecutor.tryAcquire` 把 `Long` 转成 `ReservationResultCode` 枚举，**并且对两个异常情况做了防护**：

```java
if (rawCode == null || rawCode < Integer.MIN_VALUE || rawCode > Integer.MAX_VALUE) {
    log.error("预约 Lua 返回异常：{}", rawCode);
    throw new BadRequestException("预约失败，请稍后重试");
}
try {
    return ReservationResultCode.fromCode(rawCode.intValue());
} catch (IllegalArgumentException e) {
    log.error("预约 Lua 返回未知码：{}", rawCode);
    throw new BadRequestException("预约失败，请稍后重试");
}
```

**两个防护都是有必要的**：

1. **`rawCode == null`**：`stringRedisTemplate.execute` 在脚本没返回值或连接异常时可能返回 null；
2. **范围检查 + `fromCode` 的 `IllegalArgumentException`**：`fromCode` 是遍历匹配，**遇到未知码抛 `IllegalArgumentException`**。这是**防御性的**——如果哪天有人在 Lua 里加了新的 `return 6` 但忘了同步枚举，**这里会抛异常而不是返回一个 null 枚举**（返回 null 的话，`submit` 里的 `if (resultCode != SUCCESS)` 会以为是失败，**然后 `resultCode.name()` 会 NPE**）。

**这两处体现了一个原则：从外部系统（这里是 Redis Lua）拿到的值，一定要做边界校验再转成内部类型。** 因为 Lua 是**独立于 Java 编译期检查**的——枚举少一个值，编译器不会告诉你。」

## Q18. 时段在 Java 里已经校验过了，Lua 里为什么还要再校验一次？

**推荐回答**

「**因为这是两道不同的防线，防的是两类不同的情况。**

**Java 侧的校验**在 `ReservationServiceImpl.submit` 里：

```java
LocalDateTime now = LocalDateTime.now();
if (now.isBefore(batch.getBookingStartTime())) throw new BadRequestException("预约尚未开始");
if (now.isAfter(batch.getBookingEndTime()))   throw new BadRequestException("预约已截止");
```

它用的是**从 MySQL 查出来的批次对象**——所以它防的是『**批次的时间配置本身不允许现在预约**』。

**Lua 侧的校验**用的是**从 Java 传进去的时间戳**——`ARGV[2..4]`。

**★ 那为什么需要两道？** 三个理由：

1. **快速失败，省掉一次 Redis 往返**。Java 侧先拦掉明显不合法的请求，**在写账本之前就拒绝了**——更省钱、更省事（`submit` 的前置检查在 `createPreAccepted` **之前**）；
2. **`ReservationQuotaExecutor.tryAcquire` 的契约要求窗口是开放的**。这个类的注释明确写了：『**调用方已确认窗口开放**：now ≤ bookingEndTime ≤ startTime < endTime，因此 Set 的 TTL 恒为正。』——**Java 侧的校验是这个前置条件**，如果没有它，`ttlSeconds` 可能算出负数（虽然 Redis 会忽略负 TTL，但语义上是错的）；
3. **纵深防御**——如果哪天 `submit` 里的检查被注释掉了（或者有别的调用方绕过它），**Lua 仍然会拒绝**。

**★ 但要注意一个真实的边界**：`submit` 里那个 `now` 是**在发 Redis 命令之前算的**，然后**原样传给 `tryAcquire`** 当作 Lua 的 `now`。所以：

- **Lua 里的时段判定用的是『请求开始时的时刻』**，不是『Lua 执行的时刻』；
- **两个时刻之间的差是『前置检查 + 写账本 + 发 Redis』的耗时**——通常是毫秒级，**但理论上如果这一段卡了（比如写账本遇到慢查询），Lua 判断的可能是几秒前的时间**。

**这个偏差是刻意的**：用同一个 `now` 意味着**『这次请求的准入判定以请求开始时刻为准』**，语义更一致（否则会出现『Java 说没到点、Lua 说到了』的诡异情况）。**而且 `now` 还被用来算 users 集合的 TTL**——所以它必须早于 Redis 调用。

**另外注意边界是『左闭右闭』**：`if now < bookingStartTime then return 4`（用 `<`，所以 `now == bookingStartTime` **通过**）；`if now > bookingEndTime then return 5`（用 `>`，所以 `now == bookingEndTime` **通过**）。Java 侧用 `isBefore`/`isAfter` **取反**，语义完全一致——**两边不能一个闭一个开，否则窗口边界上会出现『Java 放行、Lua 拒绝』的不一致。**」

## Q19. 名额键的 TTL 是怎么定的？为什么 +24 小时？

**推荐回答**

「名额键 `reservation:batch:quota:{id}` 的 TTL 是**在 `publish` 的时候设置的**，值是：

```java
long ttlSeconds = Duration.between(
        now,
        batch.getEndTime().plusHours(RESERVATION_BATCH_QUOTA_TTL_BUFFER_HOURS))  // +24 小时
        .getSeconds();
if (ttlSeconds <= 0) throw new BadRequestException("批次时间设置不合法");
stringRedisTemplate.opsForValue().setIfAbsent(quotaKey, totalQuota, ttlSeconds, SECONDS);
```

所以 TTL = **批次使用结束时间 + 24 小时 − 当前时间**。

**为什么是『使用结束时间 + 缓冲』而不是『预约截止时间』？**

因为**预约截止之后，名额还需要被继续读写**：

| 场景 | 发生时间 | 需要名额键吗 |
|---|---|---|
| 学生抢名额 | 预约窗口内 | ✅ |
| 取消预约（归还名额） | 直到 `endTime` 都可以取消 | ✅ **`endTime` > `bookingEndTime`** |
| 对账归还名额（补偿） | `bookingEndTime` 之后 10 分钟起 | ✅ |
| 核验 / 爽约判定 | `endTime` 之后 | ❌（不碰 Redis） |

**关键就是『取消』**：`ReservationLifecycleServiceImpl.cancel` 只检查 `now <= batch.endTime`，**不看批次状态、也不看预约窗口**。所以**学生在预约截止之后、使用结束之前仍然可以取消**——这时候 `reservationRollback.lua` 要 `SREM` + `INCR`，**两操作都要求 key 存在**。

**如果 TTL 按 `bookingEndTime` 算，那么在 `bookingEndTime` 到 `endTime` 之间取消预约时，键已经过期了**：

- `SREM` 返回 0 → 脚本 `return 0` → **不 `INCR`**；
- MySQL 侧 `remaining_quota + 1` **照常执行**；
- 结果：**MySQL 名额恢复了，Redis 键不存在** —— 这时候批次如果还在 `PUBLISHED` 状态，**用户看到有名额（`fillRemainingQuotaFromRedis` 回落 MySQL）但 Lua 返回 `BATCH_NOT_OPEN`**（就是 Q8 讲的『名额键丢失』缺口）。

**所以 +24 小时的作用是：保证名额键在所有可能用到它的操作都结束之后才过期。** 24 小时是一个**宽松的安全余量**——`endTime` 之后理论上不再有学生操作了，但留一天缓冲可以覆盖『用户隔夜才想起来取消』这种情况。」

**面试官继续追问：那为什么不干脆不设 TTL，让它永久存在？**

**追问回答**

「**因为 Redis 是缓存，不能当永久存储用，而且永久键会无限堆积。**

如果不设 TTL：

1. **内存无界增长**——每个批次一个键 + 一个 users 集合，虽然 users 集合有 TTL，但**名额键会永久留着**。批次是持续创建的，键会无限堆积；
2. **依赖 Redis 的淘汰策略**——`application.yaml` 里**没有配置 `maxmemory-policy`**（那是服务端配置）。如果是 `noeviction`，Redis 内存满了写请求直接报错；如果是 `allkeys-lru`，**它可能淘汰掉还没结束的批次的名额键**——那就直接触发了 Q8 说的『键丢失』缺口；
3. **语义上 Redis 不该是权威**——MySQL 才是权威。让 Redis 键长期存在会让『Redis 是权威』这个误解更容易发生。

**★ 但这里要诚实指出一个真实的问题**：因为名额键**只在 `publish` 时被创建**（`setIfAbsent`，且要求批次是 `DRAFT`），而**没有任何代码路径能从 MySQL 重建它**，所以 **TTL 到期对已经 `PUBLISHED` 的批次来说是一个不可恢复的事件**——键过期了，批次就再也约不上了。

**正常情况下 24 小时缓冲足够**（批次早就该用完了）。**但如果管理员的批次 `endTime` 设得很远**（比如半年后），键会存活半年——**这没问题**。**真正的问题是被 Redis 淘汰或误删**，那时 TTL 就不是保护而是**定时炸弹**了。

**加固方向**：给批次加一个从 MySQL 重建名额键的管理接口；或者把 `maxmemory-policy` 显式设成 `volatile-lru` 并把名额键设成 no-evict（但 Redis 没有 per-key 的 no-evict）。**当前两者都没做。**」

## Q20. 为什么名额键在 Lua 里不设 `EXPIRE`，而去重集合设了？

**推荐回答**

「因为**它们的生命周期语义不同，而 TTL 的设置点也就不同。**

看 Lua 的最后三行：

```lua
redis.call('DECR', KEYS[1])              -- 名额键：只扣，不设 EXPIRE
redis.call('SADD', KEYS[2], ARGV[1])     -- 去重集合：加成员
redis.call('EXPIRE', KEYS[2], ARGV[5])   -- ★ 只有 KEYS[2] 设了 TTL
```

**为什么只有 `KEYS[2]` 设 TTL？**

**① 名额键的 TTL 已经在 `publish` 时设好了，而且不应该被刷新。**

如果 Lua 里也对 `KEYS[1]` 做 `EXPIRE`，那么**每次有人抢名额都会把 TTL 重置为『现在 + 到 endTime + 24h』**。这看起来无害（甚至像是延长了寿命），但**它让 TTL 变成了一个滑动的值**——键的过期时间会随着访问不断变化，**不可预测**。而 `publish` 时设置的是一个**固定的绝对时间**（`endTime + 24h`），这是**可推理的**。

**② 去重集合的 TTL 必须在第一次写入时设置，而 Lua 是唯一能保证这一点的地方。**

`SADD` 和 `EXPIRE` **必须在同一个原子操作里**——否则会出现两种坏情况：

| 情况 | 后果 |
|---|---|
| `SADD` 成功但 `EXPIRE` 没执行（进程崩了） | **集合永久存在**——该批次的所有 userId 永远留在里面 |
| 先 `EXPIRE` 再 `SADD` | 键还不存在，`EXPIRE` **返回 0 不生效**，等于没设 |

**所以 `SADD` + `EXPIRE` 必须放在 Lua 里连着做。** 这也解释了为什么 `ARGV[5]` 要在 Java 侧算好传进来（`ReservationQuotaExecutor.tryAcquire` 里算的，见 Q19）——**Lua 里不方便做日期计算，而且把时间计算的职责留给 Java 更清晰**。

**③ 集合成员不能单独设 TTL，所以只能整键过期。**

Redis **没有『给 Set 里的某个成员设 TTL』的功能**。所以去重集合只能**整体过期**。这也是为什么 TTL 要用『`endTime + 24h`』——**只要批次彻底结束后集合过期，里面的所有成员就一起被清掉了**，不需要单独清理。」

**面试官继续追问：那 `EXPIRE` 放在 `SADD` 后面，不是每次都会重置 TTL 吗？**

**追问回答**

「**是的，每次成功的预约都会把去重集合的 TTL 重置一次。** 但这**正是想要的**——因为 `ARGV[5]` 的值是 `endTime + 24h − now`，每次重算出来的**绝对过期时刻是不同的**：

```
第一次抢（T1）  EXPIRE = (endTime + 24h) − T1
第二次抢（T2）  EXPIRE = (endTime + 24h) − T2      ← T2 > T1，所以这个值更小
```

**所以绝对过期时刻始终是 `endTime + 24h`，是固定的。** 每次 `EXPIRE` 传的秒数在变小，但算出来的截止时刻不变。**这正是『用相对 TTL 表达绝对过期时间』的标准做法。**

**★ 而名额键不一样**——它的 TTL 只在 `publish` 设一次，之后**不再被触碰**。所以名额键的 TTL 从始至终是『`publish` 那一刻算出的 `endTime + 24h − publishTime`』，而**去重集合每次都被刷新到同一个绝对时刻**。

**严格说，两者最终的过期时刻是同一个**（都是 `endTime + 24h`），因为 `publish` 时算的秒数就是从 `publishTime` 到那个时刻。**只是名额键用『设一次』达成，去重集合用『每次刷新』达成。**

**最后一个细节**：`EXPIRE` 只在**成功抢名额**时执行（`return 0` 那条路径），所以**被拒绝的请求不会刷新 TTL**。这是对的——拒绝不应该延长任何东西的寿命。」

## Q21. 20 个人同时抢 5 个名额，具体会发生什么？

**推荐回答**

「**恰好 5 个人成功，15 个人被拒，而且是一个确定的数字，不是一个概率。**

**为什么是确定的？因为 Redis 单线程 + Lua 原子。** 20 个 Lua 脚本请求到达 Redis 后会被**排队**，一个一个执行。前 5 个执行时 `quota > 0` 成立 → `DECR` → 返回 0；从第 6 个开始，`quota` 已经是 0 → 返回 **2 `SOLD_OUT`**。

| 请求序 | `quota`（执行前） | 结果 |
|---|---|---|
| 1–5 | 5,4,3,2,1 | 0 `SUCCESS`，`DECR` 后变成 4,3,2,1,0 |
| 6–20 | 0 | 2 `SOLD_OUT` |

**四条防线在这之后的角色：**

| 层 | 在这个场景里做什么 |
|---|---|
| ① **Lua** | **决定了 5 这个数字**（主防线） |
| ② **Redisson 用户锁** | **不涉及**——20 个是不同用户，锁的粒度是 userId，锁的都是不同的键 |
| ③ **条件更新** `WHERE remaining_quota > 0` | **应该全部成功**（20 个里只有 5 个会走到这里）。如果这里出现 `QUOTA_CONFLICT`，**说明 Redis 计数和 MySQL 不一致了** |
| ④ **唯一索引** `uk_user_batch_active` | **不涉及**——不同用户不同键 |

**最终状态**（假设 15 个失败请求都已即时补偿，因为 `SOLD_OUT` 是**即时返回**的——`submit` 里 Lua 返回非 0 时**当场**把账本置 `COMPENSATED`，不需要等对账）：

| 存储 | 状态 |
|---|---|
| Redis | `quota = 0`；users 集合含 5 个 userId |
| MySQL | `tb_reservation` 新增 5 行 `RESERVED`；`batch.remaining_quota = 0` |
| 账本 | 20 行：5 条 `CONFIRMED` + 15 条 `COMPENSATED`（`fail_reason = "SOLD_OUT"`） |

**用户视角**：5 个人拿到 `reservationId`，15 个人拿到 `400 名额已约满`。

**★ 注意一个设计细节**：那 15 个失败的请求**每一条都在 MySQL 里留下了一行账本记录**（`PRE_ACCEPTED` → 立即 `COMPENSATED`）。这不是浪费——**因为账本是在扣 Redis 之前写的，那时还不知道会失败**。而这些行会**永远留在表里**（终态，对账不扫）。这是**审计能力**，也是**表会持续增长**的原因。」

**面试官继续追问：这算高并发吗？能扛多少？**

**追问回答**

「**20 个并发完全不算高并发，而且我给不出『能扛多少』的数字——因为这个项目从没做过压测。**

**我要明确说清楚这一点，不能编。** README 和文档里也没有任何吞吐/延迟数据。

**但我可以做定性分析，说清瓶颈在哪：**

**单次预约请求的开销是：**

1. 一次 Redis `INCR`（取 ID）
2. 一次 MySQL `INSERT`（写账本）
3. 一次 Redis Lua（抢名额）
4. 一次 MQ 投递 + **同步等 confirm，超时 5 秒**
5. 一次 MySQL `UPDATE`（账本置 `PUBLISHED`）
6. 异步：消费者再打一次 Redis（Redisson 加锁）→ 一次 MySQL 事务（扣名额 + 插行）→ 一次 MySQL `UPDATE`（账本置 `CONFIRMED`）→ 一次 Redis（解锁）

**所以一次预约要打 4～5 次 Redis + 3～4 次 MySQL + 1 次 MQ，而且第 4 步是同步阻塞的。**

**瓶颈判断：**

- **第一优先：同步等 confirm。** 正常几毫秒，但 broker 慢时会卡满 5 秒，期间 Tomcat 线程和数据库连接都被占着。**这是最该改的一点**——改成异步（投递后立即返回『受理中』，confirm 回调里推进账本状态）。
- **第二：MySQL 连接池。** Hikari 默认 10 个连接（`application.yaml` 没配 `spring.datasource.hikari.*`），而这 10 个要和用户请求、消费者、对账任务共享。
- **第三：账本表的写入量。** 每次预约（**包括失败的**）都要写一次账本 + 一次 CAS。**失败的请求也写库**，这是为了可审计性付的代价。

**Redis 侧反而不是瓶颈**——Lua 脚本极短，而且是单线程顺序执行，**它的吞吐上限远高于后面的 MySQL 写入**。**所以这个系统的瓶颈在持久化层，不在缓存层。** 这也从反面印证了 Q8 的判断：**Redis 确实解决了最尖锐的并发准入问题，但它不是整个系统的性能上限所在。**」

## Q22. Redis 单线程，你的 Lua 脚本会不会阻塞 Redis？

**推荐回答**

「**会阻塞，但阻塞时间可以忽略——因为这个脚本里没有慢操作。**

**先说清 Redis 的单线程模型**：Redis 用**单线程处理命令**（6.0 之后网络 IO 是多线程的，但**命令执行仍然是单线程**）。所以**任何一条命令执行期间，其他所有客户端的命令都在排队**。Lua 脚本因为是『一个整体』，**整个脚本的执行时间就是阻塞时间**。

**所以判断 Lua 会不会阻塞，就是判断『脚本有多慢』。我的脚本里有 8 个 Redis 调用：**

| 调用 | 复杂度 |
|---|---|
| `EXISTS` | O(1) |
| `GET` | O(1) |
| `SISMEMBER` | O(1) |
| `DECR` | O(1) |
| `SADD` | O(1) |
| `EXPIRE` | O(1) |

**全部是 O(1) 操作**，加上几次字符串转数字。**总耗时在微秒级**，所以阻塞时间可以忽略。

**★ 下面是真正要小心的地方——Lua 脚本阻塞 Redis 的几种情形：**

1. **`KEYS *` / `SMEMBERS` / `HGETALL` 这类 O(N) 命令**——如果 `N` 是几十万，会阻塞几百毫秒甚至更久。**我的脚本里没有任何 O(N) 命令**（`SISMEMBER` 是 O(1)，不是 `SMEMBERS`）；
2. **循环里做大量操作**——比如遍历一个 Set 逐个删。**脚本里没有循环**；
3. **死循环**——Lua 脚本里写了个 `while true`。**Redis 有 `lua-time-limit`（默认 5 秒）**，超时后 Redis 会开始**回复其他客户端 `BUSY` 错误**，但这**不会自动杀掉脚本**——只能 `SCRIPT KILL`（仅当脚本没写过数据）或 `SHUTDOWN NOSAVE`。**这是生产事故级别的问题**；
4. **脚本里做日期计算 / 复杂字符串处理**——Lua 的解释执行比 C 慢很多。**这也是为什么我把 TTL 的计算放在 Java 侧（`ReservationQuotaExecutor.tryAcquire`）算好再传进 `ARGV[5]`，而不是在 Lua 里算**。

**★ 顺带说一个设计上的好处**：因为脚本**只有 27 行、无循环、全 O(1)**，它**不可能成为 Redis 的性能瓶颈**。真正会让 Redis 吃力的是**大量客户端的连接和命令量**，而不是脚本的执行时间。」

**面试官继续追问：那 `reservationRollback.lua` 呢？它会不会有并发问题？**

**追问回答**

「**不会有并发问题，而且它的设计考虑得比我最初的脚本更细。**

```lua
if redis.call('SREM', KEYS[2], ARGV[1]) == 0 then
    return 0
end
if redis.call('EXISTS', KEYS[1]) == 1 then
    redis.call('INCR', KEYS[1])
    return 1
end
return 2
```

**它只有 3 个操作，全是 O(1)，而且 `SREM` 在 `INCR` 之前——这个顺序就是幂等性的来源。**

`SREM` 的返回值就是**『这是不是我第一次归还』**的判定：

| 第几次调用 | `SREM` 返回 | `INCR` 执行吗 |
|---|---|---|
| 第 1 次 | 1（确实删掉了成员） | ✅ |
| 第 2 次 | 0（集合里已经没有这个 userId） | ❌ **直接 return 0** |

**所以名额恰好归还一次。** 这也是异常场景 13『Redis 补偿执行两次』的答案。

**★ 但这个方法有一个语义前提，必须说清楚**：它假设**『集合里没有这个 userId』等价于『该用户没有有效占用』**。**当用户『取消后重新预约』时这个前提会破裂**——同一个 userId 在 `users` 集合里，之前代表 R1，之后代表 R2，**脚本无从区分**。

**所以 Lua 的幂等粒度是 `userId`，而业务需要的粒度是 `reservationId`——两者不等价。** 真正的保护在**上层**：`ReservationServiceImpl.cancel` 里那句『只有 `TRANSITIONED` 才允许归还』（见 Q57）。**Lua 是正确的，但它不足以单独保证正确性。**」

# 第四层 · 缓存体系

## Q23. 设备详情的缓存是怎么做的？

**推荐回答**

「用的是 **Cache Aside + 空值缓存 + 互斥重建**，三种范式叠在一条读路径上。

**读路径**（`EquipmentServiceImpl` → `CacheClient.queryWithMutex`）：

```
GET lab:equipment:{id}
  ├─ 命中（非空字符串）→ 反序列化返回
  ├─ 命中空字符串 ""  → 直接返回 null（★ 防穿透）
  └─ 未命中 → 抢锁 lock:cache:{id}
        ├─ 抢到 → 双重检查缓存 → 查库
        │     ├─ 有 → 写入缓存（TTL 30min + [0,5min) 抖动）→ 返回
        │     └─ 无 → 写入空字符串（TTL 2min）→ 返回 null
        └─ 没抢到 → 短暂重试，最多 20 次
              └─ 仍未抢到 → 直查数据库（★ 且不回写缓存）
```

**三种范式分别解决：**

| 问题 | 机制 | 关键参数 |
|---|---|---|
| **缓存穿透** | **空值缓存**——查不到也写 `""`，避免同一个不存在的 id 反复打库 | `CACHE_NULL_TTL = 2L` **分钟** |
| **缓存击穿** | **互斥重建**——热点 Key 失效时只让一个线程去查库，其他线程等 | 锁 `lock:cache:` + `MUTEX_MAX_RETRY = 20` |
| **缓存雪崩** | **TTL 抖动** | `CACHE_EQUIPMENT_TTL = 30L` 分钟 + `CACHE_EQUIPMENT_TTL_JITTER = 5L` 分钟 |

**★ TTL 抖动是 `30min + [0, 5min)`**，而且是**在调用点算的，不侵入 `CacheClient.set` 的通用语义**——`MIGRATION_STATUS.md` 专门记了这一点。这样 `CacheClient` 保持通用，抖动的策略留在业务侧。

**★ 冲突解决用删不用写**：更新设备时是 `DELETE lab:equipment:{id}`，不是去更新缓存值。理由是**并发下『写缓存』可能写入旧值**（两个更新请求的完成顺序和写缓存顺序可能不一致），而**删除永远是安全的**——下次读会重新加载。」

**面试官继续追问：只有 `queryWithMutex` 在用？`CacheClient` 里别的实现呢？**

**追问回答**

「**对，这是全仓唯一一处『有意保留的无调用方生产代码』。**

`CacheClient` 里有三个查询方法：

| 方法 | 范式 | 生产调用方 |
|---|---|---|
| `queryWithMutex` | 互斥重建（防击穿） | ✅ **设备详情唯一在用** |
| `queryWithPassThrough` | 空值缓存（防穿透） | ❌ 无 |
| `queryWithLogicalExpire` | 逻辑过期 | ❌ 无 |

**`MIGRATION_STATUS.md` 里明确登记了这个决定**：『`CacheClient.queryWithPassThrough` / `queryWithLogicalExpire` 已无生产调用方（设备详情只用 `queryWithMutex`）→ ✅ **T6 结论：保留**。T1 已明定「不动 `CacheClient`」；`CacheClient.java:26` 的类注释已写明 `queryWithLogicalExpire` 是「未启用的备选实现」，读者不会被误导。**这是全仓唯一一处有意保留的无调用方生产代码**，在此显式登记，以免日后被当成疏漏重开。』

**我觉得这个处理方式值得学习**：它没有假装『这是有用的』，而是**明确登记为有意保留**，并给出两个理由——① 类注释已经说明它是备选实现，不会误导读者；② 它们是**三种缓存范式的可对照参考实现**。

**★ 但这里有一个真实的问题**：`queryWithMutex` 只实现了『互斥重建』，**它内部的空值缓存是内联在方法里的**（`CacheClient:84` 的 `set(key, "", CACHE_NULL_TTL, MINUTES)`），**不是复用 `queryWithPassThrough` 的逻辑**。所以『三种范式叠在一条路径上』是**代码层面的复制**，不是组合。如果哪天要改空值缓存的策略，**两处都得改**。

**另外 README §7 把空值缓存写成了一个独立的 Key `lab:equipment:null:{id}`**——**这个 Key 不存在**。代码用的是**同一个 `lab:equipment:{id}`，值是空字符串 `""`**。这是一个文档与源码的不一致。」

## Q24. 互斥锁重建具体怎么实现的？为什么要双重检查？

**推荐回答**

「**双重检查（Double-Check）是为了堵住『等锁期间缓存已经被别人重建好了』这个窗口。**

流程是：

```java
// 第一次检查：缓存没命中，所以走到这里
String lockKey = LOCK_CACHE_KEY + key;
String token = UUID.randomUUID().toString(true);       // ★ 归属令牌
boolean locked = tryLock(lockKey, token);              // SETNX + EXPIRE
if (!locked) {
    // 没抢到锁：短暂重试，最多 MUTEX_MAX_RETRY(=20) 次
    Thread.sleep(50);
    return queryWithMutex(key, ...);                   // ★ 递归 → 有界循环
}

try {
    // ★★ 第二次检查：拿到锁之后重新读一次缓存
    String cached = stringRedisTemplate.opsForValue().get(key);
    if (cached != null) return deserialize(cached);    // 别人已经重建好了，直接用
    // 真的没有，才查库
    ...
} finally {
    unlock(lockKey, token);                            // Lua 比对后删除
}
```

**为什么必须有第二次检查？** 因为**『第一次检查未命中』和『拿到锁』之间有时间差**。在这段时间里，**持有锁的那个线程可能已经把缓存重建好并释放锁了**。如果不重新检查：

- 线程 A 重建完缓存、释放锁；
- 线程 B 拿到锁，**又把同样的查询做了一遍**——**白白多打一次库**。

**在高并发下这个浪费会被放大**：热点 Key 失效瞬间可能有几十个线程在等锁，如果没有双重检查，**它们会排队一个一个去查库**——互斥锁就退化成了串行查询。

**★ 双重检查之后的行为是正确的**：只有**第一个拿到锁且发现缓存还空着**的线程去查库，其余线程拿到锁后发现缓存已有数据，**直接返回**。

**★ 还有一点容易被忽略**：第二次检查之后，**查到 null 的情况下要写空字符串缓存**（`CacheClient:84`）——**不是什么都不写**。否则防穿透就失效了。」

**面试官继续追问：`MUTEX_MAX_RETRY = 20`、每次 `sleep(50)`，那最坏要等 1 秒？**

**追问回答**

「**理论上是的：20 × 50ms = 1 秒。** 而且**递归调用本身还有栈开销**。

**所以这是有界的**——`MIGRATION_STATUS.md` 记载 Phase 4 做过一次修复：『**递归改有界循环**』。原来的实现是**无界递归**，在锁竞争激烈时会导致**栈溢出**或者**无限等待**。改成有界之后，超过 20 次就**放弃等锁，直接查数据库**。

**但『直接查数据库』这个兜底有一个必须说清的边界**：

**它不回写缓存！** 所以超时之后：

- 这次请求拿到了正确数据（直查库）；
- **但缓存仍然是空的**；
- **下一个请求还是会走完整的『未命中 → 抢锁』流程**。

**如果 Redis 出了某种问题导致锁永远抢不到**（比如 `unlock.lua` 因为某种原因失效，锁泄漏了），那么**所有请求都会在 1 秒后放弃、直查数据库**——**这个热键的并发会全部压到 DB 上**。

**`README §15` 主动登记了这个边界**：『`queryWithMutex` 抢锁重试 20 次仍失败时会直查数据库且**不回写缓存**，此时该热键的并发会全部压到 DB。……为它们引入补偿链路，代价大于收益。』

**★ 我的判断**：在当前数据量（12 行设备）下这完全没问题。**但这是一个『数据量小所以成立』的取舍，不是一个『设计上安全』的设计**。如果设备涨到几十万行、某个 Key 特别热，这里的兜底会变成 DB 的雪崩入口。

**★ 还有一个更细的点**：`sleep(50)` 是**阻塞 Tomcat 线程**的。20 次重试意味着**最坏情况一个请求占用线程 1 秒**。在『锁泄漏』这种极端情况下，线程池会被迅速耗尽。**更稳的做法是让等待的线程用一个短 TTL 的本地缓存先返回，或者用异步重试。当前没做。**」

## Q25. 为什么更新缓存用「删除」而不是「写入」？

**推荐回答**

「**因为在并发下『写缓存』可能写入旧值，而『删除』永远是安全的。**

**先看『写缓存』为什么危险。** 假设两个更新请求 A、B 和一次读请求：

```
时刻  A（更新 name=X）           B（更新 name=Y）         读请求
 T1   写库 name=X
 T2                             写库 name=Y
 T3                             写缓存 name=Y
 T4   写缓存 name=X  ← ★ 旧值覆盖了新值
```

**结果：DB 里是 Y，缓存里是 X——不一致，而且会持续到 TTL 到期。**

问题出在**『写库』和『写缓存』是两步，而两步之间的顺序没有保证**。这个窗口在『先写库再写缓存』和『先删缓存再写库』两种顺序下都存在。

**『删除』为什么安全？** 因为**删除是一个幂等的、结果确定的动作**：

- 无论删多少次，缓存最终都是空的；
- 缓存空了之后，**下一次读一定会从数据库加载最新值**；
- **即使删除发生在写库之前**（读请求在删除后、写库前重新加载了旧值），**最坏结果也只是缓存里有一个旧值，存活到 TTL 到期**——**不会永久不一致**。

**而且删除不携带数据**——所以不存在『谁的值更新』这个问题。

**★ 代价是『一次缓存未命中』**：删除后下一个读请求要回源查库。这就是经典的 **Cache Aside 模式的取舍**：**牺牲一次未命中，换取不会写错值。**

**★ 这个项目里的实际代码**：`EquipmentServiceImpl` 在更新/删除设备后调用 `deleteEquipmentCache`，直接 `stringRedisTemplate.delete(key)`。

**而 `README §15` 主动登记了它的缺口**：『**缓存删除不做补偿**：`EquipmentServiceImpl.deleteEquipmentCache` 直接调 `stringRedisTemplate.delete`，既无 try/catch 也无重试——Redis 不可用时异常会直接抛出，表现是「**库里的写已经生效、接口却报错**」，缓存里的旧值要等 30 分钟 TTL 才过期。』

**这个描述是准确的。** 所以这里有一个**明确的、被记录的**边界：**缓存删除失败 ≠ 数据写失败，但接口会把它们混在一起报错**，而且**旧值会存活最多 30 分钟**。修法是把删除缓存改成『失败只记日志、不影响主流程』，或者把删除任务丢进 MQ 重试。**当前没做**——理由是『为它们引入补偿链路，代价大于收益』。」

**面试官继续追问：那为什么不用延时双删？**

**追问回答**

「**『延时双删』解决的是另一个问题，而这个项目的问题不在那里。**

**延时双删要解决的是**：『先删缓存再写库』这个顺序下，读请求可能在『删除』和『写库』之间**把旧值重新加载进缓存**，然后写库完成后缓存里留的是旧值。所以延时一段时间**再删一次**，把这个窗口里被重新加载的旧值清掉。

**但这个项目没有采用『先删缓存再写库』**——它是**『先写库，再删缓存』**。

**『先写库再删缓存』的残留窗口是**：读请求在写库**之前**读了旧值，然后在写库**之后、删缓存之前**把旧值写进缓存。这个窗口也存在，但**延时双删同样不能彻底消除它**（延时多久是猜的）。

**真正彻底的方案是『延迟双删 + 读请求不写缓存』或『用版本号/时间戳让旧值写不进去』**——**复杂度陡增，收益在当前场景下不明显**。

**★ 更重要的是，延时双删引入了新问题**：

1. **第二次删除本身可能失败**——那就需要重试机制，又回到补偿链路的问题；
2. **延时多久？** 这个『多久』是**猜的**（通常取『主从复制延迟 + 一点余量』），不是可推导的；
3. **它需要一个延时任务**（`ScheduledExecutorService` 或延时队列）——**多了一个要维护的组件**。

**我的判断是：在当前场景下（设备信息读多写极少、数据量 12 行、TTL 只有 30 分钟）『先写库再删缓存』的不一致窗口最长也就 30 分钟，而且影响的是『设备名称显示错了』这种非关键信息。为它引入延时双删是过度设计。**

**但如果设备的某个字段变成了关键业务字段**（比如 `booking_enabled` 影响能不能预约），**那这个判断就要重新做**——因为那时『缓存里的旧值』会让用户在页面上看到可以预约、实际却预约不了。**当前这个字段确实参与 `submit` 的校验**（`equipment.getBookingEnabled()`），**但那个校验读的是数据库，不是缓存**，所以不受影响。」

## Q26. 你的项目里有几种锁？它们的区别是什么？

**推荐回答**

「**两种，而且它们解决的问题完全不同——这是这个项目里一个很容易混淆、但很值得讲清楚的点。**

| | 缓存重建锁 | 预约/对账锁 |
|---|---|---|
| **实现** | **手写**：`SETNX` + UUID 归属令牌 + `unlock.lua` | **Redisson `RLock`** |
| **Key** | `lock:cache:{id}` | `lock:reservation:{userId}`、`lock:reservation:reconcile` |
| **位置** | `CacheClient` | `ReservationMessageConsumer`、`ReservationReconcileServiceImpl` |
| **解决** | **缓存击穿**（热点 Key 失效时只让一个线程查库） | **同一用户消息串行化** + **对账任务多实例互斥** |
| **失败代价** | **多查几次库**（性能问题） | **数据错乱**（正确性问题） |
| **有看门狗吗** | ❌ 不需要——**持有时间短且可控**（一次查库 + 一次写缓存） | ⚠️ **一个有一个没有**，见下 |
| **为什么用它** | **为了让读者看见 `SETNX` + Lua 的完整原理**（教学价值） | **需要看门狗、可重入、以及成熟的 API** |

**★ 关键区别在于『失败代价』。** 缓存锁失效了，最坏结果是多个线程同时查库——**慢，但对**。所以可以用一个**简单的、手写的**实现。而预约相关的锁失效会导致**重复落库、重复归还名额**——所以用了 **Redisson**（它有看门狗续期、可重入、以及经过验证的解锁逻辑）。

**★ 而 Redisson 那两个锁的租约策略是相反的，这一点非常容易搞错：**

```java
// ReservationMessageConsumer：★ 显式传 leaseTime → 没有看门狗
lock.tryLock(2, 10, TimeUnit.SECONDS);

// ReservationReconcileServiceImpl：★ 只传 waitTime → 有看门狗
lock.tryLock(0, TimeUnit.MILLISECONDS);
```

**Redisson 的规则是：`tryLock(waitTime, leaseTime, unit)` 显式指定了 `leaseTime`，就不再启用看门狗。** 所以：

- **消费锁**：租约固定 10 秒，到期自动释放，**看门狗不介入**。这是一个**有意的选择**——因为消费逻辑是「一次事务内的查询 + 写入」，**执行时间可控**，给它一个硬上限可以防止线程卡死时锁永久不释放；
- **对账锁**：`tryLock(0, TimeUnit.MILLISECONDS)` 是**两参重载**（`waitTime = 0`，`leaseTime` 未指定 → 默认 -1）→ **启用看门狗，每 10 秒续期一次（`lockWatchdogTimeout` 默认 30 秒的三分之一）**。

**★ 对账锁用看门狗带来一个风险**：看门狗在 `reconcile` 线程存活期间**无限续期**。如果某个实例的 `reconcile` 卡在一次**没有超时设置的 DB 调用**上，**锁就永不释放 → 所有实例的对账静默停摆，而且没有任何告警**（对账任务只有 `log.info`）。**这是我记录的边界之一。**」

**面试官继续追问：手写的 `SETNX` 锁要注意什么？**

**追问回答**

「**三个坑，`CacheClient` 里都处理了，而且都有测试钉住。**

**① 必须设过期时间。** 否则持有锁的线程崩溃后，**锁永久存在**（死锁）。

```java
Boolean success = stringRedisTemplate.opsForValue()
        .setIfAbsent(key, token, timeout, TimeUnit.SECONDS);
```

`setIfAbsent` 带超时的重载 = `SET key value NX EX timeout`，**是原子的**。**如果分两步 `SETNX` 再 `EXPIRE`，中间崩溃就会留下无 TTL 的锁。**

**② 解锁必须验归属，而且要原子。**

```lua
-- unlock.lua
if(redis.call('get', KEYS[1]) == ARGV[1]) then
    return redis.call('del', KEYS[1])
end
return 0
```

**为什么要有归属令牌（UUID）？** 看这条时间线：

```
T1  A 抢到锁（TTL 10s）
T2  A 的执行超过 10 秒 → 锁到期自动释放
T3  B 抢到锁
T4  A 执行完，执行 DEL → ★ 删掉了 B 的锁！
```

**没有归属校验的话，A 会把 B 的锁删掉**，于是 C 也能抢到锁——**互斥彻底失效**。加了 UUID 之后，A 的 `del` 会因为『值不等于自己的 token』而**不执行**。

**为什么要用 Lua 做？** 因为 `get` 和 `del` 如果分两条命令：

```
T1  A 执行 GET → 值是自己的 token ✓（判断通过）
T2  A 的锁正好到期，B 抢到锁
T3  A 执行 DEL → ★ 还是删掉了 B 的锁
```

**所以『比较』和『删除』必须在同一个原子操作里**——这就是 `unlock.lua` 存在的理由。

**③ 递归要有界。** `MIGRATION_STATUS.md` 记载 Phase 4 的修复之一就是『**递归改有界循环**』——原实现无界递归，锁竞争激烈时会栈溢出。

**★ 顺带说一个测试上的细节**：`CacheClientMutexTest` 里有一个硬编码的脆弱断言 `assertTrue(equipmentId > 12L)`——它假设种子数据的设备 id 最大是 12，依赖了数据的现状。**这是一个脆弱的测试，但它有判别力**（`MIGRATION_STATUS.md` 评估后决定不改：『判据是「有没有判别力」而不是「优不优雅」』）。」

## Q27. 缓存雪崩在你的项目里会发生吗？

**推荐回答**

「**理论上有防护，但实际的雪崩风险很低，而且我要说清楚防护的边界。**

**雪崩的三种成因和这个项目的应对：**

| 成因 | 应对 | 有没有做 |
|---|---|---|
| **大量 Key 同时过期**（同一时刻批量预热） | **TTL 抖动**：`30min + [0, 5min)` | ✅ **做了** |
| **Redis 整体宕机** | 无 | ❌ **没做**（没有多级缓存、没有本地缓存兜底） |
| **热点 Key 过期 + 高并发** (= 击穿) | 互斥锁重建 | ✅ **做了**（但有 20 次重试上限，超了直查库且不回写） |

**TTL 抖动具体做法**（`MIGRATION_STATUS.md` 记录）：『TTL `30min + [0,5min)` 抖动（**调用点计算，不侵入 `CacheClient.set` 通用语义**）』。

**为什么抖动只有 5 分钟？** 因为缓存的**语义要求是『30 分钟有效』**，抖动太多会破坏这个语义。5 分钟是**在『打散过期时刻』和『不破坏 TTL 语义』之间的折中**。

**★ 但我要诚实指出两个真实的边界：**

**① 抖动的效果对当前数据量来说几乎为零。** 项目只有 **12 台设备**，所以『大量 Key 同时过期』这个场景**根本不存在**——12 个 Key 就算同时过期，也就是 12 次查库，对 MySQL 毫无压力。**这个防护是『为将来准备』的，不是『解决当前问题』的。**

**② Redis 整体宕机没有任何兜底。** 这时：

- 设备详情查询会抛异常（`stringRedisTemplate` 连接失败）→ 500；
- **预约会失败**（`reservation.lua` 的 `EXISTS` 拿不到键 → 或者直接连接异常）；
- **没有任何降级路径**。

**这算不算问题？** 我认为**在『Redis 是核心依赖』这个架构下，它是必然的**——因为名额判定本来就在 Redis 里，**Redis 挂了系统本来就无法预约**。**加一个『设备详情降级直查库』的本地缓存是有价值的**（设备查询比预约更重要，因为学生要能浏览），**但当前没做。**」

**面试官继续追问：那不设 TTL 不是更简单？永远不会雪崩。**

**追问回答**

「**不设 TTL 会把『雪崩』换成更糟的问题——『数据永不更新』和『内存无界增长』。**

**① 数据永不更新。** `EquipmentServiceImpl` 更新设备时是 `DELETE` 缓存（Q25）。如果不设 TTL，那么：

- **删除成功** → 没问题，下次读会重建；
- **删除失败**（Redis 抖动，而 `deleteEquipmentCache` **没有 try/catch**）→ **缓存里的旧值永久存在**，用户会**一直**看到错误的设备信息。

**有 TTL 的话，最坏也只是错 30 分钟。** 这就是 TTL 的真正价值——**它不是用来省内存的，它是一个『不一致的自动收敛上限』**。

**② 内存无界增长。** 每次查一个不存在的 id，就会写一个空值缓存。不设 TTL 的话，**攻击者可以通过遍历 id 往 Redis 里灌无限多的键**——这是**缓存穿透防护反而变成了内存泄漏**。所以 `CACHE_NULL_TTL = 2L` 分钟**比正常 TTL 短得多**，正是为了限制这个风险。

**★ 所以 TTL 的三个作用，按重要性排序：**

1. **给不一致设一个收敛上限**（删缓存失败时，最坏错 TTL 那么久）；
2. **防内存无界增长**（尤其是空值缓存）；
3. **打散过期时刻防雪崩**（配合抖动）。

**只有第 3 个是『雪崩』相关，前两个更重要。** 而**空值缓存的 TTL 只有 2 分钟、正常缓存的 TTL 有 30 分钟——这个 15 倍的差距本身就是 ① 和 ② 的体现**：空值几乎没有『内容变更』的风险（一个 id 从不存在到存在，通常是因为新建了实体，而新建走的是不同的路径），所以可以短；正常缓存有内容变更风险，所以要长一些以提升命中率。**这个对比很好的说明了 TTL 不是随便设的。**」

## Q28. 缓存和数据库的一致性你怎么保证？

**推荐回答**

「**我不能保证强一致，而且我认为在这个场景下不需要——但我要说清楚不一致的窗口有多大、影响是什么。**

**这个项目用的是 Cache Aside（先写库，再删缓存）**，所以有**两个残留窗口**：

| 窗口 | 时序 | 后果 | 持续时间 |
|---|---|---|---|
| **① 删除失败** | 写库成功 → `delete` 抛异常 | 缓存里是旧值 | **最长 30 分钟**（TTL） |
| **② 读写在删之前** | 读请求读旧值 → 写库 → 读请求写缓存（但**这个项目的读路径不会主动写缓存**；只有 `queryWithMutex` 在缓存未命中且查库成功时才写） | 缓存里是旧值 | **最长 30 分钟**（TTL） |

**窗口 ② 在这个项目里的实际可能性很低**，因为读路径写缓存的时机是『**未命中**之后查库成功时』——而这个写操作和写库的删除操作之间的竞争窗口是**毫秒级**的。

**更要紧的是，我要说清影响的严重程度：**

| 受影响的字段 | 影响 |
|---|---|
| `name` / `model` / `description` / `location` 等描述性字段 | **用户看到过期的描述**，最长 30 分钟 |
| **`status`**（`AVAILABLE` / `MAINTENANCE`） | ⚠️ **用户可能在页面上看到『可用』但实际在维护** |
| **`bookingEnabled`** | ⚠️ **同上** |

**★ 但这里有一个关键的缓解**：`ReservationServiceImpl.submit` 里对设备和批次的校验**读的是数据库、不是缓存**：

```java
Equipment equipment = equipmentService.getById(batch.getEquipmentId());
if (equipment == null
        || equipment.getStatus() != EquipmentStatus.AVAILABLE
        || !Boolean.TRUE.equals(equipment.getBookingEnabled())) {
    throw new BadRequestException("设备当前不可预约");
}
```

`equipmentService.getById` 是 **MyBatis-Plus 的默认方法（直查库）**，**不走 `CacheClient`**。

**所以缓存的陈旧只会让展示不准确，不会让一个不可预约的设备被预约成功。** 这是**一个很重要的边界划分：缓存只服务于『读展示』，不服务于『写判定』。**

**★ 我总结的这条原则**：**当一个字段参与业务判定时，读它必须走权威数据源（DB），不能走缓存。** 而这个项目做到了这一点——`CacheClient` 只被 `EquipmentServiceImpl` 的**详情/列表查询**调用，所有 `submit` / `publish` / `cancel` 的校验都直接查库。**这是正确的一致性边界设计。**」

**面试官继续追问：那你怎么保证将来不会有人用缓存做判定？**

**追问回答**

「**当前没有任何机制能保证——这是一个纯靠约定维持的边界。**

**具体的风险**：如果有人为了『优化性能』把 `submit` 里的 `equipmentService.getById` 改成走缓存，那么：

1. 管理员把设备设为 `MAINTENANCE`（写库 + 删缓存）；
2. 删缓存**如果失败**，或者有并发的读请求把旧值写回缓存；
3. **学生就在这段时间内可以成功预约一个正在维护的设备**；
4. **而且这个预约会通过后面所有的防线**（Lua 只管名额、MySQL 的条件更新只管名额、唯一索引只管重复）——**没有任何一层会发现设备不可用**。

**为什么这个风险是真实的**：因为**没有任何自动化检查会阻止这个改动**。`EquipmentServiceImpl` 里既有走缓存的方法也有直查库的方法，**两者的调用点看起来一样**，只有看实现才知道区别。

**加固方向（当前都没做）**：

1. **把缓存读封装成单独的方法名**（比如 `getByIdFromCache` vs `getById`），让调用点时就能看出区别；
2. **在 `submit` 的校验上加注释说明『这里必须直查库』**；
3. **写一个测试**断言「设备状态变更后，`submit` 会立刻拒绝」——但这个测试**在缓存和 DB 一致时是过不了的**（因为两种实现都会拒绝），**所以它没有判别力**。真正有判别力的做法是**故意让缓存陈旧**（直接往 Redis 写一个 `AVAILABLE` 的旧值，DB 里是 `MAINTENANCE`），然后断言 `submit` 仍然拒绝。**这个测试是可以写的，而且有判别力——但当前项目里没有。**

**★ 这其实是我从这个项目学到的一个更一般的教训**：**『不能这么做』的约束，如果没有一行代码或一个测试来承载，它就只是一个口头约定。**」

# 第五层 · RabbitMQ 与消息可靠性

## Q29. 讲一下你的 RabbitMQ 拓扑。

**推荐回答**

「**一个业务交换机 + 一个业务队列 + 一个死信交换机 + 一个死信队列**，四条路由：

```
                    routing key: reservation.create
reservation.exchange ──────────────────────────► reservation.create.queue
   (DirectExchange)                                 (durable, 带 DLX 参数)
                                                            │
                              被 basicNack(requeue=false) 时 │ 由 broker 自动转发
                                                            ▼
                    routing key: reservation.create.dlq
    reservation.dlx ──────────────────────────► reservation.create.dlq
   (DirectExchange)                                 (durable, 没有 DLX 参数)
```

**关键点：业务队列在声明时就绑定了死信路由**（`RabbitMQConfig.reservationCreateQueue`）：

```java
QueueBuilder.durable(RESERVATION_CREATE_QUEUE)
        .withArgument("x-dead-letter-exchange", RESERVATION_DLX)
        .withArgument("x-dead-letter-routing-key", RESERVATION_CREATE_DLQ_ROUTING_KEY)
        .build();
```

**这意味着死信转发是 broker 自动做的**——应用只需要 `basicNack(requeue=false)`，**不需要自己往 DLQ 发消息**。这是 RabbitMQ 相比 Kafka 的一个实打实的便利（Kafka 没有原生 DLX，得自己写转发）。

**★ 两个细节：**

1. **两个交换机都是 `DirectExchange`**——用路由键精确匹配。这里只有一条业务路由，不需要 `Topic` 的通配能力，也不需要 `Fanout` 的广播。**选 `Direct` 是因为路由语义确实是『精确的一个目的地』。**
2. **DLQ 自己不带 DLX 参数**——**这是有意的**：DLQ 是终点。如果 DLQ 也有 DLX，一条反复失败的消息会在两个队列之间无限弹跳。所以 `ReservationDlqConsumer` 里那段注释说：『DLQ 没有后继死信交换机，拒绝后日志是消息永久丢弃前的最后痕迹，必须保留完整原文。』」

**面试官继续追问：交换机上为什么用 JSON 转换器？DLQ 为什么又不用了？**

**追问回答**

「**因为是两条完全不同的路径，对『失败』的定义不一样。**

**业务队列用 `Jackson2JsonMessageConverter`**——消息是一个 `ReservationMessageDTO` 对象，用 JSON 传是为了可读和跨语言。

**DLQ 用的是另一个容器工厂 `ReservationDlqListenerConfig.reservationDlqListenerContainerFactory`，里面是 `SimpleMessageConverter`，而且监听器签名收的是原始 `Message`：**

```java
// ReservationDlqConsumer
@RabbitListener(queues = RESERVATION_CREATE_DLQ,
                containerFactory = ReservationDlqListenerConfig.DLQ_CONTAINER_FACTORY)
public void onDeadLetter(Message message, Channel channel) throws IOException {
    byte[] body = message.getBody();        // ★ 原始字节
    ...
}
```

**类注释写明了原因**：『**使用原始 Message 消费死信，避免反序列化失败的消息再次经过 Jackson 并形成失败循环。**』

**这个理由非常硬**：死信队列里最需要留存的消息，恰恰是**那些反序列化失败的**消息（比如生产者发了一个格式不对的 JSON）。**如果 DLQ 也用 Jackson，这条消息会在 DLQ 里再次反序列化失败 → 再次被 reject → 但 DLQ 没有后继 DLX → 消息被丢弃，而台账里什么都没有。** 用 `SimpleMessageConverter` 只按字符集转成字符串，**永远不会失败**，所以这条消息能被完整地写进 `tb_reservation_dlq.payload`。

**★ 这体现了一个通用原则**：**『失败处理路径』本身必须比主路径更不容易失败。** 错误处理器用和主路径一样脆弱的依赖，就会一起挂掉。」

## Q30. 为什么关闭了自动重试？

**推荐回答**

「**因为『手动 ACK + spring 默认重试』这个组合会让消费者卡死——这是一个真实踩过的坑。**

`application.yaml` 里的原文注释就是结论：

```yaml
listener:
  simple:
    acknowledge-mode: manual
    prefetch: 1
    # 手动 ack 模式下默认 recoverer 不会真正 nack、会卡死消费者，故关闭自动重试，由监听器显式 basicNack 进死信
    retry:
      enabled: false
```

**展开说这个坑的成因**：Spring AMQP 在 `retry.enabled=true` 时，会在监听器外层套一个 `RetryOperationsInterceptor`。监听器方法抛异常时，拦截器**在容器内部重试**（默认 3 次），重试耗尽后才调用 `MessageRecoverer` 做最终处理。

**而 `MessageRecoverer` 的默认行为是 `RejectAndDontRequeueRecoverer`——它会抛 `AmqpRejectAndDontRequeueException`，由容器统一 reject。**

**问题在于『手动 ACK 模式』下**：应用已经拿到了 `Channel` 并**自己决定**什么时候 `basicAck`/`basicNack`。如果应用选择**不处理**异常，而是**抛出去**让框架兜底——那么：

- 异常被重试拦截器捕获，**重试 3 次**；
- 3 次都失败后走 recoverer；
- **但如果应用在 catch 块里已经做了处理（比如 `basicNack` 后又抛异常），或者根本没有 `basicAck` 也没有 `basicNack`**——这条消息的 **unacked 状态永远不解除**；
- 因为 `prefetch: 1`，**这个消费者通道上就再也收不到新消息了**——**消费者静默卡死**。

**所以这个项目的做法是：把重试的责任完全收到应用手里。** `retry.enabled=false`，然后在 `ReservationMessageConsumer` 里**每一条失败路径都显式地 `basicAck` 或 `basicNack`**：

| 分支 | 动作 |
|---|---|
| 成功 / 幂等重复 | `basicAck` |
| 账本已 `COMPENSATED` | `basicAck`（**拒绝落库但确认消息**） |
| 锁超时 | `basicNack(deliveryTag, false, false)` |
| 名额冲突 | `basicNack(deliveryTag, false, false)` |
| 主键冲突 | `basicNack(deliveryTag, false, false)` |
| 其他异常 | `basicNack(deliveryTag, false, false)` |

**★ 三个参数的含义**（`basicNack(deliveryTag, multiple, requeue)`）：`multiple=false` 表示只拒绝这一条；**`requeue=false` 是进 DLQ 的关键**——**如果 `requeue=true`，消息会被重新入队，然后立刻又被这个消费者拿到、又失败，形成无限循环，把队列堵死。**

**★ 还有一层保护**：`ConditionalRejectingErrorHandler` 配了 `setRejectManual(true)`。

**这一步是必需的**：因为**反序列化失败发生在监听器方法被调用之前**——那时应用**还没有拿到 `Channel`，根本没有机会调用 `basicAck`/`basicNack`**。而 Spring AMQP 在手动 ACK 模式下，**默认的 `ConditionalRejectingErrorHandler` 不会 reject**（它认为『手动模式应该由应用自己处理』），**结果就是消息永远 unacked → 又卡死**。

`setRejectManual(true)` 就是告诉它：**即使在手动 ACK 模式下，也请你替我 reject。** `RabbitMQConfig` 里那句注释说的正是这个：『反序列化失败发生在监听器方法之前，必须明确拒绝并进入死信队列。』」

## Q31. 为什么用手动 ACK 而不是自动 ACK？

**推荐回答**

「**因为『自动 ACK』会在业务真正完成之前就把消息标记为已消费——这违背了『不丢单』的要求。**

**`acknowledge-mode: manual` 下，消息什么时候被确认完全由应用决定**，而这个项目把确认点放在了**所有副作用都完成之后**：

```java
ReservationPersistResult result = persistWithLock(messageDTO);   // ① 落库
switch (result) {
    case PERSISTED:
    case DUPLICATE:
        markConfirmedSafely(messageDTO.getReservationId());      // ② 推进账本
        channel.basicAck(deliveryTag, false);                    // ③ 最后才 ACK
        break;
```

**顺序是『落库 → 推账本 → ACK』**，不是『落库 → ACK → 推账本』。

**为什么这个顺序是必需的？** 考虑如果先 ACK 再推账本：

```
T1  落库成功（MySQL 里有一条 RESERVED 预约）
T2  ACK → broker 认为消息处理完了，删掉它
T3  推账本 CONFIRMED 失败（DB 抖动）
T4  进程崩溃
```

**结果：预约落库了，但账本永远停在 `PRE_ACCEPTED`。** 10 分钟后对账扫描到它，`reservationMapper.selectById(requestId) != null` → **推成 `CONFIRMED`**。——**这个场景其实是能自愈的**，因为对账的判定依据是『预约行在不在』，而不是账本状态。

**★ 但反过来看另一个顺序就更严重**：

```
T1  落库成功
T2  推账本 CONFIRMED 成功
T3  ★ 还没来得及 ACK，进程崩溃 → 消息 unacked → broker 会重新投递
T4  重新投递 → 账本已经是 CONFIRMED（终态）→ 走到 persist
T5  persist 的幂等分支命中（同 id + 同 user + 同 batch）→ 返回 DUPLICATE
T6  markConfirmedSafely → CAS 从『非终态』到 CONFIRMED → 失败（已经是终态）→ log.warn
T7  basicAck
```

**注意 T6 会打一条 warn 日志**：『预约已落库但账本置为 CONFIRMED 未生效』。**这不是 bug，是正常路径**——因为账本已经是终态了。

**★ 所以手动 ACK 的核心价值是**：**『ACK』这个动作代表『这一次消费的所有副作用都完成了』**，而不是『我收到了』。自动 ACK 在消息投递到监听器时（或方法正常返回时）就确认，**在方法内部抛异常的情况下无法区分『业务已提交』和『业务未提交』**。

**★ 代价是必须处理『ACK 本身失败』**，见 Q36 和异常场景 10。」

## Q32. publisher-confirm 和 publisher-returns 有什么区别？

**推荐回答**

「**它们覆盖的是两个不同的失败点，而且『confirm 通过』不代表『消息不会丢』。**

```
生产者 ──①──► Exchange ──②──► Queue
              │              │
              │              └─ ② 失败 → publisher-returns（路由失败）
              └─ ① 失败 → publisher-confirm（ACK/NACK）
```

| | `publisher-confirm` | `publisher-returns` |
|---|---|---|
| **回答的问题** | **broker 收到消息了吗？** | **broker 把消息放进队列了吗？** |
| **覆盖的失败** | 网络断开、broker 磁盘满、内部错误、队列满载被拒 | **路由键匹配不到任何队列** |
| **回调** | `ConfirmCallback(ack, cause)` | `ReturnCallback(message, replyCode, ...)` |
| **配置** | `publisher-confirm-type: correlated` | `publisher-returns: true` |
| **默认状态** | 关闭 | 关闭（且**必须配 `mandatory`** 才有意义） |

**★ 关键点：这是两个独立的失败点，必须都开才覆盖完整。**

- **只开 confirm**：消息成功到达 broker，但**路由键写错了、没有任何队列绑定** → broker 回 ACK（它确实收到了！）→ **消息被静默丢弃**。生产者以为成功了。
- **只开 returns**：`returns` 是**异步回调**，而且**只有路由失败时才触发**——**成功时它什么都不做**。所以你无法用它判断成功，只能用它判断『这一种特定的失败』。

**所以项目里两个都开了**，`@PostConstruct` 里两个回调都注册了：

```java
rabbitTemplate.setConfirmCallback((correlationData, ack, cause) -> {
    if (!ack) log.error("预约消息发送未获确认：...");
});
rabbitTemplate.setReturnCallback((message, replyCode, replyText, exchange, routingKey) ->
        log.error("预约消息路由失败：..."));
rabbitTemplate.setMandatory(true);
```

**★ 但要注意一个实现细节：这两个回调只打日志，不驱动业务决策。**

**真正的结果判定在 `publishReservationMessage` 里同步做的**（`correlationData.getFuture().get(5, SECONDS)`）。**回调是『事后审计』，future 是『同步决策』。** 两者都在，各司其职。

**★ 还有一个容易搞错的点**：`publisher-confirm-type: correlated` 这个值很关键。

- `simple`：**只启用普通的 ConfirmCallback**，`CorrelationData` 的 future **不会被完成**；
- `correlated`：**每条消息的 `CorrelationData` 会被独立完成**，才能用 `getFuture().get(...)`。

**如果配成 `simple`，`correlationData.getFuture().get(5, SECONDS)` 会一直阻塞到超时**——因为没有人去完成那个 future。**这是一个配置和代码强耦合的地方，改配置会让代码静默地永远走超时分支。**」

**面试官继续追问：那 `mandatory` 是干什么的？**

**追问回答**

「**`mandatory` 决定了『路由失败时 broker 怎么处理这条消息』——是退回给生产者，还是直接丢弃。**

- `mandatory = false`（默认）：路由失败时 broker **直接丢弃消息**，**不通知任何人**。`publisher-returns: true` 也救不了你，**因为没有消息会被退回**；
- `mandatory = true`：broker **把消息退回给生产者**，触发 `ReturnCallback`。

**所以 `publisher-returns: true` 和 `setMandatory(true)` 必须成对出现**——**只配一个，`ReturnCallback` 永远不会被调用。** 这是一个非常常见的配置失效场景：配置看起来开了，但回调从来没触发过，**而且没有任何报错**。

**★ 这个项目里还有第三个用途**：`setMandatory(true)` 让路由失败的消息**能被 Java 侧感知到**，从而在 `publishReservationMessage` 里判定为 `DEFINITELY_NOT_DELIVERED`：

```java
} else if (correlationData.getReturnedMessage() != null) {
    outcome = PublishOutcome.DEFINITELY_NOT_DELIVERED;
    failureReason = "CONFIRM_RETURN";
}
```

**这里有一个时序上的微妙之处**：`getFuture().get(5, SECONDS)` 返回的是 **confirm（ACK）**，而 `returnedMessage` 是**另一个回调设进去的**。

**RabbitMQ 的保证是：对于一条会被退回的消息，broker 会先发 basic.return，再发 basic.ack。** 所以**等到 confirm future 完成时，`getReturnedMessage()` 已经被赋值了**——这就是为什么可以在 confirm 分支里安全地检查它。

**如果这个顺序反了（或者用的是 `simple` 模式），就会漏判**：`confirm.isAck()` 为 true、`returnedMessage` 还是 null → 会被误判成 `ACKED`，**而消息其实已经丢了**。**这是这个设计里依赖 broker 行为保证的一处，值得知道它的前提。**」

## Q33. 那三种投递结果是怎么判定的？

**推荐回答**

「`publishReservationMessage` 用一个私有枚举 `PublishOutcome` 把投递结果分成**三类**：

| 结果 | 触发条件 | 之后的动作 |
|---|---|---|
| `ACKED` | confirm 是 ACK **且** 没有被退回 | 账本 → `PUBLISHED` |
| `DEFINITELY_NOT_DELIVERED` | **连接异常** / confirm **NACK** / 消息被 **return** | **立即归还名额** + 账本 → `COMPENSATED` |
| `UNKNOWN` | 等待 confirm **超时** / 被中断 / 其他运行时异常 | 账本 → **`UNKNOWN`**，**什么都不归还** |

**判定代码**：

```java
try {
    rabbitTemplate.convertAndSend(..., correlationData);
    CorrelationData.Confirm confirm = correlationData.getFuture().get(5, TimeUnit.SECONDS);
    if (!confirm.isAck()) {
        outcome = DEFINITELY_NOT_DELIVERED;  failureReason = "CONFIRM_NACK";
    } else if (correlationData.getReturnedMessage() != null) {
        outcome = DEFINITELY_NOT_DELIVERED;  failureReason = "CONFIRM_RETURN";
    } else {
        outcome = ACKED;
    }
} catch (AmqpConnectException e) {
    outcome = DEFINITELY_NOT_DELIVERED;      // 连都连不上，确定没发出去
} catch (TimeoutException | InterruptedException | ExecutionException e) {
    outcome = UNKNOWN;                        // ★ 不知道发出去没有
}
```

**★ 这个三分法的核心判断是『我知不知道』，而不是『成功还是失败』：**

- **`DEFINITELY_NOT_DELIVERED` 是『我知道它没到』**——连接异常（根本没建立连接）、NACK（broker 明确拒绝）、Return（broker 明确退回）。**这三种情况下消息一定没有进队列，所以名额可以安全归还。**
- **`UNKNOWN` 是『我不知道』**——超时意味着我发出去的命令没有任何响应。**消息可能在网络里、可能在 broker 里待确认、也可能根本没出去。** 这时：

**★ 为什么 `UNKNOWN` 绝不归还名额？** 因为**消息可能已经成功入队并被消费了**。如果归还名额，就会形成『MySQL 里有预约行 + Redis 名额被归还』——**这就是超卖**（下一个学生可以抢到这个已经被占用的名额）。

**所以 `UNKNOWN` 的选择是：宁可让一次真实成功的预约被误判为『待确认』（用户看到 503，但去『我的预约』能看到），也绝不冒超发的风险。**

**★ 而 `UNKNOWN` 不是终态**——它会被对账任务在 10 分钟后裁决。这是这个三分法真正闭合的地方：**不确定的中间态交给一个确定性的、周期性的扫描来收敛。**」

**面试官继续追问：`AmqpConnectException` 能确定消息没发出去吗？**

**追问回答**

「**不一定，这是我必须诚实说明的一个边界。**

`AmqpConnectException` 表示**获取连接失败**。它有两大类来源：

1. **`convertAndSend` 之前连不上**——此时**消息一定没有发出**，判定为 `DEFINITELY_NOT_DELIVERED` 是正确的；
2. **发送过程中连接断开**——此时**消息可能已经写到 broker 的 socket 缓冲区里了**。TCP 的语义是『写进缓冲区就算成功』，**对端有没有收到、有没有落盘，客户端无从得知**。

**所以第 2 种情况下，判定为 `DEFINITELY_NOT_DELIVERED` 并归还名额，理论上存在超卖可能。**

**为什么还是这么选？** 因为**这个分支的期望收益远大于风险**：

- **常见情形（第 1 种）**：RabbitMQ 没启动或网络断了——**这是本地开发和运维中最常见的故障，而且这种情况下消息 100% 没发出**。归还名额是**正确的、必须的**，否则每次 broker 抖动都会泄漏一批名额（只能等 10 分钟对账）；
- **罕见情形（第 2 种）**：连接在写出消息的**同一瞬间**断开——**窗口极小**，而且需要消息恰好成功入队并被消费。

**★ 更重要的是：这个风险被下一层防线挡住了。** 即使误判并归还了名额，那条消息如果**真的**进了队列，消费者会去落库，`persist` 里的 `remaining_quota > 0` 条件更新和 `uk_user_batch_active` 唯一索引**仍然会拦住超发**（见 Q53、Q54）。**MySQL 层的这两道防线是不依赖 Redis 判定正确性的。**

**所以真正准确的描述是**：`AmqpConnectException` 被归入 `DEFINITELY_NOT_DELIVERED` 是一个**工程上的乐观假设**——**假设『连接异常 = 消息没出去』，然后靠 MySQL 的防线兜住极小概率的反例。** 我在文档里把它登记为一个『有意的、有兜底的乐观判定』，而不是一个严格的证明。」

## Q34. 为什么 `prefetch = 1`？

**推荐回答**

「**为了让一个消费者一次只处理一条消息——这买到了两件事：消息级的顺序保证，和公平分发。**

**① 顺序保证。** 同一用户如果快速提交两次预约，两条消息的落库需要串行。如果 `prefetch` 是 10，一个消费者可能同时持有这两条消息并并发处理。虽然代码里还有 Redisson 用户锁兜底，但**`prefetch=1` 让并发根本不会发生**——这比『并发后用锁纠正』更简单。

**② 公平分发。** 有多个消费者实例时，`prefetch=1` 让 broker 把消息分给**当前最空闲**的消费者；如果 `prefetch` 很大，一个消费者可能囤积一堆消息而另一个闲着，**长尾延迟会很难看**。

**★ 代价是吞吐。** `prefetch=1` 意味着**一个消费者在 ACK 之前不会拿到下一条**——它把『批量并行』变成了『逐条串行』。**这是这个项目里最有争议的一个参数。**

**★ 为什么这里可以接受？**

1. **这个消费者持有的锁是用户级的**——同用户的消息本来就该串行。而不同用户的消息即使被串行处理，**代价只是一点延迟**，不影响正确性；
2. **消费逻辑是短的**：一次账本查询 + 一次 `persist`（两次 SQL 在一个事务里）+ 一次账本 CAS。**没有慢操作**；
3. **量级不大**——这是本项目的实际情况。

**★ 什么时候必须调大？** 如果预约量上来、消费者成为瓶颈，`prefetch` 和 `concurrency` 是**第一批要调的参数**（`spring.rabbitmq.listener.simple.concurrency` 现在**根本没配**，用的是默认 1 个消费者线程）。

**我要诚实说两点**：
1. **这两个参数从来没调过，也没压测过**——`concurrency` 甚至没出现在配置里；
2. **`prefetch=1` 和『用户级分布式锁』在功能上是重叠的**：都用不同的机制在做同用户串行化。这**不是冗余而是纵深防御**（prefetch 是投递层、锁是应用层），**但代价是吞吐被压了两遍**。

**如果要优化，正确的顺序是：先确认用户级串行化的必要性能否由单层承担**（比如把 `prefetch` 提到 10，完全依靠 Redisson 锁），**然后压测验证**。**当前没有做这件事。**」

## Q35. 重复消息怎么处理？消息幂等吗？

**推荐回答**

「**幂等，而且是三层幂等，每层的粒度不同。**

**第一层：`persist` 里的两个判断**（`ReservationPersistenceServiceImpl:29-46`）

```java
Reservation existing = reservationMapper.selectById(reservation.getId());
if (existing != null
        && existing.getUserId().equals(reservation.getUserId())
        && existing.getBatchId().equals(reservation.getBatchId())) {
    return ReservationPersistResult.DUPLICATE;      // ① 同 id 同归属 → 幂等确认
}
Integer existingCount = reservationMapper.selectCount(... userId + batchId + occupyingStatuses() ...);
if (existingCount > 0) {
    return ReservationPersistResult.DUPLICATE;      // ② 同用户同批次已占用 → 幂等拒绝
}
```

**注意这两个判断的语义完全不同：**

- **① 是『同一次预约的重复投递』**——消息因为 ACK 丢失被 broker 重投，或者人工从 DLQ 重放。**这是幂等的确认，不重复扣名额，返回 `DUPLICATE`，消费端会 `basicAck`。**
- **② 是『两次不同的预约』**——用户重复提交生成了**两个不同的 `reservationId`**（不同主键），但撞上了唯一索引的业务约束。**这是业务上的重复，同样返回 `DUPLICATE`。**

**★ ① 的注释里有一句非常关键的话**，是这个项目里设计最精细的地方之一：

> 只有「同 id 且同 user 且同 batch」才算同一次预约的重复投递（含 DLQ 重放），幂等确认、不重复扣名额。**同 id 但归属不同是异常的主键冲突，必须继续走到 insert 由主键约束抛出，交给消费端既有的 `catch(DuplicateKeyException)` 进死信队列；若在此提前返回 `DUPLICATE`，那条未落库的消息会被静默 ACK，DLQ 上不留任何痕迹。**

**这段话说的是：幂等判断不能过宽。** 如果只判 `existing != null` 就返回 `DUPLICATE`，那么一条『**主键撞了、但用户和批次都对不上**』的消息（说明 `RedisIdWorker` 生成了重复 ID，或者有人手工往队列里塞了脏数据）**会被当成幂等重复而静默 ACK**——**消息消失了，而且死信队列里什么都没有，运维完全不知道出过事。**

**所以它把『幂等』收窄到了『同 id + 同 user + 同 batch』这个精确的三元组**，让**其他所有的冲突都继续走到 `insert`**，由**数据库主键约束**抛出 `DuplicateKeyException`，被消费端捕获后 `basicNack` **进死信队列留痕**。

**第二层：Redisson 用户锁**（`persistWithLock`）——保证**同一用户的消息串行处理**，让上面的『查了没有 → 插入』之间不会有并发插入。

**第三层：`uk_user_batch_active` 唯一索引**——**最终的、不可绕过的防线**。即使锁失效、即使两个消费者同时插，**数据库会拒绝第二个**（见 Q54）。

**★ 三层的分工是**：**锁**减少冲突（性能），**查询**处理可预期的重复（语义），**唯一索引**兜住所有意料之外的情况（正确性）。**前两层都可以失效，第三层不会。**」

**面试官继续追问：那 `DUPLICATE` 返回之后，账本会被推成 `CONFIRMED` 吗？**

**追问回答**

「**会。而且这是刻意的。**

```java
case PERSISTED:
case DUPLICATE:
    markConfirmedSafely(messageDTO.getReservationId());
    channel.basicAck(deliveryTag, false);
    break;
```

**`DUPLICATE` 和 `PERSISTED` 走同一个分支**——都推 `CONFIRMED`、都 ACK。理由：

**`DUPLICATE` 的语义是『这条消息所代表的预约已经在库里了』**，所以从『这个请求最终成功了吗』的角度看，**答案是『成功了』**。账本置 `CONFIRMED` 是正确的终态。

**★ 但这里有一个我认为值得注意的细节**：`markConfirmedSafely` 用的是 `casStatus(requestId, CONFIRMED, NON_TERMINAL_STATUSES)`。

**在②那种情况下**（用户重复提交，两个不同的 `reservationId`），第二个请求的账本行状态是 `PRE_ACCEPTED`（它自己的 ID，从没成功过），**而它会被推成 `CONFIRMED`**。

**这意味着：账本里会有一条『状态为 CONFIRMED，但 MySQL 里没有对应 reservationId 的预约行』的记录？**

**不会。** 因为 `persist` 中的②分支返回 `DUPLICATE`，**消费端把这个 `requestId` 推成 `CONFIRMED`**，而这个 `requestId` **正好就是这条消息的 `reservationId`**（两者同源，见 Q43）。

**所以对账时 `reservationMapper.selectById(requestId)` 会返回 null** —— 但因为账本已经是 `CONFIRMED`（终态），**对账根本不会扫它**（`listStale` 只扫非终态）。

**★ 这里有一个真实的、可能引起困惑的不一致**：账本说 `CONFIRMED`，但 `tb_reservation` 里没有这个 id 的行。**从『请求结果』的语义看这是对的**（用户的预约确实成功了，只是用的是另一个 id 的行）**，但从『账本和预约行一一对应』的直觉看它是破的。**

**如果我要改进**，②这种情况应该把账本推成一个能表达『被业务去重』的状态（或者至少 `fail_reason = "DUPLICATE_USER_BATCH"`），而不是直接 `CONFIRMED`。**当前实现把它和真正的成功混在了一起，这是一个语义上的粗糙处，我登记为边界。**」

## Q36. 死信队列是怎么治理的？

**推荐回答**

「**完整链路是：消费失败 → `basicNack(requeue=false)` → broker 自动转发到 DLQ → `ReservationDlqConsumer` 用原始字节落台账 → 人工在管理端查看并重放。**

**① 落台账。** `ReservationDlqConsumer` 收原始 `Message`（**避免二次反序列化失败**，Q29），调用 `recordDeadLetter(body, xDeathReason)`：

- `payload` 存**消息完整原文**；
- `failure_reason` 从 **`x-death` 头**里取（`extractXDeathReason` 读 `deaths.get(0).get("reason")`，**失败时降级为 null 而不是抛出**）；
- `status` 默认 `NEW`，`replay_count` 默认 0。

**② 落台账失败时的处理。** 这段很讲究：

```java
} catch (Exception e) {
    String payload = body == null ? null : new String(body, StandardCharsets.UTF_8);
    // DLQ 没有后继死信交换机，拒绝后日志是消息永久丢弃前的最后痕迹，必须保留完整原文。
    log.error("死信台账落库失败，消息将永久丢弃：payload={}", payload, e);
    channel.basicNack(deliveryTag, false, false);
    return;
}
```

**它在丢弃消息之前，把消息原文打进了错误日志。** 因为 DLQ 没有后继 DLX，`basicNack` 之后这条消息**就真的永远消失了**——**日志是它存在过的唯一证据**，所以必须打全。**这是『消息丢失不可避免时，至少要留下可追溯的痕迹』的实践。**

**③ 重放。** `ReservationDlqServiceImpl.replay(id)` 在真正重投之前有**五道前置检查**：

| 序 | 检查 | 不通过时 |
|---|---|---|
| 1 | 台账 `status` 必须是 `NEW`（未处理） | `rejected("死信记录已处理，不能重复重放")` |
| 2 | `replay_count < dlq-max-replay`（默认 **3**） | `rejected("已达到最大重放次数")` |
| 3 | `payload` 能否解析出 `reservationId` | `discard("PAYLOAD_NOT_REPLAYABLE", "payload 无法重放")` |
| 4 | **预约是否已经落库** | `discard("ALREADY_PERSISTED", "已落库，无需重放")` |
| 5 | **账本是否已 `COMPENSATED`** | `discard("COMPENSATED", "请求已补偿，无法重放")` |

**④ 并发保护。** 重放次数用 **CAS** 递增，不是先读后写：

```java
reservationDlqMapper.update(null, new LambdaUpdateWrapper<ReservationDlq>()
        .eq(ReservationDlq::getId, id)
        .eq(ReservationDlq::getReplayCount, replayCount)      // ← CAS 条件
        .set(ReservationDlq::getReplayCount, replayCount + 1));
// == 1 才继续；否则 return rejected("死信记录已被并发重放")
```

**所以两个管理员同时点『重放』，只有一个能成功。**

**★ 第 5 道检查是这个设计里最有意思的地方**，因为它划出了一个**时间窗口**：

**DLQ 重放只在『请求还没被对账补偿』之前有效。** 因为对账的阈值是 **10 分钟**（`reconcile-threshold-ms: 600000`），所以：

- **消息进 DLQ 后的约 10 分钟内**：账本还是非终态 → **可以重放**，重放成功后消费者落库、账本 → `CONFIRMED`；
- **超过 10 分钟后**：对账已经把这条请求判为『失败、归还名额、`COMPENSATED`』→ **重放被 `discard` 拒绝**。因为那时 Redis 名额已经还了，再落库就会**超发**。

**所以死信治理有一个约 10 分钟的『黄金恢复窗口』。** 这是**当前实现的边界，而且我认为它是一个合理的边界**——它保证了一条消息**要么被重放成功，要么被对账补偿，绝不会两者都发生**。但这个窗口**没有被写进 README**，是我在推演异常场景时发现的。**它意味着：一个凌晨 3 点发生的死信，如果运维早上 9 点才处理，已经不能重放了——只能手工核对后走别的补偿流程。**」

# 第六层 · 状态机与最终一致性

## Q37. `tb_reservation_request` 是哪五个状态？状态图是什么？

**推荐回答**

「状态机和转移图：

```
                 ┌──────────────────────────────────────────┐
                 │                                          │
    createPreAccepted                ACKED                   │
        │                            ┌────────► PUBLISHED ───┤
        ▼                            │              │        │
   PRE_ACCEPTED ─────────────────────┘              │        │
        │  │                                        │        │
        │  │ Lua 拒绝 / 确定未投递                    │        │
        │  └────────────► COMPENSATED ★终态           │        │
        │                     ▲                       │       │
        │  UNKNOWN 超时        │                       │       │
        ├──────────► UNKNOWN ─┤                       │       │
        │                │    │ 对账：无预约行 → 补偿   │       │
        │                │    └───────────────────────┘       │
        │                │                                    │
        │                └──── 对账：有预约行 ──► CONFIRMED ★终态
        │                                          ▲
        └───────── 消费者落库成功（可能不经过 PUBLISHED）─┘

★ 终态 = CONFIRMED | COMPENSATED      （isTerminal()）
非终态 = PRE_ACCEPTED | PUBLISHED | UNKNOWN  （nonTerminalStatuses()）
```

**★ 三个必须讲清楚的点：**

**① `PUBLISHED` 不是必经点。** 状态图里有一条 `PRE_ACCEPTED → CONFIRMED` 的**直达边**。因为消息消费可能比『账本置 `PUBLISHED`』更快——`markConfirmedSafely` 用的 CAS 期望集合是 **非终态全体**（`PRE_ACCEPTED`、`PUBLISHED`、`UNKNOWN`），**所以从 `PRE_ACCEPTED` 直接推 `CONFIRMED` 是允许的**。

**这个设计很关键**：如果 CAS 的期望值写死了 `PUBLISHED`，那么快速消费的路径就会**永远推不动账本**，10 分钟后对账会看到『有预约行但账本还是 `PRE_ACCEPTED`』→ 推 `CONFIRMED`（也能自愈，但白等 10 分钟）。**用『非终态全体』做期望值，把顺序耦合解掉了。**

**② `UNKNOWN` 是非终态。** 这是它存在的全部意义——**它是『待裁决』，不是『失败』。** 如果它是终态，超时的请求就永远不会被对账扫描到，Redis 名额就永久泄漏了。

**③ 终态只有一个判据**：`isTerminal()` 返回 `CONFIRMED || COMPENSATED`。**对账的扫描条件、所有 CAS 的期望值，都从这两个方法派生**（`nonTerminalStatuses()`），**没有任何地方手写状态列表**。这是**单一事实来源**的做法——加一个新状态只需要改枚举，所有判定点自动跟上。」

**面试官继续追问：`fail_reason` 是什么角色？**

**追问回答**

「**它是审计线索，不是状态的一部分。**

**关键证据**：对账的『已落库』分支用的是 `casStatus`（**不带** `failReason` 参数）而不是 `casStatusWithFailReason`。`ReservationReconcileServiceImpl` 的类注释写明了原因：

> 已落库分支使用 `casStatus`，**刻意保留 `fail_reason` 作为最近一次失败的审计线索。**

**这句话的意思是**：一条请求可能先失败过（比如消费时锁超时，写入了 `fail_reason = "LOCK_TIMEOUT"`），然后**重投成功了**。这时：

- **状态**要变成 `CONFIRMED`（它确实成功了）；
- **`fail_reason` 要保留 `"LOCK_TIMEOUT"`**——**因为它记录了『这次预约曾经失败过一次』这个事实**。

**如果用 `casStatusWithFailReason` 把它改成 null 或某个成功字样，这段历史就丢了。** 而排查问题时，『哪些预约曾经失败过但最终成功了』恰恰是最有价值的信息。

**★ 这体现了一个设计原则**：**状态字段表达『现在是什么』，审计字段表达『曾经发生过什么』。两者不能互相覆盖。** 把审计信息塞进状态字段（或者为了『干净』而清空审计字段），都会让系统在出问题时失去可观测性。

**我在文档里也登记了它的边界**：`fail_reason` 是 `varchar(255)`，而且**只保留最近一次失败**（`recordFailReason` 是覆盖写，不是追加）。**要完整的历史，需要一张事件表**——**当前没有**。」

## Q38. 为什么要先写账本、再扣 Redis？

**推荐回答**

「**因为 Redis 是易失存储，而 MySQL 是持久的——凭据必须落在不会丢的地方，才能被后续的自愈机制找到。**

**这个顺序是『不丢单』要求的直接推论。** 看一下如果反过来的后果：

| 顺序 | 崩在中间会怎样 |
|---|---|
| **先扣 Redis，再写账本** | ❌ **Redis 已扣、账本没写** → **没有任何记录** → 对账扫不到 → **名额永久泄漏**（只有 Redis 键过期才『恢复』，但那时批次早结束了） |
| **先写账本，再扣 Redis** | ✅ 账本里有 `PRE_ACCEPTED` → **对账会扫到它** → 查 `tb_reservation` 无对应行 → **归还名额 → `COMPENSATED`** |

**第二行就是这个设计的全部价值**：**崩溃点之前留下的记录，成了恢复的锚点。**

**★ 但这里有一个我必须讲清楚的细节——顺序对，不代表漏洞没有了。**

如果崩在『写账本之后、扣 Redis 之前』，那么：

- 账本有一条 `PRE_ACCEPTED`；
- **Redis 名额根本没被扣**；
- 10 分钟后对账扫到它 → **查 `tb_reservation` 无对应行 → 执行 `rollback` → 名额 +1**！

**这就是一个真实的『反向偏差』**：**名额凭空多了一个，超卖了。**

**那为什么它没成为一个问题？** 因为 **`reservationRollback.lua` 的幂等判定挡住了它**：

```lua
if redis.call('SREM', KEYS[2], ARGV[1]) == 0 then
    return 0        -- ★ 用户本来就没在集合里 → 直接返回，不 INCR
end
```

**这个用户从没成功抢过名额，所以他不在 `users` 集合里，`SREM` 返回 0，脚本直接返回 0，`INCR` 不会执行。** 对账的 `rollback` 调用是**无害的**。

**★ 所以这两件事必须一起看：**
1. **账本前置**给出了『崩溃点在哪都能被记录』的覆盖；
2. **`SREM` 幂等**给出了『记录存在 ≠ 真的占用了名额』的区分能力。

**缺任何一个都会出错**：没有①就漏记（名额泄漏），没有②就误判（名额超发）。**这就是为什么我把 `reservationRollback.lua` 的三行逻辑（`SREM` → `EXISTS` → `INCR`）称为这个项目的『最小但最关键的一段代码』。**」

**面试官继续追问：那为什么账本不干脆记一个『Redis 已扣』的标记？**

**追问回答**

「**因为 Redis 的扣减结果本身就不是一个可以可靠持久化的东西——它会引入新的不一致。**

**设想加一个两阶段标记**：写账本 `PRE_ACCEPTED` → 扣 Redis → 写账本 `QUOTA_TAKEN`。那么崩在第二步和第三步之间时，账本还是 `PRE_ACCEPTED`，**你依然不知道 Redis 扣没扣**。

**要真正做到『知道』，只有两条路：**

1. **把 Redis 的扣减结果也写进 MySQL**（多一次写 + 依然有崩溃窗口）；
2. **查 Redis 反推**——但**对账的时候去查 Redis 是不可靠的**，因为：`users` 集合可能已经过期（TTL 到了）、名额键可能已经被删（批次关闭）、或者**用户已经取消并重新预约**（集合里有同一个 userId，但那代表的是另一条预约）。

**★ 第 2 点正是这个项目的选择：不查 Redis，用 `SREM` 的返回值来『顺带判断』。**

**这个思路的巧妙之处在于**：**它不需要事先知道 Redis 扣没扣，而是让『归还』这个动作本身携带幂等性。** 归还时如果发现『这个人根本不在集合里』，就说明**要么他从没扣成功过、要么已经被归还过了**——**两种情况都不该 `INCR`**。

**这就是为什么 `reservationRollback.lua` 不需要任何外部状态**——**幂等性内建在操作的语义里，而不是靠一个额外的标记位。** 这类设计有个通用的名字叫**『幂等令牌』**（idempotency token）：`SREM` 的返回值就是这个令牌。

**★ 有一个代价要说明**：这个方案的**幂等粒度是 `userId`，不是 `reservationId`**。所以它在『同一用户取消后重新预约』的场景下**语义会错**（Q22 和 Q57 都讲了这一点）。**真正的保护在上层：只有 `TRANSITIONED` 才允许调用 `rollback`。**」

## Q39. 为什么 `submit` 不能加 `@Transactional`？

**推荐回答**

「**因为这个方法里有三件『不应该在事务里做的事』，其中一件会阻塞 5 秒。**

**看一下 `submit` 的完整结构**：

```java
public Long submit(Long batchId) {
    // ① 一堆前置校验（只读查询）
    // ② 生成 reservationId（★ Redis：INCR）
    // ③ createPreAccepted(...)   ← ★ MySQL 写
    // ④ tryAcquire(...)          ← ★ Redis：Lua
    // ⑤ publishReservationMessage(...)  ← ★ 阻塞等 confirm，超时 5 秒
    return reservationId;
}
```

**③ 是唯一的 MySQL 写，而 ④⑤ 都是外部系统调用。**

**如果加了 `@Transactional`：**

**问题一：事务会跨越一次最长 5 秒的网络等待。** ⑤ 里的 `correlationData.getFuture().get(5, TimeUnit.SECONDS)` 是**同步阻塞**的。加到 5 秒意味着：

- **这个数据库连接被占用 5 秒**；
- Hikari 连接池**默认只有 10 个连接**（`application.yaml` 没配 `spring.datasource.hikari.*`，用的是默认值）；
- **broker 慢的时候，10 个并发请求就能把连接池打满**，然后所有请求（包括其他接口）都开始等连接——**一个慢 MQ 会拖垮整个应用**。

**问题二：事务给不了任何真实的原子性保证。** 事务能回滚的只有 ③（那条 INSERT）。**④ 的 Redis `DECR` 和 ⑤ 的 MQ 投递都不在事务里**——如果 ⑤ 失败后抛出异常触发回滚：

- MySQL 里的 `PRE_ACCEPTED` 行**被回滚掉了**；
- **但 Redis 名额已经扣了，而且没有任何记录。**

**这恰恰就是 Q38 说的最坏情况：Redis 已扣 + 没有记录 = 名额永久泄漏。** ——**加事务反而制造了它本来要防的那个漏洞。**

**问题三：账本行在事务提交前对其他连接不可见。** 如果消费极快（消息投递成功、消费者立刻处理），消费者会去查 `tb_reservation_request`——**而那条 INSERT 还没提交**（因为事务要等 ⑤ 结束才提交）。

**消费者会查不到账本行**，走到这个分支：

```java
if (request == null) {
    log.warn("预约请求账本不存在，继续落库：reservationId={}，userId={}", ...);
}
```

**这个分支是存在的**（说明开发者知道账本可能查不到），但**它跳过了『账本已 `COMPENSATED` 就拒绝落库』的保护**——那条 `COMPENSATED` 检查在 `request == null` 时不生效。

**★ 所以正确答案是**：`submit` **不加事务**，让 ③ 立刻自动提交（MyBatis-Plus 单条 `insert` 在无事务时是自动提交的），**账本立刻对其他连接可见**；④⑤ 的失败用**显式的补偿逻辑**处理，而不是靠事务回滚。

**★ 这也解释了为什么项目里只有 3 处 `@Transactional`**（`ReservationPersistenceServiceImpl.persist`、`ReservationLifecycleServiceImpl.cancel` / `complete`）——**它们都是『纯数据库的多步操作』，而且都不包含网络调用或 Redis 操作**。`persist` 是『扣名额 + 插预约行』，`cancel` 是『改预约状态 + 回补批次名额』，`complete` 是『改预约状态』。**这三个事务的边界和数据库操作的边界完全重合，不多不少。**」

## Q40. CAS 是怎么写的？为什么不用 `updateById`？

**推荐回答**

「**因为 `updateById` 是『无条件更新』——它会把并发下已经被别人改掉的状态覆盖回去。**

**先看项目的 CAS 写法**（以 `persist` 里最有代表性的一处为例）：

```java
boolean quotaDecremented = reservationBatchService.update(
        new LambdaUpdateWrapper<ReservationBatch>()
                .eq(ReservationBatch::getId, reservation.getBatchId())
                .gt(ReservationBatch::getRemainingQuota, 0)              // ★ 条件
                .setSql("remaining_quota = remaining_quota - 1"));       // ★ 自减
```

**这条 SQL 展开是**：

```sql
UPDATE tb_reservation_batch
SET remaining_quota = remaining_quota - 1
WHERE id = ? AND remaining_quota > 0
```

**InnoDB 会加行锁，而且 `WHERE` 条件在锁内重新求值**（这是 `UPDATE ... WHERE` 的语义，不是先读后写）。所以**并发执行时，第二个事务会看到第一个事务扣减后的值**——`remaining_quota > 0` 不成立，更新 0 行。

**★ 用 `updateById` 写会是什么样？**

```java
ReservationBatch batch = reservationBatchService.getById(batchId);   // 读到 remaining=1
if (batch.getRemainingQuota() > 0) {
    batch.setRemainingQuota(batch.getRemainingQuota() - 1);          // 算出 0
    reservationBatchService.updateById(batch);                        // SET remaining_quota = 0
}
```

**两个线程可以这样交错：**

```
时刻  A                                B
 T1   读到 remaining=1
 T2                                   读到 remaining=1
 T3   判断 >0 ✓
 T4                                   判断 >0 ✓
 T5   updateById → SET remaining=0
 T6                                   updateById → SET remaining=0   ← ★ 两个都成功，只扣了 1
```

**这是典型的『读-改-写』竞态（`check-then-act`）。** 结果：**两个学生都预约成功，但名额只减了 1——超卖。**

**★ 三种写法的对比**：

| 写法 | 原子性 | 问题 |
|---|---|---|
| `updateById` | ❌ | 读-改-写三步，中间可被插入 |
| `UPDATE ... SET x = x - 1`（无 `WHERE` 条件） | ✅ 原子 | **但不会拒绝『已经扣到 0』的情况**，会扣成负数 |
| **`UPDATE ... SET x = x - 1 WHERE x > 0`** | ✅ 原子 + ✅ 拒绝 | **正确** |

**★ 关键不是『用 SQL 而不是 Java』，而是『把判定条件写进 UPDATE 的 WHERE 里』。** `SET x = x - 1` 让『读当前值』和『写新值』在一条语句里完成；`WHERE x > 0` 让『判定』也在同一把行锁里完成。**判定和使用被合并成了一个原子操作——这正是在 SQL 层面解决 TOCTOU 的标准做法。**

**★ 而且它的返回值就是判定结果**：`affectedRows == 0` 表示『没扣到』，`== 1` 表示『扣到了』。**不需要再查一次库去确认。** `persist` 里就是这么用的：

```java
if (!quotaDecremented) {
    return ReservationPersistResult.QUOTA_CONFLICT;    // affectedRows == 0
}
```

**项目里有 16 处这种 `LambdaUpdateWrapper` 赋值。** 这是这个代码库最重要的一个写作习惯。」

**面试官继续追问：那批次状态迁移的 CAS 呢？**

**追问回答**

「**同理，而且那里的『条件』是状态本身。**

`ReservationServiceImpl` 里关批次是这么写的：

```java
int updated = reservationBatchMapper.update(null,
        new LambdaUpdateWrapper<ReservationBatch>()
                .eq(ReservationBatch::getId, id)
                .eq(ReservationBatch::getStatus, ReservationBatchStatus.PUBLISHED)   // ★ 期望状态
                .set(ReservationBatch::getStatus, ReservationBatchStatus.CLOSED));   // 目标状态
```

**这条 SQL 的语义是**：『**如果它现在是 `PUBLISHED`，就把它改成 `CLOSED`；否则什么都不做。**』

**它一次解决了三个问题**（1 条 SQL 换了 3 条）：

1. **状态校验**（现在是 `PUBLISHED` 吗？）——`WHERE status = 'PUBLISHED'`；
2. **并发互斥**（两个管理员同时操作呢？）——**只有一个能 `affectedRows == 1`**；
3. **幂等**（重复操作呢？）——第二次 `affectedRows == 0`。

**如果用 `updateById`，这三件事都要在 Java 里手写**：读一次、判断、写一次——**又回到读-改-写竞态**，而且**每一次都要重新想一遍『我怎么知道中间没人改过』**。

**★ 账本状态机用的也是同一个模式**（`ReservationRequestServiceImpl.casStatus`），而且它的期望值是一个**集合**：

```java
.eq(ReservationRequest::getRequestId, requestId)
.in(ReservationRequest::getStatus, Arrays.asList(expectedStatuses))   // ★ IN，不是 EQ
.set(ReservationRequest::getStatus, target)
```

**用 `IN` 而不是 `EQ` 的原因**就是 Q37 说的：**允许从任意非终态一步跳到目标态**，不要求经过 `PUBLISHED`。**这让状态机是一个『有向图』而不是『链』——更宽松，因此对执行顺序的耦合更小。**

**★ 而这里有一个必须存在的守卫**：

```java
if (expectedStatuses == null || expectedStatuses.length == 0) {
    throw new IllegalArgumentException("expectedStatuses 不能为空");
}
```

**如果没有这个检查，传入空数组会生成 `IN ()`**——这是 **SQL 语法错误**，或者（取决于实现）**条件被静默忽略**，`IN` 子句消失 → **CAS 退化成无条件更新**！那就变成了它本来要防的 `updateById` 语义。

**这个守卫有专门的测试钉住**：`ReservationRequestStateTest.shouldRejectEmptyExpectedStatuses`。**这是我见过的最值得写测试的一类守卫——它的失效是静默的。**」

## Q41. `UNKNOWN` 状态存在的意义是什么？

**推荐回答**

「**它是唯一一个表示『我不知道』的状态，而这个『不知道』是分布式系统里必须能被表达的东西。**

**三个投递结果里，只有 `UNKNOWN` 无法当场裁决**（Q33）：

- `ACKED` → 成功，推进；
- `DEFINITELY_NOT_DELIVERED` → 失败，**当场归还名额 + `COMPENSATED`**；
- `UNKNOWN` → **既不能算成功（可能没到），也不能算失败（可能到了）**。

**★ 为什么不能选一个方向草率处理？两个方向都是错的：**

| 如果草率地… | 后果 |
|---|---|
| **当作成功**（不归还名额） | 如果消息其实没到 → **Redis 名额被永久占用，而 MySQL 里没有预约行** → 一个名额凭空消失，**而且 Redis 和 MySQL 的名额永远对不上** |
| **当作失败**（归还名额） | 如果消息其实到了 → **MySQL 里有一条占用名额的预约，但 Redis 名额被还了** → **下一个学生能抢到这个名额 → 超卖** |

**所以 `UNKNOWN` 的设计是：拒绝在信息不足时做决定，把它变成一个『待裁决』的状态，交给一个信息更充分的时刻去决定。**

**★ 那个『更充分的时刻』是什么时候？10 分钟后。** 因为对账的判据是：

```java
if (reservationMapper.selectById(request.getRequestId()) != null) {
    // 有预约行 → 消息确实被消费了 → CONFIRMED
} else {
    // 无预约行 → 消息确实没被消费 → 归还名额 + COMPENSATED
}
```

**★ 这个判据比投递结果更可靠，因为它查的是『最终事实』而不是『过程中的信号』**——MySQL 里有没有那行数据，是**不可辩驳的**；而 confirm 超时只是一个**关于网络的推测**。

**★ 用一句话总结这个设计**：**当无法确定时，先记录『不确定』，然后用一个周期性的、查询最终事实的扫描来消除不确定性。**

**这就是『最终一致性』的字面意思**——**不是『永远不一致』，而是『在有限时间内收敛到一致』。**

**★ 而 10 分钟这个阈值的意义**：它必须**足够长**，让所有正常路径都有机会完成（消息投递 + 消费 + 重投）；又必须**足够短**，让用户不至于等太久。`reconcile-threshold-ms: 600000` 是 10 分钟，`reconcile-interval-ms: 300000` 是 5 分钟扫一次，**所以最坏情况下一个 `UNKNOWN` 请求要 15 分钟才被裁决**。

**★ 这个 15 分钟是我要主动说明的上界**：它不是设计出来的精确值，而是『10 分钟阈值 + 5 分钟扫描间隔』的**最坏叠加**。**如果对账的 `initialDelay` 和 `fixedDelay` 恰好对齐得不好，实际时间还会更长。**」

**面试官继续追问：那 `UNKNOWN` 状态下用户看到什么？**

**追问回答**

「**HTTP 503 + `"预约结果待确认，请稍后查询"`。**

**这是一个『诚实的错误信息』**——它没有说『预约失败』（因为可能成功），也没有说『预约成功』（因为可能失败），而是**如实告诉用户『不知道』**。

**★ 问题在于：前端的处理是把它当成失败展示的。**

`ReservationServiceImpl.submit` 抛 `ServiceUnavailableException`，`WebExceptionAdvice` 捕获后返回 **503 + `Result.fail("预约结果待确认，请稍后查询")`**。前端的 `catch` 分支会弹一个错误提示。**用户看到的是『报错』，而不是『等待中』。**

**要正确处理这个状态，前端应该：**

1. **识别 503 这个特定的状态码**（而不是把所有非 2xx 都当失败）；
2. **不弹错误提示，而是显示『预约结果处理中，请在「我的预约」查看』**；
3. **引导用户去列表页**——如果预约真的成功了，那里能看到。

**★ 而这个设计在数据层面是自洽的**：如果 `UNKNOWN` 最终被裁决为 `CONFIRMED`，那么 `tb_reservation` 里**确实有一行**，用户在『我的预约』**能看到它**。所以『去列表页查看』这个引导是**真的有效**的。

**当前项目边界**：503 这个语义**只存在于后端的错误消息文本里**，**前端没有对它做特殊处理**。文档里也没有写『前端应该如何渲染 503』。**这是一个端到端的契约缺口**——后端提供了一个比『失败』更精确的信息，但消费方把它降级成了『失败』。」

## Q42. 对账为什么用 `update_time` 而不是 `create_time` 判断「陈旧」？

**推荐回答**

「**因为 `create_time` 只表示『请求是什么时候来的』，而 `update_time` 表示『这条请求最后一次有进展是什么时候』——对账要判断的是后者。**

**代码**（`ReservationRequestServiceImpl.listStale`）：

```java
List<ReservationRequest> requests = reservationRequestMapper.selectList(
        new LambdaQueryWrapper<ReservationRequest>()
                .in(ReservationRequest::getStatus, ReservationRequestStatus.nonTerminalStatuses())
                .lt(ReservationRequest::getUpdateTime, before)          // ★ update_time
                .orderByAsc(ReservationRequest::getUpdateTime)
                .orderByAsc(ReservationRequest::getRequestId)
                .last("LIMIT " + limit));
```

**如果用 `create_time`，会发生什么？**

**一条请求从创建到被裁决，中间可能经历多次重试**——消息进 DLQ 又重放、消费时锁超时被 NACK 重投、对账上一轮处理失败。**用 `create_time` 判断，意味着一条 20 分钟前创建、但 1 分钟前刚刚重放过的请求，会被判定为『陈旧』而立即再次处理**——**对账会和正在进行的重放打架。**

**用 `update_time` 就自然解决了**：**只要这条请求有任何进展，它就会退出『陈旧窗口』，等下一个 10 分钟再被考虑。**

**★ 而这里有一个必须显式处理的坑，是这个项目里最精细的一处修复。**

**MySQL 的 `ON UPDATE CURRENT_TIMESTAMP` 有一个反直觉的行为：如果 UPDATE 语句设的值和当前值相同，它不触发。**

DDL 里 `tb_reservation_request.update_time` 是：

```sql
update_time datetime ... ON UPDATE CURRENT_TIMESTAMP
```

所以正常情况下，改任何字段都会自动推进 `update_time`。**但 `recordFailReason` 写入的是 `fail_reason`**——如果**连续两轮对账都以同样的原因失败**（比如 DB 一直超时，两次都写 `RECONCILE_ATTEMPT_FAILED`），那么：

- 第一次写 → `fail_reason` 变了 → **`ON UPDATE` 触发，`update_time` 推进**；
- 第二次写 → `fail_reason` **还是同一个值** → **MySQL 认为没有变化，`ON UPDATE` 不触发** → **`update_time` 原地不动**。

**后果**：这条请求**永远留在陈旧窗口里，而且因为 `orderByAsc(updateTime)` 一直排在队首** ——**每一轮对账都会先处理它、再失败、再占用一个 `limit` 配额**。如果 `limit` 是 200，**只要有 200 条持续失败的请求，对账就再也扫不到后面的任何请求了**——**整个自愈机制瘫痪。**

**所以 `recordFailReason` 必须显式写 `update_time`**，代码里的注释完整记录了这个推理：

```java
// 首次写入失败原因会触发 MySQL 的 ON UPDATE，但重复写入同一原因是 no-op，
// 不会自动推进 update_time；这里必须显式赋值，避免持续失败行重新钉在扫描窗口队首。
return reservationRequestMapper.update(null, new LambdaUpdateWrapper<ReservationRequest>()
        .eq(ReservationRequest::getRequestId, requestId)
        .set(ReservationRequest::getFailReason, failReason)
        .set(ReservationRequest::getUpdateTime, LocalDateTime.now())) == 1;
```

**同样的处理也用在 `releasePendingQuotas` 的失败分支**（`deferPendingQuotaReleaseSafely`）：Redis 归还失败时，显式推进 `reservation.update_time`——因为 `selectPendingQuotaReleases` 的 SQL 是 `ORDER BY r.update_time ASC, r.id ASC LIMIT #{limit}`，**同一个队首问题**。

**★ 这个坑有专门的回归测试**：`ReservationReconcileTest.shouldAdvanceUpdateTimeWhenSameReconcileFailureRepeats`。

**我认为这是整个项目里最值得学习的一个 bug 类型**——**它是『依赖了数据库的一个隐式行为，而那个行为在特定条件下不生效』**。它没有任何报错、没有任何异常，只是在数据积累到一定程度后让一个后台任务静默停摆。**而且不写那个测试，你几乎不可能发现它。**」

## Q43. 为什么 `requestId` 和 `reservationId` 是同一个值？

**推荐回答**

「**因为这样对账只需要『查一次主键』就能判断『这次预约成功了吗』——不需要任何额外的映射。**

**代码上的证据**：

- 生成：`long reservationId = redisIdWorker.nextId("reservation");`
- 写账本：`createPreAccepted(reservationId, user.getId(), batchId)` → `tb_reservation_request.request_id = reservationId`
- 发消息：`message.setReservationId(reservationId)`
- 落库：`new Reservation().setId(messageDTO.getReservationId())` → `tb_reservation.id = reservationId`
- 对账：`reservationMapper.selectById(request.getRequestId())` ← **★ 用账本的 ID 直接查预约表**

**五个地方，一个值。** 而对账的那个查询是整个自愈机制的**核心判据**：

```java
if (reservationMapper.selectById(request.getRequestId()) != null) {
    // 有行 → 成功了 → CONFIRMED
} else {
    // 无行 → 没成功 → 归还名额 → COMPENSATED
}
```

**★ 如果两者不同（比如账本有自己的自增 ID），对账会变成什么样？**

需要**先通过某种方式找到对应的 `reservationId`**：

- 加一列 `reservation_id`？——但**那条预约可能根本没落库，所以这个值是 null**，你就回到了『不知道』；
- 用 `(user_id, batch_id)` 联合查询？——**但这两个字段不能唯一确定一条预约**（用户取消后重新预约，会有两条同 `user_id` + `batch_id` 的记录，见 Q57 讲的场景）；
- 加一张映射表？——**多一张表、多一次不一致的风险**。

**所以『同源 ID』的价值是**：**它让『这次请求成功了没有』这个问题，退化成一个主键是否存在的一次查询。** 没有映射、没有联表、没有歧义。

**★ 有一个必须说清楚的边界**：这个等价关系**只在『一个 `reservationId` 对应一次预约尝试』时成立**。

**而在这个项目里它成立**，因为：

- 每次 `submit` 都会调用 `nextId("reservation")` 生成**新的** ID——**即使同一个用户对同一个批次重复提交，也是两个不同的 ID**；
- `RedisIdWorker` 保证**全局唯一 + 趋势递增**（Q55）。

**所以 `reservationId` 是『一次预约尝试』的主键，而不是『一个用户在一个批次里的预约』的主键。** 后者是靠 `uk_user_batch_active` 唯一索引约束的（Q54）。**两个不同的概念，各自有自己的主键。**

**★ 有一个之前分析过的细节值得在这里提一下**：在『用户重复提交』的情况下，**第二个请求的账本被推成 `CONFIRMED`，但 `tb_reservation` 里没有它那个 ID 的行**（Q35 追问里讲了这个）。**所以 `requestId` 存在、预约行不存在、但账本状态是终态——对账不会扫它**（只扫非终态），**所以不会引起误判。**

**这个情况从『账本与预约行一一对应』的角度看是破的**，但它**不会导致错误的自愈行为**。我把它登记为语义粗糙处，而不是缺陷。」

# 第七层 · 对账、补偿与自愈

## Q44. 对账任务具体做什么？

**推荐回答**

「`ReservationReconcileServiceImpl.scheduledReconcile` 一个调度薄壳，里面做**三件事**（按顺序）：

```java
ReconcileSummaryDTO summary = reconcile(reconcileLimit);     // ① 裁决陈旧请求
int released = releasePendingQuotas(reconcileLimit);         // ② 补偿未完成的 Redis 归还
int noShows = markNoShows(reconcileLimit);                   // ③ 判定爽约
```

**① `reconcile(limit)` —— 核心。** 扫出 `update_time` 早于『现在 − 10 分钟』**且状态非终态**的请求（最多 `limit` 条，默认 200，按 `update_time` 升序），逐条裁决：

| 条件 | 动作 | 计入 |
|---|---|---|
| `tb_reservation` 里有这个 ID 的行 | `casStatus(CONFIRMED, 非终态全体)` | `confirmed` / `skipped` |
| 没有这个行 | **先 `rollback(batchId, userId)`** → `casStatusWithFailReason(COMPENSATED, "RECONCILE_NO_RESERVATION", ...)` | `compensated` / `skipped` |
| 抛异常 | 记 `failed`，写 `fail_reason = "RECONCILE_ATTEMPT_FAILED"`，**继续处理下一条** | `failed` |

**② `releasePendingQuotas(limit)` —— 补取消时没还上的名额。**

`ReservationServiceImpl.cancel` 在 DB 事务提交之后归还 Redis 名额。**如果那一步失败**，`tb_reservation.quota_released` 会留在 `false`。这个方法扫出 `status = 'CANCELLED' AND quota_released = 0` 的行（按 `update_time` 升序，`LIMIT`），**先 `rollback` 再 CAS 置 `quota_released = true`**。

**③ `markNoShows(limit)` —— 判定爽约。**

一条 SQL 搞定：`RESERVED` 且所在批次 `end_time < now` 且批次不是 `CANCELLED` → `status = 'NO_SHOW'`。**爽约不归还名额**（名额在取消时才归还，用完了就是占用过了）。

**★ 三个任务的共同点是『都是幂等的、都能重复执行』**——这是它们能被安全地每分钟/每 5 分钟重跑的前提。

**★ 调度参数**（都可以从配置覆盖，默认值给了兜底）：

| 参数 | 默认 | 含义 |
|---|---|---|
| `reconcile-interval-ms` | 300000（5 分钟） | 两轮之间的**间隔**（`fixedDelay`，从上一轮**结束**开始算） |
| `reconcile-initial-delay-ms` | 300000（5 分钟） | 应用启动后**首次执行**的延迟 |
| `reconcile-threshold-ms` | 600000（10 分钟） | 多久没进展算『陈旧』 |
| `reconcile-limit` | 200 | 每轮每类处理的**上限** |

**★ `initialDelay` 设 5 分钟是有意的**：避免应用启动瞬间（各种初始化、缓存预热还没完成）就开始扫库。**

**面试官继续追问：一轮处理不完怎么办？**

**追问回答**

「**留给下一轮——因为 `limit` 是硬上限，而且按 `update_time` 升序，所以是『先处理最老的』。**

**这是一个刻意的取舍**：**不追求一轮清空，而是保证『最老的优先被处理』和『单轮开销有界』。**

**★ 但这里有一个真实的容量边界，我要主动算一下：**

- 每 5 分钟一轮，每轮最多 200 条 → **理论上每小时能处理 2400 条**；
- **如果积压超过这个速率，永远追不上**——而且因为按 `update_time` 升序，**积压会集中在队列尾部，新的请求要等很久**。

**更关键的是**：`limit` 是**三类任务各自**的 200 条，而且**扫描是三条独立的 SQL**——所以一轮的实际数据库操作量是 `200 × (若干次查询 + 若干次更新)`，**量级在千次上下**。

**★ 而我关心的不是容量，是『没有告警』这件事。** 目前对账的产出只有：

```java
log.debug("预约对账本轮无陈旧请求");                      // 正常
log.info("预约对账完成：scanned={}，confirmed={}，...", ...);  // 有处理
```

**没有指标、没有阈值告警。** 也就是说：

- 如果 `scanned` 每轮都是 200（**说明积压了**）——**只有一行 info 日志，没人会看到**；
- 如果 `failed` 持续增长（**说明 DB 或 Redis 有问题**）——**同样只有日志**；
- 如果对账**根本没在跑**（比如看门狗导致锁不释放，Q26）——**日志里连一行都没有**，因为 `log.debug` 在 `com.yanyuetong: debug` 下会打，但**没有『上一轮是什么时候』的心跳记录**。

**★ 加固方向**：把 `ReconcileSummaryDTO` 的三个计数暴露成 Micrometer 指标（`scanned`/`confirmed`/`compensated`/`failed`），并对 `failed > 0` 和 `scanned == limit` 设告警。**当前项目没有引入任何指标系统**（没有 Actuator、没有 Micrometer）。**这是我认为最该补的一块，因为它关系到『自愈机制本身有没有在自愈』。**」

## Q45. 分布式锁在对账里起什么作用？为什么说它只管性能？

**推荐回答**

「**锁只减少重复工作，正确性不押在锁上——这句话是写在方法注释里的，也是这个项目最重要的一个设计判断。**

```java
/**
 * 定时调度薄壳：分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证。
 */
@Scheduled(fixedDelayString = "...", initialDelayString = "...")
public void scheduledReconcile() {
    RLock lock = redissonClient.getLock(RedisConstants.LOCK_RESERVATION_RECONCILE_KEY);
    boolean locked;
    try {
        locked = lock.tryLock(0, TimeUnit.MILLISECONDS);      // ★ waitTime=0，抢不到就跳过
    } catch (InterruptedException e) { ... }
    if (!locked) {
        log.debug("预约对账未获取到分布式锁，跳过本轮");
        return;
    }
    try {
        // 三段任务
    } finally {
        if (lock.isHeldByCurrentThread()) {
            lock.unlock();
        }
    }
}
```

**★ 锁的作用是『避免多个实例做同一件事』**：如果两个实例同时扫到同一批 200 条请求，会做两倍的数据库操作、打两倍的日志——**纯浪费**。锁把这种浪费消除掉。

**★ 那为什么不押在锁上？** 因为**分布式锁本身是一个会失效的机制**：

1. **租约到期**——这里用的是 `tryLock(0, MILLISECONDS)`（两参重载，`leaseTime` 未指定 → **启用看门狗**）。看门狗每 `lockWatchdogTimeout/3`（默认 10 秒）续期一次。**但如果应用发生长 GC 停顿、或者看门狗线程所在的调度器被饿死，续期就可能失败，锁会意外释放。**
2. **网络分区**——持锁实例和 Redis 之间断了，锁会过期，另一个实例可以拿到；
3. **实例假死**——进程还在但卡住了，看门狗可能还在续期（**更糟：锁被一个僵死的实例长期持有**）。

**所以如果正确性依赖锁，那么任何一次锁失效都会导致数据错误。** 而这个项目的做法是**让正确性完全不依赖锁**：

| 任务 | 保护机制 |
|---|---|
| `reconcile` 的账本迁移 | **CAS**——`UPDATE ... WHERE request_id = ? AND status IN (非终态)`。**两个实例同时执行，只有一个 `affectedRows == 1`**，另一个计入 `skipped` |
| `reconcile` 的名额归还 | **`reservationRollback.lua` 的 `SREM` 幂等**——第二次调用返回 0，**不 `INCR`** |
| `releasePendingQuotas` | **CAS**——`.eq(Reservation::getQuotaReleased, false).set(getQuotaReleased, true)`，只有一个能改 |
| `markNoShows` | **状态迁移本身幂等**——`WHERE status = 'RESERVED'`，第二次执行匹配不到行 |

**★ 所以『两个实例同时对账』（异常场景 19）的结果是：和单实例完全相同。** 最坏情况是多做了一些无用功、多打了一些日志。

**★ 我认为这是这个项目里最值得讲的一个取舍**：**用锁换性能是安全的（错了只是慢），用锁换正确性是危险的（错了就是数据错）。** 很多人在设计分布式任务时的第一反应是『加锁保证不重复执行』——**但如果加锁变成了正确性的必要条件，那这个系统的可靠性上限就是 Redis 的可靠性。** 而把它降级成性能优化之后，**Redis 挂了最坏也只是多个实例重复劳动，结果依然正确**（当然，Redis 挂了整个系统本来就约不了，见 Q8）。」

**面试官继续追问：那看门狗在 `reconcile` 上不是有风险吗？**

**追问回答**

「**有，而且这个风险正好被『锁只影响性能』这个设计兜住了——但它的表现形式很隐蔽。**

**风险是这样**：`tryLock(0, MILLISECONDS)` 用两参重载 → **看门狗启用** → 只要 `scheduledReconcile` 这个线程还活着，**锁就每 10 秒续期一次，永不释放**。

**如果对账卡在一次没有超时设置的数据库调用上**（比如一个慢查询、或者一个被锁住的 UPDATE），那么：

- 这个线程一直卡着 → **看门狗一直续期** → **锁被无限持有**；
- **其他所有实例的对账全部跳过**（`log.debug("未获取到分布式锁，跳过本轮")`）；
- **自愈机制静默停摆。**

**而『锁只影响性能』这句话在这里救不了场**——因为**正确性虽然不依赖锁，但『自愈』依赖『对账确实在跑』**。锁不会让数据变错，**但会让错误无法被修复**。

**更糟的是可观测性**：其他实例打的是 `log.debug`，而 `application.yaml` 里 `com.yanyuetong: debug` **确实会打出这行**——**但没有人会去数『每 5 分钟有一行 debug 日志』**。而持锁的那个实例，因为卡住了，**连 `log.info` 都不会打**。所以表现是：**日志安静了，但看起来一切正常。**

**★ 加固方向（当前都没做）**：

1. **给数据库调用加超时**——`@Transactional(timeout = 30)` 或者 MyBatis 的 `defaultStatementTimeout`；
2. **给对账整体加一个超时看门狗**——比如记录『本轮开始时间』，超过 N 分钟就在下一轮强制跳过并告警；
3. **加一个心跳**——`log.info` 无条件打印『第 N 轮开始』，这样日志断流就能被监控发现；
4. **最简单的**：把 `tryLock(0, MILLISECONDS)` 改成显式租约（比如 `tryLock(0, 5, MINUTES)`），**放弃看门狗**——代价是如果对账真的超过 5 分钟，会短暂出现两个实例并行（**而这已经被证明是安全的**）。

**★ 第 4 点很有意思**：**因为正确性不依赖锁，所以『锁提前释放』这个失效模式是可以接受的，而『锁永不释放』不可接受。** 用一个**有界的租约**换掉看门狗，正好把风险从『不可接受』挪到『可接受』那一侧。**这是『正确性不依赖锁』这个设计带来的额外自由度——如果正确性依赖锁，你就不敢放弃看门狗了。**」

## Q46. 为什么对账里必须先 `rollback` 再改状态？

**推荐回答**

「**因为这个顺序决定了『失败时会怎样』——它让失败落在一个可以重试的状态上，而不是一个永久损坏的状态上。**

代码里有一句注释直接给出了理由：

```java
// 必须先补偿再推进终态：补偿失败时保留非终态，下一轮才能继续重试。
rollbackExecutor.rollback(request.getBatchId(), request.getUserId());
boolean updated = reservationRequestService.casStatusWithFailReason(
        request.getRequestId(),
        ReservationRequestStatus.COMPENSATED,
        NO_RESERVATION_FAILURE_REASON,
        NON_TERMINAL_STATUSES);
```

**两种情况对比：**

**✅ 正确顺序（rollback → CAS）：**

| 步骤 | 结果 |
|---|---|
| `rollback` 成功，CAS 成功 | `compensated++`，名额已还，**收敛** |
| `rollback` 成功，CAS **失败** | 计入 `skipped`。**下一轮会再 `rollback` 一次** → `reservationRollback.lua` 的 `SREM` 返回 0 → **不重复 `INCR`**，然后 CAS 再试一次。**收敛，且没有多还名额** |
| `rollback` **抛异常** | 抛到外层 `catch` → `failed++`，**状态仍是非终态** → 下一轮继续 | 

**❌ 错误顺序（CAS → rollback）：**

| 步骤 | 结果 |
|---|---|
| CAS 成功，`rollback` 成功 | 正常 |
| CAS 成功，`rollback` **失败** | **状态已经是 `COMPENSATED`（终态）→ `listStale` 永远不会再扫到它** → **名额永久泄漏，无人知晓** |

**★ 所以这个顺序的价值是：把『补偿失败』的后果，从『永久损坏』降级为『下一轮重试』。**

**同样的模式出现在 `releasePendingQuotas` 里**：

```java
rollbackExecutor.rollback(reservation.getBatchId(), reservation.getUserId());   // 先还名额
int updated = reservationMapper.update(null, new LambdaUpdateWrapper<Reservation>()
        .eq(Reservation::getId, reservation.getId())
        .eq(Reservation::getQuotaReleased, false)          // ★ 后置标记
        .set(Reservation::getQuotaReleased, true));
```

**★ 同样的模式还出现在 `ReservationServiceImpl.cancel` 里**：

```java
int rollbackCode = reservationQuotaRollbackExecutor.rollback(...);   // 先还名额
reservationMapper.update(null, ... .eq(getQuotaReleased, false).set(getQuotaReleased, true));  // 后置标记
```

**★ 这三处用的是同一个不变式，我把它总结成一条规则：**

> **『先做不可逆的、幂等的副作用，再记录它已经发生。』**

**为什么可以这样？因为那个副作用是幂等的**——重复执行是安全的。所以真正的顺序要求是：

**『记录』必须在『副作用成功之后』——但『副作用』必须允许重复执行。**

**如果副作用不幂等，这个顺序就不成立了**（重复执行会造成二次归还）。**所以幂等性是这套『先做后记』模式的前提，而不是附带的好处。**

**★ 反过来，如果先记后做，就必须解决『记了但没做』的恢复问题——而那时你没有任何线索知道『做没做』。** 这就是为什么这个项目在所有这类地方都选了『先做后记』。」

**面试官继续追问：`rollback` 返回 2 的时候呢？**

**追问回答**

「**返回 2 表示『用户确实占用了名额，但名额键已经不存在』——只清理了用户标记，没有 `INCR`。**

代码注释写得很清楚：

```java
/**
 * 返回 0 表示用户本来就未占用名额（重复补偿或从未占用），名额不变；
 * 返回 1 表示用户确实占用名额且名额键存在，已归还一个名额；
 * 返回 2 表示用户确实占用名额但名额键已不存在，仅清理用户标记、不归还名额。
 */
```

**★ 为什么『不归还』是正确的？这是这个脚本里最需要解释的一处。**

**关键在于 `INCR` 对一个不存在的 key 的行为**：**`INCR` 在 key 不存在时会创建它，值为 1，而且没有 TTL。**

所以如果脚本在这种情况下执行 `INCR`：

1. **会凭空创建一个名额键，值为 1**；
2. **而且这个键没有 TTL**（`reservation.lua` 里 `KEYS[1]` 也不设 `EXPIRE`）→ **永久残留**；
3. **更糟**：这个批次的 `users` 集合可能也已经过期了，但名额键现在存在了、值为 1 → **`reservation.lua` 的 `EXISTS` 检查会通过** → **一个已经结束的批次重新变得『可预约』**，而且只放一个名额进去。

**这是『用一次错误操作创造一个幽灵批次』的典型场景。**

**★ 所以返回 2 是一个保守的失败：**

- **它承认『这次归还没成功』**（名额没有被 `INCR`）；
- **但它也拒绝制造假象**（不创建假的名额键）；
- **它做了唯一安全的事**：把 `users` 集合里那个已经无意义的标记清掉（因为名额键都没了，这个标记没有任何作用）。

**★ 代价是：`remaining_quota` 在 MySQL 里 +1 了，但 Redis 侧没有。** 这形成了**台账偏离**——不过这也是**必然的**，因为**名额键都不存在了，Redis 侧本来就没有账可对**。

**这个返回值会一路传到日志里**：`ReservationServiceImpl.cancel` 记 `log.info("取消预约后 Redis 名额归还完成：reservationId={}，rollbackCode={}", ...)`。**所以 rollbackCode=2 在日志里是可见的**——**这是排查『Redis 和 MySQL 名额对不上』时第一个要 grep 的东西。**」

## Q47. `reservationRollback.lua` 的幂等是怎么实现的？

**追问式地讲这个问题**——先看脚本：

```lua
if redis.call('SREM', KEYS[2], ARGV[1]) == 0 then
    return 0
end
if redis.call('EXISTS', KEYS[1]) == 1 then
    redis.call('INCR', KEYS[1])
    return 1
end
return 2
```

**推荐回答**

「**幂等性来自 `SREM` 的返回值——它同时充当了『这是不是我第一次归还』的判定。**

**`SREM` 返回『实际移除的成员个数』**：集合里有这个 userId 就返回 1（并移除它），没有就返回 0（什么都不做）。**而『集合里有没有这个 userId』恰好等价于『这个用户是否占着一个名额』。**

| 第几次调用 | `SREM` | 行为 |
|---|---|---|
| 第 1 次 | 1 | 继续 → `INCR`（如果键在）→ 返回 1 |
| 第 2 次 | **0** | **立即返回 0，`INCR` 不执行** |

**★ 所以『恰好归还一次』不是靠外部状态保证的，而是靠『移除操作本身的返回值』保证的。** 这就是**幂等令牌**（idempotency token）的经典手法：**把一个『判断是否已经做过』的问题，转化成一个『操作是否真的改变了状态』的问题。**

**★ 这个手法有三个好处：**

1. **不需要额外的标记位**——不需要在 Redis 或 MySQL 里记『已归还』（虽然项目里确实还有 `quota_released`，但那是给**另一件事**用的，见下）；
2. **不需要锁**——`SREM` 是原子的，Lua 整体是原子的；
3. **可以无条件重复调用**——调用方不需要先查询『该不该归还』，**直接调就是了**。

**★ 那既然 Lua 已经幂等了，为什么还要 `quota_released` 这个字段？**

**因为它们保护的是不同层次的幂等：**

| | `SREM` 幂等 | `quota_released` 幂等 |
|---|---|---|
| **粒度** | **`(batchId, userId)`** | **`(reservationId)`** |
| **在哪** | Redis（易失） | MySQL（持久） |
| **防的是** | Lua 被重复调用 | **Redis 归还这一步整体失败**（比如 Redis 连不上抛异常） |
| **谁来重试** | 调用方可以随便重试 | `releasePendingQuotas` 定时扫 `quota_released = 0` 的行 |

**★ 而 MySQL 侧的那个幂等（`quota_released`）是必需的，因为 Redis 侧的幂等只在『Redis 可用』时有效。** 如果 `rollback` 抛的是连接异常：

- **Redis 侧根本没执行** → `SREM` 的幂等没起作用（它没被调用）；
- **需要有人记得『这条预约的名额还没还』** → 这就是 `quota_released = false` 的作用。

**★ 最后回到那个必须说的边界**：**`SREM` 的幂等粒度是 `(batchId, userId)`，而业务需要的粒度是 `reservationId`——两者在『取消后重新预约』时会不等价**：

```
T1  R1：用户 U 抢到名额  → users 集合有 U
T2  R1 取消 → SREM 移除 U，INCR 归还名额
T3  R2：用户 U 重新抢到  → users 集合又有 U
T4  ★ 对 R1 的重复取消 → SREM 移除 U（成功！返回 1）→ INCR 归还名额
T5  但 U 现在占的是 R2 的名额 → ★★ 超发
```

**`SREM` 只看『集合里有没有 U』，它无法区分『这个 U 代表 R1 还是 R2』。**

**所以真正的保护在上层**——`ReservationServiceImpl.cancel` 里那段最长的注释讲的就是这件事，**只有 `TRANSITIONED` 才允许调用 `rollback`**。Q57 会详细讲。」

## Q48. 对账自己失败了怎么办？

**推荐回答**

「**三层防护：单条隔离、退避重排、锁一定会释放。但**——**我要先说结果：它有防护，但没有告警。**

**① 单条隔离：一条失败不会中断整轮。**

```java
for (ReservationRequest request : staleRequests) {
    try {
        // 处理这一条
    } catch (Exception e) {
        failed++;
        log.error("预约请求对账失败：requestId={}，batchId={}，userId={}", ..., e);
        recordReconcileFailureSafely(request);
    }
}
```

**`try/catch` 在 `for` 循环**内部，所以：

- 这一条抛异常 → `failed++` → **继续处理下一条**；
- **不会因为一条坏数据回滚整轮 200 条的处理。**

**类注释明确写了这个意图**：『对账纯方法。**每条请求独立处理；单条异常不会回滚或中断本轮其他请求。**』

**② 退避重排：写 `fail_reason` 并推进 `update_time`。**

`recordReconcileFailureSafely` → `recordFailReason(requestId, "RECONCILE_ATTEMPT_FAILED")`，而 `recordFailReason` **显式 `set(updateTime, now)`**。

**效果**：这条请求的 `update_time` 变成『现在』→ **它退出了陈旧窗口** → 至少 10 分钟后才会再被扫到 → 而且因为 `orderByAsc(updateTime)`，**它被排到了队尾**。

**★ 这就是这个项目实现『退避』的方式**——**不是靠一个失败计数器（表里根本没有计数器列），而是靠时间窗口的天然过滤。**

**③ 这个 `recordReconcileFailureSafely` 自己也套了一层 `try/catch`**：

```java
private void recordReconcileFailureSafely(ReservationRequest request) {
    try {
        reservationRequestService.recordFailReason(request.getRequestId(), RECONCILE_ATTEMPT_FAILED_REASON);
    } catch (Exception e) {
        log.error("预约请求对账失败原因记录失败：requestId={}", request.getRequestId(), e);
    }
}
```

**为什么？因为如果记录失败原因本身也失败**（比如数据库连不上），那么：

- **异常会冒泡到外层 `catch (Exception e)`**（因为 `recordReconcileFailureSafely` 是在 `catch` 块里被调用的）；
- 外层的 `catch` **已经执行完了 `failed++`**，但**异常没有再被捕获**——**它会直接抛出 `reconcile`，中断整轮**！

**所以这一层保护是必需的：它保证了『处理失败』这个动作本身不会再引发失败。**

**④ 锁一定会释放。** `finally { if (lock.isHeldByCurrentThread()) lock.unlock(); }`——**即使 `reconcile` 抛异常，锁也会被释放**（Q45 讲的看门狗问题是另一回事，那是『线程卡住不返回』，不是『抛异常』）。

**⑤ `fixedDelay` 保证下一轮会来。** `fixedDelayString` 的语义是『上一次执行**结束后**再等这么久』——所以**抛异常不会取消后续调度**（Spring 的调度器会记录异常并继续排下一次）。

**★★ 但这里有一个我要主动指出的真实缺口：**

```java
try {
    ReconcileSummaryDTO summary = reconcile(reconcileLimit);     // ← 如果这里抛异常
    ...
    int released = releasePendingQuotas(reconcileLimit);         // ← 这一行不会执行
    int noShows = markNoShows(reconcileLimit);                   // ← 这一行也不会执行
} finally { ... }
```

**`reconcile()` 抛异常会跳过后面两个任务。** 而 `reconcile` 里唯一能抛出异常的地方是**循环之外的代码**——主要是 `listStale` 这条查询。**如果数据库连不上，`listStale` 抛异常 → `reconcile` 抛出 → `releasePendingQuotas` 和 `markNoShows` 都被跳过。**

**这在『数据库连不上』时是合理的**（那两个任务也要用数据库），**但如果是 `listStale` 因为别的原因失败（比如 SQL 语法问题、或者表结构被改坏了），而 `releasePendingQuotas` 本来可以正常工作——那它就被误伤了。**

**★ 而且最重要的是：这三段任务没有独立的 try/catch，也没有独立的日志聚合。** 一轮下来只有一行 `log.info`，**如果它没打出来，你无法区分『没抢到锁』『任务抛异常了』还是『进程挂了』。**

**加固方向**：给三段任务各包一层 try/catch 并各打一行日志；引入 Micrometer 指标；对 `failed > 0` 告警。**当前都没做。**」

## Q49. 消费和对账会不会打架？

**推荐回答**

「**会，而且这是一个必须显式处理的竞态——代码里有一处专门为它写的检查。**

**竞态的场景是**：一条请求卡在 `UNKNOWN`（或者 `PUBLISHED` 但消费很慢），10 分钟后对账判定它失败、归还名额、置 `COMPENSATED`——**但就在这时，那条消息被消费了。**

**如果没有保护，后果是超卖**：

```
T1  对账：查 tb_reservation 无行 → 判定失败
T2  对账：rollback → Redis 名额 +1
T3  对账：CAS → 账本 COMPENSATED（终态）
T4  ★ 消费者：persist → 扣 MySQL 名额 + 插入预约行（成功了！）
T5  ★★ 结果：Redis 名额被还了（+1），但 MySQL 里有一条占用名额的预约
         → 下一个学生能抢到这个名额 → 超卖
```

**★ 消费者侧的防护**（`ReservationMessageConsumer:51-57`）：

```java
} else if (request.getStatus() == ReservationRequestStatus.COMPENSATED) {
    // 该请求已被对账判定终结并归还名额；若此时仍落库，就会形成「MySQL 有行 + Redis 名额已归还」的超发。
    log.warn("预约请求已被补偿，拒绝落库并确认消息：reservationId={}，userId={}", ...);
    channel.basicAck(deliveryTag, false);
    return;
}
```

**消费者在落库之前，先查一次账本；如果账本已经是 `COMPENSATED`，就拒绝落库并 `basicAck`。**

**注意它是 `basicAck` 而不是 `basicNack`**——**因为这不是错误，是『正确地拒绝了一个不该做的操作』**。消息被正常处理完了（处理结果是『不做』），所以确认掉。**如果 `basicNack`，消息会进 DLQ，然后运维会看到一个『为什么要重放一条已经补偿过的请求』的困惑场景**（实际上第 5 道重放检查会拦住它，见 Q36）。

**★ 但这个检查不是原子的——它只是一个『窄化窗口』的措施。**

**为什么？** 因为『查账本』和『`persist`』之间有时间差，而对账的『CAS 置 `COMPENSATED`』可以插在中间：

```
T1  消费者：查账本 → 状态 PRE_ACCEPTED（不是 COMPENSATED，通过检查）
T2                                                      对账：rollback → 名额 +1
T3                                                      对账：CAS → COMPENSATED
T4  消费者：persist → 扣名额 + 插入行      ★ 超卖窗口
```

**★ 那这个窗口靠什么堵住？靠 `uk_user_batch_active` 唯一索引吗？——不，它堵不住这个。**

唯一索引只能保证『一个用户在一个批次里只有一条有效预约』，**而这个场景里只有一条预约，索引帮不上忙**。

**堵住它的是 `persist` 里的条件更新**——但那也只是在**名额已经被扣光**时才会拒绝：

```java
.gt(ReservationBatch::getRemainingQuota, 0)
```

**如果 MySQL 的 `remaining_quota` 还有余额，这个更新会成功。** ——**所以这个窗口是真实存在的，而且没有被完全堵住。**

**★ 那为什么它没有被完全堵住还可以接受？两个理由：**

1. **窗口极窄**——从『消费者查账本』到『persist 扣名额』之间只隔了一次 Redisson 加锁和一次查询，**是毫秒级的**；而对账要在这个精确的瞬间执行 `rollback` + `CAS`，概率极低；
2. **窗口的成因是『对账判定得太早』**——而超时阈值是 **10 分钟**，意味着消息投递后 10 分钟都没被消费。**在这种前提下，消息随后恰好被消费的概率本身就极小**（消费者要么早就处理了，要么卡住了；如果卡住，`prefetch=1` 也意味着它没在处理别的消息）。

**★ 但我要诚实说**：**这是一个『概率低 + 有部分防护』的窗口，不是一个『被证明不可能』的窗口。**

**要彻底消除它**，需要把『检查账本状态』和『落库』放进**同一把锁**（消费者持有锁时，对账不能补偿同一条请求）——**当前对账没有按 `requestId` 加锁**（它只有全局的对账锁）。**或者**，让对账在补偿前**用 CAS 把账本置成一个『正在补偿』的中间态**，消费者看到这个态就拒绝落库。**当前项目没做这个改造。**

**我把它登记为『已识别、窄窗口、低概率、有部分防护的残留竞态』，而不是『已解决』。**」

**面试官继续追问：那反过来，消费者先成功、对账后扫描呢？**

**追问回答**

「**那个方向是安全的，而且是被主路径覆盖的。**

**如果消费者先成功落库**，那么对账扫到这条请求时：

```java
if (reservationMapper.selectById(request.getRequestId()) != null) {
    boolean updated = reservationRequestService.casStatus(
            request.getRequestId(), ReservationRequestStatus.CONFIRMED, NON_TERMINAL_STATUSES);
```

**`selectById` 命中 → 走『已落库』分支 → 推 `CONFIRMED`。** 

**★ 而且这个分支根本不会碰到 Redis** ——**没有 `rollback`，没有名额变动。** 它只是一次 CAS。

**所以两个方向的差别是**：

| 谁先 | 对账做什么 | 会不会动 Redis |
|---|---|---|
| **消费者先**（正常） | 推 `CONFIRMED` | ❌ **不动** |
| **对账先**（异常） | `rollback` + `COMPENSATED` | ✅ 动，**这正是竞态的根源** |

**★ 这个不对称也是我理解这个设计的一个关键**：**对账只有在『合理的等待时间之后仍然没有结果』时才会动 Redis**——**它在默认情况下是『什么都不做』的（只推状态）。** 这让它的危险面被压到了最小。

**而且如果一个 `UNKNOWN` 请求最终被判定为 `CONFIRMED`（消息其实到了）——用户的体验是完全正常的**：他拿到了 `503 待确认`，然后 10 分钟后预约出现在他的列表里。**没有一个学生因此被超发影响。**

**这正好印证了 Q33 里那个取舍的正确性**：**把 `UNKNOWN` 当作『待裁决』而不是『失败』，代价只是少数用户看到一次误导性的错误提示，换来的是完全避免超发。**」

## Q50. 那 `releasePendingQuotas` 和对账会不会重复归还？

**推荐回答**

「**不会，因为它们操作的记录集合是互斥的，而且每一层都有幂等。**

**先看它们各自扫描什么：**

| | 扫的表 | 条件 |
|---|---|---|
| `reconcile` | `tb_reservation_request` | `status IN (PRE_ACCEPTED, PUBLISHED, UNKNOWN)` and `update_time < now - 10min` |
| `releasePendingQuotas` | `tb_reservation` | `status = 'CANCELLED' AND quota_released = 0` |

**★ 两个集合的交集是空集——因为它们的 `status` 取值域完全不重叠**：

- 账本的状态是 `PRE_ACCEPTED/PUBLISHED/CONFIRMED/UNKNOWN/COMPENSATED`（**预约请求**的状态）；
- 预约的状态是 `RESERVED/CANCELLED/COMPLETED/NO_SHOW`（**预约单**的状态）。

**一张表记『请求走到哪一步了』，另一张表记『这个预约现在是死是活』。** 同一个 `reservationId` 在两张表里各有一条记录，**状态机完全不同**。

**★ 逻辑上也不重叠**：

- `reconcile` 补偿的是**『从来没成功落库』的请求** —— 那条请求对应的预约**根本不存在**；
- `releasePendingQuotas` 补偿的是**『曾经成功落库、后来被取消、但 Redis 归还失败』的预约**。

**一个补偿『没生出来的』，一个补偿『死掉的』。** 不可能有交叠。

**★ 而且即使逻辑上重叠了，两层幂等也会挡住：**

1. **Redis 侧**：`reservationRollback.lua` 的 `SREM` 返回 0 → 不 `INCR`（Q47）；
2. **MySQL 侧**：`releasePendingQuotas` 用 CAS 置 `quota_released = true`（`.eq(getQuotaReleased, false)`），**只有一个能成功**。

**★ 幂等设计的一个通用检验方法：对任何『补偿』操作，问三个问题：**

1. **重复执行会怎样？** → 安全（`SREM` / CAS / 条件 UPDATE）
2. **两个不同的补偿机制同时执行会怎样？** → 安全（上面的重叠分析 + 各自的幂等）
3. **补偿本身失败会怎样？** → 留下可被再次扫描的状态（第 7 层所有任务都满足）

**★ 这个项目里唯一『不满足第 3 条』的地方是 `ReservationServiceImpl.cancel` 里那个 `catch`**：

```java
try {
    int rollbackCode = reservationQuotaRollbackExecutor.rollback(...);
    reservationMapper.update(null, ... .set(getQuotaReleased, true));
} catch (RuntimeException e) {
    log.error("取消预约后 Redis 名额归还失败，等待定时补偿：reservationId={}，batchId={}，userId={}", ...);
}
```

**注意它 `catch` 之后什么都没做——只是打日志。** 那么『第 3 条』是怎么满足的？

**靠 `quota_released` 的默认值和 CAS 的顺序**：`rollback` 抛异常 → `set(quotaReleased, true)` **没被执行** → 字段留在 `false` → **`releasePendingQuotas` 下一轮会扫到它。**

**★ 所以这里的『什么都不做』恰恰是正确行为**——**因为『没做』这件事本身，就是留给补偿机制的信号。** 前提是 MySQL 端的**事务已经提交了**（`cancel` 里的 `RESERVED → CANCELLED` 跃迁在 `ReservationLifecycleServiceImpl.cancel` 的 `@Transactional` 里，**已经提交**），**所以 `quota_released = false` 这条记录是持久可见的。**

**★ 这正好回答了另一个问题：为什么 Redis 归还要放在数据库事务之外？**

**因为事务内的操作是原子的——如果 `rollback` 失败导致事务回滚，那么『预约已取消』这个事实也会被回滚掉，`releasePendingQuotas` 就永远扫不到这条记录了。** **把 Redis 归还放在事务外，让『取消』这个事实先落地，再去做那个可能失败的补偿动作——这才是正确的顺序。**

**这就是 『先提交事实，再做补偿』 模式。** **而它要求补偿动作是可重试的、幂等的、并且失败时留下明确的待补偿标记**——**这三条，`reservationRollback.lua` + `quota_released = false` 都满足了。**」

# 第八层 · MySQL、事务与并发安全

## Q51. 项目里有多少处条件更新（CAS）？为什么这么多？

**推荐回答**

「`src/main` 里有 **16 处 `LambdaUpdateWrapper`**。**为什么这么多？因为这些地方每一个都在防一个具体的竞态，而不是为了好看。**

**按用途分类：**

| 用途 | 典型条件 | 防什么 |
|---|---|---|
| **批次状态迁移** | `WHERE status = 'PUBLISHED'` | 两个管理员同时操作、重复操作 |
| **账本状态迁移** | `WHERE status IN (非终态)` | 消费与对账并发推进同一条请求 |
| **名额扣减** | `WHERE remaining_quota > 0` | 超卖 |
| **名额回补** | `WHERE remaining_quota < total_quota` | 回补超过上限 |
| **预约状态迁移** | `WHERE status = 'RESERVED'` | 重复取消、取消与核验并发 |
| **取消幂等标记** | `WHERE quota_released = false` | 重复归还名额 |
| **DB 行级锁** | `WHERE id = ? AND user_id = ?` | 越权（横向权限） |

**★ 有几个特别值得指出的：**

**① `WHERE remaining_quota < total_quota`**（`ReservationLifecycleServiceImpl:65`）——**这个条件的必要性很容易被忽略**：

```java
.eq(ReservationBatch::getId, reservation.getBatchId())
.lt(ReservationBatch::getRemainingQuota, batch.getTotalQuota())     // ★ 不能超过总量
.setSql("remaining_quota = remaining_quota + 1");
```

**如果没有这个条件，重复取消会让 `remaining_quota` 一直涨**，最终超过 `total_quota`——**名额计数就废了**（虽然 Redis 侧仍是权威，但展示和兜底判定会用 MySQL 的值）。

**★ 而这个条件失败时（`affectedRows == 0`），代码不是抛异常，而是打一条 warn**：

```java
if (quotaRestored == 0) {
    // MySQL 未回补名额（批次名额已达 totalQuota 上限，或批次行在事务内已变更），
    // 而 Redis 侧仍会 +1。方向保守（不会超卖），但会形成台账偏离，必须留痕以便对账排查。
    log.warn("取消预约后批次名额未回补：reservationId={}，batchId={}，affectedRows=0", ...);
}
```

**注释里的『方向保守（不会超卖）』是关键**：`remaining_quota` **偏小**是安全的（会让后续的条件更新更容易拒绝），**偏大**才会超卖。所以这里选择『宁可少加，不多加，并留痕』。

**② 越权用 `WHERE` 而不是 `if`**（`cancel` 和 `complete`）：

```java
.eq(Reservation::getId, reservationId)
.eq(Reservation::getUserId, userId)          // ★ 归属条件写在 SQL 里
.eq(Reservation::getStatus, ReservationStatus.RESERVED)
```

**把 `user_id` 放进 `WHERE`，而不是先查出来再用 Java 判断**——这样**越权请求的 `affectedRows` 天然是 0**，**不存在『判断通过但执行的是别人的数据』的窗口**。**这是一条重要的实践：权限判定尽可能下推到 SQL 条件里。**

**③ 所有 CAS 的返回值都被检查了。** MyBatis-Plus 的 `update` 返回 `int`（影响行数），代码里**每一处都判了 `== 1` / `== 0`**，而且**据此决定后续行为**——不是打个日志就过去。**这是 CAS 写法的必要组成部分：如果不管返回值，CAS 就退化成了普通的条件更新。**

**★ 我的总结**：**CAS 的价值不在于『一条 SQL 做了三件事』，而在于『把竞态判定交给数据库的行锁去做』。** 16 处听起来多，**但它们每一个都对应一个具体的不变式，而每一个不变式都需要在一次原子操作里被检查——不能用 Java 的 `if` 替代，因为 `if` 和它保护的写操作之间永远有窗口。**」

## Q52. 为什么 `@Transactional` 只用了 3 次？

**推荐回答**

「**因为只有 3 个地方同时满足『多步数据库写』和『没有外部调用』——其他所有地方加事务要么没用，要么有害。**

**三处分别是：**

| 位置 | 方法 | 事务里的操作 |
|---|---|---|
| `ReservationPersistenceServiceImpl:27` | `persist` | **扣批次名额 + 插入预约行** |
| `ReservationLifecycleServiceImpl:30` | `cancel` | 改预约状态 + 回补批次名额 |
| `ReservationLifecycleServiceImpl:77` | `complete` | 改预约状态（含一次查询） |

**★ 它们的共同特征：**

1. **至少两步数据库写**（或者『先读后写』需要一致性）——`persist` 的『扣名额 + 插行』如果不同事务，**扣了名额但插行失败就会泄漏名额**；
2. **不包含任何网络调用**——没有 Redis、没有 MQ、没有 HTTP。**`cancel` 里看起来有 Redis（名额归还），但那一步在 `ReservationServiceImpl.cancel` 里，在事务之外**（Q50 讲了为什么必须如此）；
3. **执行时间可控**——三处都是 1–3 条 SQL，**毫秒级**。

**★ 反过来，看看哪些地方『看起来该加事务但没加』：**

| 方法 | 里面有什么 | 为什么不加 |
|---|---|---|
| `ReservationServiceImpl.submit` | 写账本 + **Redis Lua** + **阻塞等 MQ confirm（最多 5 秒）** | 事务跨网络调用，连接池会被打满；回滚会制造『Redis 已扣、账本被回滚』的泄漏（Q39） |
| `ReservationServiceImpl.cancel` | 调事务方法 + **Redis rollback** | **Redis 无法参与数据库事务**，且『先提交事实再补偿』要求 Redis 归还在事务外（Q50） |
| `ReservationServiceImpl.publish` | **Redis 建名额键** + 批次状态 CAS | 同 submit——Redis 和 MySQL 无法在同一个事务里 |
| `ReservationReconcileServiceImpl.reconcile` | 循环里 200 条记录，每条都有自己的 CAS | **长事务**——200 条记录的事务会持有大量行锁、产生大 undo log、失败后全部回滚（而这里需要的是『每条独立』，见 Q48） |
| `ReservationDlqServiceImpl.replay` | CAS 递增重试次数 + **MQ 投递** | 同 submit——MQ 在事务里 |

**★ 所以判断标准可以总结成三条：**

1. **只做数据库操作** → 可以加事务；
2. **有外部调用（Redis/MQ/HTTP）** → 不要加事务（无法回滚，且长事务会耗尽连接池）；
3. **要处理一批独立记录、每条独立成败** → 不要加事务（应该每条自己的小事务，或者靠 CAS 保证单条原子性）。

**★ 还有一个我主动指出的边界**：**`persist` 上有 `@Transactional`，但它是在消费者线程里被调用的，而它的调用方 `persistWithLock` 没有事务。** 这是对的——**事务边界应该尽可能小，只包住真正需要原子的部分。**

**而 `ReservationLifecycleServiceImpl.cancel` 上有事务，被 `ReservationServiceImpl.cancel` 调用（无事务）**——**这也是对的，而且是有意的**：**事务只覆盖『RESERVED → CANCELLED + 名额 +1』这个数据库内的一致性单元；Redis 归还、日志、异常处理都在事务外。**

**★ 这种『事务方法作为一个可复用的一致性单元被更大流程调用』的结构，是这个项目里划分得最好的一处。**」

## Q53. 条件更新怎么防超卖？它能挡住什么、挡不住什么？

**推荐回答**

「**它挡的是『数据库里名额被扣成负数』，挡不住的是『Redis 和数据库不一致』——因为它在整条防线里只负责最后一层。**

**代码**（`ReservationPersistenceServiceImpl:49-56`）：

```java
boolean quotaDecremented = reservationBatchService.update(
        new LambdaUpdateWrapper<ReservationBatch>()
                .eq(ReservationBatch::getId, reservation.getBatchId())
                .gt(ReservationBatch::getRemainingQuota, 0)                // ★ 关键条件
                .setSql("remaining_quota = remaining_quota - 1"));
if (!quotaDecremented) {
    return ReservationPersistResult.QUOTA_CONFLICT;
}
```

**展开的 SQL**：

```sql
UPDATE tb_reservation_batch
SET remaining_quota = remaining_quota - 1
WHERE id = ? AND remaining_quota > 0
```

**★ 它能挡住什么：**

| 场景 | 挡得住吗 | 为什么 |
|---|---|---|
| 两个消费者同时扣同一个批次 | ✅ | InnoDB 行锁 + `WHERE` 在锁内重新求值 |
| 已经扣到 0 了还来扣 | ✅ | `affectedRows == 0` → `QUOTA_CONFLICT` |
| **Redis 计数算错了，多放进来一批请求** | ✅ | **这是它的核心价值——它是独立于 Redis 的一层** |

**★ 它挡不住什么：**

| 场景 | 为什么挡不住 |
|---|---|
| **Redis 名额被归还了（rollback 误执行），但 MySQL 名额还是占用的** | `remaining_quota` 还有余额，**条件成立，更新成功** → 这条预约落库了，但 Redis 侧多出一个名额 → **下一个人能抢到 → 超发** |
| **Redis 名额被多扣了（比如重复扣），但 MySQL 还有余额** | 同上——MySQL 不知道 Redis 那边发生了什么 |
| **消息重复投递导致重复扣减** | ⚠️ **这个靠的是前面的幂等查询，不是这一层**（见下） |

**★ 最后一行很重要，我要说清楚**：`persist` 里的**幂等判断在条件更新之前**（`existingCount > 0` → 返回 `DUPLICATE`），**所以正常情况下重复消息不会走到扣减**。

**但幂等判断是『先查后写』，有 TOCTOU 窗口**——两个消费者同时查、都没查到、都往下走。**这时挡住重复的是**：

1. **Redisson 用户锁**（`persistWithLock`）——同一用户的消息被串行化；
2. **`uk_user_batch_active` 唯一索引**——**最终的兜底**。

**★ 所以四层防线的分工是：**

| 层 | 位置 | 挡住什么 |
|---|---|---|
| **① Lua** | Redis | **绝大多数并发**——它是唯一在准入时刻生效的 |
| **② 用户锁** | Redisson | 同一用户的消息串行 |
| **③ 条件更新** | MySQL | **Redis 计数与实际不符时的超额扣减** |
| **④ 唯一索引** | MySQL | **同一用户在同一批次的重复占用** |

**★ 四层里只有 ③④ 是『不依赖任何易失存储』的**——**这是这个设计最重要的性质**：即使 Redis 完全算错、锁完全失效，**MySQL 也不会产生负数名额、不会产生一个用户的两条有效预约**。

**★ 但要注意 ③④ 保护的范围是有上限的**：它们保证『**数据库里的账是对的**』，**不保证『Redis 和数据库一致』**。**而后者的收敛靠的是对账任务（第七层）和每一次操作时的补偿逻辑（Q46）。**

**一句话总结这个分层**：**Redis 保证『不进太多人』，MySQL 保证『进来的人账是对的不重复的』，对账保证『两本账最终对得上』。**」

## Q54. 唯一索引是怎么设计的？`active_flag` 是什么？

**推荐回答**

「**这是一个用 MySQL 特性模拟『部分唯一索引』（partial unique index）的技巧——而这个需求的本质是『允许重复的历史，但禁止并存的活跃记录』。**

**需求**：一个用户在一个批次里**同时只能有一个有效预约**，但**可以取消后重新预约**（甚至取消–预约–取消多次）。所以：

- ❌ 简单唯一索引 `(user_id, batch_id)` **不行**——取消之后就不能再预约了；
- ✅ 需要的是：**只在 `status != 'CANCELLED'` 的行上唯一**。

**PostgreSQL 直接支持**：`CREATE UNIQUE INDEX ... ON t (user_id, batch_id) WHERE status <> 'CANCELLED'`。**MySQL 不支持部分索引。**

**MySQL 的解法是用『NULL 在唯一索引中不参与比较』这个特性：**

```sql
ALTER TABLE tb_reservation
  ADD COLUMN active_flag TINYINT
    GENERATED ALWAYS AS (CASE WHEN status = 'CANCELLED' THEN NULL ELSE 1 END) STORED,
  ADD UNIQUE INDEX uk_user_batch_active (user_id, batch_id, active_flag);
```

**原理**：

| 行 | `status` | `active_flag` | 唯一索引里的三元组 |
|---|---|---|---|
| 第 1 条预约 | `RESERVED` | **1** | `(U, B, 1)` |
| 第 2 条预约（取消后重订） | `RESERVED` | **1** | `(U, B, 1)` ← **冲突，被拒** |
| 第 1 条已取消 | `CANCELLED` | **NULL** | `(U, B, NULL)` |
| 第 2 条 | `RESERVED` | **1** | `(U, B, 1)` ← **不冲突**（因为另一条是 NULL） |

**★ 关键在于 SQL 标准里 `NULL` 不等于 `NULL`**——所以**唯一索引允许任意多个 `(U, B, NULL)` 行**，但只允许**一个** `(U, B, 1)` 行。**这正好就是『部分唯一索引』的语义。**

**★ 而这个字段是 `GENERATED ALWAYS AS ... STORED`——生成列，不能直接被写。**

这就是为什么**全仓 Java 代码里对 `active_flag` 的引用是零**：**它不是业务字段，是索引的载体。**

**★ 它也修正了 README 里的一处错误描述。** README §9③ 说 `phase8`/`phase9` 用 `UPDATE ... SET active_flag = 0 WHERE id = ? AND active_flag = 1` 来检测并发修改、推导 `QUOTA_CONFLICT`。

**这是不可能的**——**生成列不能被 `SET`**（MySQL 会报 `ERROR 3105: The value specified for generated column 'active_flag' in table 'tb_reservation' is not allowed`）。

**而 `QUOTA_CONFLICT` 的真实来源是 `ReservationPersistenceServiceImpl:55` 那条 `remaining_quota > 0` 的条件更新**——**和 `active_flag` 没有任何关系。** 我在文档里把它登记为最重要的一处文档与源码不一致。」

**面试官继续追问：那这个唯一索引在哪一层拦截？**

**追问回答**

「**在 `insert` 那一瞬间——也就是 `persist` 的最后一步。**

```java
if (reservationMapper.insert(reservation) != 1) {
    throw new IllegalStateException("预约记录持久化失败");
}
```

**如果唯一索引冲突，MyBatis 会抛出 `DuplicateKeyException`**，被 `ReservationMessageConsumer` 捕获：

```java
} catch (DuplicateKeyException e) {
    // 同一用户的消息已被 persistWithLock 串行化，此处可达的冲突是 reservationId 主键冲突，不是 uk_user_batch。
    // 若 ACK，这条未落库的消息会静默消失且 DLQ 无痕迹；必须 NACK 交给死信治理。
    log.error("预约记录主键冲突，消息进入死信队列：...", e);
    channel.basicNack(deliveryTag, false, false);
}
```

**★ 注意这里注释的措辞**：它说『此处可达的冲突是 `reservationId` **主键冲突**，不是 `uk_user_batch`』。

**为什么这么判断？** 因为：

- **同一个用户的消息被 `persistWithLock` 的 Redisson 锁串行化了**——所以不可能有两条同用户的消息同时走到 `insert`；
- 因此在 `insert` 上能撞的，**只可能是两台不同用户的机器（不存在）或者 `reservationId` 主键重复**（`RedisIdWorker` 生成重复 ID、或者 DLQ 重放了一条已经落库的消息）。

**★ 但这里有一个重要的行为选择**：**无论撞的是哪个约束，代码都走 `basicNack` 进 DLQ。**

**为什么不 ACK？** 注释给了理由：**如果 ACK，这条未落库的消息会静默消失，而 DLQ 上不留任何痕迹。**

**★ 这个判断是正确的**，因为：

- 如果是**主键冲突**（异常情况，比如 ID 生成器出错）→ **必须进 DLQ 让运维看到**；
- 如果是 **`uk_user_batch_active` 冲突**（正常情况下其实不该到达）→ **也要进 DLQ**，因为**这意味着它的幂等查询没能拦住，说明有别的问题**。

**★ 所以唯一索引的作用不只是『拒绝』，还包括『让拒绝变得可见』**——**消息进 DLQ、写台账、可查询、可重放（虽然重放也会再次被拒，但至少留下了痕迹）。**

**这是一个重要的可观测性设计**：**一个静默的 ACK 会让『系统出了异常』这件事完全不可见。**」

## Q55. `RedisIdWorker` 生成的是什么 ID？是雪花算法吗？

**推荐回答**

「**不是雪花算法。它是一个自定义的『时间戳左移 + Redis 日增量』结构，我把它称为『趋势递增 ID』。**

**完整实现只有 15 行**：

```java
private static final long BEGIN_TIMESTAMP = 1640995200L;   // 2022-01-01 00:00:00 UTC
private static final int COUNT_BITS = 32;

public long nextId(String keyPrefix) {
    LocalDateTime now = LocalDateTime.now();
    long nowSecond = now.toEpochSecond(ZoneOffset.UTC);
    long timestamp = nowSecond - BEGIN_TIMESTAMP;              // ① 相对秒数

    String date = now.format(DateTimeFormatter.ofPattern("yyyy:MM:dd"));
    long count = stringRedisTemplate.opsForValue().increment("icr:" + keyPrefix + ":" + date);  // ② 日增量

    return timestamp << COUNT_BITS | count;                    // ③ 拼接
}
```

**ID 的位结构**：

```
 63                    32 31                     0
 ┌───────────────────────┬────────────────────────┐
 │  相对秒数（31 位有效）  │  当日序号（32 位）      │
 └───────────────────────┴────────────────────────┘
```

**★ 和雪花算法的对比：**

| | 雪花算法 | `RedisIdWorker` |
|---|---|---|
| 高位 | 41 位毫秒时间戳 | **31 位秒时间戳**（相对 2022-01-01） |
| 中位 | 10 位机器 ID | **无** |
| 低位 | 12 位毫秒内序号 | **32 位当日序号** |
| 序列来源 | **本机内存计数** | **Redis `INCR`（跨实例共享）** |
| 依赖时钟 | **强依赖**，回拨会出错 | **弱依赖**——时间戳变了 ID 仍然唯一（因为序号是独立的 32 位） |
| 每秒上限 | 4096 × 1000 | 2³² 每天（约 42.9 亿） |
| 跨实例唯一 | **靠机器 ID 配置** | **靠 Redis 的原子 `INCR`** |

**★ 三个关键差异值得说：**

**① 序列号是『按天』的，不是『按秒』的。** key 是 `icr:reservation:2026:10:07`——**每天一个计数器，从 1 开始**。所以**一天最多 2³² ≈ 42.9 亿个 ID**，而且**低位在一天之内是单调递增的**。

**② 没有机器 ID，靠 Redis 保证跨实例唯一。** **这是它相对雪花算法最大的优势——不需要给每个实例分配 workerId**（那需要配置管理或 ZooKeeper）。**代价是每次生成 ID 都要访问 Redis。**

**③ 秒级时间戳 + 32 位序号，意味着同一个批次/同一秒内生成的 ID 完全靠序号区分。** 只要 Redis 的 `INCR` 不重复，ID 就不会重复。

**★ 为什么叫『趋势递增』而不是『严格递增』？**

因为低位是**当天**的序号：**跨天的时候，低位会从 2³² 附近跳回 1，但高位（秒数）增加了**。所以：

- **同一天内**：ID **严格递增**（高位不变，低位递增）；
- **跨天时**：ID **仍然递增**（高位增加了 86400，低位回落到 1——`86400 << 32` 远大于任何低位的差值）。

**所以整个 ID 序列是单调递增的。** 这对 MySQL 的 B+ 树很友好（**顺序插入不会造成页分裂**），这也是它相比 UUID 的核心优势——**UUID 作为主键会让 InnoDB 的聚簇索引随机插入，性能差很多。**」

**面试官继续追问：那这个 ID 生成器有什么问题？**

**追问回答**

「**有四个，前两个是我认为比较严重的。**

**① 🔴 Redis 不可用时完全无法生成 ID。** `nextId` 里那个 `increment` 会直接抛异常，而它**没有任何降级路径**（没有本地兜底、没有数据库序列兜底）。

**而它在 `submit` 的调用位置很关键**：

```java
reservationId = redisIdWorker.nextId("reservation");
createPreAccepted(reservationId, ...);
```

**它在前置校验之后、写账本之前。** 所以 Redis 挂了 → **这里抛异常** → 用户拿到 500（**注意：不是 `ServiceUnavailableException`，因为这个异常没有被 `try/catch` 包住**，它会一路冒泡到 `WebExceptionAdvice` 的 `RuntimeException` 分支 → **500 + `"服务器异常"`**）。

**这个错误信息对用户毫无帮助**，而且**掩盖了『Redis 挂了』这个真实原因**。

**② 🟠 一次预约要打两次 Redis，而且第一次是『为了拿 ID』。** 顺序是：`INCR icr:...`（拿 ID）→ 写 MySQL → `Lua`（抢名额）。**Redis 的两次往返里，只有第二次是业务必需的，第一次是 ID 生成的开销。**

**③ 🟠 `BEGIN_TIMESTAMP` 是硬编码的 2022-01-01。** 时间戳是『相对秒数』，**所以这个 ID 只用 31 位表示秒**。**2³¹ 秒 ≈ 68 年**，所以这个 ID 生成器**理论上可以用到 2090 年**——**当前不是问题，但它是一个隐含的、没有被文档记录的寿命上限。** 如果哪天要延长，改 `BEGIN_TIMESTAMP` **会让新 ID 和旧 ID 的排序关系彻底混乱**。

**④ 🟡 32 位序号不检查溢出。** `timestamp << 32 | count`——**如果某天 `count` 超过 2³²，低位会溢出并污染高位**（用 `|` 而不是 `+`，所以溢出位会被静默丢弃）。**每天 42.9 亿次预约**——**这个项目几辈子都到不了**，但**代码里没有断言**。

**★ 而我还要说一个『不是问题但容易被误解』的点**：`count` 从 Redis 取，**如果 `icr:reservation:2026:10:07` 这个 key 被删了（或者 Redis 重启且没有持久化），计数器会从 1 重新开始**。

**这会导致 ID 重复吗？** ——**取决于时间戳**：

- **如果秒数已经变化**（几乎必然，因为要等到 key 被删/重启之后才有新请求）→ **高位不同 → ID 仍然唯一**；
- **只有在『同一秒内 key 被删 + 有新请求』时才会重复**——**这需要 Redis 在这一秒内恰好丢失这个 key 并接受新的 `INCR`，概率极低但不为零。**

**★ 而这就是为什么 §35 里 `persist` 的幂等判断那么小心**——**它必须区分『同 id 同归属』（幂等重复）和『同 id 不同归属』（ID 冲突）**。**后者如果存在，说明 ID 生成器出了问题，必须让它走到 `insert` 撞主键约束、抛异常、进 DLQ——而不是被当成幂等而静默 ACK。**

**所以这两个设计是配套的：ID 生成器有一个极小概率的重复风险，而幂等判断被刻意写成『不容忍这个风险』。** 这是一个**防御性设计的例子**——**在可能出现问题的地方，选择『暴露问题』而不是『掩盖问题』。**」

## Q56. 取消预约的幂等是怎么保证的？为什么 Redis 归还必须在特定条件下才执行？

**推荐回答**

「**这是这个项目里注释最长、推理最完整的一段代码，也是我读源码时印象最深的一处。**

**先看结构**（`ReservationServiceImpl.cancel`）：

```java
ReservationCancelOutcome outcome = reservationLifecycleService.cancel(
        reservationId, user.getId(), LocalDateTime.now());

if (outcome == NOT_FOUND)          throw new ForbiddenException("无权取消该预约");
if (outcome == NOT_CANCELLABLE)    throw new BadRequestException("当前状态不可取消");
if (outcome != TRANSITIONED) {
    // ★★ ALREADY_CANCELLED：本次调用没有发生状态跃迁，幂等返回
    return;                                          // ← 关键：直接返回，什么都不做
}

// ★ 只有真正完成了 RESERVED → CANCELLED 跃迁，才允许归还名额
int rollbackCode = reservationQuotaRollbackExecutor.rollback(reservation.getBatchId(), user.getId());
reservationMapper.update(null, ... .eq(getQuotaReleased, false).set(getQuotaReleased, true));
```

**那段注释的完整原文**（它是理解这个设计的钥匙）：

> `ALREADY_CANCELLED`：本次调用没有发生 `RESERVED→CANCELLED` 的状态跃迁，幂等返回。
> **绝不能在此路径触碰 Redis 或 `quota_released`**：`rollback` 的 Lua 虽然自身幂等，但**用户可能在取消 R1 之后重新预约得到 R2**，此时对 R1 的重复取消会 `SREM` 掉 R2 在 Redis 中的占位标记 —— Redis 多出名额而 MySQL 仍占用 R2，**既超卖又重新打开名额泄漏**（再次抢名额会在落库时被唯一键拒成 `DUPLICATE` 并静默 ACK）。
> **只有本事务真正完成跃迁（`TRANSITIONED`）才允许归还名额。**

**★ 逐层拆解这段话的推理：**

**① 数据库侧的幂等是天然的。** `ReservationLifecycleServiceImpl.cancel` 里的 CAS 是：

```java
.eq(Reservation::getId, reservationId)
.eq(Reservation::getUserId, userId)
.eq(Reservation::getStatus, ReservationStatus.RESERVED)     // ★ 只需要 RESERVED
.set(Reservation::getStatus, ReservationStatus.CANCELLED)
```

**第二次取消时，状态已经是 `CANCELLED`，`affectedRows == 0`** → 走到 `selectById` 复核 → 返回 `ALREADY_CANCELLED`。**数据库侧只跃迁一次。**

**② 但 Redis 侧如果也执行一次，就出事了。** 因为 `reservationRollback.lua` 的幂等粒度是 **`(batchId, userId)`**，而**这个粒度在『取消后重新预约』时会失效**：

```
T1  R1：用户 U 抢到名额       → Redis users 集合 = {U}
T2  R1 取消（第 1 次）        → SREM U → 集合 = {}，INCR → 名额 +1     ✅ 正确
T3  R2：U 重新抢到名额        → SADD U → 集合 = {U}                    ✅ 正确
T4  ★ 对 R1 的重复取消请求    → 数据库 CAS 失败（返回 ALREADY_CANCELLED）
      如果此时执行 rollback  → SREM U 成功（返回 1！）→ INCR → 名额 +1  ❌ 灾难
```

**T4 的两种错法（注释里都点了）：**

- **超卖**：Redis 名额 +1，但 MySQL 里 R2 还占着这个名额 → **下一个学生能抢到 → 超卖**；
- **重新打开名额泄漏**：下一个学生抢到 Redis 名额后，落库时被 **`uk_user_batch_active`** 拒绝（因为 U 已经有 R2 了——**注意这里拒绝的是另一个用户，不是 U**）……

**等等，这里的第二点注释说得更精确**：『再次抢名额会在落库时被唯一键拒成 `DUPLICATE` 并静默 ACK』。**它说的是：那个多出来的名义名额，会被某个用户抢到（Lua 通过），然后在落库时因为某种原因被拒** ——**结果是 Redis 名额少了 1（被 Lua 扣了），但 MySQL 里没有对应的预约行 → 名额永久泄漏**。

**★ 所以 T4 一次错误的 `rollback` 同时产生了两个方向的偏差**：Redis 多了一个（归还了不该归还的），然后这个多出来的名额被某个用户消耗掉但没能落库（Redis 少了 1）——**最终是 MySQL 和 Redis 两本账都乱了。**

**③ 所以『只有 `TRANSITIONED` 才归还』是必需的。**

**`TRANSITIONED` 的含义是『本次调用真的把这条预约从 `RESERVED` 改成了 `CANCELLED`』**——**它是一次性的、不可重复的事件。** **把 Redis 归还挂在这个事件上，就保证了『归还』和『取消』一一对应。**

**★ 这是这个项目里『幂等粒度不匹配』问题的最好的解法：**

**问题**：Lua 的幂等粒度（`userId`）比业务需要的粒度（`reservationId`）**更粗**，所以在特定场景下会失效。

**解法**：**不试图去修补 Lua 的幂等粒度**（那需要在 Redis 里存 `reservationId`，还得处理过期），**而是在上层用一个『真正一次性的事件』来决定要不要调用它。**

**★ 我总结的规则**：**当底层操作的幂等粒度不够细时，用一层『触发条件本身是一次性的』来补偿它。** **CAS 的 `affectedRows == 1` 就是那个『一次性事件』——它是分布式系统里最可靠的『只发生一次』信号。**」

**面试官继续追问：那 `complete`（核验）也是同样的模式吗？**

**追问回答**

「**是，而且 `complete` 的幂等语义更值得玩味——它把『重复核验』当成成功返回。**

```java
int transitioned = reservationMapper.update(null, new LambdaUpdateWrapper<Reservation>()
        .eq(Reservation::getId, reservationId)
        .eq(Reservation::getStatus, ReservationStatus.RESERVED)
        .set(Reservation::getStatus, ReservationStatus.COMPLETED));
if (transitioned == 1) {
    return true;                       // 本次真的完成了核验
}

Reservation current = reservationMapper.selectById(reservationId);
if (current != null && current.getStatus() == ReservationStatus.COMPLETED) {
    return false;                      // ★ 已经是 COMPLETED，返回 false（不报错）
}
throw new BadRequestException("当前状态不可核验");
```

**三分支：**

| `affectedRows` | 复查结果 | 返回 | 语义 |
|---|---|---|---|
| 1 | — | `true` | **本次完成了核验** |
| 0 | 已是 `COMPLETED` | **`false`** | **之前已经核验过了**——幂等，不报错 |
| 0 | 其他状态（`CANCELLED` / `NO_SHOW`） | **抛 `BadRequestException`** | **真的不能在当前状态核验** |

**★ 关键区别是『幂等重复』和『非法状态』被分开了**：

- **重复核验**（同一条预约被扫了两次码）→ **返回 `false`，不报错**——因为**用户的行为是合理的，结果也是他要的**；
- **核验一条已取消的预约** → **抛异常**——因为**这是真正的业务冲突，必须告诉用户**。

**★ 而在方法入口还有一个提前判断**：

```java
if (reservation.getStatus() == ReservationStatus.COMPLETED) {
    return false;                      // 快速路径：已经核验过，直接返回
}
if (reservation.getStatus() != ReservationStatus.RESERVED) {
    throw new BadRequestException("当前状态不可核验");
}
```

**这是『快速失败』**——省掉一次 CAS 往返。**但它不是必需的**（后面的 CAS + 复查已经覆盖了），**它只是一个优化**。**这也说明这个方法的正确性不依赖前置检查**——**即使前置检查被删掉，CAS + 复查仍然保证正确。** 这是**纵深防御**的一个好例子。

**★ 顺带一个业务规则**：`complete` 要求 `now >= batch.getStartTime()`——**『预约尚未开始，无法核验』**。这是**正确的时间语义**：你不可能在时段开始之前就用完设备了。**而 `cancel` 要求 `now <= batch.getEndTime()`**——**两个方法各自校验了自己关心的那一段时间的边界，而且都是『在服务端用 `LocalDateTime.now()` 判定』，不接受客户端传时间。**」

## Q57. `tb_reservation` 的状态和账本状态是怎么配合的？

**推荐回答**

「**两张表、两套状态机，通过 `reservationId` 关联，但各自独立演进。**

**预约单状态（`tb_reservation.status`）**：

```
RESERVED ──取消──► CANCELLED
   │
   ├──核验──► COMPLETED
   │
   └──批次结束未核验──► NO_SHOW
```

**占用名额的状态是哪些？** 由 `ReservationStatus.occupyingStatuses()` 定义——**`RESERVED` 和 `COMPLETED`**：

- `RESERVED`：占了名额，**显然**；
- `COMPLETED`：核验过了——**注意它仍然占用名额**（因为设备确实被用了）；
- `CANCELLED`：**不占用**——名额已归还；
- `NO_SHOW`：**不占用**——但是**也不归还 Redis 名额**（见下）。

**★ 为什么 `COMPLETED` 算占用？** 因为 `occupyingStatuses()` 被用在两个地方：

1. **`persist` 的幂等查询**——`existingCount = selectCount(user_id + batch_id + status IN occupyingStatuses())`。**如果一个用户已经有一条 `COMPLETED` 的预约，他还能再预约这个批次吗？** ——**不能**。因为**这个 `(user, batch)` 组合已经被他占用过了**。这是业务上的正确判断；
2. **`uk_user_batch_active` 唯一索引**——`active_flag` 只在 `CANCELLED` 时为 `NULL`。**所以 `RESERVED`、`COMPLETED`、`NO_SHOW` 都会占用唯一键槽位。**

**★★ 这里有一个必须指出的细节：`NO_SHOW` 也占用唯一键槽位，而且不归还名额。**

**`markNoShows` 只改状态、不碰 Redis**（`ReservationReconcileServiceImpl` 的注释：『**批次已结束且仍未核验的预约置为爽约。爽约不归还任何名额。**』）。

**理由**：**设备在时段内确实被『占用』了**（即使人没来），**名额不该因为爽约而释放**——因为**时段本身已经过去了**。如果归还名额，Redis 里那个批次的名额会恢复，但**那个批次的预约窗口早就关了**（`bookingEndTime <= startTime <= endTime`，而爽约判定要求 `endTime < now`）——**名额回来了也没人能抢，只会造成 Redis 和 MySQL 的永久偏离。**

**所以『不归还』是对的。** 但这带来一个可观测的后果：**爽约的预约会永远占着唯一键槽位**——**这个用户在批次结束前不能再预约这个批次。** **由于批次已经结束了，这也没有实际影响。**

**★ 而 `cancelBatch`（管理员取消批次）是一个我发现的『半成品』**：

`ReservationBatchServiceImpl.cancel` 做的是：

1. 批次状态 → `CANCELLED`（CAS）；
2. **`delete(Arrays.asList(quotaKey, usersKey))`** ——删掉 Redis 的名额键和用户集合。

**但它没有处理已经存在的 `RESERVED` 预约。** 这些预约：

- **仍然占着 `uk_user_batch_active` 的唯一键槽位**（`status` 还是 `RESERVED`，`active_flag` 还是 1）；
- **`markNoShows` 不会把它们置为爽约**——因为 `markNoShows` 的 SQL 里有一条 **`AND b.status <> 'CANCELLED'`**，**明确排除了被取消的批次**；
- **`cancel`（用户取消）仍然可以调用**（它只检查 `now <= batch.endTime`，**不看批次状态**），但**名额键已经不存在了** → `reservationRollback.lua` 返回 **2**（『用户确实占用名额但名额键已不存在』）。

**所以 `cancelBatch` 之后，那些 `RESERVED` 预约进入了一个『悬空』状态**：

- 状态永远停在 `RESERVED`（既不会变 `NO_SHOW`，用户如果不主动取消也不会变 `CANCELLED`）；
- 用户主动取消时 Redis 归还返回 2（**不归还**，这是对的，因为键都没了）；
- MySQL 侧 `remaining_quota` 会 +1（因为 `cancel` 的批次更新不检查批次状态）。

**★ 我需要明确说**：**这不一定是个 bug，但它是一个『未被定义的语义』**。**管理员取消批次之后，那些已经预约成功的学生应该怎么办？** ——**系统没有给出答案**：没有自动取消、没有通知、没有归还。

**README 里没有提到这个场景。** 我在文档里把它登记为**『`cancelBatch` 是一个未完成的语义：它阻止了新的预约，但没有定义已有预约的归宿』**。**这是一个真实的设计缺口，而不是文档遗漏。**」

## Q58. 你怎么保证你的修复是真的有效的？

**推荐回答**

「**靠变体实验：把修复改回坏状态，确认对应用例变红。只有变红了，才说明这个用例有判别力。**

**为什么不能只看『测试通过』？** 因为**一个测试通过可能有很多原因，其中最常见的是『它根本没在测东西』**：

- 断言写错了（比如断言了一个永远为真的条件）；
- Mock 没生效（**桩静默失效**，代码走的是默认路径）；
- 测试数据和代码路径不匹配（比如永远走不到那个 `if` 分支）；
- **测试和被测代码共享了同一个错误假设**（两边都错，所以『一致』）。

**这些情况下『测试通过』传达的是虚假的安全感。**

**★ 所以判据是『这个测试能不能失败』，而不是『这个测试现在是不是绿的』。**

**举两个这个项目里的实例：**

**① `ReservationRequestStateTest.shouldRejectEmptyExpectedStatuses`** ——钉住 CAS 的空数组守卫。

**变体实验**：删掉 `ReservationRequestServiceImpl` 里那两个 `if (expectedStatuses == null || expectedStatuses.length == 0) throw ...` → **用例必须变红**。

**为什么这个守卫值得测试**：因为**它的失效是静默的**。传入空数组会生成 `IN ()`——**这可能是 SQL 语法错误，也可能（取决于 MyBatis-Plus 的版本和实现）条件被忽略，`IN` 子句整个消失，CAS 退化成无条件更新**。**那就变成了它本来要防的 `updateById` 语义，而且没有任何报错。**

**② `ReservationReconcileTest.shouldAdvanceUpdateTimeWhenSameReconcileFailureRepeats`** ——钉住『重复写同一个 `fail_reason` 时 `ON UPDATE` 不触发』这个 MySQL 行为。

**变体实验**：把 `recordFailReason` 里的 `.set(ReservationRequest::getUpdateTime, LocalDateTime.now())` 删掉 → 用例必须变红。

**为什么这个测试特别有价值**：**因为如果不写它，你几乎不可能发现这个 bug**——它**没有异常、没有错误日志**，只是在数据积累到 200 条持续失败的记录之后，**对账任务静默停摆**。**而这个测试把『依赖 MySQL 的隐式行为』这件事变成了一个显式的断言。**

**★ 而这个项目做的最值得学习的一件事，是把『测不出来』的情况明确登记下来，而不是假装测过了。**

`MIGRATION_STATUS.md:836-837` 记载 `LOGIN_USER_TTL` 从 36000 改成 30 时的一段话（原文）：

> **诚实登记：全仓测试无任何断言涉及登录 token TTL，本项无变体强度证据。**

**为什么测不出来？** 因为一个有判别力的测试要么：

- **断言常量值本身**（`assertEquals(30L, LOGIN_USER_TTL)`）——**这是『为过而过』**，它在你把代码改坏时**不会变红**（改坏了常量，断言也跟着期望新值，除非你手动改断言——但那就不是在测行为了）；
- **走完整 HTTP 流程等 30 分钟**——不可行。

**所以这个改动是没有变体证据的，而他们把它写下来了。** ——**这比一个虚假的绿灯有价值得多。**

## Q59. 这个项目有哪些已知的边界和不足？

**推荐回答**

「**我按严重程度排，而且区分『有兜底的』和『没兜底的』。**

**🔴 没有兜底的（会造成数据错误或功能不可用）**

| 边界 | 后果 | 原因 |
|---|---|---|
| **名额键丢失后无法重建** | 批次仍然 `PUBLISHED`，但**所有人都预约不了**（Lua 返回 `BATCH_NOT_OPEN`），而页面显示还有名额 | 所有写这个键的路径都要求『不存在时创建』（`setIfAbsent` 且批次必须是 `DRAFT`），**已发布批次没有任何重建路径** |
| **`cancelBatch` 未定义已有预约的归宿** | 已预约的学生进入悬空状态（永远 `RESERVED`、不归名额、不置爽约） | `markNoShows` 的 SQL 明确排除 `CANCELLED` 批次；用户取消时名额键已删（返回 rollback code 2） |
| **对账的黄金恢复窗口只有约 10 分钟** | 超时后 DLQ 重放被 `discard("COMPENSATED", "请求已补偿，无法重放")` 拒绝 | 对账阈值 10 分钟；这是**有意设计**（避免重放造成超发），但**没有被文档记录** |
| **消费–对账竞态有一个窄窗口** | 理论上可超卖（毫秒级窗口 + 需精确同时） | 消费者的 `COMPENSATED` 检查不是原子的；对账没有按 `requestId` 加锁 |

**🟠 有兜底但代价明确的**

| 边界 | 兜底 | 代价 |
|---|---|---|
| **同步等 MQ confirm 阻塞 5 秒** | 超时归 `UNKNOWN` 交给对账 | broker 慢时用户请求卡 5 秒；**Hikari 默认 10 连接**，10 个并发就能打满 |
| **`AmqpConnectException` 一律当作『确定未投递』** | MySQL 的条件更新 + 唯一索引 | 极小概率的超卖窗口（连接写出瞬间断开） |
| **缓存删除无补偿** | 30 分钟 TTL 自动收敛 | 最长 30 分钟内用户看到设备旧状态（**但不影响 `submit` 的校验，它直查库**） |
| **`queryWithMutex` 抢锁 20 次失败后直查库且不回写缓存** | 请求本身能返回正确数据 | 锁泄漏场景下热键并发全压到 DB；且**阻塞 Tomcat 线程最多 1 秒** |
| **`markNoShows` 的 `LIMIT` 没有 `ORDER BY`** | 每轮都会推进（终态行不会被重复扫） | 哪批先处理**不确定**；积压时可能不公平 |

**🟡 配置与运维层面的**

| 边界 | 说明 |
|---|---|
| **Hikari 连接池完全没配** | 用默认值（`maximum-pool-size: 10`、`connection-timeout: 30s`）。**Lettuce 池却精细调了**（`max-active: 10`、`time-between-eviction-runs: 10s`）——**这个不对称是有意的还是疏忽的，代码里没有说明** |
| **`prefetch=1`、`concurrency` 未配** | 消费者单线程；吞吐受限于此。**没压测过，不知道瓶颈在哪** |
| **没有任何指标系统** | 没有 Actuator、没有 Micrometer。对账的 `scanned/confirmed/compensated/failed` **只有日志**；`failed > 0` 或 `scanned == limit`（说明积压）**没有告警** |
| **对账锁看门狗可能导致静默停摆** | `tryLock(0, MILLISECONDS)` 启用看门狗；如果线程卡在没有超时的 DB 调用上，**锁永不释放，所有实例的对账跳过（`log.debug`），且没有任何告警** |
| **Redis 没有配 `maxmemory-policy`** | 那是服务端配置。项目文档里**没有说明生产环境该用什么策略**——如果配了 `allkeys-lru`，**名额键可能被淘汰**，直接触发上面第一条🔴 |

**🟡 安全与认证的**

| 边界 | 说明 |
|---|---|
| **登录 token 没有绝对有效期** | 30 分钟滑动 TTL，**被盗 token 只要持续请求就永不失效** |
| **验证码用后不删** | `login` 成功后没有 `DELETE`，**同一验证码在 2 分钟 TTL 内可重复使用** |
| **`sendCode` 无限流** | 可以对同一手机号无限调用。**现在不造成实际损失（验证码只打 log.debug，没接短信网关），但接上真实网关就是短信轰炸 + 真实成本** |
| **`tb_user.password` 从未使用** | 密码登录未实现，**种子管理员没有密码，只能走验证码（而验证码只打日志）** |
| **`RoleInterceptor` 的类级注解分支无使用者** | 18 处 `@RequireRole` **全在方法上**。**类级分支按设计保留，但从未被执行过**（`MIGRATION_STATUS:860` 已登记） |

**🟡 数据层的**

| 边界 | 说明 |
|---|---|
| **零外键** | 整个 `db/` 目录没有 `FOREIGN KEY`。**引用完整性靠应用层**——而应用层**不完整**：`deleteEquipment` **不检查批次依赖**（`deleteLaboratory` 检查了）。**这是同一项目内的不对称，README 只登记了前者** |
| **`tb_reservation_request` 只保留最近一次失败原因** | `fail_reason` 是覆盖写、`varchar(255)`。**没有事件表记录完整历史** |
| **账本表持续增长无清理** | **失败的请求也会写账本**（`PRE_ACCEPTED` → `COMPENSATED`），而且**终态行永远不会被删除**。这是审计能力，**但没有归档/分区策略** |
| **`MybatisConfig` 只配了分页插件** | **没有配 `BlockAttackInnerInterceptor`**——一个漏写 `WHERE` 的 `update` 会真的更新整张表，**没有插件兜底** |

## Q60. 如果要你重做这个项目，你会改什么？

**推荐回答**

「**我按『投入产出比』排，前三条是结构性的，后面是工程化的。**

**① 把 `submit` 的 MQ 投递改成异步（最高优先）。**

现在是**同步等 confirm 5 秒**。改成投递后立即返回『受理中』（比如返回 202 + `reservationId`），用 confirm 回调去推进账本状态，前端轮询 `GET /reservation/{id}` 拿结果。

**收益**：Tomcat 线程和数据库连接不再被 MQ 的响应时间绑架；`UNKNOWN` 的用户体验问题（收到错误提示但实际成功）也解决了——**因为『受理中』本身就是一个诚实的、可以被 UI 正确表达的中间态。**

**代价**：前端要多一个轮询/推送的机制；账本状态的推进变成回调驱动，**需要保证回调不在时对账仍然兜底**（这一点现在的设计已经满足）。

**② 给名额键加『从 MySQL 重建』的能力。**

现在**已经 `PUBLISHED` 的批次，名额键一丢就永久约不上**——这是最严重的一个🔴。

**做法**：加一个管理接口（或让对账任务兼职）：以 `tb_reservation_batch.remaining_quota` 为准 `SET` 名额键（**用 `SET` 而不是 `setIfAbsent`**），并且用 `SELECT user_id FROM tb_reservation WHERE batch_id = ? AND status IN ('RESERVED','COMPLETED')` 重建 `users` 集合。

**★ 这个改动必须谨慎**：重建时**必须确认没有正在进行的预约请求**（否则会覆盖正在进行的扣减）。**正确的做法是重建时先给批次加一个短暂的互斥标记**（让 `submit` 拒绝），或者干脆**在重建前把批次状态临时置为 `CLOSED`**。

**③ 明确定义 `cancelBatch` 的语义。**

现在它只做两件事（批次 → `CANCELLED`、删 Redis 键），**没有定义已有 `RESERVED` 预约的归宿**。

**我会把它定义成：取消批次 = 批量取消该批次下所有 `RESERVED` 预约 + 逐个归还名额 + 通知用户。** 或者至少**明确选择『不取消、但必须有一个状态能表达它』**（比如给预约加一个 `BATCH_CANCELLED` 状态）。

**关键不是选哪个，而是必须选一个并写进文档**——现在是**未定义**。

**④ 加指标和告警。**

`ReconcileSummaryDTO` 的四个计数**已经是结构化的了**（`scanned/confirmed/compensated/skipped/failed`）——**只差把它暴露出去**。引入 Actuator + Micrometer，把四个计数做成 Counter/Gauge，然后：

- `failed > 0` → 告警；
- `scanned == limit`（持续积压）→ 告警；
- **对账心跳**（每轮无条件打一行 info）→ 断流告警。

**这一条投入最小、收益最大**，因为**它保护的是『自愈机制本身』**。

**⑤ 补上 Hikari 配置和消费者并发配置。**

- `spring.datasource.hikari.maximum-pool-size` 按并发量显式配置；
- `connection-timeout` 从默认 30 秒降到 3–5 秒（**让失败快速暴露而不是挂 30 秒**）；
- `spring.rabbitmq.listener.simple.concurrency` 显式配置；
- `prefetch` 根据压测结果调（**前提是先压测**）。

**⑥ 登录相关的三个安全缺口。**

验证码用后删除、`sendCode` 加限流（Redis 计数 + 滑动窗口）、token 加绝对有效期。

**⑦ 长期：升级 Spring Boot。**

现在为了用新版的 Lettuce 而**局部覆盖 `spring-data-redis` 和 `lettuce-core` 的版本**（`pom.xml` 里 exclude 再 re-pin），**这是一个跨小版本的混搭**——它现在能工作只是因为这些 API 在 2.x 内稳定。**正确做法是升级整个 Boot 版本，而不是局部覆盖依赖。** 顺带也能把 Java 8 升上去。

**★ 而如果只能改一件事，我选 ①。** 因为**同步等 confirm 是一个会随着负载变化而恶化的设计**——**低负载时它是无害的（几毫秒），高负载时它会变成级联故障的起点（连接池打满 → 所有接口变慢 → 更慢 → 打满）**。**而其他问题在低负载下基本是静止的。**」

## Q61. 这个系统能扛多少并发？

**推荐回答**

「**我给不出数字，因为这个项目从没做过压测。我不会编一个。**

**但我可以做定性的瓶颈分析，而且我认为这个分析比一个编造的数字更有价值。**

**★ 一次预约请求的开销（同步路径）：**

| 序 | 操作 | 类型 | 相对开销 |
|---|---|---|---|
| 1 | `INCR icr:reservation:日期` | Redis | 一次往返 |
| 2 | `INSERT tb_reservation_request` | MySQL | 一次写 + 一次提交 |
| 3 | `reservation.lua` | Redis | 一次往返 |
| 4 | `convertAndSend` + **`getFuture().get(5, SECONDS)`** | MQ | **一次往返 + 最长 5 秒阻塞** |
| 5 | `UPDATE` 账本置 `PUBLISHED` | MySQL | 一次写 |

**异步路径（消费者）：** Redisson 加锁（1 次 Redis）→ 查账本（1 次读）→ 查已存在预约（1 次读）→ 扣名额（1 次写）→ 插预约（1 次写）→ CAS 账本（1 次写）→ 解锁（1 次 Redis）。

**所以一次预约 ≈ 4 次 Redis + 3 次 MySQL + 1 次 MQ 同步往返。**

**★ 瓶颈判断（按可能性排序）：**

**① MySQL 连接池 —— 最可能的第一个瓶颈。**

`application.yaml` **完全没有配 `spring.datasource.hikari.*`**，所以是 **Hikari 默认的 10 个连接**。而这 10 个连接要和**三类消费者**共享：

- Tomcat 请求线程（`submit` 里至少 2 次 MySQL 操作，加上前置校验的若干次查询）；
- RabbitMQ 消费者线程（`persist` 的事务 + 查询）；
- 对账定时任务（每轮扫 200 条 × 3 类任务）。

**★ 这里有一个危险的正反馈**：如果 MQ 变慢，`submit` 里的线程会**持有连接 5 秒**（如果那时恰好在一个需要连接的操作里）——**连接被长时间占用 → 其他请求等连接 → 请求处理变慢 → 更多线程堆积 → 连接更紧张**。**这是级联故障的经典形态。**

**② 同步等 confirm —— 第二个瓶颈，而且和 ① 耦合。**

正常情况几毫秒，**但它是一个『外部依赖的响应时间会直接变成我的响应时间』的设计**。MQ 的网络抖动会直接传导到用户请求。**而且它占用的是 Tomcat 线程**（默认 200 个）——**200 个线程各卡 5 秒，就是 200 个并发请求的容量上限，然后新请求开始排队。**

**③ 账本表的写入量 —— 第三个。**

**每次预约（包括失败的）都要写一次账本 INSERT + 一次 CAS UPDATE。** 失败的请求也写——这是**为了可审计性付的代价**（`PRE_ACCEPTED` 必须在扣 Redis 前写，那时还不知道会失败）。

**所以账本表的写入次数 ≈ 预约请求总数 × 2**（一次 insert + 一次状态更新）。**这张表会持续增长，而且 `idx_status_update_time` 这个索引也会随之变大**——**对账的 `listStale` 查询会逐渐变慢。**

**④ Redis 不是瓶颈。**

Lua 脚本 27 行、全 O(1)、无循环——**它的执行时间是微秒级的**。**而 Redis 单线程的吞吐（十万级 QPS 的量级）远高于后面 MySQL 的写入能力。**

**★ 所以这个系统的瓶颈在持久化层，不在缓存层。** **这恰好印证了 Q8 的判断：Redis 解决的是『并发准入』这个最尖锐的问题，但它不是整个系统的性能上限。**

**★ 如果要给出一个可信的数字，需要做什么？**

1. **先配好连接池**（当前配置下的任何数字都只反映『连接池默认值 10』这个事实，没有意义）；
2. **压测工具**（JMeter / wrk / k6）打 `POST /reservation`，测**固定批次数量的多用户并发**（因为名额会耗尽，必须持续补充数据或分批测）；
3. **观察指标**：P99 延迟、错误率、Hikari 的 `activeConnections`/`pendingThreads`、RabbitMQ 的队列深度、对账的 `scanned`；
4. **找拐点**：并发上升时哪个指标先到上限。

**★ 我要明确说的一点**：**README 和所有文档里都没有吞吐数字**，这是**有意的**——因为**没有测量就没有数字**。**如果面试官问这个，我更愿意给出上面的定性分析 + 明确的『没测过』，而不是一个听起来很厉害但编造的数字。**」

## Q62. 文档和代码不一致的时候你怎么办？

**推荐回答**

「**以源码为准，并且把不一致明确写进文档——不是改掉哪一方，而是让不一致本身可见。**

**这个任务里我实际找到了 14 处不一致**（都记录在 `00-项目全景.md` 里）。**举几个有代表性的：**

**🔴 最严重的：README §9③ 描述了一个不存在的机制。**

> README 说：`phase8`/`phase9` 提供 `UPDATE ... SET active_flag = 0 WHERE id = ? AND active_flag = 1` 来检测并发修改、推导 `QUOTA_CONFLICT`。

**核对结果**：

- `active_flag` 是 **`GENERATED ALWAYS AS (...) STORED`**（生成列）——**MySQL 不允许 `SET` 生成列**（会报 `ERROR 3105`）；
- 全仓 Java 源码对 `active_flag` 的引用数是 **0**；
- `QUOTA_CONFLICT` 的**真实来源**是 `ReservationPersistenceServiceImpl:55` 的 `remaining_quota > 0` 条件更新。

**所以我写的是**：**README 描述的机制在源码中不存在，`QUOTA_CONFLICT` 的实际来源是另一处。** 而不是『把 README 的说法抄进文档』。

**🔴 第二个：README §1/§4 说对账任务会『重新投递』『超阈值进死信』。**

**核对结果**：全仓只有 **两处** `convertAndSend`——`ReservationServiceImpl:251`（首次投递）和 `ReservationDlqServiceImpl:257`（人工重放）。**对账只做 `casStatus(CONFIRMED)` / `rollback + COMPENSATED` / `releasePendingQuotas` / `markNoShows`，从来不投递任何消息。**

**🔴 第三个：README §9② 说『失败次数超过阈值』。**

**核对结果**：`tb_reservation_request` **没有计数字段**（只有 `request_id/user_id/batch_id/status/fail_reason/create_time/update_time`）。**`reconcile-threshold-ms` 是时间窗口（600000ms = 10 分钟），不是次数。** 退避是通过**推进 `update_time`** 实现的（Q42）。

**🟠 第四个：README §7 列了 `lab:equipment:null:{id}` 这个 key。**

**核对结果**：**这个 key 不存在**。`CacheClient:84` 写的是 `set(key, "", CACHE_NULL_TTL, MINUTES)`——**同一个 `lab:equipment:{id}`，值是空字符串**。

**🟡 还有一些小的**：`UserController:34` 的 javadoc 说支持密码登录（`LoginFormDTO` 只有 `phone` 和 `code`）；`UserServiceImpl:47` 的注释说『保存验证码到 session』（实际写 Redis）；`RegexUtils:9` 的 javadoc 语义反了（说『true:符合』，而 `isPhoneInvalid` 返回 true 表示**不**符合）。

**★ 我处理这些的原则有三条：**

**① 不改代码，也不改文档。** 任务约束是『只生成学习文档，不修改任何生产代码』，**而 README 也是仓库的一部分，改它同样超出了这个任务的边界**。**所以我把不一致记录下来，让读者知道真相在哪。**

**② 记录时给出『源码证据』，而不是我的判断。** 比如上面每一条我都写明了**文件名、行号、以及我是怎么核对的**（grep 了什么、读了哪个方法）。**这样读者可以自己验证，而不是相信我的结论。**

**③ 按严重程度分级。** 🔴 是『会误导实现』的，🟠 是『会误导理解』的，🟡 是『文字层面的』。**因为不是所有不一致都同等重要**——把 `RegexUtils` 的注释反了和把 `active_flag` 的机制说错，**代价完全不同**。

**★ 而我从这件事上学到的最重要的一点是**：**README 不是事实来源，源码才是。** 而**文档和代码产生分歧是必然的**——因为文档没有编译器和测试。

**所以一个健康的做法是**：**文档里明确标注它描述的是哪个版本的行为**，或者**把关键不变式写成测试**（这样文档错了测试会红）。

**这个项目里其实有一个很好的实践**——`MIGRATION_STATUS.md` 会记录『**诚实登记：本项无变体强度证据**』这类信息。**它明确区分了『我验证过的』和『我判断但没验证的』。** 这比一个看起来完整但实际上混合了事实和猜测的文档有价值得多。」

---

## Q63. 从这个项目里你学到的最重要的一件事是什么？

**推荐回答**

「**如果只能说一件，我选这个：**

> **在分布式系统里，『不知道』是一个必须被显式建模的状态——你不能把不确定当作确定来处理。**

**这个项目里最核心的几个设计，全部是这条原则的推论：**

**① 生产者把投递结果分成三类，而不是两类。**

`ACKED` / `DEFINITELY_NOT_DELIVERED` / **`UNKNOWN`**。**如果只有成功和失败两类，超时就只能被硬塞进其中一个**——塞进成功会泄漏名额，塞进失败会超卖。**而 `UNKNOWN` 让系统可以在信息不足时『暂不决定』。**

**② `UNKNOWN` 是非终态，不是终态。**

因为它**待裁决**。**如果它是终态，超时的请求就永远不会被对账扫到。** ——**这一点我一开始理解错了**，我以为 `UNKNOWN` 只是一个标记；读了 `nonTerminalStatuses()` 才发现它被刻意排除在终态之外，**是有功能的**。

**③ `reservationRollback.lua` 用 `SREM` 的返回值来判断『该不该归还』。**

它**不需要知道『Redis 扣没扣过』**——**它让『归还』这个动作自己携带幂等性**。**这是把『不确定的历史』转化成一个『确定的当前操作』的手法。**

**④ 对账的判据是『MySQL 里有没有那行』，而不是『投递成没成功』。**

**因为它查的是最终事实，不是过程信号。** 这比 confirm 回调可靠得多——**confirm 只告诉你 broker 收到了，不告诉你消费者处理了。**

**⑤ `AmqpConnectException` 的归类是一个**有意识的乐观假设**，而且它配了兜底。**

我在 Q33 追问里说过：**这个判定在理论上不严格**（连接断开时消息可能已经写出）。**但项目选择了乐观假设，并靠 MySQL 的条件更新和唯一索引兜住极小概率的反例。** ——**这也是这条原则的一部分：不严格的时候，要明确知道它不严格，并且知道兜底在哪。**

**★ 而这五条背后是同一个方法论：**

> **把『我不确定』变成一个可以被后续机制消除的状态，而不是在当下猜一个答案。**

**映射到工程上就是三件事：**

1. **状态机里要有表达不确定的状态**（`UNKNOWN`）；
2. **不确定的状态不能是终态**（要被扫描到）；
3. **消除不确定要靠查最终事实，而不是查过程信号**（`selectById`，而不是 confirm）。

**★ 而我学到的第二件事（也是这条原则的另一面）：**

> **『正确性不依赖锁』——锁可以换性能，不能换正确性。**

对账任务的方法注释写着『分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证』。**这句话改变了我的一个直觉**——**我原来的反应是『多实例跑同一个定时任务，那就加个锁保证只跑一次』。** 但作者的想法是：**锁会失效（GC 停顿、网络分区、看门狗挂掉），所以正确性不能押在它上面；把它降级成性能优化之后，锁失效最坏只是多做一遍无用功。**

**而让这句话能成立的前提是**：**每一个副作用都是幂等的**（CAS、`SREM`、条件 UPDATE）。**这两件事是配套的——没有幂等，就不敢不依赖锁。**

**★ 所以如果面试官继续问『你觉得什么样的代码是好代码』，我的回答是：**

**『不出错的时候能跑，出错的时候能收敛，而且『出错』这件事本身是被显式建模的——不是靠假设它不会发生。』**

**这个项目在这一点上做得比我之前见过的任何练手项目都好**，**因为它有 20 个异常场景的推演（`12-异常场景推演.md`），而且每一条都能指到具体的代码。** ——**而它的边界也写得很清楚：哪一些是兜住了的，哪一些是没有兜底的。**」
