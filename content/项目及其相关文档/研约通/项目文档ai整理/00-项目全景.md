# 00 · 项目全景

> **这一篇的作用**：在你深入任何一个模块之前，先建立一张「地图」——这个项目在解决什么业务问题、每个技术各自负责哪一段、哪一份文档回答哪一类问题。
>
> 只讲代码在做的事，不讲设计动机。

## 1. 一句话概括

**研约通**是一个**高校实验资源预约平台**的后端服务：管理员为实验室里的某台设备创建**预约批次**（限定开放时段 + 名额上限），学生在开放窗口内抢名额提交预约。

Spring Boot 单体应用 + MySQL + Redis + RabbitMQ，要同时满足三条硬要求：

| 要求 | 一句话做法 | 详细机制 |
|---|---|---|
| **不超卖** | 名额的准入判定收在**一个 Redis Lua 脚本**里原子完成；MySQL 侧还有条件更新兜底 | §5.1 |
| **不丢单** | 请求**先落一张状态账本表**再做异步落库；配合发布确认 + **定时对账**自动收敛 | §5.2 |
| **可自愈** | 定时任务扫描「卡住的请求」，按证据判定它是成功还是失败，然后推进到终态 | §5.3 |

**这三条是一条链上的三个环节**（提交 → 投递 → 落库 → 对账），所以 05～12 篇要连起来读。

## 2. 业务对象

### 2.1 四层结构

```
实验室 Laboratory
   └── 设备 Equipment          （如「高性能计算服务器」）
          └── 预约批次 Batch     （限定：预约窗口 + 使用时段 + 名额上限）
                 └── 预约单 Reservation  （一个学生占用一个名额）
```

「设备」只说清了**用什么**，说不出**什么时候能用、有多少名额**。批次把「一段使用时段 + 一段预约窗口 + 名额上限与余量 + 一个状态机」打成一个**可预约的原子单位**，名额才有地方挂。

**代码上的硬证据**：`ReservationServiceImpl.submit(Long batchId)` 只收一个 `batchId`，请求体 DTO 只有这一个字段——**学生预约的对象是批次，不是设备**。

### 2.2 批次上的两套「状态」

| | `ReservationBatchStatus` | `BookingState` |
|---|---|---|
| 值 | `DRAFT` / `PUBLISHED` / `CLOSED` / `CANCELLED` | `DRAFT` / `NOT_STARTED` / `OPEN` / `EXPIRED` / `CLOSED` / `CANCELLED` |
| **入库吗** | ✅ 入 `tb_reservation_batch.status` | ❌ **不入库**，读取时算出来给前端 |
| 谁决定 | **管理员的显式动作** | 管理员的动作 **+ 时间流逝** |

**`BookingState` 为什么不能入库**：它是 `(status, bookingStartTime, bookingEndTime, now)` 的纯函数，`now` 每毫秒都在变。**系统里没有任何事件**会去触发一次 UPDATE 把它刷新（没有「到点了把 `NOT_STARTED` 改成 `OPEN`」的定时任务），落库的值下一秒就过期。

判定顺序是**先状态后时间**（管理员的 `CLOSED` 优先于时间窗口）。见 [04 篇](04-预约批次.md)。

### 2.3 名额的两份账

| | Redis | MySQL |
|---|---|---|
| 存什么 | `reservation:batch:quota:{id}` 一个**整数计数器** | `tb_reservation_batch.remaining_quota` 一列 |
| **角色** | **准入判定的权威** | **账实相符的权威** |
| 谁扣它 | `reservation.lua`（学生抢名额时） | `tb_reservation` 落库时（消费者事务内） |
| 谁还它 | `reservationRollback.lua` | `cancel` 时 `remaining_quota + 1` |
| 谁判超卖 | **它**（Lua 里 `quota <= 0` → 拒绝） | 它也有第二道闸（`WHERE remaining_quota > 0`） |

**Redis 负责「谁能进」，MySQL 负责「进来的对不对」。** 两者不试图保持一致，而是各自在自己的职责范围内自洽，中间用「请求账本 + 定时对账」缝合——所以 Redis 里的名额和 MySQL 的 `remaining_quota` **允许不一致**（[12 篇场景 20](12-异常场景推演.md)）。

### 3.2 每个技术负责哪一段

| 技术 | 不可替代的那件事 | 在项目里还干了什么 |
|---|---|---|
| **Redis** | **名额闸门**：`reservation.lua` 把「查名额 + 查时段 + 查重复 + 扣减 + 记录」合成一个原子操作。没有它，「查→判→扣」就是三条命令、中间是超卖窗口，只能靠 `SELECT ... FOR UPDATE` 串行化，吞吐被行锁压死 | 去重集合 `reservation:batch:users:{id}`；登录会话 `login:token:{token}`；设备缓存 `lab:equipment:{id}`（**这一项是投资而非必需**，见 [03 篇](03-设备缓存.md)） |
| **RabbitMQ** | **把落库移出用户响应路径**：用户拿到的是「请求已被受理」（Redis 已扣 + 账本已落 `PRE_ACCEPTED`），落库后台完成 | 发布确认（三态）、手动 ACK、死信队列（[06 篇](06-RabbitMQ异步预约.md)） |
| **Redisson** | **两类锁里需要看门狗和可重入的那一类**：消费端 `lock:reservation:{userId}` 按用户串行化、对账 `lock:reservation:reconcile` 多实例互斥 | 缓存的锁是**手写 `SETNX` + `unlock.lua`**（[03 篇](03-设备缓存.md)）——**项目里两种锁完全不同，不能用同一套思路理解** |
| **MySQL** | **权威 + 兜底 + 可对账**：`remaining_quota` 和 `tb_reservation` 行是最终事实；`uk_user_batch_active` 与条件更新是最后一道闸；账本的 `status + update_time` 就是给对账扫的 | 8 张表，见 §4 |

**Spring Boot / MyBatis-Plus 没有「为什么需要」的故事**，就是当前主流默认选择。两个要知道的点：

- Boot 选 **2.3.12** 而不是更新版本，是因为项目从课程项目改造而来，**版本跟着原项目走**；Boot 2.3 已于 2021 年停止社区支持。
- `pom.xml` 里**显式排除了** Boot 管理的 `spring-data-redis` / `lettuce-core`，重新锁定为 2.6.2 / 6.1.6.RELEASE，并**额外引入 `commons-pool2`**。原因：Boot 的 starter 默认不引入 `commons-pool2`，不加它，`spring.redis.lettuce.pool.*` 的配置**完全不生效**（连接池根本不存在）。

> ⚠️ **一个配置不对称**：`application.yaml` 里精细调了 Lettuce 连接池（`max-active: 10, max-idle: 10, min-idle: 1, time-between-eviction-runs: 10s`），**却完全没有配 `spring.datasource.hikari.*`**——MySQL 连接池用的是 Hikari 默认值（`maximum-pool-size: 10`、`connection-timeout: 30s`），而且这 10 个连接要和「消费者线程 + 对账定时任务 + 用户请求」共享。见 [11 篇](11-数据库设计与并发安全.md)。

### 3.3 一张图看清全链路

```
用户点击「预约」
      │
      ▼
① 生成 reservationId
   RedisIdWorker → Redis INCR "icr:reservation:yyyy:MM:dd"          ← Redis：全局唯一 ID
      │
      ▼
② 写账本 tb_reservation_request (PRE_ACCEPTED)                      ← MySQL：先留下「凭据」
      │
      ▼
③ reservation.lua 原子执行：
   EXISTS 名额键 → 时段校验 → quota > 0 → SISMEMBER 去重             ← Redis Lua：唯一的临界区
   → DECR 名额 + SADD 用户 + EXPIRE                                    （防超卖第一道闸）
      │
      ▼
④ 投递 MQ + 等发布确认（ACKED / 未投递 / UNKNOWN 三态）              ← RabbitMQ：异步化 + 可靠性
   账本 CAS → PUBLISHED
      │
      ▼
⑤ 消费者：Redisson 用户锁 → 事务内「条件扣 MySQL 名额 + 插预约行」     ← Redisson：串行化同用户
   → 账本 CAS → CONFIRMED → 手动 ACK                                 ← MySQL：账实相符（第二道闸）
      │
      ▼
⑥ 定时对账（每 5 分钟）：扫超 10 分钟未终结的账本行                   ← 对账：缝合 Redis 与 MySQL
   有预约行 → CAS CONFIRMED（不回滚名额）
   无预约行 → rollback 归还名额 → CAS COMPENSATED
```

## 4. 领域模型与 8 张表

### 4.1 实体关系

```
tb_user ──┬── admin_user_id ──▶ tb_laboratory
          │                          │ laboratory_id
          │                          ▼
          │                     tb_equipment ──category_id──▶ tb_equipment_category
          │                          │ equipment_id
          │                          ▼
          │                     tb_reservation_batch
          │                          │ batch_id
          │                          ▼
          └── user_id ────────▶ tb_reservation
                                     ▲
                                     │ （id 与 request_id 同源同值）
          └── user_id ────────▶ tb_reservation_request
          └── user_id ────────▶ tb_reservation_dlq（通过 reservation_id 弱关联）

          tb_reservation_dlq ──reservation_id──▶ tb_reservation（弱关联，可为 NULL）
```

**这些箭头全部是「逻辑关系」，不是数据库外键**——整个 `db/` 目录里**一个 `FOREIGN KEY` 都没有**（grep 过）。

| 好处 | 代价 |
|---|---|
| 迁移脚本**无顺序耦合**（可以先建 `tb_equipment` 再建 `tb_laboratory`） | 数据库**不保证引用完整性**——`tb_equipment.laboratory_id` 可以指向不存在的实验室 |
| **删数据不需要级联处理**（`phase10` 能直接 `DROP` 10 张表） | **删除依赖要靠应用层自己检查**（`deleteLaboratory` 会拒绝删有设备的实验室） |
| 高并发写时**没有外键锁开销** | 孤儿数据只能靠 `LEFT JOIN` 让读不崩，不能靠约束拒写 |

**项目的应对方式是「应用层检查 + `LEFT JOIN`」**：`ReservationMapper.xml` 的列表查询用 `LEFT JOIN`，所以即使设备/实验室被删了，预约列表**仍能查出来**（相关字段为 null），不会因为 `INNER JOIN` 而「丢行」——这也解释了为什么 `deleteEquipment` 漏检不会让页面崩（见 [11 篇](11-数据库设计与并发安全.md)、§7 不一致清单第 6 条）。

### 4.2 8 张表的职责

| # | 表 | 一句话职责 | 建表脚本 |
|---|---|---|---|
| 1 | `tb_user` | 用户，`role` 区分 `USER` / `LAB_ADMIN` | `phase0` → `phase3` |
| 2 | `tb_laboratory` | 实验室，`admin_user_id` 指向**负责的管理员**（归属链的起点） | `phase2` → `phase5_lab_ownership` |
| 3 | `tb_equipment_category` | 设备分类（字典表） | `phase2` |
| 4 | `tb_equipment` | 设备，`booking_enabled` 控制**是否允许被预约** | `phase2` |
| 5 | `tb_reservation_batch` | 预约批次，`remaining_quota` 是**账实相符的权威** | `phase5_reservation_batch` |
| 6 | `tb_reservation` | 预约单，含 `active_flag` **生成列** + `uk_user_batch_active` | `phase7` → `phase9` |
| 7 | `tb_reservation_request` | **请求状态账本**——对账的唯一输入 | `phase8` |
| 8 | `tb_reservation_dlq` | 死信台账，`replay_count` 限最大重放次数 | `phase8` |

**第 8 张表为什么必须存在**：RabbitMQ 里**已经有**一个 `reservation.create.dlq` 队列，但 broker 的 DLQ 里只有原始消息二进制，**不能按业务字段查询、不能记录「处理过没有」、不能限制重放次数**。落一张表才能做「分页查看 + 人工重放 + 重放上限」。见 [10 篇](10-DLQ死信治理.md)。

### 4.3 生成列模拟「部分唯一索引」

**需求**：同一用户对同一批次**最多只能有一条「占用中」的预约**，但**取消过的记录要保留**（可以有多条）。

普通 `UNIQUE KEY (user_id, batch_id)` 做不到——它会连同已取消的行一起限制，用户取消一次之后就**永远无法重新预约**。MySQL 没有 `WHERE status <> 'CANCELLED'` 这种部分唯一索引，所以：

```sql
-- phase9_reservation_lifecycle.sql
ALTER TABLE tb_reservation
  ADD COLUMN `active_flag` tinyint
    GENERATED ALWAYS AS (CASE WHEN `status`='CANCELLED' THEN NULL ELSE 1 END) STORED,
  ADD UNIQUE KEY `uk_user_batch_active` (`user_id`, `batch_id`, `active_flag`);
```

**原理：在唯一索引里，多个 NULL 不算重复。**

| 行 | `user_id` | `batch_id` | `active_flag` | 唯一键冲突？ |
|---|---|---|---|---|
| R1 已取消 | 1 | 1 | **NULL** | — |
| R2 已取消 | 1 | 1 | **NULL** | ❌ 不冲突（NULL ≠ NULL） |
| R3 占用中 | 1 | 1 | **1** | ✅ 可以插入 |
| R4 再想占用 | 1 | 1 | **1** | ✅ **冲突！被拒** |

> ⚠️ **两个必须知道的点**：
> 1. **`active_flag` 是 `GENERATED ALWAYS ... STORED` 列，不能被 `SET`**——值完全由 `status` 推导。Java 源码里**零处引用**这一列（grep 过，只在 `ReservationStatus` 的注释里被提及）。
> 2. **README §9③ 描述了一个不存在的机制**：「`UPDATE ... SET active_flag = 0 WHERE id = ? AND active_flag = 1`，影响行数为 0 即判定 `QUOTA_CONFLICT`」。**这条 SQL 在代码里不存在，而且语法上就不可能执行**（生成列不可写）。`QUOTA_CONFLICT` 的真实来源是 `ReservationPersistenceServiceImpl:55` 对 **`remaining_quota` 的条件更新**。见 §7 第 1 条。

### 4.4 迁移链

```
phase0_baseline              建 tb_user（★ 注意：没有 role 列）
  ↓
phase2_laboratory_equipment  建 实验室 / 分类 / 设备 三表 + 种子数据
  ↓
phase3_user_role             给 tb_user 加 role 列 + 种子管理员
  ↓
phase5_lab_ownership         给 tb_laboratory 加 admin_user_id + 指派归属
  ↓
phase5_reservation_batch     建 预约批次表
  ↓
phase7_reservation           建 预约单表
  ↓
phase8_consistency           建 请求账本 + 死信台账
  ↓
phase9_reservation_lifecycle 给预约单加 status / quota_released / active_flag
  ↓
phase10_drop_legacy_tables   删 10 张课程时代的表（★ 一次性、不可逆）
```

拆成 9 个脚本而不是一个建表脚本，是因为**项目从已有的、装着课程数据的库（`hmdp`）改造而来**，必须**增量执行**（库里有 1011 个用户 + 10 张课程表）而不是删库重建。三个要求在脚本里都能看到：

| 要求 | 脚本里的体现 |
|---|---|
| **幂等** | `phase3` 用 `information_schema` 守卫判断列是否存在；`phase0/2` 用 `INSERT ... ON DUPLICATE KEY UPDATE` |
| **向后兼容** | `phase3` 的 `role varchar(16) NOT NULL DEFAULT 'USER'` —— **1011 个存量用户自动获得 `USER`**，一个都不报错 |
| **可回滚** | `phase9` 的注释写了回滚前必须**先删同一 `(user_id, batch_id)` 下已取消的行**，否则重建旧唯一键会失败 |

> ⚠️ **读 DDL 时要注意的顺序问题**：`tb_user` 的初始建表（`phase0_baseline.sql`）**没有 `role` 列**，而 `User` 实体里有 `role` 字段——**只跑 `phase0` 的话用户模块会启动失败**。必须按 README 11.3 的顺序跑完整条链。`phase0_baseline.sql` 的第一行注释就是执行顺序。

## 5. 三条硬要求分别由哪些机制兑现

### 5.1 不超卖 —— 四层

| 层 | 机制 | 位置 | 防的是什么 |
|---|---|---|---|
| ① | **Lua 原子脚本**：`EXISTS` → 时段 → `quota > 0` → `SISMEMBER` → `DECR` + `SADD` | `reservation.lua` | **并发超卖**（主防线） |
| ② | **Redisson 用户锁** `lock:reservation:{userId}` | `ReservationMessageConsumer` | **同一用户的**消息串行化 |
| ③ | **条件更新** `UPDATE ... SET remaining_quota = remaining_quota - 1 WHERE id = ? AND remaining_quota > 0` | `ReservationPersistenceServiceImpl` | **Redis 计数偏离**时的 MySQL 兜底 |
| ④ | **唯一索引** `uk_user_batch_active (user_id, batch_id, active_flag)` | `phase9` | **同用户重复占用**的最后兜底 |

**① 是唯一真正防并发的那层**，②③④ 都是「即使 ① 失效也不会错」的保险。**没有 ①、只有 ③④，系统仍然不会超卖**——但要靠数据库行锁串行化，性能垮掉。这就是「Redis 不可替代、而缓存是可选的」的原因。

### 5.2 不丢单 —— 先记账 + 三态投递 + 对账

| 环节 | 机制 | 解决的失败模式 |
|---|---|---|
| **先记账** | 扣 Redis **之前**先写 `tb_reservation_request(PRE_ACCEPTED)` | **Redis 已扣但进程崩溃** → 留下可扫描的凭据（[12 篇场景 2](12-异常场景推演.md)） |
| **三态投递** | `ACKED` / `DEFINITELY_NOT_DELIVERED` / `UNKNOWN` | **只有「确定没投出去」才归还名额**；「不确定」必须保持占用（[12 篇场景 6](12-异常场景推演.md)） |
| **消费幂等** | `selectById(reservationId)` 判重 → `DUPLICATE` → **ACK** | **消息重投**不会重复落库（[12 篇场景 8/10](12-异常场景推演.md)） |
| **不无限重试** | `retry.enabled: false` + `basicNack(requeue=false)` | **毒消息**不会循环拖死消费者（[12 篇场景 11](12-异常场景推演.md)） |
| **对账收敛** | 扫非终态账本行 → 有预约行则 `CONFIRMED`，无则 `rollback + COMPENSATED` | **上面全没覆盖到的**「事件从未发生」（[12 篇场景 2/6/7](12-异常场景推演.md)） |

**「先记账」是整个设计的支点**：反过来（先扣 Redis 再写账本）的话，在两者之间崩溃时 **MySQL 里没有任何记录**，对账无从下手，那一格名额**永久泄漏**。

### 5.3 可自愈 —— 五条路径

| 异常 | 自愈机制 | 恢复时间 |
|---|---|---|
| MQ 不可达 / 确认失败 / 消息被退回 | **立即** `rollback` 归还名额 + 账本 `COMPENSATED` | 立即 |
| Confirm 超时（**结果不确定**） | 账本置 `UNKNOWN`（**不动 Redis**）→ 对账裁决 | ≤ 10 分钟 |
| 消费者落库失败 | NACK 进 DLQ + 对账归还名额 | ≤ 10 分钟（名额）/ 人工（消息） |
| 取消时 Redis 归还失败 | `quota_released = 0` 留在库 → 对账扫 `status='CANCELLED' AND quota_released = 0` 补做 | ≤ 5 分钟 |
| 对账自己失败 | `recordReconcileFailureSafely` 推进 `update_time` → 退出陈旧窗口 → 下一轮再试 | 下一轮 |

**最后一条体现的设计**：**对账失败**这件事本身也被做成了「退避 + 重试」，而不是「记一个失败计数然后放弃」。见 [08 篇](08-对账与自愈.md)。
