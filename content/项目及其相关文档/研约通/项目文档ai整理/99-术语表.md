## 1. Cache Aside

**通用定义**

缓存模式的一种：**应用代码自己维护缓存和数据库的同步**，而不是靠缓存层自动做（那是 Read-Through / Write-Behind）。标准形态是「**读时：先查缓存，未命中就查库并回写；写时：先写库，再删除缓存**」。

**★ 为什么是「删除」而不是「更新」**：因为并发下「写库」和「写缓存」是两个操作，顺序无法保证——两个更新请求的写缓存顺序可能和写库顺序相反，**用旧值覆盖新值**。而删除不携带数据，最坏结果只是多一次未命中。

**在研约通里的具体体现**

**设备详情**用的是 Cache Aside。读路径是 `EquipmentServiceImpl` 调 `CacheClient.queryWithMutex`；写路径（更新/删除设备）是 `EquipmentServiceImpl.deleteEquipmentCache` → `stringRedisTemplate.delete(key)`。

**★ 两个真实边界**：

1. **缓存删除没有补偿**——`deleteEquipmentCache` 既没有 try/catch 也没有重试。**Redis 不可用时异常会直接抛出，表现是「库里的写已经成功了、接口却报错」**，而缓存里的旧值要等 30 分钟 TTL 才过期；
2. **但缓存陈旧不影响业务判定**——`submit` 里对设备和批次的校验用的是 `equipmentService.getById`（**MyBatis-Plus 默认方法，直查库**），**不走 `CacheClient`**。

**对应代码**

- `utils/CacheClient.java` — `queryWithMutex`（唯一的读实现）
- `service/impl/EquipmentServiceImpl.java` — 详情/列表查询、`deleteEquipmentCache`
- `utils/RedisConstants.java` — `CACHE_EQUIPMENT_KEY` / `CACHE_EQUIPMENT_TTL = 30L` / `CACHE_EQUIPMENT_TTL_JITTER = 5L`

## 2. 缓存穿透

**通用定义**

**查询一个数据库里根本不存在的数据**，导致每次都穿过缓存打到数据库。缓存对它天然无效（因为「查不到」这件事没有被缓存下来）。

**危害**：如果攻击者遍历不存在的 id，每次请求都会打到数据库——**缓存层形同虚设**。

**两种解法**：① **空值缓存**（把「不存在」也缓存起来，用短 TTL）；② **布隆过滤器**（前置判断 id 是否存在）。

**在研约通里的具体体现**

用的是**空值缓存**，没有用布隆过滤器。写法是**同一个 key、值是空字符串**：

```java
stringRedisTemplate.opsForValue().set(key, "", CACHE_NULL_TTL, TimeUnit.MINUTES);
```

**★ 三个关键点：**

1. **TTL 是 2 分钟，比正常缓存的 30 分钟短 15 倍。** 这是刻意的——**正常缓存有「内容变更」的风险（所以要长 TTL 提升命中率），空值几乎没有**（一个 id 从不存在到存在，是因为新建了实体，而新建走不同的路径）。**短 TTL 限制了「攻击者灌入大量空 key」的内存风险。**
2. **`⚠️ README §7 说这是一个独立的 key `lab:equipment:null:{id}`——源码里不存在这个 key。** 实际用的是**同一个 `lab:equipment:{id}`，值是 `""`**。这是文档与源码的一处不一致。
3. **空值缓存是内联在 `queryWithMutex` 里的**（`CacheClient:84`），**不是复用 `queryWithPassThrough`**——而后者**没有任何生产调用方**（它是保留的参考实现）。

**对应代码**

- `utils/CacheClient.java:84` — 空值写入
- `utils/RedisConstants.java` — `CACHE_NULL_TTL = 2L`（分钟）

## 3. 缓存击穿

**通用定义**

**一个热点 key 在失效的瞬间，大量并发请求同时未命中**，全部涌向数据库。

**★ 和穿透的区别**：穿透查的是**不存在**的数据；击穿查的是**存在但缓存刚好过期**的数据。**击穿的前提是「这个 key 很热」**——冷 key 过期了没人查，不存在击穿问题。

**两种解法**：① **互斥锁**（只让一个线程去重建，其他等待）；② **逻辑过期**（缓存永不过期，值里带一个逻辑过期时间，异步重建）。

**在研约通里的具体体现**

用的是**互斥锁重建**（`queryWithMutex`），**没有用逻辑过期**（`queryWithLogicalExpire` 存在但无调用方）。

**三个实现要点：**

1. **双重检查**——拿到锁之后**重新读一次缓存**。因为「第一次检查未命中」和「拿到锁」之间有间隙，**持锁的线程可能已经把缓存建好了**。没有双重检查，等锁的线程会排队一个一个去查库，**互斥锁退化成串行查询**；
2. **有界等待**——`MUTEX_MAX_RETRY = 20`，每次 `sleep(50)`，**递归改成了有界循环**（Phase 4 的修复，原实现无界递归会栈溢出）；
3. **兜底**——20 次仍抢不到锁就**直查数据库**。

**★ 兜底的边界**：**直查库之后不回写缓存**。所以如果锁泄漏了，**这个热键的所有请求都会在 1 秒后放弃、直查库**——并发全压到 DB。而且 `sleep(50)` 是**阻塞 Tomcat 线程**的，最坏占 1 秒。

**对应代码**

- `utils/CacheClient.java` — `queryWithMutex`、`MUTEX_MAX_RETRY = 20`（`:35`）
- `resources/unlock.lua` — 解锁
- `utils/CacheClient.java` — `queryWithLogicalExpire`（**无调用方，有意保留**）

## 4. 缓存雪崩

**通用定义**

**大量 key 在同一时刻失效**（或缓存层整体宕机），导致请求全部涌向数据库。

**★ 和击穿的区别**：击穿是**一个**热 key；雪崩是**一大批** key。

**两种成因**：① **批量预热时设了相同的 TTL**（比如都设 30 分钟，那它们在 30 分钟后同时过期）；② **缓存服务宕机**。

**两种解法**：① **TTL 加随机抖动**；② **多级缓存 / 缓存高可用**。

**在研约通里的具体体现**

**只做了 TTL 抖动**：`30min + [0, 5min)`，而且**在调用点计算，不侵入 `CacheClient.set` 的通用语义**——这样 `CacheClient` 保持通用，抖动策略留在业务侧。

**★ 而 Redis 宕机没有任何兜底**：

- 设备详情查询会抛异常（连接失败）→ 500；
- **预约会失败**（`reservation.lua` 的 `EXISTS` 拿不到键）；
- **没有降级路径**（没有本地缓存、没有多级缓存）。

**★ 我要诚实说的一点**：**抖动的效果对当前数据量来说几乎为零**——项目只有 12 台设备，就算 12 个 key 同时过期也只是 12 次查库。**这个防护是「为将来准备」的，不是「解决当前问题」的。**

**★ 而 TTL 的三个作用，按重要性排序**（这一条比「防雪崩」更重要）：

1. **给不一致设一个收敛上限**（删缓存失败时，最坏错 TTL 那么久）；
2. **防内存无界增长**（尤其是空值缓存）；
3. 打散过期时刻防雪崩。

**对应代码**

- `utils/RedisConstants.java` — `CACHE_EQUIPMENT_TTL = 30L` / `CACHE_EQUIPMENT_TTL_JITTER = 5L`
- `service/impl/EquipmentServiceImpl.java` — 调用点算抖动

## 5. Lua 原子性

**通用定义**

Redis 用**单线程**处理命令，所以**单条命令是原子的**——但**多条命令之间可以被其他客户端的命令插入**。

`EVAL` 执行的 Lua 脚本在 Redis 里**作为一个整体执行，执行期间不处理其他任何客户端的命令**。所以**把多个操作写进一个 Lua 脚本，就等于自定义了一个原子操作**。

**★ 为什么不能用 `MULTI`/`EXEC` 替代**：事务是把命令**排队**然后一次性执行，**你没法在事务里根据中间结果做分支**（不能写 `if quota <= 0 then ...`）。而准入判定恰恰需要分支。

**在研约通里的具体体现**

**三处用了 Lua：**

| 脚本 | 用途 | 原子区间 |
|---|---|---|
| `reservation.lua` | **抢名额** | 「查时段 + 查名额 + 查重复 + 扣减 + 标记」五步 |
| `reservationRollback.lua` | **归还名额** | `SREM` → `EXISTS` → `INCR` |
| `unlock.lua` | **释放缓存锁** | 「比对归属 + 删除」 |

**★ 反过来说明「为什么必须原子」**——如果不用脚本，抢名额会是这样：

```
时刻  请求 A                      请求 B
 T1   SISMEMBER → false
 T2                              SISMEMBER → false
 T3   GET quota → 1
 T4                              GET quota → 1
 T5   DECR → 0
 T6                              DECR → -1        ← 超卖
```

**★ 而 `unlock.lua` 展示了另一类必要性**——不只是「检查和使用之间」，还有「比对和删除之间」：

```
T1  A: GET → 值是自己的 token ✓（判断通过）
T2  A 的锁正好到期，B 抢到锁
T3  A: DEL → ★ 删掉了 B 的锁
```

**脚本无慢操作**：`reservation.lua` 只有 8 个 Redis 调用，**全是 O(1)**，无循环——**所以它不会阻塞 Redis**。`lua-time-limit`（默认 5 秒）在这个脚本上永远不会触发。

**对应代码**

- `resources/reservation.lua`（27 行）
- `resources/reservationRollback.lua`（8 行）
- `resources/unlock.lua`（3 行）
- `utils/ReservationQuotaExecutor.java` / `utils/ReservationQuotaRollbackExecutor.java` — 加载与执行

## 6. Publisher Confirm

**通用定义**

**生产者到 broker** 的确认机制：生产者发出消息后，broker 回一个 **ACK**（已接收并负责）或 **NACK**（拒绝，比如磁盘满、队列满、内部错误）。

**它回答的问题是**：**「broker 收到我的消息了吗？」**

**★ 两种模式**（Spring AMQP 的 `publisher-confirm-type`）：

- `simple`：只启用普通 `ConfirmCallback`，**`CorrelationData` 的 future 不会被完成**；
- `correlated`：**每条消息的 `CorrelationData` 会被独立完成**，可以用 `getFuture().get(...)` 同步等结果。

**在研约通里的具体体现**

配置是 `publisher-confirm-type: correlated`，代码里**同步等结果**：

```java
CorrelationData correlationData = new CorrelationData(String.valueOf(reservationId));
rabbitTemplate.convertAndSend(..., correlationData);
CorrelationData.Confirm confirm = correlationData.getFuture().get(5, TimeUnit.SECONDS);
```

**★ 三个必须说清的点：**

1. **必须是 `correlated`**——配成 `simple` 的话 `getFuture()` 永远不会被完成，**代码会每次阻塞到 5 秒超时**，然后全部归为 `UNKNOWN`。**这是一个配置和代码强耦合的地方。**
2. **同步等 5 秒是这个系统最大的性能问题**——它占着 Tomcat 线程和数据库连接。**broker 慢的时候，10 个并发就能打满 Hikari 的默认 10 连接。**
3. **NACK 被归为 `DEFINITELY_NOT_DELIVERED`**（`failureReason = "CONFIRM_NACK"`），**当场归还名额**——因为 broker 明确拒绝了，消息一定没进队列。

**★ 另外有一个「只打日志」的回调**：`@PostConstruct` 里的 `setConfirmCallback` **只在 `!ack` 时打 error 日志，不驱动业务决策**。**真正的结果判定在 `publishReservationMessage` 里同步做的。回调是「事后审计」，future 是「同步决策」，两者都在。**

**对应代码**

- `config/RabbitMQConfig.java:92-98` — `setConfirmCallback`
- `service/impl/ReservationServiceImpl.java:246-265` — 生成 `CorrelationData`、等 future、判 NACK
- `src/main/resources/application.yaml` — `publisher-confirm-type: correlated`

## 7. Publisher Return

**通用定义**

**broker 内部的 Exchange 到 Queue** 的退回机制：消息到达 Exchange 后**路由不到任何队列**时，如果 `mandatory=true`，broker **把消息退回给生产者**并触发 `ReturnCallback`。

**它回答的问题是**：**「broker 把消息放进队列了吗？」**

**★ 和 confirm 的关系——这是最容易搞错的地方：**

| | Confirm | Return |
|---|---|---|
| 覆盖的失败 | 网络断开、broker 磁盘满、内部错误 | **路由键匹配不到任何队列** |
| 方向 | 生产者 ↔ broker | Exchange ↔ Queue（broker 内部） |
| 触发时机 | 每条消息都触发 | **只有路由失败时才触发** |

**★ 所以两个必须都开**：只开 confirm 的话，**路由键写错、没有任何队列绑定——broker 照样回 ACK（它确实收到了！），消息被静默丢弃**。

**在研约通里的具体体现**

配置 `publisher-returns: true`，代码里 `setMandatory(true)`，**三者缺一不可**：

```java
rabbitTemplate.setReturnCallback((message, replyCode, replyText, exchange, routingKey) ->
        log.error("预约消息路由失败：..."));
rabbitTemplate.setMandatory(true);
```

**★ 三个关键点：**

1. **`mandatory=true` 是必需的**——`mandatory=false`（默认）时 broker **直接丢弃**路由失败的消息，**`ReturnCallback` 永远不会触发，而且没有任何报错**。**这是一个非常常见的「配置看起来开了但从来没生效」的场景。**
2. **`getReturnedMessage()` 被用来判定 `DEFINITELY_NOT_DELIVERED`**（`failureReason = "CONFIRM_RETURN"`）——**当场归还名额**。
3. **⚠️ 这里依赖 broker 的一个行为保证**：对于会被退回的消息，**broker 先发 `basic.return`，再发 `basic.ack`**。所以等到 confirm future 完成时，`getReturnedMessage()` 已经被赋值了。**如果这个顺序不成立，`confirm.isAck()` 为 true 而 `returnedMessage` 还是 null，会被误判成 `ACKED`——而消息其实已经丢了。**

**对应代码**

- `config/RabbitMQConfig.java:99-102` — `setReturnCallback` + `setMandatory(true)`
- `service/impl/ReservationServiceImpl.java:260-262` — `getReturnedMessage()` 判定
- `src/main/resources/application.yaml` — `publisher-returns: true`

## 8. Manual ACK

**通用定义**

消费者确认模式的一种：**消息什么时候被确认，完全由应用代码决定**（`channel.basicAck` / `basicNack`），而不是由框架在方法返回时自动确认。

**★ 为什么需要它**：自动 ACK 模式下，**消息在监听器方法返回时就被确认**——即使方法内部抛了异常、或者事务回滚了。**这会导致「消息丢了但业务没做成」。**

**在研约通里的具体体现**

配置 `acknowledge-mode: manual`，而且**确认点被放在所有副作用之后**：

```java
case PERSISTED:
case DUPLICATE:
    markConfirmedSafely(messageDTO.getReservationId());   // ① 落库（已在 persist 里完成）
    channel.basicAck(deliveryTag, false);                 // ② 推进账本 → ③ 最后才 ACK
    break;
```

**★ 顺序是「落库 → 推账本 → ACK」，不是「落库 → ACK → 推账本」。**

**★ 三条必须一起看的配置：**

| 配置 | 作用 |
|---|---|
| `acknowledge-mode: manual` | 应用自己确认 |
| **`retry.enabled: false`** | **关掉自动重试**——手动 ACK 模式下 Spring 默认的 recoverer 不会真正 nack，**会把消费者卡死** |
| **`ConditionalRejectingErrorHandler` + `setRejectManual(true)`** | **反序列化失败发生在监听器方法之前**，那时应用还没拿到 `Channel`，**没机会自己 nack**；这个处理器让框架替你 reject |

**★ `basicNack(deliveryTag, multiple, requeue)` 三个参数：**

- `multiple = false`：只拒绝这一条；
- **`requeue = false`：进 DLQ。`true` 的话消息会重新入队、立刻又被同一个消费者拿到、又失败——无限循环把队列堵死。**

**★ 每条失败路径都显式确认了**（没有一条会「既不 ACK 也不 NACK」）：

| 分支 | 动作 |
|---|---|
| 成功 / 幂等重复 | `basicAck` |
| 账本已 `COMPENSATED` | **`basicAck`**（拒绝落库但确认消息——**这不是错误，是正确地拒绝了一个不该做的操作**） |
| 锁超时 / `QUOTA_CONFLICT` / 主键冲突 / 其他异常 | `basicNack(..., false)` |

**对应代码**

- `mq/ReservationMessageConsumer.java` — 全部确认逻辑
- `config/RabbitMQConfig.java:78-90` — `rabbitListenerContainerFactory` + `errorHandler`
- `src/main/resources/application.yaml` — `acknowledge-mode: manual` / `retry.enabled: false`

## 9. DLX

**通用定义**

**Dead Letter Exchange（死信交换机）**。队列可以配置 `x-dead-letter-exchange`，当消息在这个队列里变成「死信」时，**broker 自动把它转发到那个交换机**（通常还配 `x-dead-letter-routing-key` 指定新路由键）。

**★ 消息变成死信的三种情况：**

1. **被消费者 `basicNack(requeue=false)` 或 `basicReject(requeue=false)`**（最常用）；
2. **消息 TTL 过期**；
3. **队列达到最大长度被丢弃**。

**★ 关键优势**：**转发是 broker 自动做的，应用不需要自己往 DLQ 发消息。** 这是 RabbitMQ 相比 Kafka 的一个实打实的便利（Kafka 没有原生 DLX，得自己写转发主题）。

**在研约通里的具体体现**

**业务队列在声明时就绑定了 DLX**：

```java
QueueBuilder.durable(RESERVATION_CREATE_QUEUE)
        .withArgument("x-dead-letter-exchange", RESERVATION_DLX)
        .withArgument("x-dead-letter-routing-key", RESERVATION_CREATE_DLQ_ROUTING_KEY)
        .build();
```

所以应用只需要 `basicNack(deliveryTag, false, false)`，**死信转发全交给 broker**。

**★ 两个设计细节：**

1. **DLQ 自己不带 DLX 参数**——**这是有意的**。如果 DLQ 也有 DLX，一条反复失败的消息会在两个队列之间**无限弹跳**。所以 `ReservationDlqConsumer` 里的注释说：『**DLQ 没有后继死信交换机，拒绝后日志是消息永久丢弃前的最后痕迹，必须保留完整原文。**』
2. **两个交换机都是 `DirectExchange`**——这里只有一条业务路由，不需要 `Topic` 的通配能力。**选 `Direct` 是因为路由语义确实是「精确的一个目的地」。**

**对应代码**

## 10. DLQ

**通用定义**

**Dead Letter Queue（死信队列）**——接收从 DLX 转发过来的死信。

**★ 它解决的核心问题是可观测性**：**如果没有 DLQ，失败的消息会被静默丢弃或者无限重试**，运维完全不知道出过事。有了 DLQ，失败的消息**被持久化到一个可以被查看、被统计、被重放的地方**。

**在研约通里的具体体现**

`reservation.create.dlq` 这个队列被一个**独立的消费者**处理，而且用的是**另一套容器工厂**：

```java
// ReservationDlqConsumer
@RabbitListener(queues = RESERVATION_CREATE_DLQ,
                containerFactory = ReservationDlqListenerConfig.DLQ_CONTAINER_FACTORY)
public void onDeadLetter(Message message, Channel channel) throws IOException {
    byte[] body = message.getBody();          // ★ 原始字节，不走 Jackson
```

**★ 为什么 DLQ 用 `SimpleMessageConverter` + 原始 `Message`：**

类注释写明：『**使用原始 Message 消费死信，避免反序列化失败的消息再次经过 Jackson 并形成失败循环。**』

**这个理由非常硬**：**死信队列里最需要留存的消息，恰恰是那些反序列化失败的**。如果 DLQ 也用 Jackson，这条消息会在 DLQ 里**再次失败 → 再次被 reject → 但 DLQ 没有后继 DLX → 消息被丢弃，而台账里什么都没有**。

**★ 一个通用原则**：**「失败处理路径」本身必须比主路径更不容易失败。**

**★ 落台账失败时的处理也很讲究：**

```java
} catch (Exception e) {
    String payload = body == null ? null : new String(body, StandardCharsets.UTF_8);
    log.error("死信台账落库失败，消息将永久丢弃：payload={}", payload, e);
    channel.basicNack(deliveryTag, false, false);
    return;
}
```

**它在丢弃消息之前，把消息原文打进了错误日志**——因为 `basicNack` 之后这条消息**就真的永远消失了**，**日志是它存在过的唯一证据**。

**★ 台账表 `tb_reservation_dlq` 的字段**：`payload`（完整原文）、`failure_reason`（从 `x-death` 头取的）、`replay_count`、`status`（默认 `NEW`）。

**对应代码**

- `mq/ReservationDlqConsumer.java` — 完整 62 行
- `config/ReservationDlqListenerConfig.java` — `SimpleMessageConverter`
- `service/impl/ReservationDlqServiceImpl.java` — `recordDeadLetter` / `replay` / `discard`
- `src/main/resources/db/phase8_consistency.sql` — `tb_reservation_dlq` 表结构

## 11. 幂等

**通用定义**

**同一个操作执行一次和执行多次，对系统状态的影响相同。**

**★ 它是分布式系统的基本要求**，因为：网络超时导致的重试、消息中间件的至少一次投递（at-least-once）、用户重复点击、定时任务的重复执行——**这些都无法避免「同一个操作被执行多次」**。

**★ 实现幂等的三种常见手法：**

1. **唯一约束**（数据库层面拒绝重复）；
2. **状态机 + CAS**（只有特定状态才能迁移，重复迁移 `affectedRows == 0`）；
3. **幂等令牌**（操作本身返回「我是否真的改变了状态」）。

**在研约通里的具体体现**

**★ 三种手法全用了，而且粒度不同：**

| 层 | 手法 | 粒度 | 位置 |
|---|---|---|---|
| **消费幂等** | 同 id 同 user 同 batch → `DUPLICATE` | `(reservationId, userId, batchId)` | `ReservationPersistenceServiceImpl:29` |
| **业务去重** | 同 user 同 batch 已占用 → `DUPLICATE` | `(userId, batchId)` | `ReservationPersistenceServiceImpl:39` |
| **锁** | Redisson 用户锁 | `userId` | `ReservationMessageConsumer.persistWithLock` |
| **唯一索引** | `uk_user_batch_active` | `(userId, batchId, active_flag)` | `phase9_reservation_lifecycle.sql` |
| **账本迁移** | CAS `UPDATE ... WHERE status IN (非终态)` | `requestId` | `ReservationRequestServiceImpl.casStatus` |
| **名额归还** | `SREM` 返回值为 0 就不 `INCR` | **`(batchId, userId)`** | `reservationRollback.lua` |
| **取消标记** | CAS `WHERE quota_released = false` | `reservationId` | `ReservationServiceImpl.cancel` |

**★ 三个必须能讲清的细节：**

1. **消费幂等的判断被刻意收窄了。** 第一个判断**只判「同 id + 同 user + 同 batch」三元组，不判 `existing != null`**——因为判宽了的话，一条「主键撞了但归属对不上」的消息会被当成幂等重复而**静默 ACK**：**消息消失了，死信队列里什么都没有，运维完全不知道出过事**。所以它让其他所有冲突继续走到 `insert`，**由主键约束抛异常、进 DLQ 留痕**。
2. **`SREM` 的幂等粒度是 `userId` 不是 `reservationId`** ——**在「取消后重新预约」的场景下会失效**。真正的保护在上层：**只有 CAS 真正完成 `RESERVED → CANCELLED` 跃迁（`TRANSITIONED`）才允许调用归还**。
3. **有一个「幂等但有副作用」的设计**：`DUPLICATE` 和 `PERSISTED` 走同一个分支（都推 `CONFIRMED`、都 ACK）——**因为 `DUPLICATE` 的语义是「这条消息代表的预约已经在库里了」，从「请求成功了吗」的角度看，答案是「成功了」。**

**对应代码**

- `service/impl/ReservationPersistenceServiceImpl.java` — 两个幂等判断
- `resources/reservationRollback.lua` — `SREM` 幂等令牌
- `service/impl/ReservationRequestServiceImpl.java` — `casStatus` / `casStatusWithFailReason`
- `service/impl/ReservationServiceImpl.java:152-160` — **那段最长的注释（幂等粒度不匹配的完整推理）**
- `src/main/resources/db/phase9_reservation_lifecycle.sql` — 唯一索引

## 12. CAS

**通用定义**

**Compare-And-Swap**：一种乐观并发控制——「**如果当前值是我期望的，就改成新值；否则什么都不做**」。操作返回「是否成功」，调用方据此判断有没有被别人抢先。

**★ 数据库层面的实现**就是把判定条件写进 `UPDATE` 的 `WHERE` 里：

```sql
UPDATE t SET status = 'NEW' WHERE id = ? AND status = 'OLD'
```

**InnoDB 的行锁保证 `WHERE` 在锁内重新求值**，所以并发下第二个事务会看到第一个事务修改后的值，条件不成立，`affectedRows` 是 0。

**★ 为什么不能用「先查后写」**：那是 `check-then-act`（TOCTOU），**查询和更新之间永远有窗口**。

**★ CAS 的返回值就是判定结果**——不需要再查一次库去确认。

**在研约通里的具体体现**

**16 处 `LambdaUpdateWrapper`，分成 6 类：**

| 类别 | 典型条件 | 防什么 |
|---|---|---|
| 批次状态迁移 | `eq(status, PUBLISHED)` | 并发管理操作、重复操作 |
| 账本状态迁移 | `in(status, 非终态全体)` | 消费与对账并发推进 |
| 名额扣减 | `gt(remainingQuota, 0)` | **超卖** |
| 名额回补 | `lt(remainingQuota, totalQuota)` | 回补超上限 |
| 预约状态迁移 + 权限 | `eq(status, RESERVED).eq(userId, ?)` | 重复取消、**越权** |
| 幂等标记 | `eq(quotaReleased, false)` | 重复归还名额 |

**★ 四个必须能讲清的点：**

1. **`updateById` 的反例**：它是读-改-写三步，两个线程可以都读到 `remaining=1`、都判断大于 0、都写 0——**两个都成功但只扣了 1**。而 `SET x = x - 1 ... WHERE x > 0` 让**判定和使用合并成一次原子操作**；
2. **权限判定下推到 `WHERE user_id = ?`**——**越权请求的 `affectedRows` 天然是 0**，**不存在「判断通过但执行的是别人的数据」的窗口**；
3. **账本 CAS 的期望值是一个集合（`IN`）而不是单个值（`EQ`）**——**允许从任意非终态一步跳到目标态**，解掉了「消息消费比账本更新更快」的顺序耦合；
4. **有一个必须存在的守卫**：`if (expectedStatuses == null || expectedStatuses.length == 0) throw ...`——**没有它，空数组会生成 `IN ()`**，条件可能被静默忽略，**CAS 退化成无条件更新**。**这个守卫有专门的测试钉住**（`ReservationRequestStateTest.shouldRejectEmptyExpectedStatuses`）。

**对应代码**

- `service/impl/ReservationPersistenceServiceImpl.java:49-56` — 名额扣减
- `service/impl/ReservationRequestServiceImpl.java:39-62` — 账本 CAS + 守卫
- `service/impl/ReservationLifecycleServiceImpl.java:45-66` — 取消/回补

## 13. TOCTOU

**通用定义**

**Time-Of-Check to Time-Of-Use**：**检查的时刻和使用的时刻之间存在间隙**，在这个间隙里状态可能被改变，**导致检查的结论在使用的时刻已经不成立**。

**★ 这是并发 bug 最常见的一种形态**，也是「先查后写」「先判断再操作」这类代码的固有缺陷。

**★ 一个重要的认知**：**加锁能解决 TOCTOU，但加锁不是唯一解法。** 把「检查」和「使用」合并成一个原子操作（Lua 脚本 / 条件 UPDATE / CAS）**往往更轻、更可靠**。

**在研约通里的具体体现**

**★ 四个 TOCTOU 场景，用了四种不同的解法：**

| 场景 | 检查与使用之间的间隙 | 解法 |
|---|---|---|
| **抢名额** | 「查名额」和「扣名额」之间 | **Lua 脚本**（整体原子） |
| **扣数据库名额** | 「判断有余额」和「减一」之间 | **条件 UPDATE**（`WHERE remaining_quota > 0`） |
| **释放缓存锁** | 「比对归属」和「删除」之间 | **Lua 脚本** |
| **消息幂等** | 「查有没有」和「插入」之间 | **Redisson 用户锁 + 唯一索引**（两层） |
| **消费 vs 对账** | 「查账本不是 COMPENSATED」和「落库」之间 | ⚠️ **只有窄化窗口，没有完全消除** |

**★ 而项目里还有两处「明知的 TOCTOU」，它们是被有意接受的：**

1. **`BookingState` 是读时算出来的**——算完到用户点击之间可能已经过了几秒。**所以 `submit` 必须自己再校验一次**（它确实做了：`now.isBefore(bookingStartTime)` → 抛「预约尚未开始」）。**通用原则：永远不用「读时算出来的状态」做写操作的判据。**
2. **`submit` 里那个 `now` 是在发 Redis 命令之前算的**，然后原样传给 Lua。所以 **Lua 判断的是「请求开始时的时刻」，不是「Lua 执行的时刻」**——中间的差是「前置检查 + 写账本 + 发 Redis」的耗时。**这个偏差是刻意的**：用同一个 `now` 意味着「这次请求的准入判定以请求开始时刻为准」，语义更一致（否则会出现「Java 说没到点、Lua 说到了」的诡异情况）。**而且 `now` 还要用来算 users 集合的 TTL，所以它必须早于 Redis 调用。**

**对应代码**

- `resources/reservation.lua` — 消除抢名额的 TOCTOU
- `service/impl/ReservationPersistenceServiceImpl.java:49-56` — 消除扣名额的 TOCTOU
- `resources/unlock.lua` — 消除解锁的 TOCTOU
- `service/impl/ReservationServiceImpl.java:60-140` — Java 侧的二次校验（防 `BookingState` 的 TOCTOU）

## 14. 最终一致性

**通用定义**

**系统不保证任意时刻各副本/各存储的数据都相同，但保证在没有新的更新发生的前提下，经过有限时间后收敛到一致状态。**

**★ 它是一个「有界的承诺」**——**不是「永远不一致」，而是「在有限时间内收敛」**。所以描述它的时候**必须说明收敛时间上界和收敛机制**，否则这个承诺就是空的。

**★ 和强一致的区别**：强一致要求「读到的永远是最新写入的」；最终一致允许中间态存在，**代价是用户可能短暂读到旧数据**。

**在研约通里的具体体现**

**★ 两个存储（Redis 和 MySQL）的最终一致，靠三层机制：**

| 层 | 机制 | 收敛时间 |
|---|---|---|
| **同步补偿** | `submit` 里 Lua 拒绝 / 投递确定失败 → 当场归还名额 + `COMPENSATED` | **立即** |
| **异步消费** | 消费者落库（正常路径） | **秒级** |
| **定时对账** | 扫非终态请求 → 裁决 → 补偿 | **最坏 15 分钟** |

**★ 15 分钟这个数字怎么来的**：`reconcile-threshold-ms = 600000`（**10 分钟**阈值）+ `reconcile-interval-ms = 300000`（**5 分钟**扫描间隔）**的最坏叠加**。**它不是设计出来的精确值，而是两个参数的最坏组合。**

**★ 而设计里最关键的一条是——「不知道」必须被显式建模：**

1. **投递结果分三类，`UNKNOWN` 单独一类**——超时既不能算成功也不能算失败；
2. **`UNKNOWN` 是非终态**——**如果它是终态，超时的请求就永远不会被对账扫到**；
3. **裁决的判据是「MySQL 里有没有那行数据」**——**查最终事实，而不是查过程信号**（confirm 只告诉你 broker 收到了，不告诉你消费者处理了）。

**★ 一句话总结**：**当无法确定时，先记录「不确定」（`UNKNOWN`），然后用一个周期性的、查询最终事实的扫描来消除不确定性。**

## 15. 补偿

**通用定义**

**当一个操作已经产生的副作用无法通过「回滚」撤销时，执行另一个操作去抵消它。** 补偿操作通常**不要求与正向操作原子**，但**必须幂等**（因为补偿本身也可能失败并被重试）。

**★ 补偿 vs 事务回滚**：

| | 事务回滚 | 补偿 |
|---|---|---|
| 适用 | **同一个事务内**的数据库操作 | **跨系统**（Redis/MQ/远程服务）的副作用 |
| 保证 | 原子（要么全做要么全不做） | **最终一致**（可能失败、需要重试） |
| 要求 | 无 | **补偿操作必须幂等** |

**★ 所以「用了 MQ 就一定需要补偿」——因为 Redis 扣减、消息投递这些动作无法参与数据库事务。**

**在研约通里的具体体现**

**★ 三类补偿，各有触发时机：**

| 补偿 | 触发时机 | 动作 |
|---|---|---|
| **抢名额被拒** | `submit` 里 Lua 返回非 0 | **当场** CAS 账本 → `COMPENSATED`（**注意：Redis 没被扣，所以不需要归还**） |
| **投递确定失败** | `submit` 里 `DEFINITELY_NOT_DELIVERED` | **当场** `rollback` 归还名额 + 账本 → `COMPENSATED` |
| **投递不确定** | `UNKNOWN` | **不补偿**——交给对账 |
| **对账裁决失败** | 10 分钟后无预约行 | `rollback` + 账本 → `COMPENSATED` |
| **取消归还失败** | `cancel` 里 `rollback` 抛异常 | **不当场重试**——留 `quota_released = false`，由 `releasePendingQuotas` 补偿 |
| **消费失败** | 锁超时 / 名额冲突 / 主键冲突 | `basicNack` 进 DLQ + 写 `fail_reason`，**同时留给对账兜底** |

**★★ 而整个项目里最重要的一条补偿不变式是：**

> **先做那个「不可逆的、幂等的副作用」，再记录它已经发生。**

**代码里出现了三次：**

```java
// ① 对账
// 必须先补偿再推进终态：补偿失败时保留非终态，下一轮才能继续重试。
rollbackExecutor.rollback(request.getBatchId(), request.getUserId());
boolean updated = requestService.casStatusWithFailReason(requestId, COMPENSATED, ...);

// ② 取消后的名额归还
int rollbackCode = rollbackExecutor.rollback(...);
reservationMapper.update(null, ... .eq(getQuotaReleased, false).set(getQuotaReleased, true));

// ③ releasePendingQuotas
rollbackExecutor.rollback(...);
int updated = reservationMapper.update(null, ... .eq(getQuotaReleased, false).set(getQuotaReleased, true));
```

**★ 为什么这个顺序是必需的**：**如果先改状态再补偿，补偿失败时那条记录已经是终态了——对账永远不会再扫到它，名额永久泄漏**（「记了但没做」是无法恢复的）。反过来，补偿失败时状态还留着非终态，下一轮会继续重试；**而且因为补偿脚本本身幂等，重复执行是安全的。**

**★ 这个模式的前提是「副作用必须幂等」**——**如果没有幂等，就不敢「先做后记」**（重复执行会造成二次归还）。

- `service/impl/ReservationReconcileServiceImpl.java:124-125` — **注释 + 语句顺序**

## 16. 对账

**通用定义**

**定时比对两个数据源（或「预期状态」与「实际状态」），发现差异并修复。**

**★ 它是唯一能处理「事件从未发生」这类故障的机制。**

**★ 这一点是这个术语最重要的认知**：publish confirm、手动 ACK、死信队列**都是事件驱动的**——它们只能覆盖「**事件发生了但结果是失败**」。而「**进程在发出消息之前就被 kill 了**」这种故障，**没有任何回调会被触发**。**「事件根本没发生」只能靠主动的、周期性的扫描去发现。**

**★ 所以对账任务不是可选的**——**光有 MQ 的可靠性机制是不够的。**

**在研约通里的具体体现**

**★ 三个任务，每 5 分钟一轮：**

| 任务 | 扫什么 | 做什么 |
|---|---|---|
| **`reconcile`** | `tb_reservation_request`：状态非终态 且 `update_time < now - 10min` | 有预约行 → `CONFIRMED`；无 → **`rollback` + `COMPENSATED`** |
| **`releasePendingQuotas`** | `tb_reservation`：`status='CANCELLED' AND quota_released=0` | `rollback` + CAS 置 `quota_released=true` |
| **`markNoShows`** | `tb_reservation`：`RESERVED` 且批次 `end_time < now` 且批次非 `CANCELLED` | 置 `NO_SHOW`（**不归还名额**） |

**★ 四个设计要点：**

1. **对账的判据是「最终事实」**——`reservationMapper.selectById(request.getRequestId())`。**这比投递过程信号可靠得多。** 而这依赖于 **`requestId` 和 `reservationId` 是同一个值**（Q43）；
2. **退避不用计数器**（表里根本没有这一列）——**推进 `update_time` 让记录退出陈旧窗口**。**而这里有一个 MySQL 的坑**：`ON UPDATE CURRENT_TIMESTAMP` **在写入的值和当前值相同时不触发**，所以重复写同一个 `fail_reason` 时必须**显式写 `update_time`**，否则持续失败的行会永远排在队首，**耗尽 `limit` 配额让自愈停摆**；
3. **正确性不依赖分布式锁**——锁只减少多实例重复工作。真正的保证是 **CAS + 幂等 Lua + 条件 update**；
4. **`limit` 是硬上限**（默认 200），**按 `update_time` 升序**——**保证「最老的优先」和「单轮开销有界」**。

**★ 而它的边界也很明确**：**没有指标、没有告警、没有心跳**。`scanned == limit`（积压）和 `failed > 0` 都只有日志。**这是这个项目最该补的一块。**

**对应代码**

- `service/impl/ReservationReconcileServiceImpl.java` — 完整 206 行
- `service/impl/ReservationRequestServiceImpl.java` — `listStale` / `recordFailReason`
- `mapper/ReservationMapper.xml` — `selectPendingQuotaReleases` / `markNoShows`

## 17. Redisson

**通用定义**

**基于 Redis 的 Java 分布式对象/服务框架**（不只是分布式锁）。它的 `RLock` 相比手写 `SETNX` 锁提供了三个额外能力：

1. **看门狗（watchdog）自动续期**——后台线程在锁快到期时自动延长，避免业务没执行完锁就过期；
2. **可重入**——同一线程可以重复加锁；
3. **成熟的解锁逻辑**（归属校验 + Lua 原子删除）。

**★ 看门狗的启用规则**（最容易搞错的地方）：

| 调用方式 | `leaseTime` | 看门狗 |
|---|---|---|
| `tryLock(waitTime, leaseTime, unit)` | 显式指定 | ❌ **不启用** |
| `tryLock(waitTime, unit)` | 未指定（默认 -1） | ✅ **启用**（每 `lockWatchdogTimeout/3` 续期，默认 10 秒） |

**在研约通里的具体体现**

**★ 项目里有两种锁，实现完全不同——这是最容易混淆的一点：**

| | 缓存重建锁 | 预约/对账锁 |
|---|---|---|
| **实现** | **手写**：`SETNX` + UUID 令牌 + `unlock.lua` | **Redisson `RLock`** |
| **Key** | `lock:cache:{id}` | `lock:reservation:{userId}`、`lock:reservation:reconcile` |
| **失败代价** | **多查几次库**（性能问题） | **数据错乱**（正确性问题） |
| **为什么这么选** | 简单够用，**且能让读者看见 `SETNX` + Lua 的原理** | 需要看门狗、可重入、成熟 API |

**★ 而 Redisson 那两个锁的租约策略是相反的：**

```java
// ReservationMessageConsumer：★ 显式 leaseTime=10 秒 → 没有看门狗
lock.tryLock(2, 10, TimeUnit.SECONDS);

// ReservationReconcileServiceImpl：★ 两参重载 → 有看门狗
lock.tryLock(0, TimeUnit.MILLISECONDS);
```

- **消费锁**：租约固定 10 秒，**看门狗不介入**——因为消费逻辑执行时间可控，**给它一个硬上限可以防止线程卡死时锁永久不释放**；
- **对账锁**：**启用看门狗，每 10 秒续期**——**而这带来一个风险**：如果 `reconcile` 卡在一次没有超时设置的 DB 调用上，**看门狗会无限续期，锁永不释放 → 所有实例的对账静默停摆，而且没有任何告警**。

**★ 而项目对锁的定位写在了方法注释里**：

> **「定时调度薄壳：分布式锁仅减少多实例重复工作，正确性仍由状态 CAS 与幂等补偿保证。」**

**锁可以换性能，不能换正确性**——**用锁换性能是安全的（错了只是慢），用锁换正确性是危险的（错了就是数据错）。**

**对应代码**

- `config/RedissonConfig.java` — `RedissonClient` 配置
- `mq/ReservationMessageConsumer.java:127-148` — `persistWithLock`，显式租约
- `service/impl/ReservationReconcileServiceImpl.java:54-93` — **方法注释 + `tryLock(0, MILLISECONDS)`**
- `utils/CacheClient.java` — 手写锁（对照）
- `resources/unlock.lua` — 手写锁的解锁

## 18. Unique Index

**通用定义**

**唯一索引**：保证索引列（组合）上的值不重复。**插入或更新违反唯一性时，数据库抛异常。**

**★ 它是并发控制里最可靠的一层**——**因为它不依赖应用代码的正确性、不依赖任何易失存储、不可能被「忘记检查」**。所以它常被用作「最后一道防线」。

**★ 而 `NULL` 在唯一索引里不参与比较**（SQL 标准：`NULL != NULL`）——**所以一个组合里包含 `NULL` 的行可以任意多条**。这个特性常被用来模拟「部分唯一索引」。

**在研约通里的具体体现**

**★ `uk_user_batch_active` 是一个用生成列模拟的「部分唯一索引」：**

**需求**：一个用户在一个批次里**同时只能有一条有效预约**，但**可以取消后重新预约**。所以：

- ❌ 简单唯一索引 `(user_id, batch_id)` **不行**——取消之后就不能再预约了；
- ✅ 需要的是**只在 `status != 'CANCELLED'` 的行上唯一**。

**PostgreSQL 直接支持** `CREATE UNIQUE INDEX ... WHERE status <> 'CANCELLED'`，**MySQL 不支持部分索引**。

**解法**：

```sql
ALTER TABLE tb_reservation
  ADD COLUMN active_flag TINYINT
    GENERATED ALWAYS AS (CASE WHEN status = 'CANCELLED' THEN NULL ELSE 1 END) STORED,
  ADD UNIQUE INDEX uk_user_batch_active (user_id, batch_id, active_flag);
```

| 行 | `status` | `active_flag` | 索引三元组 |
|---|---|---|---|
| 第 1 条预约 | `RESERVED` | **1** | `(U, B, 1)` |
| 第 2 条预约 | `RESERVED` | **1** | `(U, B, 1)` ← **冲突，被拒** |
| 第 1 条已取消 | `CANCELLED` | **NULL** | `(U, B, NULL)` |
| 第 2 条 | `RESERVED` | **1** | `(U, B, 1)` ← **不冲突** |

**★ 三个必须说清的点：**

1. **`GENERATED ALWAYS AS ... STORED` 是生成列，不能被 `SET`**（MySQL 会报 `ERROR 3105`）。**所以全仓 Java 代码对 `active_flag` 的引用数是 0**——**它不是业务字段，是索引的载体**；
2. **它占用槽位的状态是 `RESERVED` / `COMPLETED` / `NO_SHOW`**（只有 `CANCELLED` 是 `NULL`）。**所以一个爽约过的用户在这个批次里也占着槽位**——不过批次已经结束了，没有实际影响；
3. **⚠️ README §9③ 描述的机制不存在。** README 说 `phase8`/`phase9` 用 `UPDATE ... SET active_flag = 0 WHERE id = ? AND active_flag = 1` 检测并发修改、推导 `QUOTA_CONFLICT`——**这是不可能的**（生成列不能 `SET`）。**而 `QUOTA_CONFLICT` 的真实来源是 `ReservationPersistenceServiceImpl:55` 的 `remaining_quota > 0` 条件更新。** 这是最重要的一处文档与源码不一致。

**★ 它和主键约束的分工**（在 `persist` 里）：**唯一索引冲突会抛 `DuplicateKeyException`，被消费端捕获后 `basicNack` 进 DLQ 留痕。** 代码里的注释特别说明：**不能在这里提前返回 `DUPLICATE`——那条未落库的消息会被静默 ACK，DLQ 上不留任何痕迹。**

**对应代码**

- `src/main/resources/db/phase9_reservation_lifecycle.sql` — `active_flag` 生成列 + 唯一索引
- `service/impl/ReservationPersistenceServiceImpl.java:58-60` — `insert`
- `mq/ReservationMessageConsumer.java:80-85` — `catch (DuplicateKeyException)` → `basicNack`
- `enums/ReservationStatus.java` — `occupyingStatuses()`

## 19. 事务边界

**通用定义**

**一个事务从哪里开始、到哪里结束**——也就是「哪些操作被绑定成一个原子单元」。

**★ 事务边界的划分是设计决策，而不是「方法上要不要加 `@Transactional`」的编码问题。** 核心原则是：

> **事务应该尽可能短，只包住真正需要原子的操作集合——而「原子」的定义是「这些操作要么全做、要么全不做」的语义需求，不是「它们在业务上相关」。**

**★ 而跨越外部系统（Redis / MQ / HTTP）的操作不应该放进数据库事务**——因为它们**无法参与事务回滚**，放进去只会**制造「数据库回滚了但外部系统的副作用还在」的不一致**，同时**拉长事务、占用连接池**。

**在研约通里的具体体现**

**★ 全项目只有 3 处 `@Transactional`：**

| 位置 | 方法 | 事务里的操作 |
|---|---|---|
| `ReservationPersistenceServiceImpl:27` | `persist` | **扣批次名额 + 插入预约行** |
| `ReservationLifecycleServiceImpl:30` | `cancel` | 改预约状态 + 回补批次名额 |
| `ReservationLifecycleServiceImpl:77` | `complete` | 改预约状态（含一次查询） |

**★ 它们的共同特征（判据）：**

1. **至少两步数据库写**（`persist` 的「扣名额 + 插行」如果不同事务，**扣了名额但插行失败就会泄漏名额**）；
2. **不包含任何网络调用**——没有 Redis、没有 MQ、没有 HTTP；
3. **执行时间可控**（毫秒级）。

**★ 而「看起来该加事务但没加」的地方，每一个都有明确理由：**

| 方法 | 里面有什么 | 为什么不加 |
|---|---|---|
| **`ReservationServiceImpl.submit`** | 写账本 + **Redis Lua** + **阻塞等 confirm 最长 5 秒** | ① 事务跨网络等待，**Hikari 默认只有 10 连接**；② **事务能回滚的只有那条账本 INSERT，Redis 扣减不在事务里** → **回滚反而制造「Redis 已扣、账本没了」的名额泄漏**；③ 账本在提交前对其他连接不可见，**消费者可能查不到账本行** |
| **`ReservationServiceImpl.cancel`** | 调事务方法 + **Redis rollback** | Redis 无法参与数据库事务；且**「先提交事实、再做补偿」要求归还必须在事务外**（否则回滚会抹掉「预约已取消」这个事实，`releasePendingQuotas` 就永远扫不到） |
| **`ReservationReconcileServiceImpl.reconcile`** | 循环 200 条，每条自己的 CAS | **长事务**——200 条的事务会持有大量行锁、产生大 undo log、失败后全部回滚；**而这里需要的是「每条独立成败」**（`try/catch` 在循环内部） |
| **`ReservationDlqServiceImpl.replay`** | CAS 递增重试次数 + **MQ 投递** | 同 submit——MQ 在事务里 |

**★★ 所以判据可以总结成三条：**

1. **只做数据库操作** → 可以加事务；
2. **有外部调用（Redis / MQ / HTTP）** → **不要加事务**；
3. **要处理一批独立记录、每条独立成败** → **不要加事务**（应该每条自己的小事务，或者靠 CAS 保证单条原子性）。

**★ 还有一个值得注意的结构**：`cancel`（`ReservationLifecycleServiceImpl`）**有事务**，而它的调用方 `ReservationServiceImpl.cancel` **没有**。**这是对的，而且是有意的**——**事务方法作为一个可复用的一致性单元，被一个更大的、包含外部调用的流程去调用。** 事务**只覆盖「`RESERVED → CANCELLED` + 名额 +1」这个数据库内的一致性单元**；Redis 归还、日志、异常处理都在事务外。

- `service/impl/ReservationServiceImpl.java:60-140`（**没加事务的那个**）/ `140-176`

| # | 术语 | 一句话 |
|---|---|---|
| 1 | Cache Aside | 写库后**删除**缓存——删除不携带数据，永远安全 |
| 2 | 缓存穿透 | 查不存在的数据 → **空值缓存**（TTL 只有 2 分钟） |
| 3 | 缓存击穿 | 热 key 失效 → **互斥锁 + 双重检查**（20 次重试后直查库且**不回写**） |
| 4 | 缓存雪崩 | 批量失效 → **TTL 抖动**；**Redis 宕机没有兜底** |
| 5 | Lua 原子性 | 多条命令之间有间隙 → **脚本执行期间不处理其他命令** |

| 8 | Manual ACK | 确认点放在**所有副作用之后**；同时必须**关自动重试** + `setRejectManual(true)` |
| 9 | DLX | 队列声明时绑定，**broker 自动转发**；**DLQ 自己不带 DLX**（防止无限弹跳） |
| 10 | DLQ | 用**原始字节 + `SimpleMessageConverter`**，因为最需要留存的是**反序列化失败**的消息 |
| 11 | 幂等 | 三种手法全用了；**`SREM` 的粒度是 `userId` 不是 `reservationId`** |
| 12 | CAS | **把判定条件写进 `UPDATE` 的 `WHERE`**；16 处，六类 |
| 13 | TOCTOU | 检查和使用之间的间隙；**四种解法，一处未完全消除**（消费 vs 对账） |
| 14 | 最终一致性 | **最坏 15 分钟**（10 分钟阈值 + 5 分钟间隔）；**「不知道」必须被建模成 `UNKNOWN`** |
| 15 | 补偿 | **先做不可逆的、幂等的副作用，再记录它已经发生** |
| 16 | 对账 | **唯一能处理「事件从未发生」的机制**；退避不用计数器，靠推进 `update_time` |
| 17 | Redisson | **两个锁租约策略相反**：消费锁显式租约（无看门狗），对账锁两参重载（有看门狗） |
